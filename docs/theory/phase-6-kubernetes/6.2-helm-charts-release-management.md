# 6.2 Helm Charts & Release Management

## Why Helm Exists

A production Kubernetes deployment for a single microservice involves many resources: Deployment, Service, ConfigMap, ServiceAccount, HorizontalPodAutoscaler, PodDisruptionBudget, NetworkPolicy, and possibly more. These resources are related and must be deployed together, upgraded together, and rolled back together.

Without Helm, teams manage these as raw YAML files. The problems surface quickly:
- Different values for staging vs production require either duplicated files or manual editing
- Rolling back a failed deployment means manually reverting every affected resource
- There is no history of what changed between deployments
- Installing a new service in a new environment requires copying and editing dozens of YAML files

Helm is a package manager for Kubernetes. It packages related Kubernetes resources into a **chart**, manages configuration via **values files**, and tracks every deployment as a **release**. Install, upgrade, rollback, and diff are first-class operations.

## Helm Chart Structure

A Helm chart is a directory with a defined structure:

```
pravah-execution-service/      ← chart name
├── Chart.yaml                 ← chart metadata (name, version, dependencies)
├── values.yaml                ← default values for all environments
├── values-staging.yaml        ← staging-specific overrides
├── values-production.yaml     ← production-specific overrides
├── templates/
│   ├── deployment.yaml        ← Deployment template
│   ├── service.yaml           ← Service template
│   ├── configmap.yaml         ← ConfigMap template
│   ├── serviceaccount.yaml    ← ServiceAccount template
│   ├── hpa.yaml               ← HorizontalPodAutoscaler template
│   ├── pdb.yaml               ← PodDisruptionBudget template
│   ├── networkpolicy.yaml     ← NetworkPolicy template
│   ├── _helpers.tpl           ← named templates and helper functions
│   └── NOTES.txt              ← post-install notes (displayed to user)
└── charts/                    ← bundled dependency charts (subcharts)
```

### Chart.yaml

```yaml
apiVersion: v2
name: execution-service
description: "Pravah job execution service — dispatches jobs to runners"
type: application
version: 0.5.2           # chart version (semver) — incremented when templates change
appVersion: "1.4.2"      # application image version

# Dependencies: charts this chart depends on
dependencies:
  - name: common
    version: "1.2.0"
    repository: "https://charts.pravah.io/internal"
    # common chart: shared helper templates for all Pravah services
```

Two version numbers matter: `version` is the chart's own version (change when templates change), `appVersion` is the application image tag (change when the application code changes). They are independent — a template bug fix increments `version` without changing `appVersion`.

### Deployment Template

```yaml
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "execution-service.fullname" . }}
  namespace: {{ .Release.Namespace }}
  labels:
    {{- include "execution-service.labels" . | nindent 4 }}
  annotations:
    helm.sh/chart: {{ .Chart.Name }}-{{ .Chart.Version }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicas }}
  {{- end }}

  selector:
    matchLabels:
      {{- include "execution-service.selectorLabels" . | nindent 6 }}

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

  template:
    metadata:
      labels:
        {{- include "execution-service.selectorLabels" . | nindent 8 }}
        version: {{ .Values.image.tag | quote }}
      annotations:
        # Force pod restart when ConfigMap changes (checksum in annotation)
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
        prometheus.io/scrape: "true"
        prometheus.io/port: {{ .Values.service.managementPort | quote }}
        prometheus.io/path: "/actuator/prometheus"

    spec:
      serviceAccountName: {{ include "execution-service.serviceAccountName" . }}
      terminationGracePeriodSeconds: 60

      containers:
        - name: execution-service
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}

          ports:
            - name: http
              containerPort: 8080
            - name: management
              containerPort: {{ .Values.service.managementPort }}

          env:
            - name: SPRING_PROFILES_ACTIVE
              value: "production,kubernetes"
            - name: LOGGING_LEVEL_ROOT
              value: {{ .Values.logging.level }}
            - name: KAFKA_BOOTSTRAP_SERVERS
              value: {{ .Values.kafka.bootstrapServers }}
            - name: OTEL_TRACES_SAMPLER_ARG
              value: {{ .Values.tracing.samplingRate | quote }}

          resources:
            {{- toYaml .Values.resources | nindent 12 }}

          {{- include "execution-service.probes" . | nindent 10 }}

          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 15"]

          securityContext:
            runAsNonRoot: true
            runAsUser: 1000
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]

          volumeMounts:
            - name: vault-secrets
              mountPath: /vault/secrets
              readOnly: true
            - name: tmp
              mountPath: /tmp

      {{- include "execution-service.vaultAgentSidecar" . | nindent 6 }}

      volumes:
        - name: vault-secrets
          emptyDir:
            medium: Memory
        - name: tmp
          emptyDir: {}

      {{- include "execution-service.topologySpread" . | nindent 6 }}
```

### _helpers.tpl — Named Templates (DRY)

Named templates allow sharing common patterns across multiple template files:

```
{{/*
Expand the name of the chart.
*/}}
{{- define "execution-service.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

{{/*
Common labels — applied to all resources
*/}}
{{- define "execution-service.labels" -}}
helm.sh/chart: {{ include "execution-service.chart" . }}
app.kubernetes.io/name: {{ include "execution-service.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Values.image.tag | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
team: platform
{{- end }}

{{/*
Topology spread constraints — shared across all Pravah services
*/}}
{{- define "execution-service.topologySpread" -}}
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        {{- include "execution-service.selectorLabels" . | nindent 8 }}
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        {{- include "execution-service.selectorLabels" . | nindent 8 }}
{{- end }}
```

### HPA Template (Conditional)

```yaml
# templates/hpa.yaml
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ include "execution-service.fullname" . }}
  namespace: {{ .Release.Namespace }}
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ include "execution-service.fullname" . }}
  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}
{{- end }}
```

When `autoscaling.enabled: false`, the HPA template renders to nothing — the file is not created. This conditional pattern enables/disables features cleanly per environment.

## The Release Lifecycle

### Installing a Chart

```bash
# Install execution-service in the pravah namespace with production values
helm install execution-service ./charts/execution-service \
  --namespace pravah \
  --create-namespace \
  --values ./charts/execution-service/values-production.yaml \
  --set image.tag=1.4.2 \
  --wait \           # block until all resources are ready
  --timeout 5m       # fail if not ready within 5 minutes

# After install, Helm records a "release" with:
# - Release name: execution-service
# - Namespace: pravah
# - Chart version: 0.5.2
# - Values used (merged)
# - All Kubernetes resources created
```

### Upgrading (Deploying a New Version)

```bash
# Deploy a new application version
helm upgrade execution-service ./charts/execution-service \
  --namespace pravah \
  --values ./charts/execution-service/values-production.yaml \
  --set image.tag=1.4.3 \     # new version
  --wait \
  --timeout 5m

# Helm computes the diff, applies only changed resources
# If the Deployment spec changed → rolling update begins
# Helm records release revision 2
```

### Rolling Back a Failed Deployment

```bash
# List release history
helm history execution-service --namespace pravah
# REVISION  UPDATED           STATUS    CHART                         DESCRIPTION
# 1         2024-01-10 09:00  superseded execution-service-0.5.1      Install complete
# 2         2024-01-15 14:30  deployed   execution-service-0.5.2      Upgrade complete
# 3         2024-01-15 15:00  failed     execution-service-0.5.3      Upgrade failed

# Roll back to revision 2 (last good deployment)
helm rollback execution-service 2 --namespace pravah --wait

# Or roll back to the immediately previous revision
helm rollback execution-service --namespace pravah
```

Rollback reverts all Kubernetes resources to their state at revision 2: the Deployment spec, ConfigMaps, Services, everything managed by Helm. This is why managing resources outside of Helm ("drift") is dangerous — Helm does not know about manually applied resources and cannot roll them back.

### Diff Before Applying

```bash
# Preview what would change before upgrading (using helm-diff plugin)
helm diff upgrade execution-service ./charts/execution-service \
  --namespace pravah \
  --values ./charts/execution-service/values-production.yaml \
  --set image.tag=1.4.3

# Output shows +/- diffs for each changed resource
# deployment.apps/execution-service:
#   spec.template.spec.containers[0].image:
#     - pravah/execution-service:1.4.2
#     + pravah/execution-service:1.4.3
```

The `helm diff` plugin is essential for production deployments. Every change is reviewed before it is applied. Unexpected diffs (changes you didn't intend) surface before they reach production.

## Pravah's Chart Repository Structure

Pravah maintains a monorepo of Helm charts:

```
charts/
├── common/                    ← shared library chart (no direct install)
│   └── templates/
│       ├── _labels.tpl        ← common labels
│       ├── _probes.tpl        ← standardized probe definitions
│       ├── _topologyspread.tpl
│       └── _vault-sidecar.tpl
│
├── api-gateway/               ← one chart per service
│   ├── Chart.yaml
│   ├── values.yaml
│   ├── values-staging.yaml
│   ├── values-production.yaml
│   └── templates/
│
├── execution-service/
│   ├── Chart.yaml
│   │   dependencies:          ← depends on common library chart
│   │     - name: common
│   │       version: "1.2.0"
│   └── templates/
│
├── pipeline-service/
├── scheduler-service/
├── runner-service/
└── pravah-platform/           ← umbrella chart (installs all services together)
    ├── Chart.yaml
    │   dependencies:
    │     - name: api-gateway
    │       version: "0.3.1"
    │     - name: execution-service
    │       version: "0.5.2"
    │     - name: pipeline-service
    │       version: "0.4.0"
    │     # ...all services
    └── values.yaml
```

The `pravah-platform` umbrella chart allows installing the entire platform with one command:

```bash
# Install all services with one command
helm install pravah ./charts/pravah-platform \
  --namespace pravah \
  --values ./charts/pravah-platform/values-production.yaml

# Or upgrade all services with coordinated values
helm upgrade pravah ./charts/pravah-platform \
  --namespace pravah \
  --values ./charts/pravah-platform/values-production.yaml \
  --set execution-service.image.tag=1.4.3 \
  --set pipeline-service.image.tag=2.1.0
```

## GitOps with Argo CD

In production, Helm releases are not applied manually. Argo CD (a GitOps controller) watches the Git repository and automatically applies Helm chart changes when they are merged to the main branch.

```yaml
# Argo CD Application — manages execution-service in production
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: execution-service-production
  namespace: argocd
spec:
  project: pravah-production

  source:
    repoURL: https://github.com/Abhishekkumar2021/Pravah
    targetRevision: main
    path: charts/execution-service
    helm:
      valueFiles:
        - values.yaml
        - values-production.yaml

  destination:
    server: https://kubernetes.default.svc
    namespace: pravah

  syncPolicy:
    automated:
      prune: true        # delete resources removed from chart
      selfHeal: true     # revert manual kubectl changes
    syncOptions:
      - CreateNamespace=true
      - Wait=true

  # Health checks — Argo CD knows how to assess Deployment/StatefulSet health
  # A release is only "healthy" when all pods pass readiness
```

The GitOps flow:
1. Engineer merges a PR updating `image.tag` in `values-production.yaml`
2. Argo CD detects the change (polling or webhook)
3. Argo CD runs `helm upgrade` with the new values
4. Kubernetes performs the rolling update
5. Argo CD reports the sync status (healthy/degraded/progressing)

No engineer runs `helm upgrade` manually in production. The Git repository is the single source of truth.

## System Design Interview Angles

**"How does Helm handle the upgrade of a chart that changes the ConfigMap that a Deployment depends on?"**

> Helm applies all changed resources atomically — it sends the updated ConfigMap and updated Deployment to Kubernetes in the same upgrade transaction. Kubernetes updates the ConfigMap immediately, but existing pods still have the old ConfigMap values cached.
>
> There are two approaches to ensure pods pick up the new config. First, if the application uses Spring's `@RefreshScope` or a file watcher, it can detect the ConfigMap change and reload without a pod restart. Second, and more commonly: include a checksum annotation on the pod template: `checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}`. When the ConfigMap changes, the checksum changes, the pod template annotation changes, and Kubernetes performs a rolling restart — ensuring all pods pick up the new configuration.
>
> The checksum approach is idiomatic Helm. It creates a deliberate causal link: ConfigMap change → annotation change → rolling restart. This happens automatically as part of `helm upgrade`, without requiring manual pod restarts.

**"What is the difference between `helm install` and `helm upgrade`?"**

> `helm install` creates a new release — it applies all resources from the chart and records the release in a Kubernetes Secret in the target namespace. It fails if a release with that name already exists.
>
> `helm upgrade` applies a new revision to an existing release. Helm computes the diff between the current and desired state and applies only the changed resources. It records the new revision, preserving the history for rollback.
>
> In CI/CD, you typically use `helm upgrade --install` — which performs `install` if the release doesn't exist, or `upgrade` if it does. This makes the pipeline idempotent: the same command works for first deployment and subsequent updates.

## Key Takeaways

1. **Helm packages related Kubernetes resources as versioned, configurable releases.** Install, upgrade, rollback, and diff are first-class operations.

2. **Chart structure:** `Chart.yaml` (metadata), `values.yaml` (configuration defaults), `templates/` (Kubernetes YAML with Go template expressions).

3. **`values-production.yaml` overrides defaults.** Never pin image tags in `values.yaml` (default: `latest`). Pin in `values-production.yaml`. No manual `kubectl` in production.

4. **Conditional templates** (`{{- if .Values.autoscaling.enabled }}`) enable/disable features per environment without duplicating templates.

5. **ConfigMap checksum annotation** forces pod restart on config change: `checksum/config: {{ include ... | sha256sum }}`.

6. **`helm rollback`** reverts all managed resources to a previous revision. This is why "drift" (manual `kubectl apply`) is dangerous — those resources are invisible to Helm and cannot be rolled back.

7. **Umbrella charts** install multiple services as a unit. Library charts share helper templates across service charts.

8. **GitOps with Argo CD:** Helm upgrades never run manually in production. Git is the source of truth. Argo CD applies changes when PRs are merged. `selfHeal: true` reverts manual drift.

Autoscaling adjusts pod counts automatically based on metrics, keeping costs low during quiet periods and capacity available during bursts.
