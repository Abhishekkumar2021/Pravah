# 6.4 Kubernetes Networking & Network Policies

## The Kubernetes Networking Model

Kubernetes networking has one fundamental rule: every pod can reach every other pod directly by IP address, without NAT, across the entire cluster. This is the flat network model.

In a bare cluster with no additional configuration, a pod in the `monitoring` namespace can connect to any pod in the `pravah` namespace on any port. There are no implicit firewall rules. This is convenient for development but dangerous in production — a compromised pod has unrestricted access to every other pod.

NetworkPolicy restores the firewalling that the flat network removes. It lets you define, per pod, which other pods and external endpoints are allowed to communicate with it.

---

## Service Types — Exposing Pods

Pods have ephemeral IPs that change when they restart. Services provide stable virtual IPs and DNS names that load-balance across all ready pods.

### ClusterIP — Internal Communication

The default. Creates a virtual IP accessible only within the cluster. All internal service-to-service communication in Pravah uses ClusterIP.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: execution-service
  namespace: pravah
spec:
  type: ClusterIP    # default — can be omitted
  selector:
    app: execution-service
  ports:
    - name: http
      port: 8080
      targetPort: 8080
    - name: management
      port: 8081
      targetPort: 8081
```

DNS resolution: `execution-service.pravah.svc.cluster.local` → ClusterIP → kube-proxy → any ready pod at port 8080.

Pipeline Service calling Execution Service:
```java
// No hardcoded IPs — use DNS
String executionServiceUrl = "http://execution-service.pravah.svc:8080";
```

This URL works from any pod in the cluster, regardless of which node Execution Service is running on.

### LoadBalancer — External Cloud Load Balancer

Provisions a cloud provider load balancer (AWS NLB/ALB, GCP Cloud Load Balancer) with an external IP. Traffic flows: Internet → Load Balancer → NodePort → kube-proxy → pod.

Pravah does NOT use `type: LoadBalancer` for individual services. This approach provisions one cloud load balancer per service — expensive (each LB costs money) and operationally complex.

Instead, Pravah uses a single Ingress controller with one load balancer, routing to multiple services by hostname and path.

### Ingress — HTTP(S) Traffic Routing

Ingress routes external HTTP/HTTPS traffic to internal services based on hostname and path rules. One Ingress controller (one load balancer) handles all external traffic.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: pravah-api-ingress
  namespace: pravah
  annotations:
    # NGINX Ingress controller annotations
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/use-regex: "true"
    # Rate limiting (backed by nginx rate limiting)
    nginx.ingress.kubernetes.io/limit-rps: "100"
    nginx.ingress.kubernetes.io/limit-connections: "20"
    # Proxy timeouts
    nginx.ingress.kubernetes.io/proxy-read-timeout: "120"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "120"
    # Backend protocol
    nginx.ingress.kubernetes.io/backend-protocol: "HTTP"
    # CORS (handled by API Gateway, not Ingress)
    nginx.ingress.kubernetes.io/enable-cors: "false"

spec:
  ingressClassName: nginx

  tls:
    - hosts:
        - api.pravah.io
        - runners.pravah.io     # gRPC gateway for runners
      secretName: pravah-tls    # cert-manager managed TLS cert

  rules:
    # External API (user-facing)
    - host: api.pravah.io
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-gateway
                port:
                  number: 8080
```

```yaml
# Separate Ingress for gRPC (requires HTTP/2, different configuration)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: pravah-grpc-ingress
  namespace: pravah
  annotations:
    nginx.ingress.kubernetes.io/backend-protocol: "GRPC"    # gRPC upstream
    nginx.ingress.kubernetes.io/ssl-passthrough: "false"     # terminate TLS at ingress
    nginx.ingress.kubernetes.io/grpc-backend: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [runners.pravah.io]
      secretName: pravah-runners-tls
  rules:
    - host: runners.pravah.io
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: runner-grpc-service
                port:
                  number: 9090
```

### Management Port — Never Exposed Externally

Pravah's services expose Actuator endpoints (health, metrics) on port 8081 — a separate management port. This port has its own ClusterIP Service but is never included in any Ingress rule. It is accessible only from within the cluster (Prometheus scraping, health checks).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: execution-service-management
  namespace: pravah
spec:
  type: ClusterIP
  selector:
    app: execution-service
  ports:
    - name: management
      port: 8081
      targetPort: 8081
# No Ingress rule for this service
# Prometheus discovers it via ServiceMonitor annotation
```

## NetworkPolicy — Zero-Trust Pod-to-Pod Communication

By default, all pods in a Kubernetes cluster can communicate with all other pods. NetworkPolicy restricts this.

**Default deny posture:** apply a policy that denies all ingress and egress, then explicitly allow only what is required. This is the network equivalent of "deny all, allow exceptions" firewalling.

### Default Deny All — Applied to Entire Namespace

```yaml
# Apply first — establishes baseline deny
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: pravah
spec:
  podSelector: {}    # selects all pods in the namespace
  policyTypes:
    - Ingress
    - Egress
  # No ingress or egress rules = deny all traffic
```

After this is applied, no pod in `pravah` can communicate with anything — not even DNS. The following policies then explicitly allow what is needed.

### Allow DNS Resolution

```yaml
# DNS is required by every service — allow egress to kube-dns
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: pravah
spec:
  podSelector: {}     # all pods
  policyTypes:
    - Egress
  egress:
    - ports:
        - port: 53
          protocol: UDP
        - port: 53
          protocol: TCP
      to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
```

### Execution Service Network Policy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: execution-service-policy
  namespace: pravah
spec:
  podSelector:
    matchLabels:
      app: execution-service
  policyTypes:
    - Ingress
    - Egress

  ingress:
    # Allow traffic from API Gateway (user-initiated job triggers)
    - from:
        - podSelector:
            matchLabels:
              app: api-gateway
      ports:
        - port: 8080

    # Allow traffic from Prometheus (metrics scraping)
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
          podSelector:
            matchLabels:
              app: prometheus
      ports:
        - port: 8081    # management port only

    # Allow health checks from kube-apiserver (probe traffic)
    - from:
        - ipBlock:
            cidr: 0.0.0.0/0
            except:
              - 10.0.0.0/8       # not from other pods
              - 192.168.0.0/16
      ports:
        - port: 8081    # management only (health probes come from the node's IP)

  egress:
    # Egress to PostgreSQL (via PgBouncer)
    - to:
        - podSelector:
            matchLabels:
              app: pgbouncer
      ports:
        - port: 5432

    # Egress to Redis
    - to:
        - podSelector:
            matchLabels:
              app: redis
      ports:
        - port: 6379

    # Egress to Kafka
    - to:
        - podSelector:
            matchLabels:
              app: kafka
      ports:
        - port: 9092

    # Egress to Pipeline Service (for pipeline config validation)
    - to:
        - podSelector:
            matchLabels:
              app: pipeline-service
      ports:
        - port: 8080

    # Egress to Runner Service (for runner assignment queries)
    - to:
        - podSelector:
            matchLabels:
              app: runner-service
      ports:
        - port: 8080

    # Egress to Vault (secret retrieval — Vault Agent handles this)
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: vault
          podSelector:
            matchLabels:
              app: vault
      ports:
        - port: 8200

    # Egress to OTEL Collector (telemetry)
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
          podSelector:
            matchLabels:
              app: otel-collector
      ports:
        - port: 4317    # gRPC OTLP
        - port: 4318    # HTTP OTLP
```

### API Gateway Network Policy

The API Gateway is special — it must receive traffic from the Internet (via the Ingress controller) and route to internal services.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-gateway-policy
  namespace: pravah
spec:
  podSelector:
    matchLabels:
      app: api-gateway
  policyTypes:
    - Ingress
    - Egress

  ingress:
    # Allow traffic from the NGINX Ingress controller (external traffic entry point)
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
          podSelector:
            matchLabels:
              app.kubernetes.io/name: ingress-nginx
      ports:
        - port: 8080

  egress:
    # API Gateway can reach all Pravah services (it routes to them)
    - to:
        - podSelector:
            matchLabels:
              team: pravah-service    # common label on all Pravah microservices
      ports:
        - port: 8080
    # Auth Service (for token validation if not doing it locally)
    - to:
        - podSelector:
            matchLabels:
              app: auth-service
      ports:
        - port: 8080
```

### Namespace-Level Isolation

Monitoring components (Prometheus, Grafana, Jaeger) are in the `monitoring` namespace. They need to scrape metrics from the `pravah` namespace but should not be able to make arbitrary application requests.

```yaml
# Allow Prometheus in monitoring namespace to scrape pravah pods
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-prometheus-scraping
  namespace: pravah
spec:
  podSelector:
    matchLabels:
      team: pravah-service    # all Pravah services
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
          podSelector:
            matchLabels:
              app: prometheus
      ports:
        - port: 8081    # management port only — not application port 8080
```

Prometheus can scrape `/actuator/prometheus` from any Pravah pod, but cannot send HTTP requests to `POST /jobs` or any other application endpoint. The separation of management port (8081) from application port (8080) makes this policy precise.

## Pravah's Network Topology

```
Internet
    │
    │ HTTPS 443 (TLS terminated at Ingress)
    ▼
┌───────────────────────────────────────────────┐
│  ingress-nginx namespace                       │
│  NGINX Ingress Controller + Cloud Load Balancer│
└───────────────────────────────────────────────┘
    │
    │ HTTP 8080 (internal, TLS terminated)
    ▼
┌───────────────────────────────────────────────┐
│  pravah namespace                             │
│                                               │
│  api-gateway ──────────────────────────────┐  │
│    │ 8080                                  │  │
│    ├──► pipeline-service :8080             │  │
│    ├──► execution-service :8080            │  │
│    ├──► scheduler-service :8080            │  │
│    └──► runner-service :8080               │  │
│                                            │  │
│  execution-service ────────────────────┐   │  │
│    │                                   │   │  │
│    ├──► pgbouncer :5432                │   │  │
│    ├──► redis :6379                    │   │  │
│    ├──► kafka :9092                    │   │  │
│    └──► pipeline-service :8080         │   │  │
│                                        ▼   ▼  │
│  monitoring namespace ◄── :8081 ── all services  │
│    (prometheus scrapes only management port)   │
│                                               │
│  vault namespace ◄── :8200 ── all services    │
│    (Vault Agent sidecars fetch secrets)        │
└───────────────────────────────────────────────┘
    │
    │ gRPC 9090 (mTLS, separate load balancer)
    ▼
┌───────────────────────────────────────────────┐
│  Self-hosted Runner Infrastructure             │
│  (tenant's on-premises / cloud VMs)            │
│  ← NOT inside the Kubernetes cluster          │
└───────────────────────────────────────────────┘
```

The NetworkPolicy rules enforce this topology in code. Execution Service cannot accidentally connect to the NGINX ingress controller, the Kubernetes API server, or any other infrastructure component not in its allowed egress list.

## Service Mesh (Istio) as NetworkPolicy Complement

NetworkPolicy operates at L3/L4 (IP addresses and ports). It cannot distinguish between different HTTP endpoints on the same port — it can allow Execution Service to reach Pipeline Service on port 8080, but cannot further restrict which specific gRPC methods or REST paths are callable.

Istio's `AuthorizationPolicy` (from 5.3) adds L7 controls:

```yaml
# Allow Execution Service to call only specific Pipeline Service paths
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: pipeline-service-fine-grained
  namespace: pravah
spec:
  selector:
    matchLabels:
      app: pipeline-service
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/pravah/sa/execution-service-sa"]
      to:
        - operation:
            methods: ["GET"]
            paths: ["/pipelines/*", "/schedules/*"]
    # Execution Service cannot call POST /pipelines (create) — Pipeline Editor role required
    # Execution Service cannot call DELETE /pipelines
```

NetworkPolicy (L3/L4) + Istio AuthorizationPolicy (L7) together implement the full zero-trust model.

## System Design Interview Angles

**"What is the Kubernetes networking flat model and why does NetworkPolicy exist?"**

> Kubernetes imposes one fundamental networking rule: every pod can reach every other pod by IP, without NAT, across the cluster. This simplifies application development — pods don't need to know about the network topology. But it also means a compromised pod has unrestricted access to every other pod, every database, every internal service.
>
> NetworkPolicy adds selective firewalling back. You define, per pod label selector, which sources can send ingress traffic and which destinations can receive egress traffic. The practical approach: apply a default-deny policy to the namespace first, then explicitly allow the specific communication paths you need.
>
> For Pravah: Execution Service can send egress to PgBouncer, Redis, Kafka, Pipeline Service, and Vault. It cannot reach the Kubernetes API server, other namespaces' databases, or the NGINX ingress controller. A compromised Execution Service pod cannot pivot to other tenants' databases or the cluster control plane — the network policy blocks the attempt at the kernel level.

**"What is the difference between an Ingress and a LoadBalancer Service?"**

> `type: LoadBalancer` provisions one cloud load balancer per Service. If Pravah has 10 services exposed externally, that's 10 cloud load balancers — 10 external IPs, 10 DNS records, 10 billing line items. Each costs roughly $15–20/month on AWS, plus data transfer.
>
> Ingress uses one load balancer (or one NodePort on the edge) for all services, using L7 HTTP routing — hostname and path rules — to direct traffic to the correct backend service. API requests to `api.pravah.io/jobs` go to API Gateway, gRPC connections to `runners.pravah.io` go to the runner gRPC service. One load balancer, many services.
>
> The Ingress controller (NGINX, Traefik, or cloud-native) runs as a pod inside the cluster and handles the routing. It does TLS termination, rate limiting, connection limits, and can inject headers — capabilities that `type: LoadBalancer` does not provide.

## Key Takeaways

1. **Kubernetes networking is flat by default.** All pods can reach all pods. NetworkPolicy re-adds selective firewalling.

2. **Default deny posture.** Apply a `podSelector: {}` policy with no rules first — deny all. Then add specific allow policies. This ensures no implicit communication is allowed.

3. **Service types:**
   - `ClusterIP`: internal only (default for all Pravah services)
   - `LoadBalancer`: provisions a cloud LB (Pravah uses one for the Ingress controller only)
   - Ingress: L7 HTTP routing to multiple services through one load balancer

4. **Management port separation (8081 vs 8080).** NetworkPolicy can restrict Prometheus to scraping only port 8081 — it cannot make application requests to port 8080. This enforces the operational boundary at the network level.

5. **Namespace-based isolation.** `namespaceSelector` + `podSelector` combinations target specific pods in specific namespaces. Monitoring namespace can scrape `pravah` namespace on port 8081. `pravah` namespace cannot reach `monitoring` namespace at all.

6. **NetworkPolicy is L3/L4 only.** It enforces by IP and port. Istio AuthorizationPolicy adds L7 enforcement (HTTP method, path, gRPC method). Both are needed for full zero-trust.

7. **gRPC requires separate Ingress configuration.** HTTP/2 requirement, `backend-protocol: GRPC` annotation, separate hostnames. Pravah uses `runners.pravah.io` for runner gRPC traffic, `api.pravah.io` for REST API.

8. **Never expose management ports externally.** Actuator endpoints (`/health`, `/metrics`) have no Ingress rule. Accessible only from within the cluster (Prometheus) via ClusterIP Service.
