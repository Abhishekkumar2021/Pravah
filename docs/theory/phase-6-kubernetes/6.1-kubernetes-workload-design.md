# 6.1 Kubernetes Workload Design

## The Right Workload Type for Each Component

Kubernetes provides multiple workload primitives. Choosing the wrong one for a component results in operational problems that are hard to fix after the fact. The right choice depends on what the component does, how it stores state, whether there are ordering guarantees, and whether it should run on every node.

Pravah's components map to three workload types:

```
Deployment           → stateless services (Execution, Pipeline, Scheduler, API Gateway, etc.)
StatefulSet          → stateful components (PostgreSQL, Kafka, ZooKeeper, Redis, Vault)
DaemonSet            → node-level agents (Filebeat log collector, Prometheus node-exporter)
```

Understanding why each component gets its workload type — and what breaks when you get it wrong — is the core of this chapter.

---

## Deployment — Stateless Services

A Deployment manages a ReplicaSet of identical, interchangeable pods. Kubernetes can create, destroy, and reschedule these pods on any node without consequences for correctness.

This works because stateless services keep no local state. All durable state lives in PostgreSQL, Redis, or Kafka. Any pod can handle any request. If a pod dies, requests are distributed to surviving pods, and Kubernetes creates a replacement on any available node.

Pravah's Deployment-managed services: API Gateway, Pipeline Service, Execution Service, Scheduler Service, Notification Service, Runner Service (cloud runners).

### A Production-Grade Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: execution-service
  namespace: pravah
  labels:
    app: execution-service
    version: "1.4.2"
    team: platform
spec:
  replicas: 3                   # minimum for HA — never run critical services at 1 replica

  selector:
    matchLabels:
      app: execution-service

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0          # never take pods offline during rollout (zero-downtime)
      maxSurge: 1                # create one extra pod before removing old ones

  template:
    metadata:
      labels:
        app: execution-service
        version: "1.4.2"
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "8081"
        prometheus.io/path: "/actuator/prometheus"

    spec:
      serviceAccountName: execution-service-sa

      # Spread pods across nodes — don't put all replicas on the same node
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: execution-service
        # Also spread across availability zones
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: execution-service

      # Prefer not to run with other high-memory services on the same node
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values: [pipeline-service, scheduler-service]
                topologyKey: kubernetes.io/hostname

      # Graceful shutdown: let in-flight requests complete
      terminationGracePeriodSeconds: 60

      containers:
        - name: execution-service
          image: pravah/execution-service:1.4.2

          ports:
            - name: http
              containerPort: 8080
            - name: management
              containerPort: 8081

          env:
            - name: SPRING_PROFILES_ACTIVE
              value: "production,kubernetes"
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: POD_NAMESPACE
              valueFrom:
                fieldRef:
                  fieldPath: metadata.namespace

          resources:
            requests:
              cpu: "500m"        # 0.5 CPU cores guaranteed
              memory: "512Mi"    # 512 MB guaranteed
            limits:
              cpu: "2000m"       # 2 CPU cores maximum
              memory: "1Gi"      # 1 GB maximum — OOM if exceeded

          startupProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8081
            failureThreshold: 36
            periodSeconds: 5

          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8081
            periodSeconds: 10
            failureThreshold: 3

          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8081
            periodSeconds: 5
            failureThreshold: 3
            successThreshold: 2

          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 15"]

          volumeMounts:
            - name: vault-secrets
              mountPath: /vault/secrets
              readOnly: true
            - name: tls-certs
              mountPath: /etc/pravah/tls
              readOnly: true
            - name: tmp
              mountPath: /tmp    # writable temp, but not the container filesystem

          # Security context — principle of least privilege
          securityContext:
            runAsNonRoot: true
            runAsUser: 1000
            runAsGroup: 1000
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]

      # Vault Agent sidecar (see 5.4)
      - name: vault-agent
        image: hashicorp/vault:1.15
        args: ["agent", "-config=/vault/config/agent-config.hcl"]
        securityContext:
          runAsNonRoot: true
          runAsUser: 100
        volumeMounts:
          - name: vault-config
            mountPath: /vault/config
          - name: vault-secrets
            mountPath: /vault/secrets

      volumes:
        - name: vault-secrets
          emptyDir:
            medium: Memory        # tmpfs — not persisted to disk
        - name: vault-config
          configMap:
            name: vault-agent-config-execution
        - name: tls-certs
          secret:
            secretName: execution-service-tls-secret
        - name: tmp
          emptyDir: {}
```

### Key Deployment Design Decisions

**`maxUnavailable: 0, maxSurge: 1`:** Zero-downtime rolling updates. Kubernetes creates a new pod, waits for it to pass readiness, then terminates an old pod. The total pod count temporarily exceeds `replicas` (3+1=4) during the rollout, but traffic is never interrupted. If `maxUnavailable: 1` were used instead, one pod would be taken offline before the new one is ready — causing temporary capacity reduction that can cascade under load.

**`topologySpreadConstraints`:** without this, Kubernetes might schedule all 3 replicas on the same node. That node failing would take the entire service offline. Spread constraints force distribution across nodes, and prefer distribution across availability zones for cloud deployments. The key difference: `DoNotSchedule` for node-level spread (hard requirement), `ScheduleAnyway` for zone-level spread (best effort — don't fail scheduling if zones are unavailable).

**`readOnlyRootFilesystem: true`:** the container cannot write to its own filesystem. Any file write attempts by a compromised container fail immediately. The `/tmp` volume provides a writable scratchpad where needed. This breaks many container images that assume they can write anywhere — surfacing this assumption is a security benefit.

**`drop: ["ALL"]`:** removes all Linux capabilities from the container. Capabilities like `NET_RAW` (raw sockets), `SYS_PTRACE` (process tracing), and `SETUID` are attack primitives. Unless a specific capability is explicitly required (and documented), it is dropped.

## StatefulSet — Stateful Components

StatefulSets provide guarantees that Deployments do not:

1. **Stable network identity:** pods get deterministic names (`postgres-0`, `postgres-1`, `kafka-0`) that survive restarts. DNS entries are stable: `kafka-0.kafka.pravah.svc.cluster.local` always points to the same pod identity.

2. **Stable persistent storage:** each pod gets its own PersistentVolumeClaim (PVC). When a pod is rescheduled, it re-attaches to its own PVC — not a new empty one.

3. **Ordered deployment and scaling:** pods are created and terminated in order (0, 1, 2 on scale-up; 2, 1, 0 on scale-down). This matters for Kafka (broker 0 is typically the controller leader) and PostgreSQL (primary must start before replicas).

### PostgreSQL StatefulSet (Patroni for HA)

In production, Pravah runs PostgreSQL via the Patroni HA operator (or CloudNativePG). The StatefulSet pattern:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: pravah
spec:
  serviceName: postgres-headless   # headless service for stable DNS
  replicas: 3                      # primary + 2 standbys

  selector:
    matchLabels:
      app: postgres

  template:
    metadata:
      labels:
        app: postgres

    spec:
      serviceAccountName: postgres-sa

      containers:
        - name: postgres
          image: pravah/postgres-patroni:15.4

          env:
            - name: PATRONI_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name    # "postgres-0", "postgres-1", etc.
            - name: PATRONI_KUBERNETES_NAMESPACE
              valueFrom:
                fieldRef:
                  fieldPath: metadata.namespace
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password

          resources:
            requests:
              cpu: "2000m"
              memory: "4Gi"
            limits:
              cpu: "4000m"
              memory: "8Gi"

          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data

          ports:
            - containerPort: 5432
              name: postgres
            - containerPort: 8008
              name: patroni-api

          readinessProbe:
            exec:
              command:
                - sh
                - -c
                - "pg_isready -U postgres && curl -s http://localhost:8008/health | grep -q leader"
            periodSeconds: 10
            failureThreshold: 3

  # VolumeClaimTemplates: each pod gets its own PVC
  volumeClaimTemplates:
    - metadata:
        name: postgres-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast-ssd      # NVMe SSD storage class
        resources:
          requests:
            storage: 500Gi
```

**Why StatefulSet for PostgreSQL and not Deployment:**

A Deployment would create pods with random names (`postgres-7b4d9f-abc`) and no guaranteed PVC identity. If a pod is rescheduled, it might get a different PVC — meaning a different empty data directory. You cannot have an HA PostgreSQL cluster where replicas don't know each other's stable hostnames (for WAL streaming) or where nodes lose their data on reschedule.

StatefulSet gives `postgres-0` a guaranteed hostname and a guaranteed PVC. The primary is always `postgres-0.postgres-headless.pravah.svc`, and replicas stream WAL from it by name. This is the contract StatefulSet provides that Deployment cannot.

### Kafka StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
  namespace: pravah
spec:
  serviceName: kafka-headless
  replicas: 3

  template:
    spec:
      containers:
        - name: kafka
          image: confluentinc/cp-kafka:7.5.0

          env:
            - name: KAFKA_NODE_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name   # parsed to get ordinal: kafka-0 → 0
            - name: KAFKA_CONTROLLER_QUORUM_VOTERS
              value: "0@kafka-0.kafka-headless:9093,1@kafka-1.kafka-headless:9093,2@kafka-2.kafka-headless:9093"
            - name: KAFKA_ADVERTISED_LISTENERS
              value: "PLAINTEXT://$(POD_NAME).kafka-headless.pravah.svc:9092"

          volumeMounts:
            - name: kafka-data
              mountPath: /var/lib/kafka/data

  volumeClaimTemplates:
    - metadata:
        name: kafka-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast-ssd
        resources:
          requests:
            storage: 200Gi
```

Kafka needs stable hostnames for broker advertisement and KRaft controller quorum. `kafka-0.kafka-headless.pravah.svc` is how brokers refer to each other and how clients discover the cluster. If these names were unstable (as with a Deployment), the Kafka cluster would fragment.

## DaemonSet — Node-Level Agents

A DaemonSet ensures exactly one pod runs on every node (or on every node matching a selector). When a new node joins the cluster, the DaemonSet pod is scheduled on it automatically. When a node is removed, the pod is garbage-collected.

Pravah uses DaemonSets for:
- **Filebeat:** log collection agent — reads container logs from `/var/log/containers/` on each node
- **Prometheus node-exporter:** exposes hardware and OS metrics per node (CPU, memory, disk, network)
- **Falco:** runtime security monitoring — watches system calls per node

### Filebeat DaemonSet

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: filebeat
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: filebeat

  template:
    metadata:
      labels:
        app: filebeat

    spec:
      serviceAccountName: filebeat-sa
      terminationGracePeriodSeconds: 30

      containers:
        - name: filebeat
          image: docker.elastic.co/beats/filebeat:8.10.0

          args: ["-c", "/etc/filebeat.yml", "-e"]

          env:
            - name: ELASTICSEARCH_HOST
              value: "https://elasticsearch.monitoring.svc:9200"
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName

          resources:
            requests:
              cpu: "100m"
              memory: "100Mi"
            limits:
              cpu: "200m"
              memory: "200Mi"

          volumeMounts:
            # Read container logs from the node's filesystem
            - name: varlog
              mountPath: /var/log
              readOnly: true
            - name: varlibdockercontainers
              mountPath: /var/lib/docker/containers
              readOnly: true
            - name: filebeat-config
              mountPath: /etc/filebeat.yml
              subPath: filebeat.yml
              readOnly: true

          securityContext:
            runAsUser: 0          # must run as root to read /var/log
            privileged: false

      volumes:
        - name: varlog
          hostPath:
            path: /var/log
        - name: varlibdockercontainers
          hostPath:
            path: /var/lib/docker/containers
        - name: filebeat-config
          configMap:
            name: filebeat-config

      # Tolerate master/control-plane nodes — collect logs there too
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          effect: NoSchedule
          operator: Exists
```

The key DaemonSet patterns:
- `hostPath` volumes to access node-level resources (container log files, `/proc`, device nodes)
- Tolerations to run on all nodes including tainted master nodes
- Conservative resource limits — DaemonSet pods compete with every application pod on every node

## Workload Selection Reference

```
Component                 Type          Why
──────────────────────────────────────────────────────────────────────
API Gateway               Deployment    Stateless, replicas interchangeable
Pipeline Service          Deployment    Stateless
Execution Service         Deployment    Stateless (state in PostgreSQL)
Scheduler Service         Deployment    Stateless (leader election via Redis)
Runner Service (cloud)    Deployment    Stateless
Notification Service      Deployment    Stateless

PostgreSQL (Patroni)      StatefulSet   Stable identity, persistent data
Kafka (KRaft)             StatefulSet   Stable identity, persistent data
Redis (Sentinel)          StatefulSet   Stable identity, in-memory state
Vault                     StatefulSet   Stable identity, encrypted storage
Elasticsearch             StatefulSet   Stable identity, index storage

Filebeat                  DaemonSet     One per node, reads host log files
node-exporter             DaemonSet     One per node, reads host metrics
Falco                     DaemonSet     One per node, kernel-level monitoring
OTel Collector            DaemonSet     One per node, receives telemetry from pods
```

## Headless Services — DNS-Based Discovery for StatefulSets

StatefulSets use a headless Service (no ClusterIP) to provide stable DNS for each pod:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: kafka-headless
  namespace: pravah
spec:
  clusterIP: None      # headless — no virtual IP
  selector:
    app: kafka
  ports:
    - name: broker
      port: 9092
    - name: controller
      port: 9093
```

With a headless Service named `kafka-headless` in namespace `pravah`:
- `kafka-0.kafka-headless.pravah.svc.cluster.local` → pod `kafka-0`'s IP
- `kafka-1.kafka-headless.pravah.svc.cluster.local` → pod `kafka-1`'s IP
- `kafka-headless.pravah.svc.cluster.local` → all pod IPs (DNS returns multiple A records)

This is how brokers find each other and how clients bootstrap their connection to the cluster.

For regular Services (ClusterIP), a virtual IP is created and requests are load-balanced across all healthy pods. This is what Pravah's stateless services use — clients connect to `execution-service.pravah.svc` and any ready pod receives the request.

## Init Containers — Ordered Startup Dependencies

Init containers run to completion before any regular container starts. They enforce startup order and can perform one-time setup tasks.

```yaml
spec:
  initContainers:
    # Wait for PostgreSQL to be ready before starting Execution Service
    - name: wait-for-postgres
      image: busybox:1.35
      command: ['sh', '-c', '
        until pg_isready -h postgres-primary.pravah.svc -p 5432 -U postgres;
        do echo "waiting for postgres..."; sleep 2;
        done;
        echo "postgres is ready"
      ']

    # Run database migrations before starting the application
    - name: run-migrations
      image: pravah/execution-service:1.4.2
      command: ["java", "-jar", "app.jar", "--spring.profiles.active=migrate-only"]
      env:
        - name: SPRING_DATASOURCE_URL
          value: "jdbc:postgresql://postgres-primary.pravah.svc:5432/pravah_execution_db"
      volumeMounts:
        - name: vault-secrets
          mountPath: /vault/secrets

    # Vault Agent: fetch secrets before main container starts
    - name: vault-agent-init
      image: hashicorp/vault:1.15
      args: ["agent", "-config=/vault/config/agent-config.hcl", "-exit-after-auth"]
      volumeMounts:
        - name: vault-config
          mountPath: /vault/config
        - name: vault-secrets
          mountPath: /vault/secrets

  containers:
    - name: execution-service
      # ... starts after all init containers complete successfully ...
```

Init containers for Pravah's pattern:
1. **`wait-for-postgres`:** ensures the database is accepting connections before migrations run
2. **`run-migrations`:** Flyway migrations run exactly once, before the application starts
3. **`vault-agent-init`:** fetches initial secrets before the main container starts — the main container always has secrets available from the first millisecond

If any init container fails, Kubernetes restarts the pod and tries again. The startup probe on the main container does not start ticking until all init containers have completed.

## System Design Interview Angles

**"When would you use a StatefulSet vs a Deployment in Kubernetes?"**

> The distinction is about guarantees. Deployments manage interchangeable, stateless pods — any pod can handle any request and pods can be scheduled anywhere. StatefulSets provide three additional guarantees: stable network identity (deterministic pod names and DNS), stable persistent storage (each pod's PVC survives rescheduling), and ordered deployment and termination.
>
> For Pravah's stateless services — Execution Service, Pipeline Service, API Gateway — Deployments are correct. If any of these pods dies, Kubernetes replaces it on any available node and traffic continues to the surviving pods. No state is lost because all state lives in the database.
>
> For PostgreSQL, Kafka, and Redis, StatefulSets are required. Kafka brokers must have stable hostnames so they can advertise their addresses to clients and communicate with each other for leader election. PostgreSQL replicas must stream WAL from a specific primary by hostname. When a StatefulSet pod restarts, it reattaches to its own PVC — the same data that was there before. A Deployment would give it an empty new volume.

**"What is the purpose of `topologySpreadConstraints` and how does it differ from pod anti-affinity?"**

> Both distribute pods across topology boundaries, but differently. Pod anti-affinity rules say "don't schedule near pods with this label" — they are binary rules that can prevent scheduling entirely if satisfied pods are not available. They also don't guarantee even distribution: if you have 3 replicas and 5 nodes, anti-affinity might put all 3 on separate nodes but not distribute evenly.
>
> `topologySpreadConstraints` with `maxSkew` provides mathematical distribution control. `maxSkew: 1` means the difference between the most-loaded and least-loaded topology zone cannot exceed 1 pod. With 3 replicas across 3 zones, you get 1-1-1. With 4 replicas and 3 zones, you get at most 2-1-1, never 4-0-0 or 3-1-0.
>
> Pravah uses `DoNotSchedule` (hard constraint) for node-level spreading — we refuse to run all 3 replicas on one node — and `ScheduleAnyway` (soft constraint) for zone-level spreading. Zone spread is best-effort because zone failures are less frequent than node failures, and we don't want pod scheduling to fail if a zone has fewer nodes.

## Key Takeaways

1. **Deployment = stateless.** Interchangeable pods. Any pod can handle any request. State lives externally. Pod death → automatic replacement anywhere.

2. **StatefulSet = stateful.** Stable pod names (`postgres-0`), stable DNS, stable PVC attachment per pod. Ordered scale-up and scale-down. Required for PostgreSQL, Kafka, Redis.

3. **DaemonSet = one-per-node.** Automatically scheduled on new nodes. Used for infrastructure agents that need host-level access: log collection (Filebeat), metrics (node-exporter), security monitoring (Falco).

4. **`maxUnavailable: 0, maxSurge: 1` for zero-downtime rolling updates.** Never remove old pods before new pods pass readiness. Critical for production deployments.

5. **`topologySpreadConstraints` to prevent correlated failures.** Hard constraint on node spread (never all replicas on one node). Soft constraint on zone spread (prefer distribution, don't fail scheduling).

6. **`readOnlyRootFilesystem + drop ALL capabilities`** for container security. Writable `/tmp` via emptyDir volume where needed.

7. **Headless Services for StatefulSet DNS.** `clusterIP: None` gives each pod its own stable DNS entry. Essential for cluster-aware applications like Kafka and PostgreSQL.

8. **Init containers enforce startup ordering.** Dependency readiness checks, one-time migrations, initial secret fetching — all complete before the main container starts. Eliminates race conditions on pod startup.
