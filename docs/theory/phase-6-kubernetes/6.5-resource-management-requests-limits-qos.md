# 6.5 Resource Management — Requests, Limits & QoS

## Why Resource Management Matters

Kubernetes schedules pods onto nodes. Scheduling decisions are based on resource requests — how much CPU and memory each pod claims it needs. Without well-calibrated requests, Kubernetes makes poor scheduling decisions: either over-commits nodes (pods compete for actual resources, causing slowdowns and OOM kills) or under-utilizes nodes (wasted capacity, higher cost).

Limits set the maximum resources a pod can consume. They protect the node from runaway processes — but they also throttle pods that legitimately need more resources, causing latency spikes and OOM kills.

Getting requests and limits right is one of the most impactful things you can do for cluster performance. Getting them wrong causes subtle, hard-to-diagnose production problems.

---

## Requests — Scheduling Currency

A resource request is a reservation. When Kubernetes schedules a pod on a node, it subtracts the pod's resource requests from the node's available capacity. It will not schedule the pod on a node that does not have enough remaining capacity for the requests.

```
Node: 8 CPU cores, 32 GB RAM
Already scheduled:
  pod-a: 2 CPU request, 4 GB request
  pod-b: 1 CPU request, 8 GB request
  pod-c: 1 CPU request, 2 GB request
  Total reserved: 4 CPU, 14 GB

Remaining schedulable capacity: 4 CPU, 18 GB

New pod: 500m CPU request, 1 GB request
  → 500m <= 4000m CPU remaining ✅
  → 1 GB <= 18 GB remaining ✅
  → Schedulable on this node
```

**Requests do not limit actual CPU usage.** If the pod's request is 500m (0.5 cores) but the node has spare capacity, the pod can use 3 CPU cores. Requests affect scheduling and HPA calculations — not runtime enforcement.

**Memory requests matter for scheduling and OOM priority.** A pod using more memory than its request is at higher risk of being OOM-killed when the node is memory-pressured (it is not a guaranteed reservation against eviction, unlike limits).

### CPU — Millicores

CPU resources are measured in millicores: 1000m = 1 CPU core.

```yaml
resources:
  requests:
    cpu: "500m"    # 0.5 cores guaranteed for scheduling
    cpu: "2"       # 2 cores — can be written as "2000m"
    cpu: "0.5"     # same as 500m
```

### Memory — Bytes

```yaml
resources:
  requests:
    memory: "512Mi"    # 512 mebibytes (1 Mi = 1,048,576 bytes)
    memory: "1Gi"      # 1 gibibyte
    memory: "500M"     # 500 megabytes (1 M = 1,000,000 bytes) — different from Mi
```

Use `Mi` and `Gi` (mebibytes/gibibytes) for consistency. The difference between `M` and `Mi` is small but causes confusion — standardize on `Mi`.

## Limits — Runtime Enforcement

Limits cap the maximum resources a container can consume.

### CPU Limits — The Throttling Problem

When a container exceeds its CPU limit, the Linux kernel's CFS (Completely Fair Scheduler) throttles it. The container is put to sleep for the remainder of the current scheduling period (typically 100ms). This appears as latency spikes at the application level.

```
CPU limit: 1000m (1 core)
CPU scheduling period: 100ms

The container gets 100ms of CPU time per 100ms period.
If it tries to use 150ms of CPU in a 100ms period:
  → uses 100ms of CPU
  → throttled for the remaining 50ms of real time
  → any in-flight requests wait during the throttle period
  → p99 latency spikes
```

**The CPU throttling debate:** many engineers advocate setting no CPU limits, only CPU requests. The argument: CPU is compressible (throttling, not OOM kill). Limits cause latency spikes. Without limits, pods use available CPU freely, and the request is sufficient to guarantee scheduling priority.

The counter-argument: without limits, a runaway process can consume all available CPU on a node, starving other pods.

**Pravah's approach:** set CPU limits at 4× the request. This provides headroom for burst processing without risking starvation of other pods.

```yaml
resources:
  requests:
    cpu: "500m"    # guaranteed scheduling weight
  limits:
    cpu: "2000m"   # 4× request — throttle only extreme outliers
```

Monitor for CPU throttling:

```promql
# CPU throttling rate — percentage of time a container is throttled
rate(container_cpu_cfs_throttled_seconds_total{container="execution-service"}[5m])
/
rate(container_cpu_cfs_periods_total{container="execution-service"}[5m])
```

If throttling rate exceeds 25%, increase the CPU limit or profile what is causing the burst.

### Memory Limits — OOM Kill

When a container exceeds its memory limit, the Linux OOM killer terminates the process. Unlike CPU throttling (which is recoverable), an OOM kill terminates the container. Kubernetes restarts it, but:
- In-flight requests are dropped
- Any in-memory state is lost (cache, connection pools must rebuild)
- If OOM kills happen repeatedly and quickly, the pod enters `CrashLoopBackOff`

Memory limits must be set with enough headroom for the actual working set:

```yaml
resources:
  requests:
    memory: "512Mi"    # guaranteed working set
  limits:
    memory: "1Gi"      # 2× request — OOM kill if exceeded
```

**Java heap sizing with memory limits:**

JVM heap is a subset of total process memory. The JVM also uses off-heap memory for Metaspace, thread stacks, JIT compilation, and native memory. A JVM container configured for 512 MB heap will use ~750 MB total memory. If the memory limit is 512 MB, the container OOM-kills before the heap even fills.

```yaml
# Memory limit: 1Gi
# JVM heap: 75% of limit = 768 MB (leave 256 MB for off-heap)
env:
  - name: JAVA_OPTS
    value: "-Xms384m -Xmx768m -XX:MaxMetaspaceSize=128m -XX:+UseZGC"
# OR use container-aware heap sizing (Java 10+):
  - name: JAVA_OPTS
    value: "-XX:MaxRAMPercentage=75.0 -XX:+UseZGC"
# -XX:MaxRAMPercentage=75.0 → JVM reads container memory limit and uses 75% as max heap
```

`-XX:MaxRAMPercentage=75.0` is the recommended approach. The JVM reads the container's cgroup memory limit (which reflects the Kubernetes limit), computes 75% of it, and uses that as the max heap. When the Kubernetes memory limit changes (e.g., VPA recommendation), the JVM adapts automatically without changing the JVM flags.

## QoS Classes — What Happens Under Pressure

When a node runs out of memory, the kubelet must evict pods to free resources. QoS (Quality of Service) class determines eviction priority.

### BestEffort — No requests or limits set

```yaml
containers:
  - name: myapp
    image: myapp:latest
    # No resources block at all
```

These pods have no scheduling guarantees. They are the first to be evicted under memory pressure. **Pravah never runs production services as BestEffort.**

### Burstable — Requests set, but limits > requests (or limits omitted)

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2000m"
    memory: "1Gi"
```

Most Pravah services are Burstable. They have guaranteed scheduling weight (requests) and can burst to limits under load. Under memory pressure, they are evicted after Guaranteed pods.

### Guaranteed — Requests == Limits

```yaml
resources:
  requests:
    cpu: "1000m"
    memory: "2Gi"
  limits:
    cpu: "1000m"
    memory: "2Gi"
```

The kubelet reserves exactly what was requested and never evicts Guaranteed pods under normal memory pressure. The tradeoff: no bursting. A Guaranteed pod running at 900m CPU in a 1000m limit simply cannot burst — it is throttled at the limit even if the node has spare capacity.

**Pravah's QoS strategy:**
- **Stateful infrastructure (PostgreSQL, Kafka, Redis):** Guaranteed or near-Guaranteed. These must not be evicted. High-variance OOM kills on a database primary causes data loss scenarios.
- **Critical microservices (API Gateway, Execution Service):** Burstable with 2× memory headroom. They can burst during load spikes but are evicted before stateful components.
- **Background workers, DaemonSets:** Burstable with minimal requests. Evictable under pressure.

## LimitRange — Namespace-Level Defaults

LimitRange sets default requests and limits for pods that don't specify them, and enforces min/max bounds.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: pravah-limit-range
  namespace: pravah
spec:
  limits:
    # Container-level limits
    - type: Container
      defaultRequest:
        cpu: "200m"
        memory: "256Mi"
      default:            # default limit (applied when limit not specified)
        cpu: "1000m"
        memory: "512Mi"
      min:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "8000m"      # no container can request more than 8 CPU cores
        memory: "8Gi"     # no container can request more than 8 GB

    # Pod-level limits
    - type: Pod
      max:
        cpu: "16000m"     # total across all containers in a pod
        memory: "16Gi"

    # PersistentVolumeClaim limits
    - type: PersistentVolumeClaim
      max:
        storage: "1Ti"    # no PVC larger than 1 TB
      min:
        storage: "1Gi"
```

When a pod is created without a resource section, LimitRange applies the defaults. This prevents "BestEffort" pods from accidentally being deployed — every pod gets at least the default request and limit.

When a pod requests resources outside the min/max bounds, the admission webhook rejects it with a clear error message.

## ResourceQuota — Namespace Budget

ResourceQuota enforces aggregate resource limits across the entire namespace. Even if individual pods are within LimitRange bounds, the total namespace cannot exceed the quota.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: pravah-quota
  namespace: pravah
spec:
  hard:
    # Compute resources
    requests.cpu: "50"        # namespace can request at most 50 CPU cores
    requests.memory: "100Gi"  # namespace can request at most 100 GB
    limits.cpu: "200"         # namespace limits cannot exceed 200 CPU
    limits.memory: "200Gi"

    # Object count limits
    pods: "200"               # at most 200 pods
    services: "50"
    persistentvolumeclaims: "30"
    configmaps: "100"
    secrets: "100"

    # Count limits by resource type
    count/deployments.apps: "30"
    count/statefulsets.apps: "10"
```

ResourceQuota prevents a runaway deployment (infinite HPA scale-up, misconfigured KEDA) from consuming all cluster resources. When the namespace hits its CPU quota, new pod creation fails with a clear error — cluster-wide operations from other namespaces continue normally.

**Tenant resource quotas:** for large enterprise tenants with dedicated Kubernetes namespaces (the silo model from 5.6), ResourceQuota enforces their service tier limits:

```yaml
# Enterprise tenant silo namespace — dedicated resource budget
apiVersion: v1
kind: ResourceQuota
metadata:
  name: tenant-megacorp-quota
  namespace: pravah-tenant-megacorp
spec:
  hard:
    requests.cpu: "20"
    requests.memory: "40Gi"
    pods: "100"
```

## Priority Classes — Scheduling Priority and Eviction Order

PriorityClass assigns a priority value to pods. Higher priority pods are scheduled first when resources are constrained. Under node pressure, lower priority pods are preempted to make room for higher priority ones.

```yaml
# Platform-critical components — highest priority
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: pravah-critical
value: 1000000
globalDefault: false
description: "Platform-critical: PostgreSQL, Kafka, Vault"

---
# Core services — high priority
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: pravah-high
value: 100000
description: "Core services: API Gateway, Execution Service"

---
# Background workers — normal priority
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: pravah-normal
value: 10000
description: "Background: Cloud runners, Notification Service"
```

Usage in pod spec:

```yaml
spec:
  priorityClassName: pravah-critical    # PostgreSQL pods
  # or
  priorityClassName: pravah-high        # Execution Service pods
```

Under node pressure: `pravah-normal` pods are preempted first to free resources for `pravah-critical` components. PostgreSQL is never preempted while a cloud runner pod is running.

## FAANG Interview Angles

**"What is the difference between CPU requests and CPU limits in Kubernetes, and what is CPU throttling?"**

> CPU requests are used by the scheduler to decide which node a pod fits on — a 500m request means the scheduler will only place the pod on a node with at least 500m of remaining schedulable capacity. Requests do not restrict actual CPU usage during runtime; the pod can use more CPU than its request if the node has spare capacity.
>
> CPU limits are enforced by the Linux kernel's CFS scheduler. When a container exceeds its CPU limit, it is throttled — put to sleep for the remainder of the current 100ms scheduling period. This manifests as latency spikes: a request that would normally complete in 50ms is held for an additional 40–80ms waiting for the throttle window to end.
>
> The throttling trap: setting a CPU limit of 500m (0.5 cores) on a Java service that normally runs at 100m CPU but occasionally spikes to 1200m (GC cycles, JIT compilation bursts). The spikes trigger throttling, adding 50–100ms to tail latency. The fix: either increase the limit (2000m gives plenty of headroom), or remove the CPU limit and rely on the request for scheduling guarantees. Pravah sets limits at 4× the request to accommodate burst while providing some protection against runaway processes.

**"How do Kubernetes QoS classes affect pod eviction under node memory pressure?"**

> When a node runs low on memory, the kubelet must evict pods to prevent OOM kills at the node level. The eviction order is determined by QoS class and actual usage vs request.
>
> BestEffort pods — those with no resource requests or limits — are evicted first. They made no resource promises and the scheduler gave them no guarantees. Burstable pods — those using more memory than their request — are evicted next, starting with those furthest above their request. Guaranteed pods — those with request == limit — are evicted last, and only when there is no BestEffort or Burstable pod remaining.
>
> Pravah's stateful components (PostgreSQL, Kafka) have high memory requests relative to their actual usage. This means they are deep in the Burstable tier — rarely targeted for eviction because many other pods are further above their requests. The critical microservices have memory limits at 2× their request, keeping their excess usage below the threshold that triggers early eviction. Database pods with near-Guaranteed configuration almost never get evicted in practice.

## Key Takeaways

1. **Requests = scheduling currency.** Kubernetes schedules based on requests. Actual runtime usage can exceed requests if the node has spare capacity. Setting requests too low → over-scheduled nodes. Setting too high → wasted capacity and poor autoscaler decisions.

2. **CPU limits cause throttling, not OOM.** Container exceeding CPU limit → kernel throttles → latency spikes. Set limits at 4× request to accommodate bursts. Monitor `container_cpu_cfs_throttled_seconds_total`.

3. **Memory limits cause OOM kills.** Container exceeding memory limit → immediate process termination. Set limits with sufficient headroom for the actual working set. Java: use `-XX:MaxRAMPercentage=75.0` to set heap relative to container limit.

4. **QoS classes determine eviction priority:** BestEffort (no requests/limits) → Burstable (limits > requests) → Guaranteed (limits == requests). Pravah never uses BestEffort. Critical databases use near-Guaranteed values.

5. **LimitRange enforces namespace defaults.** No pod can slip through as BestEffort by omitting the resources block. LimitRange applies defaults and enforces min/max bounds per container.

6. **ResourceQuota bounds namespace totals.** Prevents runaway HPA/KEDA scale-up from consuming all cluster resources. Enforces service tier limits for dedicated tenant namespaces.

7. **PriorityClass controls scheduling priority and preemption.** PostgreSQL and Kafka: `pravah-critical`. Core services: `pravah-high`. Cloud runners: `pravah-normal`. Under pressure, normal pods are preempted before high-priority pods.

8. **JVM heap sizing.** `-XX:MaxRAMPercentage=75.0` makes the JVM adapt to the container memory limit. Target 75% heap / 25% off-heap. Memory limit = heap + off-heap + OS overhead (not just heap).
