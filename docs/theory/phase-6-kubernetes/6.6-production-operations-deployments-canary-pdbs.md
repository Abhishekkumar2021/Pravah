# 6.6 Production Operations — Deployments, Canary & PDBs

## The Core Goal of Production Deployments

Every production deployment of a new version has one invariant: users must not experience downtime or degradation because of the deployment itself. If the new version has a bug, users should see the bug — but the process of deploying should not introduce failures that would not have occurred had the old version stayed running.

This requires:
1. **Traffic continuity** during the rollout (old pods serving traffic until new pods are ready)
2. **Automatic rollback** if the new version is broken (health checks catching the problem)
3. **Controlled blast radius** (new version only affects a subset of traffic initially)
4. **Disruption protection** during planned maintenance (PodDisruptionBudgets)

## Rolling Updates — The Default Strategy

Kubernetes Deployment rolling updates replace pods incrementally. With `maxUnavailable: 0, maxSurge: 1`:

```
Start: 3 pods running version 1.4.2

Step 1: Create pod[4] running v1.4.3 (surge)
  Running: pod[1], pod[2], pod[3] (v1.4.2) + pod[4] (v1.4.3, starting)
  pod[4] starts, runs init containers, passes startup probe

Step 2: pod[4] passes readiness probe
  Traffic: pod[1], pod[2], pod[3], pod[4] (all receiving traffic)
  Now safe to remove an old pod

Step 3: Terminate pod[1] (v1.4.2)
  Running: pod[2], pod[3] (v1.4.2) + pod[4] (v1.4.3)
  pod[1] receives preStop hook → 15s sleep → SIGTERM → drains → terminates

Step 4: Create pod[5] running v1.4.3
  pod[5] starts, passes startup + readiness probes

Step 5: Terminate pod[2] (v1.4.2)
  Running: pod[3] (v1.4.2) + pod[4], pod[5] (v1.4.3)

Step 6: Create pod[6] running v1.4.3

Step 7: Terminate pod[3] (v1.4.2)
  Running: pod[4], pod[5], pod[6] (all v1.4.3)

Rollout complete. 3 replicas, all on v1.4.3. Zero downtime.
```

**What happens if a new pod fails its readiness probe?**

Kubernetes stops the rollout. It does not terminate any more old pods. It does not create more new pods (beyond the current `maxSurge`). The deployment enters a stuck state:

```bash
kubectl rollout status deployment/execution-service -n pravah
# Waiting for deployment "execution-service" rollout to finish:
# 1 out of 3 new replicas have been updated...

kubectl describe deployment execution-service -n pravah
# Conditions:
#   Progressing: True (reason: ReplicaSetUpdated)
#   Available:   True (reason: MinimumReplicasAvailable)
#   ReplicaSet: execution-service-7b4d9f (new, 1/3 ready)
```

Old pods are still running and serving traffic. The system is degraded (4 pods instead of 3, one new pod cycling) but not down. The rollout is paused until the readiness issue is resolved or a rollback is initiated.

### Deployment Progress Deadline

Kubernetes will wait indefinitely for a readiness probe by default. Configure a progress deadline:

```yaml
spec:
  progressDeadlineSeconds: 600    # fail the rollout if not complete within 10 minutes
```

If the rollout is still in progress after 600 seconds, Kubernetes marks the Deployment as degraded and the rollout status shows `Progressing: False` with reason `ProgressDeadlineExceeded`. Argo CD will then report the Application as degraded, triggering an alert.

## Canary Deployments with Argo Rollouts

Rolling updates are all-or-nothing — you shift 100% of traffic to the new version (gradually, but eventually). Canary deployments shift a fraction of traffic to the new version initially, monitor it, and promote to 100% only if metrics are healthy.

### Why Canary

A rolling update that moves 100% of traffic to a broken version will fail fast (health checks catch it). But some bugs only appear under specific conditions — a race condition that manifests at 1% frequency, a bug in a specific code path that only triggers for 5% of users. A rolling update delivers these bugs to all users. A canary delivers them to 5% of users — you observe the impact before promoting.

### Argo Rollouts — Canary Strategy

Argo Rollouts extends Kubernetes with a `Rollout` resource that supports canary and blue-green strategies. It replaces the standard `Deployment` for services where you want progressive delivery.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: execution-service
  namespace: pravah
spec:
  replicas: 10    # total replicas (stable + canary)

  selector:
    matchLabels:
      app: execution-service

  template:
    # Same pod template as a Deployment
    metadata:
      labels:
        app: execution-service
    spec:
      containers:
        - name: execution-service
          image: pravah/execution-service:1.4.3
          # ... rest of pod spec ...

  strategy:
    canary:
      # Step 1: shift 5% of traffic to canary
      # Step 2: wait 5 minutes, evaluate metrics
      # Step 3: if healthy, shift 25%
      # Step 4: wait 10 minutes
      # Step 5: if healthy, promote 100%
      steps:
        - setWeight: 5          # 5% of traffic to canary
        - pause: {duration: 5m} # observe for 5 minutes
        - setWeight: 25
        - pause: {duration: 10m}
        - setWeight: 50
        - pause: {duration: 5m}
        - setWeight: 75
        - pause: {}             # manual gate — requires explicit promotion or can auto-promote

      # Automatic analysis: query Prometheus and abort if metrics degrade
      analysis:
        templates:
          - templateName: job-success-rate-analysis
        startingStep: 1
        args:
          - name: service
            value: execution-service

  minReadySeconds: 30    # wait 30s after readiness before marking pod ready for rollout
```

### Analysis Template — Automated Canary Evaluation

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: job-success-rate-analysis
  namespace: pravah
spec:
  args:
    - name: service

  metrics:
    # Metric 1: Job success rate must not drop more than 1% from baseline
    - name: job-success-rate
      interval: 1m          # check every minute
      consecutiveErrorLimit: 3
      successCondition: result[0] >= 0.99    # must be >= 99%
      failureLimit: 2       # allow 2 failures before aborting rollout
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            sum(rate(pravah_job_completed_total{status="SUCCESS",
                service="{{ args.service }}"}[5m]))
            /
            sum(rate(pravah_job_completed_total{service="{{ args.service }}"}[5m]))

    # Metric 2: API error rate must not exceed 1%
    - name: api-error-rate
      interval: 1m
      successCondition: result[0] <= 0.01    # must be <= 1% error rate
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            sum(rate(http_server_requests_seconds_count{
              status=~"5..", service="{{ args.service }}"}[5m]))
            /
            sum(rate(http_server_requests_seconds_count{
              service="{{ args.service }}"}[5m]))

    # Metric 3: p99 latency must not increase more than 50% above baseline
    - name: dispatch-latency
      interval: 2m
      successCondition: result[0] <= 15      # <= 15s p99 (baseline is ~3s, 5× as limit)
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            histogram_quantile(0.99,
              sum(rate(pravah_job_dispatch_duration_seconds_bucket{
                service="{{ args.service }}"}[5m])) by (le))
```

**Automatic rollback on analysis failure:**

If any metric fails more than `failureLimit` times consecutively, Argo Rollouts automatically aborts the rollout and rolls back to the stable version. No human action required. The canary pods are replaced with stable pods.

### Traffic Splitting with the NGINX Ingress

Argo Rollouts integrates with NGINX Ingress for traffic splitting. It creates two Services — stable and canary — and configures the Ingress to split traffic:

```yaml
strategy:
  canary:
    canaryService: execution-service-canary    # service pointing to canary pods
    stableService: execution-service           # service pointing to stable pods
    trafficRouting:
      nginx:
        stableIngress: pravah-api-ingress
        annotationPrefix: nginx.ingress.kubernetes.io
```

At `setWeight: 5`, the Ingress annotation is updated:
```
nginx.ingress.kubernetes.io/canary: "true"
nginx.ingress.kubernetes.io/canary-weight: "5"
```

5% of requests go to canary pods, 95% to stable pods. This is a genuine traffic split — not just reducing the number of canary pods and relying on probabilistic distribution.

## PodDisruptionBudget — Protecting Availability During Disruptions

Planned disruptions happen constantly in production: node upgrades, cluster scaling events, zone evacuations, certificate rotations, hardware maintenance. The kubelet drains nodes for these operations — terminating pods in a controlled manner.

Without a PDB, draining a node with all three Execution Service replicas would terminate all three simultaneously, causing a complete service outage.

A PodDisruptionBudget (PDB) is a commitment from Kubernetes: "when draining or performing voluntary disruptions, never make this service completely unavailable."

### PDB Configuration

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: execution-service-pdb
  namespace: pravah
spec:
  selector:
    matchLabels:
      app: execution-service

  # At any time, at least 2 pods must be available
  minAvailable: 2

  # Alternative: at most 1 pod can be unavailable at a time
  # maxUnavailable: 1
```

**`minAvailable: 2` with 3 replicas:**

When a node drain attempts to evict Execution Service pods:
```
Drain node-1 (has pod[1]):
  PDB check: currently 3 pods. Evicting pod[1] → 2 remaining. 2 ≥ minAvailable:2 ✅
  → pod[1] evicted, reschedules on another node

Drain node-2 (has pod[2]), while pod[1] is still rescheduling:
  PDB check: currently 2 pods (pod[2], pod[3]). Evicting pod[2] → 1 remaining. 1 < minAvailable:2 ❌
  → node drain BLOCKS on pod[2]. Waits for pod[1] to reschedule and become ready.
  → Once pod[1] is ready (3 pods again), pod[2] can be evicted.
```

The drain is forced to proceed one pod at a time, maintaining minimum availability at all costs.

**Percentage-based PDB:**

```yaml
spec:
  # At least 75% of pods must be available during disruption
  # Better for deployments that autoscale — 75% scales with replica count
  minAvailable: "75%"
```

For a service with `minReplicas: 3` and `maxReplicas: 20`, `minAvailable: "75%"` means:
- At 3 replicas: at least 3 × 0.75 = 2.25 → 3 pods available (rounds up — very restrictive)
- At 20 replicas: at least 20 × 0.75 = 15 pods available

### PDB for Stateful Components

Stateful components need stronger protection. Taking two Kafka brokers offline simultaneously during a rebalance could cause data loss:

```yaml
# Kafka: never take more than 1 broker offline at a time
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: kafka-pdb
  namespace: pravah
spec:
  selector:
    matchLabels:
      app: kafka
  maxUnavailable: 1    # at most 1 broker offline during drain
```

```yaml
# PostgreSQL: never take the primary offline involuntarily
# (Patroni handles planned failover; PDB prevents involuntary loss)
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: postgres-pdb
  namespace: pravah
spec:
  selector:
    matchLabels:
      app: postgres
  maxUnavailable: 1
```

## Blue-Green Deployments — When Rolling Updates Are Not Enough

Some deployments cannot be done as rolling updates:
- **Breaking database schema changes:** adding a NOT NULL column that old pods cannot handle
- **Breaking API changes:** v1 and v2 pods cannot serve the same traffic without errors
- **State machine changes:** old and new pods have incompatible in-memory state representations

Blue-green runs two complete environments simultaneously (blue = current, green = new). When green is validated, traffic is switched atomically.

```
Blue (v1.4.2): 3 pods, all production traffic
Green (v1.4.3): 3 pods, no production traffic (being validated)

Validation:
  Run integration tests against green
  Run canary analysis against green with test traffic
  Check that green can handle existing database state

Switch:
  Update the Kubernetes Service selector from app=execution-service,version=1.4.2
  to app=execution-service,version=1.4.3
  → All traffic instantly switches to green

Teardown:
  Keep blue running for 15 minutes (quick rollback if needed)
  Scale blue to 0 after green is confirmed healthy
  → Blue resources remain for rollback capability
```

Blue-green is more expensive (2× pod count during switchover) and requires the new version to be fully tested before any production traffic. It is appropriate for breaking changes but overkill for routine deployments.

Pravah uses blue-green for database schema migration releases and rolling updates for all routine service version updates.

## The Deployment Runbook

Every production deployment follows the same checklist. Automation (Argo CD + Argo Rollouts) handles most steps, but the runbook defines what humans verify.

```markdown
## Pre-Deployment (30 minutes before)

- [ ] Verify staging deployment of same version is healthy (24+ hours running)
- [ ] Check error budget status: >20% remaining? (if <20%, deployment freeze applies)
- [ ] Review `helm diff` output — confirm only expected changes
- [ ] Check no active incidents or elevated error rates
- [ ] Post in #pravah-deployments: "Deploying execution-service 1.4.3 in 30 minutes"
- [ ] Ensure rollback plan is documented (which revision to roll back to)

## Deployment

- [ ] Merge PR to main → Argo CD detects change
- [ ] Verify Argo CD starts sync (within 3 minutes of merge)
- [ ] Watch rollout progress: `kubectl rollout status rollout/execution-service -n pravah`
- [ ] Monitor SLO dashboards during rollout:
      - Job success rate (must stay ≥ 99.5%)
      - API error rate (must stay ≤ 0.1%)
      - Job dispatch p99 (must stay ≤ 10s)
- [ ] Verify canary analysis is healthy (if using Argo Rollouts)

## Post-Deployment (30 minutes after)

- [ ] Confirm all pods are running new version
- [ ] Confirm no new error patterns in Kibana
- [ ] Confirm metrics are at or better than pre-deployment baseline
- [ ] Verify error budget has not materially decreased
- [ ] Post in #pravah-deployments: "execution-service 1.4.3 deployed ✅"

## Rollback Trigger Conditions

Trigger immediate rollback if any of the following:
  - Job success rate drops below 99%
  - API error rate exceeds 1% for 5 minutes
  - Any new CRITICAL alert fires within 30 minutes of deployment
  - Error budget burn rate exceeds 10× for 15 minutes

Rollback command:
  helm rollback execution-service -n pravah      (previous revision)
  OR
  kubectl argo rollouts abort execution-service -n pravah  (for Argo Rollouts)
```

## FAANG Interview Angles

**"What is the difference between a rolling update and a canary deployment in Kubernetes?"**

> A rolling update gradually replaces old pods with new pods — but once started, it moves 100% of traffic to the new version (just incrementally). The safety mechanism is the readiness probe: if the new pod doesn't pass readiness, the rollout stops, preserving old pods. But if the new version passes readiness and has a subtle functional bug, 100% of traffic eventually hits it.
>
> A canary deployment routes a fraction of traffic — say, 5% — to the new version and monitors it against real production metrics. Only if the canary is healthy does traffic progressively increase. A functional bug that only affects 1% of requests would be visible in the 5% canary slice (amplified by sampling), allowing abort before it affects all users.
>
> Canary is implemented via Argo Rollouts in Pravah. The strategy defines steps: shift 5% of traffic, observe for 5 minutes, shift 25%, observe 10 minutes, promote. Each step runs automated metric analysis via Prometheus queries. If job success rate or API error rate degrades during any step, Argo Rollouts automatically rolls back to the stable version without human intervention.

**"How does a PodDisruptionBudget protect against node drains?"**

> When a node needs to be drained — for maintenance, upgrades, or scaling down — Kubernetes terminates pods on that node. Without a PDB, it might terminate all pods of a service simultaneously if they happen to be on the same node.
>
> A PDB declares a minimum availability constraint: `minAvailable: 2` means at any point during voluntary disruptions, at least 2 pods must be running and ready. The cluster drainer respects this: before evicting a pod, it checks whether doing so would violate the PDB. If it would, the eviction is blocked until sufficient other pods are available.
>
> The practical effect on a node drain: if all 3 Execution Service pods are on a node being drained, the drain evicts pod[1], waits for it to reschedule and become ready elsewhere (maintaining 3 available), then evicts pod[2], waits again, then pod[3]. The drain takes longer but the service is never fully offline. Without the PDB, all three might be evicted simultaneously, causing a complete service outage during a routine node upgrade.

## Key Takeaways

1. **Rolling updates with `maxUnavailable: 0, maxSurge: 1`** create new pods before removing old ones. Zero traffic interruption. Stalls automatically if new pods fail readiness.

2. **`progressDeadlineSeconds`** prevents indefinite stalls. If the rollout hasn't completed in N seconds, it's marked as failed — triggering alerts.

3. **Canary deployments via Argo Rollouts** send a fraction of traffic to the new version, evaluate Prometheus metrics at each step, and automatically roll back if analysis fails.

4. **Automated canary analysis** — AnalysisTemplate with Prometheus queries — removes human judgment from the promotion decision. Defined success conditions are evaluated at each step. Failure → automatic rollback.

5. **PodDisruptionBudget enforces minimum availability during voluntary disruptions.** Node drains, cluster upgrades, and zone evacuations are forced to proceed one pod at a time, maintaining minimum availability.

6. **Blue-green for breaking changes.** Run both versions simultaneously. Validate green thoroughly. Switch traffic atomically. Keep blue for rollback. More expensive (2× pods) but necessary for incompatible migrations.

7. **Deployment runbook is mandatory.** Pre-check error budget, review diff, monitor during rollout, verify post-deployment. Define rollback trigger conditions clearly. No surprises during incidents.

8. **GitOps closes the loop.** Helm chart in Git → Argo CD applies → Kubernetes rolls out → Argo Rollouts manages canary → Analysis templates evaluate → automatic promotion or rollback. Humans set the policy; automation executes it.
