# 6.3 Autoscaling — HPA, VPA & KEDA

## Why Static Replica Counts Fail

A pipeline platform has inherently variable load. Enterprise tenants run ETL jobs at 9 AM. Batch pipelines trigger at scheduled intervals throughout the day. Maintenance tasks run overnight. User-triggered pipeline tests can spike at any moment.

With static replica counts:
- **Over-provisioned for average load:** running 10 pods when 3 are sufficient during off-peak hours wastes compute cost
- **Under-provisioned for peak load:** 3 pods cannot handle the 9 AM burst — jobs queue, SLOs breach

Autoscaling adjusts pod counts (and resource allocations) based on observed demand. The goal: right-size the deployment at every moment — enough capacity to serve current load, not so much that you're paying for idle compute.

## HPA — Horizontal Pod Autoscaler

The HPA watches a deployment's metrics and adjusts the replica count to maintain a target metric value.

### CPU-Based HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: execution-service
  namespace: pravah
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: execution-service

  minReplicas: 3     # never go below 3 (HA requirement)
  maxReplicas: 20    # never exceed 20 (cost limit + database connection budget)

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # target: average CPU across all pods = 70%
```

**How the HPA algorithm works:**

```
desired_replicas = ceil(current_replicas × (current_metric / target_metric))

Example:
  current_replicas = 5
  current_avg_cpu  = 90%
  target_avg_cpu   = 70%

  desired = ceil(5 × (90 / 70)) = ceil(6.43) = 7

  → scale to 7 replicas
```

The HPA evaluates every 15 seconds (configurable with `--horizontal-pod-autoscaler-sync-period`). To prevent rapid oscillation ("thrashing"), it applies stabilization windows:
- Scale-up: no stabilization — acts immediately
- Scale-down: waits for the metric to be below target for 5 minutes (configurable) before reducing replicas

This asymmetry is intentional: scale up fast (don't wait while users are affected), scale down slowly (avoid destroying capacity that may be needed again in minutes).

### Multi-Metric HPA

Pravah's Execution Service should scale on both CPU (processing load) and a custom metric (active job queue depth):

```yaml
spec:
  metrics:
    # CPU-based scaling
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

    # Memory-based scaling — prevent OOM cascades
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

    # Custom metric: active jobs per pod
    # (from Prometheus via Prometheus Adapter)
    - type: Pods
      pods:
        metric:
          name: pravah_active_jobs_per_pod
        target:
          type: AverageValue
          averageValue: "50"    # target: 50 active jobs per pod

  # Scaling behavior configuration
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0      # scale up immediately
      policies:
        - type: Pods
          value: 4                        # add at most 4 pods per 60 seconds
          periodSeconds: 60
        - type: Percent
          value: 100                      # or double the pod count, whichever is larger
          periodSeconds: 60
      selectPolicy: Max

    scaleDown:
      stabilizationWindowSeconds: 300    # wait 5 minutes before scaling down
      policies:
        - type: Pods
          value: 2                        # remove at most 2 pods per 120 seconds
          periodSeconds: 120             # (gentle scale-down to avoid thrashing)
      selectPolicy: Min
```

When multiple metrics are defined, the HPA computes the desired replica count for each and takes the maximum. This ensures the deployment scales whenever any metric requires it.

### Custom Metrics via Prometheus Adapter

The Kubernetes metrics-server only exposes CPU and memory. Custom metrics (like `pravah_active_jobs_per_pod`) require the Prometheus Adapter, which bridges Prometheus metrics to the Kubernetes Custom Metrics API.

```yaml
# Prometheus Adapter rule — expose pravah_active_jobs_per_pod as a custom metric
rules:
  - seriesQuery: 'pravah_jobs_active{namespace!="", pod!=""}'
    resources:
      overrides:
        namespace:
          resource: namespace
        pod:
          resource: pod
    name:
      matches: "pravah_jobs_active"
      as: "pravah_active_jobs_per_pod"
    metricsQuery: |
      sum(pravah_jobs_active{<<.LabelMatchers>>}) by (<<.GroupBy>>)
      /
      count(pravah_jobs_active{<<.LabelMatchers>>}) by (<<.GroupBy>>)
```

## VPA — Vertical Pod Autoscaler

HPA scales out (more pods). VPA scales up (bigger pods — more CPU/memory per pod).

VPA analyzes actual resource usage over time and recommends (or automatically updates) resource requests. This solves a common problem: engineers guess resource requests at deployment time, and those guesses are often wrong — either too low (OOMs, throttling) or too high (wasted capacity).

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: execution-service-vpa
  namespace: pravah
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: execution-service

  updatePolicy:
    updateMode: "Off"   # Recommendation only — do NOT auto-apply
    # Options:
    # "Off"        → observe + recommend, never change pods
    # "Initial"    → set resources on new pods only (no running pod eviction)
    # "Recreate"   → evict pods to apply new recommendations (causes restarts)
    # "Auto"       → Recreate + will eventually support in-place update

  resourcePolicy:
    containerPolicies:
      - containerName: execution-service
        minAllowed:
          cpu: "200m"
          memory: "256Mi"
        maxAllowed:
          cpu: "4000m"
          memory: "4Gi"
        controlledResources: ["cpu", "memory"]
```

**Pravah's VPA usage:** `updateMode: "Off"` — observe and recommend only. VPA recommendations are reviewed during quarterly capacity planning reviews. They are not automatically applied because:

1. VPA in `Recreate` mode evicts pods to apply changes. This can violate PodDisruptionBudgets and cause temporary capacity reduction.
2. VPA and HPA conflict when both manage CPU: HPA scales horizontally based on CPU, VPA changes the CPU request (which affects what "70% utilization" means). Running both simultaneously on the same metric requires careful coordination.
3. Decisions about resource allocation should be deliberate, not automated.

VPA recommendations are read periodically:

```bash
kubectl describe vpa execution-service-vpa -n pravah
# ...
# Recommendation:
#   Container Recommendations:
#     Container Name:  execution-service
#     Lower Bound:
#       Cpu:     100m
#       Memory:  256Mi
#     Target:
#       Cpu:     350m        ← what VPA recommends for current workload
#       Memory:  600Mi
#     Uncapped Target:
#       Cpu:     350m
#       Memory:  600Mi
#     Upper Bound:
#       Cpu:     2000m
#       Memory:  1500Mi
```

If the current request is `cpu: 500m` but VPA recommends `cpu: 350m`, we are over-provisioning CPU. The recommendation informs a PR to update `values-production.yaml`.

## KEDA — Kubernetes Event-Driven Autoscaler

HPA scales on CPU and memory — resource-based metrics. KEDA scales on event-driven metrics: Kafka consumer lag, SQS queue depth, Redis list length, database row count. This is the correct model for Pravah's job processing infrastructure.

### The Core Insight

When job submissions spike, the Kafka topic `job.assigned` accumulates consumer lag before CPU rises. CPU rises only after Execution Service consumers start processing messages. By the time HPA triggers on CPU, the queue has been growing for minutes — there is already a backlog.

KEDA scales on the cause (Kafka lag growing) rather than the effect (CPU rising). The scaler responds before users experience degradation.

### KEDA ScaledObject for Execution Service

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: execution-service-scaler
  namespace: pravah
spec:
  scaleTargetRef:
    name: execution-service

  minReplicaCount: 3       # never below 3 (HA)
  maxReplicaCount: 30      # upper bound

  # Cool-down: wait 5 minutes after lag drops before scaling down
  cooldownPeriod: 300

  # Scale-up: act within 30 seconds of lag appearing
  pollingInterval: 15      # check metrics every 15 seconds

  triggers:
    # Trigger 1: Scale on Kafka consumer lag for job.assigned topic
    - type: kafka
      metadata:
        bootstrapServers: "kafka.pravah.svc:9092"
        consumerGroup: "execution-service"
        topic: "job.assigned"
        lagThreshold: "100"      # target: <100 messages of lag per pod
        # With 3 pods and 1000 messages of lag: 1000/100 = 10 desired pods
        offsetResetPolicy: latest
      authenticationRef:
        name: keda-kafka-auth    # Kafka credentials for KEDA

    # Trigger 2: Scale on Kafka consumer lag for job.events (secondary)
    - type: kafka
      metadata:
        bootstrapServers: "kafka.pravah.svc:9092"
        consumerGroup: "execution-service"
        topic: "job.events"
        lagThreshold: "500"      # higher threshold — this topic is higher volume

    # Trigger 3: Scale on Prometheus metric (active job count)
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090
        metricName: pravah_jobs_active_total
        query: sum(pravah_jobs_active{service="execution-service"})
        threshold: "200"         # target: total active jobs across all pods < 200*replicas
```

**KEDA scaling calculation:**

```
lag_threshold per pod: 100 messages
current total lag on job.assigned: 1,800 messages
current pods: 5

desired = ceil(total_lag / lag_threshold) = ceil(1800 / 100) = 18

→ scale to 18 pods

As Execution Service pods process the backlog and lag drops:
lag = 500 messages (after 2 minutes)
desired = ceil(500 / 100) = 5 → but cooldown prevents scale-down for 5 minutes

lag = 80 messages (after 8 minutes)
desired = ceil(80 / 100) = 1 → but minReplicaCount = 3
final: 3 pods
```

### KEDA for Cloud Runner Scaling

Pravah's cloud runner fleet should scale based on jobs waiting for a runner:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: cloud-runner-scaler
  namespace: pravah
spec:
  scaleTargetRef:
    name: cloud-runner
  minReplicaCount: 2
  maxReplicaCount: 100
  cooldownPeriod: 120      # scale down faster for runners (2 minutes)

  triggers:
    # Scale based on jobs in PENDING state without a runner assignment
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090
        metricName: pravah_jobs_pending_without_runner
        query: |
          sum(pravah_jobs_active{status="PENDING",runner_id=""})
        threshold: "5"       # 1 new runner per 5 unassigned jobs
```

When jobs pile up waiting for runners, KEDA scales the cloud runner Deployment. New runner pods start, register with Runner Service via gRPC, and begin accepting jobs. This is event-driven infrastructure scaling — matching runner capacity to actual job demand.

### Scale to Zero

KEDA can scale a Deployment to zero replicas when there is no work:

```yaml
spec:
  minReplicaCount: 0    # allow scale to zero
  maxReplicaCount: 20

  # ScaledObject manages its own HPA internally
  # When triggered metric hits zero → scale to 0
  # When triggered metric rises → scale back up (startup latency applies)
```

For Pravah's cloud runners: scale to zero during overnight quiet periods. When a morning batch job arrives (Kafka lag appears on `job.assigned`), KEDA triggers scale-up. The first few jobs wait 30–60 seconds for runner pods to start, but this is acceptable for background batch jobs. Critical production jobs that cannot tolerate cold-start latency keep `minReplicaCount: 2`.

**`minReplicaCount: 0` with Execution Service would be inappropriate** — the service would not be available to accept incoming job triggers. Scale to zero is for background workers, not user-facing services.

## Interaction Between HPA and KEDA

KEDA creates and manages its own HPA under the hood. You should not create a separate HPA for the same Deployment that KEDA manages — they would conflict.

```
KEDA ScaledObject
  └── creates/manages → HPA (owned by KEDA)
      └── controls → Deployment replica count

❌ Do NOT create:
HPA (manually created)  ← conflicts with KEDA's HPA
```

If you need both event-driven scaling (KEDA) and CPU-based scaling (HPA), add the CPU metric as an additional trigger in the KEDA ScaledObject:

```yaml
triggers:
  - type: kafka
    metadata:
      lagThreshold: "100"
      # ...

  - type: cpu                # CPU trigger within KEDA
    metadata:
      type: Utilization
      value: "70"
```

KEDA computes desired replicas for each trigger and takes the maximum.

## Autoscaling vs PodDisruptionBudget Interaction

HPA/KEDA can scale down replicas. PDB limits how many pods can be unavailable simultaneously. These must be compatible.

```
Execution Service: minReplicas: 3, maxReplicas: 20
PDB: minAvailable: 2

HPA wants to scale down from 5 to 3 pods.
  Step 1: terminate pod 4 (5→4). PDB: 4 available ≥ 2. ✅
  Step 2: terminate pod 3 (4→3). PDB: 3 available ≥ 2. ✅
  Done.

HPA wants to scale down from 3 to 2 pods.
  Step 1: terminate pod 2 (3→2). PDB: 2 available ≥ 2. ✅
  But now minReplicas: 3 prevents further scale-down.
  → HPA stops at 3. PDB is not violated.

What if minReplicas: 3 and PDB minAvailable: 3?
  → PDB blocks any rollout or scale-down operation when at 3 replicas
  → Rolling updates would block forever
  → Set PDB minAvailable to replicas - 1 (allows 1 disruption)
```

Pravah's configuration: `minReplicas: 3`, `PDB minAvailable: 2`. One pod can be unavailable at any time — allowing rolling updates and scale-down operations to proceed.

## System Design Interview Angles

**"Why does Pravah use KEDA instead of (or in addition to) the default HPA for Execution Service?"**

> The default HPA scales on CPU and memory. CPU only rises after Execution Service is actively processing messages — which means the Kafka consumer has already been sitting on a backlog for some time. HPA is reactive to the effect of load, not the cause.
>
> KEDA scales on Kafka consumer lag — the actual queue depth. When a burst of jobs arrives, lag on `job.assigned` grows immediately. KEDA triggers scale-up within 15–30 seconds. New pods start consuming messages. The CPU spike never becomes a problem because we scaled before it peaked.
>
> The practical difference: with HPA-only, users submitting jobs during a burst see 2–3 minutes of elevated dispatch latency before HPA catches up. With KEDA, we typically catch the burst within 60 seconds (KEDA reaction: 15s + pod startup: 30–45s). The SLO for job dispatch p99 stays within bounds.

**"What is the conflict between VPA and HPA when applied to the same deployment?"**

> HPA scales the number of pods to maintain a target average CPU utilization. VPA changes the CPU request of each pod — which changes what "70% CPU utilization" means.
>
> Scenario: HPA targets 70% CPU. VPA increases the CPU request from 500m to 800m. Now each pod has more headroom, so actual utilization drops. HPA sees 45% CPU (below target) and scales down. Fewer, larger pods — but the total CPU capacity may not match the actual workload. Then workload increases, CPU rises, HPA scales up, VPA sees higher utilization and increases requests again — and the cycle can oscillate.
>
> The standard guidance: don't use both VPA and HPA on the same resource (CPU or memory) for the same deployment. You can use VPA in recommendation-only mode (Off) alongside HPA — VPA informs capacity planning without automating changes. Or use VPA for non-critical services that don't need horizontal scaling and HPA for services that scale horizontally.

## Key Takeaways

1. **HPA scales pods based on metrics.** Autoscaling/v2 supports CPU, memory, and custom metrics. Multi-metric HPA takes the maximum desired replicas across all metrics. Scale-up is immediate; scale-down has a 5-minute stabilization window to prevent thrashing.

2. **VPA right-sizes resource requests.** Analyzes actual usage over time, recommends better CPU/memory requests. Pravah uses `updateMode: "Off"` — recommendations only, not automatic eviction. Reviews inform capacity planning PRs.

3. **KEDA scales on event-driven metrics.** Kafka consumer lag, SQS queue depth, Prometheus queries. Scales on the cause (lag growing) rather than the effect (CPU rising). More responsive to burst patterns.

4. **KEDA replaces HPA for the targets it manages.** Never create both a standalone HPA and a KEDA ScaledObject for the same Deployment. KEDA creates and owns an HPA internally.

5. **Scale to zero for background workers.** Cloud runners can scale to 0 during quiet periods. User-facing services (Execution, API Gateway) must have `minReplicaCount ≥ 1` (typically ≥ 3 for HA).

6. **PDB and autoscaling must be compatible.** `PDB minAvailable` must be less than `minReplicas`. With `minReplicas: 3` and `PDB minAvailable: 3`, rolling updates would deadlock.

7. **KEDA for Pravah runners:** scale cloud runners based on `pravah_jobs_active{status="PENDING", runner_id=""}` — the count of jobs waiting for a runner. Each new runner pod handles ~5 jobs. Scale down after 2-minute cooldown.
