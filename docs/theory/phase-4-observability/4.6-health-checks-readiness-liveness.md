# 4.6 Health Checks, Readiness & Liveness Probes

## Why Probes Exist

Kubernetes manages pod lifecycle — starting pods, restarting failed pods, routing traffic. But Kubernetes cannot look inside a pod to determine if the application inside it is actually healthy. It needs the application to report its own health status.

Probes are the mechanism: Kubernetes periodically calls a probe endpoint on the pod, and based on the response, decides whether to route traffic to it, restart it, or leave it alone.

Without correctly designed probes:
- Kubernetes routes traffic to pods that started but haven't finished initialization (database migrations still running, connection pools not ready)
- Kubernetes continues routing traffic to pods that are alive but stuck (deadlocked thread, connection pool exhausted, all circuit breakers open)
- Kubernetes never restarts truly hung pods (the process is running but doing no useful work)
- Rolling deployments cause brief traffic drops because new pods receive traffic before they are ready

Good probes make Kubernetes self-healing. Bad probes make it self-destructive.

## Three Probe Types

### Liveness Probe — "Should This Pod Be Restarted?"

A liveness probe answers: is this process still able to do work? If the liveness probe fails, Kubernetes kills the pod and starts a new one.

Use case: detecting hung or deadlocked processes. A Java application's JVM might still be running (the process is alive), but all threads are deadlocked waiting on a database connection that will never be released. The application is alive but doing nothing useful. A liveness probe detects this and triggers a restart.

**What to check:** can the service respond to a trivial request at all? This should be lightweight — check that the HTTP server is responding, that the JVM is not deadlocked. Do not check external dependencies (if your database is down, restarting the pod doesn't fix the database).

**What NOT to check in liveness:** database connectivity, Kafka connectivity, Redis connectivity. If these fail and you restart the pod, you just keep restarting pods while the real problem (external dependency failure) remains. You end up in a crash loop that makes the situation worse.

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30    # wait for JVM startup before probing
  periodSeconds: 10          # probe every 10 seconds
  timeoutSeconds: 5          # probe must respond within 5s
  failureThreshold: 3        # restart after 3 consecutive failures (30s total)
  successThreshold: 1        # 1 success restores liveness
```

### Readiness Probe — "Should Traffic Be Sent to This Pod?"

A readiness probe answers: is this pod ready to handle requests right now? If the readiness probe fails, Kubernetes removes the pod from the Service endpoints — no new traffic is routed to it. The pod keeps running; it is just not receiving requests. When the probe succeeds again, the pod is re-added to endpoints.

Use cases:
1. During startup: pod is running but not yet ready (database migrations, cache warming, connection pool initializing)
2. During degradation: a circuit breaker opened because a downstream dependency is failing; this pod should not receive requests it cannot fulfill
3. During graceful shutdown: the pod received SIGTERM and is finishing in-flight requests; stop sending new ones

**What to check:** all critical dependencies this pod needs to serve requests successfully. For Execution Service: can it connect to PostgreSQL? Can it reach PgBouncer? Is its Kafka consumer group connected? If any of these are not ready, the pod should not receive traffic.

```yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5           # probe frequently — catch degradation quickly
  timeoutSeconds: 3
  failureThreshold: 3        # remove from rotation after 3 failures (15s)
  successThreshold: 2        # require 2 successes before restoring (10s)
```

### Startup Probe — "Has This Pod Finished Starting?"

A startup probe answers: has the application finished its initial startup? It is only active during the startup phase. Once the startup probe succeeds, Kubernetes switches to using liveness and readiness probes.

Without startup probes, you must choose between:
- Short `initialDelaySeconds` on liveness: fast detection of hung pods, but false restarts during slow startup
- Long `initialDelaySeconds` on liveness: accommodates slow startup, but hangs go undetected for a long time during normal operation

The startup probe eliminates this trade-off. It has a generous timeout for the initial boot sequence. Once it passes, liveness and readiness use aggressive intervals.

```yaml
startupProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 30       # 30 × 5s = 150s max startup time
  successThreshold: 1
```

With `failureThreshold: 30` and `periodSeconds: 5`, the startup probe gives the pod up to 150 seconds to start. Only after startup succeeds does liveness kick in with its aggressive 10-second interval.

## Spring Boot Actuator Health Configuration

Spring Boot Actuator provides built-in health indicators and separate endpoints for liveness and readiness.

```yaml
# application.yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus,info
  endpoint:
    health:
      show-details: always
      probes:
        enabled: true        # enables /actuator/health/liveness and /readiness
      group:
        liveness:
          include: livenessState   # built-in: is app context alive?
        readiness:
          include:
            - readinessState       # built-in: is app context ready?
            - db                   # checks all DataSource connections
            - kafka                # checks Kafka producer/consumer connectivity
            - redis                # checks Redis connectivity
```

**Liveness health response** (trivial check, always fast):
```json
GET /actuator/health/liveness
{
  "status": "UP",
  "components": {
    "livenessState": { "status": "UP" }
  }
}
```

**Readiness health response** (checks all dependencies):
```json
GET /actuator/health/readiness
{
  "status": "UP",
  "components": {
    "readinessState": { "status": "UP" },
    "db":    { "status": "UP", "details": { "database": "PostgreSQL", "validationQuery": "isValid()" } },
    "kafka": { "status": "UP", "details": { "bootstrapServers": "kafka:9092" } },
    "redis": { "status": "UP", "details": { "version": "7.0.8" } }
  }
}
```

If any dependency fails, the readiness status becomes `DOWN`:
```json
{
  "status": "DOWN",
  "components": {
    "readinessState": { "status": "UP" },
    "db":    { "status": "DOWN", "details": { "error": "Connection refused" } },
    "kafka": { "status": "UP" },
    "redis": { "status": "UP" }
  }
}
```

Kubernetes sees the `DOWN` response → removes the pod from Service endpoints → traffic stops routing to it. The pod keeps running, retrying the database connection. When it reconnects, readiness returns UP → pod re-added to rotation. All automatic, no human required.

## Custom Health Indicators for Pravah

Spring Boot's built-in indicators check connectivity (can we open a connection?). Pravah needs additional checks for application-level health.

### Execution Service: Circuit Breaker State

If the circuit breaker to Pipeline Service is open, Execution Service cannot validate pipeline configurations — it should not receive job dispatch requests.

```java
@Component
public class CircuitBreakerHealthIndicator implements HealthIndicator {

    private final CircuitBreakerRegistry circuitBreakerRegistry;

    @Override
    public Health health() {
        CircuitBreaker pipelineServiceCb = circuitBreakerRegistry
            .circuitBreaker("pipeline-service");

        CircuitBreaker.State state = pipelineServiceCb.getState();

        if (state == CircuitBreaker.State.OPEN) {
            return Health.down()
                .withDetail("circuit_breaker", "pipeline-service")
                .withDetail("state", "OPEN")
                .withDetail("failure_rate", pipelineServiceCb.getMetrics().getFailureRate())
                .build();
        }

        return Health.up()
            .withDetail("circuit_breaker", "pipeline-service")
            .withDetail("state", state.name())
            .build();
    }
}
```

Register this indicator in the readiness group:
```yaml
management:
  endpoint:
    health:
      group:
        readiness:
          include: readinessState, db, kafka, redis, circuitBreaker
```

Now when Pipeline Service is down and the circuit breaker opens, Execution Service pods become not-ready automatically. Load balancer removes them from rotation. Once Pipeline Service recovers and the circuit breaker transitions to half-open and then closed, pods become ready again.

### Runner Service: Minimum Active Runners

If Runner Service cannot maintain at least N active runners, it is degraded:

```java
@Component
public class RunnerFleetHealthIndicator implements HealthIndicator {

    private final RunnerRepository runnerRepository;
    private static final int MINIMUM_ACTIVE_RUNNERS = 3;

    @Override
    public Health health() {
        long activeRunners = runnerRepository.countByStatus("ACTIVE");

        if (activeRunners < MINIMUM_ACTIVE_RUNNERS) {
            return Health.down()
                .withDetail("active_runners", activeRunners)
                .withDetail("minimum_required", MINIMUM_ACTIVE_RUNNERS)
                .withDetail("message", "Insufficient runners to process jobs")
                .build();
        }

        return Health.up()
            .withDetail("active_runners", activeRunners)
            .build();
    }
}
```

### Outbox Relay: Queue Depth Check

If the outbox relay falls too far behind, it is a sign of a problem that should block readiness:

```java
@Component
public class OutboxHealthIndicator implements HealthIndicator {

    private final OutboxRepository outboxRepository;
    private static final int MAX_PENDING_MESSAGES = 10000;

    @Override
    public Health health() {
        long pendingCount = outboxRepository.countByStatus("PENDING");

        if (pendingCount > MAX_PENDING_MESSAGES) {
            return Health.down()
                .withDetail("pending_messages", pendingCount)
                .withDetail("threshold", MAX_PENDING_MESSAGES)
                .build();
        }

        return Health.up()
            .withDetail("pending_messages", pendingCount)
            .build();
    }
}
```

## Probe Design Pitfalls

### Pitfall 1: Liveness Checks External Dependencies

```yaml
# ❌ Wrong: liveness checks database connectivity
livenessProbe:
  httpGet:
    path: /actuator/health    # includes db, kafka, redis checks
    port: 8080
```

When the database goes down: all pods fail liveness → all pods restart → pods come up, database still down → all pods fail liveness again → crash loop. The database outage becomes a pod restart storm that makes recovery harder.

```yaml
# ✅ Correct: liveness only checks internal application state
livenessProbe:
  httpGet:
    path: /actuator/health/liveness    # only livenessState
    port: 8080
```

### Pitfall 2: Readiness Probe Too Strict

If readiness checks dependencies that have intermittent transient failures (Redis BLIP of 500ms), the pod flaps in and out of rotation rapidly. Every 500ms Redis blip → pod becomes not-ready → traffic redirected → load spike on other pods → those pods may also fail readiness → cascading failure.

Mitigation: `failureThreshold: 3` with `periodSeconds: 5` means the pod must fail for 15 seconds before being removed from rotation. A 500ms Redis blip doesn't trigger 3 consecutive failures at 5-second intervals.

```yaml
readinessProbe:
  failureThreshold: 3    # must fail for 15 seconds (3 × 5s) before removal
  successThreshold: 2    # must succeed twice (10s) before being added back
  periodSeconds: 5
```

### Pitfall 3: Missing Startup Probe for Slow-Starting Services

Execution Service runs Flyway database migrations on startup. For a large migration (adding an index on a 50M row table): migration takes 2 minutes. Without a startup probe, the liveness probe starts after `initialDelaySeconds: 30`, the migration is still running, the probe fails, Kubernetes restarts the pod, migration runs again, infinite restart loop.

```yaml
# All slow-starting services must have startupProbe
startupProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  failureThreshold: 60    # 60 × 5s = 5 minutes for migrations + startup
  periodSeconds: 5
```

### Pitfall 4: Health Check Causes Cascading Load

If 50 pods each probe `/actuator/health/readiness` every 5 seconds, and readiness checks run a `SELECT COUNT(*)` on the database: 50 pods × 12 probes/minute = 600 database queries per minute from health checks alone.

```java
// ❌ Wrong: health check queries the database on every probe
@Override
public Health health() {
    long count = jobRepository.count();   // SELECT COUNT(*) every 5 seconds
    return Health.up().withDetail("job_count", count).build();
}

// ✅ Correct: health check validates connectivity, not data
@Override
public Health health() {
    // Tests that a connection can be acquired and a trivial query succeeds
    // Spring's DataSourceHealthIndicator does this with SELECT 1 already
    return Health.up().build();
}
```

Spring Boot's built-in `db` health indicator uses `SELECT 1` or the configured `spring.datasource.hikari.connection-test-query` — lightweight by design.

## Graceful Shutdown — The Readiness Probe Integration

When Kubernetes decides to terminate a pod (scale down, rolling deployment), it sends SIGTERM. The pod should:
1. Immediately mark itself not-ready (stop receiving new traffic)
2. Finish processing in-flight requests
3. Exit cleanly

Spring Boot 2.3+ supports graceful shutdown:

```yaml
server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # wait up to 30s for in-flight requests
```

When SIGTERM is received, Spring Boot:
1. Sets the readiness state to `REFUSING_TRAFFIC` → readiness probe returns DOWN → Kubernetes removes pod from endpoints
2. Waits for in-flight requests to complete (up to 30 seconds)
3. Closes connections and shuts down

Kubernetes must be configured to wait before sending SIGKILL:

```yaml
spec:
  containers:
    - name: execution-service
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]   # give K8s endpoints time to propagate
  terminationGracePeriodSeconds: 60              # total time before SIGKILL
```

The `preStop` sleep ensures the pod is removed from load balancer endpoints before it stops accepting connections. Without it, there is a brief window where the load balancer still routes traffic to a pod that has started shutting down.

## Complete Probe Configuration for Pravah Services

```yaml
# Kubernetes Deployment spec — Execution Service
spec:
  containers:
    - name: execution-service
      image: pravah/execution-service:1.4.2

      ports:
        - containerPort: 8080
          name: http
        - containerPort: 8081
          name: management    # actuator on separate port (never exposed externally)

      # Startup probe: generous timeout for migrations
      startupProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8081
        initialDelaySeconds: 15
        periodSeconds: 5
        failureThreshold: 36    # 36 × 5s = 3 minutes maximum startup
        successThreshold: 1

      # Liveness probe: only internal state — never external deps
      livenessProbe:
        httpGet:
          path: /actuator/health/liveness
          port: 8081
        periodSeconds: 10
        timeoutSeconds: 5
        failureThreshold: 3     # restart after 30 seconds of failure
        successThreshold: 1

      # Readiness probe: all dependencies must be healthy
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8081
        periodSeconds: 5
        timeoutSeconds: 3
        failureThreshold: 3     # remove from rotation after 15 seconds
        successThreshold: 2     # restore after 10 seconds of success

      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 15"]

  terminationGracePeriodSeconds: 60
```

## System Design Interview Angles

**"What is the difference between liveness and readiness probes, and what should each check?"**

> Liveness answers "should this pod be restarted?" — it detects hung or deadlocked processes where the JVM is running but doing no useful work. Readiness answers "should traffic be sent to this pod?" — it detects when a pod is not yet ready or is temporarily degraded.
>
> The critical design rule: liveness must only check internal application state. Never check external dependencies in liveness. If your database is down and liveness checks DB connectivity, all pods fail liveness → all pods restart → pods come up, database still down → restart loop. The database outage becomes a cascading crash storm.
>
> Readiness should check all dependencies the pod needs to serve requests. If PostgreSQL is unreachable, the pod cannot handle job dispatch requests — it should not receive traffic. Kubernetes removes it from the Service endpoints automatically when readiness fails, and adds it back when readiness recovers.

**"How do you handle a slow-starting service with database migrations in Kubernetes?"**

> The startup probe. Without it, you choose between `initialDelaySeconds` that's too short (liveness fires during migrations → restart loop) or too long (hangs go undetected for a long time during normal operation).
>
> The startup probe has a generous `failureThreshold` — for Execution Service with potentially large migrations, `failureThreshold: 36` and `periodSeconds: 5` gives 3 minutes. Once the startup probe succeeds, Kubernetes switches to the liveness probe with its aggressive 10-second interval. The startup probe is only active during initial boot.
>
> This gives slow-starting services the time they need during initialization while keeping tight health monitoring during normal operation.

**"How do circuit breakers integrate with Kubernetes probes in Pravah?"**

> When a circuit breaker opens — say, because Pipeline Service is returning 5xx errors — Execution Service cannot validate pipeline configurations before dispatching jobs. Dispatching jobs in this state would fail or produce incorrect results.
>
> We implement a custom `HealthIndicator` that checks the circuit breaker state. If any critical circuit breaker is OPEN, the health indicator returns DOWN. Since this indicator is included in the readiness health group, readiness returns DOWN → Kubernetes removes the pod from load balancer endpoints → no new requests reach it.
>
> When Pipeline Service recovers, the circuit breaker transitions through half-open → closed. The health indicator returns UP. Readiness passes. Kubernetes adds the pod back to rotation. The entire cycle is automatic — no human intervention required.

## Key Takeaways

1. **Three probe types:** Startup (is boot complete?), Liveness (is the process alive and functional?), Readiness (is it ready to receive traffic right now?).

2. **Liveness checks only internal state — never external dependencies.** External dependency failure in liveness = crash loop that makes outages worse.

3. **Readiness checks all dependencies needed to serve requests.** DB unreachable → readiness DOWN → pod removed from rotation automatically.

4. **Startup probe eliminates the initialDelay trade-off.** Generous timeout only during boot. Aggressive liveness interval resumes after startup.

5. **Custom health indicators for application-level health:** circuit breaker state, minimum active runners, outbox queue depth. All contribute to readiness.

6. **Probe design pitfalls:** checking external deps in liveness, no startup probe for slow starters, overly strict readiness causing flapping, health checks that themselves cause load.

7. **Graceful shutdown requires probe cooperation.** SIGTERM → readiness DOWN (stop new traffic) → drain in-flight requests → exit. `preStop` sleep gives endpoint propagation time.

8. **Management port separation.** Actuator endpoints (`/health`, `/metrics`) on a separate port (8081) that is never exposed externally via the Ingress. The application port (8080) handles user traffic.

## What's Next

Probes enable Kubernetes to heal the system automatically when services degrade or fail. But probes are reactive — they respond to failure after it occurs. Chaos engineering is proactive — deliberately injecting failure to discover and fix weaknesses before production discovers them for you.
