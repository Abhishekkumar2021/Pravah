# 4.7 Chaos Engineering

## The Core Idea

Every system has failure modes that are only discovered in one of two ways: during a controlled experiment, or during an uncontrolled production incident.

Chaos engineering is the practice of choosing the first option deliberately. You inject failures — pod kills, network partitions, latency spikes, disk pressure, dependency outages — in a controlled environment to discover how the system behaves before a real incident forces the discovery at the worst possible time.

The goal is not to cause chaos. It is to find the weaknesses, fix them, and verify the fixes actually work. A system that has been chaos-tested has a known failure profile. A system that has never been chaos-tested has an unknown failure profile — and unknown failures become discovered failures in production.

The foundational principle of chaos engineering (from Netflix's Simian Army): **"If something is painful, do it more often so you become good at it and it stops being painful."**

---

## The Chaos Engineering Process

Chaos engineering is not randomly destroying things. It is a structured scientific method:

**Step 1: Define steady state**

What does normal look like? Establish baseline measurements before running any experiment.

```
Steady state for Pravah job execution:
  - Job success rate: 99.6% (measured over past 7 days)
  - Job dispatch p99: 3.2s
  - API p99: 180ms
  - Kafka consumer lag: <500 messages
  - No circuit breakers open
  - All pods reporting ready
```

**Step 2: Hypothesize**

State what you expect to happen when the failure is injected.

```
Hypothesis: "When one Execution Service pod is killed, surviving pods
absorb the load within 30 seconds with no user-visible degradation,
and the killed pod is replaced by Kubernetes within 60 seconds."
```

**Step 3: Inject the failure**

Inject the failure in a controlled way. Start in staging, move to production only when confident.

**Step 4: Observe**

Monitor all signals: metrics (job success rate, API latency), traces (any error traces?), logs (errors? restarts?), alerts (anything fired?).

**Step 5: Verify hypothesis or find the gap**

Did steady state hold? If yes — the system is resilient to this failure. If no — you found a real gap that would have caused a real incident.

**Step 6: Fix and repeat**

Fix the gap. Re-run the experiment to verify the fix works. Document the finding and fix.

## Chaos Tools for Kubernetes

### Chaos Mesh

An open-source chaos engineering platform for Kubernetes. Defines experiments as Kubernetes CRDs (Custom Resource Definitions).

```yaml
# Kill one execution-service pod randomly
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: execution-pod-kill
  namespace: pravah-chaos
spec:
  action: pod-kill
  mode: one          # kill one pod at a time
  selector:
    namespaces:
      - pravah
    labelSelectors:
      app: execution-service
  scheduler:
    cron: "@every 30m"   # scheduled: kill a pod every 30 minutes
```

```yaml
# Inject 500ms network latency to all execution-service pods
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: execution-network-latency
spec:
  action: delay
  mode: all
  selector:
    namespaces: [pravah]
    labelSelectors:
      app: execution-service
  delay:
    latency: "500ms"
    correlation: "25"   # 25% correlation (not all packets delayed equally)
    jitter: "100ms"
  duration: "10m"
```

```yaml
# Partition: prevent execution-service from reaching kafka
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: execution-kafka-partition
spec:
  action: partition
  mode: all
  selector:
    namespaces: [pravah]
    labelSelectors:
      app: execution-service
  direction: both
  target:
    mode: all
    selector:
      namespaces: [pravah]
      labelSelectors:
        app: kafka
  duration: "5m"
```

### Litmus

Another Kubernetes-native chaos framework. More opinionated, with a hub of pre-built experiments.

### Manual Injection with kubectl

For quick ad-hoc experiments:

```bash
# Kill a specific pod
kubectl delete pod execution-service-7b4d9f-k2x8p -n pravah

# Scale a deployment to zero (simulate complete service outage)
kubectl scale deployment execution-service --replicas=0 -n pravah

# Exec into a pod and simulate disk pressure
kubectl exec -it postgres-primary-0 -n pravah -- dd if=/dev/zero of=/var/lib/postgresql/data/fill_disk bs=1M count=1000

# Pause a container (simulate hung process without crashing)
kubectl exec -it runner-service-5f6g7h-xyz -n pravah -- kill -STOP 1
```

## Pravah's Chaos Experiment Library

### Experiment 1: Execution Service Pod Kill

**Hypothesis:** killing one pod of a 3-pod Execution Service deployment causes no user-visible job failures. Kubernetes replaces the pod within 60 seconds. The in-flight jobs on the killed pod are rescheduled.

**Setup:**
- 3 Execution Service pods running
- Stable job processing at ~200 jobs/minute
- All probes healthy

**Injection:** `kubectl delete pod execution-service-7b4d9f-k2x8p`

**Observe (30 minutes):**
- Job success rate (Grafana): did it dip below 99.5%?
- Error logs: any `RunnerUnavailableException` or `Connection refused` errors?
- Pod count: did Kubernetes create a replacement pod?
- In-flight jobs: did jobs that were processing on the killed pod get stuck or retried?

**Expected result:** Job success rate stays above 99.5%. Kubernetes starts a replacement pod within 10-15 seconds. Jobs that were in-flight on the killed pod are handled by the Saga pattern — Execution Service detects missing heartbeats on runner-assigned jobs and either waits (runner might reconnect) or marks them for retry. No user-visible impact.

**Potential gap found:** If jobs assigned to runners via gRPC stream are not tracked in a persistent saga state, they are lost when the pod dies. The fix: ensure the saga state for every in-flight job is committed to PostgreSQL before the gRPC call, so any Execution Service pod can resume tracking.

### Experiment 2: PostgreSQL Primary Failure

**Hypothesis:** when the PostgreSQL primary becomes unreachable, Patroni promotes the HA standby within 30 seconds. Service writes fail during the failover window (up to 30 seconds) but resume automatically. No data is lost (synchronous replica).

**Injection:** kill the primary PostgreSQL pod: `kubectl delete pod postgres-primary-0`

**Observe:**
- Patroni promotion log: time from primary kill to new primary election
- Service errors during failover window: expected — writes fail for up to 30s
- Job success rate: dip during failover, recovers immediately after
- Data integrity: all jobs committed before the kill appear on the new primary
- PgBouncer: reconnects to new primary after promotion

**Expected result:** 15–30 second window of write failures. Services surface errors (not silently lose data). After promotion, normal operation resumes. The synchronous HA standby means zero committed transaction loss.

**Potential gap:** If PgBouncer's `server_check_delay` is set to 30 seconds, it may take 30 seconds after promotion to detect the new primary and reconnect. During this time, connection attempts fail. Fix: reduce `server_check_delay` to 5 seconds and ensure services retry failed connections with exponential backoff.

### Experiment 3: Kafka Unavailability

**Hypothesis:** if Kafka becomes unreachable for 5 minutes, no jobs or events are lost. The outbox pattern buffers events in PostgreSQL. When Kafka recovers, the outbox relay publishes all buffered events in order.

**Injection:** scale Kafka to zero replicas (simulates Kafka outage)

**Observe:**
- Outbox relay: does it log errors gracefully and retry?
- Outbox pending message count: should grow during outage
- Job processing: jobs should continue to be dispatched via gRPC (direct path) even without Kafka events
- After Kafka recovery: does the outbox relay publish all buffered messages?

**Expected result:** outbox relay logs connection errors, backs off exponentially, keeps retrying. Pending message count grows. After recovery, relay catches up — all events published in order. No events lost.

**Potential gap:** if the outbox relay has no dead letter queue for its own internal failures (e.g., a message that consistently fails to serialize), it may retry that message infinitely and block all messages behind it. Fix: implement DLQ for the relay itself, with alerting when messages are moved to DLQ.

---

### Experiment 4: Network Latency Injection (Runner to Cloud)

**Hypothesis:** 500ms of network latency between runners and the cloud gRPC server causes job execution to slow down but not fail. The gRPC stream handles latency transparently. Heartbeat intervals adjust.

**Injection:** inject 500ms latency on the network path between runner pods and the gRPC gateway service

**Observe:**
- Job execution time: should increase by roughly the latency overhead
- gRPC stream: does it remain connected or disconnect and reconnect?
- Heartbeat detection: does Runner Service correctly track runners as active despite latency?
- Job success rate: should not drop (just slower)

**Potential gap:** if the runner's gRPC keepalive ping interval is shorter than the network round-trip time, the stream may be terminated by the server as "dead." Fix: configure keepalive with headroom above the expected maximum latency.

### Experiment 5: Redis Failure

**Hypothesis:** when Redis becomes unavailable, Pravah degrades gracefully. The scheduler falls back to PostgreSQL for leader election. Pipeline config reads fall back to PostgreSQL (cache miss). Runner heartbeats cannot be tracked (known degradation, acceptable for 30 seconds).

**Injection:** scale Redis to zero replicas

**Observe:**
- Scheduler leader election: does it fall back to PostgreSQL-based locking?
- Pipeline config cache: do cache misses fall through to PostgreSQL correctly?
- Runner heartbeat tracking: do runners appear stale after 30 seconds?
- API latency: increase from cache misses to PostgreSQL?

**Expected result:** elevated API latency (every config read goes to PostgreSQL instead of Redis cache). Scheduler continues with PostgreSQL-based leader election. Runner health degrades after 30 seconds (heartbeats expire). Platform functional but slower.

**Potential gap:** if the scheduler has no fallback for Redis leader election, it cannot elect a leader, and no pipelines are triggered during Redis outage. Fix: implement a circuit breaker + fallback to a PostgreSQL advisory lock for scheduler leader election when Redis is unavailable.

---

### Experiment 6: Memory Pressure and OOM

**Hypothesis:** if an Execution Service pod is OOM-killed by Kubernetes, it restarts cleanly and resumes processing. In-flight jobs are rescheduled by the saga pattern.

**Injection:** use a stress tool inside the pod to consume memory: `stress --vm 1 --vm-bytes 4G` on a pod with `resources.limits.memory: 2Gi`

**Observe:**
- OOM kill event: `kubectl describe pod execution-service-xxx | grep OOM`
- Restart count in Kubernetes
- Job saga recovery: did in-flight jobs resume?
- Alert: did any alert fire for the restart?

**Expected result:** Kubernetes kills the pod (OOM), restarts it. Restart count increments. Saga recovery picks up in-flight jobs. Alert for unexpected pod restart fires.

---

### Experiment 7: Slow Dependency (Bulkhead Test)

**Hypothesis:** if Pipeline Service becomes slow (p99 latency 5 seconds instead of 100ms), Execution Service's circuit breaker opens, and Execution Service falls back to cached pipeline configs rather than blocking on slow gRPC calls.

**Injection:** inject 5-second latency on all traffic to Pipeline Service

**Observe:**
- Execution Service thread pools: are they exhausting trying to call Pipeline Service?
- Circuit breaker state: does it transition from CLOSED → OPEN?
- Readiness probe: does it fail when circuit breaker opens?
- Job dispatch: do jobs continue being dispatched using cached config?
- Recovery: when latency injection stops, does circuit breaker transition OPEN → HALF_OPEN → CLOSED?

**Potential gap:** if Execution Service uses the default Spring RestTemplate without timeouts, slow Pipeline Service calls block threads indefinitely. 50 blocked threads → thread pool exhausted → no capacity for job dispatch → cascading failure. Fix: configure explicit timeouts (3 seconds for Pipeline Service gRPC calls), bulkhead (separate thread pool for external calls).

---

### Experiment 8: Data Corruption (Chaos for Correctness)

**Hypothesis:** if a runner reports a job as COMPLETE but the job record in PostgreSQL is in a conflicting state, the system detects and resolves the inconsistency without data loss.

**Injection:** manually update a job's status in PostgreSQL to RUNNING while the runner's gRPC stream reports it as COMPLETE

```sql
UPDATE jobs SET status = 'RUNNING' WHERE id = 'job-xyz' AND status = 'COMPLETE';
```

**Observe:**
- Does the reconciliation loop detect the inconsistency?
- Does it resolve to the correct state?
- Is an alert fired for the anomaly?

## The Chaos Schedule — Making It Routine

Chaos engineering only works if it is done regularly, not as a one-time event. Real systems change constantly — new code, new dependencies, infrastructure changes. A chaos test that passed 3 months ago may fail today because of an unrelated change.

**Pravah's chaos schedule:**

```
Daily (automated, staging only):
  - Random pod kill (any non-critical service)
  - 100ms latency injection on one service for 10 minutes

Weekly (automated, staging + canary production):
  - PostgreSQL primary failover test
  - Redis failure + recovery
  - Kafka 5-minute unavailability

Monthly (manual, full production):
  - Full cascading failure scenario (multiple failures simultaneously)
  - New failure mode based on recent incidents
  - SLO breach simulation: verify SLO alerts fire and runbooks work
```

**Game Days:** quarterly event where the engineering team deliberately runs the most destructive chaos scenarios during working hours, with everyone watching. Treats failure as a team exercise rather than an emergency. Builds muscle memory for incident response.

## Safety Mechanisms for Production Chaos

Running chaos experiments in production requires guardrails to prevent uncontrolled damage.

**1. Blast radius control:** always limit the scope of the experiment.

```yaml
# Never kill all pods — always leave at least one running
spec:
  mode: one           # kill exactly one pod
  # NOT mode: all    # this would kill everything simultaneously
```

**2. Automatic termination:** every experiment has a time limit. If the experiment is not manually stopped, it auto-terminates.

```yaml
duration: "10m"    # experiment stops after 10 minutes regardless
```

**3. Steady-state verification before injection:** if the system is already degraded, don't inject chaos — you'll make it worse and won't learn anything clean.

```yaml
# Chaos Mesh: conditional experiment — only run if API success rate is healthy
spec:
  # Custom precondition: abort if error rate > 1% already
  conditions:
    - type: custom
      check: prometheus_api_error_rate < 0.01
```

**4. One experiment at a time:** never run two chaos experiments simultaneously. Overlapping failures make it impossible to determine which caused what.

**5. Clear communication:** post in the incident channel before every production chaos experiment. All on-call engineers are aware and ready.

```
#pravah-incidents: ⚗️ CHAOS EXPERIMENT STARTING in 5 minutes
Type: PostgreSQL primary failover
Duration: 15 minutes
Expected impact: Up to 30s write failures during failover window
Monitor: https://grafana.pravah.io/d/platform-overview
Contact: @platform-on-call
```

## FAANG Interview Angles

**"How does Pravah use chaos engineering to validate its resilience patterns?"**

> We treat chaos as a testing discipline, not a heroic exercise. Every resilience pattern we implement — saga compensating transactions, outbox pattern, circuit breakers, automatic failover — has a corresponding chaos experiment that verifies it works in practice, not just in theory.
>
> For example, the outbox pattern is supposed to ensure no events are lost if Kafka becomes unavailable. Theory says it works because events are stored in PostgreSQL atomically with the business transaction. The chaos experiment proves it: we scale Kafka to zero for 5 minutes, observe that pending messages accumulate in the outbox table, then restore Kafka and verify the relay publishes all buffered messages in order with no duplicates.
>
> The gaps we find are more valuable than the confirmations. We once discovered that our PgBouncer `server_check_delay` was 30 seconds, meaning it took 30 seconds after a PostgreSQL primary failover for services to start writing to the new primary. We found this during a scheduled chaos experiment, not during a real outage. Fixed it the next day. Without chaos engineering, we would have discovered it during a real incident at 3 AM.

**"What is the most dangerous chaos experiment Pravah runs and why is it safe to run?"**

> Full PostgreSQL primary failover in production. It is dangerous because it causes a 15–30 second write failure window across all services — jobs cannot be dispatched, pipeline configs cannot be written. It is safe because we have verified it extensively in staging first, Patroni's synchronous replication means zero committed data loss, and we run it during business hours with all on-call engineers watching.
>
> The preparation is what makes it safe: we post in the incident channel 5 minutes before so everyone is aware, we have a blast radius limit (it only affects writes, reads continue via replicas), and the experiment auto-terminates after 15 minutes regardless. We have the runbook open and ready. The first time we ran it, we discovered PgBouncer reconnect delay. The second time, we confirmed the fix worked. Now it passes cleanly every month.

**"What is the difference between chaos engineering and testing?"**

> Unit and integration tests verify that code works correctly in isolation, with controlled inputs and expected outputs. Chaos engineering verifies that the system works correctly under real-world failure conditions that you cannot fully predict or simulate in a test.
>
> A unit test can verify that the outbox relay retries Kafka publish on failure. But it cannot verify that when a real Kafka broker fails mid-message, the message isn't partially written, the retry correctly picks it up, the deduplication prevents double-publishing, and the consumer correctly handles out-of-order delivery during recovery — all in a real distributed environment with real timing, real network conditions, and real concurrent load.
>
> Tests give you confidence in the code. Chaos gives you confidence in the system.

## Key Takeaways

1. **Chaos engineering = finding gaps before production does.** Controlled failure injection reveals weaknesses in resilience patterns, failure recovery, and operational procedures.

2. **The process is scientific:** define steady state → hypothesize → inject → observe → verify → fix → repeat. Not random destruction.

3. **Pravah's key experiments:** pod kill (Kubernetes self-healing), PostgreSQL failover (Patroni + zero data loss), Kafka outage (outbox pattern), network latency (gRPC keepalive + circuit breaker), Redis failure (fallback paths), OOM kill (saga recovery), slow dependency (bulkhead + timeout).

4. **Safety mechanisms are mandatory for production:** blast radius limits (kill one pod, not all), time limits (auto-terminate after N minutes), preconditions (don't inject if already degraded), one experiment at a time, advance communication.

5. **Scheduled chaos is better than ad-hoc chaos.** Daily in staging (pod kills, latency), weekly in canary production (failovers), monthly in full production (cascading failures), quarterly Game Days (team exercises).

6. **Document every experiment.** Confirmed hypotheses give confidence. Found gaps give improvement. Both are valuable. The documentation builds institutional knowledge about the system's actual failure behavior.

7. **Gaps are the point.** Finding that PgBouncer reconnect takes 30 seconds during failover during a chaos experiment means fixing it during business hours. Finding it during a real incident means a longer outage during production.
