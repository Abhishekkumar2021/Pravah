# 4.2 Metrics with Prometheus & Grafana

## What Metrics Are For

Metrics answer the question: "Is the system behaving correctly right now, and is it trending in the right direction?"

They are distinct from logs (individual events with context) and traces (the path of a specific request). Metrics are aggregated numerical measurements over time — they are cheap to store, fast to query, and the foundation of every alert and dashboard.

Without metrics, you find out about problems when users report them. With metrics, you find out before users do — and with enough context to know where to look.

---

## Prometheus Architecture

Prometheus is a pull-based metrics system. Rather than services pushing metrics to a central collector, Prometheus scrapes metrics from services at regular intervals.

```
┌─────────────────────────────────────────────────────────────┐
│                     Kubernetes Cluster                      │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  Execution   │  │  Scheduler   │  │  Runner      │      │
│  │  Service     │  │  Service     │  │  Service     │      │
│  │ :8080/metrics│  │ :8080/metrics│  │ :8080/metrics│      │

│         │                 │                 │               │

│                           │ scrape every 15s                │
│                           ▼                                 │
│              ┌────────────────────────┐                     │
│              │       Prometheus       │                     │
│              │                        │                     │
│              │  Time series database  │                     │
│              │  15s scrape interval   │                     │
```

Every Pravah service exposes a `/metrics` endpoint (via Micrometer + Spring Boot Actuator). Prometheus discovers these endpoints via Kubernetes Service Discovery and scrapes them every 15 seconds.

## The Four Metric Types

### Counter — Monotonically Increasing

A counter only goes up. It counts occurrences of events. On service restart, it resets to zero — Prometheus handles this via the `rate()` and `increase()` functions.

```java
// Micrometer counter in Pravah
Counter jobsCompleted = Counter.builder("pravah.job.completed")
    .tag("status", "SUCCESS")
    .tag("pipeline_id", pipelineId)
    .register(meterRegistry);

jobsCompleted.increment();
```

Prometheus exposition format:
```
# HELP pravah_job_completed_total Total jobs completed
# TYPE pravah_job_completed_total counter
pravah_job_completed_total{status="SUCCESS",pipeline_id="pipe-abc"} 15234
pravah_job_completed_total{status="FAILED",pipeline_id="pipe-abc"}  342
pravah_job_completed_total{status="SUCCESS",pipeline_id="pipe-def"} 8901
```

PromQL usage:
```promql
# Rate of job completions per second (5-minute window)
rate(pravah_job_completed_total[5m])

# Total job failures in the last hour
increase(pravah_job_completed_total{status="FAILED"}[1h])

# Success ratio
sum(rate(pravah_job_completed_total{status="SUCCESS"}[5m]))
/
sum(rate(pravah_job_completed_total[5m]))
```

Use counters for: request counts, error counts, job completions, bytes processed, events published.

### Gauge — Current Value (Can Go Up or Down)

A gauge records a current snapshot value. It can increase or decrease.

```java
// Active job count — current state
Gauge.builder("pravah.jobs.active", jobRepository, repo -> repo.countByStatus("RUNNING"))
    .register(meterRegistry);

// PgBouncer pool utilization
Gauge.builder("pravah.pgbouncer.pool.used", pgBouncerMetrics, m -> m.getActiveConnections())
    .tag("database", "execution_db")
    .register(meterRegistry);
```

Prometheus exposition:
```
pravah_jobs_active 1432
pravah_pgbouncer_pool_used{database="execution_db"} 18
```

PromQL usage:
```promql
# Current active jobs by tenant (requires tag)
pravah_jobs_active{tenant_id="megacorp"}

# PgBouncer utilization percentage
pravah_pgbouncer_pool_used / pravah_pgbouncer_pool_size * 100
```

Use gauges for: active connections, queue depth, cache size, current memory usage, number of running pods.

### Histogram — Distribution of Values

A histogram measures the distribution of observed values. It creates multiple time series: a bucket count for each defined boundary, a total sum, and a total count.

```java
// Job dispatch latency — how long from trigger to runner receiving job
Timer jobDispatchLatency = Timer.builder("pravah.job.dispatch.duration")
    .tag("pipeline_type", pipelineType)
    .publishPercentileHistogram()  // enable histogram buckets for Prometheus
    .sla(
        Duration.ofMillis(100),
        Duration.ofMillis(500),
        Duration.ofSeconds(1),
        Duration.ofSeconds(5),
        Duration.ofSeconds(10),
        Duration.ofSeconds(30)
    )
    .register(meterRegistry);

jobDispatchLatency.record(dispatchDurationMs, TimeUnit.MILLISECONDS);
```

Prometheus exposition:
```
pravah_job_dispatch_duration_seconds_bucket{le="0.1"}  89234
pravah_job_dispatch_duration_seconds_bucket{le="0.5"}  94821
pravah_job_dispatch_duration_seconds_bucket{le="1.0"}  96432
pravah_job_dispatch_duration_seconds_bucket{le="5.0"}  99801
pravah_job_dispatch_duration_seconds_bucket{le="10.0"} 99954
pravah_job_dispatch_duration_seconds_bucket{le="30.0"} 100000
pravah_job_dispatch_duration_seconds_bucket{le="+Inf"} 100000
pravah_job_dispatch_duration_seconds_sum    48234.5
pravah_job_dispatch_duration_seconds_count  100000
```

PromQL usage:
```promql
# p99 dispatch latency over 5-minute window
histogram_quantile(0.99,
  sum(rate(pravah_job_dispatch_duration_seconds_bucket[5m])) by (le)
)

# p50, p95, p99 for a specific pipeline type
histogram_quantile(0.99,
  sum(rate(pravah_job_dispatch_duration_seconds_bucket{
    pipeline_type="etl"
  }[5m])) by (le)
)
```

Use histograms for: request latency, job duration, message size, queue wait time, database query time — anything where you care about the distribution, not just the average.

**Why averages lie:** if 99% of jobs complete in 1s and 1% take 60s, the average is ~1.6s. The average tells you nothing is wrong. The p99 tells you 1 in 100 users waits a minute. Histograms are the only way to see this.

### Summary — Pre-computed Quantiles (Use Histograms Instead)

Summaries compute quantiles on the client side. They cannot be aggregated across instances — each pod computes its own quantiles, and you cannot combine them correctly.

Pravah does not use summaries. Histograms with `histogram_quantile()` on the Prometheus server provide the same information with correct cross-instance aggregation.

## The Cardinality Trap — The Most Common Prometheus Mistake

Cardinality is the number of unique time series Prometheus stores. Each unique combination of metric name and label values is one time series.

```
pravah_job_completed_total{status="SUCCESS", pipeline_id="pipe-abc"}  ← 1 series
pravah_job_completed_total{status="FAILED",  pipeline_id="pipe-abc"}  ← 1 series
pravah_job_completed_total{status="SUCCESS", pipeline_id="pipe-def"}  ← 1 series
...
```

With 10,000 pipelines × 5 statuses = **50,000 time series** from one metric. This is manageable.

**The cardinality trap: using high-cardinality values as labels.**

```java
// ❌ NEVER do this — job_id has millions of unique values
Counter.builder("pravah.job.completed")
    .tag("job_id", jobId)  // 10,000,000 unique job IDs → 10M time series
    .register(meterRegistry);

// ❌ Never use user IDs, request IDs, trace IDs, or timestamps as labels
Counter.builder("pravah.api.requests")
    .tag("user_id", userId)    // thousands of users → thousands of series per endpoint
    .tag("request_id", reqId)  // infinite cardinality → Prometheus dies
    .register(meterRegistry);
```

High cardinality kills Prometheus:
- Memory: each series requires ~1–2 KB in memory. 10M series = 10–20 GB of RAM just for series metadata
- CPU: label matching across 10M series takes seconds per query
- Storage: 15 days × 10M series × 15-second scrapes = petabytes

**Pravah's cardinality rules:**

```
ALLOWED labels:
  status        (5–10 values)
  pipeline_type (3–5 values: ETL, STREAMING, BATCH, SYNC)
  service       (8–10 values: one per microservice)
  runner_type   (3 values: SELF_HOSTED, CLOUD, EPHEMERAL)
  region        (5–10 values: eu-west, us-east, ap-south, ...)
  tenant_tier   (3 values: FREE, GROWTH, ENTERPRISE)
  http_method   (5 values: GET, POST, PUT, DELETE, PATCH)
  http_status   (use status class: 2xx, 4xx, 5xx — not individual codes)

FORBIDDEN labels:
  job_id        (millions of unique values)
  pipeline_id   (tens of thousands of unique values)
  user_id       (thousands of unique values)
  tenant_id     (thousands of unique values — use tenant_tier instead)
  request_id    (infinite)
  trace_id      (infinite)
  any timestamp (infinite)
```

Per-pipeline and per-tenant breakdowns are handled by logs and traces — not metrics.

## Recording Rules for Performance

Raw PromQL queries against high-cardinality metrics are slow. Recording rules pre-compute expensive expressions on a schedule and store results as new time series.

```yaml
groups:
  - name: pravah_recording_rules
    interval: 30s
    rules:

      # Pre-compute job success rate — used in SLO dashboard and alerts
      - record: pravah:job:success_rate:5m
        expr: |
          sum(rate(pravah_job_completed_total{status="SUCCESS"}[5m]))
          /
          sum(rate(pravah_job_completed_total[5m]))

      # Pre-compute p99 dispatch latency — used in SLO and runner dashboards
      - record: pravah:job:dispatch_p99:5m
        expr: |
          histogram_quantile(0.99,
            sum(rate(pravah_job_dispatch_duration_seconds_bucket[5m])) by (le)
          )

      # Pre-compute runner capacity utilization
      - record: pravah:runner:capacity_utilization:5m
        expr: |
          sum(pravah_runners_capacity_used)
          /
          sum(pravah_runners_capacity_total)

      # Pre-compute API error rate by service
      - record: pravah:api:error_rate:5m
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) by (service)
          /
          sum(rate(http_server_requests_seconds_count[5m])) by (service)
```

Dashboard queries reference the recording rule series (`pravah:job:success_rate:5m`) instead of computing from raw counters. Dashboards load in milliseconds instead of seconds.

## Prometheus Federation and Long-Term Storage

Pravah may run across multiple Kubernetes clusters (primary region + DR region). Each cluster runs its own Prometheus. Federation allows a global Prometheus to scrape aggregated data from each cluster Prometheus.

```yaml
# Global Prometheus — scrapes from cluster Prometheus instances
scrape_configs:
  - job_name: federate
    scrape_interval: 60s
    honor_labels: true
    metrics_path: /federate
    params:
      match[]:
        - '{__name__=~"pravah:.*"}'  # only recording rule series (pre-aggregated)
    static_configs:
      - targets:
          - prometheus-eu-west:9090
          - prometheus-us-east:9090
          - prometheus-ap-south:9090
```

For long-term storage (beyond 15-day Prometheus retention), Pravah uses **Thanos** or **VictoriaMetrics** — both provide S3-compatible object storage backends for metric data, enabling months of historical metric queries.

## System Design Interview Angles

**"What is the cardinality problem in Prometheus and how do you avoid it?"**

> Cardinality is the total number of unique time series — each unique combination of metric name and label values. Prometheus stores each series in memory and indexes it. High cardinality explodes memory and query time.
>
> The trap: using high-cardinality values as labels. Job ID has millions of unique values — one label creates millions of series from one metric. User ID, request ID, trace ID — all infinite cardinality. A single bad label can consume gigabytes of Prometheus memory and make all queries slow.
>
> Pravah's rule: labels must have bounded, low cardinality — status (5 values), runner type (3 values), service (10 values), tenant tier (3 values). Per-job and per-tenant breakdowns belong in logs and traces, where you look them up by ID. Metrics are for aggregate patterns, not individual events.

**"How would you instrument job dispatch latency in Pravah and use it to drive an SLO alert?"**

> Instrument with a Micrometer `Timer` configured as a histogram with relevant SLO buckets — 100ms, 500ms, 1s, 5s, 10s, 30s. Each observation records the milliseconds from pipeline trigger to runner receiving the job.
>
> In Prometheus, use `histogram_quantile(0.99, rate(...bucket[5m]))` to compute the rolling p99. A recording rule pre-computes this every 30 seconds as `pravah:job:dispatch_p99:5m`.
>
> The SLO alert fires when `pravah:job:dispatch_p99:5m > 10` (10 seconds) sustained for 5 minutes across both a 1-hour and 5-minute window — the multi-window pattern prevents transient spikes from paging on-call. The Grafana SLO dashboard shows the p99 trend alongside the error budget burn rate.

**"Why do you use histograms instead of summaries in Pravah?"**

> Summaries compute quantiles on the client — each service pod computes its own p99. You cannot average quantiles across pods. If pod A's p99 is 200ms and pod B's p99 is 800ms, the "average p99" is 500ms, which is meaningless — neither pod has a p99 of 500ms.
>
> Histograms store bucket counts. Bucket counts can be summed correctly across all pods. `histogram_quantile()` computes the quantile server-side from the combined buckets across all instances. The result is the actual system-wide p99, not an average of pod-level p99s.
>
> The only downside of histograms is that bucket boundaries must be defined upfront — if your latency distribution changes significantly, you may miss precision between buckets. That is why Pravah defines fine-grained buckets at the expected SLO thresholds.

## Key Takeaways

1. **Four metric types:** Counter (monotonically increasing, use `rate()`), Gauge (current value, can go up or down), Histogram (distribution, use `histogram_quantile()` for percentiles), Summary (avoid — cannot aggregate across instances).

2. **Cardinality is the most common Prometheus failure mode.** Never use job IDs, user IDs, request IDs, or timestamps as labels. Labels must have bounded low cardinality (single digits to dozens of values).

3. **Histograms over averages.** Average latency hides tail behavior. p99 via histogram shows what 1% of users actually experience. Define histogram buckets at your SLO thresholds.

4. **Recording rules are mandatory at scale.** Pre-compute expensive PromQL expressions on a schedule. Dashboard queries hit pre-computed series — millisecond response instead of seconds.

5. **Pull-based architecture.** Prometheus scrapes `/metrics` endpoints. Services don't push. This means Prometheus controls the scrape rate and can detect dead services (no scrape = no data = alert).

6. **Pravah's critical metrics hierarchy:**
   - Job success rate + dispatch p99 → SLO dashboards + alerts
   - Outbox pending count → detect relay failures
   - Kafka consumer lag → detect event processing stalls
   - PgBouncer waiting connections → detect pool exhaustion
   - Runner capacity utilization → detect job starvation

7. **Federation for multi-cluster.** Each cluster has its own Prometheus. A global Prometheus federates pre-aggregated recording rule series for cross-cluster visibility.

8. **Long-term storage:** Thanos or VictoriaMetrics for metrics beyond 15-day Prometheus retention. Essential for month-over-month SLO analysis and capacity planning.

## What's Next

Metrics tell you that something is wrong. They do not tell you where in the distributed request path the problem occurred. A job that takes 45 seconds might be slow because of Kafka lag, a slow runner assignment, a PostgreSQL query, or a gRPC timeout on a downstream service. Metrics cannot distinguish these.
