# 4.5 Alerting Strategy

## The Cost of Bad Alerts

Every false positive alert that wakes someone up at 3 AM has a cost: interrupted sleep, degraded next-day performance, and most importantly, training the on-call engineer to ignore alerts. Alert fatigue is the silent killer of operational reliability.

When alerts fire constantly for non-issues, engineers stop responding urgently. They start dismissing alerts without investigating, silencing alert rules without fixing the root cause, and delaying real incident response because they assume it is another false positive. This is the state in which real outages become catastrophic — the signal is buried in noise.

Good alerting has one goal: **every alert that wakes someone up is actionable and represents a real problem that requires immediate human intervention.**

Everything else belongs in a different tier.

---

## The Three-Tier Alert Model

Not all problems require immediate human response. Pravah classifies alerts into three tiers based on urgency and required response time.

### Tier 1 — Page (Immediate Human Response Required)

The system is currently impacting users, or will impact users within the next 2 hours if not addressed.

Characteristics:
- Wakes on-call engineer (phone call or SMS, not just Slack)
- Requires response within 5 minutes
- Always backed by an error budget burn rate or a direct SLO violation
- Has a runbook immediately accessible

Examples:
- Job success SLO burn rate > 14x for 1 hour (error budget exhausted in 2 days)
- API error rate > 5% sustained for 5 minutes (active user impact)
- All runners offline for a tenant (jobs cannot execute)
- Kafka consumer lag growing uncontrollably (jobs will pile up)
- PostgreSQL primary unreachable (complete data loss risk)

### Tier 2 — Ticket (Action Required Within Hours)

Something is degraded or trending toward failure, but is not yet impacting users.

Characteristics:
- Notification to Slack on-call channel + creates a PagerDuty low-priority ticket
- Response required within 4 hours during business hours
- No middle-of-night wake-up
- Includes diagnosis guidance

Examples:
- Error budget burn rate > 3x sustained (trending toward problem)
- PgBouncer pool utilization > 80% (approaching exhaustion)
- Disk usage > 75% on any PostgreSQL node
- Replication lag > 30 seconds sustained (read replicas stale)
- Kafka consumer lag growing for 30 minutes but not yet critical
- Certificate expiring within 14 days

### Tier 3 — Dashboard (Informational, No Action Required)

Metric of interest visible on dashboards. Not actionable by itself. Provides context for investigation when something else goes wrong.

Characteristics:
- Grafana dashboard only — no notification
- Reviewed during weekly SLO review or post-incident
- May inform capacity planning

Examples:
- Cache hit rate trending down (visible on dashboard)
- Job dispatch p99 trending up but within SLO
- Runner pool utilization at 60% (healthy but informational)
- Outbox relay processing rate

## What Makes a Good Alert Rule

**Criterion 1: It maps to a user-visible problem (or imminent one)**

`CPU > 80%` is not a good alert by itself. CPU can be high because of legitimate load, a batch job, index creation — any number of benign causes. CPU > 80% that also causes request latency > 2 seconds is user-visible.

Tie alerts to outcomes, not proxies.

```yaml
# Bad: proxy metric
- alert: HighCPU
  expr: cpu_usage_percent > 80

# Good: outcome metric
- alert: APILatencyDegraded
  expr: pravah:api:latency_p99:5m > 2
  for: 5m
  annotations:
    summary: "API p99 latency {{ $value }}s — users experiencing slow responses"
```

**Criterion 2: It has a `for` duration that filters transient spikes**

An alert that fires for 30 seconds of elevated error rate pages on-call for a blip that resolved itself. The `for` clause requires the condition to be sustained before alerting.

```yaml
# Bad: fires on any transient spike
- alert: HighErrorRate
  expr: pravah:api:error_rate:5m > 0.01

# Good: sustained condition
- alert: HighErrorRate
  expr: pravah:api:error_rate:5m > 0.01
  for: 5m   # must be elevated for 5 minutes
```

**Criterion 3: Every page-level alert has a runbook**

An alert without a runbook forces the on-call engineer to diagnose from scratch at 3 AM. A runbook provides: what the alert means, what immediate actions to take, what to look at first, when to escalate.

```yaml
- alert: RunnerPoolExhausted
  expr: pravah:runner:capacity_utilization:5m > 0.95
  for: 5m
  labels:
    severity: page
    team: platform
  annotations:
    summary: "Runner pool {{ $value | humanizePercentage }} utilized"
    description: "Job queue will grow. Runners cannot accept new work."
    runbook: "https://wiki.pravah.io/runbooks/runner-pool-exhausted"
    dashboard: "https://grafana.pravah.io/d/runner-health"
```

**Criterion 4: It uses multi-window burn rate for SLO alerts (not raw thresholds)**

As covered in 4.1: raw threshold alerts fire on spikes. Multi-window burn rate alerts fire on sustained consumption. The difference is the gap between alert fatigue and useful signals.

## Pravah's Complete Alert Ruleset

### Critical (Page) Alerts

```yaml
groups:
  - name: pravah_critical
    rules:

      # SLO-1: Job success rate burning fast
      - alert: JobSuccessRateFastBurn
        expr: |
          pravah:job:success_rate_error_budget_burn:1h > 14
          AND pravah:job:success_rate_error_budget_burn:5m > 14
        for: 2m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "Job success SLO burning at {{ $value | humanize }}x rate"
          description: |
            Error budget will exhaust in {{ div 28 $value | int }} days.
            Currently {{ printf "%.1f" (mul (sub 1 (query "pravah:job:success_rate:5m" | first | value)) 100) }}% failure rate.
          runbook: "https://wiki.pravah.io/runbooks/job-success-burn"

      # Runner pool saturation
      - alert: RunnerPoolSaturated
        expr: |
          (sum(pravah_runners_active_jobs) / sum(pravah_runners_max_concurrent)) > 0.95
        for: 5m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "Runner pool {{ $value | humanizePercentage }} full — jobs queuing"
          runbook: "https://wiki.pravah.io/runbooks/runner-saturation"

      # Kafka consumer lag explosion — jobs piling up
      - alert: KafkaLagCritical
        expr: |
          max(kafka_consumer_fetch_manager_records_lag_max{
            topic="job.assigned"
          }) > 10000
        for: 3m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "job.assigned consumer lag {{ $value }} records — jobs not being processed"
          runbook: "https://wiki.pravah.io/runbooks/kafka-lag-critical"

      # Database primary unreachable
      - alert: PostgresPrimaryUnreachable
        expr: |
          pg_up{job="postgres-primary"} == 0
        for: 1m
        labels:
          severity: critical
          team: data
        annotations:
          summary: "PostgreSQL primary unreachable — writes failing"
          runbook: "https://wiki.pravah.io/runbooks/postgres-primary-down"

      # API completely down
      - alert: APIGatewayDown
        expr: |
          sum(up{job="api-gateway"}) == 0
        for: 1m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "All API Gateway pods down — platform unreachable"
          runbook: "https://wiki.pravah.io/runbooks/api-gateway-down"

      # PgBouncer pool exhausted — services cannot write
      - alert: PgBouncerPoolExhausted
        expr: |
          pgbouncer_pools_client_waiting_connections{
            database=~"pravah_execution_db|pravah_pipeline_db"
          } > 10
        for: 2m
        labels:
          severity: critical
          team: data
        annotations:
          summary: "{{ $labels.database }} PgBouncer has {{ $value }} clients waiting"
          runbook: "https://wiki.pravah.io/runbooks/pgbouncer-pool-exhausted"
```

### Warning (Ticket) Alerts

```yaml
  - name: pravah_warning
    rules:

      # Slow burn SLO
      - alert: JobSuccessRateSlowBurn
        expr: |
          pravah:job:success_rate_error_budget_burn:6h > 3
          AND pravah:job:success_rate_error_budget_burn:30m > 3
        for: 15m
        labels:
          severity: warning
          team: platform
        annotations:
          summary: "Job success SLO burning at {{ $value | humanize }}x rate"
          description: "Investigate within 4 hours."

      # PgBouncer utilization high
      - alert: PgBouncerHighUtilization
        expr: |
          (pgbouncer_pools_server_active_connections /
           pgbouncer_pools_server_idle_connections) > 0.8
        for: 10m
        labels:
          severity: warning
          team: data
        annotations:
          summary: "{{ $labels.database }} PgBouncer pool {{ $value | humanizePercentage }} utilized"

      # Replication lag elevated
      - alert: PostgresReplicationLagHigh
        expr: |
          pg_replication_lag_seconds > 30
        for: 5m
        labels:
          severity: warning
          team: data
        annotations:
          summary: "Read replica {{ $labels.replica }} is {{ $value }}s behind primary"

      # Table bloat growing
      - alert: TableBloatHigh
        expr: |
          (pg_stat_user_tables_n_dead_tup /
           NULLIF(pg_stat_user_tables_n_live_tup + pg_stat_user_tables_n_dead_tup, 0)) > 0.1
        for: 30m
        labels:
          severity: warning
          team: data
        annotations:
          summary: "Table {{ $labels.relname }} has {{ $value | humanizePercentage }} dead tuples"

      # Kafka consumer lag moderate
      - alert: KafkaLagElevated
        expr: |
          max(kafka_consumer_fetch_manager_records_lag_max{
            topic="job.assigned"
          }) > 1000
        for: 10m
        labels:
          severity: warning
          team: platform
        annotations:
          summary: "job.assigned consumer lag {{ $value }} records and growing"

      # Certificate expiry
      - alert: CertificateExpiringSoon
        expr: |
          (probe_ssl_earliest_cert_expiry - time()) / 86400 < 14
        labels:
          severity: warning
          team: platform
        annotations:
          summary: "Certificate for {{ $labels.instance }} expires in {{ $value | humanizeDuration }}"

      # Disk space
      - alert: DiskSpaceHigh
        expr: |
          (1 - (node_filesystem_avail_bytes / node_filesystem_size_bytes)) > 0.75
        for: 30m
        labels:
          severity: warning
          team: data
        annotations:
          summary: "Node {{ $labels.instance }} disk {{ $value | humanizePercentage }} full"
```

## Alertmanager — Routing, Grouping, and Silencing

Alertmanager receives firing alerts from Prometheus and handles routing, deduplication, grouping, and notification.

### Routing Configuration

```yaml
# alertmanager.yaml
global:
  resolve_timeout: 5m
  pagerduty_url: https://events.pagerduty.com/v2/enqueue
  slack_api_url: https://hooks.slack.com/services/...

route:
  receiver: default-receiver
  group_by: [alertname, service, team]
  group_wait: 30s      # wait 30s before sending (group related alerts)
  group_interval: 5m   # minimum time between grouped notifications
  repeat_interval: 4h  # re-notify if still firing after 4h

  routes:
    # Critical alerts → PagerDuty (phone/SMS)
    - match:
        severity: critical
      receiver: pagerduty-critical
      repeat_interval: 30m    # re-page every 30min if not acknowledged

    # Warning alerts → Slack + ticket
    - match:
        severity: warning
      receiver: slack-warning
      repeat_interval: 4h

    # Data team alerts
    - match:
        team: data
        severity: critical
      receiver: pagerduty-data-team
      continue: true  # also send to default

    # Platform team alerts
    - match:
        team: platform
        severity: critical
      receiver: pagerduty-platform-team
      continue: true

receivers:
  - name: pagerduty-critical
    pagerduty_configs:
      - service_key: ${PAGERDUTY_SERVICE_KEY}
        severity: critical
        description: |
          {{ .CommonAnnotations.summary }}
          Runbook: {{ .CommonAnnotations.runbook }}

  - name: slack-warning
    slack_configs:
      - channel: "#pravah-alerts"
        title: "⚠️ {{ .CommonAnnotations.summary }}"
        text: |
          {{ .CommonAnnotations.description }}
          Runbook: {{ .CommonAnnotations.runbook }}
        send_resolved: true
```

### Alert Grouping — Preventing Alert Storms

During a large incident (e.g., a Kubernetes node failure), dozens of alerts might fire simultaneously. Without grouping, every alert sends a separate notification — the on-call engineer gets 50 PagerDuty pages in 30 seconds.

Grouping consolidates related alerts into one notification:

```yaml
group_by: [alertname, service, team]
group_wait: 30s
```

With `group_wait: 30s`: Alertmanager waits 30 seconds after the first alert fires, collecting all related alerts, then sends one grouped notification. The engineer sees: "3 alerts firing for execution-service" rather than 3 separate pages.

### Inhibition Rules — Suppress Downstream Alerts

When a fundamental dependency fails, all dependent alerts are noise. If the PostgreSQL primary is unreachable, `PgBouncerPoolExhausted` and `JobSuccessRateFastBurn` will also fire — but these are caused by the primary being down, not independent problems.

Inhibition rules suppress dependent alerts when a root cause alert is active:

```yaml
inhibit_rules:
  # If postgres primary is down, suppress dependent alerts
  - source_match:
      alertname: PostgresPrimaryUnreachable
    target_match_re:
      alertname: PgBouncerPoolExhausted|JobSuccessRateFastBurn|KafkaLagCritical
    equal: [team]

  # If API Gateway is completely down, suppress individual endpoint alerts
  - source_match:
      alertname: APIGatewayDown
    target_match_re:
      alertname: APILatencyHigh|APIErrorRateHigh
```

Result: one page for "PostgreSQL primary unreachable" instead of four separate pages for symptoms.

## Runbook Design

A runbook is a step-by-step guide for responding to a specific alert. It is written when the alert is created — not when the alert fires.

**Runbook structure for Pravah:**

```markdown
# Runbook: Job Success Rate Fast Burn

## Overview
**Alert:** JobSuccessRateFastBurn
**Severity:** Critical / Page
**SLO:** Job execution success rate ≥ 99.5% over 28 days
**Error budget impact:** >14x burn rate → exhausts budget in <2 days

## Immediate Triage (first 5 minutes)

1. Open the Job Success SLO dashboard → check current failure rate and recent trend
2. Filter Kibana for errors: `level:ERROR AND service:execution-service AND @timestamp:[now-15m TO now]`
3. Identify the dominant error type from the `error.type` field aggregation
4. Check if failures are:
   - All tenants affected → platform-wide issue
   - Specific tenant(s) → tenant-specific issue (runner, config, quota)
   - Specific service → component failure

## Common Causes and Resolution

### Case 1: Runner Pool Saturated
- Dashboard shows: runner capacity utilization > 95%
- Logs show: `assignment.result: QUEUED`, `queue_depth: >100`
- Resolution:
  a. Check if runner fleet is online: `kubectl get pods -l app=runner-cloud`
  b. If cloud runners are down: scale up `runner-cloud` deployment
  c. If self-hosted runner offline: contact tenant via status page
  d. Temporary: provision burst cloud runners → `kubectl scale deployment/runner-cloud --replicas=20`

### Case 2: Database Failure
- Dashboard shows: PgBouncer errors, postgres_up=0
- Logs show: `CannotAcquireJdbcConnectionException` or `Connection refused`
- Resolution: → See PostgresPrimaryUnreachable runbook

### Case 3: Kafka Consumer Lag
- Dashboard shows: job.assigned consumer lag growing
- Logs show: `Consumer group lag: XXXXX`
- Resolution:
  a. Check if execution-service pods are running: `kubectl get pods -l app=execution-service`
  b. Check for rebalancing: `kafka-consumer-groups.sh --describe --group execution-service`
  c. If consumer group stuck: restart execution-service pods one by one

### Case 4: Code Bug (recent deployment)
- Check if failure rate spiked after a deployment: compare `version` label in error logs
- If yes: roll back immediately → `kubectl rollout undo deployment/execution-service`

## Escalation
- After 15 minutes without resolution: escalate to team lead
- After 30 minutes: executive notification via Slack #pravah-incidents
- If SLA breach imminent: customer success team notification

## Post-Incident
- File post-mortem within 24 hours
- Update this runbook with new case if root cause was not covered
```

## On-Call Practices

**On-call rotation:** weekly rotation across the platform team. Minimum 3 engineers in the rotation to avoid burnout (one person every 3 weeks).

**Escalation path:**
```
Primary on-call
  → Secondary on-call (if no response within 5 minutes)
  → Team lead (if no response within 15 minutes)
  → Engineering manager (if no resolution within 30 minutes)
```

**Alert hygiene reviews:** weekly 15-minute review of all alerts that fired in the past week:
- True positives: did the runbook help? Update if not.
- False positives: fix the alert condition or add a `for` duration.
- Silenced alerts: why was it silenced? Was it legitimate?
- Fired but not paged (warning): is the threshold correct?

**The alert death rule:** any alert that fires more than 3 times in a week without causing a real incident is either deleted or moved to dashboard-only. Alert fatigue is more dangerous than missing alerts.

## FAANG Interview Angles

**"What is the difference between a good alert and a bad alert?"**

> A good alert has three properties. First, it is actionable — waking someone up means there is a specific action they must take immediately. An alert for "CPU > 80%" with no corresponding user impact is not actionable. An alert for "API p99 latency > 2 seconds sustained for 5 minutes" is — users are experiencing slowness right now.
>
> Second, it has low false positive rate. Every false positive trains engineers to treat the next alert with less urgency. Multi-window burn rate alerts dramatically reduce false positives compared to simple threshold alerts — they require sustained condition, not a transient spike.
>
> Third, it has a runbook. An alert that fires at 3 AM with no guidance forces the on-call engineer to diagnose from scratch while exhausted. A runbook with the 3 most common causes and resolution steps turns a 45-minute incident into a 5-minute one.

**"How do you handle alert storms during large incidents?"**

> Two mechanisms: grouping and inhibition. Alertmanager grouping waits 30 seconds after the first alert fires, collects all related alerts (by alertname, service, and team), and sends one consolidated notification. Instead of 30 separate pages, the on-call engineer gets one page: "3 alerts firing for execution-service."
>
> Inhibition rules suppress alerts that are caused by a more fundamental alert. If the PostgreSQL primary is down, PgBouncer pool exhaustion and job success SLO burn will also fire — but these are symptoms, not independent problems. An inhibition rule suppresses them when the primary-down alert is active. The engineer focuses on one root cause, not three symptoms.

**"How do you decide what error budget burn rate to alert on?"**

> The goal is to give the on-call engineer time to respond before the SLO is breached. For a 28-day error budget: a 14x burn rate means the budget exhausts in 2 days — that is urgent, page immediately. A 6x burn rate means exhaustion in 4.5 days — that is concerning, create a ticket and respond within hours.
>
> The multi-window requirement (14x for 1 hour AND 14x for 5 minutes) prevents transient spikes from paging. A 60-second spike at 50x burn rate consumes almost no budget — the 1-hour window absorbs it. Only sustained elevation triggers the page.

## Key Takeaways

1. **Alert fatigue is the enemy of reliability.** Every false positive trains engineers to ignore alerts. The goal: every page is real, every page is actionable.

2. **Three-tier model:** Page (immediate human response), Ticket (action within hours), Dashboard (informational, no notification). Most alerts should be Ticket or Dashboard, not Page.

3. **Page-level alerts must be:** user-impacting or imminent, tied to SLO burn rate not raw thresholds, sustained (using `for` duration), and backed by a runbook.

4. **Multi-window burn rate > simple thresholds.** 14x burn rate for 1 hour AND 5 minutes = real problem. Single threshold crossing = noise.

5. **Alertmanager features are critical:** grouping (consolidates alert storms), inhibition (suppresses symptoms when root cause fires), routing (right team gets right alerts), repeat interval (re-pages if not acknowledged).

6. **Runbooks must exist before the alert fires.** Written at alert creation time. Include: what this alert means, 3 most common causes, resolution steps for each, escalation path.

7. **Alert hygiene reviews:** weekly review of all fired alerts. More than 3 false positives per week → fix or delete the alert. Alert death rule prevents entropy.

8. **Inhibition rules for root cause suppression:** PostgreSQL primary down → suppress PgBouncer and SLO burn alerts. API Gateway down → suppress individual endpoint alerts. Engineer focuses on one root cause.
