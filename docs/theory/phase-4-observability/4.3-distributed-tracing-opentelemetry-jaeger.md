# 4.3 Distributed Tracing with OpenTelemetry & Jaeger

## The Problem Metrics Cannot Solve

A Pravah user reports: "My pipeline took 45 seconds to run, but it normally takes 5 seconds."

Metrics tell you the p99 latency is elevated across the board. But they cannot tell you:

- Was the 40 seconds spent waiting in the Kafka queue for a consumer?
- Was it waiting for a runner to become available?
- Was it a slow SQL query in Execution Service?
- Was it the runner itself executing slowly (user's code)?
- Was it a downstream gRPC call to Pipeline Service timing out?

A 45-second job touches: API Gateway → Scheduler → Kafka → Execution Service → Runner Assignment → gRPC → Runner → gRPC callback → Execution Service → Kafka → Notification Service. Metrics show aggregate behavior. **Tracing shows the path of one specific request across every service it touched, with timing for each step.**

---

## Core Concepts

### Trace

A trace represents the complete end-to-end journey of one request or operation through the system. It has a globally unique ID (trace ID) that ties together all the work done across all services for that one request.

```
TraceID: a3b4c5d6e7f8...

Pipeline trigger: POST /pipelines/pipe-abc/trigger
│
├── Scheduler Service: resolve DAG and enqueue jobs
│   ├── PostgreSQL: SELECT pipeline config
│   └── Kafka: publish job.assigned message
│
├── Execution Service: consume job.assigned, assign runner
│   ├── Redis: check runner availability
│   ├── PostgreSQL: write job record + outbox
│   └── gRPC: send job to runner
│
└── Runner: execute pipeline
    ├── DuckDB: extract source data
    ├── DuckDB: transform
    └── gRPC callback: publish result
```

Total: 45 seconds. Each box is a span with its own start time and duration. The trace shows exactly where the 40 extra seconds went.

### Span

A span is a single unit of work within a trace. It has:
- A name (operation name: "HTTP POST /trigger", "PostgreSQL SELECT", "Kafka publish")
- A start timestamp and duration
- The trace ID (links it to the parent trace)
- A parent span ID (links it to the calling span)
- Attributes (key-value metadata: HTTP status, DB table, Kafka topic, etc.)
- Events (timestamped log messages within the span)
- Status (OK, ERROR, UNSET)

```
Span: "Execution Service: assign runner"
  trace_id:      a3b4c5d6e7f8...
  span_id:       f1e2d3c4...
  parent_span_id: b5a6c7d8... (from Kafka consumer span)
  start:         2024-01-15T10:00:00.100Z
  duration:      28,400ms      ← 28 seconds here
  status:        OK
  attributes:
    job_id:      job-xyz
    runner_id:   null    ← was waiting for available runner
    queue_depth: 847     ← 847 jobs ahead in queue
```

The runner assignment span lasting 28 seconds, with `runner_id: null` and `queue_depth: 847`, immediately tells you: the runner pool was saturated. The bottleneck was runner starvation, not any service bug.

### Context Propagation

For a trace to span multiple services, the trace context (trace ID + parent span ID) must travel with the request. This is propagation.

**Over HTTP:** injected into headers using the W3C TraceContext standard:

```
POST /assign HTTP/1.1
traceparent: 00-a3b4c5d6e7f8901234567890abcdef-b5a6c7d8e9f0-01
             ^^ version  ^^^^ trace-id (128-bit) ^^ span-id  ^^ flags
```

**Over gRPC:** injected into gRPC metadata (headers):

```
metadata:
  traceparent: 00-a3b4c5d6e7f8901234567890abcdef-b5a6c7d8e9f0-01
```

**Over Kafka:** injected into Kafka message headers:

```java
// Producer: inject trace context into Kafka headers
ProducerRecord<String, byte[]> record = new ProducerRecord<>(topic, key, payload);
// OpenTelemetry automatically injects traceparent into record headers
```

```java
// Consumer: extract trace context from Kafka headers and create child span
// OpenTelemetry Kafka instrumentation handles this automatically
```

When services use the OpenTelemetry SDK, HTTP and gRPC propagation happens automatically via instrumentation. Kafka requires explicit configuration of the Kafka instrumentation.

## OpenTelemetry — The Standard

OpenTelemetry (OTel) is the open standard for telemetry collection — traces, metrics, and logs. It provides:
- APIs and SDKs for every major language
- An instrumentation library that auto-instruments common frameworks (Spring Boot, Kafka, PostgreSQL JDBC, gRPC, Redis)
- The OpenTelemetry Collector — a vendor-neutral agent that receives telemetry and exports to any backend

**Why OpenTelemetry instead of a vendor SDK (Datadog, Dynatrace)?**

Vendor lock-in. If Pravah instruments with the Datadog SDK directly, migrating to another observability backend requires rewriting all instrumentation. OTel is instrumented once — backends are swapped by changing Collector configuration.

```
Pravah Service
  │
  │ OpenTelemetry SDK (traces, metrics, logs)
  ▼
OTEL Collector (sidecar or DaemonSet)
  │
  ├──► Jaeger (tracing)
  ├──► Prometheus (metrics)
  └──► Elasticsearch (logs)
```

## Instrumentation in Pravah

### Auto-Instrumentation via Spring Boot

Adding the OpenTelemetry Spring Boot starter automatically instruments:
- All HTTP requests (incoming and outgoing via RestTemplate/WebClient)
- All gRPC calls (server and client interceptors)
- All Kafka producer and consumer operations
- All JDBC queries (PostgreSQL, with query text capture)
- Spring `@Async` and `@Scheduled` methods

```xml
<!-- pom.xml -->
<dependency>
    <groupId>io.opentelemetry.instrumentation</groupId>
    <artifactId>opentelemetry-spring-boot-starter</artifactId>
    <version>2.x.x</version>
</dependency>
```

```yaml
# application.yaml
otel:
  service.name: execution-service
  traces:
    exporter: otlp
  exporter:
    otlp:
      endpoint: http://otel-collector:4317
  instrumentation:
    spring-web:
      enabled: true
    kafka:
      enabled: true
    jdbc:
      enabled: true
      db-statement-sanitizer.enabled: true  # sanitize query params
```

### Manual Instrumentation for Business Logic

Auto-instrumentation covers infrastructure. Business logic needs manual spans to be meaningful.

```java
@Service
public class JobAssignmentService {

    private final Tracer tracer;

    public RunnerAssignment assignRunner(Job job) {
        // Create a child span for the assignment decision
        Span span = tracer.spanBuilder("assign-runner")
            .setAttribute("job.id", job.getId())
            .setAttribute("job.pipeline_id", job.getPipelineId())
            .setAttribute("job.tenant_id", job.getTenantId())
            .setAttribute("job.required_tags", job.getRequiredTags().toString())
            .startSpan();

        try (Scope scope = span.makeCurrent()) {
            // Find eligible runners
            List<Runner> candidates = findEligibleRunners(job);
            span.setAttribute("assignment.candidates_found", candidates.size());

            if (candidates.isEmpty()) {
                span.setAttribute("assignment.result", "QUEUED");
                span.setAttribute("assignment.queue_depth", getQueueDepth(job.getTenantId()));
                return RunnerAssignment.queued();
            }

            Runner selected = selectOptimalRunner(candidates);
            span.setAttribute("assignment.result", "ASSIGNED");
            span.setAttribute("assignment.runner_id", selected.getId());
            span.setAttribute("assignment.runner_load", selected.getCurrentLoad());
            return RunnerAssignment.assigned(selected);

        } catch (Exception e) {
            span.recordException(e);
            span.setStatus(StatusCode.ERROR, e.getMessage());
            throw e;
        } finally {
            span.end();
        }
    }
}
```

The resulting span in Jaeger has all the context needed to understand the assignment decision — without reading logs or querying the database.

### Enriching Spans with Business Attributes

Standard attributes tell you what happened at the infrastructure level. Business attributes tell you what it meant.

```java
// Standard (auto-instrumented): "HTTP POST /jobs — 200ms"
// With business attributes: "POST /jobs — tenant:megacorp, pipeline:daily-etl, 200ms"

@RestController
public class JobController {

    @PostMapping("/jobs/{jobId}/trigger")
    public ResponseEntity<JobResult> triggerJob(
            @PathVariable String jobId,
            @RequestHeader("X-Tenant-ID") String tenantId) {

        // Enrich the current span with business context
        Span.current()
            .setAttribute("tenant.id", tenantId)
            .setAttribute("tenant.tier", getTenantTier(tenantId))
            .setAttribute("job.id", jobId);

        // ... execute job ...
    }
}
```

Now when filtering traces in Jaeger by `tenant.id = megacorp`, every trace for that tenant is visible — including all internal service calls they triggered.

## Sampling Strategies — Controlling Cost

Tracing every request at full detail is expensive. A platform processing 10,000 jobs per minute with 20 spans per job = 200,000 spans per minute. At 1 KB per span, that is 200 MB per minute, 280 GB per day.

Sampling reduces this to a manageable volume while preserving the traces you actually need.

### Head-Based Sampling — Decide at the Start

The sampling decision is made at the beginning of the trace (when the first span is created). It applies to all spans in that trace.

```yaml
# Simple: sample 1% of all requests
otel:
  traces:
    sampler: traceidratio
    sampler.arg: 0.01  # 1%
```

**Problem with simple ratio sampling:** most traces are boring (successful requests). Error traces — the ones you most need — might be in the 99% that are not sampled.

### Tail-Based Sampling — Decide After the Fact

The sampling decision is made after the trace is complete, based on what happened.

This requires the OpenTelemetry Collector (or Jaeger) to buffer spans and apply policies after seeing the full trace:

```yaml
# OpenTelemetry Collector configuration
processors:
  tail_sampling:
    decision_wait: 10s    # wait up to 10s for all spans to arrive
    num_traces: 100000    # buffer up to 100K concurrent traces
    policies:
      # Always sample traces with errors
      - name: errors-policy
        type: status_code
        status_code:
          status_codes: [ERROR]

      # Always sample slow traces (> 5 seconds)
      - name: latency-policy
        type: latency
        latency:
          threshold_ms: 5000

      # Sample 1% of healthy fast traces (baseline)
      - name: baseline-policy
        type: probabilistic
        probabilistic:
          sampling_percentage: 1

      # Always sample first 5 traces/second per tenant (new tenant detection)
      - name: rate-limit-policy
        type: rate_limiting
        rate_limiting:
          spans_per_second: 5
```

**Pravah's sampling policy:**
- All error traces: 100% sampled — you always want to see what failed
- All traces with latency > 5 seconds: 100% sampled — always want to see slow paths
- All traces for new or unknown tenants: higher sampling rate for observability
- Normal successful fast traces: 1% sampled — baseline for pattern analysis

This results in roughly 5–10% of total traces being kept, with 100% retention for the traces that actually matter.

## Trace Context Through Kafka — The Hard Part

HTTP and gRPC propagation is automatic. Kafka is harder because messages are asynchronous — the producer and consumer are decoupled in time. The trace context must travel through the Kafka message headers.

**The problem without propagation:**

```
Execution Service publishes to job.assigned (starts a trace: T1)
  ... message sits in Kafka for 200ms ...
Consumer in Execution Service reads from job.assigned (starts a NEW trace: T2)
```

T1 and T2 are separate traces. You cannot see that T2 was caused by T1. The trace is broken.

**With propagation:**

```java
// Producer side — inject trace context into message headers
@Service
public class JobEventPublisher {

    public void publishJobAssigned(Job job) {
        ProducerRecord<String, byte[]> record = new ProducerRecord<>(
            "job.assigned", job.getId(), serialize(job)
        );

        // OpenTelemetry Kafka instrumentation automatically injects:
        // traceparent header into the Kafka record
        // The current span's context travels with the message
        kafkaTemplate.send(record);
    }
}
```

```java
// Consumer side — extract trace context from message headers
@KafkaListener(topics = "job.assigned")
public void handleJobAssigned(ConsumerRecord<String, byte[]> record) {
    // OpenTelemetry Kafka instrumentation automatically:
    // 1. Extracts traceparent from record headers
    // 2. Creates a new span as a child of the producer's span
    // 3. Sets it as the current span for this thread

    Job job = deserialize(record.value());
    assignmentService.process(job);
}
```

The result: a single trace shows the entire journey — API Gateway → Scheduler → Kafka (producer span) → Kafka (consumer span) → Execution Service → gRPC → Runner, with the 200ms Kafka transit time visible as the gap between producer and consumer spans.

## Jaeger — The Tracing Backend

Jaeger stores traces and provides a UI for searching, filtering, and visualizing them.

### Trace Search in Pravah

Common Jaeger queries during incident investigation:

```
# Find all traces for a specific job
service=execution-service, tag=job.id:job-xyz-123

# Find all error traces in the last hour
service=*, error=true, lookback=1h

# Find all slow traces (>5s) for a specific tenant
service=api-gateway, tag=tenant.id:megacorp, duration>5000ms

# Find traces related to runner assignment failures
service=runner-service, operation=assign-runner, tag=assignment.result:QUEUED, lookback=30m
```

### Trace Visualization

Jaeger renders traces as Gantt charts — each span is a horizontal bar showing when it ran and how long it took:

```
Trace: pipeline-trigger (total: 45.3s)
├── API Gateway: POST /trigger                          [100ms]
├── Scheduler: resolve-dag                             [200ms]
│   ├── PostgreSQL: SELECT pipeline config             [12ms]
│   └── Kafka: publish job.assigned                    [8ms]
├── [Kafka transit: job.assigned queue]                [150ms]
├── Execution Service: consume job.assigned
│   ├── Redis: check-runner-availability               [3ms]
│   ├── assign-runner (waiting for runner)             [28,400ms] ← HERE
│   ├── PostgreSQL: insert job + outbox                [15ms]
│   └── gRPC: send job to runner-001                   [22ms]
├── [Runner: execute pipeline]                         [16,200ms]
└── gRPC callback: publish result                      [45ms]
```

The 28.4-second runner assignment span is immediately visible as the bottleneck. The `queue_depth: 847` attribute tells you why: 847 jobs were ahead in the queue.

## Correlating Traces with Logs and Metrics

The power of observability comes from correlating all three signals.

**Trace → Logs:** every log entry in Pravah includes the `trace_id` and `span_id` from the current trace. When you find a slow span in Jaeger, you can search Kibana/Elasticsearch for all log entries with that `trace_id`:

```json
{
  "timestamp": "2024-01-15T10:00:28.400Z",
  "level": "WARN",
  "service": "execution-service",
  "trace_id": "a3b4c5d6e7f8901234567890abcdef",
  "span_id": "f1e2d3c4b5a6",
  "message": "Runner assignment delayed — queue depth 847, waiting for available runner",
  "tenant_id": "megacorp",
  "job_id": "job-xyz"
}
```

**Trace → Metrics:** Jaeger can be configured to emit RED metrics (Request rate, Error rate, Duration) per service and operation, automatically derived from trace data. This connects the trace-level detail back to the metric-level alerting.

**Metrics → Traces:** Grafana's exemplar support links data points on a metric graph to representative traces. When the p99 latency spike appears on the dashboard, clicking the data point opens the Jaeger trace that caused it.

```yaml
# Prometheus exemplar configuration (connects metrics to traces)
# Each histogram observation can carry a trace_id exemplar
pravah_job_dispatch_duration_seconds_bucket{le="10.0"} 99954
# Exemplar: {trace_id="a3b4c5d6..."} 45.3
```

## System Design Interview Angles

**"How does Pravah propagate trace context through Kafka messages?"**

> Kafka is asynchronous — the producer and consumer are decoupled in time, unlike HTTP where context propagation is synchronous. Without explicit propagation, producer and consumer create separate traces with no link between them.
>
> OpenTelemetry's Kafka instrumentation handles this automatically. On the producer side, it injects the current span's context into Kafka message headers as a `traceparent` header following the W3C TraceContext spec. On the consumer side, it extracts the trace context from message headers and creates a child span with the producer span as parent.
>
> The result is a single continuous trace that shows the message transit time as a visible gap between the producer span ending and the consumer span beginning. When we see a 200ms gap, that's Kafka processing time. When we see a 10-second gap, that's consumer lag — the message was sitting in the partition waiting for a consumer to process it.

**"How do you decide what sampling rate to use for tracing?"**

> The goal is to capture traces that are useful while controlling storage and processing cost. Simple probabilistic sampling (1%) works for baseline analysis but misses the traces you most need: errors and slow requests.
>
> Pravah uses tail-based sampling in the OpenTelemetry Collector. The collector buffers spans for up to 10 seconds and applies policies after seeing the complete trace. The policies: always keep traces with any error span (100%), always keep traces above 5 seconds (100%), keep 1% of normal healthy traces for baseline, and keep higher rates for traces from new tenants.
>
> This results in roughly 5–10% of traces stored but 100% of error and slow traces stored. Storage cost is controlled while the traces that matter most are never lost.

**"What attributes do you add to spans beyond what auto-instrumentation provides?"**

> Auto-instrumentation captures the infrastructure layer — HTTP method, status code, SQL query text, Kafka topic, gRPC method. That tells you what happened technically. Business attributes tell you what it meant.
>
> In Pravah: `tenant.id`, `tenant.tier`, `job.id`, `pipeline.id`, `pipeline.type`, `runner.id`, `runner.type`, `assignment.result`, `assignment.queue_depth`, `saga.compensation_triggered`. These attributes turn a generic "Execution Service called PostgreSQL" span into "megacorp's ETL job was queued because 847 jobs were ahead with a saturation runner pool." The first is infrastructure telemetry. The second is operational insight.

## Key Takeaways

1. **Metrics show aggregate behavior; traces show individual request paths.** Both are necessary. Metrics tell you p99 latency is elevated. Traces tell you the specific bottleneck in the specific slow request.

2. **Trace = collection of spans with a shared trace ID.** Span = single unit of work with start time, duration, parent reference, and attributes. Context propagation links spans across service boundaries.

3. **Propagation over HTTP:** W3C `traceparent` header (auto). Over gRPC: metadata header (auto). Over Kafka: message headers (auto with OTel Kafka instrumentation). Kafka propagation is the critical one to understand — the async nature means you must explicitly configure it.

4. **OpenTelemetry is the standard.** Single SDK instruments once. Backend (Jaeger, Datadog, Tempo) is a Collector configuration change. Avoids vendor lock-in.

5. **Tail-based sampling over head-based.** Head-based samples blindly — error traces get sampled out. Tail-based samples after seeing the complete trace — 100% of errors and slow traces, 1% of normal traces.

6. **Business attributes are as important as infrastructure attributes.** `job.id`, `tenant.id`, `assignment.result`, `queue_depth` turn infrastructure traces into operational insights.

7. **Correlation is the payoff.** Trace → logs via `trace_id` in every log entry. Metrics → traces via Grafana exemplars. Traces → metrics via RED metrics derived from span data. Together: find the metric spike, click to the exemplar trace, navigate to the log entries, see the full story.
