# 4.4 Structured Logging & the ELK Stack

## Why Logs Exist and What They Are For

Metrics show you that something is wrong. Traces show you where in the request path the problem occurred. Logs show you exactly what the system was doing at each moment — the specific data, the decision made, and the error encountered.

A log is a discrete, timestamped record of a notable event. Unlike metrics (aggregated numbers) and traces (request paths), logs capture the full context of individual events — the exact SQL query that failed, the specific payload that caused a deserialization error, the precise state of a saga when a compensating transaction triggered.

Logs are indispensable for:
- Root cause analysis after an incident
- Debugging errors that only appear in specific conditions
- Audit trails for compliance (who did what, when)
- Understanding behavior that metrics and traces cannot capture

## Unstructured Logs — Why They Fail at Scale

A typical Java application's default log output looks like this:

```
2024-01-15 10:00:23.142 INFO  [scheduling-1] c.p.scheduler.TriggerService - 
  Triggering pipeline pipe-abc for tenant megacorp at 10:00

2024-01-15 10:00:23.987 ERROR [execution-2] c.p.execution.JobService - 
  Failed to assign runner for job job-xyz: no runners available, queue depth: 847

2024-01-15 10:00:24.001 WARN  [kafka-consumer-1] c.p.outbox.OutboxRelay - 
  Outbox publish retry 3/5 for message msg-999
```

This is unstructured log output. For a single developer reading logs locally, it is adequate. At Pravah's scale — 10 services, each with 5 pods, emitting thousands of log lines per second — it becomes unusable:

- **Grep fails:** `grep "job-xyz"` across 50 pod log files simultaneously returns a flood of unformatted lines with no reliable field boundaries
- **Aggregation is impossible:** counting errors by type, by tenant, or by time period requires complex regex parsing — fragile and slow
- **Correlation breaks:** the error log and the trace that caused it have no reliable link
- **Schema drift:** `"no runners available, queue depth: 847"` today, `"runner pool exhausted (depth=847)"` tomorrow — both mean the same thing but grep misses one
- **Alerting is fragile:** alerting on log content requires pattern matching on human-readable strings that change with refactoring

**Structured logging solves all of this** by emitting logs as machine-readable JSON with defined, consistent fields.

## Structured Logging in Pravah

Every log line from every Pravah service is a JSON object with a defined schema:

```json
{
  "timestamp": "2024-01-15T10:00:23.987Z",
  "level": "ERROR",
  "service": "execution-service",
  "pod": "execution-service-7b4d9f-k2x8p",
  "version": "1.4.2",
  "trace_id": "a3b4c5d6e7f8901234567890abcdef12",
  "span_id": "f1e2d3c4b5a60000",
  "tenant_id": "megacorp",
  "job_id": "job-xyz-789",
  "pipeline_id": "pipe-abc",
  "logger": "com.pravah.execution.JobAssignmentService",
  "thread": "kafka-consumer-1",
  "message": "Failed to assign runner — no eligible runners available",
  "error": {
    "type": "RunnerUnavailableException",
    "message": "No runners with required tags [gpu, eu-west] have capacity",
    "stack_trace": "com.pravah.execution.RunnerUnavailableException: ..."
  },
  "context": {
    "required_tags": ["gpu", "eu-west"],
    "eligible_runners_found": 0,
    "queue_depth": 847,
    "assignment_attempt": 1
  }
}
```

Every field has a defined name, type, and meaning. This log is immediately filterable, searchable, and aggregatable — no regex required.

### Pravah's Mandatory Log Fields

Every log entry across every service must include:

| Field | Type | Description |
|---|---|---|
| `timestamp` | ISO 8601 UTC | When the event occurred |
| `level` | enum | DEBUG, INFO, WARN, ERROR |
| `service` | string | Service name (execution-service, runner-service, ...) |
| `pod` | string | Kubernetes pod name (for multi-pod correlation) |
| `version` | string | Service version (for deployment-correlated debugging) |
| `trace_id` | string | OpenTelemetry trace ID (links log to trace in Jaeger) |
| `span_id` | string | OpenTelemetry span ID |
| `logger` | string | Fully qualified class name |
| `thread` | string | Thread name |
| `message` | string | Human-readable description (concise, not the only data) |

Context-dependent fields (added when available):

| Field | When Present |
|---|---|
| `tenant_id` | Any tenant-scoped operation |
| `job_id` | Any job lifecycle event |
| `pipeline_id` | Any pipeline operation |
| `runner_id` | Any runner operation |
| `kafka_topic` | Any Kafka publish/consume event |
| `kafka_offset` | Kafka consume events |
| `http_method`, `http_path`, `http_status` | HTTP request handling |
| `db_table`, `db_operation` | Database operations |
| `error` | Any error or exception |

### Logback Configuration for Structured JSON Output

```xml
<!-- logback-spring.xml — all Pravah services -->
<configuration>
    <springProfile name="!local">
        <!-- Production: JSON output for ELK ingestion -->
        <appender name="JSON_STDOUT" class="ch.qos.logback.core.ConsoleAppender">
            <encoder class="net.logstash.logback.encoder.LogstashEncoder">
                <includeCallerData>false</includeCallerData>
                <includeMdc>true</includeMdc>
                <fieldNames>
                    <timestamp>timestamp</timestamp>
                    <message>message</message>
                    <levelValue>[ignore]</levelValue>
                </fieldNames>
                <!-- Custom fields added to every log line -->
                <customFields>{"service":"${SERVICE_NAME}","version":"${SERVICE_VERSION}"}</customFields>
                <providers>
                    <mdc/>           <!-- includes MDC fields: trace_id, tenant_id, job_id -->
                    <context/>       <!-- logback context properties -->
                    <timestamp/>
                    <logLevel/>
                    <loggerName/>
                    <threadName/>
                    <message/>
                    <logstashMarkers/>
                    <stackTrace/>
                </providers>
            </encoder>
        </appender>
        <root level="INFO">
            <appender-ref ref="JSON_STDOUT"/>
        </root>
    </springProfile>

    <springProfile name="local">
        <!-- Development: human-readable format -->
        <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
            <encoder>
                <pattern>%d{HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n</pattern>
            </encoder>
        </appender>
        <root level="DEBUG">
            <appender-ref ref="CONSOLE"/>
        </root>
    </springProfile>
</configuration>
```

### MDC — Mapped Diagnostic Context

MDC is a thread-local map that Logback automatically includes in every log line from that thread. Pravah uses MDC to propagate context fields without passing them to every method:

```java
@Component
public class LoggingContextFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
                         FilterChain chain) throws IOException, ServletException {
        try {
            HttpServletRequest httpRequest = (HttpServletRequest) request;
            String tenantId = httpRequest.getHeader("X-Tenant-ID");
            String requestId = httpRequest.getHeader("X-Request-ID");

            // Set MDC — automatically included in every log from this thread
            MDC.put("tenant_id", tenantId);
            MDC.put("request_id", requestId);

            // OpenTelemetry sets trace_id and span_id in MDC automatically
            // (via opentelemetry-logback-appender)

            chain.doFilter(request, response);
        } finally {
            MDC.clear();  // critical — thread pool reuse requires cleanup
        }
    }
}
```

```java
// For Kafka consumers — set MDC from message context
@KafkaListener(topics = "job.assigned")
public void handleJobAssigned(ConsumerRecord<String, byte[]> record) {
    try {
        MDC.put("kafka_topic", record.topic());
        MDC.put("kafka_partition", String.valueOf(record.partition()));
        MDC.put("kafka_offset", String.valueOf(record.offset()));

        Job job = deserialize(record.value());
        MDC.put("job_id", job.getId());
        MDC.put("tenant_id", job.getTenantId());
        MDC.put("pipeline_id", job.getPipelineId());

        assignmentService.process(job);
    } finally {
        MDC.clear();
    }
}
```

With MDC, every log line from the job assignment process automatically includes `job_id`, `tenant_id`, `pipeline_id`, `kafka_topic`, `trace_id` — without any of the business logic methods receiving these as parameters.

## What to Log and What Not to Log

This is where most teams get it wrong. Too little logging means you cannot debug. Too much is noise, cost, and a security risk.

### Log This

**Business-significant events (always at INFO):**
```java
log.info("Pipeline triggered", structured("pipeline_id", pipelineId, "source", source));
log.info("Job assigned to runner", structured("job_id", jobId, "runner_id", runnerId));
log.info("Saga compensation triggered", structured("saga_id", sagaId, "step", step));
log.info("Runner disconnected", structured("runner_id", runnerId, "reason", reason));
```

**Warnings — unexpected but recoverable:**
```java
log.warn("Outbox publish retry", structured("message_id", msgId, "attempt", attempt));
log.warn("Cache miss — falling back to database", structured("key", key));
log.warn("Runner heartbeat missed — marking stale", structured("runner_id", runnerId));
```

**Errors — unexpected and potentially impactful:**
```java
log.error("Failed to assign runner", e, structured("job_id", jobId, "queue_depth", depth));
log.error("Database connection failed", e, structured("service", service, "host", host));
log.error("Saga compensation failed", e, structured("saga_id", sagaId, "step", step));
```

**Security-relevant events (always at INFO or higher):**
```java
log.info("Authentication failed", structured("user_id", userId, "ip", ip, "reason", reason));
log.info("API key rotated", structured("tenant_id", tenantId, "rotated_by", actor));
log.warn("Rate limit exceeded", structured("tenant_id", tenantId, "endpoint", endpoint));
```

### Never Log This

**Secrets and credentials — ever:**
```java
// ❌ Never
log.info("Connecting to database with password: " + dbPassword);
log.debug("JWT token: " + jwtToken);
log.info("Vault secret: " + secretValue);
```

**PII (Personally Identifiable Information):**
```java
// ❌ Never — GDPR/compliance violation
log.info("User email: " + user.getEmail());
log.debug("User name: " + user.getFullName());
```

**High-volume debug paths in production:**
```java
// ❌ This fires for every Kafka message — 10,000/min → millions of log lines
log.debug("Processing message from Kafka");  // at DEBUG in prod = millions/min

// ✅ Use sampling or only log on exceptions
if (log.isDebugEnabled()) {
    log.debug("Kafka message details", structured("offset", offset, "size", payload.length));
}
```

**Full request/response bodies:**
```java
// ❌ Could contain secrets, PII, or be enormous
log.info("Request body: " + requestBody.toString());

// ✅ Log the shape, not the content
log.info("Request received", structured("endpoint", endpoint, "content_length", body.length));
```

## The ELK Stack — Aggregation and Search

ELK = Elasticsearch + Logstash + Kibana. Together they collect, store, and query logs from all pods across all services.

```
Pravah Pod (any service)
  │ JSON logs to stdout
  ▼
Filebeat (DaemonSet — one per Kubernetes node)
  Reads container log files from /var/log/containers/
  Adds metadata: pod name, namespace, node, labels
  │
  ▼
Logstash (aggregation and parsing pipeline)
  Parses JSON → validates schema → enriches → routes
  │
  ▼
Elasticsearch (storage and indexing)
  Index: pravah-logs-YYYY.MM.DD (daily rotation)
  Retention: 30 days hot → 90 days warm → archive
  │
  ▼
Kibana (search and visualization)
  Incident investigation, log exploration, dashboards
```

### Filebeat Configuration (Kubernetes DaemonSet)

```yaml
# filebeat.yaml
filebeat.autodiscover:
  providers:
    - type: kubernetes
      node: ${NODE_NAME}
      hints.enabled: true
      hints.default_config:
        type: container
        paths:
          - /var/log/containers/*${data.kubernetes.container.id}.log

processors:
  - add_kubernetes_metadata:
      host: ${NODE_NAME}
      matchers:
        - logs_path:
            logs_path: /var/log/containers/

  # Drop non-Pravah pods
  - drop_event:
      when:
        not:
          equals:
            kubernetes.namespace: pravah

output.logstash:
  hosts: ["logstash:5044"]
```

### Logstash Pipeline for Pravah Logs

```ruby
# logstash.conf
input {
  beats {
    port => 5044
  }
}

filter {
  # Parse JSON log output from Pravah services
  json {
    source => "message"
    target => "log"
    remove_field => ["message"]
  }

  # Validate required fields — drop malformed logs
  if ![log][service] or ![log][timestamp] {
    drop {}
  }

  # Map to Elasticsearch document structure
  mutate {
    add_field => {
      "[@timestamp]"  => "%{[log][timestamp]}"
      "[service]"     => "%{[log][service]}"
      "[level]"       => "%{[log][level]}"
      "[trace_id]"    => "%{[log][trace_id]}"
      "[tenant_id]"   => "%{[log][tenant_id]}"
      "[job_id]"      => "%{[log][job_id]}"
      "[message]"     => "%{[log][message]}"
    }
  }

  # Add Kubernetes metadata from Filebeat
  mutate {
    add_field => {
      "[pod]"         => "%{[kubernetes][pod][name]}"
      "[node]"        => "%{[kubernetes][node][name]}"
    }
  }
}

output {
  elasticsearch {
    hosts => ["elasticsearch:9200"]
    index => "pravah-logs-%{+YYYY.MM.dd}"
    template_name => "pravah-logs"
    template_overwrite => true
  }
}
```

### Elasticsearch Index Template

The index template defines field types — critical for search performance:

```json
{
  "index_patterns": ["pravah-logs-*"],
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1,
    "index.lifecycle.name": "pravah-logs-policy",
    "index.lifecycle.rollover_alias": "pravah-logs"
  },
  "mappings": {
    "properties": {
      "@timestamp":   { "type": "date" },
      "service":      { "type": "keyword" },
      "level":        { "type": "keyword" },
      "trace_id":     { "type": "keyword" },
      "span_id":      { "type": "keyword" },
      "tenant_id":    { "type": "keyword" },
      "job_id":       { "type": "keyword" },
      "pipeline_id":  { "type": "keyword" },
      "runner_id":    { "type": "keyword" },
      "message":      { "type": "text", "analyzer": "standard" },
      "pod":          { "type": "keyword" },
      "version":      { "type": "keyword" },
      "error": {
        "properties": {
          "type":       { "type": "keyword" },
          "message":    { "type": "text" },
          "stack_trace":{ "type": "text", "index": false }
        }
      }
    }
  }
}
```

`keyword` fields support exact-match filtering and aggregations. `text` fields are full-text searched. Stack traces are stored but not indexed (too large, rarely searched directly).

### Index Lifecycle Management (ILM)

Logs older than 30 days are cold. Older than 90 days are archived or deleted.

```json
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_size": "50gb",
            "max_age": "1d"
          },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "30d",
        "actions": {
          "shrink": { "number_of_shards": 1 },
          "forcemerge": { "max_num_segments": 1 },
          "set_priority": { "priority": 50 }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

## Incident Investigation with Kibana

During an incident, logs are how you understand exactly what happened. A structured, well-indexed log store makes the difference between a 5-minute and a 50-minute investigation.

**Scenario: Jobs failing for tenant megacorp for the last 10 minutes**

**Step 1 — Find error logs for the affected tenant:**

Kibana query:
```
tenant_id: "megacorp" AND level: "ERROR" AND @timestamp: [now-15m TO now]
```

Returns: 342 error logs. All from `execution-service`. All with:
```
"message": "Failed to assign runner — no eligible runners available"
"context.queue_depth": 847
"context.required_tags": ["gpu", "eu-west"]
```

**Step 2 — Check if this is tenant-specific or platform-wide:**

```
level: "ERROR" AND @timestamp: [now-15m TO now]
```

Aggregation by `tenant_id`: 342 errors for `megacorp`, 0 for all other tenants.

Platform-wide issue ruled out. Specific to megacorp.

**Step 3 — Trace the specific failure:**

Find the `trace_id` from one of the error logs: `a3b4c5d6e7f8...`

Open Jaeger, search for this trace. See the full journey — 28.4 seconds in runner assignment, `queue_depth: 847`, `eligible_runners_found: 0`.

**Step 4 — Understand why the runner pool is exhausted:**

```
tenant_id: "megacorp" AND service: "runner-service" AND @timestamp: [now-2h TO now]
```

Find: two hours ago, megacorp's self-hosted runner cluster went offline (network partition between on-prem and cloud). All 12 of their runners disconnected. All their queued jobs are waiting for runners that aren't there.

**Step 5 — Confirm the timeline:**

```
tenant_id: "megacorp" AND message: "Runner disconnected" AND @timestamp: [now-2h TO now-90m]
```

12 runner disconnection events at 08:00 UTC. Queue depth started growing at 08:01.

Root cause identified in under 5 minutes. Resolution: notify tenant of their runner connectivity issue, provision cloud runners to process their backlog.

## Log Volume Management

At Pravah's scale, unmanaged logging creates enormous volume and cost.

**Volume estimation:**
```
Services:          10
Pods per service:  5 average
Log lines/pod/sec: 100 average, 500 at peak
JSON bytes/line:   600 bytes average

Steady state: 10 × 5 × 100 × 600 = 3 MB/second = 250 GB/day
Peak:         10 × 5 × 500 × 600 = 15 MB/second = 1.3 TB/day
```

**Techniques to manage volume:**

**1. Level discipline:** DEBUG only in local/staging. INFO for business events. WARN for anomalies. ERROR for failures. Never DEBUG in production.

**2. Sampling high-volume paths:** health check endpoint logs are useless and frequent:
```java
// Suppress access logs for /health and /metrics — 1000s of lines/min of noise
@Bean
public CommonsRequestLoggingFilter loggingFilter() {
    CommonsRequestLoggingFilter filter = new CommonsRequestLoggingFilter();
    filter.setExcludeUriPatterns("/actuator/health", "/actuator/prometheus");
    return filter;
}
```

**3. Deduplication in Logstash:** repeated identical errors (same message, same stack trace, within 1 second) can be collapsed with a count:
```ruby
# Logstash: deduplicate rapid repeated errors
aggregate {
  task_id => "%{service}-%{[error][type]}"
  code => "map['count'] ||= 0; map['count'] += 1; event.set('error_count', map['count'])"
  push_previous_map_as_event => true
  timeout => 1
}
```

**4. Index partitioning by log level:** ERROR and WARN logs go to a separate high-priority index with longer retention. DEBUG and INFO logs have shorter retention.

## FAANG Interview Angles

**"What is structured logging and why does it matter at scale?"**

> Structured logging means emitting logs as machine-readable JSON with defined field names rather than free-form text strings. At small scale, `grep` on human-readable text works. At Pravah's scale — 10 services, 50 pods, thousands of log lines per second — you need to query logs the same way you query a database.
>
> With structured logging, finding all errors for tenant megacorp in the last 15 minutes is a two-second Kibana query: `tenant_id:"megacorp" AND level:"ERROR"`. With unstructured logs, it's a fragile regex across 50 log files that breaks whenever a developer changes the error message wording.
>
> The other critical benefit is correlation: every structured log line includes the `trace_id` from the current OpenTelemetry span. When Jaeger shows a slow trace, I can immediately find all log lines with that trace ID in Kibana and see exactly what each service was doing during that trace.

**"How do you prevent logging secrets or PII in a microservices system?"**

> Three layers of defense. First, developer discipline and code review — any log statement containing user data, credentials, or request bodies is rejected in review. Second, static analysis — we run a linter that flags common patterns like `log.*password`, `log.*token`, `log.*secret` in CI. Third, log scrubbing in Logstash — a filter masks values whose keys match a blocklist: `password`, `secret`, `token`, `authorization`, `api_key`.
>
> The structural approach also helps: by logging field names rather than formatted strings (`log.info("Job created", structured("job_id", jobId))` rather than `log.info("Created job " + jobId + " for user " + user.getEmail())`), you're less likely to accidentally include sensitive context because the fields are explicit.

**"How does MDC help and what can go wrong with it?"**

> MDC (Mapped Diagnostic Context) is a thread-local map in Logback. You set fields like `tenant_id`, `job_id`, and `trace_id` once when a request arrives, and every log statement from that thread for the rest of the request automatically includes those fields — without passing them as parameters to every method.
>
> The critical failure mode: thread pool reuse. When a thread finishes handling one request and is returned to the pool, the MDC is still set from the previous request. The next request processed by that thread logs with the wrong `tenant_id` and `job_id`. This causes mis-correlated logs — you search for megacorp's logs and find techgiant's events.
>
> The fix: always clear MDC in a `finally` block when the request completes. `MDC.clear()` must be called unconditionally — not just on success. We enforce this with a filter that wraps all incoming requests and clears MDC after the filter chain completes.

## Key Takeaways

1. **Structured logging = JSON with defined fields.** Makes logs queryable like a database. Unstructured text logs are only useful for a single developer reading in real-time.

2. **Mandatory fields on every log line:** `timestamp`, `level`, `service`, `pod`, `version`, `trace_id`, `span_id`. `trace_id` is the critical link between logs and traces.

3. **MDC propagates context automatically.** Set `tenant_id`, `job_id`, `pipeline_id` once in the request filter or Kafka consumer. Every subsequent log from that thread includes these fields. Clear MDC in a `finally` block — thread pool reuse without clearing causes mis-correlated logs.

4. **Never log:** credentials, API keys, JWT tokens, passwords, PII (email, name, phone). Enforce in code review + static analysis + Logstash scrubbing.

5. **ELK pipeline:** Filebeat (pod log collection, DaemonSet) → Logstash (parse, validate, enrich) → Elasticsearch (index with field types) → Kibana (search, dashboards, investigation).

6. **Elasticsearch field types matter:** `keyword` for exact-match search and aggregation (tenant_id, level, service), `text` for full-text search (message), `date` for time range queries. Wrong field type = slow queries or missing results.

7. **ILM for cost management:** 30 days hot → warm (compressed, single shard) → 90 days delete. Separate indexes for ERROR/WARN (longer retention) vs DEBUG/INFO.

8. **Incident investigation flow:** filter by `tenant_id` + `level:ERROR` → identify error pattern → find `trace_id` → open in Jaeger → full request path → correlate with metrics → root cause.
