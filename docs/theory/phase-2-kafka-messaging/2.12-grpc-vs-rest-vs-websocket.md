# 2.12 gRPC vs REST vs WebSocket — When to Use What

## The Protocol Choice Problem

Pravah has many different communication needs, and no single protocol wins everywhere. Understanding when each fits is what matters for system design interviews.

| Communication need | Protocol chosen |
|---|---|
| User creates pipeline in UI | REST |
| Runner streams logs to cloud | gRPC bidirectional |
| UI shows live pipeline execution progress | WebSocket |
| Scheduler calls Execution Service | gRPC unary |
| Enterprise client calls Pravah API | REST |
| Agent chat (streaming LLM responses) | WebSocket |

---

## The Three Protocols — Core Characteristics

### REST (HTTP/1.1 or HTTP/2)

**Model:** Request → Response. Client always initiates. Server responds once.

**Strengths:**
- Every language has an HTTP client — universal compatibility
- `curl`, Postman, browser DevTools, OpenAPI/Swagger documentation
- Built-in caching for GET requests (ETags, Cache-Control, CDN)
- Stateless by design — scales horizontally without session affinity
- Human-readable JSON payloads (easy to debug)
- URL-based versioning (`/v1/`, `/v2/`) is well understood

**Weaknesses:**
- No server push — server cannot send data without a client request
- New TCP connection overhead per request (HTTP/1.1) or new stream per request (HTTP/2)
- Verbose JSON headers and payloads
- Not suitable for high-frequency, low-latency communication

### gRPC (HTTP/2)

**Model:** Four patterns — unary, server streaming, client streaming, bidirectional streaming.

**Strengths:**
- Binary Protobuf encoding: compact, fast to serialize/deserialize
- HTTP/2 multiplexing: multiple streams over one TCP connection
- HPACK header compression: near-zero header overhead after first request
- Strict schema with code generation: type safety at compile time
- Built-in deadline propagation: cancellation flows through the call chain
- Native flow control via HTTP/2 window sizes

**Weaknesses:**
- No native browser support (requires `grpc-web` proxy)
- Not human-readable — harder to debug without tooling
- Requires protoc code generation; cannot call from `curl` directly
- Caching not built-in

### WebSocket (HTTP Upgrade → WS protocol)

**Model:** Full-duplex persistent connection. Either side can send at any time. Established via HTTP upgrade handshake.

**Strengths:**
- Native browser support — JavaScript `WebSocket` API
- Bidirectional — server can push without client polling
- Low overhead per message (2–14 byte frame headers)
- Good for streaming and real-time push

**Weaknesses:**
- No built-in schema enforcement — application defines message format
- No built-in flow control — must implement application-level pause/resume
- Sticky connections complicate load balancing (need Redis pub/sub fan-out)
- No code generation

## Head-to-Head Comparison

| Dimension | REST | gRPC | WebSocket |
|---|---|---|---|
| Communication direction | Client → Server | Both (4 patterns) | Both |
| Connection model | Stateless per request | Persistent stream | Persistent connection |
| Payload efficiency | Low (JSON + headers) | Very high (Protobuf + HTTP/2) | Medium (app-defined) |
| Browser support | Native ✅ | None ❌ (needs grpc-web) | Native ✅ |
| Server push | No ❌ | Yes ✅ | Yes ✅ |
| Schema enforcement | OpenAPI (optional) | Protobuf (strict) | None |
| Code generation | OpenAPI (optional) | protoc (required) | None |
| Streaming | SSE workaround | Built-in ✅ | Built-in ✅ |
| Load balancing | Easy (per request) | Complex (L7 aware) | Sticky session |
| Firewall friendliness | Excellent (port 443) | Good (port 443) | Good (port 443) |
| First request latency | High (connection setup) | High (connection setup) | High (upgrade) |
| Subsequent latency | Medium (new conn each time) | Very low (existing stream) | Very low (existing conn) |
| Error handling | HTTP status codes | gRPC status codes | Application-defined |

## Pravah's Protocol Architecture

### External boundary — REST

```
Browser UI         ──── REST ──────────────► API Gateway
Enterprise clients ──── REST ──────────────► API Gateway
Python/Java SDK    ──── REST ──────────────► API Gateway
Terraform provider ──── REST ──────────────► API Gateway
Webhook delivery   ──── REST ──────────────► Client endpoints (outbound)
```

**Why REST for external:** Maximum compatibility. Enterprise clients need to call from any language with any HTTP client. REST works with `curl`. OpenAPI generates client SDKs and documentation automatically. GET responses are cacheable by CDN. URL-based versioning is universally understood.

### Browser boundary — REST + WebSocket

```
Browser CRUD operations        ──── REST via API Gateway
Live pipeline execution logs   ──── WebSocket
Live pipeline status updates   ──── WebSocket (or Server-Sent Events)
Agent chat interface           ──── WebSocket
Dashboard metrics (charts)     ──── REST (polling every 5s)
```

**Why WebSocket for real-time browser features:** Server needs to push updates without the client polling. WebSocket is native in browsers. Bidirectional communication enables flow control (pause/resume log stream) and user commands (cancel job). LLM streaming responses require token-by-token push, which WebSocket handles naturally.

**Why REST for dashboard metrics:** Metrics do not need sub-second freshness. REST polling every 5 seconds is simpler than maintaining WebSocket subscriptions for data that changes slowly.

### Internal service boundary — gRPC

```
API Gateway ──── gRPC ──────────► Pipeline Service
API Gateway ──── gRPC ──────────► Scheduler Service
Scheduler   ──── gRPC ──────────► Execution Service
Execution   ──── gRPC ──────────► Runner Service
Execution   ──── gRPC ──────────► Secret Service
Agent       ──── gRPC ──────────► Metadata Service

All services ─── Kafka ──────────► All services (async events)
```

**Why gRPC for internal:** Binary Protobuf is 10× more efficient than JSON. Deadline propagation cancels downstream work when upstream times out. Code generation from `.proto` files ensures type safety across services. The same Protobuf types used for Kafka schemas → single schema language across the system.

### Runner boundary — gRPC bidirectional streaming

```
Self-hosted runner  ──── gRPC bidir stream ──► Cloud control plane
Cloud runner        ──── gRPC bidir stream ──► Cloud control plane
Ephemeral runner    ──── gRPC bidir stream ──► Cloud control plane
```

**Why gRPC bidirectional for runners:** Runners initiate (no inbound ports required). Cloud pushes jobs. Runners stream logs back. All on one persistent connection with HTTP/2 multiplexing, built-in flow control, mTLS, and compact Protobuf encoding.

## REST Design in Pravah

API Gateway exposes REST at `https://api.pravah.io/v1/`.

**Resource design (noun-based, HTTP verbs):**

```
GET    /pipelines                     list pipelines
POST   /pipelines                     create pipeline
GET    /pipelines/{id}                get pipeline
PATCH  /pipelines/{id}                partial update
DELETE /pipelines/{id}                delete pipeline
POST   /pipelines/{id}/trigger        trigger a run (returns 202)
GET    /pipelines/{id}/runs/{run_id}  get specific run

GET    /runners                       list runners
GET    /runners/{id}/jobs             current jobs on runner

GET    /jobs                          list jobs (filterable)
POST   /jobs/{id}/cancel              cancel running job
```

**HTTP status codes used by Pravah:**

| Code | Usage |
|---|---|
| 200 | Successful GET, PUT, PATCH |
| 201 | Successful POST (resource created) |
| 202 | Async operation started (trigger pipeline) |
| 204 | Successful DELETE |
| 400 | Validation error |
| 401 | Missing/invalid JWT |
| 403 | Valid token, insufficient RBAC permission |
| 404 | Resource not found |
| 409 | Optimistic lock conflict |
| 422 | Business rule violation (pipeline dependency cycle) |
| 429 | Rate limit exceeded |
| 503 | Circuit breaker open — service degraded |

**Async pipeline trigger (202 Accepted):**

```
POST /pipelines/abc/trigger
→ 202 Accepted
→ { "run_id": "run-xyz", "status": "QUEUED",
    "poll_url": "/v1/pipelines/abc/runs/run-xyz" }

Client polls:
GET /pipelines/abc/runs/run-xyz
→ { "status": "RUNNING", "progress": 45 }
→ { "status": "COMPLETED", "duration": 145 }

Or subscribes via WebSocket for push updates.
```

**Standard response envelope:**

```json
{
  "data": { "id": "pipe-abc", "name": "Sales ETL", "status": "ACTIVE" },
  "meta": { "page": 1, "per_page": 20, "total": 147, "request_id": "req-xyz-123" },
  "links": { "self": "...", "next": "...", "last": "..." }
}
```

## WebSocket Design in Pravah

WebSocket endpoint: `wss://api.pravah.io/ws/v1/`

**Message envelope:**

```json
{
  "type":    "subscribe | event | command | error",
  "channel": "pipeline.runs | job.logs | agent.chat",
  "payload": { ... }
}
```

**Live log streaming:**

```json
// Client subscribes:
{ "type": "subscribe", "channel": "job.logs", "payload": { "job_id": "job-xyz" } }

// Server streams (continuously):
{ "type": "event", "channel": "job.logs",
  "payload": { "job_id": "job-xyz", "timestamp": "10:05:23.441",
               "level": "INFO", "message": "Extracting 0/1,000,000 rows" } }

// Client pauses:
{ "type": "command", "channel": "job.logs", "payload": { "action": "pause" } }

// Client resumes:
{ "type": "command", "channel": "job.logs", "payload": { "action": "resume" } }
```

**Agent chat (streaming LLM responses token by token):**

```json
// Client sends question:
{ "type": "command", "channel": "agent.chat",
  "payload": { "message": "Why did pipeline-abc fail?",
               "context": { "pipeline_id": "pipe-abc" } } }

// Server streams tokens:
{ "type": "event", "channel": "agent.chat", "payload": { "token": "The", "done": false } }
{ "type": "event", "channel": "agent.chat", "payload": { "token": " pipeline", "done": false } }
{ "type": "event", "channel": "agent.chat", "payload": { "token": ".", "done": true } }
```

**WebSocket scaling — Redis pub/sub fan-out:**

WebSocket connections are sticky: a client connected to Pod 1 cannot receive updates from Pod 2. When Pod 1 crashes, the client reconnects to Pod 2, which has no subscription state.

Pravah solves this with Redis pub/sub as a fan-out layer:

```
Pipeline event occurs (any pod)
        │
        ▼
Redis: PUBLISH channel:pipeline.runs:megacorp {event}
        │
        ▼
ALL gateway pods subscribe to this Redis channel
        │
        ▼
Each pod: find WebSocket clients subscribed → push event ✅

Result: Pod crash → client reconnects to any pod → works ✅
```

## gRPC for Internal Services — Key Feature: Deadline Propagation

Every gRPC call carries a deadline. Deadlines propagate through the entire call chain.

```
User API call → deadline: 30 seconds

API Gateway → Pipeline Service (deadline: 29s)
  Pipeline Service → Runner Service (deadline: 25s)
    Runner Service → Secret Service (deadline: 20s)
      Secret Service: responds in 15s ✅
```

If Secret Service hangs:
```
Secret Service → timeout at deadline
Runner Service: "context cancelled — stop waiting"
Pipeline Service: "context cancelled — stop waiting"
API Gateway: 503 to user

Without deadline propagation:
  User cancels browser request
  API Gateway: 408 timeout
  BUT internal services keep calling Secret Service until their own timeouts
  Wasting threads, connections, compute for minutes
```

With deadline propagation, cancellation flows downstream immediately, freeing all resources.

## REST → gRPC Transcoding at API Gateway

The browser speaks REST and WebSocket. Internal services speak gRPC. The API Gateway bridges them.

```
Browser PATCH /v1/pipelines/pipe-abc
Body: { "name": "Sales ETL v2" }

Gateway:
  1. Parse Authorization header → verify JWT
  2. Extract tenant_id from JWT claims
  3. Check RBAC: can this user update pipe-abc?
  4. Build gRPC request:
       UpdatePipelineRequest {
         pipeline_id: "pipe-abc"
         tenant_id:   "megacorp"
         name:        "Sales ETL v2"
         actor:       "user-xyz"
       }
  5. Call PipelineService.UpdatePipeline(request) → deadline: 10s
  6. Receive Protobuf response
  7. Convert to JSON
  8. Return HTTP 200 with JSON body
```

## Common Mistakes in Protocol Choice

**Mistake 1: REST for high-frequency internal calls**
1000 runners heartbeating via REST = 1000 requests/second + 2KB headers each = 2MB/second in headers. Fix: gRPC bidirectional streaming.

**Mistake 2: WebSocket for simple CRUD**
Opening a WebSocket connection to create one resource (100ms+ setup overhead) is overkill. Fix: REST POST.

**Mistake 3: gRPC for external-facing API**
Enterprise client: "Can I curl your API?" gRPC requires protobuf-generated clients. Fix: REST for external, gRPC internally.

**Mistake 4: Polling instead of WebSocket for live updates**
100 users polling status every 500ms = 200 requests/second just for status. Fix: WebSocket subscription — server pushes only on change.

**Mistake 5: gRPC streaming for durable events**
gRPC streams have no persistence, no replay. If the receiving service crashes, events are lost. Fix: Kafka for durable event streaming; gRPC for real-time control.

```
EXTERNAL:
  Browser UI         ──── REST  ────────► API Gateway
  Browser UI         ──── WS    ────────► API Gateway
  Enterprise clients ──── REST  ────────► API Gateway
  Webhooks (outbound)──── REST  ────────► Client endpoints

INTERNAL SERVICES:
  API Gateway        ──── gRPC  ────────► Pipeline Service
  API Gateway        ──── gRPC  ────────► Scheduler Service
  Scheduler          ──── gRPC  ────────► Execution Service
  Execution          ──── gRPC  ────────► Runner Service
  All services       ──── Kafka ────────► All services (async)

RUNNER PROTOCOL:
  Self-hosted runner ──── gRPC bidir ──► Cloud control plane
  Cloud runner       ──── gRPC bidir ──► Cloud control plane

OBSERVABILITY:
  All services       ──── Prometheus HTTP scrape ──► Prometheus
  All services       ──── OTLP gRPC ──────────────► Jaeger
  All services       ──── TCP log shipper ─────────► ELK
```

**Summary:**
- **REST:** external facing, browser CRUD, webhooks, anything that needs `curl` compatibility
- **WebSocket:** browser real-time push (logs, status, LLM chat)
- **gRPC:** internal services, runner protocol, distributed tracing
- **Kafka:** async events, persistence, replay, fan-out to multiple consumers

## FAANG Interview Angles

**"Walk me through every protocol Pravah uses and why each was chosen."**

> Pravah uses four protocols, each for a specific communication pattern. REST for all external-facing APIs — enterprise clients, Python SDK, Terraform provider need maximum compatibility; REST over HTTPS works from any language with any HTTP client, GET requests are cacheable, and OpenAPI generates documentation and client SDKs. WebSocket for browser real-time features — live log streaming, pipeline status updates, and LLM response streaming require server push, which WebSocket provides natively in browsers; Redis pub/sub fan-out solves the sticky connection problem. gRPC for internal service-to-service calls — binary Protobuf is 10× more efficient than JSON, deadline propagation cancels downstream work when upstream times out, and code generation ensures type safety. gRPC bidirectional streaming for the runner protocol — runners initiate (no inbound ports), cloud pushes jobs, runners stream logs back — all on one persistent connection with built-in flow control and mTLS.

**"Why doesn't Pravah use WebSocket for the runner protocol instead of gRPC?"**

> WebSocket would work but gRPC gives three things WebSocket doesn't. First, schema enforcement: the runner protocol is defined in `.proto` files; protoc generates Java code for both runner and cloud, making type mismatches compile errors rather than runtime surprises. Second, flow control: HTTP/2's window-based flow control automatically throttles runners when they generate logs faster than the cloud can process — no application-level pause/resume messages needed. Third, efficiency: a heartbeat is 49 bytes over gRPC versus 2KB+ over WebSocket with JSON; at 10,000 runners heartbeating every 10 seconds, that difference is meaningful.

---

## Key Takeaways

1. **No single protocol wins everywhere** — match protocol to the communication pattern
2. **REST:** external clients, browser CRUD, caching, maximum ecosystem compatibility
3. **WebSocket:** browser real-time push, bidirectional browser communication, streaming responses
4. **gRPC:** internal service-to-service, high-frequency efficiency, type safety, deadline propagation, persistent streaming
5. **Kafka:** decoupled async, persistence, replay, fan-out — not a substitute for real-time control
6. **WebSocket scaling:** Redis pub/sub fan-out solves sticky connection problem — any pod can serve any subscription
7. **Deadline propagation:** critical for preventing resource waste — cancelled request stops all downstream work
8. **REST ↔ gRPC translation** at API Gateway: JSON ↔ Protobuf conversion; authentication + RBAC at gateway boundary
