2.12 gRPC vs REST vs WebSocket — When to Use What
🧩 Start With The Core Question
THE PROTOCOL CHOICE PROBLEM
────────────────────────────────────────────────────────────

Pravah has many different communication needs:

  User creates pipeline in UI
  → Single request, expects response
  → REST ✅

  Runner continuously streams logs to cloud
  → Long-lived, bidirectional, high throughput
  → gRPC ✅

  UI shows live pipeline execution progress
  → Server pushes updates to browser
  → WebSocket ✅

  Scheduler calls Execution Service
  → Internal service-to-service, type-safe
  → gRPC ✅

  Enterprise client calls Pravah API
  → External, needs broad language support
  → REST ✅

  No single protocol wins everywhere.
  Understanding WHY each fits is what matters.
📡 The Three Protocols — Core Characteristics
REST (HTTP/1.1 or HTTP/2)
────────────────────────────────────────────────────────────

Model: Request → Response
       Client always initiates
       Server responds once

Transport: HTTP/1.1 (most common) or HTTP/2

Format: JSON (usually), XML, plain text
        Human readable ✅
        Verbose ❌

State: Stateless by design
       Each request independent
       Server holds no client state

Caching: Built-in (GET requests, ETags, Cache-Control)
         HTTP caches, CDN caches

Tooling: Excellent
         Every language has HTTP client
         curl, Postman, browser DevTools
         OpenAPI/Swagger documentation

Versioning: URL-based (/v1/, /v2/)
            Header-based (Accept: application/vnd.pravah.v2+json)

gRPC (HTTP/2)
────────────────────────────────────────────────────────────

Model: Four patterns (unary, server stream,
       client stream, bidirectional)
       
Transport: HTTP/2 only
           Multiplexed streams
           Binary framing

Format: Protocol Buffers (binary)
        Compact ✅
        Not human readable ❌

State: Stateful (persistent streams)
       Server can track stream context

Caching: Not built-in
         Must implement manually if needed

Tooling: Good but requires setup
         grpcurl, Postman (limited), gRPC UI
         protoc for code generation
         Not directly usable from browser

Versioning: Field numbers in Protobuf
            Package namespacing (v1, v2)

WebSocket (HTTP Upgrade → WS protocol)
────────────────────────────────────────────────────────────

Model: Full duplex, persistent connection
       Either side can send at any time
       After HTTP upgrade

Transport: TCP (upgraded from HTTP)
           Text or binary frames
           Lightweight framing (2-14 byte headers)

Format: Application-defined
        Typically JSON for browser compatibility
        No built-in schema

State: Stateful (persistent connection)
       Server tracks each connected client

Caching: None
         Real-time data not cacheable

Tooling: Good browser support
         JavaScript WebSocket API native
         No code generation

Versioning: Application-defined
            Usually URL-based or message-based

🌐 REST in Pravah — Where and Why
PRAVAH'S REST API DESIGN
────────────────────────────────────────────────────────────

API Gateway exposes REST to:
  1. Browser UI (Next.js frontend)
  2. Enterprise clients (via SDK)
  3. Terraform provider
  4. Webhook callbacks

BASE URL: https://api.pravah.io/v1/

RESOURCE DESIGN (noun-based, HTTP verbs):
────────────────────────────────────────────────────────────

Pipelines:
  GET    /pipelines              list pipelines
  POST   /pipelines              create pipeline
  GET    /pipelines/{id}         get pipeline
  PUT    /pipelines/{id}         replace pipeline
  PATCH  /pipelines/{id}         partial update
  DELETE /pipelines/{id}         delete pipeline

  GET    /pipelines/{id}/runs    list runs for pipeline
  POST   /pipelines/{id}/trigger trigger pipeline run
  GET    /pipelines/{id}/runs/{run_id} get specific run

Runners:
  GET    /runners                list runners
  GET    /runners/{id}           get runner
  DELETE /runners/{id}           deregister runner
  GET    /runners/{id}/jobs      current jobs on runner

Jobs:
  GET    /jobs                   list jobs (filterable)
  GET    /jobs/{id}              get job
  POST   /jobs/{id}/cancel       cancel running job

Connectors:
  GET    /connectors             marketplace listing
  POST   /connectors/{id}/install install connector
  GET    /connectors/{id}/versions version history

HTTP STATUS CODES IN PRAVAH:
────────────────────────────────────────────────────────────

200 OK:           Successful GET, PUT, PATCH
201 Created:      Successful POST (resource created)
202 Accepted:     Async operation started (trigger pipeline)
204 No Content:   Successful DELETE
400 Bad Request:  Validation error (invalid pipeline config)
401 Unauthorized: Missing/invalid JWT token
403 Forbidden:    Valid token, insufficient RBAC permission
404 Not Found:    Pipeline/runner not found
409 Conflict:     Optimistic lock conflict (version mismatch)
422 Unprocessable:Business rule violation (pipeline cycle)
429 Too Many:     Rate limit exceeded (token bucket)
500 Server Error: Unexpected internal error
503 Unavailable:  Service degraded (circuit breaker open)

ASYNC API PATTERN (202 Accepted):
────────────────────────────────────────────────────────────

Triggering a pipeline is an async operation.
Don't make client wait for completion.

POST /pipelines/abc/trigger
  → 202 Accepted
  → Response: {
      "run_id": "run-xyz",
      "status": "QUEUED",
      "poll_url": "/v1/pipelines/abc/runs/run-xyz"
    }

Client polls:
GET /pipelines/abc/runs/run-xyz
  → 200 OK { status: "RUNNING", progress: 45% }
  → 200 OK { status: "RUNNING", progress: 78% }
  → 200 OK { status: "COMPLETED", duration: 145s }

Or client subscribes via WebSocket for push updates.

MESSAGE FORMAT (JSON over WebSocket):
────────────────────────────────────────────────────────────

All WebSocket messages follow envelope:
{
  "type":          "subscribe|event|command|error",
  "channel":       "pipeline.runs|job.logs|agent.chat",
  "payload":       { ... }
}

USE CASE 1: LIVE LOG STREAMING
────────────────────────────────────────────────────────────

UI subscribes to job logs:
  Client → Server:
  {
    "type": "subscribe",
    "channel": "job.logs",
    "payload": { "job_id": "job-xyz" }
  }

  Server → Client (continuous):
  {
    "type": "event",
    "channel": "job.logs",
    "payload": {
      "job_id": "job-xyz",
      "timestamp": "10:05:23.441",
      "level": "INFO",
      "message": "Extracting from Postgres: 0/1,000,000 rows",
      "task": "extract"
    }
  }
  (hundreds of these per second)

  Client → Server (flow control):
  {
    "type": "command",
    "channel": "job.logs",
    "payload": { "action": "pause" }
  }

  Server: stops sending logs until resume
  {
    "type": "command",
    "channel": "job.logs",
    "payload": { "action": "resume" }
  }

USE CASE 2: PIPELINE STATUS DASHBOARD
────────────────────────────────────────────────────────────

  Client → Server:
  {
    "type": "subscribe",
    "channel": "pipeline.runs",
    "payload": { "tenant_id": "megacorp" }
  }

  Server → Client (on any pipeline change):
  {
    "type": "event",
    "channel": "pipeline.runs",
    "payload": {
      "pipeline_id": "pipe-abc",
      "run_id": "run-xyz",
      "status": "RUNNING",
      "progress": 45,
      "current_task": "transform",
      "records_processed": 450000
    }
  }

USE CASE 3: AGENT CHAT (STREAMING LLM)
────────────────────────────────────────────────────────────

  User types: "Why did pipeline-abc fail?"

  Client → Server:
  {
    "type": "command",
    "channel": "agent.chat",
    "payload": {
      "message": "Why did pipeline-abc fail?",
      "context": { "pipeline_id": "pipe-abc" }
    }
  }

  Server → Client (token by token from LLM):
  { "type": "event", "channel": "agent.chat",
    "payload": { "token": "The", "done": false } }
  { "type": "event", "channel": "agent.chat",
    "payload": { "token": " pipeline", "done": false } }
  { "type": "event", "channel": "agent.chat",
    "payload": { "token": " failed", "done": false } }
  ...
  { "type": "event", "channel": "agent.chat",
    "payload": { "token": ".", "done": true } }

WEBSOCKET SCALING CHALLENGE:
────────────────────────────────────────────────────────────

Problem: WebSocket connections are sticky.
  UI connects to Pod 1.
  Pod 1 sends live updates.
  Pod 1 crashes → connection lost.
  UI reconnects → might hit Pod 2.
  Pod 2 doesn't have subscription state! ❌

Pravah's solution: Redis pub/sub as fan-out layer

  Pipeline event occurs (any pod knows about it)
        │
        ▼
  Redis: PUBLISH channel:pipeline.runs:megacorp {event}
        │
        ▼
  ALL gateway pods subscribed to this Redis channel
        │
        ▼
  Each pod: find WebSocket clients subscribed to this channel
            Push event to those clients ✅

  Result: Any pod can serve any client's subscription.
          Pod crash → client reconnects to any pod → works ✅
⚙️ gRPC in Pravah — Internal Services
PRAVAH INTERNAL gRPC SERVICES
────────────────────────────────────────────────────────────

Every Pravah service exposes a gRPC interface
for internal service-to-service calls.

PIPELINE SERVICE gRPC API:
────────────────────────────────────────────────────────────

syntax = "proto3";
package io.pravah.internal.pipeline.v1;

service PipelineService {
  // Unary RPCs (request-response)
  rpc GetPipeline(GetPipelineRequest)
      returns (Pipeline);
  rpc CreateJob(CreateJobRequest)
      returns (Job);
  rpc UpdateJobStatus(UpdateJobStatusRequest)
      returns (UpdateJobStatusResponse);
  rpc GetPipelineConfig(GetConfigRequest)
      returns (PipelineConfig);

  // Server streaming (cloud pushes to caller)
  rpc WatchPipelineEvents(WatchRequest)
      returns (stream PipelineEvent);
}

DEADLINE PROPAGATION — KEY gRPC FEATURE:
────────────────────────────────────────────────────────────

Every gRPC call has a deadline.
Deadline propagates through the call chain.

User makes API call → deadline: 30 seconds

  API Gateway → Pipeline Service (deadline: 29s)
    Pipeline Service → Runner Service (deadline: 25s)
      Runner Service → Secret Service (deadline: 20s)
        Secret Service: responds in 15s ✅
      Runner Service: responds ✅
    Pipeline Service: responds ✅
  API Gateway: responds to user ✅

If Secret Service hangs (10 sec timeout):
  Secret Service → timeout at deadline 20s
  Runner Service: "context cancelled, stop waiting"
  Pipeline Service: "context cancelled, stop waiting"
  API Gateway: "Request timed out" → 503 to user

CRITICAL: Without deadline propagation:
  User cancels request at browser
  API Gateway: 408 timeout
  BUT: internal services keep calling Secret Service
       wasting threads, connections, compute
       Until their own timeouts

WITH deadline propagation:
  User cancels → context cancelled propagates
  All internal calls stop immediately ✅
  Resources freed ✅

gRPC vs REST for internal services:
────────────────────────────────────────────────────────────

Why NOT REST for internal:

  REST for Saga orchestrator calling Runner Service:
    POST /internal/runner-service/allocate-runner
    Headers: 2KB
    JSON body: 500 bytes
    Parse JSON → Java object
    Total overhead: ~50μs

  gRPC unary for same call:
    Protobuf binary: 50 bytes
    Direct deserialize to Java object
    Total overhead: ~5μs

  10× lower overhead per internal call.
  With 100,000 calls/minute:
    REST: 5 seconds of CPU wasted on parsing
    gRPC: 0.5 seconds ✅

  At Pravah's scale: this matters.
🔄 Protocol Bridge — API Gateway
HOW API GATEWAY TRANSLATES PROTOCOLS
────────────────────────────────────────────────────────────

Browser speaks REST and WebSocket.
Internal services speak gRPC.
API Gateway bridges them.

┌──────────────────────────────────────────────────────────┐
│                   API GATEWAY                           │
│              (Spring Cloud Gateway)                     │
│                                                         │
│  REST endpoints (/v1/pipelines/...)                     │
│       │                                                 │
│       ▼                                                 │
│  REST → gRPC transcoding:                               │
│    Parse JSON body → Protobuf message                   │
│    Call internal gRPC service                           │
│    Protobuf response → JSON                             │
│    Return HTTP response                                 │
│                                                         │
│  WebSocket endpoints (/ws/v1/...)                       │
│       │                                                 │
│       ▼                                                 │
│  WebSocket → Kafka/Redis subscription:                  │
│    Client subscribes → add to Redis pub/sub group      │
│    Kafka consumer → Redis publish → WebSocket push     │
│                                                         │
│  BOTH need:                                             │
│    Authentication (JWT validation)                      │
│    Rate limiting (token bucket per tenant)              │
│    RBAC checking (can this user do this?)               │
│    Correlation ID injection                             │
│    Request logging                                      │
└──────────────────────────────────────────────────────────┘

REST TO gRPC TRANSCODING EXAMPLE:
────────────────────────────────────────────────────────────

User calls:
  PATCH /v1/pipelines/pipe-abc
  Body: { "name": "Sales ETL v2" }

Gateway:
  1. Parse Authorization header → verify JWT
  2. Extract tenant_id from JWT claims
  3. Check RBAC: can this user update pipe-abc?
  4. Build gRPC request:
       UpdatePipelineRequest {
         pipeline_id: "pipe-abc"
         tenant_id:   "megacorp"
         name:        "Sales ETL v2"
         actor:       "user-xyz"
       }
  5. Call PipelineService.UpdatePipeline(request)
     with deadline: 10 seconds
  6. Receive gRPC response (Protobuf)
  7. Convert to JSON
  8. Return HTTP 200 with JSON body

gRPC-WEB (FUTURE OPTION):
────────────────────────────────────────────────────────────

gRPC-Web allows browsers to call gRPC directly.
Via a proxy that translates HTTP/1.1 → HTTP/2 gRPC.

  Browser → grpc-web proxy → gRPC service

Pravah considers this for the future:
  PRO: Single protocol everywhere
  PRO: Type-safe from browser to service
  CON: Less browser tooling than REST
  CON: Harder debugging (binary protocol)
  CON: Browser DevTools doesn't show gRPC nicely

  Decision: REST for external, gRPC internal.
  Revisit when browser gRPC tooling matures.
🚨 Common Mistakes in Protocol Choice
ANTI-PATTERNS TO AVOID IN PRAVAH
────────────────────────────────────────────────────────────

MISTAKE 1: REST for high-frequency internal calls
  POST /internal/heartbeat every 10 seconds
  1000 runners = 1000 requests/second
  2KB JSON headers per request = 2MB/sec in headers
  
  Fix: gRPC bidirectional streaming
  All heartbeats on persistent stream
  49 bytes per heartbeat ✅

MISTAKE 2: WebSocket for simple CRUD
  User clicks "Create Pipeline"
  Opening WebSocket to create one resource?
  Overkill. WebSocket connection setup: 100ms+
  
  Fix: REST POST /pipelines
  Simple. Cacheable for GET. Standard semantics ✅

MISTAKE 3: gRPC for external-facing API
  Enterprise client: "Can I curl your API?"
  gRPC: "You need protobuf generated client..."
  Enterprise client: "Nevermind."
  
  Fix: REST for external.
  gRPC internally. REST externally. ✅

MISTAKE 4: Polling instead of WebSocket for live updates
  UI polls GET /runs/{id}/status every 500ms
  100 users × 2 requests/second = 200 req/sec
  Just for status updates!
  
  Fix: WebSocket subscription
  Server pushes only on change
  100 users × 0 polling = 0 wasted requests ✅

MISTAKE 5: gRPC streaming for persistent storage needs
  Service streams events to another service via gRPC
  Receiving service crashes → events LOST
  (gRPC streams have no persistence, no replay)
  
  Fix: Kafka for persistent event streaming
  gRPC for real-time control
  Kafka for durable event streaming ✅

❓ "Walk me through every protocol Pravah uses

  "Pravah uses four protocols, each chosen for

   clients, the Python SDK, Terraform provider —
   all need maximum compatibility. REST over HTTPS
   works from any language with any HTTP client,
   supports caching for GET requests, and OpenAPI
   generates documentation and client SDKs.

   WebSocket for browser real-time features. The
   UI needs live log streaming, pipeline status
   updates, and streaming LLM responses for the
   agent chat. WebSocket is native in browsers,
   allows server push, and handles bidirectional
   communication. We use Redis pub/sub behind the
   API Gateway so any gateway pod can serve any
   client's subscription, solving the stickiness
   problem.

   gRPC for internal service-to-service calls.
   Binary Protobuf is 10× more efficient than JSON,
   deadline propagation cancels downstream work when
   upstream times out, and code generation from .proto
   files ensures type safety across services. The
   same Protobuf types we use for Kafka schemas.

   gRPC bidirectional streaming for the runner
   protocol. Runners initiate (no inbound ports),
   cloud pushes jobs, runners stream logs back —
   all on one persistent connection. HTTP/2
   multiplexing handles this elegantly with built-in
   flow control for the log stream."

❓ "Why doesn't Pravah use WebSocket for
    the runner protocol instead of gRPC?"

Good answer:
  "WebSocket would work but gRPC gives us three
   things WebSocket doesn't.

   First, schema enforcement. Our runner protocol
   is defined in .proto files with strict field
   types. protoc generates Java code for both
   runner and cloud — type mismatches are compile
   errors, not runtime surprises. WebSocket messages
   are application-defined — we'd implement custom
   JSON schema validation manually.

   Second, flow control. HTTP/2 has built-in
   window-based flow control. When runners stream
   10,000 log lines per second and the cloud processes
   1,000 per second, HTTP/2 automatically throttles
   the runner by shrinking its send window. WebSocket
   has no built-in flow control — we'd implement
   application-level pause/resume messages.

   Third, efficiency. A runner heartbeat is 49 bytes
   over gRPC vs 2KB+ over WebSocket with JSON. With
   10,000 runners heartbeating every 10 seconds,
   that's 4.9MB/minute vs 1.2GB/minute. At scale,
   this matters for both bandwidth and CPU."
📌 Key Takeaways
1. No single protocol wins everywhere.
   Match protocol to communication pattern.

2. REST when:
   External clients need to call you
   Browser CRUD operations
   Caching is valuable (GET resources)
   Human readability matters (debugging)
   Maximum ecosystem compatibility needed

3. WebSocket when:
   Browser needs real-time server push
   Bidirectional browser communication
   Streaming responses (LLM tokens, logs)
   Subscription-based updates

4. gRPC when:
   Internal service-to-service calls
   High-frequency, efficiency matters
   Strong typing + code generation needed
   Deadline propagation required
   Persistent streaming (runner protocol)

5. Kafka when:
   Decoupled async communication
   Persistence and replay needed
   Multiple consumers for same event
   Fan-out without tight coupling

6. WebSocket scaling: sticky connections solved
   by Redis pub/sub fan-out layer.
   Any gateway pod can serve any subscription.

7. Deadline propagation in gRPC:
   Critical for preventing resource waste.
   Cancelled request → all downstream stops.
   Not available in REST without custom headers.

8. REST ↔ gRPC translation at API Gateway:
   Browser speaks REST, services speak gRPC.
   Gateway bridges: JSON ↔ Protobuf conversion.
   Authentication + RBAC at gateway boundary.

### COMPLETED: Phase 2 — Messaging & Kafka

2.1  Why Kafka
     5 killer requirements: multi-consumer, replay,
     ordering, on-prem runners, CDC+streaming
     RabbitMQ: deletes on consume (no replay)
     SQS: AWS-only, no ordering, no replay
     Kafka: immutable log, consumer groups, CDC ecosystem

2.2  Kafka Architecture
     Broker → Topic → Partition → Segment
     Partition = unit of parallelism + ordering
     Offset = monotonically increasing per partition
     ISR = replicas caught up within lag threshold
