# 2.3 Producer Internals — Batching, Compression & Acknowledgments

## Why Producer Internals Matter

Most engineers treat the Kafka producer as a black box: `producer.send(record)` and done. Getting the internals wrong causes data loss on broker failure, duplicate messages on retry, 10× worse throughput than achievable, and latency spikes under load.

---

## Inside the Producer

```
Application: producer.send(ProducerRecord("pipeline.events", "pipe-abc", payload))

Step 1  SERIALIZATION
        Key:   "pipe-abc" → bytes
        Value: {event:...} → Avro bytes (via schema registry)

Step 2  PARTITIONING
        hash("pipe-abc") % 12 = 7 → partition 7

Step 3  RECORD ACCUMULATOR (in-memory buffer)
        ┌──────────────────────────────────────────┐
        │  Partition 7 batch: [r1][r2][r3] ...     │
        │  Partition 3 batch: [r1][r2]             │
        │  Partition 11 batch: [r1]                │
        └──────────────────────────────────────────┘
              │
              │  when: batch.size reached OR linger.ms elapsed
              ▼
Step 4  COMPRESSION
        Batch compressed as a unit (much better ratio than per-message)

Step 5  SENDER THREAD
        Sends compressed batches to broker leaders.
        Handles acks, retries, in-flight request tracking.
```

---

## Batching — The Throughput Multiplier

**Without batching:**
```
Message 1: [TCP overhead][Kafka header][1 KB payload] → 1 network round trip
Message 2: [TCP overhead][Kafka header][1 KB payload] → 1 network round trip
...
100 messages = 100 round trips × 10ms latency = 1000ms total
Throughput: ~100 messages/sec per partition
```

**With batching:**
```
Batch: [TCP overhead][Kafka header][100 KB payload] → 1 network round trip
100 messages = 1 round trip × 10ms latency = 10ms total
Throughput: ~10,000 messages/sec per partition (100× improvement)
```

**Two controls:**

| Config | Default | Pravah | Meaning |
|---|---|---|---|
| `batch.size` | 16384 (16 KB) | 65536 (64 KB) | Max batch size — send when full |
| `linger.ms` | 0 | 5 | Wait up to N ms for more messages |

A batch sends when **either** limit is hit — whichever comes first.

**Why Pravah uses 5ms linger:** Pipeline jobs trigger in bursts at cron times. A 5ms window accumulates 50–100 messages, improving throughput 10× during bursts. Five milliseconds of added latency is invisible to users. For latency-sensitive paths (audit logs), Pravah uses `linger.ms=1`.

```
t=0ms    Record 1 arrives → starts batch for partition 7
t=1ms    Record 2 arrives → added to batch
t=3ms    Record 3 arrives → added to batch
t=5ms    linger.ms elapsed → SEND (3 records, 1 round trip)
t=13ms   Broker ACKs ✅

Without batching:
t=0ms    Record 1 → send → ACK at t=8ms
t=8ms    Record 2 → send → ACK at t=16ms
t=16ms   Record 3 → send → ACK at t=24ms   (3× slower)
```

## Compression — The Bandwidth Saver

Kafka compresses **batches**, not individual messages. Messages in a batch are similar (same topic, same time period) — similar data compresses extremely well.

A typical Pravah batch of `pipeline.events` in JSON has enormous repeated strings: `"event"`, `"pipeline"`, `"tenant"`, `"megacorp"`, `"timestamp"`, `"2024-01-15T10:00"`. Compression ratio: 5:1 to 10:1 for JSON, 3:1 to 5:1 for Avro.

| Algorithm | Ratio | Speed | CPU Cost |
|---|---|---|---|
| none | 1:1 | fastest | none |
| gzip | 5:1 | slowest | high |
| snappy | 3:1 | fast | low |
| lz4 | 3:1 | fastest | very low |
| **zstd** | **5:1** | **fast** | medium |

**Pravah uses zstd** — best compression ratio with fast decompression. Decompression happens on the consumer side; brokers store and forward without decompressing.

## Acknowledgment Levels (acks)

`acks` controls when the broker tells the producer "I got it":

**`acks=0` — Fire and forget:**
```
Producer sends → does not wait for ACK.
Throughput: highest.
Data loss: yes, if broker crashes before writing to disk.
Pravah uses for: runner capability broadcasts (losing one is acceptable).
```

**`acks=1` — Leader ACK:**
```
Broker writes to leader's log → ACKs producer.
Does not wait for follower replication.
Data loss: if leader crashes before replication, message is lost.
Throughput: high.
Pravah does NOT use this for any critical path.
```

**`acks=all` (or `-1`) — All ISR ACK:**
```
Broker writes to leader → replicates to all ISR members → ACKs producer.
Data loss: none (with min.insync.replicas=2 and replication factor 3).
Throughput: slightly lower (waits for ISR replication).
Pravah uses for: all business-critical topics.
```

**With `acks=all` + `min.insync.replicas=2`:**
```
Producer sends to Broker 1 (leader for partition 7).
Broker 1 appends to local log.
Broker 1 replicates to Broker 2 and Broker 3.
Both replicas confirm write.
Broker 1 → Producer: "Confirmed at offset 1000" ✅

Worst case: Broker 1 crashes after ACK.
Broker 2 or 3 has the message (they confirmed).
New leader elected → message preserved. ✅
```

## Retries and Idempotent Producer

**The retry problem:**

```
t=0   Producer sends batch to Broker 1
t=5   Network timeout (no ACK received)
t=5   Producer: "Did it arrive? I don't know. Retry."
t=5   Producer resends same batch

Possible outcomes:
  A: Message was never received → retry is correct ✅
  B: Message was received but ACK was lost → retry = DUPLICATE ❌
```

**Idempotent producer — solves this:**

```properties
enable.idempotence=true
acks=all
retries=2147483647   # effectively infinite
max.in.flight.requests.per.connection=5
```

When enabled, the producer gets a stable **Producer ID (PID)** from the broker. Each message batch gets an auto-incrementing **sequence number** per partition.

```
Broker tracks: {PID=42, partition=7} → last_sequence_number=100

Producer sends batch with PID=42, seq=101 → Broker accepts, records 101 ✅
Network drops. Producer retries: PID=42, seq=101.
Broker: "I already have seq=101 for PID=42. Duplicate." → ignores ✅
Producer retry causes zero duplicates.
```

**Pravah producer configuration:**

```properties
# Reliability
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5

# Throughput
batch.size=65536
linger.ms=5
compression.type=zstd
buffer.memory=67108864  # 64MB send buffer

# Timeout
delivery.timeout.ms=120000    # 2 minutes total
request.timeout.ms=30000      # 30s per request
```

## The Sender Thread and In-Flight Requests

The producer has a background **Sender Thread** that:
1. Drains batches from the Record Accumulator
2. Groups batches by broker (one request per broker, not per partition)
3. Sends up to `max.in.flight.requests.per.connection=5` requests without waiting for ACK
4. Tracks in-flight requests and handles responses

**Why max 5 in-flight?** With idempotence enabled, up to 5 in-flight requests are safe — the broker can reorder them using sequence numbers. If set higher (without idempotence), retries could arrive out of order, breaking ordering within a partition.

**Record Accumulator buffer:**

```
buffer.memory=64MB   total send buffer

If buffer fills up (brokers slow, producing fast):
  producer.send() blocks for max.block.ms=60000ms
  If still full after 60s → TimeoutException

Pravah monitoring:
  pravah_kafka_producer_buffer_available_bytes{topic="job.assigned"}
  Alert when < 10MB → producer backpressure
```

## Message Lifecycle End-to-End

```
1. Application calls producer.send(record)
   → returns a Future<RecordMetadata>

2. Serializer converts key and value to bytes

3. Partitioner computes target partition (hash of key)

4. Record added to RecordAccumulator batch for that partition

5. Sender Thread picks up batch (batch.size or linger.ms triggered)

6. Sender compresses batch (zstd)

7. Sender sends ProduceRequest to leader broker:
   {partition: 7, records: [compressed batch], acks: all}

8. Broker appends to local log segment (sequential write)

9. Broker replicates to ISR followers

10. All ISR confirm → Broker sends ProduceResponse:
    {partition: 7, offset: 1000, error: None}

11. Sender marks batch as complete, resolves Future ✅

12. On error: Sender retries (up to delivery.timeout.ms)
    Idempotent sequence numbers prevent duplicates on retry
```

## FAANG Interview Angles

**"How does Pravah achieve high throughput when publishing pipeline events to Kafka?"**

> Three mechanisms: batching, compression, and async sending. We configure `batch.size=64KB` and `linger.ms=5` — the producer accumulates messages for 5ms before sending, reducing network round trips by 50–100×. We use zstd compression, achieving 5:1 ratios on JSON payloads — reducing network bandwidth and disk usage. The Sender Thread operates asynchronously with up to 5 in-flight requests, keeping the broker busy without blocking the application thread.

**"How does Pravah prevent duplicate messages when a producer retries after a network timeout?"**

> Idempotent producer. Each producer instance gets a stable Producer ID from the broker on startup. Each message batch gets an auto-incrementing sequence number per partition. The broker tracks `{PID, partition} → last_sequence`. On retry, the broker sees the same sequence number and ignores the duplicate. `enable.idempotence=true` with `acks=all` gives us exactly-once delivery from producer to broker.

**"What is the trade-off between `acks=1` and `acks=all` for Pravah?"**

> `acks=1` ACKs after the leader writes locally, without waiting for follower replication. If the leader crashes immediately after ACKing, the message is lost — followers haven't replicated it yet. `acks=all` waits for all ISR members to confirm before ACKing — with `min.insync.replicas=2`, we can lose one broker with zero data loss. The throughput difference is small (one extra network round trip within the same data center) and completely worth it for a data pipeline platform where data loss is unacceptable.

## 📌 Key Takeaways

1. Producer pipeline: serialize → partition → accumulate → compress → send → handle ACK
2. Batching is the biggest throughput lever: `batch.size=64KB` + `linger.ms=5` → 100× throughput
3. Compression at batch level exploits repeated data in similar messages — zstd gives 5:1 ratio
4. `acks=all` + `min.insync.replicas=2` = zero data loss with replication factor 3
5. Idempotent producer (PID + sequence numbers) prevents duplicates on retry — required for exactly-once
6. Sender Thread is async with up to 5 in-flight requests — keeps brokers saturated
7. Monitor: buffer available bytes, batch fill rate, request latency — producer health directly affects pipeline throughput
