🧩 Why Producer Internals Matter
Most engineers treat the Kafka producer as a black box:

NAIVE VIEW:

What actually happens inside:
  → Is it sent immediately or buffered?
  → What if the broker is slow?
  → What if network drops mid-send?
  → How does compression work?
  → When exactly does "send" return?
  → What makes it idempotent?

Getting these wrong in Pravah means:
  → Data loss on broker failure
  → Duplicate messages on retry
  → 10× worse throughput than possible

📦 Batching — The Throughput Multiplier
WHY BATCHING EXISTS
────────────────────────────────────────────────────────────

Without batching — send each message immediately:

  Message 1: [TCP overhead][Kafka overhead][1KB payload]
  Message 2: [TCP overhead][Kafka overhead][1KB payload]
  Message 3: [TCP overhead][Kafka overhead][1KB payload]

  100 messages = 100 network round trips
  100 × 10ms latency = 1000ms total
  Throughput: ~100 msg/sec per partition

With batching — accumulate, send together:

  Batch: [TCP overhead][Kafka overhead][100KB payload]
         (100 messages in one batch)

  100 messages = 1 network round trip
  1 × 10ms latency = 10ms total
  Throughput: ~10,000 msg/sec per partition

  100× throughput improvement ✅
The two batching controls:

BATCHING CONFIGURATION
────────────────────────────────────────────────────────────

batch.size = 16384 (16KB default, Pravah uses 65536 = 64KB)
  Maximum bytes in a batch before it's sent.
  Batch sent when EITHER limit is hit.

linger.ms = 0 (default, Pravah uses 5ms)
  How long to wait for more messages before sending.
  0 = send immediately (low latency, poor batching)
  5 = wait 5ms for more messages (better batching)

PRAVAH BATCHING STRATEGY:
────────────────────────────────────────────────────────────

  batch.size = 65536    (64KB per batch)
  linger.ms  = 5        (wait up to 5ms)

  Batch sent when:
    Batch reaches 64KB  → send immediately
    OR 5ms passes       → send whatever we have

  WHY 5ms linger for Pravah?
    Pravah dispatches jobs in bursts (cron triggers).
    5ms window accumulates 50-100 messages.
    Throughput 10× better during bursts.
    5ms added latency is invisible to users.

VISUAL — BATCHING TIMELINE:
────────────────────────────────────────────────────────────

t=0ms:    Record 1 arrives → starts batch for partition 7
t=1ms:    Record 2 arrives → added to batch
t=2ms:    Record 3 arrives → added to batch
t=3ms:    Record 4 arrives → added to batch
t=5ms:    linger.ms elapsed → SEND BATCH (4 records)
          [Network round trip: 8ms]
t=13ms:   Broker ACKs batch ✅

vs without batching:
t=0ms:    Record 1 → SEND → broker ACK at t=8ms
t=8ms:    Record 2 → SEND → broker ACK at t=16ms
t=16ms:   Record 3 → SEND → broker ACK at t=24ms
t=24ms:   Record 4 → SEND → broker ACK at t=32ms

Batching: 4 records done at t=13ms
No batch: 4 records done at t=32ms
2.5× faster even with only 4 records ✅
🗜️ Compression — The Bandwidth Saver
WHY COMPRESSION WORKS SO WELL IN KAFKA
────────────────────────────────────────────────────────────

Key insight: Kafka compresses BATCHES, not individual messages.

Messages in a batch are similar (same topic, same time).
Similar data compresses extremely well.

Example Pravah batch (pipeline.events):
  Message 1: {"event":"TRIGGERED","pipeline":"pipe-abc","tenant":"megacorp","timestamp":"2024-01-15T10:00:00"}
  Message 2: {"event":"TRIGGERED","pipeline":"pipe-def","tenant":"megacorp","timestamp":"2024-01-15T10:00:01"}
  Message 3: {"event":"RUNNING","pipeline":"pipe-abc","tenant":"megacorp","timestamp":"2024-01-15T10:00:05"}

  These share many repeated strings:
  "event", "pipeline", "tenant", "megacorp", "timestamp"
  "2024-01-15T10:00", "TRIGGERED", etc.

  Compression ratio: 5:1 to 10:1 for JSON
                     3:1 to 5:1 for Avro (already compact)
Compression algorithms compared:

COMPRESSION ALGORITHM COMPARISON
────────────────────────────────────────────────────────────

┌──────────────┬──────────────┬─────────────┬─────────────┐
│ Algorithm    │ Ratio        │ Speed       │ CPU Cost    │
├──────────────┼──────────────┼─────────────┼─────────────┤
│ none         │ 1:1          │ fastest     │ none        │
│ gzip         │ best (5:1)   │ slowest     │ high        │
│ snappy       │ good (3:1)   │ fast        │ low         │
│ lz4          │ good (3:1)   │ fastest     │ very low    │
│ zstd         │ best (5:1)   │ fast        │ medium      │
└──────────────┴──────────────┴─────────────┴─────────────┘

PRAVAH USES: zstd
  Best compression ratio (like gzip)
  Fast decompression (like lz4)
  Good for Pravah's JSON/Avro payloads
  Saves 60-80% network bandwidth ✅

WHERE COMPRESSION/DECOMPRESSION HAPPENS:
  Producer:       compresses batch before sending
  Broker:         stores compressed (no decompression!)
  Consumer:       decompresses batch after receiving

  Broker never decompresses = broker CPU stays free ✅
  Compression ratio applies to both network AND disk ✅

PRAVAH PRODUCER CONFIG:
  compression.type = zstd
  batch.size       = 65536
  linger.ms        = 5
✅ Acknowledgments — The Durability Control
THE ACK QUESTION
────────────────────────────────────────────────────────────

When producer sends a batch, when does it get confirmation?
This is the most critical durability decision.

Three ack levels: 0, 1, all
acks=0 — Fire and forget:

ACKS = 0 (fire and forget)
────────────────────────────────────────────────────────────

Producer → Broker: [batch]
Producer: "I don't care if you got it. Moving on."

Timeline:
  t=0ms: Producer sends batch
  t=0ms: Producer immediately considers it "sent"
  t=8ms: Broker receives (producer doesn't know/care)

Risk: If broker crashes at t=4ms:
  Batch lost. Producer never knows. ❌

Use when: Metrics, telemetry where loss is acceptable.
Pravah uses for: runner.heartbeat (slightly stale = ok)
                 capability broadcasts (volatile data)

Throughput: MAXIMUM (no waiting)
Durability: NONE
acks=1 — Leader acknowledges:

ACKS = 1 (leader ack)
────────────────────────────────────────────────────────────

Producer → Leader: [batch]
Leader: writes to local log
Leader → Producer: "Got it ✅"
(followers replicate asynchronously)

Timeline:
  t=0ms:  Producer sends batch
  t=8ms:  Leader writes to disk
  t=8ms:  Leader ACKs producer
  t=9ms:  Producer continues (batch "committed")
  t=10ms: Followers start replicating...

Risk: Leader crashes at t=9ms (after ACK, before replication):
  Producer thinks: "committed ✅"
  Followers: "never got it"
  New leader elected from followers
  BATCH LOST. Producer doesn't know. ❌

Use when: Moderate durability, higher throughput.
Pravah uses for: NOTHING critical
                (risk of silent loss unacceptable)

Throughput: HIGH
Durability: MEDIUM (leader ack only)
acks=all — Full durability:

ACKS = ALL (ISR acknowledgment)
────────────────────────────────────────────────────────────

Producer → Leader: [batch]
Leader: writes to local log
Leader → Followers: replicate
Followers → Leader: "Got it"
Leader → Producer: "ALL ISR confirmed ✅"

Timeline:
  t=0ms:  Producer sends batch
  t=8ms:  Leader writes to disk
  t=9ms:  Leader replicates to Broker2, Broker3
  t=11ms: Both followers confirm
  t=11ms: Leader ACKs producer
  t=11ms: Producer continues

Extra latency vs acks=1: ~3ms (replication time)

Risk: Leader crashes after all ISR confirmed:
  ALL followers have the data ✅
  New leader elected from ISR ✅
  No data loss ✅

Use when: Data durability is non-negotiable.
Pravah uses for: ALL critical topics
  pipeline.events, job.assigned, job.results,
  audit.log, lineage.events

Throughput: SLIGHTLY LOWER (replication round trip)
Durability: MAXIMUM ✅

PRAVAH PRODUCER DURABILITY CONFIG:
  acks                      = all
  min.insync.replicas       = 2   (on broker side)
  enable.idempotence        = true
  retries                   = Integer.MAX_VALUE
  delivery.timeout.ms       = 120000  (2 minutes)
  request.timeout.ms        = 30000   (30 seconds)
🔁 Retries — The Correctness Problem
WHY RETRIES ARE DANGEROUS WITHOUT IDEMPOTENCE
────────────────────────────────────────────────────────────

t=0ms:  Producer sends batch (sequence: pipe-abc events 1-10)
t=30ms: Request times out (network hiccup)
t=30ms: Producer retries (sends same batch again)
t=35ms: Broker receives BOTH copies!

  First copy:  written at offsets 1000-1009
  Second copy: written at offsets 1010-1019

  DUPLICATES in Kafka! ❌
  Event sourcing gets duplicate events.
  Job dispatch fires twice.
  Data corruption.

THE SOLUTION: IDEMPOTENT PRODUCER
────────────────────────────────────────────────────────────

enable.idempotence = true

What this does:
  1. Broker assigns Producer ID (PID) to each producer
  2. Producer tags each batch with:
     PID + Sequence Number (monotonically increasing)

  ┌─────────────────────────────────────────────────────┐
  │  Batch 1: PID=42, Seq=0, [10 records]               │
  │  Batch 2: PID=42, Seq=1, [8 records]                │
  │  Batch 3: PID=42, Seq=2, [12 records]               │
  └─────────────────────────────────────────────────────┘

  Broker tracks: {PID=42 → last seen Seq=1}

  Producer retries Batch 2 (Seq=1):
    Broker checks: "PID=42, Seq=1 — already have this!"
    Broker DEDUPLICATES. Ignores second copy. ✅
    Returns success to producer.

  Producer gets:
    "Successfully written" (even though deduplicated)
    Exactly-once within a session ✅

IDEMPOTENCY SCOPE:
  Per producer session (PID assigned on connection)
  Per partition (dedup per partition)
  NOT across producer restarts:
    Producer restarts → new PID
    Old PID + sequences gone
    That's why we use: outbox pattern + idempotency keys
    (application-level dedup handles cross-restart)
🔄 The Complete Retry Logic
PRAVAH PRODUCER RETRY FLOW
────────────────────────────────────────────────────────────

Producer sends batch. What happens on failure?

┌─────────────────────────────────────────────────────────┐
│                  ERROR CLASSIFICATION                   │
│                                                         │
│  RETRIABLE ERRORS:                                      │
│    LEADER_NOT_AVAILABLE  ← leader election in progress  │
│    NOT_LEADER_FOR_PARTITION ← stale metadata            │
│    NETWORK_EXCEPTION      ← transient connectivity      │
│    REQUEST_TIMED_OUT      ← broker overloaded           │
│    → Producer retries automatically ✅                  │
│                                                         │
│  NON-RETRIABLE ERRORS:                                  │
│    MESSAGE_TOO_LARGE   ← payload exceeds max.msg.bytes  │
│    INVALID_CONFIG      ← wrong producer config          │
│    AUTHORIZATION_FAILED ← ACL violation                 │
│    → Producer fails immediately, no retry ❌            │
│                                                         │
│  RETRIABLE WITH BACKOFF:                                │
│    TOPIC_AUTHORIZATION_FAILED ← might resolve           │
│    UNKNOWN_PRODUCER_ID   ← producer restarted           │
└─────────────────────────────────────────────────────────┘

RETRY WITH BACKOFF:
  Attempt 1: send → LEADER_NOT_AVAILABLE
  Wait:       100ms
  Attempt 2:  send → LEADER_NOT_AVAILABLE
  Wait:       200ms
  Attempt 3:  send → SUCCESS ✅

  retry.backoff.ms = 100ms (base)
  Exponential backoff with jitter applied

  MAX RETRIES: Integer.MAX_VALUE (effectively infinite)
  DELIVERY TIMEOUT: 120 seconds (outer time limit)
  "Keep retrying until 120 seconds total elapsed"

IN-FLIGHT REQUESTS:
  max.in.flight.requests.per.connection = 5
  (default — 5 batches can be in-flight simultaneously)

  With idempotence enabled:
    Automatically set to 1 if > 5 would break ordering
    Actually: idempotent producer allows up to 5
    Broker uses sequence numbers to reorder if needed ✅

  Without idempotence:
    max.in.flight = 1 for strict ordering
    (otherwise retry of batch 1 after batch 2 arrives
     = ordering violation)
📊 Memory Buffer — What Happens When Full
RECORD ACCUMULATOR MEMORY
────────────────────────────────────────────────────────────

buffer.memory = 33554432 (32MB default)
                67108864 (64MB — Pravah's config)

This is the total memory for all pending batches.

WHAT HAPPENS WHEN BUFFER IS FULL:
  max.block.ms = 60000 (60 seconds)

  producer.send() BLOCKS for up to 60 seconds.
  Waiting for buffer space (broker consuming batches).

  If still full after 60s:
    throws TimeoutException

  In Pravah: this is a backpressure signal!
    Outbox relay slowing down
    → Kafka brokers overloaded
    → Natural backpressure to scheduler

  We monitor buffer utilization:
  pravah_producer_buffer_used_bytes
  Alert at 80% utilization

VISUALIZING THE BUFFER:

⚡ Idempotent Producer — Full Internal Flow
IDEMPOTENT PRODUCER INTERNALS
────────────────────────────────────────────────────────────

INITIALIZATION:
  Producer starts up
  Sends InitProducerId request to broker
  Broker returns: PID = 42, Epoch = 0
  Producer stores: {PID: 42, Epoch: 0, SeqNum: 0}

SENDING A BATCH:
  Batch for partition 7:
    Header: {PID: 42, Epoch: 0, SeqNum: 5}
    Payload: [record1, record2, record3]

BROKER RECEIVES BATCH:
  Broker checks partition 7 producer state:
    {PID: 42 → last committed SeqNum: 4}

  SeqNum received: 5
  Expected: 4 + 1 = 5 ✅
  Accept and write

DUPLICATE DETECTION:
  Network retry → same batch arrives again:
    Header: {PID: 42, Epoch: 0, SeqNum: 5}

  Broker checks: last committed for PID 42 = 5
  SeqNum received: 5 = already committed
  DUPLICATE! Ignore silently.
  Return success to producer. ✅

OUT OF ORDER DETECTION:
  Batch 6 arrives before Batch 5 (network reorder):
    Header: {PID: 42, Epoch: 0, SeqNum: 6}

  Broker checks: last committed = 4
  Expected: 5, got: 6
  OUT OF SEQUENCE!
  Return: OutOfOrderSequenceException

  Producer: will not retry this — ordering issue
  Sends to DLQ for investigation

PRODUCER RESTART:
  Producer crashes, restarts
  Gets NEW PID: 43, Epoch: 1

  Old batches (PID 42) in flight:
    Broker receives PID 42 batch after new PID 43 issued
    Broker rejects: stale epoch
    Producer 42 is dead anyway (process killed)
    No confusion ✅

🎯 FAANG Interview Angles
❓ "How does Pravah achieve high throughput
    when publishing pipeline events to Kafka?"

Good answer:
  "Three mechanisms work together. Batching:
   we set linger.ms=5 and batch.size=64KB.
   The producer accumulates records for 5ms,
   bundling typically 50-100 messages into one
   network request — reducing round trips by 50-100×.

   Compression: we use zstd which achieves 5:1
   compression on our JSON/Avro payloads.
   The broker stores and transmits compressed batches,
   saving 60-80% bandwidth and disk.

   Parallelism: 12-24 partitions per topic means
   12-24 broker connections sending simultaneously.
   With 5 in-flight requests per connection,
   we saturate broker I/O without blocking."

❓ "What's the difference between acks=1 and
    acks=all, and which does Pravah use?"

Good answer:
  "acks=1 means only the partition leader confirms
   receipt. If the leader crashes after ACKing but
   before replicating, the message is lost silently
   — the producer thinks it succeeded.

   acks=all means ALL in-sync replicas confirm.
   With min.insync.replicas=2 and replication
   factor 3, we can lose one broker with zero
   data loss. The extra latency is ~3ms for
   replication — invisible at Pravah's scale.

   Pravah uses acks=all for all critical topics:
   pipeline.events, job.assigned, audit.log.
   The only exception is runner.heartbeat where
   we use acks=0 — a slightly stale heartbeat is
   acceptable and we want maximum throughput."

❓ "Explain idempotent producers — what problem
    do they solve and how do they work?"

Good answer:
  "Without idempotence, retries cause duplicates.
   If a batch times out and the producer retries,
   the broker might have actually written it the
   first time — so it writes it again. Duplicates.

   Idempotent producers solve this with PID and
   sequence numbers. On connection, the broker
   assigns a Producer ID. Every batch is tagged
   with PID + monotonically increasing sequence
   number. The broker tracks the last committed
   sequence per PID per partition.

   On retry: broker sees same PID + same sequence
   = already committed. Silently deduplicates,
   returns success. Producer gets exactly-once
   guarantee within a session.

   In Pravah, this combines with our outbox
   idempotency keys for cross-session dedup —
   idempotent producer handles within-session
   retries, outbox handles cross-restart scenarios."
📌 Key Takeaways
1. Producer pipeline:
   Serialize → Partition → Accumulate → Compress
   → Send → Ack → Retry

2. Batching = throughput multiplier
   batch.size + linger.ms control the tradeoff
   Pravah: 64KB batches, 5ms linger

3. Compression on batches (not individual messages)
   Similar messages compress 5:1 to 10:1
   Pravah: zstd for best ratio + speed
   Broker stores compressed — no CPU waste

4. acks=0: fire and forget (heartbeats only)
   acks=1: leader only (nothing critical in Pravah)
   acks=all: full ISR (all critical Pravah topics)

5. Retries are dangerous without idempotence
   enable.idempotence=true: PID + sequence numbers
   Broker deduplicates retried batches automatically

6. Idempotence scope: per session, per partition
   Cross-restart dedup: outbox + application keys

7. Buffer full = natural backpressure signal
   Monitor buffer utilization — alert at 80%

8. Different topics need different producer configs
   Critical: acks=all + idempotent
   Volatile: acks=0 + maximum throughput
