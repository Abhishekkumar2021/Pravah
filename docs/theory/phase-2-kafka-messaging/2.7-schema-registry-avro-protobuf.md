# 2.7 Schema Registry — Avro/Protobuf Versioning

## The Schema Evolution Problem

On Day 1, `pipeline.events` has a simple schema. Five services consume it. All deployed and working.

On Day 30, the product team wants task-level tracking. Pipeline Service adds a new `task_count` field and deploys. What happens?

- **Lineage Service (not yet updated):** receives the new message format — Java deserializer throws "unknown field" or silently ignores it with unpredictable results
- **Agent Service (updated first):** receives OLD messages from before the change — tries to read `task_count` → NullPointerException

Without schema management: services break randomly on deployment. Nobody knows what changed or when. The debugging trail is "Lineage Service is crashing" → "Pipeline Service changed the schema" → "When? Nobody told us."

---

## What Is a Schema Registry?

A Schema Registry is a centralized catalog that:

1. **Stores** all schema versions for each topic
2. **Validates** new schemas before they are used
3. **Enforces** compatibility rules between versions
4. **Distributes** schemas to producers and consumers on demand
5. **Enables** schema evolution without breaking changes

```
Without registry:
  Producer → Kafka → Consumer
  Schema: "figure it out yourself"

With registry:
  Producer → Schema Registry → Kafka → Consumer
             "Is schema valid?"          "Give me schema ID=42"
             "Yes, ID=42"                Registry → {full schema}
```

**Message overhead:** only 5 bytes per message (1 magic byte + 4-byte schema ID). The consumer fetches the full schema from the registry on first encounter, then caches it locally. No registry call on every message.

---

## How Confluent Schema Registry Works

```
┌─────────────────────────────────────────────────────────┐
│              Confluent Schema Registry                  │
│                                                         │
│  Subjects (one per topic per side):                     │
│    pipeline.events-value → schema versions 1, 2, 3...  │
│    job.assigned-value    → schema versions 1, 2...      │
│                                                         │
│  Storage: Kafka topic "_schemas"                        │
│  REST API: POST /subjects/{subject}/versions            │
│            GET  /schemas/ids/{id}                       │
│            POST /compatibility/{subject}                │
└─────────────────────────────────────────────────────────┘
```

**Kafka message wire format with schema:**
```
Byte 0:    0x00 (magic byte — "this message has a schema")
Bytes 1-4: schema ID (int32, e.g., 42)
Bytes 5+:  Avro or Protobuf encoded payload
```

Consumer flow:
1. Read magic byte `0x00` → schema-encoded
2. Read schema ID: 42
3. Fetch schema from registry (or local cache)
4. Deserialize bytes 5+ using schema 42
5. Deliver Java/Go/Python object to application

## Avro vs Protobuf

| Property | Avro | Protobuf |
|---|---|---|
| Schema format | JSON | `.proto` file |
| Field identification | By name | By field number |
| Binary size | Very compact | Slightly smaller (field numbers vs names) |
| Code generation | Optional | Required (`protoc`) |
| gRPC support | No | Native |
| Language support | Good | Excellent |
| Schema evolution safety | Good | Excellent (field numbers) |
| Tooling | Schema Registry tools | `buf`, `protoc`, IDE plugins |

**Pravah uses Protobuf for all Kafka messages:**

1. Pravah already uses Protobuf for gRPC between runners and the cloud control plane — one schema language for both Kafka and gRPC
2. Field numbers make evolution safer by default: remove field 4, add field 5 — old consumers ignore unknown field numbers without configuration
3. Strong typing and compile-time validation catch schema misuse before deployment
4. `buf` tooling provides schema linting and breaking change detection in CI

**Pravah schema organization:**

```
/schemas/
  kafka/
    pipeline_event.proto
    job_event.proto
    runner_event.proto
    lineage_event.proto
    billing_event.proto
  grpc/
    runner_gateway.proto
    pipeline_service.proto
```

**Example Pravah Protobuf schema:**

```protobuf
syntax = "proto3";
package io.pravah.events;

message PipelineEvent {
  string pipeline_id  = 1;
  string event_type   = 2;   // "TRIGGERED", "RUNNING", etc.
  int64  timestamp    = 3;   // HLC timestamp, milliseconds
  string tenant_id    = 4;
  string run_id       = 5;
  optional int32 task_count = 6;  // added in v2, optional with default
  map<string, string> metadata = 7;
}
```

## Schema Compatibility Modes

The registry checks every new schema version against existing versions according to the configured compatibility mode.

**BACKWARD compatible (Pravah's default):**
New schema can read data written by the old schema. Old consumers can read new messages.

Safe changes:
- Add an optional field with a default value (`optional int32 task_count = 6`)
- Remove a field that had a default value
- Widen a field type (e.g., `int32` → `int64`)

Unsafe changes:
- Remove a required field
- Rename a field (breaks name-based matching in Avro; field number stays in Protobuf)
- Change a field type incompatibly

**FORWARD compatible:**
Old schema can read data written by the new schema. New consumers can handle old messages. Used when old consumers must run alongside new producers.

**FULL compatible:**
Both backward and forward compatible simultaneously. The strictest mode. Required for Pravah's billing and audit topics where correctness is non-negotiable.

**NONE:**
No compatibility check. Used only in development environments.

**Pravah's configuration:**

| Topic | Compatibility Mode | Reasoning |
|---|---|---|
| `pipeline.events` | BACKWARD | Services deploy at different times; old consumers must handle new producers |
| `job.assigned` | FULL | Job execution schema cannot break in either direction |
| `lineage.events` | BACKWARD | Lineage consumers deploy independently |
| `billing.compute.used` | FULL | Billing schema must be stable in both directions |
| `audit.log` | FULL | Compliance requires schema stability |

## Registering and Evolving Schemas in Pravah

**Day 1 — Register initial schema:**

```bash
# Register PipelineEvent v1 for pipeline.events-value
curl -X POST http://schema-registry:8081/subjects/pipeline.events-value/versions \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  -d '{"schemaType": "PROTOBUF", "schema": "...(v1 proto content)..."}'

# Response: {"id": 1}
```

**Day 30 — Evolve schema (add optional field):**

```bash
# Check compatibility BEFORE registering
curl -X POST http://schema-registry:8081/compatibility/subjects/pipeline.events-value/versions/latest \
  -d '{"schemaType": "PROTOBUF", "schema": "...(v2 proto with task_count)..."}'

# Response: {"is_compatible": true}

# Register v2
curl -X POST http://schema-registry:8081/subjects/pipeline.events-value/versions \
  -d '{"schemaType": "PROTOBUF", "schema": "...(v2)..."}'

# Response: {"id": 2}
```

**Deployment sequence for backward-compatible change:**

```
Step 1  Register new schema version in registry (compatibility check passes)
Step 2  Deploy new version of Pipeline Service (producer)
        → New messages carry schema ID 2 with task_count field
Step 3  Old Lineage Service reads new message:
        → Fetches schema ID 2
        → Protobuf: unknown field 6 (task_count) → silently ignored ✅
Step 4  Deploy new Lineage Service over the next days
        → Now reads task_count from schema ID 2 messages ✅
```

Old consumers keep working throughout the rollout.

## Schema in CI/CD Pipeline

```yaml
# .github/workflows/schema-check.yml
steps:
  - name: Lint .proto files
    run: buf lint ./schemas/

  - name: Check breaking changes
    run: buf breaking ./schemas/ --against '.git#branch=main'
    # Fails if any change would break existing consumers ✅

  - name: Register schema (after merge)
    run: |
      confluent schema-registry subject update \
        --subject pipeline.events-value \
        --compatibility BACKWARD
      confluent schema-registry schema create \
        --subject pipeline.events-value \
        --schema ./schemas/kafka/pipeline_event.proto \
        --type PROTOBUF
```

Breaking changes are caught in CI — before they reach production. The `buf breaking` command understands Protobuf field number semantics and catches renumbering or type changes that would break existing consumers.

## System Design Interview Angles

**"What happens in Pravah when Pipeline Service deploys a new schema version before consumers are updated?"**

> Confluent Schema Registry handles this. The producer registers the new schema (say, schema ID=42 with an added `task_count` field). Protobuf with BACKWARD compatibility means old consumers can still decode messages written with schema ID=42 — unknown field numbers are silently ignored per Protobuf's wire format spec. Consumers fetch schema ID=42 from the registry on first encounter, but since they don't have a field mapping for field 6 (task_count), they simply skip it. The old consumer keeps running correctly without any code change.

**"Why does Pravah use Protobuf instead of Avro for Kafka messages?"**

> Three main reasons. First, Pravah already uses Protobuf for gRPC between runners and the cloud — using Protobuf for Kafka as well means a single schema language, single toolchain, and shared `.proto` definitions across both communication channels. Second, Protobuf's field numbers provide safer schema evolution — removing a field by number doesn't break consumers, unlike Avro's name-based matching. Third, `buf` tooling integrates into CI and catches breaking changes before they deploy, giving us schema governance without manual review overhead.

**"What is the overhead of schema registry on Kafka performance?"**

> Minimal. The schema ID is only 5 bytes per message (1 magic byte + 4-byte int32). The schema itself is fetched from the registry once per unique schema ID encountered, then cached locally on the consumer. In steady state (no schema evolution), there are zero registry calls on the critical path. During schema evolution, there is one registry HTTP call per new schema ID — typically milliseconds, and only on the first message with that ID. The registry itself stores schemas in a Kafka topic and scales horizontally.

## 📌 Key Takeaways

1. Schema registry solves schema evolution: centralized versioning, compatibility enforcement, no runtime surprises
2. Message overhead: 5 bytes per message (schema ID); full schema cached after first fetch
3. Avro: mature Kafka ecosystem, JSON schema, name-based matching; Protobuf: field numbers, gRPC compatible, better tooling
4. Pravah uses Protobuf: single schema language for both Kafka and gRPC, safer evolution, `buf` CI integration
5. BACKWARD compatibility: new schema can read old data; old consumers can read new messages — deploy producer first, consumers follow at their own pace
6. FULL compatibility: bidirectional — required for billing and audit topics where correctness is non-negotiable
7. Schema checks in CI with `buf breaking` catch incompatible changes before production
