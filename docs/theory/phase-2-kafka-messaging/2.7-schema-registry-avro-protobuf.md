```text
📖 What Is A Schema Registry?
SCHEMA REGISTRY — THE CONCEPT
────────────────────────────────────────────────────────────
```

A Schema Registry is a centralized catalog that:

  1. STORES all schema versions for each topic
  2. VALIDATES new schemas before they're used
  3. ENFORCES compatibility rules between versions
  4. DISTRIBUTES schemas to producers and consumers
  5. ENABLES schema evolution without breaking changes

WITHOUT SCHEMA REGISTRY:
```text
  Producer → Kafka → Consumer
  Schema: "figure it out yourself"
  Versioning: "hope nobody breaks anything"

WITH SCHEMA REGISTRY:
  Producer → Schema Registry → Kafka → Consumer
               "Is my schema valid?"        "Give me schema"
               "Yes, here's schema ID=42"   "ID=42 → {schema}"
```
               
  Schema embedded in message: just a 4-byte ID
  Consumer fetches full schema from registry
  Deserialization: always correct ✅

SCHEMA ID IN KAFKA MESSAGES:

Every Kafka message with schema looks like:

```text
  Byte 0:      Magic byte (0x00) ← "this has a schema"
  Bytes 1-4:   Schema ID (int32) ← e.g., 42
  Bytes 5+:    Avro/Protobuf encoded payload

  Total overhead: 5 bytes per message ← extremely small!
```

  Consumer receives message:
```text
    1. Read magic byte: 0x00 → schema-encoded
    2. Read schema ID: 42
    3. Fetch schema from registry (cached after first fetch)
    4. Deserialize bytes 5+ using schema 42
    5. Get Java object ✅
```

SCHEMA CACHING:
  Schemas fetched ONCE per schema ID, then cached.
```text
  schema.registry.url → local cache → deserialize
  No registry call on every message.
  Network: only on first encounter of new schema ID.
📐 Avro vs Protobuf — Which Does Pravah Use?
AVRO
────────────────────────────────────────────────────────────
```

Schema defined in JSON:

{
  "type": "record",
  "name": "PipelineEvent",
  "namespace": "io.pravah.events",
  "fields": [
    {"name": "pipeline_id", "type": "string"},
    {"name": "event_type",  "type": "string"},
    {"name": "timestamp",   "type": "long", "logicalType": "timestamp-millis"},
    {"name": "task_count",  "type": ["null", "int"], "default": null}
  ]
}

Pros:
  ✅ Schema stored separately (not in message)
  ✅ Very compact binary encoding
  ✅ Native Kafka ecosystem support
  ✅ Schema evolution built-in
  ✅ Dynamic typing (schema at runtime)

Cons:
  ❌ No field numbers (evolution by name matching)
  ❌ JSON schema (verbose for complex types)
  ❌ Less language support than Protobuf

PROTOBUF

Schema defined in .proto file:

```protobuf
syntax = "proto3";
package io.pravah.events;

message PipelineEvent {
  string pipeline_id = 1;
  string event_type  = 2;
  int64  timestamp   = 3;
  optional int32 task_count = 4;
}
```

Pros:
  ✅ Field numbers (forward/backward compat by default)
  ✅ Strongly typed, code generation
  ✅ Excellent language support (Java, Go, Python...)
  ✅ Smaller binary than Avro for most cases
  ✅ gRPC uses Protobuf natively
  ✅ Better for complex nested types

Cons:
  ❌ .proto files need compilation step
  ❌ Schema registry integration slightly more complex

PRAVAH DECISION: Protobuf for everything

Why Protobuf wins for Pravah:

  1. We already use Protobuf for gRPC (runner protocol)
```text
     → Single schema language across Kafka AND gRPC ✅
```

  2. Field numbers = safer evolution
     Remove field 4: old consumers ignore it.
     Add field 5: old consumers ignore it.
     By name NOT by number — fewer mistakes ✅

  3. Strong typing + code generation
     Compile-time errors on schema misuse ✅

  4. Better tooling (protoc, buf)
     Schema linting, breaking change detection ✅

  5. Confluent Schema Registry supports Protobuf
     since version 5.5 ✅

🔄 Schema Evolution — The Four Compatibility Modes
COMPATIBILITY MODES

When you register a new schema version,
the registry checks it against existing versions.

Four modes:

MODE 1: BACKWARD COMPATIBLE (default, Pravah uses this)
  New schema can READ data written by OLD schema.
  Old consumers can read new messages.
  
  Safe changes:
    ✅ Add optional field (with default)
    ✅ Remove field that had a default
    ✅ Change field to more permissive type
  
  Unsafe changes:
    ❌ Remove required field
    ❌ Rename field (breaking by name matching)
    ❌ Change field type incompatibly

MODE 2: FORWARD COMPATIBLE
  Old schema can READ data written by NEW schema.
  New consumers can read old messages.
  
  Safe changes:
    ✅ Add required field (old readers ignore it)
    ✅ Remove optional field
  
  Unsafe changes:
    ❌ Remove required field (old readers expect it)

MODE 3: FULL COMPATIBLE
  Both backward AND forward compatible.
  Any version can read any other version.
  
  Most restrictive but safest.
  
  Safe changes ONLY:
    ✅ Add optional field with default
    ✅ Remove optional field that had default

MODE 4: NONE
  No compatibility checking.
  Any schema accepted.
  
  Use for: Development only.
  Never in Pravah production. ❌

PRAVAH COMPATIBILITY STRATEGY:
  All Kafka topics: BACKWARD_TRANSITIVE
  (backward compatible against ALL previous versions,
   not just latest — maximum safety)
🔬 Schema Evolution Rules — Deep Dive
PROTOBUF EVOLUTION RULES IN PRAVAH

RULE 1: NEVER CHANGE FIELD NUMBERS
  Field number is the wire identity of the field.
  Change it = all existing data becomes unreadable.

  // Version 1
```protobuf
  message PipelineEvent {
    string pipeline_id = 1;  ← field number 1
    string event_type  = 2;
  }
```

  // BAD Version 2 ❌
```protobuf
  message PipelineEvent {
    string event_type  = 1;  ← pipeline_id was 1!
    string pipeline_id = 2;  ← now it's 2!
  }
  // Old messages: field 1 was pipeline_id
  //               new schema reads field 1 as event_type
  //               DATA CORRUPTION ❌
```

RULE 2: NEVER REMOVE REQUIRED FIELDS
  Old messages in Kafka don't have your new required field.
```text
  Deserializer: "required field missing" → crash ❌
```

  // Version 1
```protobuf
  message JobEvent {
    string job_id     = 1;
    string runner_id  = 2;
  }
```

  // BAD Version 2 ❌ — removed runner_id
```protobuf
  message JobEvent {
    string job_id     = 1;
    // runner_id removed — but old messages still have it!
  }
  // Old messages have field 2 bytes in them.
  // New schema doesn't know field 2.
  // Result: field 2 bytes ignored (Protobuf handles this)
  // Actually SAFE in Protobuf! (unknown fields preserved)
  // But consumers expecting runner_id get empty string ❌
```

RULE 3: NEVER REUSE FIELD NUMBERS
  Even if you delete field 2, never use number 2 again.
  Old messages have old data at field 2.
  New field at 2 = garbage data.

  // Version 1
```protobuf
  message RunnerEvent {
    string runner_id  = 1;
    string old_field  = 2;  ← deleted in v2
  }
```

  // BAD Version 3 ❌ — reusing field number 2
```protobuf
  message RunnerEvent {
    string runner_id  = 1;
    string new_field  = 2;  ← REUSED! old data here!
  }
```

  // CORRECT Version 3 ✅ — use new field number
```protobuf
  message RunnerEvent {
    string runner_id  = 1;
    // old_field = 2 (RESERVED — never reuse)
    string new_field  = 3;  ← new number ✅
    reserved 2;  ← explicitly reserve to prevent reuse
    reserved "old_field";  ← reserve name too
  }
```

RULE 4: ADD OPTIONAL FIELDS ONLY
  New fields must be optional with defaults.
```text
  Old consumers: field absent → use default → fine ✅
  New consumers: field present → use value → fine ✅
```

  // Version 1
```protobuf
  message PipelineEvent {
    string pipeline_id = 1;
    string event_type  = 2;
    int64  timestamp   = 3;
  }
```

  // GOOD Version 2 ✅ — adding optional field
```protobuf
  message PipelineEvent {
    string pipeline_id = 1;
    string event_type  = 2;
    int64  timestamp   = 3;
    optional int32 task_count = 4;   ← optional, has default
    optional string tenant_id = 5;  ← optional, has default
  }
```

  Old consumers: see task_count=0 (default), ignore ✅
  New consumers: see actual task_count ✅
🚦 Pravah's Schema Governance Process
HOW SCHEMA CHANGES SHIP IN PRAVAH

STEP 1: DEVELOPER PROPOSES CHANGE
  Modifies .proto file in /schemas/kafka/
  Opens Pull Request to schema repository

STEP 2: AUTOMATED COMPATIBILITY CHECK (CI/CD)
```text
  buf lint                    ← proto syntax check
  buf breaking --against HEAD ← breaking change detection
```

  buf breaking output:
    pipeline_event.proto:14:3:Field "2" on message
    "PipelineEvent" changed type from "string" to "int32".
```text
    ← BLOCKED ❌
```

  Or:
    No breaking changes detected ✅
```text
    ← Allowed to proceed
```

STEP 3: REGISTER WITH SCHEMA REGISTRY (Staging)
  curl -X POST http://schema-registry:8081/subjects/
       pipeline.events-value/versions \
    -H "Content-Type: application/vnd.schemaregistry.v1+json" \
    -d '{"schemaType": "PROTOBUF", "schema": "..."}'

```text
  Response: {"id": 43}  ← new schema version ID
```

STEP 4: COMPATIBILITY VERIFICATION
  curl -X POST http://schema-registry:8081/compatibility/
       subjects/pipeline.events-value/versions/latest \
    -d '{"schemaType": "PROTOBUF", "schema": "..."}'

  Response: {"is_compatible": true} ✅
  OR: {"is_compatible": false, "messages": ["..."]} ❌

STEP 5: DEPLOY CONSUMERS FIRST (backward compat)
  New consumers handle both old and new schema.
  Deploy all consumer services.
  Verify they handle old messages correctly.

STEP 6: DEPLOY PRODUCERS
  Producers start sending new schema.
```text
  Consumers already updated → handle fine ✅
```

STEP 7: SCHEMA REGISTERED IN PRODUCTION
  Schema ID auto-increments.
  All services start seeing new schema ID in messages.
  Registry cache updated on next encounter.

```protobuf
ROLLBACK PLAN:
  Schemas are never deleted (immutable log).
  Producers rollback → send old schema ID again.
  Consumers: already handle old schema (backward compat).
  Zero-downtime rollback ✅
```

🎯 FAANG Interview Angles
❓ "How does Pravah manage schema changes across
    15+ services consuming the same Kafka topics?"

Good answer:
  "We use Confluent Schema Registry with Protobuf
   and BACKWARD_TRANSITIVE compatibility mode.

   Every schema change goes through a governance
   process: the developer modifies the .proto file,
   CI runs 'buf breaking' to detect breaking changes —
   field number changes, type changes, required field
   removal all fail the build automatically.

   Compatible changes — adding optional fields with
   defaults — pass CI and get registered in staging
   registry. We always deploy consumers before producers.
   Consumers already handle both old and new schemas
   before producers start sending new fields.

   Schema IDs are embedded in every Kafka message as
   a 5-byte prefix. Consumers look up the schema once,
   cache it locally, and deserialize correctly regardless
   of schema version. Rollback is zero-downtime —
   producers just revert to the old schema ID."

❓ "Why did you choose Protobuf over Avro for
    Pravah's Kafka schemas?"

Good answer:
  "Three reasons. First, we already use Protobuf for
   gRPC between the runner and cloud control plane.
```sql
   Having one schema language across both Kafka and
   gRPC means developers maintain one set of .proto
   files — reusing types across transport boundaries.
```

   Second, field numbers make Protobuf evolution safer
   than Avro. Avro matches fields by name — rename a
   field and old data becomes unreadable. Protobuf
   matches by field number — you can rename fields
   freely as long as the number stays the same.

   Third, 'buf' tooling gives us compile-time breaking
   change detection in CI. 'buf breaking' catches
   field number changes, type changes, and required
   field removal before they ever reach a Kafka topic.
   Avro has similar tools but Protobuf's ecosystem
   is more mature for this use case."

❓ "What is backward compatibility in schema
    evolution and why does Pravah use it?"

Good answer:
  "Backward compatibility means a new schema version
   can read data written by an older schema version.
   This is the most important compatibility direction
   for Kafka because messages can sit in the log for
   30 days — a new consumer version must be able to
   read messages written by old producer versions.

   We use BACKWARD_TRANSITIVE, not just BACKWARD.
   BACKWARD checks against the latest version only.
   BACKWARD_TRANSITIVE checks against ALL previous
   versions. This is critical because Kafka retains
   messages for 30 days — a consumer might encounter
   a message from 25 days ago written under schema
   version 1, even if we're now on version 8. With
   BACKWARD_TRANSITIVE, schema version 8 is guaranteed
   to read version 1 messages correctly."

## 📌 Key Takeaways

1. Schema Registry solves three problems:
   Documentation (what is the schema?)
   Validation (is this change safe?)
   Distribution (how do consumers get the schema?)

2. Message format: [0x00][4-byte schema ID][payload]
   Only 5 bytes overhead per message
   Consumer fetches full schema once, caches it

3. Avro vs Protobuf:
   Avro: JSON schema, name-based field matching
   Protobuf: .proto files, number-based matching
   Pravah: Protobuf (gRPC reuse + safer evolution)

4. Four compatibility modes:
```yaml
   BACKWARD: new reads old ← Pravah uses TRANSITIVE
   FORWARD: old reads new
   FULL: both directions
   NONE: no checking (dev only)
```

5. Evolution rules (Protobuf):
   NEVER change field numbers
   NEVER reuse field numbers (use reserved)
   NEVER remove required fields
   ALWAYS add optional fields with defaults

6. Schema governance in Pravah:
```text
   buf lint → buf breaking → staging registry
   → deploy consumers first → deploy producers
   → rollback = zero downtime (revert schema ID)
```

7. Registry HA: schemas stored in Kafka itself
   Consumer cache: registry down = existing schemas ok
   New schemas: registry must be available

8. BACKWARD_TRANSITIVE vs BACKWARD:
   BACKWARD: compatible with latest only
   BACKWARD_TRANSITIVE: compatible with ALL versions
   Pravah uses TRANSITIVE (30-day message retention)
