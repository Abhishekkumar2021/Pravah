🌐 HTTP/2 — The Foundation of gRPC
HTTP/1.1 LIMITATIONS

HTTP/1.1 was designed in 1997 for document fetching.

PROBLEM 1: ONE REQUEST AT A TIME PER CONNECTION

```text
  Connection 1: Request A ──────────────► Response A
                            (waiting...)
  Connection 2: Request B ──────────────► Response B
  Connection 3: Request C ──────────────► Response C
```

  Each request needs its own TCP connection.
  OR requests must wait in line (head-of-line blocking).

  1000 runners × 1 connection each = 1000 TCP connections
  Expensive! OS limits! Memory heavy!

PROBLEM 2: HEADER REPETITION

  Every HTTP/1.1 request sends full headers:
    GET /heartbeat HTTP/1.1
    Host: pravah-cloud.internal
    Authorization: Bearer eyJhbGci...very long token...
    Content-Type: application/json
    X-Correlation-Id: corr-123
    X-Tenant-Id: megacorp
    ... (20+ headers, 2KB+)

  Runner sends 1 heartbeat every 10 seconds.
  1 runner sends: 6 × 2KB = 12KB/minute just for headers.
  1000 runners: 12MB/minute in HEADERS ALONE.
  Wasteful!

PROBLEM 3: NO SERVER PUSH

```text
  HTTP/1.1 is strictly request → response.
  Server cannot send data without a client request.
  Cloud cannot push job assignments to runner.
  Runner must poll: "Any jobs for me?" every second.
HTTP/2 solves all three:
```

HTTP/2 ARCHITECTURE

HTTP/2 introduces STREAMS and FRAMES.

```text
  ONE TCP connection → MULTIPLE concurrent streams
  Each stream = one logical request/response
  Streams multiplexed on same connection

  ┌─────────────────────────────────────────────────────┐
  │              Single TCP Connection                  │
  │                                                     │
  │  Stream 1: ──── heartbeat ──────────────────────►  │
  │                                 ◄── ack ──────────  │
  │                                                     │
  │  Stream 2: ──── job status update ──────────────►  │
  │                                 ◄── ack ──────────  │
  │                                                     │
  │  Stream 3:                      ◄── job assigned ─  │
  │            ──── job result ────────────────────────► │
  │                                                     │
  │  Stream 4: ──── log lines (streaming) ──────────►  │
  │            ──── log lines (streaming) ──────────►  │
  │            ──── log lines (streaming) ──────────►  │
  └─────────────────────────────────────────────────────┘
```

  All streams share ONE TCP connection ✅
  No head-of-line blocking between streams ✅
  1000 runners × 1 TCP connection = 1000 connections ✅

FRAMES — THE ATOMIC UNIT:

HTTP/2 data travels as FRAMES.
Each frame tagged with stream ID.

  Frame types:
    HEADERS frame:    HTTP headers (compressed)
    DATA frame:       Request/response body
    SETTINGS frame:   Connection parameters
    PING frame:       Keep-alive
    GOAWAY frame:     Graceful shutdown
    WINDOW_UPDATE:    Flow control signal
    RST_STREAM:       Cancel a stream

HEADER COMPRESSION (HPACK):

HTTP/2 compresses headers using HPACK algorithm.

  First heartbeat request:
    Send full headers: Authorization: Bearer token...
```text
    Headers table: [1: Authorization → Bearer token]
```

  Second heartbeat request:
    Send just index: [header 1]
    Receiver looks up table: Authorization: Bearer token
```text
    2KB headers → 1 byte! 99.95% reduction ✅
```

  For Pravah runners:
```text
    12MB/minute headers → ~6KB/minute ✅

FOUR gRPC PATTERNS
```

PATTERN 1: UNARY (request-response)
```protobuf
  Client sends one request → Server sends one response.
  Like a regular REST call but over gRPC.

  rpc GetPipelineConfig(PipelineId) returns (PipelineConfig);
```

  Use for: Simple lookups, single operations
  Pravah uses for: Runner fetching pipeline config

PATTERN 2: SERVER STREAMING
```protobuf
  Client sends one request → Server sends many responses.
  Stream stays open until server closes it.

  rpc StreamJobLogs(JobId) returns (stream LogLine);
```

  Use for: Server pushing data to client
  Pravah uses for: Pushing live logs to UI

PATTERN 3: CLIENT STREAMING
```protobuf
  Client sends many requests → Server sends one response.

  rpc UploadDataChunks(stream DataChunk) returns (UploadResult);
```

  Use for: Client uploading large data
  Pravah uses for: Runner uploading large job artifacts

```protobuf
PATTERN 4: BIDIRECTIONAL STREAMING ← PRAVAH'S MAIN PATTERN
  Client sends many requests → Server sends many responses.
  Both sides stream simultaneously and independently.
  
  rpc Connect(stream RunnerMessage) returns (stream ControlMessage);
```

  Use for: Full duplex communication
  Pravah uses for: THE RUNNER ↔ CLOUD PROTOCOL

Let's trace a Heartbeat message at the frame level:

gRPC message = HTTP/2 DATA frame(s) with specific format:

```text
  ┌──────────────────────────────────────────────────────┐
  │  gRPC Message Format (inside HTTP/2 DATA frame)     │
  │                                                      │
  │  Byte 0:     Compression flag (0=uncompressed)       │
  │  Bytes 1-4:  Message length (big-endian uint32)      │
  │  Bytes 5+:   Protobuf-encoded message body          │
  └──────────────────────────────────────────────────────┘
```

HEARTBEAT MESSAGE EXAMPLE:
  Protobuf message:
    RunnerMessage {
      heartbeat: Heartbeat {
        runner_id: "runner-001"
        status: RUNNER_BUSY
        active_jobs: 2
        cpu_usage: 0.73
        memory_usage: 0.45
        heartbeat_at: 1705312800000
      }
    }

  Serialized Protobuf bytes: ~35 bytes

  gRPC framing: [0x00][0x00 0x00 0x00 0x23][35 bytes]
  Total: 5 + 35 = 40 bytes

  HTTP/2 DATA frame:
```text
    ┌────────────────────────────────────────┐
    │ Length: 40                             │
    │ Type: DATA (0x0)                       │
    │ Flags: 0x0 (not end of stream)         │
    │ Stream ID: 1 (our bidirectional stream)│
    │ Payload: [gRPC frame: 40 bytes]        │
    └────────────────────────────────────────┘
```

  HTTP/2 frame header: 9 bytes
  Total on wire: 9 + 40 = 49 bytes per heartbeat

  Compare to HTTP/1.1 REST equivalent:
    POST /heartbeat HTTP/1.1
    + headers (2KB+)
    + JSON body (200+ bytes)
    Total: 2200+ bytes

  gRPC: 49 bytes vs REST: 2200+ bytes
  44× more efficient per heartbeat ✅
  1000 runners × every 10s:
    gRPC:  4.9MB/minute
    REST:  220MB/minute
🌊 Flow Control — Preventing Overwhelm
WHY FLOW CONTROL IS ESSENTIAL

Scenario: Runner is processing a job.
          Job generates 10,000 log lines/second.
          Runner sends all logs immediately to cloud.
          Cloud log processor: handles 1,000 lines/second.
```text
          Cloud buffer fills up → OOM → crash ❌
```

Without flow control:
  Fast sender + slow receiver = buffer overflow = crash

HTTP/2 HAS BUILT-IN FLOW CONTROL:

TWO LEVELS:
  Connection level: controls ALL streams combined
  Stream level:     controls one specific stream

Both use WINDOW SIZE — how many bytes receiver
can accept without explicit permission from receiver.

Default window: 65,535 bytes (64KB)
Pravah configures: 1MB per stream, 4MB per connection

FLOW CONTROL MECHANISM:

Runner (sender)          Cloud (receiver)
```text
    │                         │
    │  Initial window: 1MB    │
    │                         │
    │──── LogBatch (50KB) ───►│  window: 1MB - 50KB = 974KB
    │──── LogBatch (50KB) ───►│  window: 974KB - 50KB = 924KB
    │──── LogBatch (50KB) ───►│  window: 924KB - 50KB = 874KB
    │    ...                  │
    │──── LogBatch (50KB) ───►│  window: 50KB (almost full!)
    │                         │
    │  Runner checks window:  │
    │  "Only 50KB left.       │
    │   Must stop sending."   │
    │  Runner PAUSES ⏸️        │
    │                         │
    │   Cloud processes logs  │
    │   Frees up buffer space │
    │                         │
    │◄── WINDOW_UPDATE(500KB) │  "I have room for 500KB more"
    │                         │
    │  Runner RESUMES ▶️       │
    │──── LogBatch (50KB) ───►│
    │──── LogBatch (50KB) ───►│
    │    ...                  │
```

PRAVAH FLOW CONTROL CONFIGURATION:
  Initial stream window: 1MB
  Initial connection window: 4MB
  
  Cloud receiver:
```text
    Processes log batch → sends WINDOW_UPDATE
    Frequency: after consuming 50% of window
```
    
  This prevents:
    Runner overwhelming cloud ✅
    Cloud OOM from log flood ✅
    Natural backpressure signal ✅
🛡️ mTLS — Mutual Authentication
HOW mTLS WORKS IN PRAVAH

Standard TLS: Server proves identity to client.
  Client: "Show me your certificate"
  Server: "Here's my cert signed by trusted CA"
  Client: "Trust established"
  (client is anonymous)

mTLS: BOTH sides prove identity.
  Client: "Here's MY cert signed by trusted CA"
  Server: "Here's MY cert signed by trusted CA"
  BOTH: "We both verified each other. Trust established."

WHY mTLS FOR PRAVAH RUNNERS:
  Runner is on client's machine (potentially untrusted network)
  Cloud must verify: "Is this a legitimate Pravah runner?"
  Runner must verify: "Is this actually Pravah's cloud?"
  Both must be proven. mTLS. ✅

CERTIFICATE LIFECYCLE IN PRAVAH:

PRAVAH CA (Certificate Authority):
  Pravah operates its own internal CA.
  Signs certificates for:
    - Cloud gRPC endpoints
    - Each registered runner

RUNNER CERTIFICATE ISSUANCE:
  Step 1: Admin registers runner in Pravah UI
          Provides: tenant_id, runner_name, tags

  Step 2: Pravah issues runner certificate:
          {
            subject: "runner-001.megacorp.pravah.internal",
            issuer:  "pravah-internal-ca",
            validity: 90 days,
            extensions: {
              tenant_id: "megacorp",
              runner_id: "runner-001",
              allowed_tags: ["gpu", "eu-west"]
            }
          }

  Step 3: Admin downloads certificate bundle:
          runner-001.crt (certificate)
          runner-001.key (private key)
          pravah-ca.crt  (CA certificate for verification)

  Step 4: Runner deployed with certificate bundle
          Configured in runner.yaml:
            tls:
              cert: /etc/pravah/runner-001.crt
              key:  /etc/pravah/runner-001.key
              ca:   /etc/pravah/pravah-ca.crt

CERTIFICATE ROTATION (zero downtime):

90 days before expiry:
  Pravah CA issues new certificate for runner
  Runner downloads new cert alongside old cert
  Runner config: cert_bundle = [new.crt, old.crt]

During rotation window:
  Cloud accepts BOTH old and new certificates
  Runner starts using new cert for new connections
  Existing connections: continue with old cert

After old cert expires:
  Cloud stops accepting old cert
  All connections use new cert ✅
  Zero downtime ✅
🔄 Stream Recovery — Handling Disconnections
WHAT HAPPENS WHEN THE STREAM BREAKS

Runner loses network connectivity:
  TCP connection drops
  gRPC stream terminates (both sides)
  Runner: connection error
  Cloud: runner stream gone

  Cloud: "Runner heartbeat gone"
  Cloud: starts suspect timer (30 seconds)

RUNNER RECONNECTION STRATEGY:

EXPONENTIAL BACKOFF WITH JITTER:

  Connection attempt 1: immediate
  Connection attempt 2: wait 1s
  Connection attempt 3: wait 2s
  Connection attempt 4: wait 4s
  Connection attempt 5: wait 8s
  Connection attempt 6: wait 16s
  Connection attempt 7: wait 30s (max)
  Connection attempt 8+: wait 30s (stays at max)

  Jitter: ±50% random to prevent thundering herd
  (if 1000 runners all disconnect and reconnect
   at exactly same time = cloud overloaded)

```sql
  With jitter:
    Runner A retries at 1.3s
    Runner B retries at 0.7s
    Runner C retries at 1.1s
    Spread across time ✅
```

WHAT RUNNER DOES DURING DISCONNECT:

Job was running during disconnect:
  Runner CONTINUES executing the job ✅
  Runner stores: status updates, logs, results locally
  (SQLite on runner machine)

  When reconnected:
    Re-registers with cloud
    Gets new fencing token (higher epoch)
    Sends buffered status updates
    Sends buffered log lines
    Sends job result (if completed during disconnect)

CLOUD HANDLES RECONNECT:
  Receives RegisterRequest from runner-001
  Checks: is runner-001 currently marked DEAD?
```text
    YES → resurrect: mark ALIVE, assign new token
    NO  → welcome back: mark ALIVE, update token
```

  Receives buffered job result:
    Validates fencing token ✅
    Accepts result ✅
    Marks job complete ✅

WHAT IF JOB WAS REASSIGNED DURING DISCONNECT:

Runner-001 disconnects at t=0
```text
Cloud waits 60s → marks DEAD at t=60
Cloud reassigns job to Runner-002 at t=61
Runner-002 completes job at t=120
Job marked COMPLETE at t=120
```

Runner-001 reconnects at t=150:
  Sends buffered job result for Job-X
  Cloud: "Job-X already COMPLETE (Runner-002 did it)"
```text
  Cloud: validates idempotency key → DUPLICATE
  Cloud: IGNORES Runner-001's result ✅
  No double processing ✅
  Fencing token check: Runner-001's token < current
  Extra safety: would also reject on token basis ✅
📊 gRPC Health Checking & Keepalives
KEEPALIVE — DETECTING DEAD CONNECTIONS
────────────────────────────────────────────────────────────
```

Problem: TCP connection might appear alive to OS
         but actually be dead (NAT timeout, firewall
         silently dropped, cable pulled).

Without keepalives:
```text
  Runner thinks stream open → sending heartbeats
  Cloud thinks stream open → waiting for heartbeats
  Neither knows connection is dead!
  Minutes pass with no detection.
```

GRPC KEEPALIVES:
  Send HTTP/2 PING frames periodically.
```text
  If no response within timeout → declare connection dead.
```

  Runner (client) config:
```yaml
    keepAliveTime:    30s   ← send PING every 30s
    keepAliveTimeout: 10s   ← wait 10s for PONG
    keepAliveWithoutCalls: true ← ping even on idle stream
```

  Cloud (server) config:
```yaml
    keepAliveTime:    60s   ← allow client pings every 60s min
    keepAliveTimeout: 20s   ← wait 20s for client response
    permitKeepAliveWithoutCalls: true
```

PING/PONG FLOW:
```text
  Runner ──── PING (stream 0) ────────────────────────────►│
              [8 random bytes as opaque data]               │
  Runner ◄─── PONG (stream 0) ───────────────────────────────
              [same 8 bytes echoed back]
```

  If PONG not received within 10s:
    Runner: "Connection dead. Closing and reconnecting."

```text
🏗️ Pravah's gRPC Server Design
CLOUD gRPC SERVER — HANDLING 10,000 RUNNERS
────────────────────────────────────────────────────────────
```

Each runner = one persistent bidirectional stream.
10,000 runners = 10,000 concurrent streams.

gRPC server handles this with:

NETTY THREAD MODEL:
  Boss threads:   Accept new TCP connections (2 threads)
  Worker threads: Handle I/O on existing connections (N threads)
  Business threads: Execute handler logic (thread pool)

  N = 2 × CPU cores (e.g., 8 core machine = 16 workers)
  16 worker threads handle 10,000 streams via non-blocking I/O
  (Event loop model — no thread per connection needed)

STREAM HANDLER:
```java
  @Override
  public StreamObserver<RunnerMessage> connect(
      StreamObserver<ControlMessage> responseObserver) {
```

    // Called once when runner opens bidirectional stream
    // responseObserver = handle to send TO runner

```java
    return new StreamObserver<RunnerMessage>() {

      @Override
      public void onNext(RunnerMessage message) {
        // Called for each message FROM runner
        switch (message.getPayloadCase()) {
          case REGISTER:
            handleRegistration(message.getRegister(),
                               responseObserver);
            break;
          case HEARTBEAT:
            handleHeartbeat(message.getHeartbeat());
            break;
          case JOB_UPDATE:
            handleJobUpdate(message.getJobUpdate());
            break;
          case JOB_RESULT:
            handleJobResult(message.getJobResult());
            break;
          case LOGS:
            handleLogBatch(message.getLogs());
            break;
        }
      }

      @Override
      public void onError(Throwable error) {
        // Runner disconnected with error
        // Mark runner SUSPECT → start death timer
        runnerRegistry.markSuspect(runnerId);
        log.warn("Runner {} stream error: {}",
                  runnerId, error.getMessage());
      }

      @Override
      public void onCompleted() {
        // Runner gracefully closed stream
        // (drain signal responded to)
        runnerRegistry.markOffline(runnerId);
        log.info("Runner {} gracefully disconnected", runnerId);
      }
    };
  }
```

  // Sending TO runner (from any service):
  void dispatchJob(String runnerId, JobAssignment job) {
    StreamObserver<ControlMessage> runnerStream =

    if (runnerStream == null) {

    runnerStream.onNext(ControlMessage.newBuilder()

🎯 FAANG Interview Angles
❓ "Why did Pravah choose gRPC over REST or
    WebSocket for runner communication?"

Good answer:
  "Three technical requirements drove the decision.

   First, bidirectional streaming. Runners initiate
   the connection (no inbound ports needed through
   corporate firewalls), but the cloud needs to push
   job assignments to runners in real-time. HTTP/1.1
   REST is strictly request-response — the cloud
   can't push without the runner polling constantly.
   WebSocket supports bidirectional, but gRPC on
   HTTP/2 gives us multiplexed streams, built-in
   flow control, and header compression.

   Second, efficiency. 1000 runners heartbeating
   every 10 seconds over REST would send 2KB+ of
   headers per request — 220MB/minute in headers
   alone. gRPC's Protobuf encoding and HTTP/2 HPACK
   compression reduces a heartbeat to 49 bytes on
   the wire. 44× more efficient per message.

   Third, schema and code generation. Our runner
   protocol is defined in .proto files — the same
   schema language as our Kafka topics. Protobuf
   generates type-safe client and server code in
   Java and Go. Schema registry enforces compatibility
   on Kafka; Protobuf field numbers enforce it for
   gRPC. Zero ambiguity about message format."

❓ "How does HTTP/2 multiplexing help Pravah
```sql
    with 10,000 concurrent runners?"
```

Good answer:
  "HTTP/2 multiplexing allows multiple logical streams
   over a single TCP connection. Each runner maintains
   one TCP connection to the cloud, and all
   communication — heartbeats, job assignments, log
   streaming, result reporting — happens as separate
   streams on that one connection.

   Without multiplexing: 10,000 runners × 1 connection
   per request type = tens of thousands of TCP
   connections per gRPC server. TCP connection setup
   is expensive: 3-way handshake, TLS negotiation,
   HTTP/2 settings exchange — roughly 100ms and
   significant CPU per new connection.

```sql
   With multiplexing: 10,000 runners × 1 TCP connection
   = 10,000 connections total. Each new runner message
   type is a new HTTP/2 stream ID on the existing
   connection — zero connection overhead. Netty handles
   10,000 concurrent streams with 16 non-blocking I/O
   threads via event loop architecture."
```

❓ "What is HTTP/2 flow control and how does
    Pravah use it for log streaming?"

Good answer:
  "HTTP/2 flow control uses window sizes to prevent
   a fast sender from overwhelming a slow receiver.
   Each stream has a window — the sender can send
   at most window_size bytes before pausing and
   waiting for a WINDOW_UPDATE frame from the receiver.

   In Pravah, runners can generate 10,000 log lines
   per second during intensive jobs, but the cloud
   log processor handles around 1,000 lines per second.
   Without flow control, the runner would fill the
   cloud's buffers and cause OOM crashes.

   We configure a 1MB stream window for log streams.
   The runner sends log batches until it's sent 1MB
   without a WINDOW_UPDATE. Then it pauses. The cloud
   processes buffered logs, freeing space, and sends
   WINDOW_UPDATE(500KB) — the runner resumes. This
```sql
   creates natural backpressure: the runner's log
   generation rate is automatically throttled to match
   the cloud's processing rate. No separate rate
   limiting code needed — HTTP/2 handles it natively."
```

## 📌 Key Takeaways

1. HTTP/1.1 problems: head-of-line blocking,
   header repetition, no server push
   HTTP/2 solves: multiplexing, HPACK compression,
   bidirectional streams, server push

2. gRPC on HTTP/2:
   One TCP connection per runner (multiplexed)
   Protobuf encoding: 44× smaller than REST+JSON
   HPACK compression: headers compressed after first request

3. Four gRPC patterns:
   Unary: single request-response (config fetch)
   Server streaming: one request, many responses (log push)
   Client streaming: many requests, one response (upload)
   Bidirectional: both sides stream (runner ↔ cloud)

4. Bidirectional stream = Pravah's runner protocol:
   One persistent stream per runner lifetime
   Heartbeats, jobs, logs, results all on same stream
   Stream recovery: exponential backoff with jitter

5. Flow control prevents overwhelm:
   Window size = max bytes sender can send before pause
   Receiver sends WINDOW_UPDATE to grant more budget
   Natural backpressure for log streaming

6. mTLS: both runner AND cloud prove identity
   Runner cert: signed by Pravah CA, contains tenant_id
```text
   Cloud verifies runner cert → no unauthorized runners
   Runner verifies cloud cert → no man-in-the-middle
   90-day cert rotation with zero downtime
```

7. Keepalives: HTTP/2 PING/PONG detect dead connections
   Without: silent dead connection for minutes
   With: detected in 10 seconds, reconnect immediately

8. Cloud handles 10,000 runners:
   Netty event loop: 16 threads for 10,000 streams
   Non-blocking I/O: no thread per connection
   RunnerRegistry: ConcurrentHashMap of active streams
