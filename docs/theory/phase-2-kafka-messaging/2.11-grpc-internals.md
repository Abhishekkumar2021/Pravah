# 2.11 gRPC Internals: HTTP/2, Bidirectional Streaming & Flow Control

## Why gRPC for Pravah's Runners

Runners run on client machines or VMs. The cloud control plane runs in Kubernetes. The communication requirements are demanding:

- Runner initiates the connection (no inbound ports needed through corporate firewalls)
- Cloud pushes job assignments to runner in real-time
- Runner streams logs back continuously during job execution
- Heartbeats every 10 seconds
- Works through corporate firewalls
- Handles millions of messages per day
- Secure (mTLS)
- Efficient (low overhead per message)

**Options considered:**

| Option | Problem |
|---|---|
| REST (HTTP/1.1) | Request-response only — cloud cannot push to runner; 1000 runners polling every second = 1000 requests/sec just for heartbeats |
| WebSocket | Bidirectional but no built-in flow control, no schema enforcement, no code generation |
| gRPC | Bidirectional streaming, HTTP/2 multiplexing, Protobuf schema, flow control, mTLS — perfect fit |

---

## HTTP/2 — The Foundation of gRPC

HTTP/1.1 was designed in 1997 for document fetching. Three problems make it unsuitable for Pravah's runner communication.

**Problem 1: One request at a time per connection (head-of-line blocking)**

Each request needs its own TCP connection or must wait in line. 1000 runners × 1 connection each = 1000 TCP connections, expensive at OS and memory level.

**Problem 2: Header repetition**

Every HTTP/1.1 request sends full headers — authorization token, content-type, correlation ID — often 2KB+ per request. 1000 runners heartbeating every 10 seconds: 12MB/minute in headers alone.

**Problem 3: No server push**

HTTP/1.1 is strictly request → response. The server cannot send data without a client request. Cloud cannot push job assignments to runners — runners must poll constantly.

**HTTP/2 solves all three:**

HTTP/2 introduces streams and frames. A single TCP connection carries multiple concurrent logical streams, each with a unique stream ID. Frames are the atomic unit, tagged with stream ID.

```
┌─────────────────────────────────────────────────────┐
│              Single TCP Connection                  │
│                                                     │
│  Stream 1: ──── heartbeat ────────────────────────► │
│                                  ◄── ack ─────────  │
│                                                     │
│  Stream 2: ──── job status update ───────────────►  │
│                                                     │
│  Stream 3:                       ◄── job assigned ─ │
│            ──── job result ─────────────────────────►│
│                                                     │
│  Stream 4: ──── log lines (streaming) ────────────► │
│            ──── log lines (streaming) ────────────► │
└─────────────────────────────────────────────────────┘
```

No head-of-line blocking between streams. 1000 runners × 1 TCP connection = 1000 connections total (not tens of thousands).

**HPACK header compression:**

HTTP/2 compresses headers using HPACK. On first request, headers are sent in full and added to a shared table. Subsequent requests reference the table entry by index.

```
First heartbeat:  send full Authorization header (2KB)
                  table[1] = "Authorization: Bearer token"

Second heartbeat: send index [1]  → receiver looks up table
                  2KB → 1 byte (99.95% reduction) ✅
```

For Pravah runners: 12MB/minute in headers → ~6KB/minute ✅

## Four gRPC Communication Patterns

```protobuf
// Unary — single request, single response (like REST)
rpc GetPipelineConfig(PipelineId) returns (PipelineConfig);

// Server streaming — one request, many responses
rpc StreamJobLogs(JobId) returns (stream LogLine);

// Client streaming — many requests, one response
rpc UploadDataChunks(stream DataChunk) returns (UploadResult);

// Bidirectional streaming — both sides stream simultaneously
rpc Connect(stream RunnerMessage) returns (stream ControlMessage);
```

Pravah uses all four, but bidirectional streaming is the core of the runner protocol.

## Pravah's Bidirectional Stream Protocol

When a runner starts up, it opens ONE bidirectional stream to the cloud. This stream stays open for the runner's lifetime. All communication happens on this single stream.

**Message types:**

```protobuf
// Runner → Cloud
message RunnerMessage {
  oneof payload {
    RegisterRequest  register   = 1;
    Heartbeat        heartbeat  = 2;
    JobStatusUpdate  job_update = 3;
    JobResult        job_result = 4;
    LogBatch         logs       = 5;
    MetricsSnapshot  metrics    = 6;
  }
}

// Cloud → Runner
message ControlMessage {
  oneof payload {
    RegisterAck      ack        = 1;
    JobAssignment    job        = 2;
    CancelJob        cancel     = 3;
    ConfigUpdate     config     = 4;
    DrainSignal      drain      = 5;
    UpgradeSignal    upgrade    = 6;
  }
}
```

**Stream lifecycle:**

```
Runner                              Cloud (gRPC Server)
  │                                        │
  │──── TCP handshake + TLS ──────────────►│
  │──── HTTP/2 connection preface ────────►│
  │──── HEADERS frame (stream 1) ─────────►│
  │     (POST /RunnerGateway/Connect)      │
  │                                        │
  │──── DATA: RegisterRequest ────────────►│
  │     {runner_id, version, tags,         │
  │      tenant_id, capabilities}          │
  │                                        │
  │◄─── DATA: RegisterAck ─────────────────│
  │     {runner_id, fencing_token: 42,     │
  │      heartbeat_interval: 10s}          │
  │                                        │
  │         STREAM STAYS OPEN INDEFINITELY │
  │                                        │
  │──── DATA: Heartbeat ──────────────────►│  every 10s
  │◄─── DATA: JobAssignment ───────────────│  when job ready
  │──── DATA: JobStatusUpdate (RUNNING) ──►│
  │──── DATA: LogBatch ────────────────────►│  streaming
  │──── DATA: JobResult ───────────────────►│  on completion
  │◄─── DATA: DrainSignal ─────────────────│  graceful shutdown
  │──── DATA: JobResult ───────────────────►│  finish current job
  │──── HEADERS (END_STREAM) ─────────────►│  stream closes
```

## HTTP/2 Frames on the Wire

A heartbeat message at the wire level:

**gRPC message format (inside HTTP/2 DATA frame):**
```
Byte 0:     Compression flag (0 = uncompressed)
Bytes 1-4:  Message length (big-endian uint32)
Bytes 5+:   Protobuf-encoded message body
```

**Heartbeat example:**

Protobuf encodes to ~35 bytes. gRPC framing adds 5 bytes. HTTP/2 frame header adds 9 bytes. Total on wire: **49 bytes**.

Compare to HTTP/1.1 REST equivalent:
- POST /heartbeat + full headers (2KB+) + JSON body (200+ bytes)
- Total: **2,200+ bytes**

gRPC is 44× more efficient per heartbeat ✅

For 1000 runners heartbeating every 10 seconds:
- gRPC: 4.9 MB/minute
- REST: 220 MB/minute

## Flow Control — Preventing Buffer Overload

**The problem:** A runner executing an intensive job can generate 10,000 log lines per second. The cloud log processor handles 1,000 lines per second. Without flow control, the runner fills the cloud's buffers and causes OOM crashes.

HTTP/2 has built-in flow control via window sizes. The sender can transmit at most `window_size` bytes before pausing and waiting for a `WINDOW_UPDATE` frame from the receiver.

**Two levels:**
- Connection level: controls all streams combined
- Stream level: controls one specific stream

**Pravah configuration:** 1MB per stream, 4MB per connection.

**Flow control in action:**

```
Runner (sender)          Cloud (receiver)
    │                         │
    │  Initial window: 1MB    │
    │                         │
    │──── LogBatch (50KB) ───►│  window: 950KB
    │──── LogBatch (50KB) ───►│  window: 900KB
    │    (19 more batches)    │  window: ~50KB
    │                         │
    │  Runner: window < 50KB  │
    │  Runner PAUSES ⏸️        │
    │                         │
    │   Cloud processes logs  │
    │   frees buffer space    │
    │                         │
    │◄── WINDOW_UPDATE(500KB) │  "I have room for 500KB more"
    │                         │
    │  Runner RESUMES ▶️       │
    │──── LogBatch (50KB) ───►│
    │    ...                  │
```

Natural backpressure: the runner's log generation rate is automatically throttled to match the cloud's processing rate. No separate rate limiting code needed.

## mTLS — Mutual Authentication

Standard TLS: server proves its identity to the client. Client is anonymous.

mTLS: **both** sides prove identity. Essential for Pravah because runners run on client machines in potentially untrusted networks.

**Certificate lifecycle:**

1. Admin registers runner in Pravah UI (provides tenant_id, runner_name, tags)
2. Pravah CA issues a runner certificate:
   ```json
   {
     "subject": "runner-001.megacorp.pravah.internal",
     "issuer":  "pravah-internal-ca",
     "validity": "90 days",
     "extensions": { "tenant_id": "megacorp", "runner_id": "runner-001" }
   }
   ```
3. Admin downloads certificate bundle (`.crt`, `.key`, `pravah-ca.crt`)
4. Runner deployed with bundle; configured in `runner.yaml`

**mTLS handshake (simplified):**

```
Runner                              Cloud
  │──── ClientHello ────────────────►│
  │◄─── ServerHello + Certificate ───│
  │◄─── CertificateRequest ──────────│  "Send your cert too"
  │──── Certificate (runner cert) ──►│
  │──── CertificateVerify ───────────►│
  │                                   │
  │  Cloud verifies:                  │
  │    Is runner cert signed by Pravah CA? ✅
  │    Is tenant_id in cert correct? ✅
  │    Is runner_id not revoked? ✅
  │                                   │
  │  Runner verifies:                 │
  │    Is cloud cert signed by Pravah CA? ✅
  │◄─── Finished ─────────────────────│
  │──── Finished ──────────────────────►│
  │   TLS established ✅               │
  │   gRPC stream begins               │
```

**Certificate rotation (zero downtime):**

90 days before expiry, Pravah CA issues a new certificate. During the rotation window, the cloud accepts both old and new certificates. The runner uses the new certificate for new connections. After the old certificate expires, only the new one is accepted. No downtime, no service interruption.

## Stream Recovery — Handling Disconnections

When a runner loses network connectivity, the TCP connection drops and the gRPC stream terminates on both sides.

**Runner reconnection strategy — exponential backoff with jitter:**

```
Attempt 1: immediate
Attempt 2: wait 1 second  (± 50% jitter)
Attempt 3: wait 2 seconds
Attempt 4: wait 4 seconds
Attempt 5: wait 8 seconds
Attempt 6: wait 16 seconds
Attempt 7+: wait 30 seconds (max)
```

Jitter is essential: if 1000 runners all disconnect and reconnect simultaneously at exactly the same moment, the cloud is overloaded. With jitter, reconnection attempts are spread across time.

**During disconnect, the runner continues executing its job:**

Status updates, logs, and job results are buffered locally in SQLite. On reconnection, the runner re-registers, gets a new fencing token (higher epoch), and sends all buffered data. If the job completed during the disconnect, the result is submitted with the original idempotency key — the cloud deduplicates it correctly.

**If the job was reassigned during disconnect:**

```
Runner-001 disconnects at t=0
Cloud waits 60s → marks DEAD at t=60
Cloud reassigns job to Runner-002 at t=61
Runner-002 completes job at t=120
Job marked COMPLETE

Runner-001 reconnects at t=150:
  Submits buffered job result
  Cloud: "job already COMPLETE — idempotency key duplicate"
  Cloud: IGNORES Runner-001's result ✅
  Extra safety: Runner-001's fencing token < current token → also rejected ✅
```

## Keepalives — Detecting Dead Connections

**The problem:** A TCP connection might appear alive to the OS but actually be dead (NAT timeout, firewall silently dropped the connection, cable unplugged). Without keepalives, neither side detects this for minutes.

**Solution — HTTP/2 PING frames:**

```yaml
# Runner (client) config:
keepAliveTime:    30s    # send PING every 30 seconds
keepAliveTimeout: 10s    # wait 10 seconds for PONG
keepAliveWithoutCalls: true  # ping even on idle stream

# Cloud (server) config:
keepAliveTime:    60s
keepAliveTimeout: 20s
permitKeepAliveWithoutCalls: true
```

If PONG is not received within 10 seconds: "Connection dead. Close and reconnect."

## Cloud gRPC Server Design — Handling 10,000 Runners

Each runner = one persistent bidirectional stream. 10,000 runners = 10,000 concurrent streams.

gRPC on Netty uses an event loop architecture:
- **Boss threads:** accept new TCP connections (2 threads)
- **Worker threads:** handle I/O on existing connections via non-blocking I/O (2 × CPU cores)
- **Business threads:** execute handler logic

16 worker threads handle 10,000 streams via non-blocking I/O. No thread per connection needed.

```java
@Override
public StreamObserver<RunnerMessage> connect(
        StreamObserver<ControlMessage> responseObserver) {
    // Called once when runner opens bidirectional stream
    // responseObserver = handle to send TO this runner

    return new StreamObserver<RunnerMessage>() {
        @Override
        public void onNext(RunnerMessage message) {
            switch (message.getPayloadCase()) {
                case REGISTER:  handleRegistration(message.getRegister(), responseObserver); break;
                case HEARTBEAT: handleHeartbeat(message.getHeartbeat()); break;
                case JOB_UPDATE: handleJobUpdate(message.getJobUpdate()); break;
                case JOB_RESULT: handleJobResult(message.getJobResult()); break;
                case LOGS:      handleLogBatch(message.getLogs()); break;
            }
        }

        @Override
        public void onError(Throwable error) {
            // Runner disconnected with error — start death timer
            runnerRegistry.markSuspect(runnerId);
        }

        @Override
        public void onCompleted() {
            // Runner gracefully closed stream (responded to drain signal)
            runnerRegistry.markOffline(runnerId);
        }
    };
}

// Dispatching a job TO a runner (called from Scheduler/Execution Service):
void dispatchJob(String runnerId, JobAssignment job) {
    StreamObserver<ControlMessage> runnerStream = runnerRegistry.getStream(runnerId);
    if (runnerStream == null) {
        pendingJobs.enqueue(runnerId, job);  // runner not connected — queue for later
        return;
    }
    runnerStream.onNext(ControlMessage.newBuilder().setJob(job).build());
}
```

**Runner Registry** tracks all active streams in `ConcurrentHashMap<String, RunnerState>`:

```
RunnerState {
  runnerId, tenantId
  stream: StreamObserver<ControlMessage>  ← handle to send to this runner
  lastHeartbeat, status, fencingToken
  tags, activeJobs
}
```

When a job needs dispatching: find active runners with required tags, filter by available capacity, pick lowest load, call `stream.onNext(jobAssignment)`.

## System Design Interview Angles

**"Why did Pravah choose gRPC over REST or WebSocket for runner communication?"**

> Three technical requirements drove the decision. First, bidirectional streaming — runners initiate the connection (no inbound ports through corporate firewalls), but the cloud needs to push job assignments to runners in real-time. HTTP/1.1 REST is request-response only. WebSocket supports bidirectional, but gRPC on HTTP/2 gives us multiplexed streams, built-in flow control, and header compression.
>
> Second, efficiency — 1000 runners heartbeating over REST would send 2KB+ of headers per request, 220MB/minute in headers alone. gRPC reduces a heartbeat to 49 bytes on the wire (44× more efficient).
>
> Third, schema and code generation — the runner protocol is defined in `.proto` files, the same schema language as our Kafka topics. Protobuf generates type-safe client and server code. Schema registry enforces compatibility on Kafka; Protobuf field numbers enforce it for gRPC.

**"How does HTTP/2 flow control work in Pravah's log streaming?"**

> HTTP/2 flow control uses window sizes to prevent a fast sender from overwhelming a slow receiver. The sender can transmit at most `window_size` bytes before pausing for a `WINDOW_UPDATE` from the receiver.
>
> In Pravah, runners can generate 10,000 log lines per second but the cloud processes around 1,000. We configure a 1MB stream window. The runner sends log batches until it has sent 1MB without a WINDOW_UPDATE — then it pauses. The cloud processes buffered logs, frees space, and sends `WINDOW_UPDATE(500KB)`. The runner resumes. This creates natural backpressure: the runner's log rate is automatically throttled to match cloud processing capacity. No separate rate limiting code needed.

## Key Takeaways

1. **HTTP/1.1 problems:** head-of-line blocking, 2KB+ repeated headers, no server push; HTTP/2 solves all three with multiplexing, HPACK compression, and bidirectional streams
2. **gRPC efficiency:** 49 bytes per heartbeat vs 2,200+ for REST+JSON; HPACK reduces headers to 1 byte after first exchange
3. **Four gRPC patterns:** unary (config fetch), server streaming (log push to UI), client streaming (artifact upload), bidirectional (runner ↔ cloud)
4. **Bidirectional stream = Pravah's runner protocol:** one persistent stream per runner lifetime; all communication on that stream; exponential backoff with jitter for reconnection
5. **Flow control:** HTTP/2 window sizes throttle fast senders automatically; natural backpressure for log streaming
6. **mTLS:** both runner AND cloud prove identity via certificates signed by Pravah CA; 90-day rotation with zero downtime
7. **Keepalives:** HTTP/2 PING/PONG detects dead connections in 10 seconds instead of minutes
8. **Cloud handles 10,000 runners:** Netty event loop with 16 threads; non-blocking I/O; RunnerRegistry maps runner ID to stream handle
