# 2.5 Partition Strategy for Pravah's Topics
## 🧩 Why Partition Strategy Is a Critical Design Decision
THE PARTITION STRATEGY PROBLEM
────────────────────────────────────────────────────────────

Partition strategy answers TWO questions simultaneously:

  Question 1: ORDERING
    Which messages must be processed in order?
    Messages with same key → same partition → ordered.
    Wrong key choice = ordering violations.

  Question 2: PARALLELISM
    How evenly is load distributed across partitions?
    Uneven distribution = hot partitions = bottleneck.
    Wrong key choice = one partition doing all the work.

These two goals CONFLICT with each other:

  Perfect ordering → one partition → no parallelism
  Perfect parallelism → random keys → no ordering

  Partition strategy = finding the right balance.

EXAMPLE OF GETTING IT WRONG IN PRAVAH:
────────────────────────────────────────────────────────────

BAD CHOICE 1: Use tenant_id as key for job.assigned

  Tenant MegaCorp runs 90% of Pravah's jobs.
  hash("megacorp") % 24 = partition 7.
  
  Partition 7: 90% of all traffic ← HOT PARTITION 🔥
  Partitions 0-6, 8-23: 10% of traffic (idle)
  
  Result:
    One Execution Service consumer overwhelmed ❌
    23 consumers mostly idle ❌
    Throughput limited by one partition ❌

BAD CHOICE 2: Use random UUID as key for pipeline.events

  Every message → random partition.
  Load perfectly balanced ✅
  
  But: pipe-abc events scattered across all partitions:
    CREATED   → partition 7
    TRIGGERED → partition 3
    RUNNING   → partition 11
    COMPLETED → partition 2
  
  Lineage Service processes COMPLETED before TRIGGERED ❌
  Agent Service sees events out of causal order ❌
  Event sourcing broken ❌
🔑 The Four Partition Key Patterns
PATTERN 1: ENTITY KEY
────────────────────────────────────────────────────────────

Key = ID of the entity the message is about.
All messages about same entity → same partition → ordered.

  pipeline.events key = pipeline_id
  job.assigned    key = job_id
  runner.events   key = runner_id

  Use when: Ordering per entity is required.
  Trade-off: Hot partition if entity distribution is skewed.

PATTERN 2: TENANT KEY
────────────────────────────────────────────────────────────

Key = tenant_id.
All messages for same tenant → same partition.

  Use when: Per-tenant ordering matters.
            Tenant isolation needed.
  Trade-off: Massive hot partition for large tenants.

PATTERN 3: COMPOSITE KEY
────────────────────────────────────────────────────────────

Key = combination of multiple fields.
Finer-grained distribution than single field.

  Key = tenant_id + pipeline_id
  Key = date + pipeline_id

  Use when: Single entity key causes hot partitions.
            Ordering only needed within sub-scope.

PATTERN 4: NULL KEY (Round Robin)
────────────────────────────────────────────────────────────

Key = null.
Messages distributed round-robin across partitions.

  Use when: No ordering requirement.
            Maximum throughput needed.
            Messages are independent.

  Pravah uses for: runner.heartbeat
                   notifications.outbound
                   metrics events
🌡️ Hot Partition Detection and Solutions
WHAT IS A HOT PARTITION?
────────────────────────────────────────────────────────────

A hot partition receives disproportionately more
messages than other partitions.

  Partition 7: 50,000 messages/sec  ← HOT 🔥
  Partition 0-6, 8-23: 500 msg/sec each ← COLD 🧊

  Problems:
    Broker 1 (owns partition 7) CPU: 100% ❌
    Consumer reading partition 7: overwhelmed ❌
    Other consumers: mostly idle ❌
    Overall throughput: limited by partition 7 ❌

HOW TO DETECT:
  Metric: kafka_partition_message_in_rate
  Alert: any partition > 3× average rate

  Pravah monitors per-partition throughput:
    pravah_kafka_partition_bytes_in{partition="7"} = high
    → investigate partition key distribution

HOT PARTITION SOLUTIONS:
────────────────────────────────────────────────────────────

SOLUTION 1: KEY SALTING
  Add random suffix to key for high-volume entities.

  Without salting:
    "megacorp" → always partition 7

  With salting (salt = 0 to 9):
    "megacorp-0" → partition 3
    "megacorp-1" → partition 11
    "megacorp-2" → partition 7
    "megacorp-3" → partition 2
    ...
    "megacorp-9" → partition 8

    MegaCorp traffic spread across 10 partitions!

  Trade-off: ordering lost within MegaCorp.
             Messages for same pipeline still ordered
             (pipeline_id key handles that).
             Tenant-level ordering: acceptable loss.

SOLUTION 2: CUSTOM PARTITIONER
  Override default hash partitioner with custom logic.

  class PravahPartitioner implements Partitioner {
    
    @Override
    int partition(String topic, Object key, ...) {
      
      String keyStr = (String) key;
      
      // VIP tenants get dedicated partition ranges
      if (keyStr.startsWith("megacorp")) {
        // MegaCorp gets partitions 0-5 (6 dedicated)
        return random.nextInt(6);
      }
      
      if (keyStr.startsWith("globalbank")) {
        // GlobalBank gets partitions 6-11 (6 dedicated)
        return 6 + random.nextInt(6);
      }
      
      // Others share partitions 12-23 (12 shared)
      return 12 + Math.abs(keyStr.hashCode() % 12);
    }
  }

  Result:
    MegaCorp: distributed across 6 partitions ✅
    GlobalBank: distributed across 6 partitions ✅
    Others: distributed across 12 partitions ✅
    No hot partitions ✅

SOLUTION 3: INCREASE PARTITION COUNT
  More partitions = more distribution points.
  hash("megacorp") % 24 vs % 12:
    More buckets = less concentration.
  
  Trade-off: More partitions = more overhead.
             Rebalances take longer.
             More file handles on broker.
  
  Pravah: start with 24 for job.assigned,
          increase if hot partitions detected.
🗺️ Pravah's Complete Topic Partition Strategy
Now let's go through every major Pravah topic and design the partition strategy:

TOPIC 1: pipeline.events
────────────────────────────────────────────────────────────

What flows here:
  Every pipeline lifecycle event:
  CREATED, CONFIGURED, TRIGGERED, RUNNING,
  TASK_COMPLETED, TASK_FAILED, COMPLETED, FAILED

Ordering requirement:
  ALL events for a pipeline must be ordered.
  RUNNING must come after TRIGGERED.
  COMPLETED must come after all TASK_COMPLETED.
  → Strict per-pipeline ordering required.

Distribution concern:
  Pipelines distributed across tenants.
  No single pipeline is extremely hot.
  (Each pipeline runs at most once per minute)

DECISION: Key = pipeline_id
  hash("pipe-abc") % 12 = 7
  All pipe-abc events → partition 7 → ordered ✅
  Distribution: even (pipelines spread naturally) ✅

Partitions: 12
Replication: 3
Retention: 30 days (audit + agent replay)

TOPIC 2: job.assigned
────────────────────────────────────────────────────────────

What flows here:
  Job dispatch commands from Scheduler to
  Execution Service.
  One message per job to be executed.

Ordering requirement:
  Within a pipeline: jobs must start in dependency order.
  job-B (depends on job-A) must start after job-A.
  → Per-pipeline ordering required.

Distribution concern:
  HIGHEST VOLUME TOPIC in Pravah.
  1000+ jobs/sec during peak midnight burst.
  Must be distributed maximally.

DECISION: Key = pipeline_id
  All jobs for pipe-abc → same partition.
  Pipeline DAG execution order preserved ✅
  
  But: high-volume pipelines could cause hot partition.
  Solution: if pipeline has > 100 tasks/run:
    Use key = pipeline_id + task_id
    (ordering within pipeline by task_id still works
     because Execution Service resolves DAG locally)

Partitions: 24 (highest volume → most partitions)
Replication: 3
Retention: 7 days

TOPIC 3: job.results
────────────────────────────────────────────────────────────

What flows here:
  Job completion results from runners.
  Success, failure, output metadata.

Ordering requirement:
  Results processed in any order is fine.
  Scheduler just marks jobs complete.
  No inter-result ordering needed.

Distribution concern:
  High volume (matches job.assigned volume).
  Maximum distribution wanted.

DECISION: Key = job_id (UUID)
  UUIDs distribute randomly = perfect balance ✅
  No ordering needed → UUID key is fine ✅

  Why not pipeline_id?
    Results don't need pipeline ordering.
    UUID gives better distribution than pipeline_id.

Partitions: 24
Replication: 3
Retention: 7 days

TOPIC 4: runner.heartbeat
────────────────────────────────────────────────────────────

What flows here:
  Runner → Cloud: "I'm alive, here's my load"
  Every 10 seconds per runner.
  Potentially 10,000+ runners = 1000 msg/sec.

Ordering requirement:
  None. Heartbeats are independent.
  Latest heartbeat is all that matters.
  Old heartbeats can be overwritten.

Distribution concern:
  High frequency, low payload.
  Maximize distribution.

DECISION: Key = null (round-robin)
  Perfect distribution ✅
  No ordering needed ✅
  
  BONUS: Use Kafka Log Compaction
    compaction.policy = compact
    Only latest heartbeat per runner_id kept on disk.
    (Uses runner_id as LOG COMPACTION KEY in message,
     not as partition key)
    Disk usage stays bounded ✅

Partitions: 6 (lower volume per partition)
Replication: 2 (lower durability ok for heartbeats)
Retention: 1 day (compact + short retention)

TOPIC 5: lineage.events
────────────────────────────────────────────────────────────

What flows here:
  Data lineage tracking (OpenLineage spec).
  For each pipeline run:
    START event (what inputs)
    COMPLETE event (what outputs)
    Column-level transformations

Ordering requirement:
  START must be processed before COMPLETE.
  Per-run ordering required.
  → Key by run_id (unique per pipeline execution)

Distribution concern:
  Moderate volume.
  run_id is UUID → good distribution.

DECISION: Key = run_id (UUID)
  UUID = good distribution ✅
  All events for same run → same partition ✅
  START always before COMPLETE (within partition) ✅

Partitions: 12
Replication: 3
Retention: 90 days (catalog needs long history)

TOPIC 6: audit.log
────────────────────────────────────────────────────────────

What flows here:
  Immutable audit trail.
  Every action: who, what, when, result.
  Used for compliance (GDPR, HIPAA).

Ordering requirement:
  Per-tenant audit events should be ordered.
  "User changed config" before "Pipeline ran with new config"
  → Key by tenant_id

Distribution concern:
  Large tenants = hot partitions.
  Compliance doesn't need real-time — slight lag ok.

DECISION: Key = tenant_id + hash suffix
  "megacorp-" + (sequence % 3)
  → MegaCorp spread across 3 sub-keys ✅
  → Tenant-level ordering maintained ✅

Partitions: 6
Replication: 3
Retention: 365 days (compliance)

TOPIC 7: schema.drift.detected
────────────────────────────────────────────────────────────

What flows here:
  When source schema changes detected.
  Agent needs to react and suggest fixes.

Ordering requirement:
  Multiple drifts on same pipeline must be ordered.
  Can't suggest fix for drift-2 before seeing drift-1.

DECISION: Key = pipeline_id
  All drift events for pipe-abc → same partition ✅
  Agent processes in order ✅

Partitions: 6 (low volume topic)
Replication: 3
Retention: 30 days

TOPIC 8: data.quality.alerts
────────────────────────────────────────────────────────────

What flows here:
  Quality rule violations.
  "null_count > 5% for column revenue"
  "row_count < 1000 (expected > 50000)"

Ordering requirement:
  Alerts for same pipeline ordered.
  Pattern detection needs sequence.

DECISION: Key = pipeline_id + rule_id
  Composite key: finer distribution than pipeline_id alone
  Still ordered per pipeline+rule combination ✅

Partitions: 6
Replication: 3
Retention: 30 days

TOPIC 9: notifications.outbound
────────────────────────────────────────────────────────────

What flows here:
  Slack messages, emails, webhooks to send.

Ordering requirement:
  None. Notifications are fire-and-forget.
  User gets them in any order (Slack handles it).

Distribution:
  Maximize throughput.

DECISION: Key = null (round-robin)
Partitions: 3 (low volume)
Replication: 2 (best-effort delivery ok)
Retention: 1 day

TOPIC 10: billing.compute.used
────────────────────────────────────────────────────────────

What flows here:
  Compute usage metering per job.
  "job-xyz used 4.2 compute units, 45 minutes"

Ordering requirement:
  Per-tenant billing events should be ordered.
  Monthly invoice calculated from ordered events.

DECISION: Key = tenant_id
  All billing events for megacorp → same partition.
  Invoice calculation correct ✅
  
  Hot partition concern:
    MegaCorp has many jobs.
    Use composite key: tenant_id + month
    "megacorp-2024-01" → partition 3
    "megacorp-2024-02" → partition 7
    Distributes across months ✅

Partitions: 6
Replication: 3
Retention: 365 days (billing compliance)

🔍 Log Compaction — Special Strategy for Heartbeats
LOG COMPACTION — KEEPING ONLY LATEST VALUE PER KEY
────────────────────────────────────────────────────────────

Normal retention: delete old segments after time expires.

Log compaction: keep only LATEST message per key.
  Older messages with same key → deleted.
  At least one message per key → always kept.

  runner.heartbeat topic with compaction:
  
  BEFORE COMPACTION:
  [runner-001:load=0.3][runner-002:load=0.7]
  [runner-001:load=0.4][runner-003:load=0.1]
  [runner-001:load=0.5][runner-002:load=0.6]
  [runner-001:load=0.2][runner-003:load=0.2]
  
  AFTER COMPACTION:
  [runner-001:load=0.2]  ← only latest kept
  [runner-002:load=0.6]  ← only latest kept
  [runner-003:load=0.2]  ← only latest kept

  Consumer on new instance:
    Reads compacted log → gets current state of all runners
    No need to replay ALL heartbeats → just latest ✅
    Disk usage: O(unique_runners) not O(time) ✅

PRAVAH USES COMPACTION FOR:
  runner.heartbeat       ← latest runner state
  runner.capability      ← latest runner tags
  pipeline.config.latest ← latest pipeline version
  tenant.quota.current   ← latest quota per tenant

COMPACTION CONFIG:
  cleanup.policy = compact
  min.cleanable.dirty.ratio = 0.5
  segment.ms = 3600000  (1 hour segments for compaction)
⚠️ Partition Strategy Anti-Patterns
ANTI-PATTERNS TO AVOID IN PRAVAH
────────────────────────────────────────────────────────────

ANTI-PATTERN 1: Timestamp as key
  Key = event_timestamp.milliseconds
  
  Problem: Every message gets unique key.
           = effectively random distribution.
           No ordering guarantees (millisecond resolution
           means multiple events same ms = any order).
  
  Better: Use entity_id for ordering,
          timestamp as message field not key.

ANTI-PATTERN 2: Sequential integer as key
  Key = auto_increment_job_id
  
  Problem: New jobs always have highest IDs.
           All recent jobs cluster to same partition.
           Hot partition grows over time.
  
  Better: Use UUID (random distribution) or
          hash(pipeline_id) for entity ordering.

ANTI-PATTERN 3: Status as key
  Key = job.status ("RUNNING", "COMPLETED", "FAILED")
  
  Problem: Only 5-6 unique keys.
           5-6 partitions ever used (rest idle).
           Status changes cause ordering violations
           (same job's events on different partitions).
  
  Better: Entity ID as key always.

ANTI-PATTERN 4: Changing partition count mid-stream
  Increase pipeline.events from 12 to 24 partitions.
  
  Before: hash("pipe-abc") % 12 = partition 7
  After:  hash("pipe-abc") % 24 = partition 19
  
  pipe-abc history: partition 7
  pipe-abc new events: partition 19
  
  Consumers must read BOTH partitions for full history.
  Lineage and ordering broken. ❌
  
  Solution: Never change partition count for ordered topics.
            Create new topic with more partitions.
            Migrate consumers gradually.
            Pravah: plan partition count upfront.

ANTI-PATTERN 5: Too many partitions
  Temptation: "more partitions = more parallel"
  Set all topics to 100 partitions.
  
  Problems:
    Each partition = file handles on broker
    100 topics × 100 partitions × 3 replicas = 30,000 files
    Broker JVM heap pressure (partition metadata in memory)
    Rebalances take much longer (more partitions to move)
    Controller election slower (more metadata)
  
  Pravah rule: partitions = 2 × expected_peak_consumers
               Never exceed 50 per topic without analysis
🎯 FAANG Interview Angles
❓ "How did you decide partition keys for
    Pravah's different Kafka topics?"

Good answer:
  "Each topic has different ordering and distribution
   requirements — there's no one-size-fits-all key.

   For pipeline.events, ordering is critical:
   RUNNING must come after TRIGGERED for the same
   pipeline. We use pipeline_id as key — all events
   for the same pipeline land on the same partition
   in strict offset order.

   For job.results, ordering doesn't matter — the
   scheduler just marks jobs complete regardless of
   result order. We use job_id (UUID) for maximum
   distribution across 24 partitions.

   For runner.heartbeat, no ordering, maximum
   throughput. We use null key (round-robin) plus
   log compaction — only the latest heartbeat per
   runner is retained, keeping disk usage bounded.

   The common thread: identify what needs ordering,
   use that entity's ID as key. Where no ordering
   needed, use UUID or null for distribution."

❓ "What is a hot partition and how would you
    detect and fix one in Pravah?"

Good answer:
  "A hot partition receives disproportionately more
   messages than others — typically because a high-
   volume entity's ID always hashes to the same
   partition. In Pravah, MegaCorp running 90% of
   jobs would hot-partition job.assigned if we keyed
   by tenant_id.

   Detection: monitor kafka_partition_message_in_rate
   per partition. Alert when any partition exceeds
   3× the average rate across all partitions.

   Fix depends on cause. If one tenant is hot:
   custom partitioner that spreads that tenant across
   multiple partitions (sacrificing tenant-level
   ordering if it's not required). If one pipeline
   is hot — key salting: append random suffix 0-9
   to pipeline_id, spreading across 10× more
   partitions while keeping pipeline_id in the message
   body for processing logic."

❓ "Why can't you decrease partition count in
    production and how do you handle scaling?"

Good answer:
  "Partition assignment is deterministic:
   partition = hash(key) % num_partitions.
   Reducing partitions changes the mapping —
   pipe-abc was on partition 7 with 12 partitions,
   would move to partition 1 with 6 partitions.
   Historical data stays on partition 7, new
   messages go to partition 1. Consumers reading
   both would see events out of order.

   Partition count is a one-way door — only
   increases allowed. Pravah handles this by
   planning upfront: we use 2× the expected peak
   consumer count as starting partition count.
   For job.assigned we started at 24 — enough
   headroom for scaling to 24 consumer instances.
   If we genuinely need more, we create a new
   topic with higher partition count and migrate
   consumers gradually using a dual-read period."
## 📌 Key Takeaways
1. Partition strategy balances TWO goals:
   Ordering (same key → same partition → ordered)
   Distribution (even load → no hot partitions)

2. Four key patterns:
   Entity key: ordering per entity (pipeline_id)
   Tenant key: tenant isolation (hot partition risk)
   Composite key: finer distribution (tenant+month)
   Null key: maximum distribution (no ordering)

3. Hot partition detection:
   Monitor partition_message_in_rate per partition
   Alert at 3× average → investigate

4. Hot partition fixes:
   Key salting: append random suffix
   Custom partitioner: VIP tenant routing
   Increase partition count (one-way door)

5. Log compaction: keep only latest per key
   Perfect for: heartbeats, current config, quotas
   Disk usage: O(unique keys) not O(time)

6. Partition count: can increase, never decrease
   Plan upfront: 2× expected peak consumers
   New topic approach for major partition changes

7. Anti-patterns to avoid:
   Timestamp as key (no ordering)
   Sequential int as key (hot partition grows)
   Status as key (few unique values)
   Too many partitions (broker overhead)

8. Pravah total: ~186 partitions, ~486 replicas
   job.assigned highest volume: 24 partitions
   audit.log longest retention: 365 days
