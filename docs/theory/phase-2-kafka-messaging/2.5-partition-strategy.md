# 2.5 Partition Strategy for Pravah's Topics

## The Dual Problem

Choosing a partition key answers two questions simultaneously:

**Ordering** — which messages must be processed in sequence? Messages with the same key always go to the same partition and are consumed in strict offset order.

**Distribution** — how evenly is load spread? An uneven key causes a hot partition, bottlenecking the entire topic.

These two goals conflict:
- Perfect ordering → one partition → no parallelism
- Perfect distribution → random keys → no ordering

Partition strategy is finding the right balance for each specific topic.

---

## The Four Key Patterns

| Pattern | Key | Use When |
|---|---|---|
| **Entity key** | The entity's own ID (e.g., `pipeline_id`) | Ordering per entity is required |
| **Tenant key** | `tenant_id` | Per-tenant ordering matters, low tenant variance |
| **Composite key** | e.g., `tenant_id + month` | Single field causes hot partitions; sub-scope ordering sufficient |
| **Null (round-robin)** | `null` | No ordering requirement; maximum distribution |

---

## Hot Partitions — Detection and Fixes

A hot partition receives disproportionately more messages than others. Example: MegaCorp runs 90% of Pravah's jobs. If `tenant_id` is the key for `job.assigned`, `hash("megacorp") % 24 = partition 7` receives 90% of all traffic. The consumer on partition 7 is overwhelmed; 23 others are idle.

**Detection:** monitor `kafka_partition_message_in_rate` per partition. Alert when any partition exceeds 3× the cluster average.

**Fix 1 — Key salting:** append a random suffix `0–9` to the key:
```
Without salting: "megacorp" → always partition 7

With salting:
  "megacorp-0" → partition 3
  "megacorp-1" → partition 11
  "megacorp-2" → partition 7
  ...
  "megacorp-9" → partition 8

MegaCorp traffic spread across ~10 partitions ✅
Trade-off: tenant-level ordering lost (usually acceptable)
```

**Fix 2 — Custom partitioner:** route VIP tenants to dedicated partition ranges:
```java
public int partition(String topic, Object key, ...) {
    String keyStr = (String) key;
    if (keyStr.startsWith("megacorp")) return random.nextInt(6);        // partitions 0-5
    if (keyStr.startsWith("globalbank")) return 6 + random.nextInt(6);  // partitions 6-11
    return 12 + Math.abs(keyStr.hashCode() % 12);                       // partitions 12-23
}
```

**Fix 3 — Increase partition count:** more partitions = more hash buckets = less concentration per key. Trade-off: more file handles, longer rebalances.

## Pravah's Topic-by-Topic Partition Design

### `pipeline.events`

Events: CREATED, CONFIGURED, TRIGGERED, RUNNING, TASK_COMPLETED, TASK_FAILED, COMPLETED, FAILED.

Ordering requirement: all events for a pipeline must be in sequence. RUNNING must come after TRIGGERED. COMPLETED must come after all TASK_COMPLETED.

Distribution: pipelines are naturally distributed across tenants. No single pipeline is extremely hot (each runs at most once per minute).

**Decision: key = `pipeline_id`**

```
hash("pipe-abc") % 12 = partition 7 → always
All pipe-abc events → partition 7 → strict ordering ✅
```

Partitions: 12 | Replication: 3 | Retention: 30 days

### `job.assigned`

Dispatches from Scheduler to Execution Service. One message per job.

Ordering requirement: within a pipeline, jobs must execute in dependency order — job-B (depends on job-A) must start after job-A.

Distribution: highest-volume topic in Pravah — 1000+ jobs/sec at peak. Must be distributed maximally.

**Decision: key = `pipeline_id`**

All jobs for `pipe-abc` → same partition → DAG execution order preserved. For very large pipelines (>100 tasks), use `pipeline_id + task_id` — the Execution Service resolves DAG locally.

Partitions: 24 | Replication: 3 | Retention: 7 days

### `job.results`

Completion results from runners: success, failure, output metadata.

Ordering requirement: none — the Scheduler marks jobs complete regardless of result order.

Distribution: same volume as `job.assigned`. Maximum distribution wanted.

**Decision: key = `job_id` (UUID)**

UUID distributes randomly, giving near-perfect load balance across all 24 partitions.

Partitions: 24 | Replication: 3 | Retention: 7 days

### `runner.heartbeat`

Every runner sends a heartbeat every 10 seconds. 10,000 runners = 1,000 messages/sec. Only the latest heartbeat per runner matters.

Ordering requirement: none. Heartbeats are independent.

**Decision: key = `null` (round-robin) + Log Compaction**

```
cleanup.policy=compact

BEFORE compaction:
  [runner-001: load=0.3][runner-002: load=0.7]
  [runner-001: load=0.4][runner-001: load=0.5]
  [runner-001: load=0.2]

AFTER compaction:
  [runner-001: load=0.2]  ← only latest kept
  [runner-002: load=0.7]  ← only latest kept

A new consumer starting from earliest reads only current state.
Disk usage: O(unique runners) not O(time) ✅
```

Partitions: 6 | Replication: 2 | Retention: 1 day (compact)

### `lineage.events`

OpenLineage spec events: START (what inputs) and COMPLETE (what outputs) per pipeline run.

Ordering requirement: START must be processed before COMPLETE for the same run.

**Decision: key = `run_id` (UUID)**

Each pipeline execution gets a unique `run_id`. UUID distributes randomly. All events for the same run land on the same partition in order.

Partitions: 12 | Replication: 3 | Retention: 90 days

### `audit.log`

Immutable audit trail for compliance. Every action: who, what, when, result.

Ordering requirement: per-tenant — "user changed config" before "pipeline ran with new config."

Hot partition concern: large tenants generate most audit events. Fixed with salting: `key = tenant_id + random_suffix_0_to_9`.

Partitions: 6 | Replication: 3 | Retention: 365 days

### `billing.compute.used`

Compute metering events — foundation for billing accuracy. Must be queryable by tenant and time period.

Ordering requirement: per-tenant per-month events must be ordered (to compute running totals correctly).

**Decision: key = `tenant_id + month` (e.g., `megacorp-2024-01`)**

Composite key distributes by tenant AND month — MegaCorp generates events across 12 monthly partitions rather than one.

Partitions: 6 | Replication: 3 | Retention: 365 days

## Anti-Patterns to Avoid

**Timestamp as key:** every message gets a unique key → random distribution → no ordering.

**Sequential integer as key:** new jobs always have the highest IDs → recent events cluster on the same partition → hot partition grows over time.

**Status as key:** only 5–6 unique values → 5–6 partitions active → others idle → breaks ordering for the same entity across status changes.

**Changing partition count mid-stream:** `hash("pipe-abc") % 12 = 7` but `hash("pipe-abc") % 24 = 19`. Historical data on partition 7, new data on partition 19. Ordering broken. Solution: create a new topic with the higher count and migrate consumers gradually.

**Too many partitions:** each partition = file handles on brokers + memory for metadata. 100 topics × 100 partitions × 3 replicas = 30,000 files. Rebalances get slow. Pravah rule: never exceed 50 partitions per topic without analysis; start at 2× expected peak consumer count.

## System Design Interview Angles

**"How did you decide partition keys for Pravah's different Kafka topics?"**

> Each topic has different ordering and distribution requirements. For `pipeline.events`, ordering is critical — RUNNING must come after TRIGGERED — so we use `pipeline_id` as the key. For `job.results`, ordering doesn't matter — we use `job_id` (UUID) for maximum distribution. For `runner.heartbeat`, no ordering and we want only the latest state, so we use null key with log compaction — disk stays bounded at O(unique runners). The principle: identify what needs ordering, use that entity's ID as key. Where no ordering is needed, use UUID or null for distribution.

**"What is a hot partition and how would you detect and fix one in Pravah?"**

> A hot partition receives disproportionately more messages — typically because a high-volume entity always hashes to the same partition. Detection: monitor `kafka_partition_message_in_rate` per partition, alert when any exceeds 3× average. Fixes depend on cause: key salting (append random suffix 0–9 to the key, spreading across 10× more partitions), custom partitioner routing VIP tenants to dedicated partition ranges, or increasing partition count. The right fix depends on whether per-entity ordering must be preserved.

**"Why can't you decrease partition count in production?"**

> Partition assignment is deterministic: `hash(key) % num_partitions`. Reducing partitions changes every hash mapping — historical data on the old partition, new data on a different one. Consumers reading both would see events out of order. Partition count is a one-way door. Pravah plans upfront using 2× the expected peak consumer count, and for genuine re-partitioning we create a new topic and migrate consumers gradually with a dual-read period.

## 📌 Key Takeaways

1. Partition strategy balances two conflicting goals: ordering (same key → same partition) and distribution (even load → no hot partitions)
2. Four key patterns: entity ID for ordering, tenant ID for isolation, composite for fine distribution, null for maximum throughput
3. Hot partition = one partition overwhelmed; detect via per-partition throughput metrics; fix with salting or custom partitioner
4. Log compaction: keep only the latest value per key — ideal for current state topics (heartbeats, config, quotas)
5. Partition count: can increase, never decrease — plan upfront at 2× expected peak consumer count
6. Anti-patterns: timestamp key, sequential integer key, status key, too many partitions
