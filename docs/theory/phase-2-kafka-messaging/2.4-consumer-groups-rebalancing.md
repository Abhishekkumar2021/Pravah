# 2.4 Consumer Groups, Rebalancing & Offset Management

## The Multi-Consumer Challenge

When `pipeline.events` is published, Pravah has four simultaneous requirements:

1. **Every service sees every event** — Execution, Lineage, and Agent Services all need all events → they must be independent consumers
2. **Within a service, work is parallel** — three Execution Service instances should divide the work → they must cooperate as one logical consumer
3. **No event processed twice by the same service** — two instances must not both process the same event
4. **No event missed if an instance crashes** — a crashed instance's partitions must be taken over

Consumer Groups solve all four.

---

## Consumer Groups — The Core Concept

A **consumer group** is a logical subscriber to a topic. Each group receives a complete copy of all messages. Within a group, partitions are divided — each partition is assigned to exactly one instance.

```
Topic: pipeline.events (12 partitions)

Group: execution-service-group
  Instance 1: partitions 0,1,2,3    (4 partitions)
  Instance 2: partitions 4,5,6,7    (4 partitions)
  Instance 3: partitions 8,9,10,11  (4 partitions)
  Each partition processed by EXACTLY ONE instance ✅

Group: lineage-service-group
  Instance 1: partitions 0-5        (6 partitions)
  Instance 2: partitions 6-11       (6 partitions)
  COMPLETELY INDEPENDENT from execution-service-group ✅

Group: agent-service-group
  Instance 1: ALL 12 partitions (singleton service)
```

One topic. Three groups. Each group reads all messages independently. Within each group, no duplication.

---

## Group Coordinator and Lifecycle

The **Group Coordinator** is a specific Kafka broker responsible for tracking group membership, managing heartbeats, storing committed offsets, and triggering rebalances. Which broker? `hash(group_id) % num_partitions_of___consumer_offsets` — always the same, deterministic.

**Consumer lifecycle:**

```
Step 1  JoinGroupRequest
        Consumer starts → finds coordinator → sends JoinGroupRequest
        {group_id: "execution-service-group", protocols: ["CooperativeStickyAssignor"]}

Step 2  Elect Group Leader
        Coordinator picks one consumer as Group Leader (usually first to join).
        Note: different from Kafka controller or partition leader.

Step 3  Partition Assignment
        Group Leader runs assignment algorithm, sends result to Coordinator.
        Coordinator distributes assignments to all members.

Step 4  Consume
        Each consumer reads its assigned partitions.
        Sends heartbeats every heartbeat.interval.ms.

Step 5  Rebalance (on membership change)
        Consumer leaves or crashes → Coordinator triggers rebalance.
```

## The Rebalance Problem

A rebalance occurs when partition assignments need to change: a consumer joins, crashes, leaves, or new partitions are added.

**Classic eager rebalance (stop-the-world):**

```
t=0  Consumer-3 crashes (session timeout exceeded)
     REBALANCE TRIGGERED

t=1  ALL consumers stop consuming ← 😱
     Consumer-1 drops partitions 0,1,2,3
     Consumer-2 drops partitions 4,5,6,7

t=2  All consumers re-join group, send JoinGroupRequest

t=3  New assignment computed:
     Consumer-1: partitions 0,1,2,3,4,5  (gained P4,P5)
     Consumer-2: partitions 6,7,8,9,10,11 (gained P8-11)

t=4  All consumers resume
```

Duration: 2–30 seconds depending on group size. During this window in Pravah: job assignments not consumed, pipeline events not processed, Agent not monitoring, Lineage not recording.

**Incremental cooperative rebalance (Kafka 2.4+):**

Only revoke partitions that need to move. Others keep consuming.

```
Consumer-4 joins. REBALANCE TRIGGERED.

Round 1 — while ALL consumers keep consuming:
  Leader computes: C4 needs P3, P7, P11
  SyncGroup: "C1 revoke P3, C2 revoke P7, C3 revoke P11"
  C1, C2, C3 continue reading their other partitions ✅

Round 2:
  C1 revokes P3, C2 revokes P7, C3 revokes P11
  C4 assigned P3, P7, P11 → starts consuming ✅

Result: only 3 partitions paused; 9 consumed continuously.
        Rebalance impact reduced by 75%.
```

**Pravah configuration:** `partition.assignment.strategy=CooperativeStickyAssignor`

"Sticky" means: preserve existing assignments during rebalance — minimize movement. A consumer keeps all its current partitions that are not being moved.

## Heartbeats and Timeouts

Three independent timeouts, each serving a different purpose:

| Config | Pravah value | Purpose |
|---|---|---|
| `heartbeat.interval.ms` | 3000 | How often consumer pings the coordinator ("I'm alive"). Separate thread — consumer can be slow processing and still heartbeat. |
| `session.timeout.ms` | 45000 | If no heartbeat received for 45s → consumer declared dead → rebalance. 45s gives buffer for transient network issues. |
| `max.poll.interval.ms` | 300000 | If main thread doesn't call `poll()` for 5 min → consumer stuck → rebalance. Detects consumers that heartbeat fine but are hung in processing. |

**Why max.poll.interval.ms matters for Pravah's Agent Service:**

LLM calls take 30+ seconds. The heartbeat thread stays alive, but the main thread is blocked waiting for the LLM. Without a long `max.poll.interval.ms`, Kafka declares the consumer dead mid-LLM-call.

```
Agent Service config:
  max.poll.records=10        (small batches → finish quickly)
  max.poll.interval.ms=600000 (10 minutes for LLM latency)
```

## Offset Management

Consumer offsets are stored in Kafka itself — the internal `__consumer_offsets` topic. Key: `{group_id, topic, partition}`. Value: `{offset}`.

**Never use auto-commit for critical services:**

```
Auto commit (enable.auto.commit=true):
  t=0  Consume records 0-99
  t=5  AUTO COMMIT fires! Offsets 0-99 committed.
  t=6  Consumer crashes before finishing processing.
  t=7  Restarts, reads committed offset 100.
  t=7  Records 50-99 were never fully processed! DATA LOSS ❌
```

**Manual commit pattern (Pravah's approach):**

```java
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));

    for (ConsumerRecord<String, String> record : records) {
        try {
            processRecord(record);  // idempotent
        } catch (NonRetryableException e) {
            sendToDLQ(record, e);   // bad record → DLQ
        }
    }

    // Commit ONLY AFTER the full batch is processed
    consumer.commitSync(currentOffsets(records));
}
```

On crash before commit: consumer restarts, re-reads from last committed offset, re-processes some records. Idempotency keys deduplicate them. At-least-once delivery + idempotent processing = effectively exactly-once.

**Commit per partition, not globally:**

```java
Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
offsets.put(new TopicPartition("pipeline.events", 7), new OffsetAndMetadata(1001));
offsets.put(new TopicPartition("pipeline.events", 3), new OffsetAndMetadata(451));
consumer.commitSync(offsets);
```

**Handle rebalance mid-processing with `ConsumerRebalanceListener`:**

```java
consumer.subscribe(topics, new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // Called BEFORE partitions are taken away.
        // Commit current offsets NOW to prevent re-processing by new owner.
        consumer.commitSync(currentOffsets(partitions));
    }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // Reset any partition-specific in-memory state.
        resetStateForPartitions(partitions);
    }
});
```

Without this listener, a consumer that crashes mid-batch may have its partitions reassigned, and the new owner re-processes records the crashed consumer already processed (but didn't commit).

## Consumer Parallelism Rules

```
pipeline.events has 12 partitions.

1 consumer:   reads all 12 partitions (no parallelism)
3 consumers:  4 partitions each (balanced)
12 consumers: 1 partition each (maximum parallelism)
13 consumers: 12 active + 1 IDLE (wasted resource)
```

Consumers > partitions → idle consumers. Adding consumers beyond the partition count provides zero benefit. Pravah scales Execution Service pods via KEDA based on Kafka consumer lag — stops scaling when lag reaches zero or consumer count reaches partition count.

## FAANG Interview Angles

**"How does Pravah ensure the same pipeline event isn't processed twice by two Execution Service instances?"**

> Partition assignment within a consumer group guarantees exactly one consumer owns each partition at any time. We use `pipeline_id` as the message key — all events for `pipe-abc` land on the same partition. That partition is assigned to exactly one Execution Service instance. If the instance crashes, rebalance assigns that partition to another instance which resumes from the last committed offset. It may re-process a few records (at-least-once), but idempotency keys in our processing store deduplicate them.

**"What is the stop-the-world rebalance problem and how does Pravah avoid it?"**

> Classic eager rebalancing revokes ALL partitions from ALL consumers when any membership change happens — even adding one consumer stops all processing for 5–30 seconds. We use `CooperativeStickyAssignor` (incremental cooperative rebalancing): only partitions that actually need to move are revoked. If a new Execution Service pod joins, only 4 of 24 partitions move — the other 20 keep consuming continuously. "Sticky" means consumers keep their existing partitions when possible, minimizing movement.

**"What happens if a consumer is processing a slow LLM call when Kafka decides it's dead?"**

> This is exactly why `max.poll.interval.ms` exists separately from `session.timeout.ms`. The heartbeat thread runs independently — the consumer can heartbeat fine while blocked on an LLM call. But if the main thread doesn't call `poll()` for longer than `max.poll.interval.ms`, Kafka considers the consumer stuck and triggers a rebalance. For Agent Service, we set `max.poll.records=10` (small batches finish faster) and `max.poll.interval.ms=600000` (10 minutes to accommodate LLM latency).

---

## 📌 Key Takeaways

1. Consumer Group = logical subscriber; each group gets all messages; within a group partitions are shared
2. Eager rebalance = stop the world; `CooperativeStickyAssignor` = incremental, only moved partitions pause
3. Three timeouts: heartbeat frequency, dead detection, stuck detection — each independent
4. Always use manual commit (`enable.auto.commit=false`); commit after processing, not before
5. `ConsumerRebalanceListener::onPartitionsRevoked` must commit current offsets to prevent re-processing
6. Max parallelism = partition count; consumers beyond that are idle
7. `auto.offset.reset=earliest` for services that need full history (Agent); `latest` for notification-style consumers
