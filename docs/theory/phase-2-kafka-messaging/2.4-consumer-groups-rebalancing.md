# 2.4 Consumer Groups, Rebalancing & Offset Management

## 🧩 Start With The Core Problem

THE MULTI-CONSUMER CHALLENGE

Pravah publishes pipeline.events to Kafka.
15+ services need to react to these events.

REQUIREMENT 1: Every service sees every event
  Execution Service needs ALL pipeline events
  Lineage Service needs ALL pipeline events
  Agent Service needs ALL pipeline events
```text
  → They must be INDEPENDENT consumers
```

REQUIREMENT 2: Within each service, work is parallel
  Execution Service has 3 instances running
  All 3 should share the work
```text
  → They must COOPERATE as one logical consumer
```

REQUIREMENT 3: No event processed twice by same service
  Execution Service instance 1 processes pipe-abc
  Instance 2 must NOT also process pipe-abc
```text
  → Partitions must be exclusively assigned
```

REQUIREMENT 4: No event missed if instance crashes
  Instance 1 was processing partition 7
  Instance 1 crashes
```text
  → Instance 2 or 3 must take over partition 7
```

Consumer Groups solve ALL of these. Here's how.
👥 Consumer Groups — The Mental Model
CONSUMER GROUP CONCEPT

A Consumer Group = a logical subscriber to a topic.
Each group gets a COMPLETE COPY of all messages.
Within a group, partitions are SHARED (no duplicates).

Topic: pipeline.events (12 partitions)

```text
┌─────────────────────────────────────────────────────────┐
│  Group: execution-service-group                         │
│                                                         │
│  Instance 1: partitions 0,1,2,3    (owns 4 partitions) │
│  Instance 2: partitions 4,5,6,7    (owns 4 partitions) │
│  Instance 3: partitions 8,9,10,11  (owns 4 partitions) │
│                                                         │
│  Each partition processed by EXACTLY ONE instance ✅    │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  Group: lineage-service-group                           │
│                                                         │
│  Instance 1: partitions 0,1,2,3,4,5   (6 partitions)  │
│  Instance 2: partitions 6,7,8,9,10,11 (6 partitions)  │
│                                                         │
│  COMPLETELY INDEPENDENT from execution-service-group ✅ │
│  Both groups read ALL 12 partitions' messages          │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  Group: agent-service-group                             │
```

  One topic, many groups = Kafka's fanout superpower
🔗 The Group Coordinator
HOW KAFKA MANAGES CONSUMER GROUPS

Every consumer group has a GROUP COORDINATOR:
  A specific Kafka broker responsible for:
```text
    → Tracking group membership
    → Triggering rebalances
    → Storing committed offsets
    → Managing heartbeats
```

  Which broker is coordinator?
    hash(group_id) % num_partitions_of___consumer_offsets
    = always deterministic, always the same broker
```text
    (unless that broker fails → new coordinator elected)
```

CONSUMER LIFECYCLE:

Step 1: JOIN GROUP
```yaml
  Consumer starts → finds coordinator broker
  Sends: JoinGroupRequest
    {group_id: "execution-service-group",
     member_id: "",  ← empty on first join
     protocols: ["RangeAssignor", "RoundRobinAssignor"]}
```

Step 2: ELECT LEADER
  Coordinator picks one consumer as GROUP LEADER
  (not same as Kafka controller or partition leader)
  Group Leader = first consumer to join (usually)

Step 3: SYNC GROUP
  Coordinator tells all members: "wait for assignment"
  Group Leader runs partition assignment algorithm
  Group Leader sends assignment to Coordinator
  Coordinator distributes assignments to all members

Step 4: CONSUME
  Each consumer reads its assigned partitions
  Sends heartbeats every heartbeat.interval.ms

Step 5: LEAVE/CRASH
  Consumer sends LeaveGroup (graceful)
  OR misses heartbeats (crash)
```text
  → Triggers REBALANCE
```

```text
⚡ The Rebalance Problem
WHAT IS A REBALANCE?
────────────────────────────────────────────────────────────
```

A rebalance is when Kafka redistributes partitions
among consumers in a group.

TRIGGERS:
```text
  → New consumer joins the group
  → Consumer crashes (misses heartbeats)
  → Consumer gracefully leaves
  → New partitions added to topic
  → Subscription changes
```

THE STOP-THE-WORLD REBALANCE (EAGER):

Default behavior (classic rebalance):

t=0:  Consumer-3 crashes
t=0:  Coordinator: session timeout exceeded
t=0:  REBALANCE TRIGGERED

```yaml
t=1:  ALL consumers stop consuming ← 😱
      Consumer-1: drops P0,P1,P2,P3
      Consumer-2: drops P4,P5,P6,P7
```

t=2:  All consumers re-join group
      All send JoinGroupRequest

t=3:  New assignment computed:
      Consumer-1: P0,P1,P2,P3,P4,P5  (got P4,P5 from C3)
      Consumer-2: P6,P7,P8,P9,P10,P11 (got P8-11 from C3)

t=4:  All consumers get new assignment
      Resume consuming

DURATION OF STOP:
  t=1 to t=4 = REBALANCE WINDOW
  No consumption during this window

  Typical duration:
    Small group (3 consumers): 2-5 seconds
    Large group (50 consumers): 10-30 seconds

  During this time in Pravah:
    Job assignments not consumed
    Pipeline events not processed
    Agent not monitoring
    Lineage not recorded
    
    This is why rebalances must be MINIMIZED ✅
The modern solution — Incremental Cooperative Rebalancing:

COOPERATIVE REBALANCING (Kafka 2.4+)

Key idea: Only revoke partitions that NEED to move.
          Others keep consuming during rebalance.

t=0:  Consumer-4 joins group (scale up event)
      REBALANCE TRIGGERED

ROUND 1 — Identify what needs to move:
  t=1:  All consumers send JoinGroup
        (but KEEP CONSUMING their current partitions!)
  t=2:  Leader computes new assignment:
        C1: P0,P1,P2    (was P0,P1,P2,P3 — loses P3)
        C2: P4,P5,P6    (was P4,P5,P6,P7 — loses P7)
        C3: P8,P9,P10   (was P8,P9,P10,P11 — loses P11)
        C4: P3,P7,P11   (new consumer gets these)

  t=3:  SyncGroup: "C1 revoke P3, C2 revoke P7, C3 revoke P11"
        C1, C2, C3 continue consuming OTHER partitions ✅
        Only P3, P7, P11 paused

ROUND 2 — Assign revoked partitions:
  t=4:  C1 revokes P3
        C2 revokes P7
        C3 revokes P11
        All send JoinGroup again

  t=5:  C4 gets assigned P3, P7, P11
        C4 starts consuming ✅

RESULT:
  Only 3 partitions paused (P3, P7, P11)
  9 partitions consumed continuously ✅
  Rebalance impact: 75% reduction ✅

PRAVAH CONFIG:
  partition.assignment.strategy =
```text
    CooperativeStickyAssignor  ← incremental + sticky
```
  
  "Sticky" means: try to keep same partitions
  as before rebalance (minimize movement)
💓 Heartbeats & Session Timeouts
HOW KAFKA DETECTS CONSUMER FAILURE

Consumer sends heartbeats to coordinator:

  heartbeat.interval.ms = 3000    (every 3 seconds)
  session.timeout.ms    = 45000   (45 second timeout)
  max.poll.interval.ms  = 300000  (5 minute max between polls)

THREE DIFFERENT TIMEOUTS — EACH DOES SOMETHING DIFFERENT:

1. heartbeat.interval.ms (3s):
   How often consumer pings coordinator.
   "I'm alive"
   Separate thread from processing.
   Consumer can be slow processing AND still heartbeat.

2. session.timeout.ms (45s):
   If coordinator doesn't hear heartbeat for 45s:
```text
   Consumer declared DEAD → rebalance triggered.
```
   
   Why 45s and not 3s?
   Network glitch might delay a few heartbeats.
   3s would cause false positives constantly.
   45s = enough buffer for transient issues.

3. max.poll.interval.ms (5min):
   If consumer polls Kafka but takes > 5min to
   process records between polls:
```text
   Consumer declared DEAD → rebalance triggered.
```
   
   Why this exists:
   Consumer might heartbeat fine (alive thread)
   But be stuck in processing (long DB operation).
   After 5min stuck: assume consumer is broken,
   give its partitions to someone else.
   
   Pravah sets this high for Agent Service:
   LLM calls can take 30+ seconds per batch.
   max.poll.interval.ms = 600000 (10 minutes)

VISUAL HEARTBEAT FLOW:

Consumer-1 main thread:        Consumer-1 heartbeat thread:
```text
  poll() → process records       every 3s: send heartbeat
  poll() → process records       every 3s: send heartbeat
  poll() → STUCK (slow job)      every 3s: send heartbeat ✅
  (5 minutes pass)               every 3s: send heartbeat ✅
  poll() → still stuck           every 3s: send heartbeat ✅
  (max.poll.interval exceeded)   every 3s: send heartbeat ✅
```
                                 
Coordinator: "Heartbeats fine, but no poll for 5min"
             "Consumer-1 declared dead. Rebalance."

Consumer-1 heartbeat gets response: "REBALANCE_IN_PROGRESS"
Consumer-1 stops processing, rejoins group.
📍 Offset Management — The Full Picture
OFFSET STORAGE

Consumer offsets stored in Kafka itself:
  Internal topic: __consumer_offsets
  Key:   {group_id, topic, partition}
  Value: {offset, metadata, timestamp}

  Replicated, durable, backed by Kafka's own storage.
  No external state store needed.

TWO COMMIT MODES:

AUTO COMMIT (enable.auto.commit = true):
  auto.commit.interval.ms = 5000 (every 5 seconds)

  Problem:
    t=0:  Consume records 0-99
    t=3:  Processing records 0-99...
    t=5:  AUTO COMMIT fires! Offsets 0-99 committed!
    t=6:  Consumer crashes before finishing processing
    t=7:  Consumer restarts
    t=7:  Reads committed offset: 100 (start from 100)
    t=7:  Records 50-99 were NOT fully processed! ❌
    
    DATA LOSS — committed before processing complete.
    
  Pravah: NEVER uses auto commit for critical services.

MANUAL COMMIT (enable.auto.commit = false):
  Application controls exactly when to commit.

  Two types:
  
```sql
  commitSync():
    Blocks until broker confirms commit.
    Safe but slower.
    Use for: low-throughput critical operations.
    
  commitAsync():
    Non-blocking, callback on completion.
    Faster but requires careful error handling.
    Use for: high-throughput processing.
```

PRAVAH OFFSET COMMIT STRATEGY:

  enable.auto.commit = false

  For each batch of records:
    1. Poll records
    2. Process records (with idempotency)
    3. Commit offset AFTER successful processing
```text
    4. If processing fails → DON'T commit → retry
```

  CODE PATTERN:
  while (running) {
    ConsumerRecords records = consumer.poll(Duration.ofMs(100));
    
    for (ConsumerRecord record : records) {
      try {
        processRecord(record);  // idempotent processing
      } catch (NonRetryableException e) {
```text
        sendToDLQ(record);      // bad record → DLQ
      }
    }
```
    
    // Commit only after ALL records in batch processed
    consumer.commitSync();  // or commitAsync with retry
  }

AT-LEAST-ONCE DELIVERY:
  Crash after processing but before commit:
```text
    Consumer restarts → re-reads from last commit
    Re-processes already-processed records
    Idempotency keys deduplicate ✅
```
    
  This is intentional — at-least-once + idempotency
  = effectively exactly-once ✅
🔄 Offset Commit Edge Cases
EDGE CASE 1: PARTIAL BATCH FAILURE

Batch: records at offsets 100, 101, 102, 103, 104

  offset 100: processed ✅
  offset 101: processed ✅
  offset 102: FAILED (bad data)
  offset 103: not yet processed
  offset 104: not yet processed

Options:
  A) Commit offset 102 (skip bad record):
```text
     → Bad record goes to DLQ
     → Commit offset 103
     → Continue with 103, 104 ✅
```

  B) Don't commit anything, retry entire batch:
```text
     → Re-process 100, 101 (idempotent → safe)
     → Re-process 102 → fails again → DLQ
     → Commit 103, continue ✅
```

Pravah uses Option A:
  Per-record error handling
```text
  Bad records → DLQ immediately
  Good records committed normally
  No stalls on bad data ✅
```

EDGE CASE 2: COMMIT OFFSET PER PARTITION

Consumer reads from multiple partitions simultaneously.
Each partition has independent offset.
Must commit per partition, not globally.

  partition 7 offset: 1000 (processed up to here)
  partition 3 offset: 450  (processed up to here)
  partition 11 offset: 230 (processed up to here)

  Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
  offsets.put(new TopicPartition("pipeline.events", 7),
```java
              new OffsetAndMetadata(1001));
  offsets.put(new TopicPartition("pipeline.events", 3),
              new OffsetAndMetadata(451));
  offsets.put(new TopicPartition("pipeline.events", 11),
              new OffsetAndMetadata(231));
```

  consumer.commitSync(offsets);  // commit per partition ✅

EDGE CASE 3: REBALANCE DURING PROCESSING

Consumer-1 is processing records from partition 7.
Mid-processing: REBALANCE triggered.
Partition 7 is being moved to Consumer-2.

Without handling:
  Consumer-1: finishes processing, commits partition 7 offset
  But partition 7 now belongs to Consumer-2!
  Consumer-2 already started consuming partition 7 from last commit
  Consumer-2 re-processes records Consumer-1 already processed
  DUPLICATES ❌

```sql
With ConsumerRebalanceListener:
```

  consumer.subscribe(topics, new ConsumerRebalanceListener() {
    
```java
    @Override
    onPartitionsRevoked(Collection<TopicPartition> partitions) {
      // Called BEFORE partitions are taken away
      // Commit current offsets for these partitions NOW
      commitCurrentOffsets(partitions);  // ← critical!
    }
    
    @Override
    onPartitionsAssigned(Collection<TopicPartition> partitions) {
      // Called AFTER new partitions assigned
      // Reset any partition-specific state
      resetStateForPartitions(partitions);
    }
  });
```

  When rebalance starts:
    onPartitionsRevoked called with [partition 7]
    Consumer-1 commits partition 7's current offset
    Rebalance completes
    Consumer-2 gets partition 7
    Consumer-2 starts from committed offset ✅
    No duplicates ✅

🎯 FAANG Interview Angles
❓ "How does Pravah ensure the same pipeline event
    isn't processed twice by two Execution Service
    instances?"

Good answer:
  "Partition assignment within a consumer group
   guarantees exactly one consumer owns each partition
   at any time. pipeline.events uses pipeline_id as
   the message key — all events for pipe-abc land on
   the same partition. That partition is assigned to
   exactly one Execution Service instance.

   If the instance crashes, the rebalance assigns
   that partition to another instance, which resumes
```sql
   from the last committed offset. The new instance
   might re-process a few records if the crash happened
   before commit — but idempotency keys in our
   processing store deduplicate those. So we get
   effectively exactly-once processing."
```

❓ "What is the stop-the-world rebalance problem
    and how does Pravah avoid it?"

Good answer:
  "Classic eager rebalancing revokes ALL partitions
```sql
   from ALL consumers when any membership change
   happens — even adding one consumer stops all
   processing for 5-30 seconds while partitions
   are reassigned. At Pravah's scale this means
   thousands of pipeline events unprocessed.
```

   We use CooperativeStickyAssignor which implements
   incremental cooperative rebalancing. Only partitions
   that actually need to move are revoked. If a new
   Execution Service pod joins, only 4 of 24 partitions
   move — the other 20 keep consuming continuously.
   The 'sticky' part means consumers keep their
   existing partitions when possible, minimizing
   movement across rebalances."

❓ "What happens if a consumer is processing a
    slow LLM call when Kafka decides it's dead?"

Good answer:
  "This is why max.poll.interval.ms exists separately
```sql
   from session.timeout.ms. The heartbeat thread runs
   independently of the processing thread — so the
   consumer can heartbeat fine while stuck in a long
   LLM call.
```

   But if the main thread doesn't call poll() for
   longer than max.poll.interval.ms, Kafka considers
   the consumer unhealthy — it's not making progress.
   For Pravah's Agent Service, LLM calls can take
   30+ seconds, so we set max.poll.records=10 (small
   batches) and max.poll.interval.ms=600000 (10 min).
   Small batches mean each poll cycle processes fewer
   records, finishing LLM calls within the window."

## 📌 Key Takeaways

1. Consumer Group = logical subscriber
   Each group gets complete copy of all messages
   Within group: partitions shared, no duplicates

2. Group Leader handles partition assignment
   Coordinator broker manages group membership
   Assignment strategies: Range, RoundRobin,
   Sticky, CooperativeSticky

3. Eager rebalance = stop the world (avoid!)
   CooperativeStickyAssignor = incremental rebalance
   Only moved partitions pause, others continue

4. Three timeouts serve different purposes:
   heartbeat.interval.ms = liveness ping frequency
   session.timeout.ms = dead detection threshold
   max.poll.interval.ms = processing stuck detection

5. Always use manual commit (auto.commit = false)
```sql
   Commit AFTER processing, not before
   Use ConsumerRebalanceListener to commit on revoke
```

6. Max parallelism = partition count
   Consumers > partitions = idle consumers (waste)
   Pravah: 24 partitions for job.assigned (scalable)

7. At-least-once + idempotency = effectively
   exactly-once without Kafka transactions overhead
   Kafka transactions (exactly-once) covered in 2.6

8. Different services need different configs:
   Agent: small batches, long poll interval (LLM)
   Execution: large batches, fast poll interval
