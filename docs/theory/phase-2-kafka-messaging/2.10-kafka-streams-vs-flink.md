# 2.10 Kafka Streams vs Flink for Streaming Pipelines

## 🧩 Start With The Context

PRAVAH'S STREAMING PIPELINE FEATURE

Pravah supports three execution modes:

  BATCH:        Process data in scheduled chunks
                Run at midnight, process yesterday's data
                Latency: minutes to hours

  MICRO-BATCH:  Process small chunks frequently
                Run every 30 seconds
                Latency: seconds to minutes

  STREAMING:    Process data as it arrives
                React to each event immediately
                Latency: milliseconds to seconds

When enterprise client says:
  "Alert me within 5 seconds when a customer's
   order exceeds ₹50,000"
```text
  → STREAMING mode required
```

  "Calculate hourly revenue by region in real-time"
```text
  → STREAMING with windowing required
```

  "Detect fraudulent transactions as they happen"
```text
  → STREAMING with stateful processing required
```

Two tools solve this: Kafka Streams and Apache Flink.
They look similar on the surface.
Underneath they're architecturally very different.
📊 The Fundamental Difference
KAFKA STREAMS vs FLINK — THE CORE DISTINCTION

KAFKA STREAMS:
  A LIBRARY embedded in your Java application.
  No separate cluster needed.
  Runs inside your Spring Boot service.
  Kafka is both input AND state store.

  Your App
```text
  ┌────────────────────────────────────────┐
  │  Spring Boot Service                   │
  │  ┌──────────────────────────────────┐  │
  │  │     Kafka Streams Library        │  │
  │  │  topology runs here              │  │
  │  │  state stored in RocksDB (local) │  │
  │  └──────────────────────────────────┘  │
  └────────────────────────────────────────┘
       ↕ reads/writes
  Kafka Cluster
```

APACHE FLINK:
  A SEPARATE DISTRIBUTED SYSTEM (cluster).
  Your code submitted as a job to Flink cluster.
  Independent of Kafka (reads from it, writes to it).
  Manages its own state, checkpointing, scaling.

  Your Job (JAR)
```text
       ↓ submitted to
  ┌───────────────────────────────────────────┐
  │         Flink Cluster                     │
  │  ┌───────────┐  ┌───────────────────────┐ │
  │  │ JobManager│  │    TaskManagers        │ │
  │  │(coordinator)│  │ (parallel workers)  │ │
  │  └───────────┘  └───────────────────────┘ │
  └───────────────────────────────────────────┘
       ↕ reads/writes
  Kafka Cluster + State Backend (RocksDB/S3)
```

Pipeline: Monitor orders, alert when total > ₹50K

StreamsBuilder builder = new StreamsBuilder();

// Source: read from Kafka topic
KStream<String, OrderEvent> orders = builder.stream(
    "pravah-source-postgres.public.orders",
    Consumed.with(Serdes.String(), orderSerde));

// Step 1: Filter — only completed orders
KStream<String, OrderEvent> completed = orders
    .filter((orderId, order) ->
        order.getStatus().equals("COMPLETED"));

// Step 2: Map — extract customer + amount
KStream<String, CustomerAmount> byCustomer = completed
    .map((orderId, order) ->
        KeyValue.pair(
            order.getCustomerId(),         // rekey by customer
```java
            new CustomerAmount(
                order.getCustomerId(),
                order.getAmount())));
```

// Step 3: Aggregate — running total per customer
// Tumbling window: reset every 1 hour
KTable<Windowed<String>, Double> hourlyTotals = byCustomer
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(
        Duration.ofHours(1)))
    .aggregate(
        () -> 0.0,                          // initializer
        (customerId, newAmount, currentTotal) ->
            currentTotal + newAmount.getAmount(), // aggregator
        Materialized.<String, Double, WindowStore<Bytes, byte[]>>as(
            "customer-hourly-totals")       // state store name
            .withValueSerde(Serdes.Double())
    );

// Step 4: Filter — only totals exceeding ₹50K
KStream<String, AlertEvent> alerts = hourlyTotals
    .toStream()
    .filter((windowedKey, total) -> total > 50000.0)
    .map((windowedKey, total) ->
        KeyValue.pair(
            windowedKey.key(),             // customer ID
            AlertEvent.builder()
                .customerId(windowedKey.key())
                .totalAmount(total)
                .windowStart(windowedKey.window().start())
                .windowEnd(windowedKey.window().end())
                .build()));

// Step 5: Sink — publish alerts to Kafka
alerts.to("pravah.alerts.high-value-customers",
    Produced.with(Serdes.String(), alertSerde));

// Build and start
KafkaStreams streams = new KafkaStreams(
    builder.build(), streamsConfig);
streams.start();

```text
Flink's killer feature — Event Time Processing:
```

EVENT TIME vs PROCESSING TIME

PROCESSING TIME:
  When did Flink receive the event?
  Simple. Fast. Wrong for out-of-order events.

  Problem:
    Order placed at 10:00:00 (event time)
```text
    Network delay → Flink receives at 10:00:05 (processing time)
    Flink assigns to 10:00-11:00 window: ✅ CORRECT
```

    Mobile app order at 10:00:58 (event time)
```text
    App offline → syncs at 10:02:30 (processing time)
    Flink assigns to 10:00-11:00 window: ❌ WRONG!
    (processing time 10:02 → assigned to 10:00-11:00 window
     BUT arrived 2 minutes late — window may already be closed)
```

EVENT TIME:
  When did the event ACTUALLY happen?
  Uses timestamp embedded in the event.
  Correct for late-arriving events.
  Requires watermarks to know when window is complete.

```text
  Order at 10:00:00 event_time → correct 10:00-11:00 window ✅
  Late order at 10:00:58 event_time → correct 10:00-11:00 window ✅
  Even if it arrives at 10:02:30 ✅
```

WATERMARKS — THE KEY CONCEPT:

Problem: How does Flink know when ALL events for a
         time window have arrived?
         Events can be late by seconds, minutes, hours.
         It can't wait forever.

Solution: Watermarks — a signal that says:
  "I believe all events with timestamp < W have arrived.
   It's safe to close windows with end time < W."

WATERMARK EXAMPLE:
  Events arrive:
```text
    t=10:00:01  order-A (event_time: 10:00:01) → watermark: 09:59:56
    t=10:00:02  order-B (event_time: 10:00:02) → watermark: 09:59:57
    t=10:00:05  order-C (event_time: 10:00:04) → watermark: 09:59:59
    t=10:00:08  order-D (event_time: 10:00:07) → watermark: 10:00:02
    t=10:00:10  order-E (event_time: 10:00:09) → watermark: 10:00:04
```

  Watermark = max(event_time_seen) - 5 seconds (allowed lateness)
  
  When watermark passes 10:00:00:
    "All events before 10:00:00 have arrived"
    "Window 09:00-10:00 can now be finalized" ✅

  Late event arrives (event_time: 09:59:30) at t=10:00:15:
    Watermark already past 10:00:00.
    This event is LATE.
    Options:
      A) Drop it (simple)
      B) Update result (allowed lateness)
      C) Send to side output for separate handling
    Pravah uses: B + C (update + side output for very late)

⏱️ Windowing — Types and When to Use Each
WINDOW TYPES IN PRAVAH

TUMBLING WINDOW:
  Fixed size. No overlap. Events in exactly one window.

  Size: 1 hour
```text
  ────────────────────────────────────────────────────
  |  09:00 - 10:00  |  10:00 - 11:00  |  11:00 - 12:00  |
  ────────────────────────────────────────────────────
```

  Use for: Hourly revenue reports
           Daily pipeline run counts
           Periodic billing calculations

  Pravah: "Calculate total data processed per hour per tenant"

SLIDING WINDOW:
  Fixed size. Overlapping. Events in multiple windows.

  Size: 1 hour. Slide: 15 minutes.
```text
  ────────────────────────────────────────────────────
  |09:00──────────────────10:00|
      |09:15─────────────────10:15|
          |09:30────────────────10:30|
              |09:45───────────────10:45|
  ────────────────────────────────────────────────────
```

  Use for: Rolling averages
           Moving window anomaly detection
           Continuous monitoring metrics

  Pravah: "Alert if pipeline error rate > 5%
           in any rolling 30-minute window"

SESSION WINDOW:
  Dynamic size. Gap-based. Closes after inactivity.

  Gap: 10 minutes
```text
  ────────────────────────────────────────────────────
  Events: ●●●  (gap > 10min)  ●●●●●  (gap > 10min)  ●●
          |session 1|          |session 2|            |s3|
  ────────────────────────────────────────────────────
```

  Use for: User session analysis
           IoT device active periods
           API call burst patterns

  Pravah: "Group a runner's activity into work sessions
           (active periods separated by idle gaps)"

GLOBAL WINDOW:
  All events in one window forever.
  Requires custom trigger to emit results.

  Use for: Custom trigger logic
           Event-count-based windowing

  Pravah: "Alert after every 1000th job failure
           (regardless of time)"

```text
🎯 FAANG Interview Angles
❓ "What's the difference between Kafka Streams
    and Flink, and when does Pravah use each?"
```

Good answer:
  "The fundamental difference is deployment model.
   Kafka Streams is a library that runs inside your
   application — no separate cluster, state lives in
   local RocksDB backed by Kafka changelog topics.
   Flink is a separate distributed processing cluster
   — jobs are submitted to it, it manages parallelism,
   state backends, and checkpointing independently.

   Pravah uses Kafka Streams for simpler transformations
   embedded in existing Spring Boot services: filtering,
   enrichment via stream-table joins, simple windowed
   counts. Zero operational overhead — it just runs.

   We use Flink when pipelines need advanced features:
   complex event pattern matching via CEP, session
   windows, out-of-order event handling with watermarks,
   or unified batch-and-stream processing. Flink's
   event time semantics correctly handle mobile app
   events arriving minutes late — Kafka Streams has
   limited support for this. The tradeoff: Flink
   requires a separate cluster with its own HA setup."

❓ "What is a watermark in Flink and why is it
    necessary for Pravah's streaming pipelines?"

Good answer:
  "A watermark is Flink's mechanism for deciding
   when it's safe to close a time window despite
   events potentially arriving out of order.

   The problem: event time and processing time differ.
   A mobile app order placed at 10:00 might reach
   Flink at 10:02 if the app was briefly offline.
   Without watermarks, Flink can't know whether
   the 10:00-11:00 window is complete — more events
```sql
   with event_time < 11:00 might still be coming.
```

   Watermarks solve this by asserting: 'all events
```sql
   with timestamp < W have arrived.' In Pravah we
   set a bounded-out-of-orderness watermark with a
   10-second delay: watermark = max_event_time_seen
   - 10 seconds. When the watermark passes a window's
   end time, Flink fires the window result.
```

   Events arriving after the watermark has passed
   their window are 'late events.' Pravah configures
   10 minutes of allowed lateness — Flink updates
   the window result if the event arrives within
   10 minutes of window close. Beyond that, events
   are routed to a side output topic for separate
   investigation."

❓ "How does Flink ensure exactly-once processing
    in Pravah's streaming pipelines?"

Good answer:
  "Flink uses a distributed snapshot algorithm called
   Chandy-Lamport to take consistent checkpoints of
   all operator state simultaneously.

   Every 30 seconds, the JobManager injects checkpoint
   barriers into the source streams — special markers
   that flow through the topology like regular events.
   When an operator receives barriers from all its
   inputs, it snapshots its state to MinIO and
   acknowledges back to JobManager.

   On failure, Flink restarts from the latest complete
   checkpoint — all operators restore their state from
   MinIO snapshots and resume Kafka consumption from
   the offset recorded in that checkpoint.

   For Kafka sinks, Flink uses two-phase commit
   aligned with checkpoints: events are pre-committed
   to Kafka but not yet visible. When the checkpoint
   completes, Flink commits the Kafka transaction —
   making events visible. This gives end-to-end
   exactly-once: from Kafka source through processing
   state to Kafka sink, aligned with checkpoint
   boundaries."

## 📌 Key Takeaways

1. Kafka Streams = library in your app
   Flink = separate distributed cluster
   Same end goal: streaming event processing
   Very different operational profiles

2. Kafka Streams strengths:
   Simple to deploy (runs in Spring Boot)
   Native Kafka integration
   Good for: filter, map, join, simple aggregation
   State: RocksDB local + Kafka changelog backup

3. Flink strengths:
   Event time processing with watermarks
   Complex event pattern matching (CEP)
   Out-of-order event handling
   Unified batch + stream
   State: RocksDB + S3 checkpoints

4. Watermarks = signal that time window is complete
   Bounded out-of-orderness: W = max_seen - delay
   Late events: update window OR side output

5. Window types:
   Tumbling: non-overlapping (hourly revenue)
   Sliding: overlapping (rolling 30-min average)
   Session: gap-based (user activity sessions)
   Global: custom trigger (count-based)

6. Flink checkpointing = exactly-once guarantee:
   Every 30s: snapshot all operator state to MinIO
   Failure: restart from checkpoint + replay Kafka
   Kafka sink: 2PC aligned with checkpoints

7. Pravah uses both:
   Kafka Streams: simple transformations in services
   Flink: complex streaming pipelines submitted as jobs
   Complexity classifier decides which to use

8. Late data strategy:
   Allowed lateness: update window (10 min in Pravah)
```text
   Very late: side output → separate topic → investigate
```
