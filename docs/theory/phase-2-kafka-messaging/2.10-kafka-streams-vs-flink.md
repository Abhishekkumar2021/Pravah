# 2.10 Kafka Streams vs Flink for Streaming Pipelines

## Pravah's Streaming Pipeline Feature

Pravah supports three execution modes:

| Mode | Description | Latency |
|---|---|---|
| **Batch** | Process data in scheduled chunks | Minutes to hours |
| **Micro-batch** | Process small chunks frequently (every 30 seconds) | Seconds to minutes |
| **Streaming** | Process data as it arrives, react to each event | Milliseconds to seconds |

Enterprise client use cases that require streaming:
- "Alert me within 5 seconds when a customer's order exceeds ₹50,000" → streaming with windowing
- "Calculate hourly revenue by region in real-time" → streaming with tumbling window
- "Detect fraudulent transactions as they happen" → streaming with stateful pattern matching

Two tools solve this: Kafka Streams and Apache Flink. They look similar on the surface. Underneath they are architecturally very different.

---

## The Fundamental Difference

**Kafka Streams** is a library embedded in your Java application. No separate cluster. Runs inside your Spring Boot service. Kafka is both input source and state changelog.

```
┌────────────────────────────────────────┐
│  Spring Boot Service                   │
│  ┌──────────────────────────────────┐  │
│  │     Kafka Streams Library        │  │
│  │  topology runs here              │  │
│  │  state stored in RocksDB (local) │  │
│  └──────────────────────────────────┘  │
└────────────────────────────────────────┘
       ↕ reads/writes
Kafka Cluster
```

**Apache Flink** is a separate distributed processing cluster. Your code is submitted as a job to the Flink cluster. Manages its own state, checkpointing, and scaling independently of Kafka.

```
Your Job (JAR)
     ↓ submitted to
┌───────────────────────────────────────────┐
│         Flink Cluster                     │
│  ┌───────────┐  ┌───────────────────────┐ │
│  │ JobManager│  │    TaskManagers       │ │
│  │(coordinator│  │ (parallel workers)   │ │
│  └───────────┘  └───────────────────────┘ │
└───────────────────────────────────────────┘
     ↕ reads/writes
Kafka + State Backend (RocksDB / S3)
```

## Kafka Streams — Deep Dive

**Core abstractions:**

- `KStream` — unbounded stream of records; each record is an independent event (every order transaction)
- `KTable` — changelog stream materialized to a view; latest value per key (current balance per customer)
- `GlobalKTable` — `KTable` replicated to all instances; for small lookup tables (product catalog, tenant config)

A **Topology** is a directed acyclic graph of processing steps:

```
Source → [stateless processor] → [stateful processor] → Sink
             (filter, map)          (aggregate, join)
```

**Pravah example — real-time order monitoring:**

Pipeline: Monitor orders, alert when hourly total per customer exceeds ₹50,000.

```java
StreamsBuilder builder = new StreamsBuilder();

KStream<String, OrderEvent> orders = builder.stream(
    "pravah-source-postgres.public.orders",
    Consumed.with(Serdes.String(), orderSerde));

KStream<String, CustomerAmount> byCustomer = orders
    .filter((orderId, order) -> order.getStatus().equals("COMPLETED"))
    .map((orderId, order) -> KeyValue.pair(
        order.getCustomerId(),
        new CustomerAmount(order.getCustomerId(), order.getAmount())));

KTable<Windowed<String>, Double> hourlyTotals = byCustomer
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofHours(1)))
    .aggregate(
        () -> 0.0,
        (customerId, newAmount, current) -> current + newAmount.getAmount(),
        Materialized.as("customer-hourly-totals").withValueSerde(Serdes.Double())
    );

KStream<String, AlertEvent> alerts = hourlyTotals
    .toStream()
    .filter((windowedKey, total) -> total > 50000.0)
    .map((windowedKey, total) -> KeyValue.pair(
        windowedKey.key(),
        AlertEvent.builder()
            .customerId(windowedKey.key())
            .totalAmount(total)
            .windowStart(windowedKey.window().start())
            .build()));

alerts.to("pravah.alerts.high-value-customers",
    Produced.with(Serdes.String(), alertSerde));

KafkaStreams streams = new KafkaStreams(builder.build(), streamsConfig);
streams.start();
```

**State management:**

State lives in RocksDB (embedded, same JVM). State is backed up to a Kafka changelog topic. On restart, state is restored from the changelog — crash recovery without external coordination.

**Scaling:**

Run 3 instances of the service. Kafka Streams distributes partitions across instances. Each instance handles a subset of customers. State is local to each instance by partition key.

```
Instance 1: partitions 0-3  → customers A-D
Instance 2: partitions 4-7  → customers E-H
Instance 3: partitions 8-11 → customers I-Z
```

Customer-001 always routes to the same instance → correct local state accumulation ✅

## Apache Flink — Deep Dive

Flink is a full distributed processing framework designed for both bounded (batch) and unbounded (stream) processing on the same engine.

**Cluster components:**

```
┌─────────────────────────────────────────────────────────┐
│                    FLINK CLUSTER                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │                  JobManager                      │  │
│  │  - Receives submitted jobs                       │  │
│  │  - Optimizes execution plan                      │  │
│  │  - Coordinates checkpointing                     │  │
│  │  - HA: standby JobManagers via Raft              │  │
│  └──────────────────────────────────────────────────┘  │
│             │              │              │             │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐   │
│  │ TaskManager 1│ │ TaskManager 2│ │ TaskManager 3│   │
│  │ [Task Slot]  │ │ [Task Slot]  │ │ [Task Slot]  │   │
│  │ RocksDB state│ │ RocksDB state│ │ RocksDB state│   │
│  └──────────────┘ └──────────────┘ └──────────────┘   │
│  State Backend: RocksDB → checkpointed to S3/MinIO     │
└─────────────────────────────────────────────────────────┘
```

**Flink's key differentiator — Event Time Processing:**

**Processing time** = when Flink received the event. Simple but wrong for out-of-order events. A mobile app order placed at 10:00:58 but synced at 10:02:30 would be assigned to the wrong window.

**Event time** = when the event actually happened (timestamp embedded in the event). Correct for late-arriving events. Requires watermarks to know when a window is complete.

**Watermarks** — the key concept:

A watermark is a signal that says: "I believe all events with timestamp < W have arrived. Windows ending before W can now be finalized."

```
Events arrive (event_time → processing time):
  order-A: 10:00:01 → watermark: 09:59:56
  order-B: 10:00:02 → watermark: 09:59:57
  order-C: 10:00:04 → watermark: 09:59:59
  order-D: 10:00:07 → watermark: 10:00:02

Watermark = max(event_time_seen) - 5 seconds (allowed lateness)

When watermark passes 10:00:00:
  "All events before 10:00:00 have arrived"
  "Window 09:00-10:00 can now be finalized" ✅

Late event arrives (event_time: 09:59:30) at 10:00:15:
  Watermark already past 10:00:00 → this event is late
  Pravah: update window result (allowed lateness: 10 min)
           OR route to side output for very late events
```

**Flink example — fraud detection:**

```java
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.enableCheckpointing(30000);  // checkpoint every 30 seconds
env.getCheckpointConfig().setCheckpointStorage("s3://pravah-flink-state/checkpoints/");
env.setStateBackend(new EmbeddedRocksDBStateBackend());

KafkaSource<TransactionEvent> source = KafkaSource.<TransactionEvent>builder()
    .setBootstrapServers("kafka:9092")
    .setTopics("pravah-source-postgres.public.transactions")
    .setGroupId("pravah-fraud-detection")
    .setValueOnlyDeserializer(new TransactionDeserializer())
    .build();

DataStream<TransactionEvent> transactions = env.fromSource(
    source,
    WatermarkStrategy.<TransactionEvent>forBoundedOutOfOrderness(Duration.ofSeconds(10))
        .withTimestampAssigner((event, ts) -> event.getTransactionTime()),
    "Kafka Source");

// Detect: 3 transactions > ₹10K within 5 minutes (CEP)
Pattern<TransactionEvent, ?> fraudPattern = Pattern
    .<TransactionEvent>begin("first")
        .where(new SimpleCondition<>() {
            public boolean filter(TransactionEvent e) { return e.getAmount() > 10000; }
        })
    .next("second")
        .where(new SimpleCondition<>() {
            public boolean filter(TransactionEvent e) { return e.getAmount() > 10000; }
        })
    .next("third")
        .where(new SimpleCondition<>() {
            public boolean filter(TransactionEvent e) { return e.getAmount() > 10000; }
        })
    .within(Time.minutes(5));

PatternStream<TransactionEvent> patternStream =
    CEP.pattern(transactions.keyBy(TransactionEvent::getAccountId), fraudPattern);

DataStream<FraudAlert> fraudAlerts = patternStream.select(pattern ->
    FraudAlert.builder()
        .accountId(pattern.get("first").get(0).getAccountId())
        .detectedAt(Instant.now())
        .build());

KafkaSink<FraudAlert> sink = KafkaSink.<FraudAlert>builder()
    .setBootstrapServers("kafka:9092")
    .setRecordSerializer(KafkaRecordSerializationSchema.builder()
        .setTopic("pravah.alerts.fraud")
        .setValueSerializationSchema(new FraudAlertSerializer())
        .build())
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
    .build();

fraudAlerts.sinkTo(sink);
env.execute("Pravah Fraud Detection Pipeline");
```

## Window Types in Pravah

**Tumbling window:** Fixed size, no overlap. Events belong to exactly one window.

```
|  09:00 ─────────── 10:00  |  10:00 ─────────── 11:00  |  11:00 ─────────── 12:00  |
```

Use for: hourly revenue reports, periodic billing calculations, daily pipeline run counts.

**Sliding window:** Fixed size, overlapping. Events belong to multiple windows.

Size: 1 hour. Slide: 15 minutes.
```
|09:00──────────────────────10:00|
    |09:15─────────────────────10:15|
        |09:30────────────────────10:30|
```

Use for: rolling averages, continuous monitoring metrics, moving window anomaly detection.

**Session window:** Dynamic size, gap-based. Closes after inactivity.

Gap: 10 minutes.
```
Events: ●●●  (gap > 10min)  ●●●●●  (gap > 10min)  ●●
        |  session 1  |     |  session 2  |         |s3|
```

Use for: user session analysis, IoT device active periods, API call burst patterns.

**Global window:** All events in one window forever. Requires a custom trigger. Use for: count-based windowing ("alert after every 1000th job failure").

## Kafka Streams vs Flink — Complete Comparison

| Dimension | Kafka Streams | Flink |
|---|---|---|
| Deployment model | Library in your app | Separate cluster |
| Operational complexity | Low | High |
| Throughput | High | Very high |
| Latency | Low (milliseconds) | Very low (sub-millisecond) |
| Event time processing | Basic | Full (watermarks, CEP) |
| Out-of-order handling | Limited | Excellent |
| Complex event patterns | No | Yes (CEP) |
| SQL support | ksqlDB | Flink SQL |
| State management | RocksDB local | RocksDB + S3 backend |
| Exactly-once | Yes | Yes |
| Batch + stream unified | No | Yes |
| Spring/Java integration | Native | Good |

**Pravah's decision rules:**

Use **Kafka Streams** for:
- Simple filtering and transformation ("remove PII fields before forwarding")
- Simple aggregations with Kafka as both input and output
- Low-latency lookups and enrichment via stream-table joins
- Services already running in Spring Boot (no separate cluster needed)

Use **Flink** for:
- Complex event processing — fraud detection, pattern matching across event sequences
- Out-of-order event handling — mobile apps, IoT devices with unreliable connectivity
- Advanced windowing — session windows, CEP
- Large-scale stateful processing — millions of accounts with heavy state
- Streaming + batch unified pipelines — same job handles historical backfill and live stream
- SQL-based streaming: `SELECT * FROM orders GROUP BY customer_id, TUMBLE(event_time, INTERVAL '1' HOUR)`

## Pravah's Streaming Architecture

When a user creates a streaming pipeline in Pravah UI, Pravah translates it to the appropriate engine:

```
Simple pipeline (filter, enrich, count) → Kafka Streams (embedded in service)
Complex pipeline (CEP, session windows, out-of-order) → Flink job submission
```

**Pipeline complexity classifier:**

```
Uses CEP patterns?       → Flink
Session windows?         → Flink
Out-of-order events?     → Flink
Multiple complex joins?  → Flink
Everything else          → Kafka Streams (simpler ops)
```

**Flink checkpointing for crash recovery:**

Every 30 seconds, the Flink JobManager injects checkpoint barriers into the source streams. When an operator receives barriers from all inputs, it snapshots its state to MinIO. On failure, Flink restarts from the latest complete checkpoint — all operators restore state from MinIO and resume Kafka consumption from the offset recorded in that checkpoint.

Checkpoint storage:
```
s3://pravah-flink-state/{pipeline_id}/
  checkpoints/chk-1/, chk-2/, chk-3/   ← rolling window of checkpoints
  savepoints/sp-manual-2026-05-10/      ← manual pause points
```

**Late data strategy in Pravah:**

```
Zone 1 — On time:       Process in window normally
Zone 2 — Allowed late:  Update window result (up to 10 minutes after close)
Zone 3 — Very late:     Route to side output topic → investigate
```

Flink configuration:

```java
.allowedLateness(Time.minutes(10))
.sideOutputLateData(lateOutputTag)

DataStream<TransactionEvent> lateEvents = mainStream.getSideOutput(lateOutputTag);
lateEvents.sinkTo(lateDataKafkaSink);  // → pravah.streaming.late-data.{pipeline_id}
```

## System Design Interview Angles

**"What's the difference between Kafka Streams and Flink, and when does Pravah use each?"**

> The fundamental difference is deployment model. Kafka Streams is a library that runs inside your application — no separate cluster, state lives in local RocksDB backed by Kafka changelog topics. Flink is a separate distributed processing cluster — jobs are submitted to it, it manages parallelism, state backends, and checkpointing independently.
>
> Pravah uses Kafka Streams for simpler transformations embedded in existing Spring Boot services: filtering, enrichment via stream-table joins, simple windowed counts. Zero operational overhead. We use Flink when pipelines need advanced features: complex event pattern matching via CEP, session windows, out-of-order event handling with watermarks, or unified batch-and-stream processing. Flink's event time semantics correctly handle mobile app events arriving minutes late. The tradeoff: Flink requires a separate cluster with its own HA setup.

**"What is a watermark in Flink and why is it necessary?"**

> A watermark is Flink's mechanism for deciding when it is safe to close a time window despite events potentially arriving out of order. The problem is that event time and processing time differ — a mobile app order placed at 10:00 might reach Flink at 10:02 if the app was briefly offline. Without watermarks, Flink cannot know whether the 10:00–11:00 window is complete because more events with event_time before 11:00 might still be in transit.
>
> Watermarks solve this by asserting: "all events with timestamp < W have arrived." In Pravah we set a bounded-out-of-orderness watermark with 10 seconds: watermark = max_event_time_seen − 10 seconds. When the watermark passes a window's end time, Flink fires the window result. Events arriving after the watermark has passed their window are late — Pravah configures 10 minutes of allowed lateness so Flink updates the window result if the event arrives within 10 minutes of close. Beyond that, events are routed to a side output topic.

## Key Takeaways

1. **Kafka Streams:** library in your app; no separate cluster; native Kafka integration; good for filter, map, join, simple aggregation; state in RocksDB + Kafka changelog
2. **Flink:** separate distributed cluster; event time + watermarks; CEP; out-of-order handling; unified batch + stream; state in RocksDB + S3 checkpoints
3. **Watermarks:** signal that a time window is complete; W = max_event_time_seen − allowed_lateness; late events trigger window update OR side output
4. **Window types:** tumbling (hourly revenue), sliding (rolling 30-min average), session (user activity), global (count-based)
5. **Flink checkpointing = exactly-once:** every 30 seconds snapshot all operator state to MinIO; failure restarts from checkpoint + Kafka replay; Kafka sink uses 2PC aligned with checkpoints
6. **Pravah uses both:** Kafka Streams for simpler in-service processing; Flink for complex streaming jobs; complexity classifier decides
