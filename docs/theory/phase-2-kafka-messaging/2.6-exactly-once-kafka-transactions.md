2.6 Exactly-Once in Kafka: Transactions
🧩 Start With The Problem
THE CONSUME-TRANSFORM-PRODUCE PROBLEM
────────────────────────────────────────────────────────────

Most Pravah services follow this pattern:

  1. CONSUME:   Read event from Kafka topic A
  2. TRANSFORM: Process it (update DB, call service)
  3. PRODUCE:   Write result to Kafka topic B
  4. COMMIT:    Mark offset consumed in topic A

This is the most common microservice pattern.
And it has a fundamental correctness problem.

SCENARIO: Execution Service processing job.assigned
─────────────────────────────────────────────────────

  Consume:    job.assigned offset 1000 (pipe-abc job)
  Transform:  Create job record in PostgreSQL ✅
              Call Runner Service to allocate runner ✅
  Produce:    Publish job.dispatched to Kafka ✅
  Commit:     Mark offset 1001 as committed...
              💥 CRASH before commit!

  Restart:
  Consume:    job.assigned from offset 1000 (re-reads!)
  Transform:  Creates ANOTHER job record ← duplicate!
              Calls Runner Service AGAIN ← double allocation!
  Produce:    Publishes job.dispatched AGAIN ← duplicate!
  Commit:     offset 1001 ✅

WITHOUT EXACTLY-ONCE:
  Job runs twice. Runner double-allocated.
  Data warehouse loaded twice.
  Billing charged twice.
  ❌❌❌

WITHOUT KAFKA TRANSACTIONS — THREE PARTIAL FAILURES:
────────────────────────────────────────────────────────────

FAILURE A: Crash after produce, before commit offset
  → Re-reads → re-processes → duplicate ❌

FAILURE B: Produce succeeds but commit fails
  → Same as A ❌

FAILURE C: Produce fails but commit succeeds
  → Event lost — never processed downstream ❌

All three happen in real production systems.
Kafka transactions solve ALL THREE atomically.
🏦 The Solution: Kafka Transactions
KAFKA TRANSACTION GUARANTEE
────────────────────────────────────────────────────────────

Kafka transactions make this atomic:

  BEGIN TRANSACTION
    Consume from topic A (read offset 1000)
    Produce to topic B   (write job.dispatched)
    Commit offset 1000   (mark consumed)
  COMMIT

  Either ALL THREE happen, or NONE happen.
  No partial state. No duplicates. No losses.

KEY INSIGHT:
  Kafka transactions are different from DB transactions.
  
  DB transaction: locks rows, rollback on failure.
  Kafka transaction: marks messages as "pending"
                     visible only after COMMIT.
                     Uncommitted = invisible to consumers.
🔧 Transaction Internals — Step by Step
KAFKA TRANSACTION COMPONENTS
────────────────────────────────────────────────────────────

Transaction Coordinator:
  Special role on one broker per transaction.
  Tracks transaction state.
  Assigned by: hash(transactional.id) % num_partitions
               of __transaction_state internal topic.

Transactional ID:
  Stable identity for a producer across restarts.
  "pravah-execution-service-instance-1"
  
  Producer restarts → same transactional ID →
  coordinator knows this producer's history.

Transaction Log:
  __transaction_state internal topic (50 partitions).
  Stores: {transactional_id → current transaction state}
  Replicated like any Kafka topic.
Complete transaction flow:

KAFKA TRANSACTION — FULL SEQUENCE
────────────────────────────────────────────────────────────

INITIALIZATION (once per producer lifetime):
─────────────────────────────────────────────

Producer config:
  transactional.id = "pravah-execution-svc-1"
  enable.idempotence = true  (required for transactions)

Producer → Transaction Coordinator:
  InitProducerId(transactional.id="pravah-execution-svc-1")

Coordinator:
  Checks: any open transaction for this ID?
  If yes: abort it (previous crash cleanup)
  Assigns: PID=42, Epoch=3
  (Epoch increments each time producer initializes
   → fences zombie producers from previous epoch)

Coordinator → Producer: {PID=42, Epoch=3}

TRANSACTION EXECUTION:
───────────────────────

Step 1: BEGIN TRANSACTION
  producer.beginTransaction()
  (local state only — no network call yet)
  Producer state: {txn_id: "pravah-exec-1", status: BEGUN}

Step 2: CONSUME from job.assigned (offset 1000)
  Normal Kafka consumer poll.
  (consumption not part of transaction yet)

Step 3: TRANSFORM
  Process record. Call services. Update DB.
  (outside Kafka transaction scope)

Step 4: PRODUCE to job.dispatched
  producer.send(ProducerRecord("job.dispatched", ...))

  4a. Producer → Transaction Coordinator:
      AddPartitionsToTxn("job.dispatched", partition 7)
      
  4b. Coordinator:
      Records: {txn "pravah-exec-1" → writing to job.dispatched-7}
      Status: ONGOING
      
  4c. Producer → Broker (job.dispatched-7 leader):
      Sends batch tagged: {PID=42, Epoch=3, Seq=0, txn=true}
      
  4d. Broker:
      Writes message to log BUT marks as UNCOMMITTED
      (invisible to read_committed consumers)
      
  4e. Broker → Producer: ACK ✅

Step 5: COMMIT OFFSET (include in transaction!)
  consumer.commitSync(offsets, groupId)
  
  → This is KEY: offset commit is PART of transaction
  
  5a. Producer → Transaction Coordinator:
      AddOffsetsToTxn(group="execution-service-group",
                      offsets={job.assigned-7: 1001})
      
  5b. Coordinator:
      Records: {txn also commits offset 1001}
      
  5c. Producer → __consumer_offsets broker:
      TxnOffsetCommit({job.assigned-7: 1001})
      Offset written but UNCOMMITTED (part of txn)

Step 6: COMMIT TRANSACTION
  producer.commitTransaction()
  
  6a. Producer → Transaction Coordinator:
      EndTransaction(COMMIT)
      
  6b. Coordinator:
      Writes PREPARE_COMMIT to __transaction_state
      (durable — survives coordinator crash)
      
  6c. Coordinator → Broker (job.dispatched-7):
      WriteTxnMarker(COMMIT, PID=42, Epoch=3)
      
  6d. Broker (job.dispatched-7):
      Appends COMMIT MARKER to log
      Messages now VISIBLE to read_committed consumers ✅
      
  6e. Coordinator → __consumer_offsets broker:
      WriteTxnMarker(COMMIT for offset 1001)
      
  6f. __consumer_offsets broker:
      Offset 1001 now COMMITTED ✅
      
  6g. Coordinator:
      Writes COMPLETE to __transaction_state
      
  6h. Coordinator → Producer: Transaction committed ✅

💥 Failure Scenarios — All Handled
FAILURE 1: Producer crashes after produce, before commit
────────────────────────────────────────────────────────────

  ...Step 4: message written (uncommitted) to broker
  💥 Producer crashes

  State:
    Broker: has uncommitted message in log
    Coordinator: has ONGOING transaction for PID=42,Ep=3

  Producer restarts:
    Sends InitProducerId("pravah-execution-svc-1")
    
  Coordinator:
    Sees: open ONGOING transaction for this txn_id
    Epoch: 3 → 4 (fences old producer)
    Aborts old transaction:
      Sends WriteTxnMarker(ABORT) to broker
      Broker: marks uncommitted messages as aborted
              (consumers never see them)
    Assigns new PID with Epoch=4

  Producer resumes from offset 1000 (never committed)
  Re-processes cleanly ✅
  Old uncommitted message: aborted, invisible ✅
  NO DUPLICATE ✅

FAILURE 2: Transaction Coordinator crashes mid-commit
────────────────────────────────────────────────────────────

  ...Step 6b: Coordinator writes PREPARE_COMMIT to log
  💥 Coordinator crashes

  New coordinator takes over (Raft election):
    Reads __transaction_state
    Sees: txn "pravah-exec-1" in PREPARE_COMMIT state
    
    PREPARE_COMMIT = coordinator committed to committing.
    New coordinator MUST complete the commit.
    
    Sends WriteTxnMarker(COMMIT) to all affected brokers
    Transaction completes ✅
  
  This is two-phase commit within Kafka itself!
  But it's safe because:
    Coordinator logs PREPARE_COMMIT durably first
    New coordinator can always complete it
    Never leaves partial state ✅

FAILURE 3: Broker crashes with uncommitted messages
────────────────────────────────────────────────────────────

  Broker has uncommitted messages from transaction.
  Broker crashes. New leader elected from ISR.
  New leader has same messages (replicated).
  
  Transaction Coordinator sends WriteTxnMarker
  to new leader → same result ✅
  
  (This is why replication + transactions work together)

FAILURE 4: Zombie producer with old epoch
────────────────────────────────────────────────────────────

  Producer-1 (Epoch=3) crashes.
  Producer-2 starts (Epoch=4) — takes over.
  Producer-1 revives (GC pause ended).
  
  Producer-1 (Epoch=3) tries to continue transaction:
    Sends AddPartitionsToTxn with Epoch=3
    
  Coordinator: "Current epoch is 4, not 3!"
               "You are a zombie! REJECTED!" ❌
  
  Producer-1 gets FencedException → stops. ✅
  Producer-2 (Epoch=4) continues safely. ✅
👁️ Consumer Side: read_committed
HOW CONSUMERS SEE TRANSACTIONAL MESSAGES
────────────────────────────────────────────────────────────

TWO ISOLATION LEVELS:

isolation.level = read_uncommitted (default):
  Consumer sees ALL messages immediately.
  Including uncommitted transactional messages.
  Risk: Consumer processes message that gets ABORTED!
  Use for: Non-transactional consumers, metrics.

isolation.level = read_committed:
  Consumer only sees:
    1. Committed transactional messages
    2. Non-transactional messages
    3. Transaction ABORT markers (skips those records)
  
  Never sees uncommitted or aborted messages.
  Use for: All Pravah critical consumers. ✅

VISUAL — WHAT CONSUMER SEES:
────────────────────────────────────────────────────────────

Partition log (job.dispatched):
  offset 0: [non-txn message] ← always visible
  offset 1: [txn msg, PID=42, UNCOMMITTED]
  offset 2: [non-txn message] ← always visible
  offset 3: [COMMIT marker for PID=42]
  offset 4: [txn msg, PID=43, UNCOMMITTED]
  offset 5: [ABORT marker for PID=43]
  offset 6: [non-txn message]

read_uncommitted consumer sees:
  offset 0 ✅, offset 1 ✅, offset 2 ✅,
  offset 3 (marker), offset 4 ✅, offset 5 (marker),
  offset 6 ✅

read_committed consumer sees:
  offset 0 ✅, offset 2 ✅, offset 1 ✅ (after commit),
  offset 6 ✅
  (offset 4 NEVER seen — aborted transaction)
  
  NOTE: read_committed waits at offset 1 until
  commit/abort marker arrives before proceeding.
  This causes "Last Stable Offset" (LSO) concept.

LAST STABLE OFFSET (LSO):
────────────────────────────────────────────────────────────

read_committed consumers can only read up to LSO.
LSO = lowest offset of any open transaction.

  Open transaction at offset 1:
    Consumer blocked at offset 0.
    Cannot read offset 2 yet.
    (It might be in same transaction!)

  After commit marker at offset 3:
    LSO advances past offset 3.
    Consumer can read 0, 1, 2.

  IMPLICATION FOR PRAVAH:
    Long-running transactions increase LSO lag.
    Other consumers blocked behind open transaction.
    Keep transactions SHORT. ✅
    Pravah: max transaction duration = 30 seconds.
    transaction.timeout.ms = 30000
⚖️ Kafka Transactions vs Application-Level Idempotency
WHEN TO USE WHICH IN PRAVAH
────────────────────────────────────────────────────────────

KAFKA TRANSACTIONS:
  Use when: consume → produce pipeline in Kafka only.
            No external systems involved.
            Pure Kafka stream processing.

  Pravah examples:
    ✅ Execution Service: job.assigned → job.dispatched
       (consume job, produce dispatch event, commit offset)
    
    ✅ Lineage Service: pipeline.events → lineage.events
       (consume pipeline event, produce lineage event)
    
    ✅ Notification Service: pipeline.events → notifications.outbound
       (consume event, produce notification)

APPLICATION-LEVEL IDEMPOTENCY (Outbox + Dedup):
  Use when: External systems involved (DB, REST APIs).
            Cannot include in Kafka transaction.

  Pravah examples:
    ✅ Saga Orchestrator: consumes event, calls Runner Service REST API
       (REST call can't be in Kafka transaction)
       → Use outbox pattern for DB atomicity
       → Use idempotency keys for REST dedup
    
    ✅ Data destination loading: consumes event, loads to DWH
       (DWH write can't be in Kafka transaction)
       → Use staging table + idempotency in DWH

HYBRID APPROACH (Pravah's typical pattern):
────────────────────────────────────────────────────────────

  1. Consume from Kafka (read_committed)
  
  2. Process with external systems:
     - Write to PostgreSQL (outbox pattern)
     - Call external APIs (idempotency keys)
  
  3. Kafka transaction for Kafka-only part:
     - Produce result event to output topic
     - Commit input offset
     (atomic within Kafka even if DB step is separate)
  
  This gives:
    External system: idempotency (application level)
    Kafka routing: exactly-once (transaction level)
    Combined: end-to-end exactly-once ✅

TRANSACTION PRODUCER CONFIG
────────────────────────────────────────────────────────────

# Required for transactions
transactional.id     = pravah-{service}-{instance-id}
enable.idempotence   = true   (mandatory with transactions)
acks                 = all    (mandatory with transactions)

# Transaction timeout
transaction.timeout.ms = 30000  (30 seconds max)
  → If transaction not committed in 30s → auto-abort
  → Prevents LSO from blocking forever
  → Pravah: all transactions complete in < 5 seconds

# Retries (infinite — outer timeout controls duration)
retries              = Integer.MAX_VALUE
delivery.timeout.ms  = 120000

# Isolation for consumers
isolation.level      = read_committed

TRANSACTIONAL ID DESIGN:
────────────────────────────────────────────────────────────

Must be UNIQUE per producer instance.
Must be STABLE across restarts (same instance → same ID).

Pravah pattern:
  pravah-execution-svc-{pod-name}

  pod-name from K8s: pravah-execution-svc-7d9f8b-xk2p4
  
  Transactional ID: pravah-execution-svc-pravah-execution-svc-7d9f8b-xk2p4

  Same pod restarts → same pod name → same txn ID
  Coordinator recognizes it → fences old epoch → safe ✅

  Pod replaced (new pod name):
    New transactional ID → fresh producer state ✅

CONSUMER CONFIG (transactional):
  isolation.level          = read_committed
  enable.auto.commit       = false  (manual commit in txn)
  max.poll.interval.ms     = 300000 (must commit in 5 min)

BROKER CONFIG:
  transaction.state.log.replication.factor = 3
  transaction.state.log.min.isr            = 2
  (transaction log must be durable — replicated)
📊 Performance Impact of Transactions
TRANSACTION OVERHEAD
────────────────────────────────────────────────────────────

Additional network calls per transaction:
  InitProducerId:        1 call (once per lifetime)
  AddPartitionsToTxn:    1 call per unique topic/partition
  AddOffsetsToTxn:       1 call per consumer group
  EndTransaction:        1 call (commit or abort)
  WriteTxnMarkers:       1 call per affected broker

  Typical overhead: 3-5 additional network calls
  Extra latency: 5-15ms per transaction

THROUGHPUT IMPACT:
  Non-transactional: 1M+ messages/sec
  Transactional: 200K-400K messages/sec

  Why lower?
    Transaction coordinator is bottleneck
    LSO can slow down consumers
    Additional log writes for markers

MITIGATION IN PRAVAH:
  Batch multiple records per transaction:
    NOT: one transaction per message (overhead × N)
    YES: one transaction per poll() batch

  consumer.poll() → get 500 records
  Process all 500
  ONE transaction:
    produce 500 result records
    commit offset for batch
  
  Amortizes overhead across 500 records ✅
  Throughput impact: minimal per-record ✅

WHEN TO AVOID TRANSACTIONS:
  High-throughput topics where exactly-once
  can be achieved via application idempotency:
    runner.heartbeat → no transactions (too fast)
    pipeline statistics → no transactions (best-effort)
    notifications.outbound → idempotent delivery ok

🎯 FAANG Interview Angles
❓ "Explain how Kafka achieves exactly-once
    semantics in Pravah's consume-produce pipeline"

Good answer:
  "Kafka exactly-once combines three mechanisms.

   First, idempotent producer: PID + sequence numbers
   mean the broker deduplicates retried messages.
   Producer restarts get new epochs that fence
   zombie producers.

   Second, transactions: the consume, produce, and
   offset commit are wrapped atomically. Messages
   are written to brokers but marked uncommitted
   until the transaction coordinator writes the
   commit marker. Consumers with isolation.level=
   read_committed never see uncommitted messages.

   Third, the transaction coordinator persists
   PREPARE_COMMIT durably before finalizing.
   If the coordinator crashes mid-commit, the
   new coordinator reads this state and completes
   the commit — no partial transactions possible.

   In Pravah's Execution Service: consuming
   job.assigned at offset 1000, producing
   job.dispatched, and committing offset 1001
   are all atomic. Either all happen or none —
   no duplicate job dispatch, no lost jobs."

❓ "What is the Last Stable Offset and why
    does it matter for Pravah?"

Good answer:
  "The Last Stable Offset is the lowest offset
   of any open transaction in a partition.
   read_committed consumers can only read up to
   the LSO — they must wait for open transactions
   to commit or abort before reading past them.

   This matters because long-running transactions
   block ALL consumers on that partition, even for
   messages not part of the transaction.

   In Pravah we set transaction.timeout.ms=30000
   — transactions abort automatically after 30
   seconds. We also batch records per transaction
   rather than one transaction per message, so
   transactions complete quickly (typically < 1
   second per batch of 500 records).

   If a transaction gets stuck, the 30-second
   auto-abort prevents LSO from blocking
   downstream consumers indefinitely."

❓ "When would you NOT use Kafka transactions
    in Pravah and what would you use instead?"

Good answer:
  "Whenever the operation involves external systems
   that can't participate in a Kafka transaction.

   The Agent Service calls our LLM API — that HTTP
   call can't be inside a Kafka transaction. Instead
   we use application-level idempotency: each LLM
   call has a unique idempotency key, the response
   is cached in Redis, retries return the cached
   response rather than calling LLM again.

   The Runner Service dispatches jobs via gRPC to
   runners — again, external to Kafka. We use the
   outbox pattern: write to DB and outbox table
   atomically, relay publishes to Kafka with
   idempotent producer.

   Rule: Kafka transactions for pure Kafka pipelines.
   Application idempotency + outbox for anything
   touching external systems. Together they give
   end-to-end exactly-once across the full stack."
📌 Key Takeaways
1. Consume-transform-produce has three failure modes:
   crash after produce, commit fails, produce fails
   Kafka transactions solve ALL THREE atomically

2. Three components work together:
   Idempotent producer (PID + sequence + epochs)
   Transaction coordinator (durably logs state)
   read_committed consumers (see only committed)

3. Transaction sequence:
   InitProducerId → beginTxn → AddPartitions →
   produce → AddOffsets → commitOffset →
   EndTxn(COMMIT) → WriteTxnMarkers

4. PREPARE_COMMIT durably written before finalizing
   New coordinator completes interrupted commits
   Epoch fencing prevents zombie producers

5. LSO (Last Stable Offset):
   read_committed consumers blocked at open transactions
   Keep transactions short (Pravah: 30s max timeout)
   Batch records per transaction (not one per record)

6. Kafka txn vs application idempotency:
   Pure Kafka pipeline → Kafka transactions
   External systems involved → outbox + idempotency
   Pravah uses both depending on service

7. Performance impact: ~3-5 extra network calls
   Mitigate: batch 500 records per transaction
   Don't use for high-frequency low-value topics

8. Transactional ID must be unique + stable
   K8s pod name works perfectly for Pravah
