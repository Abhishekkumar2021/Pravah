# 2.6 Exactly-Once in Kafka — Transactions

## The Consume-Transform-Produce Problem

Most Pravah services follow this pattern: consume an event from topic A, process it, produce a result to topic B, then commit the offset. This is the most common microservice pattern, and it has a fundamental correctness problem.

**What can go wrong (Execution Service processing `job.assigned`):**

```
Consume:    job.assigned offset 1000 (pipe-abc job)
Transform:  Create job record in PostgreSQL ✅
            Allocate runner via Runner Service ✅
Produce:    Publish job.dispatched to Kafka ✅
Commit:     Mark offset 1001... 💥 CRASH before commit

Restart:
Consume:    job.assigned from offset 1000 (re-read!)
Transform:  Creates ANOTHER job record ← duplicate
            Allocates runner AGAIN ← double allocation
Produce:    Publishes job.dispatched AGAIN ← duplicate
```

Three distinct failure modes:
- Crash after produce, before commit → duplicate
- Produce succeeds but commit fails → same as above
- Produce fails but commit succeeds → event lost

All three happen in real production systems. Kafka transactions solve all three atomically.

---

## Kafka Transaction Guarantee

```sql
BEGIN KAFKA TRANSACTION
  Consume from topic A      (read offset 1000)
  Produce to topic B        (write job.dispatched)
  Commit offset 1000        (mark consumed)
COMMIT KAFKA TRANSACTION
```

Either all three happen, or none happen. No partial state, no duplicates, no losses.

**Key difference from database transactions:** Kafka transactions do not lock rows or enable rollback. Instead, messages produced within a transaction are written to the log but marked as UNCOMMITTED — invisible to consumers with `isolation.level=read_committed` until the transaction commits.

---

## Transaction Internals

**Transaction Coordinator** — a specific broker, assigned by `hash(transactional.id) % num_partitions_of___transaction_state`. Tracks transaction state in the `__transaction_state` internal topic.

**Transactional ID** — stable identity for a producer across restarts: `"pravah-execution-service-instance-1"`. When the producer reinitializes, the coordinator aborts any open transaction from a previous crashed instance.

**Producer Epoch** — incremented each time a producer initializes with the same transactional ID. Fences zombie producers — a broker rejects writes from an old epoch.

**Complete transaction flow:**

```
INITIALIZATION (once per producer lifetime):

producer.initTransactions()
  Producer → Coordinator: InitProducerId("pravah-execution-svc-1")
  Coordinator: assigns PID=42, Epoch=3
               (aborts any prior open transaction for this ID)
  Producer receives: {PID=42, Epoch=3}

TRANSACTION EXECUTION:

Step 1: producer.beginTransaction()
        Local state only, no network call.

Step 2: consumer.poll(...)
        Normal consumption. Not yet part of transaction.

Step 3: Transform — process record, update DB, call services.

Step 4: producer.send(ProducerRecord("job.dispatched", ...))
        Producer → Coordinator: AddPartitionsToTxn("job.dispatched", partition 7)
        Coordinator records: this transaction writes to job.dispatched-7. Status: ONGOING.
        Producer → Broker: batch tagged {PID=42, Epoch=3, Seq=0, txn=true}
        Broker: appends to log, marked UNCOMMITTED (invisible to read_committed consumers)
        Broker → Producer: ACK ✅

Step 5: Include offset commit IN the transaction:
        producer.sendOffsetsToTransaction(offsets, groupMetadata)
        Producer → Coordinator: AddOffsetsToTxn(group="exec-svc-group", offset=1001)
        Producer → __consumer_offsets broker: TxnOffsetCommit({job.assigned-7: 1001})
        Offset written but UNCOMMITTED (part of transaction)

Step 6: producer.commitTransaction()
        Producer → Coordinator: EndTransaction(COMMIT)
        Coordinator: writes PREPARE_COMMIT to __transaction_state (durable)
        Coordinator → Broker (job.dispatched-7): WriteTxnMarker(COMMIT)
        Broker: appends COMMIT MARKER → messages now VISIBLE to read_committed ✅
        Coordinator → __consumer_offsets broker: WriteTxnMarker(COMMIT for offset 1001)
        Offset 1001 now committed ✅
        Coordinator: writes COMPLETE to __transaction_state
```

**What happens on crash during commit:**

The `PREPARE_COMMIT` record is written durably before any commit markers are sent. If the coordinator crashes after writing `PREPARE_COMMIT`, the next coordinator picks up and finishes sending commit markers. The transaction completes — no data loss, no duplicate.

---

## Consumer Side — `isolation.level=read_committed`

```properties
isolation.level=read_committed
```

With this setting, consumers only see messages from **committed** transactions. Uncommitted messages are buffered on the consumer side and delivered after their transaction commits.

```
Timeline of what a consumer sees:

t=0   Batch produced (UNCOMMITTED) → consumer skips
t=1   More messages from other producers → consumer reads these ✅
t=5   Transaction commits → commit marker appears in log
t=6   Consumer reads buffered batch → delivers to application ✅
```

`read_uncommitted` (the default) sees all messages including those in open or aborted transactions — acceptable for non-critical consumers like metrics collectors.

## Kafka Transactions in Java

```java
// Producer setup
Properties props = new Properties();
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "pravah-execution-svc-" + instanceId);
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true"); // required
props.put(ProducerConfig.ACKS_CONFIG, "all");                // required

KafkaProducer<String, byte[]> producer = new KafkaProducer<>(props);
producer.initTransactions();

// Consumer setup
props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
KafkaConsumer<String, byte[]> consumer = new KafkaConsumer<>(props);

// Processing loop
while (running) {
    ConsumerRecords<String, byte[]> records = consumer.poll(Duration.ofMillis(100));

    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, byte[]> record : records) {
            // Transform
            JobDispatch dispatch = process(record);

            // Produce result
            producer.send(new ProducerRecord<>("job.dispatched",
                dispatch.getJobId(), serialize(dispatch)));
        }

        // Commit offset as part of the same transaction
        producer.sendOffsetsToTransaction(
            currentOffsets(records),
            consumer.groupMetadata()
        );

        producer.commitTransaction(); // all or nothing ✅

    } catch (Exception e) {
        producer.abortTransaction();  // roll back produced messages
        // offsets not committed → will re-read and retry
    }
}
```

## Where Pravah Uses Kafka Transactions

Not everywhere. Kafka transactions have overhead (coordinator round trips, transaction markers in the log). Use them only where the exactly-once guarantee is required.

| Scenario | Uses Kafka Transactions? | Reasoning |
|---|---|---|
| Execution Service: `job.assigned` → `job.dispatched` | ✅ Yes | Duplicate dispatch = double execution, data corruption |
| Pipeline Service outbox → `pipeline.events` | ❌ No | Outbox pattern + idempotent producer is sufficient |
| Lineage Service: events → lineage graph | ❌ No | Idempotent upsert at destination; duplicate lineage entries are harmless and deduped |
| Agent Service: observations → suggestions | ❌ No | Suggestions are idempotent; duplicates filtered by ID |
| Notification Service: events → alerts | ❌ No | At-least-once with dedup store; slightly duplicate alerts acceptable |
| Billing Service: compute usage metering | ✅ Yes | Duplicate billing event = overcharge |

## Idempotent Producer vs Transactions — Comparison

| Mechanism | What It Solves | Overhead | Pravah Uses For |
|---|---|---|---|
| **Idempotent producer** | Duplicate messages from producer retries (producer → broker) | Very low (sequence numbers) | All producers; prevents duplicate writes |
| **Kafka transactions** | Atomic consume-transform-produce; prevents both duplicate and lost processing | Medium (coordinator round trips) | Job dispatch, billing metering |
| **Application-level idempotency** | Duplicate processing at the application layer | Low (DB lookup) | All consumers; catch-all safety net |

These layers compose: idempotent producer handles network-level duplicates, Kafka transactions handle crash-recovery duplicates at the broker level, application-level idempotency handles any remaining duplicates at the processing level.

## System Design Interview Angles

**"How does Pravah achieve exactly-once job execution end-to-end?"**

> Multiple coordinated layers. At the Kafka level, Execution Service uses Kafka transactions: consuming from `job.assigned`, producing to `job.dispatched`, and committing the offset are all one atomic operation — either all happen or none happen. At the application level, every job has an idempotency key (`pipeline_id + scheduled_time + attempt_number`). The runner checks this key in local SQLite before executing — duplicate delivery is a no-op. At the data destination level, we use staging tables and UPSERT — retried loads produce identical results.

**"What is the transaction coordinator and what happens if it crashes?"**

> The transaction coordinator is a specific broker assigned by hashing the transactional ID. It tracks transaction state in the `__transaction_state` internal topic. When a transaction is committed, the coordinator first durably writes `PREPARE_COMMIT` to `__transaction_state`. If the coordinator crashes after this point, the next elected coordinator reads the `PREPARE_COMMIT` record and finishes sending commit markers to all involved brokers. The transaction completes — no data is lost and no duplicate occurs. The `PREPARE_COMMIT` is the crash-recovery anchor.

**"Why not use Kafka transactions for all Pravah services?"**

> Kafka transactions add overhead: an extra network round trip to the coordinator for `AddPartitionsToTxn` and `EndTransaction`, plus transaction markers written to the log. For most services, application-level idempotency (idempotency key + dedup store) achieves the same safety with lower overhead and simpler code. We use Kafka transactions only where a crash between producing and committing the offset would cause severe consequences — duplicate job execution or duplicate billing. For notifications or lineage events, a duplicate is harmless and caught by application-level dedup.

## 📌 Key Takeaways

1. Consume-transform-produce has three failure modes: crash before commit → duplicate; produce fails, commit succeeds → lost; these cannot be solved without atomic semantics
2. Kafka transactions make consume + produce + offset commit a single atomic operation
3. Messages in an open transaction are UNCOMMITTED — invisible to `read_committed` consumers until the transaction commits
4. Transaction coordinator durably writes `PREPARE_COMMIT` before sending commit markers — crash-safe at the coordinator level
5. Idempotent producer handles producer-broker duplicate; Kafka transactions handle broker-consumer duplicate; application idempotency is the final safety net
6. Use Kafka transactions only where duplicates cause severe harm — they add overhead; application-level idempotency is sufficient for most consumers
