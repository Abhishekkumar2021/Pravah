2.8 Dead Letter Queues & Poison Pill Handling
🧩 Start With The Problem
THE POISON PILL SCENARIO
────────────────────────────────────────────────────────────

Pravah's Execution Service consuming job.assigned:

  Partition 7 messages:
  [offset 1000: pipe-abc job] ← processes fine ✅
  [offset 1001: pipe-def job] ← processes fine ✅
  [offset 1002: CORRUPTED   ] ← 💀 POISON PILL
  [offset 1003: pipe-ghi job] ← waiting...
  [offset 1004: pipe-jkl job] ← waiting...
  [offset 1005: pipe-mno job] ← waiting...
  ...
  [offset 1999: pipe-xyz job] ← 998 jobs waiting!

What happens without poison pill handling?

  Consumer reads offset 1002 → tries to deserialize
  → DeserializationException ❌
  
  Consumer: "I failed! I'll retry."
  Retry 1: reads offset 1002 → crash ❌
  Retry 2: reads offset 1002 → crash ❌
  Retry 3: reads offset 1002 → crash ❌
  ...
  
  Consumer STUCK at offset 1002 FOREVER.
  Offsets 1003-1999: NEVER PROCESSED.
  998 pipeline jobs: NEVER DISPATCHED.
  998 enterprise pipelines: MISSED SLA.
  
  One corrupted message → 998 jobs blocked.
  This is the poison pill problem.
🔍 Types of Unprocessable Messages
NOT ALL FAILURES ARE EQUAL
────────────────────────────────────────────────────────────

TYPE 1: DESERIALIZATION FAILURE
  Message bytes are corrupted or wrong format.
  Cannot even parse the message.
  
  Causes:
    Producer bug wrote wrong format
    Schema registry mismatch
    Message manually injected with wrong encoding
    Bit rot in storage (very rare)
  
  Retryable? NO.
    Same bytes = same failure forever.
    Will never succeed on retry.

TYPE 2: BUSINESS LOGIC FAILURE (Non-retryable)
  Message parsed fine. Processing fails.
  Error will always happen for this message.
  
  Causes:
    Pipeline ID doesn't exist (deleted after queuing)
    Tenant account suspended (will stay suspended)
    Invalid pipeline configuration (wrong from start)
    Data constraint violation
  
  Retryable? NO.
    Same message = same failure forever.

TYPE 3: TRANSIENT FAILURE (Retryable)
  Processing fails due to temporary condition.
  Will likely succeed if retried later.
  
  Causes:
    Runner Service temporarily down
    Database connection timeout
    Network blip to external service
    Rate limit hit (retry after backoff)
  
  Retryable? YES.
    Retry with backoff. Will eventually succeed.

TYPE 4: SLOW POISON (Partial processing)
  Message starts processing but takes too long.
  Blocks consumer for extended period.
  
  Causes:
    LLM call hangs indefinitely
    Deadlock in processing
    Infinite loop in transformation
  
  Retryable? DEPENDS.
    Need timeout + retry with circuit breaker.

🔄 Retry Strategy — Before DLQ
EXPONENTIAL BACKOFF WITH JITTER
────────────────────────────────────────────────────────────

Don't send to DLQ immediately on first failure.
Transient failures resolve quickly with backoff.

RETRY SCHEDULE FOR PRAVAH:
  Attempt 1: fails → wait 1 second
  Attempt 2: fails → wait 2 seconds
  Attempt 3: fails → wait 4 seconds
  Attempt 4: fails → wait 8 seconds
  Attempt 5: fails → SEND TO DLQ

  Total wait before DLQ: ~15 seconds
  Short enough: doesn't block partition too long
  Long enough: transient network issues resolve

JITTER — WHY IT'S ESSENTIAL:
  Without jitter: all retries at same time
    t=1s: 1000 messages retry simultaneously
    t=2s: 999 messages retry simultaneously
    → THUNDERING HERD on downstream service ❌

  With jitter: spread retries randomly
    retry_wait = base * 2^attempt * random(0.5, 1.5)
    t=0.8s: message A retries
    t=1.1s: message B retries
    t=0.9s: message C retries
    → Smooth load on downstream service ✅

WHAT ABOUT KAFKA CONSUMER PAUSING?
────────────────────────────────────────────────────────────

Problem: Kafka consumer must keep polling during retry.
         But we're retrying a specific message.
         How to retry without blocking the partition?

SOLUTION: PAUSE + IN-MEMORY RETRY QUEUE

  Consumer reads offset 1002 → fails
  
  1. Add {offset:1002, message, attempt:1} to retry queue
  2. PAUSE partition 7 (consumer.pause(partition7))
     (paused = no more messages from partition 7)
  3. Keep polling other partitions (8, 9, 10, 11)
     (other partitions continue normally!)
  
  After 1 second (backoff):
  4. RESUME partition 7 (consumer.resume(partition7))
  5. Read offset 1002 again → retry
  
  If succeeds: commit offset 1003, continue ✅
  If fails again: pause again, wait 2 seconds

VISUAL:
────────────────────────────────────────────────────────────

t=0:   Partition 7 offset 1002 → FAIL
       Pause partition 7 ⏸️
       Continue processing partitions 8,9,10,11 ✅

t=1s:  Resume partition 7 ▶️
       Retry offset 1002 → FAIL again
       Pause partition 7 ⏸️

t=3s:  Resume partition 7 ▶️
       Retry offset 1002 → FAIL again
       Pause partition 7 ⏸️

t=7s:  Resume partition 7 ▶️
       Retry offset 1002 → FAIL again
       Pause partition 7 ⏸️

t=15s: Resume partition 7 ▶️
       Retry offset 1002 → FAIL (attempt 5)
       SEND TO DLQ 💀
       Commit offset 1003 ✅
       Continue with offset 1003 ✅

TOTAL DELAY: 15 seconds for this partition
OTHER PARTITIONS: zero delay throughout ✅
🛠️ Implementation — Complete DLQ Handler
PRAVAH DLQ HANDLER (Java/Spring)
────────────────────────────────────────────────────────────

@Component
public class PravahDlqHandler {

  private final KafkaTemplate<String, byte[]> dlqProducer;
  private final MeterRegistry metrics;
  private final Map<TopicPartition, RetryState> retryStates
      = new ConcurrentHashMap<>();

  // Called when a message fails processing
  public RetryDecision handleFailure(
      ConsumerRecord<String, ?> record,
      Exception exception,
      Consumer<?,?> consumer) {

    TopicPartition tp = new TopicPartition(
        record.topic(), record.partition());

    RetryState state = retryStates.computeIfAbsent(
        tp, k -> new RetryState());

    // Classify the failure
    FailureType type = classify(exception);

    if (type == FailureType.NON_RETRYABLE
        || state.attempts >= MAX_ATTEMPTS) {

      // Send to DLQ
      sendToDlq(record, exception, state);

      // Commit this offset — move past poison pill
      commitOffset(consumer, record);

      // Clean up retry state
      retryStates.remove(tp);

      // Resume partition immediately
      consumer.resume(Collections.singleton(tp));

      metrics.counter("pravah.dlq.messages",
          "topic", record.topic(),
          "failure_type", type.name()).increment();

      return RetryDecision.SKIP;

    } else {
      // Schedule retry with backoff
      long backoffMs = calculateBackoff(state.attempts);
      state.attempts++;
      state.nextRetryAt = System.currentTimeMillis() + backoffMs;

      // Pause this partition during backoff
      consumer.pause(Collections.singleton(tp));

      // Schedule resume
      scheduler.schedule(
          () -> consumer.resume(Collections.singleton(tp)),
          backoffMs,
          TimeUnit.MILLISECONDS);

      metrics.counter("pravah.retry.scheduled",
          "topic", record.topic(),
          "attempt", String.valueOf(state.attempts)).increment();

      return RetryDecision.RETRY;
    }
  }

  private void sendToDlq(
      ConsumerRecord<String, ?> record,
      Exception exception,
      RetryState state) {

    String dlqTopic = record.topic() + ".dlq";

    // Build DLQ message with full context
    DlqMessage dlqMessage = DlqMessage.newBuilder()
        .setOriginalTopic(record.topic())
        .setOriginalPartition(record.partition())
        .setOriginalOffset(record.offset())
        .setOriginalKey(record.key())
        .setOriginalValue(toBytes(record.value()))
        .setFailureReason(exception.getClass().getSimpleName())
        .setFailureMessage(exception.getMessage())
        .setFailureType(classify(exception).name())
        .setFailedAt(Instant.now().toEpochMilli())
        .setAttemptCount(state.attempts)
        .setFirstFailedAt(state.firstFailedAt)
        .setCorrelationId(extractHeader(record, "correlation-id"))
        .setTenantId(extractHeader(record, "tenant-id"))
        .build();

    // Send to DLQ (not transactional — best effort)
    dlqProducer.send(
        dlqTopic,
        record.key(),
        dlqMessage.toByteArray()
    ).addCallback(
        result -> log.info("Sent to DLQ: {}", dlqTopic),
        ex -> log.error("Failed to send to DLQ!", ex)
        // If DLQ send fails → log + alert + continue
        // Never let DLQ failure block main processing
    );
  }

  private long calculateBackoff(int attempt) {
    // Exponential backoff with jitter
    long base = 1000L;  // 1 second base
    long exponential = base * (long) Math.pow(2, attempt);
    long cap = 30000L;  // max 30 seconds
    long capped = Math.min(exponential, cap);

    // Add jitter: ±50% random variation
    double jitter = 0.5 + random.nextDouble();
    return (long) (capped * jitter);
  }

  private FailureType classify(Exception exception) {
    if (exception instanceof SerializationException
        || exception instanceof InvalidProtocolBufferException) {
      return FailureType.NON_RETRYABLE;  // bad data
    }
    if (exception instanceof PipelineNotFoundException
        || exception instanceof TenantSuspendedException) {
      return FailureType.NON_RETRYABLE;  // business logic
    }
    if (exception instanceof ConnectException
        || exception instanceof TimeoutException) {
      return FailureType.RETRYABLE;      // transient
    }
    return FailureType.RETRYABLE;  // unknown = assume retryable
  }
}

🔄 DLQ Replay — How It Works
REPLAY MECHANISM
────────────────────────────────────────────────────────────

Operator clicks "Replay" for DLQ message:

SIMPLE REPLAY (re-process as-is):
  1. Read original message bytes from DLQ topic
  2. Publish to original topic (job.assigned)
     with same key, same payload
     NEW header: x-pravah-replay: true
                 x-pravah-replay-count: 1
                 x-pravah-original-dlq-offset: 42
  3. Consumer picks up replayed message
  4. Processes normally (idempotency key deduplicates
     if already partially processed)

MODIFIED REPLAY (fix and replay):
  1. Operator edits payload in DLQ UI
     (fix the schema mismatch, correct the data)
  2. UI sends PATCH /dlq/{dlq-offset}/replay
     with modified payload
  3. Backend publishes modified message to original topic
  4. Consumer processes corrected message ✅

REPLAY SAFETY:
  All replayed messages tagged: x-pravah-replay: true
  Idempotency key preserved from original message
  If original was partially processed:
    → Idempotency check at consumer deduplicates ✅
  Double-replay protection:
    → DLQ tracks replay status per message
    → Cannot replay same DLQ message twice
       without explicit override

🔀 Handling Deserialization Failures Specially
THE DESERIALIZATION PROBLEM
────────────────────────────────────────────────────────────

Special challenge: If the VALUE can't be deserialized,
the consumer throws exception BEFORE your code runs.
The standard error handler never even sees the message content.

Kafka's ErrorHandlingDeserializer solves this:

SPRING KAFKA DESERIALIZATION ERROR HANDLING:
────────────────────────────────────────────────────────────

config.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
           ErrorHandlingDeserializer.class);

config.put(ErrorHandlingDeserializer.VALUE_DESERIALIZER_CLASS,
           KafkaProtobufDeserializer.class.getName());

How ErrorHandlingDeserializer works:

  Normal: KafkaProtobufDeserializer succeeds
    → Returns PipelineEvent object ✅
    → Consumer processes normally ✅

  Failure: KafkaProtobufDeserializer throws exception
    → ErrorHandlingDeserializer CATCHES it
    → Wraps raw bytes in DeserializationException
    → Returns ErrorHandlingDeserializer.Result object
    → Consumer receives Result (not null, not crash)
    → Consumer checks: is this a deserialization error?
    → YES → route to DLQ immediately (non-retryable)
    → Commit offset, continue with next message ✅

  KEY BENEFIT:
    Consumer code never crashes.
    Partition never blocked.
    Bad message isolated immediately.
    Raw bytes preserved in DLQ for investigation.

@KafkaListener(topics = "job.assigned")
public void handleJobAssigned(
    ConsumerRecord<String, Object> record) {

  // Check for deserialization failure
  if (record.value() instanceof DeserializationException ex) {
    dlqHandler.sendToDlqImmediately(record, ex);
    return;  // Don't commit — let error handler do it
  }

  // Normal processing
  JobAssigned job = (JobAssigned) record.value();
  processJob(job);
}

🎯 FAANG Interview Angles
❓ "How does Pravah prevent one bad Kafka message
    from blocking thousands of good ones?"

Good answer:
  "We use a partition pause strategy combined with
   exponential backoff and DLQ routing.

   When a message fails, we classify it immediately.
   Non-retryable failures (deserialization errors,
   business logic failures like 'pipeline not found')
   go straight to the DLQ — we commit the offset and
   continue processing the next message. Zero blocking.

   Retryable failures (transient network issues) trigger
   partition pausing: we pause only that specific
   partition during the backoff window (1s, 2s, 4s, 8s)
   while other partitions continue processing normally.
   After max retries, non-resolved messages go to DLQ.

   The DLQ itself is a Kafka topic — durable, replayable,
   queryable. Operators see failed messages in our UI
   with full context, Agent analysis, and one-click
   replay after fixing the root cause."

❓ "What is the ErrorHandlingDeserializer and
    why does Pravah need it?"

Good answer:
  "The challenge with deserialization failures is they
   happen before your consumer code even runs — the
   Kafka deserializer throws an exception and the
   consumer crashes or loops forever.

   ErrorHandlingDeserializer wraps the actual deserializer.
   If deserialization fails, instead of throwing, it
   catches the exception and returns a wrapper object
   containing the raw bytes and the exception. The
   consumer receives this wrapper, checks for it
   explicitly, and routes to DLQ immediately.

   This is critical because without it, a single
   corrupted message format crashes the consumer
   repeatedly — the partition gets stuck because
   the consumer can't commit the offset and move on.
   With ErrorHandlingDeserializer, Pravah handles
   corrupted bytes gracefully, preserves the raw
   bytes in DLQ for investigation, and continues
   processing the remaining messages in the partition."

❓ "How does Pravah's Agent Service help with
    DLQ resolution?"

Good answer:
  "When a message lands in the DLQ, we publish a
   DLQ event to the agent.observations topic. The
   Agent Service consumes this and performs automated
   root cause analysis.

   For example, if the failure is 'Unknown field
   task_priority', the agent queries the Schema Registry
   to find what changed between versions, checks
   deployment logs to find which service was recently
   updated, and correlates: 'Pipeline Service deployed
   schema v3 at 09:45, but Execution Service is still
   on v2 — that's the mismatch.'

   The agent posts a structured RCA to Slack with
   the exact fix needed and marks affected DLQ messages
   as auto_replayable — once it detects the consumer
   has updated to v3, it can automatically trigger
   replay without operator intervention. This reduces
   MTTR from hours to minutes for common failure
   patterns."
📌 Key Takeaways
1. Poison pill = one bad message blocks entire partition
   Core risk: consumer stuck forever, 1000s jobs delayed

2. Three failure types need different handling:
   Deserialization: non-retryable → DLQ immediately
   Business logic:  non-retryable → DLQ immediately
   Transient:       retryable → backoff → DLQ if exhausted

3. Partition pause strategy:
   Pause only the affected partition during backoff
   Other partitions continue processing unaffected
   Resume after backoff, retry, DLQ if max attempts

4. ErrorHandlingDeserializer:
   Catches deserialization exceptions before consumer
   Returns wrapper object with raw bytes preserved
   Consumer checks for wrapper → routes to DLQ
   Partition never blocked by corrupted bytes

5. DLQ message structure:
   Original bytes (preserved exactly)
   Full failure context (type, message, stack trace)
   Retry history (attempts, timestamps, backoffs)
   Correlation IDs for tracing

6. DLQ replay:
   Simple: replay as-is to original topic
   Modified: operator edits payload, then replays
   Bulk: replay N messages with rate limiting
   Safety: idempotency keys prevent double processing

7. Agent + DLQ = automated RCA:
   Schema mismatches → detected automatically
   Deployment correlation → root cause in seconds
   Auto-replay after fix → MTTR minutes not hours

8. Monitor DLQ continuously:
   ANY message in critical topic DLQ → alert
   DLQ growth rate → systemic problem indicator
   Replay success rate → is fix effective?
