# 2.8 Dead Letter Queues & Poison Pill Handling

## The Poison Pill Problem

Pravah's Execution Service is consuming `job.assigned`. Everything is working. Then one message arrives that cannot be processed.

```
Partition 7:
  [offset 1000: pipe-abc job] ← processed fine ✅
  [offset 1001: pipe-def job] ← processed fine ✅
  [offset 1002: CORRUPTED   ] ← poison pill 💀
  [offset 1003: pipe-ghi job] ← waiting...
  [offset 1004: pipe-jkl job] ← waiting...
  ...
  [offset 1999: pipe-xyz job] ← 998 jobs blocked
```

Without poison pill handling:

```
Consumer reads offset 1002 → DeserializationException
Retry 1: reads offset 1002 → crash
Retry 2: reads offset 1002 → crash
Retry 3: reads offset 1002 → crash
... forever
```

Consumer is stuck at offset 1002. Offsets 1003–1999 never process. 998 pipeline jobs miss their SLA.

One corrupted message blocking 998 good ones — this is the poison pill problem.

---

## Types of Unprocessable Messages

Not all failures are equal. The handling strategy depends on the failure type.

**Type 1: Deserialization Failure**

Message bytes are corrupted or in the wrong format. Cannot be parsed at all.

- Causes: producer bug, schema registry mismatch, manual injection with wrong encoding
- Retryable: **No** — same bytes will always produce the same failure

**Type 2: Business Logic Failure (Non-retryable)**

Message parsed correctly but processing always fails for this specific message.

- Causes: pipeline deleted after queuing, tenant account suspended, invalid pipeline configuration
- Retryable: **No** — same message always produces same business error

**Type 3: Transient Failure (Retryable)**

Processing fails due to a temporary condition that will likely resolve.

- Causes: Runner Service temporarily down, database connection timeout, network blip, rate limit
- Retryable: **Yes** — will succeed on retry after backoff

**Type 4: Slow Poison (Timeout)**

Message starts processing but takes too long — LLM call hangs, deadlock, infinite loop.

- Retryable: **Depends** — requires timeout detection plus circuit breaker

**Pravah DLQ decision tree:**

```
Message fails
      │
      ▼
Is it retryable?
      │
   ┌──┴──┐
  YES    NO
   │      └──► Send to DLQ immediately
   │
   ▼
Retry with exponential backoff
      │
      ▼
Max retries exceeded?
      │
     YES
      │
      ▼
Send to DLQ
```

## Retry Strategy — Before DLQ

Transient failures should not go to DLQ immediately. They are likely to resolve with a brief backoff.

**Pravah's retry schedule:**

```
Attempt 1: fails → wait 1 second
Attempt 2: fails → wait 2 seconds
Attempt 3: fails → wait 4 seconds
Attempt 4: fails → wait 8 seconds
Attempt 5: fails → send to DLQ
```

Total wait before DLQ: ~15 seconds — short enough not to block a partition long, long enough for transient issues to resolve.

**Why jitter is essential:**

Without jitter, all 1000 messages retrying at exactly the same time create a thundering herd on the downstream service. With jitter, retry timing is spread out:

```
retry_wait = base × 2^attempt × random(0.5, 1.5)

Without jitter: 1000 messages all retry at t=1s, t=2s, t=4s
With jitter:    messages retry at t=0.8s, t=1.1s, t=0.9s...
                → smooth load on downstream service ✅
```

**Partition pause during backoff:**

Kafka consumers must keep polling during retries. But we cannot commit the failed offset and move on. The solution is to pause the specific partition during the backoff window:

```
Consumer reads offset 1002 → fails

1. Add {offset:1002, attempt:1} to retry queue
2. PAUSE partition 7 (no more messages from that partition)
3. Keep consuming other partitions 8, 9, 10, 11 normally ✅

After 1 second:
4. RESUME partition 7
5. Retry offset 1002

If succeeds: commit offset 1003, continue ✅
If fails again: pause again, wait 2 seconds
After 5 attempts: send to DLQ, commit offset 1003, continue ✅
```

Other partitions experience zero delay throughout this process. Only the one affected partition is paused.

## Implementation — DLQ Handler

```java
@Component
public class PravahDlqHandler {

    private final KafkaTemplate<String, byte[]> dlqProducer;
    private final MeterRegistry metrics;
    private final Map<TopicPartition, RetryState> retryStates = new ConcurrentHashMap<>();

    public RetryDecision handleFailure(
            ConsumerRecord<String, ?> record,
            Exception exception,
            Consumer<?, ?> consumer) {

        TopicPartition tp = new TopicPartition(record.topic(), record.partition());
        RetryState state = retryStates.computeIfAbsent(tp, k -> new RetryState());
        FailureType type = classify(exception);

        if (type == FailureType.NON_RETRYABLE || state.attempts >= MAX_ATTEMPTS) {
            sendToDlq(record, exception, state);
            commitOffset(consumer, record);
            retryStates.remove(tp);
            consumer.resume(Collections.singleton(tp));
            metrics.counter("pravah.dlq.messages",
                "topic", record.topic(),
                "failure_type", type.name()).increment();
            return RetryDecision.SKIP;
        }

        long backoffMs = calculateBackoff(state.attempts);
        state.attempts++;
        state.nextRetryAt = System.currentTimeMillis() + backoffMs;

        consumer.pause(Collections.singleton(tp));
        scheduler.schedule(
            () -> consumer.resume(Collections.singleton(tp)),
            backoffMs, TimeUnit.MILLISECONDS);

        return RetryDecision.RETRY;
    }

    private void sendToDlq(
            ConsumerRecord<String, ?> record,
            Exception exception,
            RetryState state) {

        String dlqTopic = record.topic() + ".dlq";

        DlqMessage dlqMessage = DlqMessage.newBuilder()
            .setOriginalTopic(record.topic())
            .setOriginalPartition(record.partition())
            .setOriginalOffset(record.offset())
            .setOriginalKey(record.key())
            .setOriginalValue(toBytes(record.value()))
            .setFailureReason(exception.getClass().getSimpleName())
            .setFailureMessage(exception.getMessage())
            .setFailureType(classify(exception).name())
            .setFailedAt(Instant.now().toEpochMilli())
            .setAttemptCount(state.attempts)
            .setCorrelationId(extractHeader(record, "correlation-id"))
            .setTenantId(extractHeader(record, "tenant-id"))
            .build();

        dlqProducer.send(dlqTopic, record.key(), dlqMessage.toByteArray())
            .addCallback(
                result -> log.info("Sent to DLQ: {}", dlqTopic),
                ex    -> log.error("DLQ send failed — logging and continuing", ex)
                // Never let DLQ failure block main processing
            );
    }

    private long calculateBackoff(int attempt) {
        long base = 1000L;
        long exponential = base * (long) Math.pow(2, attempt);
        long capped = Math.min(exponential, 30000L);
        return (long) (capped * (0.5 + random.nextDouble()));  // ±50% jitter
    }

    private FailureType classify(Exception exception) {
        if (exception instanceof SerializationException
                || exception instanceof InvalidProtocolBufferException) {
            return FailureType.NON_RETRYABLE;
        }
        if (exception instanceof PipelineNotFoundException
                || exception instanceof TenantSuspendedException) {
            return FailureType.NON_RETRYABLE;
        }
        if (exception instanceof ConnectException
                || exception instanceof TimeoutException) {
            return FailureType.RETRYABLE;
        }
        return FailureType.RETRYABLE;  // unknown → assume retryable
    }
}
```

## Handling Deserialization Failures Specially

Deserialization failures present a special challenge: the exception is thrown before any consumer code runs. The standard error handler never sees the message.

Kafka's `ErrorHandlingDeserializer` solves this:

```java
config.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
           ErrorHandlingDeserializer.class);
config.put(ErrorHandlingDeserializer.VALUE_DESERIALIZER_CLASS,
           KafkaProtobufDeserializer.class.getName());
```

How it works:
- **Normal:** protobuf deserialization succeeds → consumer receives `PipelineEvent` object ✅
- **Failure:** protobuf throws → `ErrorHandlingDeserializer` catches it → wraps raw bytes in a `DeserializationException` wrapper → consumer receives the wrapper (not null, not crash)

Consumer checks for the wrapper and routes to DLQ immediately:

```java
@KafkaListener(topics = "job.assigned")
public void handleJobAssigned(ConsumerRecord<String, Object> record) {
    if (record.value() instanceof DeserializationException ex) {
        dlqHandler.sendToDlqImmediately(record, ex);
        return;
    }

    JobAssigned job = (JobAssigned) record.value();
    processJob(job);
}
```

Benefits: consumer never crashes, partition never blocked, raw bytes preserved in DLQ for investigation, deserialization errors isolated immediately.

## DLQ Replay

When the root cause is fixed, operators replay failed messages through the Pravah UI.

**Simple replay** — re-process as-is:
1. Read original message bytes from DLQ topic
2. Publish to original topic with same key and payload
3. Add headers: `x-pravah-replay: true`, `x-pravah-replay-count: 1`
4. Consumer picks up replayed message and processes normally (idempotency key deduplicates if already partially processed)

**Modified replay** — fix and replay:
1. Operator edits payload in DLQ UI (fix schema mismatch, correct bad data)
2. Backend publishes corrected message to original topic
3. Consumer processes the fixed message ✅

**Bulk replay** — replay a batch after fixing root cause:

For example, 23 messages in `job.assigned.dlq` due to a schema misconfiguration:
1. Fix deployed (schema version corrected in consumer)
2. Operator selects all 23 messages in DLQ UI
3. Backend reads and re-publishes with rate limiting (10/second — prevents replay thundering herd)
4. Execution Service processes all 23 normally over ~2.3 seconds
5. DLQ cleared ✅

**Replay safety:** All replayed messages carry `x-pravah-replay: true` header. Idempotency keys are preserved from the original message. Double-replay is prevented — DLQ tracks replay status and requires explicit override to replay the same message twice.

## Agent-Assisted Root Cause Analysis

When a message lands in the DLQ, a DLQ event is published to `agent.observations`. The Agent Service analyzes the failure automatically.

**Example — schema mismatch:**

```
failure_type = "SerializationException"
failure_message = "Unknown field 'task_priority'"

Agent queries Schema Registry:
  → "What changed between schema v2 and v3?"
  → "Field task_priority added in v3"

Agent queries deployment log:
  → "When was Pipeline Service v3 deployed?"
  → "09:45 — 15 minutes ago"

Agent queries Execution Service:
  → "What schema version is currently running?"
  → "Schema v2 (deployment still pending)"

Agent conclusion:
  Pipeline Service upgraded to schema v3 (added task_priority)
  Execution Service still on v2.
  23 messages in DLQ are all deserialization failures.
  Fix: deploy Execution Service schema v3 update, then replay.
```

The agent creates a PagerDuty incident, posts the analysis to Slack, tags affected DLQ messages as `auto_replayable=true`, and triggers automatic replay once it detects the consumer has updated to v3.

## System Design Interview Angles

**"How does Pravah prevent one bad Kafka message from blocking thousands of good ones?"**

> We use a partition pause strategy combined with exponential backoff and DLQ routing. When a message fails, we classify it immediately. Non-retryable failures — deserialization errors, business logic failures like "pipeline not found" — go straight to DLQ: we commit the offset and continue processing the next message. Zero blocking.
>
> Retryable failures trigger partition pausing: we pause only that specific partition during the backoff window (1s, 2s, 4s, 8s) while other partitions continue processing normally. After max retries, unresolved messages go to DLQ.
>
> The DLQ itself is a Kafka topic — durable, replayable, queryable. Operators see failed messages in our UI with full context, Agent-generated root cause analysis, and one-click replay after fixing the root cause.

**"What is ErrorHandlingDeserializer and why does Pravah need it?"**

> The challenge with deserialization failures is they happen before your consumer code even runs — the Kafka deserializer throws an exception and the consumer either crashes or loops forever.
>
> `ErrorHandlingDeserializer` wraps the actual deserializer. If deserialization fails, instead of throwing, it catches the exception and returns a wrapper object containing the raw bytes and the exception. The consumer receives this wrapper, checks for it explicitly, and routes to DLQ immediately.
>
> Without it, a single corrupted message format crashes the consumer repeatedly — the partition gets stuck because the consumer can't commit the offset and move on. With it, Pravah handles corrupted bytes gracefully, preserves the raw bytes in DLQ for investigation, and continues processing remaining messages.

## Key Takeaways

1. **Poison pill** = one bad message blocks an entire Kafka partition forever — the core risk
2. **Three failure types:** deserialization (non-retryable), business logic (non-retryable), transient (retryable)
3. **Partition pause strategy:** pause only the affected partition during retry backoff; other partitions continue unaffected
4. **`ErrorHandlingDeserializer`:** catches deserialization exceptions before consumer; returns wrapper with raw bytes preserved; partition never blocked by corrupted bytes
5. **DLQ message structure:** original bytes + full failure context + retry history + correlation IDs for tracing
6. **Replay safety:** idempotency keys prevent double processing; rate limiting prevents thundering herd on bulk replay
7. **Agent + DLQ = automated RCA:** schema mismatches and deployment correlations detected automatically; MTTR reduced from hours to minutes
