# 2.9 Kafka Connect & CDC with Debezium

## The Data Ingestion Challenge

Pravah's ETL platform needs to ingest data from customer source systems: PostgreSQL, MySQL, MongoDB, Oracle, REST APIs. The simplest approach is to poll source databases periodically:

```sql
SELECT * FROM orders WHERE updated_at > last_run_time
```

This approach fails at production scale:
- Requires an `updated_at` column — not always present
- Misses hard deletes entirely (deleted rows become invisible)
- `updated_at` is often not indexed, causing full table scans
- Clock skew between Pravah and source DB causes edge case misses
- Polling interval equals ingestion latency — 5-minute poll means 5-minute lag
- Polling load impacts the source database during every run
- Race conditions at the exact poll boundary miss changes

The ideal approach is to react to changes as they happen, with millisecond latency, zero load on the source database, and capturing inserts, updates, and deletes. This is **Change Data Capture (CDC)**.

---

## What Is Change Data Capture?

Every production database maintains a transaction log that records every change before it happens. This is how databases recover from crashes. It is also how standby replication works.

- **PostgreSQL:** Write-Ahead Log (WAL)
- **MySQL:** Binary Log (binlog)
- **MongoDB:** Oplog (operations log)
- **Oracle:** Redo Log

CDC taps into this log to stream changes out. The source database experiences essentially zero additional load — Debezium connects as a replication client, the same mechanism used by standby databases.

**PostgreSQL WAL entries for common operations:**

An `INSERT` into `orders`:
```yaml
LSN: 0/1A2B3C4D
Transaction: 789
Relation: public.orders
Operation: INSERT
New values: { id: 123, customer_id: "cust-abc", amount: 500.00, status: "PENDING" }
```

An `UPDATE` changing status:
```yaml
LSN: 0/1A2B3C50
Transaction: 790
Relation: public.orders
Operation: UPDATE
Old values: { id: 123, status: "PENDING", ... }   ← before image
New values: { id: 123, status: "SHIPPED", ... }   ← after image
```

A `DELETE`:
```yaml
LSN: 0/1A2B3C60
Transaction: 791
Relation: public.orders
Operation: DELETE
Old values: { id: 123, customer_id: "cust-abc", ... }   ← deleted row
```

CDC reads these WAL entries and publishes them to Kafka. Pravah consumers receive changes within milliseconds of the source transaction committing.

## Debezium Architecture

Debezium is a distributed CDC platform built on Kafka Connect. It reads database transaction logs and publishes changes as structured Kafka events.

```
┌──────────────────────────────────────────────────────────┐
│                      SOURCE SYSTEM                       │
│  PostgreSQL                                              │
│  ┌─────────────────────────────────────────────────┐    │
│  │  orders table  │  WAL (replication slot)         │    │
│  │                │  LSN: 0/1A2B3C4D INSERT...      │    │
│  │                │  LSN: 0/1A2B3C50 UPDATE...      │    │
│  └─────────────────────────────────────────────────┘    │
└──────────────────────────┬───────────────────────────────┘
                           │ logical replication
                           │ (reads WAL via replication slot)
┌──────────────────────────▼───────────────────────────────┐
│              KAFKA CONNECT CLUSTER                        │
│  ┌──────────────────────────────────────────────────┐    │
│  │       Debezium PostgreSQL Connector              │    │
│  │  1. Connects to PG replication slot             │    │
│  │  2. Receives WAL changes as logical messages    │    │
│  │  3. Transforms to Debezium event format         │    │
│  │  4. Publishes to Kafka topics                   │    │
│  │  5. Tracks LSN offset in Kafka                  │    │
│  └──────────────────────────────────────────────────┘    │
└──────────────────────────┬───────────────────────────────┘
                           │ Kafka events
┌──────────────────────────▼───────────────────────────────┐
│                    KAFKA TOPICS                          │
│  pravah.source.postgres.public.orders                    │
│  pravah.source.postgres.public.customers                 │
│  pravah.source.postgres.public.products                  │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│                  PRAVAH CONSUMERS                        │
│  Pipeline Execution Engine                               │
│  Data Quality Service                                    │
│  Lineage Service                                         │
└──────────────────────────────────────────────────────────┘
```

## Debezium Event Format

Every Debezium event has a key and a value.

**Key** — identifies the changed row (maps to the primary key):
```json
{
  "schema": { "type": "struct", "fields": [{"field": "id", "type": "int64"}] },
  "payload": { "id": 123 }
}
```

Same row always produces the same Kafka key → same partition → ordered changes for that row ✅

**Value** — the full change event:
```json
{
  "payload": {
    "before": {
      "id": 123, "customer_id": "cust-abc", "amount": 500.00, "status": "PENDING"
    },
    "after": {
      "id": 123, "customer_id": "cust-abc", "amount": 500.00, "status": "SHIPPED"
    },
    "source": {
      "connector": "postgresql",
      "name": "pravah-source-postgres",
      "ts_ms": 1705312800000,
      "db": "ecommerce",
      "schema": "public",
      "table": "orders",
      "txId": 790,
      "lsn": 27565072
    },
    "op": "u",
    "ts_ms": 1705312800100
  }
}
```

Operation codes:
- `"c"` = CREATE (INSERT), `before` is null
- `"u"` = UPDATE, both `before` and `after` present
- `"d"` = DELETE, `after` is null
- `"r"` = READ (initial snapshot)
- `"t"` = TRUNCATE

## Kafka Connect — The Framework

Kafka Connect is the framework that Debezium runs on. It handles offset tracking, worker distribution, and error reporting so connector implementations do not have to.

**Two connector types:**
- **Source connectors:** external system → Kafka (Debezium CDC connectors, REST API connectors)
- **Sink connectors:** Kafka → external system (S3 sink, Elasticsearch sink, JDBC sink)

**Kafka Connect cluster components:**

```
┌─────────────────────────────────────────────────────────┐
│              Kafka Connect Cluster                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │   Worker 1   │  │   Worker 2   │  │   Worker 3   │  │
│  │  Connector A │  │  Connector B │  │  Connector A │  │
│  │  Task 1,2    │  │  Task 1,2    │  │  Task 3      │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
│                                                         │
│  Connector: configuration unit (what to connect)       │
│  Task: worker unit (does the actual work)              │
│  Worker: JVM process hosting tasks                     │
│                                                         │
│  Config stored in Kafka topics:                        │
│    connect-configs   ← connector configurations        │
│    connect-offsets   ← source offsets (WAL positions)  │
│    connect-status    ← connector/task health           │
└─────────────────────────────────────────────────────────┘
```

The REST API for managing connectors:

```
POST /connectors           ← create
GET  /connectors/{name}/status ← health check
PUT  /connectors/{name}/pause  ← pause
PUT  /connectors/{name}/resume ← resume
POST /connectors/{name}/restart ← restart
```

## Setting Up Debezium for Pravah

**Step 1: Configure PostgreSQL for logical replication**

In `postgresql.conf`:
```
wal_level = logical
max_replication_slots = 10
max_wal_senders = 10
```

**Step 2: Create replication user**

```sql
CREATE ROLE debezium WITH LOGIN REPLICATION PASSWORD 'secure-password';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO debezium;
GRANT USAGE ON SCHEMA public TO debezium;
```

**Step 3: Create publication**

```sql
CREATE PUBLICATION pravah_publication
  FOR TABLE orders, customers, products, inventory;
```

**Step 4: Deploy Debezium connector**

```json
{
  "name": "pravah-postgres-source",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "customer-db.internal",
    "database.port":     "5432",
    "database.user":     "debezium",
    "database.password": "${file:/secrets/db-password.properties:password}",
    "database.dbname":   "ecommerce",
    "database.server.name": "pravah-source-postgres",

    "plugin.name":       "pgoutput",
    "slot.name":         "pravah_replication_slot",
    "publication.name":  "pravah_publication",

    "table.include.list": "public.orders,public.customers,public.products",

    "key.converter": "io.confluent.connect.avro.AvroConverter",
    "key.converter.schema.registry.url": "http://schema-registry:8081",
    "value.converter": "io.confluent.connect.avro.AvroConverter",
    "value.converter.schema.registry.url": "http://schema-registry:8081",

    "snapshot.mode": "initial",
    "heartbeat.interval.ms": "10000",
    "heartbeat.action.query": "INSERT INTO debezium_heartbeat(ts) VALUES(NOW())",

    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "connect-dlq",
    "errors.deadletterqueue.context.headers.enable": "true"
  }
}
```

## Initial Snapshot — Loading Existing Data

When Debezium first connects, it must capture all existing data before streaming only new changes.

**Snapshot process:**

```
Step 1: Acquire brief lock (ACCESS SHARE MODE)
Step 2: Record current WAL position: SELECT pg_current_wal_lsn() → 0/1A2B3C70
Step 3: Release lock, open REPEATABLE READ transaction
Step 4: Read ALL existing rows in batches (10,240 rows/batch)
        → Publish each row as op="r" event
Step 5: Snapshot complete; record in offset: "snapshot done at LSN 0/1A2B3C70"
Step 6: Stream all WAL changes from LSN 0/1A2B3C70 onwards
```

The resulting Kafka topic for `orders` looks like:
```
[op:r row1][op:r row2]...[op:r row1M]   ← snapshot phase
[op:c new_row]                           ← streaming begins
[op:u updated_row]                       ← live changes
[op:d deleted_row]
```

No data gap between snapshot and streaming. For large tables (100M rows), snapshot runs in parallel threads and takes ~33 minutes; live changes are captured concurrently and applied seamlessly when streaming begins.

## WAL Retention — Critical Operational Risk

PostgreSQL replication slots instruct the database to retain WAL entries until Debezium confirms processing them. If Debezium is down, WAL accumulates on the source database disk.

**The risk:** Debezium down for 2+ hours → WAL fills disk → PostgreSQL cannot write → **source database crashes**.

**Pravah safeguards:**

**1. Monitor WAL lag:**
```sql
SELECT
  slot_name,
  pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)
  ) AS replication_lag
FROM pg_replication_slots;
```
Alert at 1GB lag. Critical alert at 5GB.

**2. Capped slot size:**
```
max_slot_wal_keep_size = 10GB
```
If slot lag exceeds 10GB, PostgreSQL automatically drops the replication slot. Debezium triggers a full re-snapshot. Data is not lost, but it is an operational incident.

**3. Automatic Debezium restart:**
Kubernetes liveness probe monitors `/connector/status`. Unhealthy connector → pod restart → Debezium reads last committed LSN from `connect-offsets` → resumes from that position, no data gap.

**4. Heartbeat to keep slot advancing:**
The heartbeat query (`INSERT INTO debezium_heartbeat(ts) VALUES(NOW())`) causes a WAL entry. Debezium processes it and advances the slot confirmation LSN. Even during idle periods — no changes to monitored tables — the slot does not fall behind. ✅

## Kafka Connect Sink Connectors

Pravah uses Kafka Connect for data destinations as well.

**S3 Sink — Parquet files for data lake:**

```json
{
  "connector.class": "io.confluent.connect.s3.S3SinkConnector",
  "topics": "pravah.transformed.orders",
  "s3.region": "eu-west-1",
  "s3.bucket.name": "pravah-data-lake",
  "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat",
  "partitioner.class": "io.confluent.connect.storage.partitioner.TimeBasedPartitioner",
  "path.format": "'year'=YYYY/'month'=MM/'day'=dd/'hour'=HH",
  "flush.size": "100000",
  "rotate.interval.ms": "3600000"
}
```

Result: `s3://pravah-data-lake/pravah.transformed.orders/year=2026/month=05/day=10/hour=11/`

**Elasticsearch Sink — search and lineage:**

```json
{
  "connector.class": "io.confluent.connect.elasticsearch.ElasticsearchSinkConnector",
  "connection.url": "http://elasticsearch:9200",
  "topics": "pravah.transformed.products",
  "write.method": "UPSERT",
  "behavior.on.null.values": "DELETE"
}
```

**JDBC Sink — loading to relational databases:**

```json
{
  "connector.class": "io.confluent.connect.jdbc.JdbcSinkConnector",
```

## Monitoring CDC Health

| Metric | Alert Condition |
|---|---|
| `debezium_connector_status` | Not RUNNING for > 30 seconds |
| `debezium_streaming_lag_ms` | > 30 seconds (near real-time SLA at risk) |
| `debezium_streaming_lag_ms` | > 5 minutes (SLA breached) |
| `debezium_events_per_second` | Sudden drop to 0 (connector stuck?) |
| WAL lag (pg_replication_slots) | > 1GB (warning), > 5GB (critical) |

## FAANG Interview Angles

**"How does Pravah capture database changes without polling and without impacting the source database?"**

> We use Change Data Capture via Debezium, which reads PostgreSQL's Write-Ahead Log. Every database already writes to the WAL for crash recovery and standby replication. Debezium connects as a replication client — the same way a standby database would. It reads logical WAL entries and publishes them as structured Kafka events containing the operation type, before image, and after image of every row change. Source database impact is essentially zero — no queries, no table scans, no polling load. And we capture inserts, updates, AND deletes, including hard deletes that polling completely misses.

**"What happens if Debezium goes down for 2 hours in Pravah?"**

> No data is lost, but there is operational risk. Debezium's replication slot instructs PostgreSQL to retain WAL entries until Debezium confirms processing them. So during the 2-hour outage, those WAL entries accumulate. When Debezium restarts, it reads its last committed LSN from Kafka's `connect-offsets` topic and resumes from exactly that position — replaying all 2 hours of buffered WAL in order. No gaps, no duplicates. The risk is disk: accumulated WAL can fill the source database disk. We mitigate with monitoring alerts at 1GB and 5GB lag thresholds, automatic Debezium restart via Kubernetes liveness probes, and `max_slot_wal_keep_size=10GB` to prevent runaway accumulation.

## Key Takeaways

1. **CDC vs polling:** CDC captures all changes including deletes, near-zero source DB impact, millisecond latency; polling misses deletes, requires `updated_at`, causes polling load
2. **Debezium reads database transaction logs:** PostgreSQL WAL via logical replication slot; each change = Kafka event with before/after images and operation code
3. **Initial snapshot:** existing data published as `op=r` events; seamless transition to streaming at snapshot LSN; no data gap
4. **Replication slot risk:** Debezium down → WAL accumulates → disk fills; mitigate with monitoring, K8s restart, and `max_slot_wal_keep_size`
5. **Heartbeat query:** keeps replication slot advancing during idle periods; prevents WAL lag even when monitored tables have no activity
6. **Kafka Connect = managed connector framework:** offset tracking, worker distribution, error handling; source connectors (DB → Kafka) and sink connectors (Kafka → destinations)
7. **Sink connectors:** S3 (Parquet, time-based partitioning), Elasticsearch (upsert), JDBC (upsert, auto schema evolve)
