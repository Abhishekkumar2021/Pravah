# 2.9 Kafka Connect & CDC with Debezium

## 🧩 Start With The Problem

THE DATA INGESTION CHALLENGE

Pravah's ETL platform needs to ingest data from:
```text
  → PostgreSQL databases (customer transaction data)
  → MySQL databases (legacy CRM systems)
  → MongoDB collections (document stores)
  → Oracle databases (enterprise ERP systems)
```

NAIVE APPROACH: Query the source database periodically

```sql
  SELECT * FROM orders WHERE updated_at > last_run_time
```

  Problems:
    ❌ Requires updated_at column (not always exists)
    ❌ Misses hard deletes (deleted rows invisible)
```text
    ❌ updated_at not always indexed → full table scan
    ❌ Clock skew between Pravah and source DB
    ❌ Polling interval = latency (5min poll = 5min lag)
    ❌ Heavy load on source database during poll
    ❌ Race condition: update at exact poll boundary missed
```

IDEAL APPROACH: React to changes AS THEY HAPPEN

```text
  Source DB changes a row →
  Pravah knows within milliseconds →
  Zero load on source DB →
  No missed changes →
  Captures inserts, updates, AND deletes
```

  This is Change Data Capture (CDC).
  Debezium implements CDC for Pravah.
📖 What Is Change Data Capture?
CDC — THE CORE CONCEPT

Every production database maintains a transaction log:

  PostgreSQL: Write-Ahead Log (WAL)
  MySQL:      Binary Log (binlog)
  MongoDB:    Oplog (operations log)
  Oracle:     Redo Log

This log records EVERY change before it happens.
It's how databases recover from crashes.
It's how replication works (standby databases read it).

CDC taps into this log to stream changes out.

POSTGRESQL WAL — WHAT IT LOOKS LIKE:

Customer inserts order:
```sql
  INSERT INTO orders (id, customer_id, amount, status)
  VALUES (123, 'cust-abc', 500.00, 'PENDING');
```

WAL entry:
```yaml
  LSN: 0/1A2B3C4D          ← Log Sequence Number
  Transaction: 789
  Relation: public.orders
  Operation: INSERT
  New values: {
    id: 123,
    customer_id: "cust-abc",
    amount: 500.00,
    status: "PENDING",
    created_at: "2024-01-15T10:00:00Z"
  }
```

Customer updates order:
```sql
  UPDATE orders SET status = 'SHIPPED' WHERE id = 123;
```

WAL entry:
  LSN: 0/1A2B3C50
  Transaction: 790
  Relation: public.orders
  Operation: UPDATE
```text
  Old values: {id: 123, status: "PENDING", ...}  ← before
  New values: {id: 123, status: "SHIPPED", ...}  ← after
```

Customer deletes order:
```sql
  DELETE FROM orders WHERE id = 123;
```

WAL entry:
  LSN: 0/1A2B3C60
  Transaction: 791
  Relation: public.orders
  Operation: DELETE
  Old values: {id: 123, customer_id: "cust-abc", ...}

```text
CDC reads these WAL entries → publishes to Kafka.
Pravah consumes from Kafka → processes changes.
Source DB: zero additional load from Pravah ✅
```

```text
📨 Debezium Event Format
DEBEZIUM KAFKA MESSAGE STRUCTURE
────────────────────────────────────────────────────────────
```

Every Debezium event has KEY and VALUE.

KEY (identifies the changed row):
  {
    "schema": {
      "type": "struct",
      "fields": [{"field": "id", "type": "int64"}]
    },
    "payload": {
      "id": 123
    }
  }

  Key = primary key of changed row.
```text
  Same row → same Kafka partition → ordered changes ✅
```

VALUE (the full change event):
  {
    "schema": { ... },
    "payload": {

```text
      "before": {                    ← row BEFORE change
        "id": 123,
        "customer_id": "cust-abc",
        "amount": 500.00,
        "status": "PENDING"
      },

      "after": {                     ← row AFTER change
        "id": 123,
        "customer_id": "cust-abc",
        "amount": 500.00,
        "status": "SHIPPED"
      },
```

      "source": {
        "version": "2.4.0.Final",
        "connector": "postgresql",
        "name": "pravah-source-postgres",
```text
        "ts_ms": 1705312800000,      ← DB commit timestamp
        "db": "ecommerce",
        "schema": "public",
        "table": "orders",
        "txId": 790,                 ← PostgreSQL transaction ID
        "lsn": 27565072,             ← WAL position
        "xmin": null
      },

      "op": "u",                     ← operation type
      "ts_ms": 1705312800100,        ← Debezium processing time

      "transaction": {               ← transaction metadata
        "id": "790:27565072",
        "total_order": 2,            ← position within transaction
        "data_collection_order": 1
      }
    }
  }
```

OPERATION TYPES:
  "c" = CREATE (INSERT)
  "u" = UPDATE
  "d" = DELETE
```text
  "r" = READ (snapshot)   ← initial load
  "t" = TRUNCATE
```

FOR DELETE OPERATIONS:
```text
  "before": { full row data }    ← the deleted row
  "after":  null                  ← nothing after delete
```

FOR INSERT OPERATIONS:
```text
  "before": null                  ← nothing before insert
  "after":  { full row data }    ← the new row
```

🔄 Initial Snapshot — Loading Existing Data
HOW DEBEZIUM HANDLES EXISTING DATA

When Debezium first connects to a source DB,
it needs to capture ALL EXISTING DATA before
streaming only new changes.

This is the SNAPSHOT PHASE.

SNAPSHOT PROCESS:

Step 1: Acquire lock (briefly)
  LOCK TABLE orders IN ACCESS SHARE MODE;
  (blocks writes briefly — typically < 1 second)

Step 2: Record current WAL position
```sql
  SELECT pg_current_wal_lsn();
  → 0/1A2B3C70  ← this is our starting point
```

Step 3: Release lock
```sql
  BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
  SET TRANSACTION SNAPSHOT '00000005-0000002B-1';
```

Step 4: Read ALL existing rows (in batches)
```sql
  SELECT * FROM orders;
  → Publishes each row as op="r" (read) event
```

Step 5: Snapshot complete
  Record in offset: snapshot complete at LSN 0/1A2B3C70

Step 6: Stream changes from LSN 0/1A2B3C70 onwards
```text
  All changes AFTER snapshot point → published normally
```

SNAPSHOT IN KAFKA:
  pravah-source-postgres.public.orders topic:
```text
  [op:r row1][op:r row2]...[op:r row1M]  ← snapshot
  [op:c new_row]                          ← streaming starts
  [op:u updated_row]                      ← live changes
  [op:d deleted_row]
```

SNAPSHOT FOR LARGE TABLES:
  orders table has 100 million rows.
  Snapshot = 100M events published to Kafka.
  
  Pravah handles this with:
    snapshot.fetch.size = 10240  (10K rows per batch)
    snapshot.max.threads = 4    (parallel snapshot)
    
  Estimated time: 100M rows / 50K rows/sec ≈ 33 minutes
  
  During snapshot: live changes also captured
  After snapshot: seamless transition to streaming
  No data gap between snapshot and streaming ✅
🔐 WAL Retention — Critical Operational Concern
THE REPLICATION SLOT PROBLEM

PostgreSQL replication slots:
  Keep WAL entries until the slot consumer catches up.
  If Debezium is DOWN: WAL accumulates!

  Debezium down for 2 hours:
    2 hours of WAL entries retained
    PostgreSQL disk: filling up!
    If disk full: PostgreSQL CRASHES ❌❌❌

PRAVAH SAFEGUARDS:

Safeguard 1: Monitor WAL size
  ALERT: pg_replication_slot lag > 1GB
  ALERT: pg_replication_slot lag > 10GB (critical)

```sql
  SELECT
    slot_name,
    pg_size_pretty(
      pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)
    ) AS replication_lag
  FROM pg_replication_slots;
```

Safeguard 2: Max WAL retention limit
  max_slot_wal_keep_size = 10GB  (in postgresql.conf)
  
  If slot lag exceeds 10GB:
    PostgreSQL automatically DROPS the slot!
    Debezium gets error: slot no longer exists
```text
    → Pravah triggers full re-snapshot
    → Data still captured (from snapshot + stream)
    → No data loss, but operational pain
```

Safeguard 3: Automatic Debezium restart
  K8s liveness probe: /connector/status
```text
  If Debezium connector unhealthy → restart pod
```
  
  Restart sequence:
    1. Debezium restarts
    2. Reads last committed offset from Kafka
       (connect-offsets topic: last confirmed LSN)
    3. Resumes from that LSN
    4. No data loss ✅ (WAL preserved by slot)

Safeguard 4: Heartbeat to keep slot alive
  heartbeat.interval.ms = 10000
  heartbeat.action.query:
```sql
    INSERT INTO debezium_heartbeat(ts) VALUES(NOW())
```
  
  This query causes a WAL entry.
```text
  Debezium processes it → advances slot confirmation.
  Even during idle periods → slot stays current ✅

```

  void start(Map<String, String> config);

EXAMPLE: Pravah REST API Source Connector
```java
────────────────────────────────────────────────────────────

@PravahConnector(name = "pravah-rest-source")
public class RestSourceConnector implements PravahSourceConnector {

  @Override
  public ConnectorInfo info() {
    return ConnectorInfo.builder()
        .name("pravah-rest-source")
        .description("Polls REST APIs and publishes to Kafka")
        .version("1.0.0")
        .type(ConnectorType.SOURCE)
        .build();
  }

  @Override
  public ConfigDef config() {
    return new ConfigDef()
        .define("api.url", Type.STRING, Importance.HIGH,
                "REST API endpoint URL")
        .define("api.auth.type", Type.STRING, "none",
                Importance.MEDIUM, "none|bearer|basic")
        .define("poll.interval.ms", Type.LONG, 60000L,
                Importance.MEDIUM, "Polling interval")
        .define("response.json.path", Type.STRING, "$",
                Importance.LOW, "JSONPath to extract records");
  }
}

@PravahTask
public class RestSourceTask implements PravahSourceTask {
```

  private String apiUrl;
  private long pollIntervalMs;
  private Instant lastPolled;

```java
  @Override
  public List<SourceRecord> poll() throws InterruptedException {
    // Wait until next poll interval
    Duration sinceLastPoll = Duration.between(lastPolled, Instant.now());
    if (sinceLastPoll.toMillis() < pollIntervalMs) {
      Thread.sleep(pollIntervalMs - sinceLastPoll.toMillis());
    }
```

    // Call REST API
    RestResponse response = httpClient.get(apiUrl);
    lastPolled = Instant.now();

    // Extract records from response
    List<JsonNode> records = jsonPath.read(
        response.body(), config.get("response.json.path"));

    // Convert to Kafka records
```java
    return records.stream()
        .map(record -> new SourceRecord(
            sourcePartition(),   // {api: apiUrl}
            sourceOffset(),      // {timestamp: lastPolled}
            outputTopic,
            Schema.STRING_SCHEMA,
            record.get("id").asText(),  // key
            recordSchema,
            convertToStruct(record)     // value
        ))
        .collect(toList());
  }
}
```

```text
❓ "How does Pravah capture database changes
    without polling and without impacting
    the source database?"
```

Good answer:
  "We use Change Data Capture via Debezium,
   which reads the database's transaction log —
   PostgreSQL's Write-Ahead Log specifically.

   Every database already writes to the WAL for
   crash recovery and standby replication. Debezium
   connects as a replication client — the same way
   a standby database would. It reads logical WAL
   entries and publishes them as structured Kafka
   events containing the operation type, before
   image, and after image of every row change.

   Source database impact is essentially zero —
   it's the same mechanism used for built-in
   replication. No additional queries, no table
   scans, no polling load. And we capture inserts,
```sql
   updates, AND deletes — including hard deletes
   that polling-based approaches completely miss."
```

❓ "What happens if Debezium goes down for
    2 hours in Pravah? Is data lost?"

Good answer:
  "No data is lost, but there's an operational risk.

   Debezium uses a PostgreSQL replication slot which
   instructs the database to retain WAL entries until
   Debezium confirms processing them. So during the
   2-hour outage, WAL entries accumulate — the database
   holds them for us.

   When Debezium restarts, it reads its last committed
   offset from Kafka's connect-offsets topic — the
   exact WAL LSN it last processed — and resumes from
   there. It replays all 2 hours of buffered WAL
   entries in order. No gaps, no duplicates.

   The operational risk is disk: if Debezium is down
   long enough, accumulated WAL can fill the source
   database disk. We mitigate this with monitoring
   alerts at 1GB lag and 5GB critical threshold,
   automatic Debezium restart via Kubernetes liveness
   probes, and max_slot_wal_keep_size=10GB to prevent
   runaway accumulation from crashing the source DB."

❓ "How does Kafka Connect differ from writing
    a custom Kafka producer/consumer directly?"

Good answer:
  "Kafka Connect handles all the operational
   scaffolding that would otherwise need custom code.

   Offset management: Connect stores source offsets
   in Kafka itself — crash and restart automatically
   resumes from the last position. Custom code needs
   to implement this manually.

   Scalability: Connect distributes tasks across
   worker nodes automatically. Adding workers =
   automatic rebalancing of tasks. Custom code
   needs manual partitioning logic.

   Schema management: Connect integrates with
   Schema Registry natively. Custom code needs
   explicit schema handling.

   Error handling: Connect has built-in DLQ
   integration, retry policies, and error reporting.

   For Pravah, Connect means Debezium CDC,
   S3 sink, Elasticsearch sink, and JDBC sink
   all run on the same Connect cluster with
   unified monitoring, deployment, and operations.
   The alternative — six custom services with
   custom offset tracking — would be much higher
   maintenance burden."

## 📌 Key Takeaways

1. CDC vs polling:
   Polling: misses deletes, needs updated_at column,
            heavy source DB load, polling interval = lag
   CDC: captures all changes including deletes,
        near-zero source DB impact, millisecond lag

2. Debezium reads database transaction logs:
   PostgreSQL: WAL via logical replication slot
   MySQL: binary log
   MongoDB: oplog
   Each change = Kafka event with before/after images

3. Debezium event structure:
```yaml
   Key: primary key (same row → same partition → ordered)
   Value: op + before + after + source metadata
   Operations: c=create, u=update, d=delete, r=read
```

4. Initial snapshot:
```text
   Existing data → op=r events
   Seamless transition to streaming at snapshot LSN
   No data gap between snapshot and streaming
```

5. Replication slot risk:
```text
   Debezium down → WAL accumulates → disk fills
   Mitigate: monitoring, K8s restart, max slot size
```

6. Kafka Connect = managed connector framework:
   Offset tracking, worker distribution, error handling
```text
   Source connectors (DB → Kafka) + Sink (Kafka → DB)
   Pravah extends with custom connector SDK
```

7. Sink connectors for destinations:
   S3 sink: Parquet files with time-based partitioning
   Elasticsearch sink: Upsert by document ID
   JDBC sink: Upsert by primary key, auto-schema-evolve

8. Monitor CDC lag continuously:
   > 30s lag = near real-time SLA at risk
   > 1GB WAL = operational risk to source DB
   Debezium down > 30s = PagerDuty
