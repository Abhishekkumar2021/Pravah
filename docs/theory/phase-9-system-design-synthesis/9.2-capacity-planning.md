# 9.2 Capacity Planning & Back-of-Envelope Estimation

## Why Estimate Before Building

Capacity planning forces you to think concretely about scale before writing code. If you estimate 100 pipeline runs per second and PostgreSQL can handle 10,000 writes/second, you have headroom. If you estimate 1,000,000 events per second and your Kafka cluster is sized for 100,000, you will have a production incident on day one.

The goal is not perfect accuracy — it is the right order of magnitude. An estimate that is 2× off is useful. An estimate that is 100× off indicates a fundamental misunderstanding of the system.

## Pravah Capacity Estimates

### Assumptions (medium-scale SaaS)

| Parameter | Value |
|-----------|-------|
| Active tenants | 500 |
| Pipelines per tenant (average) | 20 |
| Total pipelines | 10,000 |
| Pipeline runs per day (per pipeline) | 3 (hourly is common, some are daily, some real-time) |
| Total pipeline runs per day | 30,000 |
| Steps per pipeline (average) | 6 |
| Total step executions per day | 180,000 |

---

### Scheduler Service Load

```
30,000 pipeline runs/day ÷ 86,400 seconds/day = ~0.35 triggers/second (average)

Peak: most pipelines run at top-of-hour or daily at midnight
  → peak load: 30× average = ~10 triggers/second at 00:00 UTC

Scheduler SELECT queries:
  - Cron evaluation: poll due schedules every 5 seconds
  - 10,000 pipeline schedules / 5s = 2,000 rows/query — trivially fast

PostgreSQL writes:
  - 10 trigger events/second at peak → 10 writes/second
  - Well within single PostgreSQL primary capacity
```

**Conclusion:** The Scheduler is compute-light and I/O-light. 1 pod (2 CPU cores, 2GB RAM) is sufficient with a hot-standby replica for HA.

---

### Execution Service Load

```
Step dispatches per second:
  180,000 steps/day ÷ 86,400 = 2 dispatches/second (average)
  Peak (10× average): 20 dispatches/second

Each dispatch:
  - 1 PostgreSQL UPDATE (job status → RUNNING): ~1ms
  - 1 gRPC call to runner: 5-50ms (async, doesn't block the dispatcher)
  - 1 Kafka publish (execution.events): ~2ms

PostgreSQL TPS at peak:
  Dispatches:    20/s × 1 write = 20 writes/s
  Completions:   20/s × 3 writes (complete + trigger successors) = 60 writes/s
  Heartbeats:    500 runners × 1 update/15s = 33 writes/s
  Total: ~113 writes/second at peak

PostgreSQL capacity: 10,000 simple writes/second per primary
  → 113/10,000 = 1.1% utilization — enormous headroom
```

**Conclusion:** Execution Service at medium scale is comfortably within PostgreSQL capacity. 2-3 pods with a single primary + 1 replica is sufficient.

### Kafka Sizing

```
Topics: pipeline.events, execution.events, lineage.events,
        schema.drift.detected, data.quality.alerts,
        billing.compute.used, notifications.outbound, agent.observations

Events per day:
  execution.events: 180,000 step events + 30,000 pipeline events = 210,000/day
  lineage.events: 1 per step completion = 180,000/day
  All other topics: ~50,000/day combined

Total: ~440,000 events/day = ~5 events/second (average)
Peak: 50 events/second

Message size: average 2KB (JSON envelope + payload)

Kafka throughput at peak: 50 events/s × 2KB = 100KB/s
  → Kafka can handle 100s of MB/s per broker
  → 100KB/s is negligible even for a 3-broker cluster

Retention: 7 days × 440,000 events/day × 2KB = 6.2GB total
  → 3 replicas: 18.6GB of disk for Kafka storage
  → Each broker needs ~7GB SSD

Kafka cluster: 3 brokers, 8 partitions per topic, 3 replicas per partition
  → Handles 10,000× current load without changes
```

### PostgreSQL Storage

```
Jobs table (step executions):
  180,000 rows/day × 365 days = 65.7M rows/year
  Average row size: 500 bytes
  65.7M × 500B = 32.8GB/year (before archival)

Pipeline events (event store):
  30,000 runs/day × 10 events/run = 300,000 events/day
  Average event size: 2KB (JSONB)
  300,000 × 2KB × 365 = 219GB/year

With archival (Chapter 3.11): archive after 90 days
  Hot storage: 90 days × 180,000 steps × 500B = 8.1GB (jobs)
  Hot storage: 90 days × 300,000 events × 2KB = 54GB (pipeline events)
  Total hot PostgreSQL: ~65GB — trivially managed

Parquet archives (MinIO):
  180,000 steps × 90 days → archive
  365 days × 180,000 steps/day × average 50MB Parquet output per step
  = 3.3PB/year (this is data throughput, not storage — each Parquet is temporary)

  Actually: per-step Parquet is cleaned up after 30 days (lifecycle policy)
  Peak simultaneous Parquet on MinIO: 30 days × 180,000 steps × 50MB (average)
  = 270TB — this is large; in practice step outputs average much smaller (MBs not GBs)
  Realistic: 30 days × 180,000 steps × 50MB average = 270TB → too high

  Revised with realistic step output sizes:
  90% of steps: < 1MB output (short transforms, validation results)
  9% of steps: 1MB–1GB
  1% of steps: > 1GB (large data moves)

  Average: ~5MB per step output
  30 days × 180,000 steps × 5MB = 27TB MinIO storage for artifacts
```

**Conclusion:** MinIO needs ~30TB usable storage for 30-day artifact retention. 4 nodes × 10TB = 40TB with erasure coding redundancy.

### Runner Sizing

```
Steps per day: 180,000
Average step duration: 10 minutes (mix of seconds to hours)
Concurrent steps needed:
  180,000 steps × 10 min / 1440 min = 1,250 concurrent steps at any time

Runners (1 job per runner): 1,250 runners needed
  But: not all steps run simultaneously; peak might be 3× average
  Peak: ~3,750 runners

Runner resource profile:
  Small jobs (most common): 2 CPU, 4GB RAM
  Large jobs: 8 CPU, 16GB RAM
  Average: 2.5 CPU, 5GB RAM

Total compute at peak:
  3,750 runners × 2.5 CPU = 9,375 CPU cores
  3,750 runners × 5GB = 18.75TB RAM

This is customer-side compute (runners run in customer infrastructure).
Pravah's control plane does not provision this — customers bring their own runner capacity.
```

### Cost Modeling (Control Plane)

```
Kubernetes cluster (control plane services):
  11 services × 2 pods average × 2 CPU / 4GB = 22 CPU cores, 44GB RAM
  Cloud VM: 4 × 8-core, 32GB = cost ~$2,000/month

PostgreSQL cluster:
  5 service databases, each 3-node Patroni cluster
  Average: 8 CPU, 32GB RAM per node × 15 nodes = 120 CPU, 480GB RAM
  Cost: ~$8,000/month

MinIO cluster:
  4 nodes × 10TB NVMe = 40TB usable
  Cost: ~$1,500/month (hardware-based) or ~$3,000/month (cloud block storage)

Kafka cluster:
  3 brokers × 4 CPU, 16GB RAM = 12 CPU, 48GB RAM
  Cost: ~$800/month

Elasticsearch cluster:
  3 nodes × 8 CPU, 32GB RAM = 24 CPU, 96GB RAM
  Cost: ~$2,000/month

Total control plane: ~$15,000/month for 500 tenants = $30/tenant/month
At 1,000 tenants (with same infrastructure, linear headroom): $15/tenant/month
```

## Back-of-Envelope as a Design Tool

The capacity estimates above reveal several important design constraints:

**1. Kafka is not the bottleneck**: at 5 events/second average, even a single Kafka broker handles this trivially. Scale for burst (50/s) not average. Kafka partitioning (8 per topic) provides 10× headroom for parallel consumers.

**2. PostgreSQL is not the bottleneck**: at 113 writes/second peak, PostgreSQL at 10,000 TPS capacity has 99× headroom. The bottleneck is not database TPS — it is probably connection management (PgBouncer) and query latency for complex DAG evaluations.

**3. MinIO is the expensive component**: 30TB of artifact storage is the largest infrastructure cost. The 30-day lifecycle policy is critical to keep this bounded. Without it, storage grows unboundedly.

**4. Runner compute is the customer's problem**: Pravah's value proposition is that customers don't need to run an orchestration platform — but they do need to run runners. The runner resource model must be clearly documented so customers plan appropriately.

## Scaling Triggers

Define in advance at what scale you add capacity:

| Metric | Threshold | Action |
|--------|-----------|--------|
| PostgreSQL primary CPU > 60% | Sustained 15min | Add read replicas; evaluate sharding |
| PostgreSQL write TPS > 5,000 | Peak | Add execution_db sharding by tenant |
| Kafka consumer lag > 10,000 events | 5 min sustained | Add Kafka partitions + consumers |
| MinIO storage > 80% capacity | — | Add nodes; review lifecycle policies |
| API Gateway latency p99 > 500ms | — | Add pods; investigate slow endpoints |
| Execution Service dispatch lag | > 30s from trigger | Add pods; check DB connection pool |
