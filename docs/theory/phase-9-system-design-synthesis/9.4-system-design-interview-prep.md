# 9.4 System Design Interview Preparation

> This chapter treats Pravah itself as the subject of a FAANG-level system design interview. After nine phases of theory and three chapters of synthesis, you now have all the raw material. This chapter teaches you how to present it.

---

## The Framework: How to Answer Any System Design Question

FAANG interviewers evaluate four things, in order of importance:

1. **Clarification** — do you ask the right questions before designing?
2. **Scope** — can you make sharp decisions about what to build and what to defer?
3. **Depth** — do you understand the internals of each component you propose?
4. **Trade-offs** — can you reason about the cost of each decision?

A common mistake: jumping to components ("we'll use Kafka, PostgreSQL, Redis…") before establishing requirements. The interviewer wants to see how you think, not a list of technologies.

**The five-step framework:**

```
Step 1: Clarify (3-5 minutes)
  - Scale: how many users, requests/sec, data volume?
  - Consistency requirements: is it OK to show stale data?
  - Latency: p99 requirements per operation?
  - Geography: single region or multi-region?
  - SLA: what is acceptable downtime?

Step 2: High-Level Design (5-8 minutes)
  - Draw the major components and their interactions
  - Define the API surface (key endpoints)
  - Identify the primary data flows

Step 3: Data Model (5-8 minutes)
  - Schema for the core entities
  - Partitioning and indexing strategy
  - Read/write ratio and resulting database choices

Step 4: Deep Dive (10-15 minutes)
  - Pick the hardest problem and go deep
  - Usually: consistency, scale, or failure handling
  - Show you understand internals, not just API surfaces

Step 5: Trade-offs & Scaling (5 minutes)
  - What are the bottlenecks in your design?
  - What breaks first at 10× scale?
  - What would you do differently with more time?
```

## "Design Pravah" — Model Answer

This is the canonical system design question for this codebase. Walk through it using the framework.

### Step 1: Clarification

```
Q: How many tenants, pipelines, and job executions per day?
A: 10,000 tenants, 1M pipeline definitions, 100M job executions/day.

Q: Is job dispatch latency critical?
A: Yes — pipelines triggered by events must start within 30 seconds.

Q: Can runners be on-premise?
A: Yes. Runners run in customer infrastructure. The cloud is control plane only.

Q: What consistency model for pipeline state?
A: Pipeline definitions are critical — must be linearizable.
   Job status in the UI can be slightly stale (1-2 seconds acceptable).

Q: Multi-region?
A: Control plane in one primary region; runners in any region.
   Data stays in the runner's region.
```

### Step 2: High-Level Design

```
External Users
    │ HTTPS
    ▼
API Gateway          ← JWT auth, rate limiting, routing
    │ gRPC (mTLS)
    ├── Pipeline Service    ← CRUD, DAG validation, event sourcing
    ├── Scheduler Service   ← Cron, triggers, leader election
    ├── Execution Service   ← Job lifecycle, saga orchestration
    └── Runner Service      ← Fleet registry, gRPC streaming
         │ gRPC bidirectional (runner-initiated, mTLS)
    ┌────▼────────────────────────────────┐
    │         Customer Infrastructure      │
    │   Runner → executes jobs locally     │
    └──────────────────────────────────────┘

Async backbone: Apache Kafka (all service-to-service events)
Data: PostgreSQL per service, Redis (cache/lock), Elasticsearch (lineage)
Secrets: HashiCorp Vault (dynamic credentials, mTLS certs)
```

### Step 3: Data Model

**Core tables (Execution Service):**

```sql
-- An execution is one run of a pipeline
CREATE TABLE executions (
    id              UUID PRIMARY KEY,
    tenant_id       VARCHAR(255) NOT NULL,
    pipeline_id     UUID NOT NULL,
    pipeline_version INT NOT NULL,
    status          VARCHAR(50) NOT NULL,  -- PENDING, RUNNING, SUCCEEDED, FAILED
    triggered_by    VARCHAR(50) NOT NULL,  -- CRON, EVENT, MANUAL, BACKFILL
    triggered_at    TIMESTAMPTZ NOT NULL,
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- A job is one step of an execution
CREATE TABLE jobs (
    id              UUID PRIMARY KEY,
    tenant_id       VARCHAR(255) NOT NULL,
    execution_id    UUID NOT NULL,
    step_id         VARCHAR(255) NOT NULL,
    status          VARCHAR(50) NOT NULL,
    runner_id       UUID,
    attempt_number  INT NOT NULL DEFAULT 1,
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    error_message   TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- Indexes
CREATE INDEX idx_jobs_execution ON jobs (execution_id) WHERE status != 'SUCCEEDED';
CREATE INDEX idx_jobs_tenant_status ON jobs (tenant_id, status, created_at DESC);
```

**Key design decisions to explain:**
- Partitioned by `created_at` (monthly) — enables instant archival by `DROP TABLE`
- Partial index on `WHERE status != 'SUCCEEDED'` — 95% of queries are for active jobs
- `tenant_id` on every table + PostgreSQL RLS — defense-in-depth tenant isolation

### Step 4: Deep Dive — The Hard Problem

**The interviewer will ask: "How do you guarantee a pipeline runs exactly once when the cron fires?"**

```
Problem: Scheduler has 3 replicas for HA. All three see the cron fire at 09:00.
         Without coordination, all three trigger the pipeline → triple execution.

Solution: Distributed lock + fencing token

1. Each Scheduler replica races to acquire a Redis lock:
   SET scheduler:lock:{pipeline_id}:{window} {pod_id} NX PX 30000

2. The winner (NX succeeds) proceeds to evaluate and trigger.
   It publishes pipeline.triggered with a fencing_token (monotonically increasing).

3. The losers (NX fails) see the lock exists and skip.

4. The Execution Service checks: is this fencing_token > last_seen_token?
   If yes: create execution.
   If no: duplicate — silently drop.

5. The lock expires after 30 seconds. If the winner crashes before publishing,
   another replica acquires the lock and triggers. The fencing token prevents
   double-execution even if both publish.
```

**The interviewer will ask: "What if the runner crashes mid-job?"**

```
1. Runner sends heartbeats every 10 seconds.
2. Runner Service marks runner SUSPECT after 30 seconds of silence.
3. After 60 seconds, runner marked DEAD.
4. A timeout monitor in Execution Service polls for:
   SELECT * FROM jobs
   WHERE status = 'RUNNING'
   AND runner_id IN (SELECT id FROM runners WHERE status = 'DEAD')
   AND started_at < NOW() - INTERVAL '60 seconds'

5. For each: increment attempt_number. If attempt_number <= max_retries: re-queue.
   If attempt_number > max_retries: FAILED with reason 'runner_lost'.

6. Idempotency: if the runner comes back and tries to submit results for a job
   that has already been reassigned, the fencing token rejects it.
   The job's current runner_id no longer matches.
```

### Step 5: Trade-offs

| Decision | Trade-off |
|----------|-----------|
| Choreography saga over orchestration | Harder to trace, easier to scale; no central bottleneck |
| Pool multi-tenancy over silo | Cheaper to operate; noisy neighbor risk; RLS is the safety net |
| Kafka over RabbitMQ | Replay + multi-consumer fan-out; harder DLQ handling |
| Polling outbox over CDC | Simpler to operate; adds 100ms publish latency |
| gRPC for runners over WebSocket | Binary efficiency + bidirectional streaming; harder to debug |

**What breaks first at 10× scale:**
- `jobs` table write throughput → solved by increasing partition count and sharding by `tenant_id` (Citus)
- Kafka consumer lag → KEDA adds more Execution Service replicas
- Runner Service gRPC connection count → horizontal scaling limited by state; migrate to stateless routing layer

## Common Interview Questions — Short Answers

**"How do you handle schema evolution in your API?"**
Protobuf for gRPC (field numbers, backward compatibility). Avro with Schema Registry for Kafka (BACKWARD_TRANSITIVE). REST API versioned by URL path (`/v1/`, `/v2/`). Old and new versions run simultaneously during transition.

**"How do you prevent data loss when a service crashes?"**
Outbox Pattern: business state change and event publication are in the same PostgreSQL transaction. If the service crashes after the commit, the outbox relay retries publication on restart. If it crashes before the commit, nothing was written — no partial state.

**"How do you scale to 1 billion jobs per day?"**
Back-of-envelope: 1B/day = ~11,600/sec. Each job record is ~500 bytes. Write throughput: ~5.8 MB/s — well within PostgreSQL's capacity with partitioning. The bottleneck is Kafka consumer throughput: 11,600 events/sec across 24 partitions = 483/sec per partition. Each Execution Service instance handles ~1,000 jobs/sec → need 12 instances. KEDA handles this automatically.

**"How do you debug a pipeline that failed 3 days ago?"**
1. Query Elasticsearch for all log lines with `execution_id = X` (7-day retention)
2. Pull the distributed trace from Jaeger using the `trace_id` from the log (tail-sampled: 100% of errors retained)
3. Check the outbox table for any events that failed to publish around that time
4. Replay the `pipeline.events` Kafka topic from the execution's `triggered_at` offset

**"How do you handle a 10× traffic spike?"**
KEDA detects Kafka consumer lag → scales Execution Service 3→30 replicas in ~90 seconds. Cluster Autoscaler adds nodes if the existing nodes can't schedule the new pods. Rate limiting at the API Gateway prevents the Kafka producer from getting too far ahead of consumers. PgBouncer absorbs the database connection spike — 30 pods still share the same 25 database connections.

**"How do you ensure tenant A can't see tenant B's data?"**
Five-layer defense:
1. JWT carries `tenant_id` — extracted by API Gateway
2. All repository methods: `findByIdAndTenantId()` — application layer
3. PostgreSQL RLS: `FORCE ROW LEVEL SECURITY` with `SET LOCAL pravah.current_tenant_id` — database layer
4. Kafka events: `tenant_id` in every message; consumers validate before processing
5. Vault Transit: per-tenant encryption keys — even a cross-tenant leak returns ciphertext

**"What's your disaster recovery strategy?"**
RPO < 5 minutes: PostgreSQL streaming replication with WAL shipping to replica (continuous). RTO < 15 minutes: Patroni automatic failover promotes replica to primary; Kubernetes readiness probes gate traffic until the new primary is ready; Kafka is already multi-broker (3 replicas, min.insync.replicas=2) — survives broker loss without data loss.

## What FAANG Interviewers Actually Care About

**They don't care if you pick Kafka vs RabbitMQ.** They care if you can explain why you picked Kafka — specifically: "because we need log-based replay for exactly-once semantics across multiple consumers, which a queue-based system cannot provide."

**They don't care about the happy path.** They ask "what happens when X fails?" for every component. For Pravah:
- What if Kafka is down? → Outbox accumulates; no data loss
- What if the runner loses network? → Heartbeat timeout → reassign
- What if PostgreSQL primary fails? → Patroni promotes replica in < 30 seconds
- What if Vault is unavailable? → Agent caches last-known secrets; alerts immediately

**They test whether you understand the internals**, not just the API. "How does Kafka guarantee ordering?" (partition-level, not global). "How does PostgreSQL handle concurrent writes?" (MVCC — each write creates a new row version; VACUUM reclaims dead versions). "How does Redis distributed locking work?" (SET NX PX — atomic; fencing tokens prevent zombie locks from causing damage).

**They look for calibrated confidence.** "I would choose X for this reason, but it has this trade-off. If Y constraint changes, I would reconsider Z." Not "X is always the right answer."

## The One Question That Separates Good From Great Answers

After presenting any design, the best candidates ask themselves:

**"Where is the single point of failure in what I just described?"**

For every component you propose, be ready to answer:
- What happens if it goes down for 30 seconds?
- What happens if it returns wrong data?
- What happens if it's slow (not down)?

Pravah's answers:
- Kafka broker down → two remaining brokers handle traffic; leader election within seconds
- PostgreSQL primary slow → PgBouncer queue fills → circuit breaker trips → 503 to client
- Redis down → rate limiting degrades gracefully (fail open); distributed locks fall back to PostgreSQL advisory locks
- Vault down → agents use cached secrets for up to 5 minutes; then services start failing with explicit errors (fail closed for security)

The ability to reason clearly about partial failure — not just total failure — is what FAANG interviews test at the senior level.
