# 9.1 Full Architecture Walkthrough

## Reading a System End to End

The deepest test of understanding a distributed system is being able to trace a single request through every layer, identify every component that participates, and state what happens when each one fails. This chapter walks three critical flows in Pravah from first principles — not as a list of components, but as a causal chain of events.

---

## Flow 1: Pipeline Triggered by Schedule

**Scenario:** The `orders-daily-etl` pipeline is scheduled to run at 09:00 UTC every day.

```
09:00:00  Scheduler Service (cron evaluation)
  → Reads schedule "0 9 * * *" from PostgreSQL (execution_db.pipeline_schedules)
  → Checks concurrency policy: SKIP if already running
  → Verifies no active execution for this pipeline + tenant
  → Creates Execution record in PostgreSQL (status: QUEUED)
  → Publishes PipelineTriggered event to Kafka (pipeline.events topic)
  → Returns: execution_id = "exec-abc-2026-05-10"

09:00:00  Kafka (pipeline.events)
  → Message retained per retention policy (7 days)
  → Partition selected by hash(tenant_id) → partition 3

09:00:01  Execution Service (consumer of pipeline.events)
  → Receives PipelineTriggered
  → Calls Pipeline Service gRPC: GetPipelineDefinition("orders-daily-etl")
  → Pipeline Service reads from Redis cache → HIT → returns definition in 2ms
  → Validates DAG (topological sort, no cycles)
  → Creates Job records in PostgreSQL for each step:
      job-1: extract   (status: READY   — no deps)
      job-2: validate  (status: WAITING — deps: extract)
      job-3: transform (status: WAITING — deps: validate)
      job-4: load_dw   (status: WAITING — deps: transform)
      job-5: load_s3   (status: WAITING — deps: transform)
      job-6: notify    (status: WAITING — deps: load_dw, load_s3)
  → Publishes JobCreated to Kafka (execution.events topic) for job-1

09:00:01  Execution Service (dispatcher)
  → Picks up job-1 (READY)
  → Selects runner: queries Redis for available runners with extract capability
  → Runner-7 selected (megacorp tenant, capacity available)
  → Sends gRPC JobAssignment to Runner-7 (via Istio-mTLS encrypted channel)
  → Updates job-1 status: READY → RUNNING, runner_id = runner-7

09:00:02  Runner-7 (customer infrastructure)
  → Receives JobAssignment for extract step
  → Calls Execution Service: "give me a MinIO upload URL for step output"
  → Execution Service validates tenant, generates pre-signed PUT URL (15-min TTL)
  → Runner calls Vault Agent for DB credentials: postgres://prod-orders-db
  → Runner executes: DuckDB reads from PostgreSQL (JDBC), writes to MinIO as Parquet
     SELECT * FROM orders WHERE order_date = '2026-05-09'
     → 8.2M rows, 3.4GB on disk → compressed to 420MB ZSTD Parquet
  → Runner calls Metadata Service: emit OpenLineage RunEvent (COMPLETE)
  → Runner calls Execution Service: JobSucceeded(job-1, output_path=s3://...)

09:00:45  Execution Service (JobSucceeded handler)
  → Updates job-1: RUNNING → SUCCEEDED, checkpoint_path set
  → Evaluates dependents: job-2 (validate) — all deps SUCCEEDED? Yes → WAITING → READY
  → Dispatches job-2 to a runner

09:00:46  [validation, transform, load_dw, load_s3 steps execute in sequence/parallel]
  [load_dw and load_s3 dispatch simultaneously after transform SUCCEEDS]
  [notify waits until BOTH load_dw and load_s3 SUCCEED]

09:04:23  Execution Service (all steps SUCCEEDED)
  → Updates Execution: status QUEUED → RUNNING → SUCCEEDED
  → Publishes ExecutionSucceeded to Kafka (pipeline.events)
  → Notification Service sends summary email to pipeline owner

09:04:23  Metadata Service (consumer of lineage.events)
  → Has been processing OpenLineage events from each step as they completed
  → Updates pipeline catalog: last_run_at, last_run_status, run_duration
  → Updates schema catalog: schema versions for input/output datasets

09:04:24  Observability (metrics, traces)
  → Execution duration: 4m23s → histogram metric recorded
  → OpenTelemetry traces from each service stitched into one trace
  → Jaeger shows end-to-end trace: 6 gRPC calls, 12 Kafka messages, 3 DB queries
```

**Failure scenario: Runner-7 crashes during extract step at 09:00:30:**

```
09:01:00  Runner-7 misses heartbeat (last heartbeat: 09:00:15)
09:01:45  Execution Service heartbeat monitor: Runner-7 not seen for 45s
           → marks Runner-7 as DISCONNECTED
           → job-1 status: RUNNING → INTERRUPTED
           → creates job-1 attempt 2 (new Job record, same step_id, attempt_number=2)
           → dispatches to Runner-12

Runner-12:
  → Checks MinIO: does extract step have .completed sentinel? NO (crashed mid-upload)
  → Runs extract from scratch (partial upload was abandoned)
  → Uploads complete → writes .completed sentinel → reports JobSucceeded

Total delay: ~2 minutes (runner detection + new runner pickup)
Data correctness: identical result (idempotent extraction + MERGE at destination)
```

## Flow 2: Schema Drift Auto-Heal

**Scenario:** The source database's `orders` table had the `loyalty_tier` column removed at 14:00 on May 8. The daily pipeline fails at 09:00 on May 10.

```
09:00:00  [pipeline triggered, extract succeeds]

09:00:45  Runner executes transform step
  → DuckDB executes: SELECT customer_id, loyalty_tier, revenue FROM orders
  → orders input from Parquet (extract output) — no loyalty_tier column
  → DuckDB throws: "Column 'loyalty_tier' not found"
  → Runner reports: JobFailed(job-3, error_category=SCHEMA_MISMATCH, retry=false)
     [SCHEMA_MISMATCH is in no-retry list — retry won't help]

09:00:46  Execution Service
  → job-3 (transform): RUNNING → FAILED (no retry)
  → Cancel downstream: job-4 (load_dw), job-5 (load_s3), job-6 (notify) → CANCELLED
  → Execution: RUNNING → FAILED
  → Publishes ExecutionFailed event to Kafka

09:00:46  Agent Service (consumer of execution.events)
  → Receives ExecutionFailed for pipeline orders-daily-etl
  → Checks: auto_heal_enabled=true for this pipeline
  → Starts ReAct loop...

ReAct loop:
  Action: get_execution_logs(exec_id, step_id=transform)
  Observation: "Column 'loyalty_tier' not found in table read from Parquet"

  Action: get_column_lineage(dataset=postgres://prod/public.orders)
  Observation: loyalty_tier last seen 2026-05-08, schema drift detected at 14:32

  Action: get_pipeline_definition(orders-daily-etl, step=transform)
  Observation: SQL = "SELECT customer_id, loyalty_tier, revenue FROM orders"

  Action: propose_fix(orders-daily-etl, transform,
    "SELECT customer_id, COALESCE(loyalty_tier, 'UNKNOWN') AS loyalty_tier, revenue FROM orders")
  Observation: { draft_version: v4, validation: PASSED }

  Action: trigger_pipeline(orders-daily-etl, parameters={version: v4, business_date: 2026-05-09})

09:01:30  Pipeline re-runs with draft v4 → succeeds

09:01:31  Agent Service
  → Records resolution: SCHEMA_DRIFT + COALESCE fix
  → Indexes pattern in failure_patterns (pgvector) for long-term memory
  → Sends notification: "Auto-healed pipeline orders-daily-etl: schema drift fixed"
  → Total time from failure to resolution: 45 seconds
```

## Flow 3: New Tenant Onboarding

**Scenario:** A new enterprise customer "Acme Corp" activates their Pravah account.

```
User signs up → API Gateway receives POST /v1/tenants

API Gateway:
  → Validates JWT (new user token from OAuth 2.0 flow)
  → Routes to Pipeline Service (tenant provisioning)

Pipeline Service:
  → Creates tenant record: tenant_id = "acme-corp"
  → Sets pool-model resources: shared cluster, dedicated schemas

PostgreSQL (provisioning):
  → Creates schemas in shared cluster:
    CREATE SCHEMA "acme_corp_pipelines";
    CREATE SCHEMA "acme_corp_executions";
  → Enables Row-Level Security (ADR-013)
  → Creates tenant RLS policies on all tables

Vault provisioning:
  → Creates namespace: acme-corp
  → Creates database credential role: acme-corp-execution-db
  → Issues initial credentials

Redis:
  → Sets tenant configuration: { tier: ENTERPRISE, max_runners: 50, ... }

Kafka:
  → Creates tenant-specific consumer groups (no new topics — shared topics with tenant_id key)

Kubernetes:
  → If dedicated runner pool requested: creates RunnerPool K8s resource
  → KEDA ScaledObject created for acme-corp runner pool

Notification:
  → Sends welcome email with API credentials and documentation links

Response: { tenant_id: "acme-corp", api_key: "...", onboarding_guide: "..." }
```

The entire provisioning takes ~5 seconds. No manual steps, no ticket to the infrastructure team.

```
             └──────┬──────┘ └──────────────┘
                    │
            Elasticsearch
            (lineage, catalog)

Data layer:
  PostgreSQL (Patroni HA): pipeline_db, execution_db, scheduler_db, agent_db
  Redis: caching, sessions, rate limiting, distributed locks
  MinIO: artifacts, Parquet, Flink checkpoints, cold archives
  Vault: secrets, PKI, dynamic credentials

Runners (customer infrastructure):
  ← gRPC + mTLS (Vault PKI certificates)
  → MinIO (pre-signed URLs via Execution Service)
  → DuckDB (in-process columnar transforms)
```

Every arrow in this diagram is a communication path that can fail. Distributed systems design is fundamentally about deciding which failures to tolerate (via redundancy, retry, circuit breaking) and which are terminal (requiring human intervention).
