# 9.3 Bottleneck Analysis & Performance Engineering

## The Fundamental Principle: You Cannot Optimize What You Cannot Measure

Every performance engineering effort starts with measurement, not hypothesis. Premature optimization ("I think the database is slow") without data is how engineers spend weeks optimizing something that contributes 0.1% of latency.

The workflow is always:
1. **Measure**: where does time actually go? Distributed traces, profiling, metrics
2. **Identify**: which component contributes the most to latency or resource usage?
3. **Theorize**: why is this component the bottleneck? Is it CPU, I/O, network, lock contention?
4. **Hypothesize**: what change would reduce the bottleneck?
5. **Test**: implement the change in isolation, measure the effect
6. **Confirm**: did latency/throughput improve as expected?

If step 6 shows no improvement, the hypothesis was wrong. Return to step 3.

## Performance Profiling Stack for Pravah

**End-to-end: distributed traces (OpenTelemetry → Jaeger)**

The first tool: look at a trace for the slow request. A trace shows the causal chain of calls with actual durations for each span:

```
Trace for exec-abc (total: 4m23s):
  Execution Service: process PipelineTriggered         12ms
    └── Pipeline Service: GetPipelineDefinition        3ms  (cache hit)
    └── PostgreSQL: create 6 job records               8ms
    └── Kafka: publish 1 message                       2ms

  Runner-7: extract step                               44,000ms  ← 99% of total time
    ├── Vault: get credentials                         45ms
    ├── PostgreSQL JDBC: read 8.2M rows                32,000ms  ← 73% of step
    ├── DuckDB: process and compress                   10,000ms
    └── MinIO: upload 420MB                            2,000ms

  Execution Service: dispatch validate                 5ms
  ...
```

The trace reveals: **99% of the pipeline time is in the extract step, and 73% of that is PostgreSQL JDBC read time**. Optimization efforts should focus here, not on the Execution Service's 12ms overhead.

**Component level: JVM profiling**

For the runner's JDBC read performance, attach a JVM profiler (async-profiler, JFR) during a representative execution:

```
Flame graph output:
  72% → PostgreSQL JDBC read → socket receive → ByteBuffer copy
    → root cause: JDBC is receiving data in small packets (fetch size too small)

Fix: set fetch size to 10,000 rows (default is 10)
  conn.prepareStatement(sql).setFetchSize(10000);

Result: 32,000ms → 8,000ms (4× improvement — larger packets, fewer round trips)
```

**Database level: PostgreSQL `pg_stat_statements`**

For slow PostgreSQL queries:

```sql
SELECT query, calls, total_exec_time, mean_exec_time, stddev_exec_time
FROM pg_stat_statements
WHERE mean_exec_time > 100   -- queries averaging > 100ms
ORDER BY total_exec_time DESC
LIMIT 20;
```

Common findings and fixes:

| Finding | Fix |
|---------|-----|
| Sequential scan on large table | Add index on the filtered column |
| High `stddev_exec_time` | Autovacuum backlog; bloated table; run VACUUM ANALYZE |
| Lock wait (`waiting = true` in `pg_stat_activity`) | Identify blocking transaction; review transaction scope |
| Index scan but high cost | Index is correct but outdated statistics; run ANALYZE |
| N+1 query pattern | Batch the queries; use JOIN instead of loop |

**Kafka: consumer lag**

```bash
kafka-consumer-groups.sh --describe --group execution-service

GROUP               TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
execution-service   pipeline.events 0          12450           12450           0
execution-service   pipeline.events 1          9876            10234           358   ← LAG
execution-service   pipeline.events 2          8123            8123            0
```

Partition 1 has 358 messages of lag — the consumer is behind. Diagnoses:
- Consumer is slow processing each message → profile the message handler
- Consumer pod is restarting → check pod logs for OOM or errors
- Not enough consumer parallelism → add more consumer pods (max: one per partition = 8)

## The Pravah-Specific Bottlenecks

**Bottleneck 1: PostgreSQL write contention on the jobs table**

At peak, all Execution Service instances write to the `jobs` table simultaneously. The `job_id` primary key is UUID (random) — good for avoiding hot spots on the B-tree index. But the composite index `(execution_id, status)` used for "find all READY jobs for this execution" may become a hot spot if many executions are completing simultaneously.

Mitigation:
- PgBouncer in transaction mode (pool connections, don't hold between queries)
- `FOR UPDATE SKIP LOCKED` for job dispatch (no blocking between competing Execution Service instances)
- Partition `jobs` table by `created_at` month — reduces index size per query

**Bottleneck 2: Redis cache stampede**

When a frequently-accessed pipeline is updated and its cache key is invalidated, many concurrent requests hit the cache cold and all query PostgreSQL simultaneously.

Mitigation: single-flight pattern (only one request fetches from DB; others wait for the result). Spring's `@Cacheable` with a custom cache manager that implements single-flight.

**Bottleneck 3: Kafka rebalancing during deployment**

When Execution Service pods are restarted during deployment, Kafka consumer groups rebalance. During rebalancing (30–90 seconds), no consumer is processing messages — effective consumer downtime.

Mitigation:
- Use `CooperativeStickyAssignor` (incremental rebalancing — partitions are reassigned one at a time, not all at once)
- `session.timeout.ms = 30s` (quick failure detection)
- `max.poll.interval.ms = 300s` (allow slow message processing without false rebalancing)

**Bottleneck 4: gRPC timeout cascades**

The API Gateway calls the Pipeline Service with a 5-second timeout. The Pipeline Service calls the Execution Service with a 4-second timeout. If the Execution Service is slow, the Pipeline Service times out, the API Gateway times out, and the user sees a 500 error — even if the operation would have succeeded with more time.

Mitigation: timeout budget propagation. Each service receives the remaining time budget from the caller's context and uses at most 80% of it for its own downstream calls:

```java
long remainingBudget = grpcContext.getDeadline().timeRemaining(TimeUnit.MILLISECONDS);
long childTimeout = (long)(remainingBudget * 0.8);  // leave 20% for our own work
```

This ensures that a downstream slow response doesn't cascade into simultaneous timeouts at every layer.

## Query Optimization in Practice

**The EXPLAIN ANALYZE loop:**

```sql
-- Slow query: find all FAILED executions for a tenant in the last 30 days
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT e.id, e.status, e.created_at, p.name
FROM executions e
JOIN pipelines p ON e.pipeline_id = p.id
WHERE e.tenant_id = 'megacorp'
  AND e.status = 'FAILED'
  AND e.created_at > NOW() - INTERVAL '30 days'
ORDER BY e.created_at DESC
LIMIT 100;

Output:
  Sort (cost=12450..12455 rows=100 width=200) (actual time=2344..2345 rows=100)
    → Seq Scan on executions (cost=0..12400 rows=450 width=150)
         Filter: (tenant_id='megacorp' AND status='FAILED' AND created_at > ...)
         Rows Removed by Filter: 1,850,000   ← reading 1.85M rows to find 450

Fix: add composite index on (tenant_id, status, created_at):
  CREATE INDEX idx_executions_tenant_status_date
      ON executions (tenant_id, status, created_at DESC);

After index:
  Index Scan on idx_executions_tenant_status_date
      actual time=0.3..2.1 rows=100
  → 1000× faster
```

## Load Testing Strategy

Performance problems found in production are expensive. Load tests find them in pre-production.

**K6 load test for Pravah's pipeline trigger API:**

```javascript
import http from 'k6/http';
import { check } from 'k6';

export let options = {
  stages: [
    { duration: '1m', target: 10 },    // ramp to 10 users
    { duration: '5m', target: 100 },   // ramp to 100 users (peak estimate × 3)
    { duration: '2m', target: 0 },     // ramp down
  ],
  thresholds: {
    http_req_duration: ['p99 < 500'],   // 99% of requests < 500ms
    http_req_failed:   ['rate < 0.01'], // < 1% error rate
  },
};

export default function() {
  let res = http.post('https://api.pravah.io/v1/pipelines/test-pipeline/trigger',
    JSON.stringify({ parameters: { business_date: '2026-05-01' }}),
    { headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${TOKEN}` }}
  );

  check(res, {
    'status is 202':       (r) => r.status === 202,
    'has execution_id':    (r) => r.json('execution_id') !== undefined,
    'response time < 1s':  (r) => r.timings.duration < 1000,
  });
}
```

Run against a staging environment that mirrors production. The test uncovers bottlenecks under load before they affect real customers.
