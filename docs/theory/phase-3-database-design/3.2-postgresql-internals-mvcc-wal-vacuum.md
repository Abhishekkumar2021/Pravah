```text
🔄 MVCC — Multi-Version Concurrency Control
THE PROBLEM MVCC SOLVES
────────────────────────────────────────────────────────────
```

Traditional locking (naive approach):

  Reader wants to read job-xyz
  Writer wants to update job-xyz simultaneously

```text
  Option A: Reader waits for writer → HIGH LATENCY
  Option B: Writer waits for reader → LOW THROUGHPUT
  Option C: Both proceed → DATA CORRUPTION
```

  None of these are acceptable for Pravah.
  We need reads AND writes simultaneously
```sql
  with zero corruption and minimal waiting.
```

MVCC INSIGHT:
  Don't lock the row.
  Keep MULTIPLE VERSIONS of the row.
  Readers see the version appropriate for their transaction.
  Writers create new versions without blocking readers.

  "Readers never block writers.
   Writers never block readers."

  This is PostgreSQL's fundamental concurrency model.
How MVCC works — row versions:

TUPLE STRUCTURE IN POSTGRESQL

Every row (called a "tuple") has hidden system columns:

  xmin:   Transaction ID that CREATED this version
  xmax:   Transaction ID that DELETED/UPDATED this version
          (0 if still current/alive)
  ctid:   Physical location (page, offset) of this tuple

EXAMPLE: job-xyz lifecycle in execution_db

Transaction 100: INSERT job-xyz (status=PENDING)
```text
  ┌─────────────────────────────────────────────────────┐
  │ xmin=100 │ xmax=0 │ job_id=xyz │ status=PENDING    │
  └─────────────────────────────────────────────────────┘
  xmin=100: "created by transaction 100"
  xmax=0:   "not deleted, still alive"
```

Transaction 200: UPDATE job-xyz SET status=RUNNING
  PostgreSQL does NOT modify the existing row.
  It creates a NEW version:

```text
  ┌─────────────────────────────────────────────────────┐
  │ xmin=100 │ xmax=200 │ job_id=xyz │ status=PENDING  │ ← OLD
  └─────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────┐
  │ xmin=200 │ xmax=0   │ job_id=xyz │ status=RUNNING  │ ← NEW
  └─────────────────────────────────────────────────────┘
```
  
  Old row: xmax=200 means "deleted by transaction 200"
  New row: xmin=200, xmax=0 means "created by 200, still alive"

Transaction 300: UPDATE job-xyz SET status=COMPLETE
```text
  ┌─────────────────────────────────────────────────────┐
  │ xmin=100 │ xmax=200 │ job_id=xyz │ status=PENDING  │ ← DEAD
  └─────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────┐
  │ xmin=200 │ xmax=300 │ job_id=xyz │ status=RUNNING  │ ← DEAD
  └─────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────┐
  │ xmin=300 │ xmax=0   │ job_id=xyz │ status=COMPLETE │ ← LIVE
  └─────────────────────────────────────────────────────┘
What each transaction sees:
```

SNAPSHOT ISOLATION — WHO SEES WHAT

At the start of each transaction, PostgreSQL takes
a SNAPSHOT: "which transaction IDs are committed?"

Transaction 250 starts (between 200 and 300):
  Snapshot: {committed: [100, 200], in-progress: [250]}

  Reads job-xyz:
    Row xmin=100, xmax=200: "200 is committed AND < 250"
```text
                             → this row is DELETED for me
    Row xmin=200, xmax=0:   "200 is committed, xmax=0"
                             → this row is ALIVE for me
```
    
    Transaction 250 sees: status=RUNNING ✅
    (even if transaction 300 commits later,
     250 already took its snapshot)

SIMULTANEOUS READ + WRITE:

t=0: Transaction A starts (reads dashboard)
     Snapshot: {committed: [1..999]}

t=1: Transaction B: UPDATE jobs SET status=RUNNING WHERE id=xyz
```sql
     Creates new version (xmin=1000)
```

t=2: Transaction A reads jobs table
     Sees: version xmin=999 (PENDING) — B not in snapshot!
     Returns status=PENDING ✅ (consistent with its start)

t=3: Transaction B commits
t=4: Transaction A still running — still sees PENDING

t=5: Transaction C starts (new transaction)
     Snapshot: {committed: [1..1000]}
     Sees: version xmin=1000 (RUNNING) ✅

RESULT:
  Transaction A: no waiting, reads consistent snapshot ✅
  Transaction B: no waiting, writes new version ✅
  Zero blocking between reader and writer ✅
📝 WAL — Write-Ahead Log
WHAT IS THE WAL?

Before PostgreSQL writes ANYTHING to the actual
data files, it writes to the WAL first.

"Write-Ahead" = write to log BEFORE writing to data files.

WHY?
  Crash safety:
    If PostgreSQL crashes mid-write to data file:
      Data file = partially written = corrupted ❌
    
```sql
    With WAL:
      WAL written first (sequential, fast, durable)
      Data file written after (can be async, batched)
      If crash: replay WAL → data files reconstructed ✅
```

WAL STRUCTURE:

WAL is a sequence of RECORDS, each describing a change:

```yaml
  LSN: 0/1A2B3C00  ← Log Sequence Number (unique position)
  Type: HEAP_INSERT
  Relation: execution_db.public.jobs
  Block: 42  ← which 8KB page
  Offset: 15 ← position on that page
  Data: {xmin:1000, job_id:'xyz', status:'PENDING', ...}
```

  LSN: 0/1A2B3C50
  Type: HEAP_UPDATE
  Relation: execution_db.public.jobs
  Old tuple: (block:42, offset:15)
  New data: {xmin:1001, job_id:'xyz', status:'RUNNING', ...}

  LSN: 0/1A2B3C80
  Type: COMMIT
  Transaction: 1001
  Timestamp: 2024-01-15T10:00:05.123Z

WAL FILES ON DISK:
  /var/lib/postgresql/data/pg_wal/
```text
    000000010000000000000001  ← 16MB WAL segment
    000000010000000000000002
    000000010000000000000003
    ...
```
  
  Each file: 16MB (configurable)
```text
  Filled sequentially → old files recycled or archived
```

WAL IN PRAVAH'S CONTEXT:

1. CRASH RECOVERY:
   PostgreSQL restarts after crash:
```text
   → Finds last checkpoint position in WAL
   → Replays all WAL records after checkpoint
   → Data files brought to consistent state ✅
```

2. REPLICATION (Read Replicas):
   Standby PostgreSQL reads WAL from primary
```text
   → Replays WAL records → stays in sync
   This is how Pravah's read replicas work (3.5)
```

3. DEBEZIUM CDC:
   Debezium reads WAL as logical replication stream
```text
   → Publishes changes to Kafka (2.9)
   WAL is the source of truth for CDC ✅
```

4. PERFORMANCE INSIGHT:
   wal_buffers: WAL cached before fsync (default 16MB)
   synchronous_commit: when to fsync WAL to disk
```yaml
     on:      wait for WAL flush → safe, slower
     off:     don't wait → faster, slight data loss risk
     local:   wait for local WAL, not replica WAL
```

   Pravah config:
     Critical services (Pipeline, Execution):
       synchronous_commit = on (safety > speed)
     High-throughput services (Audit, Metrics):
       synchronous_commit = local (speed > replica sync)
♻️ Vacuum — The MVCC Cleanup Problem
THE DEAD TUPLE PROBLEM

Remember our job-xyz example:
```text
  After status → COMPLETE, we have 3 row versions:
  
  ┌───────────────────────────────────────────────────┐
  │ xmin=100 │ xmax=200 │ status=PENDING  │ ← DEAD   │
  └───────────────────────────────────────────────────┘
  ┌───────────────────────────────────────────────────┐
  │ xmin=200 │ xmax=300 │ status=RUNNING  │ ← DEAD   │
  └───────────────────────────────────────────────────┘
  ┌───────────────────────────────────────────────────┐
  │ xmin=300 │ xmax=0   │ status=COMPLETE │ ← LIVE   │
  └───────────────────────────────────────────────────┘
```

  Dead tuples still occupy disk space.
  PostgreSQL doesn't delete them immediately.
  (Some old transaction might still need them for snapshot)

  Pravah processes 10,000 jobs/minute.
  Each job: 3-5 status updates.
  Each update: 1 dead tuple.
  
  10,000 jobs × 4 updates = 40,000 dead tuples/minute!
  40,000 × 60 minutes = 2,400,000 dead tuples/hour!
  
  These dead tuples:
    ❌ Waste disk space
    ❌ Slow down sequential scans (must skip dead tuples)
    ❌ Cause table bloat (pages full of dead tuples)
    ❌ Eventually cause TRANSACTION ID WRAPAROUND 💀

TRANSACTION ID WRAPAROUND — THE MOST DANGEROUS PROBLEM:

Transaction IDs are 32-bit integers.
Maximum value: ~2.1 billion.

After 2.1 billion transactions:
  XID wraps around to 0.
  All past transactions suddenly appear "in the future."
  ALL data appears invisible! (xmin > current xid)
  DATABASE CANNOT BE READ. ❌❌❌

PostgreSQL prevents this with:
```sql
  VACUUM marks old tuples as "frozen" (visible to all)
  Frozen tuples don't count toward wraparound.
  But: VACUUM must run regularly to keep up.

  vacuum_freeze_max_age = 200,000,000 (200M transactions)
  PostgreSQL FORCES autovacuum when approaching this.
  At the limit: database goes into read-only mode.
```
  
  Pravah mitigation:
    Monitor: pg_stat_user_tables.n_dead_tup
    Monitor: age(relfrozenxid) per table
```sql
    Alert:   age > 150,000,000 → investigate
    Alert:   age > 180,000,000 → emergency
How VACUUM works:

VACUUM OPERATION
────────────────────────────────────────────────────────────
```

REGULAR VACUUM:
  1. Scans table pages
  2. Identifies dead tuples (xmax committed + no snapshot needs them)
  3. Marks dead tuple space as "free space" (FSM update)
  4. Does NOT return space to OS (file stays same size)
```text
  5. Updates Free Space Map (FSM) → future inserts use this space
  6. Updates Visibility Map (VM) → marks pages with all-live tuples
  7. Freezes old tuples (prevents XID wraparound)
```

  Effect: Space reused by new rows ✅
          Table file size: unchanged ⚠️

```sql
VACUUM FULL:
  1. Rewrites entire table to new file (compacts it)
  2. Returns space to OS
  3. Requires ACCESS EXCLUSIVE LOCK (blocks all queries!) ❌
  4. Takes hours on large tables
```

  Effect: Table size shrinks ✅
          Blocks ALL operations during run ❌
          
  Pravah policy: NEVER run VACUUM FULL on production.
                 Use pg_repack instead (online compaction).

AUTOVACUUM — THE AUTOMATIC SOLUTION:

PostgreSQL runs autovacuum daemon automatically.
Triggers when dead tuple threshold exceeded:

  autovacuum_vacuum_threshold = 50          (base threshold)
  autovacuum_vacuum_scale_factor = 0.2      (20% of table)
  
  Trigger: dead_tuples > 50 + (0.2 × total_rows)

  jobs table with 100,000 rows:
    Trigger: 50 + (0.2 × 100,000) = 20,050 dead tuples
    Autovacuum fires when dead tuples > 20,050 ✅

PRAVAH AUTOVACUUM TUNING:

Jobs table (very high churn — 10K updates/minute):
  Standard autovacuum too slow! Triggers too late!

  Per-table override:
```sql
  ALTER TABLE jobs SET (
    autovacuum_vacuum_scale_factor = 0.01,  ← trigger at 1%
    autovacuum_vacuum_threshold    = 100,   ← lower base
    autovacuum_vacuum_cost_delay   = 2ms    ← run faster
  );
```

  Result: Autovacuum triggers at 1% dead tuples
```text
          (not 20%) → dead tuples cleaned rapidly ✅
```

Events table (append-only — never updated):
  Standard autovacuum is FINE.
  No updates = no dead tuples from updates.
  Only XID freezing needed.

```sql
  ALTER TABLE events SET (
    autovacuum_freeze_max_age = 150000000,  ← freeze earlier
    autovacuum_vacuum_scale_factor = 0.5    ← trigger late (ok)
  );
```

BLOAT MONITORING IN PRAVAH:
```text
────────────────────────────────────────────────────────────

  SELECT
    schemaname,
    tablename,
    n_dead_tup,
    n_live_tup,
    round(n_dead_tup::numeric / 
          NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2)
      AS dead_pct,
    last_autovacuum,
    last_autoanalyze
  FROM pg_stat_user_tables
  ORDER BY n_dead_tup DESC;

  Alert: dead_pct > 10% → autovacuum not keeping up
  Alert: last_autovacuum > 1 hour ago for hot tables
🔍 ANALYZE — Keeping Statistics Fresh
WHAT IS ANALYZE?
────────────────────────────────────────────────────────────
```

PostgreSQL's query planner makes decisions based on
STATISTICS about table data:
  - Number of rows
  - Value distribution (most common values)
  - Histogram of data ranges
  - Correlation (how sorted is the data?)

These statistics live in: pg_statistic

```sql
ANALYZE collects these statistics by sampling the table.
```

WHY IT MATTERS FOR PRAVAH:

jobs table: 10 million rows
  99% of jobs: status = 'COMPLETE'
  1% of jobs:  status = 'RUNNING' (about 100,000 rows)

Query: SELECT * FROM jobs WHERE status = 'RUNNING'

```sql
With FRESH statistics:
  Planner knows: 1% of rows match
  Planner chooses: INDEX SCAN on status index ✅
  Result: reads only 100,000 rows, fast ✅

With STALE statistics (table was empty when analyzed):
  Planner thinks: 50% of rows might match (default)
  Planner chooses: SEQUENTIAL SCAN (why use index for 50%?)
  Result: reads 10,000,000 rows, very slow ❌

ANALYZE is run automatically by autovacuum.
Same trigger threshold as VACUUM.
Pravah tunes it per table same way. ✅
```

PRACTICAL PRAVAH SCENARIO:

New deployment: pipeline_runs table starts empty.
```sql
ANALYZE runs: statistics = "0 rows"
```

After 1 hour: 50,000 rows inserted.
Autovacuum hasn't run ANALYZE yet.
Statistics: still shows ~0 rows.

Dashboard query:
```sql
  SELECT * FROM pipeline_runs
  WHERE tenant_id = 'megacorp'
  AND status = 'FAILED'
  ORDER BY started_at DESC
  LIMIT 20
```

Planner: "0 rows, no stats, just seq scan"
```text
Actual: 50,000 rows → seq scan → 3 seconds ❌
```

After autovacuum runs ANALYZE:
  Statistics: 50,000 rows, tenant_id distribution known
  Planner: INDEX SCAN on (tenant_id, status, started_at)
  Query: 20ms ✅

LESSON: After bulk loads or major data changes:
  Run ANALYZE manually before expecting good plans.
```sql
  ANALYZE jobs; ← runs in seconds, safe on production
🔗 Putting It Together — Pravah's PostgreSQL Architecture
HOW MVCC + WAL + VACUUM INTERACT
────────────────────────────────────────────────────────────
```

WRITE PATH (job status update):

  Application:
```text
    UPDATE jobs SET status='RUNNING' WHERE id='xyz'
                          │
                          ▼
  WAL buffer:
    Write WAL record (HEAP_UPDATE) to wal_buffers
    (in-memory, not yet on disk)
                          │
                          ▼
  Shared buffers:
    Create new tuple version in shared_buffers (8KB pages)
    Mark old tuple with xmax (dead but not removed)
    (in-memory, not yet on disk)
                          │
                          ▼
  On COMMIT:
    WAL record fsynced to disk (synchronous_commit=on)
    → Transaction durably committed ✅
    Shared buffers: dirty pages written to disk LATER
    (background writer flushes periodically)
                          │
                          ▼
  Old tuple remains in shared buffers + data file.
  Visible to no future transaction (xmax committed).
  Waiting for VACUUM to reclaim its space.
```

READ PATH (dashboard query):

  Application:
```text
    SELECT * FROM jobs WHERE tenant_id='megacorp'
                          │
                          ▼
  Query planner:
    Checks pg_statistic for tenant_id distribution
    Estimates rows → chooses index scan
                          │
                          ▼
  Buffer manager:
    Check shared_buffers for needed 8KB pages
    Cache hit → serve directly (no disk I/O) ✅
    Cache miss → read from data file → into shared_buffers
                          │
                          ▼
  MVCC visibility check:
    For each tuple: is xmin committed before my snapshot?
                    is xmax not committed OR after my snapshot?
    Visible tuples → return to application
    Dead tuples → skip (but still read from disk!) ⚠️
```

```text
🎯 FAANG Interview Angles
❓ "Explain MVCC and why PostgreSQL uses it
    instead of traditional locking."
```

Good answer:
  "MVCC solves the fundamental tension between
   concurrent readers and writers. Traditional
   locking forces one to wait for the other —
   either readers block writers or writers block
   readers, killing throughput.

   MVCC keeps multiple versions of each row using
   hidden system columns: xmin (which transaction
```sql
   created this version) and xmax (which transaction
   deleted it). When a row is updated, PostgreSQL
   creates a NEW version rather than modifying the
   existing one. The old version stays with xmax
   set to the updating transaction.
```

   Each transaction takes a snapshot at start time —
   a record of which transaction IDs are committed.
   When reading a row, it checks: is xmin committed
   in my snapshot AND is xmax either zero or not
```sql
   committed in my snapshot? If yes, this version
   is visible to me.
```

   In Pravah, this means our dashboard reads and
   job status updates happen completely independently.
   Execution Service updates job status — creates
```java
   new row versions. Scheduler Service reads jobs
   — sees consistent snapshot from its start time.
   Zero blocking between them."
```

❓ "What is table bloat in PostgreSQL and how
    does Pravah handle it?"

Good answer:
  "Table bloat is the accumulation of dead tuples —
   old row versions left behind by MVCC after updates
   and deletes. PostgreSQL doesn't immediately remove
   them because some long-running transaction might
   still need them for snapshot isolation.

   Pravah's jobs table is especially vulnerable —
   10,000 jobs per minute, each with 3-5 status
```sql
   updates, generates 40,000+ dead tuples per minute.
   Without aggressive vacuuming, the table bloats
   with dead tuples that slow sequential scans and
   waste disk space.
```

   We handle this with per-table autovacuum tuning.
   For the jobs table we set autovacuum_vacuum_scale
   _factor=0.01 — trigger at 1% dead tuples instead
   of the default 20%. We also set a lower cost delay
   so autovacuum runs faster. We monitor dead tuple
   percentage via pg_stat_user_tables and alert when
   it exceeds 10%, which means autovacuum isn't
   keeping up and we need to investigate."

❓ "How does PostgreSQL's WAL relate to Pravah's
    Debezium CDC setup?"

Good answer:
  "The WAL is the foundation of our entire CDC
   pipeline. Every change in PostgreSQL — inserts,
```sql
   updates, deletes — is recorded in the WAL before
   being applied to data files. The WAL is how
   PostgreSQL achieves crash safety and powers
   streaming replication to standby databases.
```

   Debezium connects to PostgreSQL as a logical
   replication client — the same mechanism used
   by standby databases. We set wal_level=logical
   which makes PostgreSQL include enough information
   in WAL records to reconstruct full row changes
   (not just physical byte differences). Debezium
```sql
   creates a replication slot which instructs
   PostgreSQL to retain WAL segments until Debezium
   confirms it has processed them.
```

   This gives us millisecond-latency change capture
```sql
   with zero impact on the source database —
   Debezium reading the WAL is as cheap as a
   standby database replicating from primary."
```

## 📌 Key Takeaways

1. MVCC: multiple row versions, not locking
   xmin = created by, xmax = deleted by
```text
   Readers take snapshot → see consistent state
   Writers create new versions → never block readers
   "Readers never block writers, writers never block readers"
```

2. UPDATE in PostgreSQL = INSERT new version + mark old dead
   Old versions accumulate as dead tuples
   Dead tuples waste space and slow scans

3. WAL: write log before data files
```yaml
   Crash safety: replay WAL → reconstruct data
   Replication: standby reads WAL → stays in sync
   CDC: Debezium reads logical WAL → Kafka events
   wal_level=logical required for Debezium
```

4. VACUUM: reclaims dead tuple space
   Regular: marks space free (file size unchanged)
```sql
   VACUUM FULL: compacts file (blocks all queries!) Never in prod
   XID wraparound: VACUUM freezes old tuples → prevents it
   Alert at age > 150M transactions
```

5. AUTOVACUUM: automatic vacuum daemon
   Triggers at: threshold + scale_factor × total_rows
   Pravah jobs table: 1% threshold (vs 20% default)
   Monitor: pg_stat_user_tables.n_dead_tup

6. ANALYZE: updates query planner statistics
```text
   Stale stats → wrong execution plan → slow queries
   Run manually after bulk loads
   Autovacuum runs it automatically
```

7. Pravah configuration priorities:
   shared_buffers = 25% RAM (cache hot pages)
   wal_level = logical (CDC requirement)
   autovacuum tuned per table (high churn tables)
   statement_timeout = 30s (prevent runaway queries)

8. Synchronous commit tuning:
   Critical services: synchronous_commit=on (safe)
   High throughput: synchronous_commit=local (fast)
