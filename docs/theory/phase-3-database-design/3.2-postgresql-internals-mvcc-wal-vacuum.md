# 3.2 PostgreSQL Internals: MVCC, WAL & Vacuum

## Why PostgreSQL Internals Matter for Pravah

Pravah's `execution_db` handles 10,000+ job inserts per minute at peak, constant status updates (PENDING → RUNNING → COMPLETE), heavy concurrent reads from dashboard queries, and long-running analytical queries for SLA reports.

Without understanding PostgreSQL internals:
- You write queries that cause table bloat
- You create indexes that slow writes
- You miss why autovacuum is killing performance
- You cannot explain why read replicas lag
- You design schemas that cause lock contention

With internals knowledge, you predict problems before they happen, tune PostgreSQL correctly for Pravah's workload, and can explain WAL-based CDC with precision.

## MVCC — Multi-Version Concurrency Control

### The Problem MVCC Solves

Traditional locking creates a fundamental dilemma when a reader and writer access the same row simultaneously:

- Option A: Reader waits for writer → high latency
- Option B: Writer waits for reader → low throughput
- Option C: Both proceed without coordination → data corruption

None of these are acceptable for Pravah. The system needs reads and writes simultaneously with zero corruption and minimal waiting.

**MVCC's insight:** don't lock the row. Keep multiple versions of the row. Readers see the version appropriate for their transaction. Writers create new versions without blocking readers.

> "Readers never block writers. Writers never block readers."

This is PostgreSQL's fundamental concurrency model.

---

### How MVCC Works — Row Versions

Every row (called a "tuple") has hidden system columns:

- `xmin`: transaction ID that created this version
- `xmax`: transaction ID that deleted or updated this version (0 if still alive)
- `ctid`: physical location (page, offset) of this tuple

**Example: `job-xyz` lifecycle in `execution_db`**

Transaction 100 inserts `job-xyz` with status PENDING:

```
┌─────────────────────────────────────────────────────┐
│ xmin=100 │ xmax=0   │ job_id=xyz │ status=PENDING   │
└─────────────────────────────────────────────────────┘
```

Transaction 200 updates `job-xyz` to RUNNING. PostgreSQL does not modify the existing row — it creates a new version:

```
┌─────────────────────────────────────────────────────┐
│ xmin=100 │ xmax=200 │ job_id=xyz │ status=PENDING   │  ← OLD (dead)
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ xmin=200 │ xmax=0   │ job_id=xyz │ status=RUNNING   │  ← NEW (live)
└─────────────────────────────────────────────────────┘
```

Transaction 300 updates to COMPLETE:

```
┌─────────────────────────────────────────────────────┐
│ xmin=100 │ xmax=200 │ job_id=xyz │ status=PENDING   │  ← DEAD
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ xmin=200 │ xmax=300 │ job_id=xyz │ status=RUNNING   │  ← DEAD
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ xmin=300 │ xmax=0   │ job_id=xyz │ status=COMPLETE  │  ← LIVE
└─────────────────────────────────────────────────────┘
```

---

### Snapshot Isolation — Who Sees What

At the start of each transaction, PostgreSQL takes a **snapshot**: a record of which transaction IDs are committed.

Transaction 250 starts between transactions 200 and 300. Its snapshot: `{committed: [100, 200], in-progress: [250]}`.

When it reads `job-xyz`:
- Row `xmin=100, xmax=200`: xmax=200 is committed and less than 250 → this row is deleted for transaction 250
- Row `xmin=200, xmax=0`: xmin=200 is committed, xmax=0 → this row is alive for transaction 250

Transaction 250 sees `status=RUNNING`, even if transaction 300 commits later — it already took its snapshot.

**Simultaneous read and write:**

```
t=0: Transaction A starts (reads dashboard)
     Snapshot: {committed: [1..999]}

t=1: Transaction B: UPDATE jobs SET status=RUNNING WHERE id=xyz
     Creates new version (xmin=1000)

t=2: Transaction A reads jobs table
     Sees version xmin=999 (PENDING) — transaction 1000 not in snapshot
     Returns status=PENDING ✅ (consistent with its start time)

t=3: Transaction B commits

t=4: Transaction A still running — still sees PENDING

t=5: Transaction C starts (new transaction)
     Snapshot: {committed: [1..1000]}
     Sees version xmin=1000 (RUNNING) ✅
```

Transaction A reads without waiting. Transaction B writes without waiting. Zero blocking between reader and writer.

## WAL — Write-Ahead Log

### What Is the WAL?

Before PostgreSQL writes anything to actual data files, it writes to the WAL first.

"Write-Ahead" means: write to log *before* writing to data files.

**Why crash safety requires this:**

If PostgreSQL crashes mid-write to a data file, the data file is partially written and corrupted. With WAL: the WAL is written first (sequential, fast, durable), then data files are written after (can be async, batched). On crash, PostgreSQL replays WAL records from the last checkpoint to reconstruct data files.

### WAL Structure

WAL is a sequence of records, each describing a change:

```
LSN: 0/1A2B3C00    ← Log Sequence Number (unique position)
Type: HEAP_INSERT
Relation: execution_db.public.jobs
Block: 42          ← which 8KB page
Offset: 15         ← position on that page
Data: {xmin:1000, job_id:'xyz', status:'PENDING', ...}

LSN: 0/1A2B3C50
Type: HEAP_UPDATE
Relation: execution_db.public.jobs
Old tuple: (block:42, offset:15)
New data: {xmin:1001, job_id:'xyz', status:'RUNNING', ...}

LSN: 0/1A2B3C80
Type: COMMIT
Transaction: 1001
Timestamp: 2024-01-15T10:00:05.123Z
```

WAL files live in `/var/lib/postgresql/data/pg_wal/`. Each segment is 16MB (configurable). Segments are filled sequentially and then recycled or archived.

### WAL in Pravah's Context

**Crash recovery:** PostgreSQL restarts after a crash, finds the last checkpoint position in WAL, replays all records after the checkpoint, and brings data files to a consistent state.

**Replication (read replicas):** Standby PostgreSQL continuously reads WAL from the primary and replays records to stay in sync. This is how Pravah's read replicas work.

**Debezium CDC:** Debezium reads WAL as a logical replication stream and publishes changes to Kafka. WAL is the source of truth for all CDC pipelines. `wal_level = logical` is required for this.

**Synchronous commit configuration:**

- `on`: wait for WAL flush before acknowledging commit → safe, slightly slower
- `off`: do not wait → faster, small risk of losing last few transactions on crash
- `local`: wait for local WAL flush, not replica → middle ground

Pravah's approach:
- Critical services (Pipeline, Execution): `synchronous_commit = on` — safety over speed
- High-throughput services (Audit, Metrics): `synchronous_commit = local` — speed over replica sync

## Vacuum — The MVCC Cleanup Problem

### The Dead Tuple Problem

After `job-xyz` reaches COMPLETE status, three row versions exist physically on disk. Dead tuples do not disappear automatically — PostgreSQL cannot remove them immediately because a long-running transaction might still need them for snapshot isolation.

Consider Pravah's workload:
- 10,000 jobs per minute
- Each job: 3–5 status updates
- Each update: 1 dead tuple
- Result: 30,000–50,000 dead tuples per minute

Dead tuples:
- Waste disk space
- Slow sequential scans (must physically read and skip dead tuples)
- Cause table bloat (pages full of dead rows)
- Eventually cause transaction ID wraparound — the most dangerous failure mode

### Transaction ID Wraparound

Transaction IDs are 32-bit integers. The maximum value is approximately 2.1 billion. After 2.1 billion transactions, XIDs wrap around to zero. All past transactions suddenly appear to be "in the future." All data becomes invisible. The database cannot be read.

PostgreSQL prevents this by *freezing* old tuples — marking them as visible to all transactions regardless of XID. VACUUM performs this freezing. If VACUUM does not run regularly enough to keep up, PostgreSQL forces autovacuum as the age approaches the limit. At the absolute limit, the database enters read-only mode.

Pravah monitors this with:
```sql
SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY xid_age DESC;
```

Alert thresholds:
- age > 150,000,000 → investigate
- age > 180,000,000 → emergency

---

### How VACUUM Works

**Regular VACUUM:**
1. Scans table pages
2. Identifies dead tuples whose XID is old enough that no active snapshot needs them
3. Marks dead tuple space as free in the Free Space Map (FSM)
4. Updates the Visibility Map — marks pages where all tuples are visible to all transactions
5. Freezes old tuples to prevent XID wraparound
6. Does not shrink the physical file — space is reused by future inserts

**VACUUM FULL:**
1. Rewrites the entire table to a new file (compacts it)
2. Returns freed space to the OS
3. Requires `ACCESS EXCLUSIVE LOCK` — blocks all queries on the table
4. Can take hours on large tables

Pravah's policy: never run `VACUUM FULL` on production tables. Use `pg_repack` instead, which performs online compaction without taking an exclusive lock.

### Autovacuum — The Automatic Solution

PostgreSQL runs an autovacuum daemon that triggers automatically when dead tuples exceed a threshold:

```
trigger: dead_tuples > autovacuum_vacuum_threshold + (autovacuum_vacuum_scale_factor × total_rows)
default: dead_tuples > 50 + (0.2 × total_rows)
```

For the `jobs` table with 100,000 rows: autovacuum fires when dead tuples exceed 20,050.

**Pravah's per-table autovacuum tuning:**

The `jobs` table has very high churn — 10,000 updates per minute. The default 20% threshold means autovacuum triggers too late and falls behind.

```sql
ALTER TABLE jobs SET (
    autovacuum_vacuum_scale_factor = 0.01,  -- trigger at 1% dead tuples
    autovacuum_vacuum_threshold    = 100,   -- lower base threshold
    autovacuum_vacuum_cost_delay   = 2      -- run faster (ms)
);
```

Result: autovacuum triggers at 1% dead tuples instead of 20%, preventing bloat accumulation.

The `events` table is append-only — no updates, no dead tuples from updates. Standard autovacuum is fine. The concern is only XID freezing:

```sql
ALTER TABLE events SET (
    autovacuum_freeze_max_age    = 150000000, -- freeze earlier
    autovacuum_vacuum_scale_factor = 0.5      -- trigger late (acceptable)
);
```

### Monitoring Bloat in Pravah

```sql
SELECT
    schemaname,
    tablename,
    n_dead_tup,
    n_live_tup,
    round(n_dead_tup::numeric /
          NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_pct,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Alert: `dead_pct > 10%` → autovacuum is not keeping up; `last_autovacuum > 1 hour ago` on hot tables → investigate.

## ANALYZE — Keeping Statistics Fresh

### What Is ANALYZE?

PostgreSQL's query planner makes decisions based on statistics about table data: row counts, value distributions, histograms of data ranges, and column correlation. These statistics live in `pg_statistic`. `ANALYZE` collects them by sampling the table.

### Why Stale Statistics Cause Disasters

The `jobs` table has 10 million rows: 99% `COMPLETE`, 1% `RUNNING` (about 100,000 rows).

Query: `SELECT * FROM jobs WHERE status = 'RUNNING'`

**With fresh statistics:** the planner knows 1% of rows match → chooses index scan → reads only 100,000 rows → 20ms.

**With stale statistics (table was empty when last analyzed):** the planner guesses 50% of rows might match → chooses sequential scan (index not worth it for 50%) → reads 10,000,000 rows → minutes.

`ANALYZE` runs automatically alongside autovacuum at the same trigger threshold. Pravah tunes it per table the same way.

**Critical scenario:** after a new deployment, a table starts empty. ANALYZE runs and records "zero rows". After one hour, 50,000 rows have been inserted. Autovacuum has not yet re-run ANALYZE. The planner still plans for zero rows and chooses a sequential scan.

Resolution: run `ANALYZE jobs;` manually after bulk loads or major data changes. It completes in seconds and is safe on production.

## How MVCC, WAL, and Vacuum Interact

**Write path for a job status update:**

```
Application: UPDATE jobs SET status='RUNNING' WHERE id='xyz'
      │
      ▼
WAL buffer: write HEAP_UPDATE record to wal_buffers (in-memory)
      │
      ▼
Shared buffers: create new tuple version (old tuple gets xmax set)
      │
      ▼
On COMMIT: WAL record fsynced to disk (synchronous_commit=on)
           → Transaction durably committed ✅
           Shared buffers: dirty pages written to disk later
                           (background writer flushes periodically)
      │
      ▼
Old tuple: physically present, xmax committed, invisible to new transactions
           Waiting for VACUUM to reclaim its space
```

**Read path for a dashboard query:**

```
Application: SELECT * FROM jobs WHERE tenant_id='megacorp'
      │
      ▼
Query planner: checks pg_statistic → estimates rows → chooses index scan
      │
      ▼
Buffer manager: check shared_buffers for needed 8KB pages
                cache hit → serve directly (no disk I/O)
                cache miss → read from data file → cache in shared_buffers
      │
      ▼
MVCC visibility check: for each tuple:
    is xmin committed before my snapshot?
    is xmax zero OR not committed in my snapshot?
    → visible: return to application
    → dead: skip (but still physically read from disk — bloat penalty)
```

## Key PostgreSQL Configuration for Pravah

```ini
# Memory
shared_buffers            = 8GB     # 25% of 32GB RAM
effective_cache_size      = 24GB    # hints to planner about OS cache
work_mem                  = 64MB    # per sort/hash operation
maintenance_work_mem      = 2GB     # for VACUUM, CREATE INDEX

# WAL
wal_buffers               = 64MB    # WAL in-memory before flush
wal_level                 = logical # required for Debezium CDC
max_wal_size              = 4GB     # before checkpoint is forced
min_wal_size              = 1GB     # keep at least this much WAL on disk
checkpoint_completion_target = 0.9  # spread checkpoint I/O over 90% of interval

# Autovacuum
autovacuum_max_workers    = 6       # more workers for high churn
autovacuum_vacuum_cost_delay = 2    # vacuum faster (ms)
autovacuum_analyze_scale_factor = 0.05  # analyze at 5% change

# Replication
max_replication_slots     = 10      # Debezium replication slots
max_wal_senders           = 10      # standby connections

# Timeouts
statement_timeout         = 30000   # 30s max query time
lock_timeout              = 5000    # 5s max lock wait
idle_in_transaction_timeout = 60000 # 60s max idle transaction
```

## FAANG Interview Angles

**"Explain MVCC and why PostgreSQL uses it instead of traditional locking."**

> MVCC solves the fundamental tension between concurrent readers and writers. Traditional locking forces one to wait for the other — readers block writers or writers block readers, killing throughput.
>
> MVCC keeps multiple versions of each row using hidden system columns: `xmin` records which transaction created this version, `xmax` records which transaction deleted it. When a row is updated, PostgreSQL creates a new version rather than modifying the existing one. The old version stays with `xmax` set to the updating transaction.
>
> Each transaction takes a snapshot at start time — a record of which transaction IDs are committed. When reading a row, it checks: is `xmin` committed in my snapshot AND is `xmax` either zero or not committed in my snapshot? If yes, this version is visible.
>
> In Pravah, dashboard reads and job status updates happen completely independently. Execution Service updates job status — creates new row versions. Scheduler Service reads jobs — sees the consistent snapshot from its start time. Zero blocking between them.

**"What is table bloat in PostgreSQL and how does Pravah handle it?"**

> Table bloat is the accumulation of dead tuples — old row versions left behind by MVCC after updates and deletes. PostgreSQL cannot immediately remove them because some long-running transaction might still need them for snapshot isolation.
>
> Pravah's `jobs` table is especially vulnerable — 10,000 jobs per minute each with 3–5 status updates generates 40,000+ dead tuples per minute. Without aggressive vacuuming, the table bloats, slowing sequential scans and wasting disk.
>
> We handle this with per-table autovacuum tuning. For the `jobs` table we set `autovacuum_vacuum_scale_factor = 0.01` — trigger at 1% dead tuples instead of the default 20%. We set a lower cost delay so autovacuum runs faster. We monitor dead tuple percentage via `pg_stat_user_tables` and alert when it exceeds 10%.

**"How does PostgreSQL's WAL relate to Pravah's Debezium CDC setup?"**

> The WAL is the foundation of our entire CDC pipeline. Every change in PostgreSQL — inserts, updates, deletes — is recorded in the WAL before being applied to data files. The WAL is how PostgreSQL achieves crash safety and powers streaming replication to standby databases.
>
> Debezium connects to PostgreSQL as a logical replication client — the same mechanism used by standby databases. We set `wal_level = logical`, which makes PostgreSQL include enough information in WAL records to reconstruct full row changes, not just physical byte differences. Debezium creates a replication slot, which instructs PostgreSQL to retain WAL segments until Debezium confirms it has processed them.
>
> This gives millisecond-latency change capture with negligible impact on the source database. Reading the WAL costs roughly the same as a standby replica replicating from the primary.

## Key Takeaways

1. **MVCC:** multiple row versions, not locking. `xmin` = created by, `xmax` = deleted by. Readers take a snapshot and see a consistent state. Writers create new versions without blocking readers.

2. **UPDATE = INSERT new version + mark old dead.** Old versions accumulate as dead tuples, wasting space and slowing scans.

3. **WAL:** write log before data files. Crash safety via WAL replay. Streaming replication via WAL. Debezium CDC via logical WAL. `wal_level = logical` required.

4. **VACUUM:** reclaims dead tuple space. Regular VACUUM marks space free but does not shrink the file. VACUUM FULL compacts but takes exclusive lock — never run on production. XID wraparound prevention requires regular freezing.

5. **Autovacuum:** automatic vacuum daemon triggered by dead tuple thresholds. Pravah's `jobs` table uses 1% threshold (vs default 20%) to prevent bloat on a high-churn table.

6. **ANALYZE:** updates query planner statistics. Stale statistics cause catastrophically wrong execution plans. Run manually after bulk loads.

7. **Configuration priorities:** `shared_buffers = 25% RAM`, `wal_level = logical`, per-table autovacuum tuning, `statement_timeout = 30s`.
