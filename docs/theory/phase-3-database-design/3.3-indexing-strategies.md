# 3.3 Indexing Strategies for Pravah's Tables

## Why Indexing Is a Critical Design Decision

The stakes at Pravah's scale are concrete. The `jobs` table has 50 million rows representing one year of data. A query like "show me all failed jobs for tenant megacorp in the last 24 hours" produces wildly different results depending on the index:

- **No index:** PostgreSQL reads all 50 million rows. Time: 45 seconds. The dashboard shows a loading spinner indefinitely.
- **Wrong index** (on `status` alone): PostgreSQL finds all 5 million failed rows, then filters tenant and time across those. Time: 8 seconds. Still unacceptable.
- **Right index** (composite on `tenant_id, status, created_at`): PostgreSQL jumps directly to megacorp's failed rows in the last 24 hours. Time: 2ms. The dashboard is instant.

Index choice is not optimization — it is the difference between a working product and a broken one.

---

## Index Types in PostgreSQL

PostgreSQL supports six index types. Pravah uses three: B-tree, GIN, and BRIN.

| Index Type | What It Does | Best For |
|---|---|---|
| **B-tree** | Sorted balanced tree. Equality + range queries. | 90% of use cases |
| **Hash** | Hash table. Equality only, slightly faster than B-tree for pure equality. | Rare — usually B-tree wins |
| **GIN** | Generalized Inverted Index. Indexes composite values. | JSONB, arrays, full-text search |
| **BRIN** | Block Range Index. Tiny index storing min/max per block range. | Append-only time-series data |
| **GiST** | Generalized Search Tree for geometric/range types. | PostGIS geometry, range overlap |
| **SP-GiST** | Space-partitioned GiST for non-balanced distributions. | Specialized use cases |

## B-Tree Index — The Workhorse

### How B-Tree Works Internally

A B-tree is a balanced tree where all leaf nodes sit at the same depth. For an index on `jobs.status`:

```
                      ROOT
                    [RUNNING]
                   /          \
            [FAILED]          [SUCCESS]
            /      \           /      \
        [F..][F..]  [F..][F..]  [S..][S..][S..]
        (leaf)       (leaf)       (leaf)
```

Each leaf node contains `[status value] → [list of ctids: page 42 offset 7, page 42 offset 8, ...]` — physical row locations.

### What B-Tree Can and Cannot Do

```
Equality:   WHERE status = 'FAILED'
            → B-tree search: O(log n) ✅

Range:      WHERE created_at BETWEEN t1 AND t2
            → Find t1 in tree, scan leaves forward ✅

Prefix:     WHERE pipeline_name LIKE 'sales%'
            → Works — prefix is a range query on strings ✅

Suffix:     WHERE pipeline_name LIKE '%etl'
            → Does NOT use index ❌ — no defined start point

NULL:       WHERE status IS NULL
            → B-tree includes NULL values ✅

ORDER BY:   ORDER BY created_at DESC
            → B-tree already sorted, no sort step needed ✅
              (only when index matches ORDER BY direction)

NOT EQUAL:  WHERE status != 'RUNNING'
            → Usually sequential scan — most rows match,
              so the index offers no benefit
```

## Composite Indexes — The Most Important Concept

### The Leftmost Prefix Rule

A composite index on `(col_a, col_b, col_c)` is sorted first by `col_a`, then by `col_b` within each `col_a` value, then by `col_c` within each `col_b` value.

This means the index serves queries that match columns from the left:
- `col_a` alone: works
- `col_a + col_b`: works
- `col_a + col_b + col_c`: works (optimal)
- `col_b` alone: does not work — values are scattered across all `col_a` sections
- `col_c` alone: does not work
- `col_b + col_c`: does not work

**Example: Index on `(tenant_id, status, created_at)`**

Data sorted in the index:

```
megacorp | FAILED   | 2024-01-14T09:00  → ctid(42,7)
megacorp | FAILED   | 2024-01-14T10:00  → ctid(42,8)
megacorp | FAILED   | 2024-01-15T09:00  → ctid(43,2)
megacorp | RUNNING  | 2024-01-15T10:00  → ctid(44,1)
megacorp | SUCCESS  | 2024-01-14T08:00  → ctid(45,3)
techgiant| FAILED   | 2024-01-15T11:00  → ctid(46,2)
techgiant| RUNNING  | 2024-01-15T12:00  → ctid(47,1)
```

Queries this index serves:

```sql
-- ✅ Leftmost prefix: tenant_id
WHERE tenant_id = 'megacorp'

-- ✅ Leftmost prefix: tenant_id + status
WHERE tenant_id = 'megacorp' AND status = 'FAILED'

-- ✅ Full composite index
WHERE tenant_id = 'megacorp'
  AND status = 'FAILED'
  AND created_at > '2024-01-14'

-- ❌ Missing leftmost column: tenant_id
WHERE status = 'FAILED'
-- → Sequential scan or a separate index needed

-- ❌ Missing leftmost two columns
WHERE created_at > '2024-01-14'
-- → Different index needed
```

### Column Ordering Rules

1. **Equality conditions first** — `tenant_id = 'X'`
2. **Range conditions last** — `created_at > X`
3. **Higher cardinality before lower cardinality** — `tenant_id` (1,000 distinct values) before `status` (5 distinct values)

The reason: the index seeks to the first matching `tenant_id`, immediately eliminating 999 out of 1,000 tenants. Within that section, it seeks to the matching `status`, eliminating 4 out of 5 status values. Then it range-scans `created_at`. The result is a tiny set of rows read.

If columns were ordered `(status, tenant_id, created_at)`, filtering by `status = 'FAILED'` narrows to 20% of all rows across all tenants. Then `tenant_id` is applied within that 20%. Much less effective.

## Partial Indexes — Index Only What You Query

A partial index includes only rows matching a `WHERE` condition. Smaller index means faster queries, less disk, and lower write overhead.

**Example: The `jobs` table**

```
Total rows:  50 million
COMPLETE:    49 million (98%)
RUNNING:       500,000  (1%)
FAILED:        400,000  (0.8%)
PENDING:       100,000  (0.2%)
```

Dashboard queries focus almost entirely on RUNNING, FAILED, and PENDING jobs. Nobody monitors COMPLETE jobs in real time — those go to historical reports.

- Full index on `status`: indexes 50 million rows
- Partial index `WHERE status IN ('PENDING', 'RUNNING', 'FAILED')`: indexes 1 million rows

Result: 98% smaller index, 98% less write overhead, identical query performance for live monitoring.

### Pravah's Partial Index Examples

```sql
-- Only active runners (most runner queries filter on status='ACTIVE')
CREATE INDEX idx_runners_active
ON runners (tenant_id, tags, last_heartbeat)
WHERE status = 'ACTIVE';

-- Only pending outbox messages (the relay's hot query)
CREATE INDEX idx_outbox_pending
ON outbox (created_at)
WHERE status = 'PENDING';
-- The relay runs: SELECT ... FROM outbox WHERE status = 'PENDING'
--                 ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100
-- This partial index is tiny and serves the most critical query.

-- Only live jobs (dashboard monitoring)
CREATE INDEX idx_jobs_live
ON jobs (tenant_id, status, created_at)
WHERE status IN ('PENDING', 'RUNNING', 'FAILED');
```

## Covering Indexes — Avoid Table Lookups

### The Heap Fetch Problem

A normal index lookup has two steps:
1. Search index → find `ctid` (page 42, offset 7)
2. Go to page 42 in the table → read the row → extract needed columns

Step 2 is a "heap fetch" — random I/O against the table data file. For large result sets, this dominates query time.

An index-only scan eliminates step 2 by storing the needed columns directly in the index leaf nodes. The query never touches the table.

### Covering Indexes with INCLUDE

PostgreSQL 11+ supports the `INCLUDE` clause: extra columns stored in index leaf nodes, not part of the sort key.

```sql
-- Without covering index:
-- Index finds ctids → heap fetch for duration_ms, pipeline_id per row
SELECT job_id, status, duration_ms, pipeline_id
FROM jobs
WHERE tenant_id = 'megacorp'
  AND created_at > NOW() - INTERVAL '1 hour';

-- With covering index:
CREATE INDEX idx_jobs_dashboard
ON jobs (tenant_id, created_at DESC)
INCLUDE (job_id, status, duration_ms, pipeline_id);
```

The index leaf node now contains:
```
(megacorp, 2024-01-15T10:00) → {job_id:'xyz', status:'COMPLETE',
                                  duration_ms:45000, pipeline_id:'abc'}
```

Query satisfied entirely from index. Zero heap fetches. 10–100× faster for cold data.

**When to use INCLUDE:**
- Frequently queried columns that are not in `WHERE` or `ORDER BY`
- Small columns (int, varchar, uuid)

**When to avoid INCLUDE:**
- Large columns (text, JSONB) — bloats the index
- Columns that change frequently — every update triggers index maintenance

**Important:** index-only scans require the Visibility Map to be current. VACUUM updates the Visibility Map. Tables with infrequent autovacuum may still require heap fetches despite a covering index. Pravah ensures aggressive autovacuum on all covered tables.

## GIN Index — For JSONB and Arrays

### Why GIN for JSONB

Pravah stores pipeline configuration as JSONB:

```
│ pipe-abc │ {"tasks": [...], "tags": ["finance", "daily"],   │
│          │  "owner": "data-team", "notifications": {...}}   │
│ pipe-def │ {"tasks": [...], "tags": ["marketing", "hourly"],│
│          │  "owner": "ml-team", ...}                        │
```

Query: "find all pipelines tagged 'finance'"
```sql
WHERE config @> '{"tags": ["finance"]}'
```

A B-tree cannot index JSONB — there is no single sortable key. A GIN index handles it natively.

### How GIN Works

GIN stands for Generalized Inverted Index — like a book index: `word → list of pages containing it`.

For a JSONB GIN index:
```
"finance"    → [pipe-abc, pipe-xyz, pipe-mno]
"daily"      → [pipe-abc, pipe-jkl]
"marketing"  → [pipe-def, pipe-pqr]
"data-team"  → [pipe-abc, pipe-ghi]
"ml-team"    → [pipe-def, pipe-stu]
```

Query `config @> '{"tags": ["finance"]}'` → GIN lookup for "finance" → returns `[pipe-abc, pipe-xyz, pipe-mno]` directly. No table scan.

### Pravah's GIN Index Examples

```sql
-- Pipeline config JSONB search
-- jsonb_path_ops: smaller index, only supports @> operator
-- jsonb_ops: larger, supports all JSONB operators
CREATE INDEX idx_pipelines_config_gin
ON pipelines USING gin(config jsonb_path_ops);

-- Runner tags array search
-- runners.tags = ARRAY['gpu', 'eu-west', 'docker']
CREATE INDEX idx_runners_tags_gin
ON runners USING gin(tags);
-- Query: WHERE tags @> ARRAY['gpu']::text[]

-- Full-text search on pipeline names and descriptions
CREATE INDEX idx_pipelines_search_gin
ON pipelines USING gin(
    to_tsvector('english', name || ' ' || COALESCE(description, ''))
);
-- Query: WHERE to_tsvector(...) @@ to_tsquery('etl & orders')
```

**GIN write overhead:** GIN indexes are more expensive to update than B-tree. Each JSONB key/value becomes a separate index entry. PostgreSQL mitigates this by buffering GIN updates in a pending list and flushing periodically.

Pravah configuration: `gin_pending_list_limit = 64MB`.

## BRIN Index — For Time-Series Data

### How BRIN Works

BRIN stands for Block Range Index. It works only when data has natural physical ordering — specifically when the column value correlates with physical insertion order.

BRIN stores the minimum and maximum values for each range of disk pages (128 pages by default). The entire index is kilobytes to megabytes, regardless of table size.

**Example: `audit_log` table — append-only, ordered by `created_at`**

Physical layout on disk (pages inserted chronologically):
```
Pages 1–128:    Jan 1 events    → BRIN entry: min=Jan 1, max=Jan 1
Pages 129–256:  Jan 2 events    → BRIN entry: min=Jan 2, max=Jan 2
Pages 257–384:  Jan 3 events    → BRIN entry: min=Jan 3, max=Jan 3
```

Query: `WHERE created_at = '2024-01-02'`
BRIN: only block range 129–256 can contain Jan 2 data → read only pages 129–256 → skip everything else.

### BRIN vs B-Tree Comparison

For a 500 million row `audit_log` table (50GB):

| | B-tree on `created_at` | BRIN on `created_at` |
|---|---|---|
| Index size | ~10GB (20% of table) | ~1MB (0.002% of table) |
| Write overhead | High — every insert updates index | Minimal — just track min/max per range |
| Point lookup | Very fast | Fast for ranges, less precise for points |
| Best for | Exact point lookups, unordered data | Append-only, range queries, minimize write cost |

BRIN wins for Pravah's `audit_log` and `events` tables: data is inserted chronologically, queries are time-range based, and write overhead matters at high volume. B-tree wins for the `jobs` table: status updates create new versions in random physical locations, breaking the correlation between `created_at` and physical order.

### Pravah's BRIN Index Examples

```sql
-- Audit log: append-only, ordered by created_at
CREATE INDEX idx_audit_log_brin
ON audit_log USING brin(created_at)
WITH (pages_per_range = 128);

-- Pipeline run history: time-series
CREATE INDEX idx_pipeline_runs_brin
ON pipeline_runs USING brin(started_at)
WITH (pages_per_range = 64);  -- smaller ranges for higher-traffic table
```

## Complete Index Strategy for Pravah's Core Tables

### Jobs Table — `execution_db`

```sql
CREATE TABLE jobs (
    id              UUID         PRIMARY KEY,
    pipeline_id     VARCHAR(255) NOT NULL,
    run_id          UUID         NOT NULL,
    tenant_id       VARCHAR(255) NOT NULL,
    status          VARCHAR(50)  NOT NULL DEFAULT 'PENDING',
    runner_id       VARCHAR(255),
    idempotency_key VARCHAR(500) NOT NULL UNIQUE,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    duration_ms     BIGINT,
    attempt_number  INT          NOT NULL DEFAULT 1,
    error_message   TEXT,
    result_ref      VARCHAR(1000),
    version         INT          NOT NULL DEFAULT 0
);

-- Dashboard: tenant's live jobs (partial + covering)
CREATE INDEX idx_jobs_tenant_live
ON jobs (tenant_id, status, created_at DESC)
INCLUDE (pipeline_id, runner_id, duration_ms)
WHERE status IN ('PENDING', 'RUNNING', 'FAILED');
-- Partial: only 2% of rows (live jobs)
-- Covering: includes all columns the dashboard needs

-- Scheduler: jobs by pipeline for dependency resolution
CREATE INDEX idx_jobs_pipeline
ON jobs (pipeline_id, created_at DESC)
INCLUDE (status, attempt_number);

-- Runner assignment: what jobs is this runner running?
CREATE INDEX idx_jobs_runner
ON jobs (runner_id, status)
WHERE runner_id IS NOT NULL
  AND status = 'RUNNING';

-- Idempotency key: UNIQUE constraint creates this automatically
-- idx_jobs_idempotency_key

-- Archival: find jobs older than 90 days for cleanup
CREATE INDEX idx_jobs_created_brin
ON jobs USING brin(created_at)
WITH (pages_per_range = 128);
```

### Pipelines Table — `pipeline_db`

```sql
CREATE TABLE pipelines (
    id          VARCHAR(255) PRIMARY KEY,
    tenant_id   VARCHAR(255) NOT NULL,
    name        VARCHAR(500) NOT NULL,
    description TEXT,
    status      VARCHAR(50)  NOT NULL DEFAULT 'ACTIVE',
    config      JSONB        NOT NULL,
    version     INT          NOT NULL DEFAULT 1,
    created_by  VARCHAR(255) NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    deleted_at  TIMESTAMPTZ  -- soft delete
);

-- Tenant's pipeline list (partial: exclude soft-deleted)
CREATE INDEX idx_pipelines_tenant
ON pipelines (tenant_id, status, updated_at DESC)
WHERE deleted_at IS NULL;

-- Pipeline search by name
CREATE INDEX idx_pipelines_name
ON pipelines (tenant_id, name)
WHERE deleted_at IS NULL;

-- JSONB config search: tags, owner, notifications
CREATE INDEX idx_pipelines_config_gin
ON pipelines USING gin(config jsonb_path_ops)
WHERE deleted_at IS NULL;

-- Full-text search on name and description
CREATE INDEX idx_pipelines_fts
ON pipelines USING gin(
    to_tsvector('english',
        COALESCE(name, '') || ' ' || COALESCE(description, ''))
)
WHERE deleted_at IS NULL;
```

### Runners Table — `runner_db`

```sql
CREATE TABLE runners (
    id             VARCHAR(255) PRIMARY KEY,
    tenant_id      VARCHAR(255) NOT NULL,
    name           VARCHAR(500) NOT NULL,
    status         VARCHAR(50)  NOT NULL DEFAULT 'OFFLINE',
    runner_type    VARCHAR(50)  NOT NULL,
    tags           TEXT[]       NOT NULL DEFAULT '{}',
    region         VARCHAR(100),
    max_concurrent INT          NOT NULL DEFAULT 4,
    active_jobs    INT          NOT NULL DEFAULT 0,
    last_heartbeat TIMESTAMPTZ,
    registered_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    fencing_token  BIGINT       NOT NULL DEFAULT 0,
    version        INT          NOT NULL DEFAULT 0
);

-- Runner selection: find available runners with capacity
CREATE INDEX idx_runners_available
ON runners (tenant_id, active_jobs, last_heartbeat DESC)
WHERE status = 'ACTIVE'
  AND active_jobs < max_concurrent;

-- Tag-based runner lookup (GIN for array containment)
CREATE INDEX idx_runners_tags
ON runners USING gin(tags)
WHERE status = 'ACTIVE';
-- Query: WHERE tags @> ARRAY['gpu', 'eu-west']

-- Heartbeat monitoring: detect silent runners
CREATE INDEX idx_runners_heartbeat
ON runners (tenant_id, last_heartbeat)
WHERE status = 'ACTIVE';
-- Query: WHERE last_heartbeat < NOW() - INTERVAL '30 seconds'
```

### Events Table — Event Store (`pipeline_db`)

```sql
CREATE TABLE events (
    id              UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_id    VARCHAR(255) NOT NULL,
    aggregate_type  VARCHAR(100) NOT NULL,
    event_type      VARCHAR(100) NOT NULL,
    sequence_number BIGINT       NOT NULL,
    tenant_id       VARCHAR(255) NOT NULL,
    actor           VARCHAR(255),
    occurred_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    payload         JSONB        NOT NULL,
    schema_version  VARCHAR(20)  NOT NULL DEFAULT '1.0',
    UNIQUE (aggregate_id, sequence_number)
);

-- Event sourcing: load all events for an aggregate in order
CREATE INDEX idx_events_aggregate
ON events (aggregate_id, sequence_number ASC);

-- Time-travel: load events up to a specific point in time
CREATE INDEX idx_events_aggregate_time
ON events (aggregate_id, occurred_at ASC)
INCLUDE (event_type, sequence_number);

-- BRIN for archival queries (events inserted chronologically)
CREATE INDEX idx_events_occurred_brin
ON events USING brin(occurred_at)
WITH (pages_per_range = 64);

-- Tenant audit: all events for a tenant
CREATE INDEX idx_events_tenant
ON events (tenant_id, occurred_at DESC)
INCLUDE (aggregate_id, aggregate_type, event_type);
```

```sql
CREATE TABLE outbox (

);

-- Relay's hot query: find pending messages to publish
CREATE INDEX idx_outbox_relay

-- Partial: only pending rows (99% are already PROCESSED, 1% are PENDING)
-- Tiny index serving the single most critical query in the outbox relay

-- Stuck detection: PROCESSING messages older than 5 minutes
CREATE INDEX idx_outbox_stuck
ON outbox (status, created_at)
WHERE status = 'PROCESSING';
```

## Index Trade-offs — Write Overhead

Every index has a write cost. For each INSERT, PostgreSQL updates every index on the table. For each UPDATE to an indexed column, PostgreSQL marks the old index entry dead and inserts a new one (index bloat, cleaned by autovacuum). For each DELETE, index entries are marked dead.

**Pravah's `jobs` table write overhead:**

```
10,000 inserts/minute at peak
+ 5 status updates per job
= 60,000 index operations/minute on the jobs table

With 6 indexes: 60,000 × 6 = 360,000 index operations/minute
```

This is substantial. Index creation must be deliberate.

**Decision framework:**

Create an index when:
- The query runs frequently (more than 10 times/second)
- The table is large (more than 100,000 rows)
- The query is currently slow (more than 100ms)
- The column has high selectivity (many distinct values)

Skip an index when:
- The table is small (fewer than 10,000 rows) — sequential scan is fine
- The column has very low cardinality (boolean, 3-value status) — unless a partial index on a specific value
- The table is write-heavy with rare reads
- The column rarely appears in `WHERE` clauses

**Unused index detection:**

```sql
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,       -- times this index was used
    idx_tup_read,   -- tuples read via this index
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE 'pg_%'
ORDER BY pg_relation_size(indexrelid) DESC;
```

Alert: index never used after 7 days → candidate for removal. Removing unused indexes directly reduces write overhead.

## System Design Interview Angles

**"How would you design indexes for a table that has both heavy writes and complex reads?"**

> This is exactly Pravah's `jobs` table challenge: 50 million rows with 10,000 inserts per minute and complex dashboard queries.
>
> First, I identify the critical query patterns: tenant's live jobs, jobs by pipeline, runner's current jobs. I design indexes specifically for these patterns rather than trying to cover every possible query.
>
> For live job monitoring: a partial index on `(tenant_id, status, created_at)` where `status IN ('PENDING', 'RUNNING', 'FAILED')` covers only 2% of rows — 98% smaller than a full index. I add `INCLUDE` for the columns the query needs, eliminating heap fetches entirely.
>
> For write overhead: partial indexes are key — smaller index means cheaper maintenance. I monitor `pg_stat_user_indexes` for unused indexes and remove them aggressively. Every unnecessary index consumes write throughput.

**"When would you use a BRIN index instead of a B-tree?"**

> BRIN works when data is physically ordered the same way as the query access pattern — specifically append-only time-series data.
>
> Pravah's `audit_log` is perfect for BRIN: events are appended in timestamp order, so pages 1–128 physically contain January data, pages 129–256 contain February data. BRIN just stores min/max timestamps per block range. The entire index for a 500 million row audit table is about 1MB versus 10GB for a B-tree.
>
> For range queries like "show me all audit events for last week," BRIN eliminates all block ranges outside that week.
>
> I would not use BRIN for the `jobs` table. Status updates create new row versions in whatever physical page has free space — the `created_at` timestamp of a row bears no relationship to its physical location. BRIN ranges would have min/max spanning the entire table, making the index useless for pruning.

**"Explain the leftmost prefix rule for composite indexes."**

> A composite index on `(tenant_id, status, created_at)` is sorted first by `tenant_id`, then by `status` within each tenant, then by `created_at` within each status. A query can only use this index efficiently if it filters on the leftmost columns.
>
> A query with only `tenant_id` can use it — seeks to that tenant's section. A query with `tenant_id AND status` can use it — seeks to that tenant's failed section. A query with all three is optimal.
>
> A query with only `status` cannot use this index efficiently — `FAILED` rows are scattered across all tenants in the index, so PostgreSQL would need to scan the entire index anyway.
>
> This drove our column ordering: `tenant_id` first (highest cardinality — 1,000 values eliminates 999/1,000 of data on first seek), `status` second (equality, low cardinality), `created_at` last (range condition — must come last because once you start scanning a range, subsequent columns cannot be used for seeking).

## Key Takeaways

1. **Index types in Pravah:** B-tree for most queries (90%), GIN for JSONB and arrays, BRIN for append-only time-series, partial for hot subsets, covering (`INCLUDE`) to eliminate heap fetches.

2. **Composite index column ordering:** equality conditions first, range conditions last, high cardinality before low cardinality. The leftmost prefix rule governs which queries can use the index.

3. **Partial indexes are underused but powerful:** `jobs` live monitoring — only 2% of rows indexed, 98% smaller. Outbox relay — only `PENDING` rows indexed, tiny index serving the highest-frequency query.

4. **Covering indexes eliminate heap fetches:** `INCLUDE` columns the query needs. Index-only scans require the Visibility Map to be current — autovacuum must run frequently on these tables.

5. **Every index has write cost:** INSERT updates all indexes; UPDATE to indexed columns creates new index entries; DELETE marks entries dead. Monitor `pg_stat_user_indexes`, remove unused indexes aggressively.

6. **BRIN for time-series:** `audit_log`, `events` — append-only and time-ordered. 1MB index for 500M rows versus 10GB B-tree. Range queries only, not point lookups.

7. **GIN for JSONB and arrays:** pipeline config search, runner tag matching, full-text search. Higher write cost — buffer with `gin_pending_list_limit`.

8. **Index design process:** identify hot queries → design specific indexes → measure with `EXPLAIN ANALYZE` before and after → monitor usage → remove unused indexes → balance read speed against write overhead.
