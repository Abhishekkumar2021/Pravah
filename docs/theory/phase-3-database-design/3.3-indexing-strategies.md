3.3 Indexing Strategies for Pravah's Tables
🧩 Why Indexing Is a Critical Design Decision
THE STAKES IN PRAVAH
────────────────────────────────────────────────────────────

jobs table: 50 million rows (1 year of data)
Query: "Show me all FAILED jobs for tenant megacorp
        in the last 24 hours"

WITHOUT index:
  PostgreSQL: "I'll read all 50 million rows"
  Time: 45 seconds ❌
  Dashboard: "Loading..." forever
  Enterprise client: cancels subscription

WITH wrong index:
  Index on status only
  PostgreSQL: finds all FAILED rows (5 million)
  Then filters tenant + time on those 5 million
  Time: 8 seconds ❌ (better but still unacceptable)

WITH right index:
  Composite index on (tenant_id, status, created_at)
  PostgreSQL: jumps directly to megacorp+FAILED+24h
  Time: 2ms ✅
  Dashboard: instant

Index choice = difference between 45 seconds and 2ms.
That's not optimization. That's the difference between
a working product and a broken one.
📚 Index Types in PostgreSQL
POSTGRESQL INDEX TYPES — OVERVIEW
────────────────────────────────────────────────────────────

PostgreSQL supports 6 index types.
Each optimized for different query patterns.

B-TREE:    Default. Sorted tree. Equality + range queries.
           Use for: most things (90% of use cases)

HASH:      Hash table. Equality ONLY. Slightly faster than
           B-tree for pure equality. Rarely used.
           Use for: pure equality lookups on high-cardinality

GIN:       Generalized Inverted Index. For composite values.
           Use for: JSONB, arrays, full-text search

BRIN:      Block Range INdex. Tiny index for sorted data.
           Use for: time-series, append-only tables

GiST:      Generalized Search Tree. For geometric/range types.
           Use for: PostGIS geometry, range overlap queries

SP-GiST:   Space-Partitioned GiST. Partitioned structures.
           Use for: non-balanced data distributions

Pravah uses: B-tree (primary), GIN (JSONB), BRIN (time-series)
🌳 B-Tree Index — The Workhorse
HOW B-TREE WORKS INTERNALLY
────────────────────────────────────────────────────────────

B-tree = Balanced Tree. All leaf nodes at same depth.

For index on jobs.status:

                    ROOT
                  [RUNNING]
                 /          \
          [FAILED]          [SUCCESS]
          /      \           /      \
      [F..][F..]  [F..][F..]  [S..][S..][S..]
      (leaf)       (leaf)       (leaf)

Each leaf node:
  [status value] → [ctid: page 42, offset 7]
                → [ctid: page 42, offset 8]
                → [ctid: page 43, offset 2]
  (list of physical row locations)

B-TREE QUERY TYPES:
────────────────────────────────────────────────────────────

Equality:   WHERE status = 'FAILED'
            → B-tree search: O(log n) ✅

Range:      WHERE created_at BETWEEN t1 AND t2
            → Find t1 in tree, scan leaves forward ✅

Prefix:     WHERE pipeline_name LIKE 'sales%'
            → Works! (prefix = range query on strings) ✅

Suffix:     WHERE pipeline_name LIKE '%etl'
            → Does NOT use index ❌ (can't know start point)

NULL:       WHERE status IS NULL
            → B-tree includes NULL values ✅

ORDER BY:   ORDER BY created_at DESC
            → B-tree already sorted → no sort step ✅
            (if index matches ORDER BY direction)

NOT EQUAL:  WHERE status != 'RUNNING'
            → Usually seq scan (most rows match) ❌
            (planner chooses based on selectivity)
🔑 Composite Indexes — The Most Important Concept
COMPOSITE INDEX COLUMN ORDERING
────────────────────────────────────────────────────────────

Index on (col_a, col_b, col_c):
  Can serve queries on: col_a alone
                        col_a + col_b
                        col_a + col_b + col_c
  Cannot serve:         col_b alone
                        col_c alone
                        col_b + col_c

This is the LEFTMOST PREFIX RULE.
The index is sorted by col_a first, then col_b within col_a,
then col_c within col_b.

EXAMPLE: Index on (tenant_id, status, created_at)

  Sorted in index:
    megacorp | FAILED   | 2024-01-14T09:00  → ctid(42,7)
    megacorp | FAILED   | 2024-01-14T10:00  → ctid(42,8)
    megacorp | FAILED   | 2024-01-15T09:00  → ctid(43,2)
    megacorp | RUNNING  | 2024-01-15T10:00  → ctid(44,1)
    megacorp | SUCCESS  | 2024-01-14T08:00  → ctid(45,3)
    techgiant| FAILED   | 2024-01-15T11:00  → ctid(46,2)
    techgiant| RUNNING  | 2024-01-15T12:00  → ctid(47,1)

QUERIES THIS INDEX CAN SERVE:
  ✅ WHERE tenant_id = 'megacorp'
     (leftmost prefix: tenant_id)

  ✅ WHERE tenant_id = 'megacorp' AND status = 'FAILED'
     (leftmost prefix: tenant_id + status)

  ✅ WHERE tenant_id = 'megacorp'
     AND status = 'FAILED'
     AND created_at > '2024-01-14'
     (full composite index used)

  ✅ WHERE tenant_id = 'megacorp'
     AND created_at > '2024-01-14'
     (tenant_id matched, created_at used for range filtering
      but status is skipped — still uses index partially)

  ❌ WHERE status = 'FAILED'
     (missing leftmost: tenant_id)
     → Seq scan or separate index needed

  ❌ WHERE created_at > '2024-01-14'
     (missing leftmost: tenant_id AND status)
     → Different index needed

COLUMN ORDERING RULE:
  1. Equality conditions first (tenant_id = 'X')
  2. Range conditions last (created_at > X)
  3. High cardinality before low cardinality
     (tenant_id has 1000 values,
      status has 5 values)
     → tenant_id first ✅

  WHY? Index seeks to first matching tenant_id
       (eliminates 999/1000 of data immediately)
       Then filters status within that
       (eliminates 4/5 of remaining data)
       Then range scans created_at
       Final result: tiny set read ✅
🎯 Partial Indexes — Index Only What You Query
PARTIAL INDEX CONCEPT
────────────────────────────────────────────────────────────

A partial index only includes rows matching a condition.
Smaller index → faster queries + less disk + less write overhead.

EXAMPLE: jobs table
  Total rows: 50 million
  COMPLETED: 49 million (98%)
  RUNNING:   500,000   (1%)
  FAILED:    400,000   (0.8%)
  PENDING:   100,000   (0.2%)

Dashboard queries 99% focus on RUNNING + FAILED + PENDING.
Nobody queries COMPLETED jobs in the dashboard
(they're in historical reports, not live monitoring).

FULL INDEX on status: indexes 50 million rows
PARTIAL INDEX on (status) WHERE status != 'COMPLETED':
  Only indexes 1,000,000 rows (2% of table!)
  98% smaller ✅
  98% faster writes (less index maintenance) ✅
  Serves all live monitoring queries ✅

PRAVAH PARTIAL INDEX EXAMPLES:
────────────────────────────────────────────────────────────

-- Only index active runners (most queries)
CREATE INDEX idx_runners_active
ON runners (tenant_id, tags, last_heartbeat)
WHERE status = 'ACTIVE';

-- Only index unprocessed outbox messages
CREATE INDEX idx_outbox_pending
ON outbox (created_at)
WHERE status = 'PENDING';
-- This is the relay's hot query:
-- SELECT ... FROM outbox WHERE status = 'PENDING'
-- ORDER BY created_at FOR UPDATE SKIP LOCKED

-- Only index non-completed jobs (live monitoring)
CREATE INDEX idx_jobs_live
ON jobs (tenant_id, status, created_at)
WHERE status IN ('PENDING', 'RUNNING', 'FAILED');

-- Only index recent pipeline runs (dashboard)
-- (combined with table partitioning in 3.4)
CREATE INDEX idx_pipeline_runs_recent
ON pipeline_runs (tenant_id, pipeline_id, started_at)
WHERE started_at > NOW() - INTERVAL '7 days';
-- NOTE: This would need to be recreated periodically
-- Better: use partitioned indexes (covered in 3.4)
📦 Covering Indexes — Avoid Table Lookups
THE INDEX-ONLY SCAN OPTIMIZATION
────────────────────────────────────────────────────────────

Normal index lookup:
  1. Search index → find ctid (page 42, offset 7)
  2. Go to page 42 in table → read row → extract columns
  Step 2 = "heap fetch" = random I/O = SLOW

Index-only scan:
  1. Search index → find all needed column values IN INDEX
  2. No heap fetch needed (all data in index)
  Much faster for read-heavy queries ✅

COVERING INDEX WITH INCLUDE:
  PostgreSQL 11+ supports INCLUDE clause:
  Stores extra columns in index leaf nodes.
  Not part of sort order, just stored data.

  -- Query: get job status and duration for dashboard
  SELECT job_id, status, duration_ms, pipeline_id
  FROM jobs
  WHERE tenant_id = 'megacorp'
  AND created_at > NOW() - INTERVAL '1 hour'

  Without covering index:
    Index finds ctids → heap fetch for duration_ms, pipeline_id
    Random I/O for every matching row ❌

  WITH covering index:
  CREATE INDEX idx_jobs_dashboard
  ON jobs (tenant_id, created_at DESC)
  INCLUDE (job_id, status, duration_ms, pipeline_id);

  Index leaf node now contains:
    (megacorp, 2024-01-15T10:00) →
    {job_id:'xyz', status:'COMPLETE', duration:45000, pipeline:'abc'}

  Query satisfied entirely from index.
  Zero heap fetches ✅
  10-100× faster for cold data ✅

WHEN TO USE INCLUDE:
  ✅ Frequently queried columns not in WHERE/ORDER BY
  ✅ Small columns (int, varchar, uuid)
  ❌ Large columns (text, jsonb) — bloats index
  ❌ Columns that change frequently — index maintenance cost

VISIBILITY MAP REQUIREMENT:
  Index-only scan requires heap pages to be in
  Visibility Map (all tuples on page are visible to all).
  VACUUM updates Visibility Map.
  Fresh tables or low-vacuum tables → heap fetches anyway.
  Pravah: ensure autovacuum runs frequently on covered tables.
🔍 GIN Index — For JSONB and Arrays
WHY GIN FOR JSONB
────────────────────────────────────────────────────────────

Pravah stores pipeline configuration as JSONB:

  pipelines table:
  ┌────────────┬──────────────────────────────────────────┐
  │ id         │ config (JSONB)                           │
  ├────────────┼──────────────────────────────────────────┤
  │ pipe-abc   │ {"tasks": [...], "tags": ["finance",     │
  │            │  "daily"], "owner": "data-team",         │
  │            │  "notifications": {"slack": "#alerts"}}  │
  ├────────────┼──────────────────────────────────────────┤
  │ pipe-def   │ {"tasks": [...], "tags": ["marketing",   │
  │            │  "hourly"], "owner": "ml-team", ...}     │
  └────────────┴──────────────────────────────────────────┘

Query: "Find all pipelines tagged 'finance'"
  WHERE config @> '{"tags": ["finance"]}'
  (contains operator)

B-TREE on JSONB: impossible (unordered structure)
GIN on JSONB:    works perfectly

GIN INDEX INTERNALS:
────────────────────────────────────────────────────────────

GIN = Generalized Inverted Index
Like a book index: word → list of pages containing it

For JSONB GIN index:
  "finance"    → [pipe-abc, pipe-xyz, pipe-mno]
  "daily"      → [pipe-abc, pipe-jkl]
  "marketing"  → [pipe-def, pipe-pqr]
  "data-team"  → [pipe-abc, pipe-ghi]
  "ml-team"    → [pipe-def, pipe-stu]

Query: config @> '{"tags": ["finance"]}'
  GIN: "find all rows containing 'finance'"
  → [pipe-abc, pipe-xyz, pipe-mno] — direct lookup ✅

PRAVAH GIN INDEX EXAMPLES:
────────────────────────────────────────────────────────────

-- Pipeline config JSONB search
CREATE INDEX idx_pipelines_config_gin
ON pipelines USING gin(config jsonb_path_ops);
-- jsonb_path_ops: smaller index, only supports @> operator
-- jsonb_ops: larger, supports all JSONB operators

-- Runner tags array search
-- runners.tags = ['gpu', 'eu-west', 'docker']
CREATE INDEX idx_runners_tags_gin
ON runners USING gin(tags);

-- Query: find runners with 'gpu' tag
-- WHERE tags @> ARRAY['gpu']::text[]
-- GIN handles array containment ✅

-- Full-text search on pipeline names/descriptions
CREATE INDEX idx_pipelines_search_gin
ON pipelines USING gin(
  to_tsvector('english', name || ' ' || description)
);
-- Query: WHERE to_tsvector(...) @@ to_tsquery('etl & orders')

GIN WRITE OVERHEAD:
  GIN indexes are expensive to update.
  Each JSONB key/value = separate GIN entry.
  Large JSONB documents → many index entries per row.

  Mitigation: gin_pending_list_limit
    PostgreSQL buffers GIN updates in pending list
    Flushes periodically (not on every write)
    Trades write latency for write throughput

  Pravah config: gin_pending_list_limit = 64MB
⏱️ BRIN Index — For Time-Series Data
BRIN — BLOCK RANGE INDEX
────────────────────────────────────────────────────────────

BRIN is for data with natural physical ordering.
Stores min/max values per RANGE of pages (128 pages default).
Tiny index (kilobytes) vs B-tree (gigabytes) for same table.

HOW BRIN WORKS:
────────────────────────────────────────────────────────────

audit_log table: append-only, ordered by created_at

Physical layout on disk:
  Pages 1-128:    Jan 1 events   (BRIN entry: min=Jan1, max=Jan1)
  Pages 129-256:  Jan 2 events   (BRIN entry: min=Jan2, max=Jan2)
  Pages 257-384:  Jan 3 events   (BRIN entry: min=Jan3, max=Jan3)
  ...

BRIN index (tiny!):
  Block range 1-128:    min=2024-01-01, max=2024-01-01
  Block range 129-256:  min=2024-01-02, max=2024-01-02
  Block range 257-384:  min=2024-01-03, max=2024-01-03

Query: WHERE created_at = '2024-01-02'
  BRIN: "only block range 129-256 can contain Jan 2"
  Read only pages 129-256 → skip everything else ✅

Query: WHERE created_at BETWEEN '2024-01-01' AND '2024-01-03'
  BRIN: "ranges 1-384 can contain this range"
  Read pages 1-384 → skip everything else ✅

BRIN vs B-TREE COMPARISON:
────────────────────────────────────────────────────────────

audit_log: 500 million rows, 50GB table

  B-TREE on created_at:
    Index size: ~10GB (20% of table)
    Write overhead: high (every insert updates index)
    Query: very fast (exact point lookup)

  BRIN on created_at:
    Index size: ~1MB (0.002% of table!)
    Write overhead: minimal (just track min/max per range)
    Query: fast for ranges, reads whole block ranges

  BRIN WINS for:
    Append-only time-series (data ordered as inserted)
    Range queries on the ordered column
    Tables where minimizing write overhead matters

  B-TREE WINS for:
    Exact point lookups (WHERE id = 'specific-value')
    Unordered data (created_at has gaps/reordering)
    Small tables (B-tree overhead negligible)

PRAVAH BRIN USAGE:
────────────────────────────────────────────────────────────

-- Audit log: append-only, ordered by created_at
CREATE INDEX idx_audit_log_brin
ON audit_log USING brin(created_at)
WITH (pages_per_range = 128);

-- Pipeline run history: time-series
CREATE INDEX idx_pipeline_runs_brin
ON pipeline_runs USING brin(started_at)
WITH (pages_per_range = 64);  -- smaller ranges for hot table

-- Job history: partitioned table (covered in 3.4)
-- BRIN on each partition naturally
🗺️ Complete Index Strategy for Pravah's Core Tables
JOBS TABLE — EXECUTION_DB
────────────────────────────────────────────────────────────

CREATE TABLE jobs (
  id              UUID PRIMARY KEY,
  pipeline_id     VARCHAR(255) NOT NULL,
  run_id          UUID NOT NULL,
  tenant_id       VARCHAR(255) NOT NULL,
  status          VARCHAR(50)  NOT NULL DEFAULT 'PENDING',
  runner_id       VARCHAR(255),
  idempotency_key VARCHAR(500) UNIQUE NOT NULL,
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  started_at      TIMESTAMPTZ,
  completed_at    TIMESTAMPTZ,
  duration_ms     BIGINT,
  attempt_number  INT NOT NULL DEFAULT 1,
  error_message   TEXT,
  result_ref      VARCHAR(1000),
  version         INT NOT NULL DEFAULT 0
);

-- PRIMARY: id (auto-created for PRIMARY KEY)

-- Dashboard: tenant's live jobs
CREATE INDEX idx_jobs_tenant_live
ON jobs (tenant_id, status, created_at DESC)
INCLUDE (pipeline_id, runner_id, duration_ms)
WHERE status IN ('PENDING', 'RUNNING', 'FAILED');
-- Partial: only live jobs (2% of table)
-- Covering: includes columns needed by dashboard
-- Descending created_at: dashboard shows newest first

-- Scheduler: find jobs by pipeline (for dependency resolution)
CREATE INDEX idx_jobs_pipeline
ON jobs (pipeline_id, created_at DESC)
INCLUDE (status, attempt_number);

-- Runner assignment: what jobs are on this runner?
CREATE INDEX idx_jobs_runner
ON jobs (runner_id, status)
WHERE runner_id IS NOT NULL
AND status = 'RUNNING';
-- Partial: only running jobs on a runner

-- Idempotency: already has UNIQUE constraint (auto-indexed)
-- idx_jobs_idempotency_key automatically created

-- Historical: time-based archival queries
CREATE INDEX idx_jobs_created_brin
ON jobs USING brin(created_at)
WITH (pages_per_range = 128);
-- For archival: "find all jobs older than 90 days"

PIPELINES TABLE — PIPELINE_DB
────────────────────────────────────────────────────────────

CREATE TABLE pipelines (
  id              VARCHAR(255) PRIMARY KEY,
  tenant_id       VARCHAR(255) NOT NULL,
  name            VARCHAR(500) NOT NULL,
  description     TEXT,
  status          VARCHAR(50)  NOT NULL DEFAULT 'ACTIVE',
  config          JSONB        NOT NULL,
  version         INT NOT NULL DEFAULT 1,
  created_by      VARCHAR(255) NOT NULL,
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  deleted_at      TIMESTAMPTZ  -- soft delete
);

-- Tenant's pipelines (main list view)
CREATE INDEX idx_pipelines_tenant
ON pipelines (tenant_id, status, updated_at DESC)
WHERE deleted_at IS NULL;
-- Partial: exclude soft-deleted

-- Pipeline search by name (exact or prefix)
CREATE INDEX idx_pipelines_name
ON pipelines (tenant_id, name)
WHERE deleted_at IS NULL;

-- JSONB config search (tags, owner, etc)
CREATE INDEX idx_pipelines_config_gin
ON pipelines USING gin(config jsonb_path_ops)
WHERE deleted_at IS NULL;

-- Full-text search
CREATE INDEX idx_pipelines_fts
ON pipelines USING gin(
  to_tsvector('english',
    COALESCE(name, '') || ' ' || COALESCE(description, ''))
)
WHERE deleted_at IS NULL;

CREATE TABLE runners (

  tenant_id       VARCHAR(255) NOT NULL,
  name            VARCHAR(500) NOT NULL,
  status          VARCHAR(50)  NOT NULL DEFAULT 'OFFLINE',
  runner_type     VARCHAR(50)  NOT NULL, -- SELF_HOSTED/CLOUD/EPHEMERAL

-- Runner selection: find available runner with matching tags
CREATE INDEX idx_runners_available
ON runners (tenant_id, active_jobs, last_heartbeat DESC)
WHERE status = 'ACTIVE'
AND active_jobs < max_concurrent;
-- Partial: only active runners with capacity

-- Tag-based runner lookup (GIN for array containment)
CREATE INDEX idx_runners_tags
ON runners USING gin(tags)
WHERE status = 'ACTIVE';
-- Query: WHERE tags @> ARRAY['gpu', 'eu-west']

-- Heartbeat monitoring: find silent runners
CREATE INDEX idx_runners_heartbeat
ON runners (tenant_id, last_heartbeat)
WHERE status = 'ACTIVE';
-- Query: WHERE last_heartbeat < NOW() - INTERVAL '30 seconds'

EVENTS TABLE — PIPELINE_DB (Event Store)
────────────────────────────────────────────────────────────

CREATE TABLE events (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aggregate_id    VARCHAR(255) NOT NULL,
  aggregate_type  VARCHAR(100) NOT NULL,
  event_type      VARCHAR(100) NOT NULL,
  sequence_number BIGINT       NOT NULL,
  tenant_id       VARCHAR(255) NOT NULL,
  actor           VARCHAR(255),
  occurred_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  payload         JSONB        NOT NULL,
  schema_version  VARCHAR(20)  NOT NULL DEFAULT '1.0',

  -- Optimistic locking: no two events with same aggregate+sequence
  UNIQUE (aggregate_id, sequence_number)
);

-- Event sourcing: load events for an aggregate
CREATE INDEX idx_events_aggregate
ON events (aggregate_id, sequence_number ASC);
-- Covers: load all events for pipe-abc in order
-- Append-only table: B-tree grows but rarely re-read old

-- Time-travel: load events up to a specific time
CREATE INDEX idx_events_aggregate_time
ON events (aggregate_id, occurred_at ASC)
INCLUDE (event_type, sequence_number);

-- BRIN for archival (events ordered by occurred_at as inserted)
CREATE INDEX idx_events_occurred_brin
ON events USING brin(occurred_at)
WITH (pages_per_range = 64);

-- Tenant audit: all events for a tenant
CREATE INDEX idx_events_tenant
ON events (tenant_id, occurred_at DESC)
INCLUDE (aggregate_id, aggregate_type, event_type);

CREATE TABLE outbox (

);

-- RELAY'S HOT QUERY: find pending messages to process
-- SELECT ... FROM outbox WHERE status='PENDING'
-- ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100
CREATE INDEX idx_outbox_relay
ON outbox (created_at ASC)
WHERE status = 'PENDING';
-- Partial: ONLY pending (99% processed, 1% pending)
-- TINY index serving the most critical query ✅

-- Stuck detection: PROCESSING messages older than 5 minutes
CREATE INDEX idx_outbox_stuck
ON outbox (status, created_at)
WHERE status = 'PROCESSING';
⚖️ Index Trade-offs — Write Overhead
EVERY INDEX HAS A WRITE COST
────────────────────────────────────────────────────────────

For every INSERT:
  Update every index → extra I/O

For every UPDATE:
  If indexed column changes → update that index
  (B-tree: mark old entry deleted, insert new entry)
  → Dead tuple in index too (index bloat!)

For every DELETE:
  Mark index entries as dead → vacuumed later

PRAVAH WRITE OVERHEAD ANALYSIS:
────────────────────────────────────────────────────────────

jobs table: 10,000 inserts/minute at peak
  + 5 status updates per job
  = 60,000 index operations/minute

With 6 indexes on jobs table:
  60,000 × 6 = 360,000 index operations/minute

This is substantial. Must balance read speed vs write cost.

INDEXING DECISION FRAMEWORK:
────────────────────────────────────────────────────────────

✅ CREATE INDEX when:
  Query runs frequently (>10/second)
  Table is large (>100K rows)
  Query currently slow (>100ms)
  Column has high selectivity (many distinct values)

❌ SKIP INDEX when:
  Table is small (<10K rows) → seq scan is fine
  Column has low cardinality (true/false, 3 statuses)
  → Unless partial index on one value
  Write-heavy table with rare reads
  Column rarely used in WHERE clause

⚠️ MONITOR after adding:
  EXPLAIN ANALYZE before and after
  Check if planner actually uses it
  Watch write performance under load

UNUSED INDEX DETECTION IN PRAVAH:
────────────────────────────────────────────────────────────

  SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,           ← times index was used
    idx_tup_read,       ← tuples read via index
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
  FROM pg_stat_user_indexes
  WHERE idx_scan = 0    ← never used!
  AND indexrelname NOT LIKE 'pg_%'
  ORDER BY pg_relation_size(indexrelid) DESC;

  Alert: index never used after 7 days → candidate for removal
  Remove unused indexes → reduces write overhead
🎯 FAANG Interview Angles
❓ "How would you design indexes for a table
    that has both heavy writes and complex reads?"

Good answer:
  "This is exactly Pravah's jobs table challenge.
   50 million rows with 10,000 inserts per minute
   and complex dashboard queries.

   First, I identify the critical query patterns:
   tenant's live jobs, jobs by pipeline, runner's
   current jobs. Then I design indexes specifically
   for these patterns rather than trying to cover
   all possible queries.

   For live job monitoring, a partial index on
   (tenant_id, status, created_at) WHERE status
   IN ('PENDING','RUNNING','FAILED') covers only
   2% of rows — 98% smaller than a full index.
   Add INCLUDE for columns the query needs to
   avoid heap fetches entirely.

   For write overhead, I use partial indexes
   wherever possible — smaller index = cheaper
   maintenance. I monitor pg_stat_user_indexes
   for unused indexes and remove them aggressively.
   Every unnecessary index costs write throughput."

❓ "When would you use a BRIN index instead
    of a B-tree in Pravah?"

Good answer:
  "BRIN works when data is physically ordered the
   same way as the query access pattern — typically
   append-only time-series data.

   Pravah's audit_log is perfect for BRIN: events
   are appended in timestamp order, so pages 1-128
   contain January data, pages 129-256 contain
   February data, and so on. BRIN just stores
   min/max timestamps per block range — the entire
   index for a 500 million row audit table is about
   1MB versus 10GB for a B-tree.

   For range queries like 'show me all audit events
   for last week', BRIN eliminates all block ranges
   outside that week. The only downside is BRIN
   reads entire matching block ranges, so for very
   precise point lookups, B-tree is faster.

   I wouldn't use BRIN for the jobs table because
   status updates create new versions in random
   physical locations — the physical order no longer
   matches the timestamp order. BRIN would be useless
   there."

❓ "Explain the leftmost prefix rule for
    composite indexes and how it affects Pravah."

Good answer:
  "A composite index on (tenant_id, status, created_at)
   is sorted first by tenant_id, then by status within
   each tenant, then by created_at within each status.
   This means the index can only be efficiently used
   when queries start with the leftmost columns.

   A query with just tenant_id can use the index —
   it jumps to that tenant's section. A query with
   tenant_id AND status can use it — jumps to that
   tenant's failed section. A query with all three
   is optimal — jumps to exactly the right place.

   But a query with only status cannot use this index
   efficiently — status values are scattered throughout
   all tenants in the index, so PostgreSQL would need
   to scan the entire index anyway.

   This drove our column ordering decision: tenant_id
   first (highest cardinality, most selective),
   status second (equality condition), created_at
   last (range condition). Range conditions must come
   last because once you start scanning a range,
   you can't use subsequent index columns for seeking."
📌 Key Takeaways
1. Index types in Pravah:
   B-tree: default, equality + range (90% of cases)
   GIN: JSONB, arrays, full-text search
   BRIN: append-only time-series (tiny, fast writes)
   Partial: subset of rows (hot queries on small subset)
   Covering (INCLUDE): avoid heap fetches entirely

2. Composite index column order:
   Equality conditions FIRST (tenant_id = 'X')
   Range conditions LAST (created_at > X)
   High cardinality before low cardinality
   Leftmost prefix rule: queries must match from left

3. Partial indexes are underused but powerful:
   jobs live monitoring: WHERE status IN ('PENDING','RUNNING','FAILED')
   Only 2% of rows → 98% smaller index
   outbox relay: WHERE status = 'PENDING' → tiny hot index

4. Covering indexes eliminate heap fetches:
   INCLUDE columns the query needs
   Index-only scan = no random I/O to table
   Requires Visibility Map current (autovacuum must run)

5. Every index has write cost:
   INSERT: update all indexes
   UPDATE: update indexes for changed columns
   Monitor: pg_stat_user_indexes for unused indexes
   Remove unused: reduces write overhead significantly

6. BRIN for Pravah:
   audit_log, pipeline_runs: append-only + time-ordered
   1MB index for 500M rows (vs 10GB B-tree)
   Range queries only, not point lookups

7. GIN for Pravah:
   Pipeline config JSONB: @> containment queries
   Runner tags array: @> array containment
   Full-text search: to_tsvector + to_tsquery

8. Index design process:
   Identify hot queries → design specific indexes
   Measure with EXPLAIN ANALYZE before/after
   Monitor usage → remove unused indexes
   Balance read speed vs write overhead
