# 3.12 Elasticsearch for Search and Lineage Graphs

## Why Not PostgreSQL for Search

PostgreSQL is exceptional for structured queries: `WHERE status = 'FAILED' AND tenant_id = 'x' AND created_at > '...'`. These are equality and range predicates on indexed columns — PostgreSQL handles them in microseconds.

But a data catalog search is different:

- "Find all pipelines that read from any table with 'customer' in the name"
- "Search for pipelines tagged 'pii' owned by the 'data' team"
- "Show me all datasets related to 'revenue' with high data quality scores"
- "Find all columns named 'email' across all source systems"

These queries require **full-text search** (any field containing a word), **fuzzy matching** (typo-tolerant search: 'revnue' should match 'revenue'), **relevance ranking** (most relevant result first), and **aggregations** (faceted search: "filter by owner" shows how many results each owner has).

PostgreSQL's `tsvector` and `GIN` indexes provide basic full-text search, but:
- Relevance ranking (TF-IDF / BM25) requires significant custom implementation
- Fuzzy matching and n-gram tokenization are available but complex to configure correctly
- Search-specific performance characteristics (inverted index, distributed across shards) are not PostgreSQL's strength

**Elasticsearch** is purpose-built for this. Its inverted index stores term → document mappings natively, its BM25 scoring provides relevance ranking out of the box, and its horizontal sharding scales search across many nodes.

## Elasticsearch Core Concepts

**Index**: equivalent to a table. All lineage events might be in the `lineage-events` index. Each index has a mapping (schema).

**Document**: a JSON object stored in an index. Documents have an `_id` and arbitrary fields.

**Shard**: an index is divided into shards. Each shard is a self-contained Lucene index. Elasticsearch distributes shards across nodes for parallelism.

**Replica shard**: a copy of a primary shard on a different node. Provides redundancy and read parallelism.

**Inverted index**: for each term (word) in a text field, Elasticsearch stores the list of documents containing that term. This is the core data structure that makes text search fast.

```
Input document: "orders pipeline reads from customer_database"

Inverted index:
  "orders"     → [doc1]
  "pipeline"   → [doc1, doc3, doc7]
  "reads"      → [doc1, doc2]
  "customer"   → [doc1, doc4]
  "database"   → [doc1, doc5]

Query: "customer pipeline"
→ find documents with "customer" AND "pipeline"
→ intersection of [doc1, doc4] and [doc1, doc3, doc7] = [doc1]
→ return doc1
```

**Relevance scoring (BM25)**: not all results are equally relevant. BM25 scores documents based on:
- **Term frequency**: "pipeline" appears 3 times in doc1, once in doc3 → doc1 more relevant
- **Inverse document frequency**: "pipeline" appears in 100 docs out of 1000 total → common word, lower weight; "debezium" appears in 2 docs → rare, higher weight
- **Field length normalization**: finding "pipeline" in a 5-word title is more significant than finding it in a 500-word description

## Elasticsearch Mappings for Pravah

**Pipeline catalog index:**

```json
PUT /pipeline-catalog
{
  "mappings": {
    "properties": {
      "pipeline_id":   { "type": "keyword" },        // exact match only
      "tenant_id":     { "type": "keyword" },
      "name":          { "type": "text",              // full-text search
                         "fields": {
                           "keyword": { "type": "keyword" }  // also exact match
                         }},
      "description":   { "type": "text" },
      "tags":          { "type": "keyword" },
      "owner_team":    { "type": "keyword" },
      "status":        { "type": "keyword" },
      "source_datasets": {
        "type": "nested",                             // nested array of objects
        "properties": {
          "namespace": { "type": "keyword" },
          "name":      { "type": "text", "fields": { "keyword": { "type": "keyword" }}}
        }
      },
      "last_run_at":   { "type": "date" },
      "quality_score": { "type": "float" }
    }
  }
}
```

**`text` vs `keyword`**: `text` fields are tokenized and analyzed (lowercased, stop words removed, stemmed) — used for full-text search. `keyword` fields are stored verbatim — used for exact match, sorting, and aggregations. Fields can be both (using `fields`).

**Nested type for arrays of objects**: if `source_datasets` were a regular `object` array, Elasticsearch would flatten it — losing the correlation between `namespace` and `name` within the same dataset object. `nested` preserves the object structure, enabling queries like "find pipelines where a source dataset has namespace='postgres://prod' AND name contains 'orders'".

## Queries

**Full-text search with relevance:**

```json
GET /pipeline-catalog/_search
{
  "query": {
    "bool": {
      "must": [
        { "term": { "tenant_id": "megacorp" }},          // filter: exact match
        { "multi_match": {                                // full-text across fields
            "query": "customer orders revenue",
            "fields": ["name^3", "description", "tags^2"], // name weighted 3×
            "fuzziness": "AUTO"                           // typo tolerance
          }}
      ]
    }
  },
  "sort": [
    { "_score": { "order": "desc" }},                    // by relevance
    { "last_run_at": { "order": "desc" }}                // tie-break by recency
  ]
}
```

**Faceted search (aggregations):**

```json
GET /pipeline-catalog/_search
{
  "query": { "term": { "tenant_id": "megacorp" }},
  "aggs": {
    "by_team": {
      "terms": { "field": "owner_team", "size": 10 }     // "how many pipelines per team?"
    },
    "by_status": {
      "terms": { "field": "status" }
    },
    "quality_histogram": {
      "histogram": { "field": "quality_score", "interval": 0.1 }
    }
  }
}
```

This drives the left-side filter panel in a search UI — "Filter by team: data-eng (45), analytics (23), ..." — with document counts per filter value.

## Lineage Graph in Elasticsearch

Graph storage in Elasticsearch uses **edge documents** — each document represents a directed edge in the lineage graph:

```json
// Edge: pipeline X reads from dataset Y (input edge)
{
  "run_id":            "job-uuid-abc",
  "pipeline_id":       "pipeline-orders-etl",
  "dataset_namespace": "postgres://prod-db",
  "dataset_name":      "public.orders",
  "direction":         "INPUT",
  "column_lineage": [
    { "source_field": "email",
      "target_field": "email_hash",
      "target_dataset": "snowflake://dw/analytics.dw_orders",
      "transform": "SHA256" }
  ],
  "occurred_at": "2026-05-10T09:00:05.000Z",
  "tenant_id":   "megacorp"
}
```

**Impact analysis** (what breaks if dataset Y changes?):

```json
// Level 1: who reads from public.orders?
GET /lineage-graph/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "dataset_name": "public.orders" }},
        { "term": { "direction": "INPUT" }},
        { "term": { "tenant_id": "megacorp" }}
      ]
    }
  }
}
// Returns: pipeline-orders-etl, pipeline-orders-archive, pipeline-orders-reporting

// Level 2: what do these pipelines write to?
// ... and so on, up to max_depth levels
```

The graph traversal is implemented as a recursive search loop (not a native graph query — Elasticsearch is not a graph database, but it handles this use case adequately up to ~10 levels deep).

## Elasticsearch Operational Considerations

**Cluster sizing for Pravah:**

A 3-node Elasticsearch cluster with 3 primary shards and 1 replica per shard:
- Provides fault tolerance: 1 node failure is tolerable (replicas cover the lost primaries)
- Provides read parallelism: both primary and replica shards serve read requests
- Pravah-scale data volume (millions of lineage events/year) fits comfortably on 3 nodes

**Index Lifecycle Management (ILM):**

```json
PUT /_ilm/policy/lineage-policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_size": "50GB", "max_age": "30d" }
        }
      },
      "warm": {
        "min_age": "30d",
        "actions": {
          "shrink": { "number_of_shards": 1 },
          "forcemerge": { "max_num_segments": 1 }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

Hot phase: actively written indices, full shards, fast writes.  
Warm phase: older data, shrunken to 1 shard, force-merged for read efficiency.  
Delete phase: data exceeding retention is removed.

**Synchronization with PostgreSQL:**

Elasticsearch is a secondary store — PostgreSQL (or Kafka events) is the source of truth. The pipeline catalog in Elasticsearch is populated and kept in sync by consuming `pipeline.events` from Kafka. If the Elasticsearch index is corrupted or out of sync, it can be rebuilt by replaying all pipeline events from the beginning.

## Application in Pravah

Pravah uses Elasticsearch for two distinct purposes:

**1. Pipeline catalog search**: users search for pipelines by name, description, tags, source datasets, and owner. Elasticsearch powers the search API with relevance ranking and faceted filtering.

**2. Lineage graph storage**: OpenLineage events (ADR-019) are stored as edge documents in Elasticsearch. Impact analysis and column-level lineage traversal are Elasticsearch queries rather than PostgreSQL recursive CTEs. At lineage scale (millions of events), Elasticsearch's distributed inverted index outperforms PostgreSQL for this read pattern.

Both use cases are served by the same Elasticsearch cluster, in separate indices. The Metadata Service is the sole component that writes to and reads from these indices.
