# 3.8 Redis — Caching, Locking & Pub/Sub

## What Redis Is and Isn't

Redis is an in-memory data structure store. That single phrase contains everything important about it:

- **In-memory:** all data lives in RAM. Reads and writes complete in microseconds — typically 100–500µs versus 1–10ms for PostgreSQL on NVMe SSDs. There is no disk seek, no buffer cache miss, no WAL write on the critical path.
- **Data structure store:** Redis is not a key-value store in the naive sense. It stores strings, hashes, lists, sets, sorted sets, bitmaps, streams, and more. The data structure choice determines which operations are efficient.
- **Store:** it persists data (optionally). It is not purely a cache — data survives restarts if configured to do so.

**What Redis is not:**

Redis does not replace PostgreSQL. It has no SQL, no complex querying, no joins, no ACID multi-table transactions, no schema. Data is stored in RAM — you cannot store terabytes cheaply. Redis handles specific access patterns at very high speed. PostgreSQL handles durability, complex queries, and relational integrity.

The two are complements, not competitors.

## Why Pravah Needs Redis

Pravah has several requirements that PostgreSQL handles poorly and Redis handles excellently:

**Runner heartbeats:** 10,000 runners sending heartbeats every 10 seconds. A heartbeat is a tiny write (`runner-id → {load, capacity, timestamp}`) that must expire automatically if the runner goes silent. In PostgreSQL, this requires: INSERT/UPDATE, an indexed column for expiry, and a background job to clean up expired records. In Redis: `SET runner:heartbeat:001 "{...}" EX 30` — one command, automatic expiry, microsecond latency.

**Leader election:** the Scheduler Service must have exactly one active leader across all pods. Leader election requires atomic compare-and-set semantics with a timeout. Redis provides this natively: `SET scheduler:leader scheduler-pod-1 NX PX 30000` — set only if not exists (`NX`), expire in 30 seconds (`PX 30000`).

**Pipeline config cache:** Execution Service reads pipeline configuration before every job dispatch. The config lives in PostgreSQL. Reading it from PostgreSQL on every job dispatch adds 5–10ms and database load. Caching it in Redis for 5 minutes makes the common case a 200µs Redis GET.

**Rate limiting:** per-tenant API rate limits require a counter that increments on every request and expires every second. PostgreSQL row updates per second for this volume is expensive. Redis atomic `INCR` with `EXPIRE` handles millions of rate limit checks per second trivially.

**Real-time pub/sub:** when a job completes, the UI dashboard needs to update immediately. WebSocket connections for dashboard streaming need a signal delivery mechanism. Redis pub/sub delivers messages to all subscribers in under a millisecond, without durability overhead (this is a fire-and-forget signal, not a durable event — Kafka handles the durable event).

## Redis Data Structures Pravah Uses

### Strings — The Universal Type

The simplest type. A string key maps to a string value (which can be serialized JSON, a number, or binary data).

```
Key:   runner:heartbeat:runner-001
Value: {"load":0.73,"capacity":4,"active_jobs":2,"region":"eu-west"}
TTL:   30 seconds (auto-expires if runner stops sending)
```

Commands: `GET`, `SET`, `SETNX`, `SETEX`, `INCR`, `DECR`, `APPEND`.

**Atomic increment for rate limiting:**

```
Key:   ratelimit:tenant:megacorp:api:/pipelines:2024-01-15T10:00:35
Value: 42 (number of API calls this second)
TTL:   2 seconds (expires soon after the window closes)
```

`INCR` is atomic — no race condition between threads checking and incrementing. `EXPIRE` is set once on key creation. Both operations complete in under 1ms.

### Hashes — Objects Without Serialization

A hash maps multiple field-value pairs under one key. Like a dictionary or a row.

```
Key:   runner:state:runner-001
Fields:
  status:       "ACTIVE"
  active_jobs:  "2"
  max_jobs:     "4"
  fencing_token:"42"
  last_seen:    "1705312800000"
```

Commands: `HGET`, `HSET`, `HMSET`, `HGETALL`, `HINCRBY`.

Advantage over JSON string: can update individual fields without reading, deserializing, modifying, and re-serializing the whole object.

```
HSET runner:state:runner-001 active_jobs 3
-- Atomic increment of just one field
HINCRBY runner:state:runner-001 active_jobs 1
```

Pravah uses hashes for runner state and tenant quota counters.

### Sorted Sets — Ordered Collections

A sorted set stores members each with a floating-point score. Members are ordered by score. Supports range queries by score.

```
Key:   scheduler:pending_pipelines
Members:
  pipe-abc → score: 1705316400  (Unix timestamp: next run at 10:00)
  pipe-def → score: 1705316460  (next run at 10:01)
  pipe-xyz → score: 1705316500  (next run at 10:01:40)
```

Commands: `ZADD`, `ZRANGEBYSCORE`, `ZREM`, `ZCARD`.

```
-- Get all pipelines scheduled to run before now
ZRANGEBYSCORE scheduler:pending_pipelines -inf 1705316400
```

Pravah uses sorted sets for the scheduler's in-memory next-run index. The scheduler polls Redis for pipelines due in the next 60 seconds rather than querying PostgreSQL every second.

### Lists — Queues and Stacks

Ordered list of strings. Supports push/pop from both ends.

```
Key:   notification:queue:tenant:megacorp
Values: [notification-1, notification-2, notification-3, ...]
```

Commands: `LPUSH`, `RPUSH`, `LPOP`, `RPOP`, `BLPOP` (blocking pop).

Pravah uses lists for lightweight notification queues within a tenant — less critical than Kafka events, used for real-time in-app notifications.

### Sets — Deduplication

Unordered collection of unique strings. Membership checks are O(1).

```
Key:   runners:active
Members: runner-001, runner-003, runner-007, runner-012
```

Commands: `SADD`, `SREM`, `SISMEMBER`, `SMEMBERS`, `SINTER`, `SUNION`.

Pravah uses sets for tracking active runner IDs per tenant, and for deduplication of processed event IDs in exactly-once processing.

## Caching Patterns

### Cache-Aside (Lazy Loading) — Pravah's Primary Pattern

The application manages the cache explicitly:

```
Read request:
  1. Check Redis cache
  2. If HIT: return cached value (fast path)
  3. If MISS: query PostgreSQL
  4. Write result to Redis with TTL
  5. Return result

Write request:
  1. Write to PostgreSQL (source of truth)
  2. Invalidate or update Redis cache
```

```java
@Service
public class PipelineConfigService {

    private static final Duration CACHE_TTL = Duration.ofMinutes(5);

    public PipelineConfig getConfig(String pipelineId) {
        String cacheKey = "pipeline:config:" + pipelineId;

        // Step 1: Check cache
        String cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return deserialize(cached);       // cache hit — 200µs
        }

        // Step 2: Cache miss — fetch from PostgreSQL
        PipelineConfig config = pipelineRepository.findById(pipelineId)
            .orElseThrow(() -> new PipelineNotFoundException(pipelineId));

        // Step 3: Populate cache
        redisTemplate.opsForValue().set(cacheKey, serialize(config), CACHE_TTL);

        return config;
    }

    public void updateConfig(String pipelineId, PipelineConfig updated) {
        // Step 1: Write to PostgreSQL (source of truth)
        pipelineRepository.save(updated);

        // Step 2: Invalidate cache — next read will fetch fresh from PG
        redisTemplate.delete("pipeline:config:" + pipelineId);
    }
}
```

**Why invalidate on write rather than update the cache?** Race condition: if two requests update the same pipeline simultaneously, the second update might write its value to the cache after the first, but then the first update overwrites PostgreSQL. Cache would contain stale data. Invalidation is safe — next read fetches fresh from the source of truth.

**Cache-aside is Pravah's primary pattern because:**
- Application controls what gets cached (selective caching)
- Cache failures don't affect writes (PostgreSQL is always updated first)
- Tolerates Redis downtime — cache miss falls through to PostgreSQL
- Simple to reason about

### Write-Through — For High Consistency Requirements

Write always goes to both PostgreSQL and Redis atomically (within the same write operation):

```
Write request:
  1. Write to PostgreSQL
  2. Write to Redis (same data, same transaction window)
  3. Both succeed or both fail
```

Pravah uses write-through for tenant quota state — quota consumption must be reflected in Redis immediately to be useful for rate limiting:

```java
@Transactional
public void consumeQuota(String tenantId, int units) {
    // Write to PostgreSQL for durability
    quotaRepository.consumeUnits(tenantId, units);

    // Write to Redis for fast rate limiting reads
    String key = "quota:remaining:" + tenantId;
    redisTemplate.opsForValue().decrement(key, units);
}
```

**Trade-off:** every write now has two I/O operations. Write latency increases. Acceptable when read consistency is more important than write speed.

### Write-Behind (Write-Back) — For Maximum Write Throughput

The application writes to Redis only. A background process periodically flushes Redis state to PostgreSQL.

```
Write request:
  1. Write to Redis only (fast — microseconds)
  2. Background: flush Redis → PostgreSQL every N seconds
```

Pravah uses write-behind for runner heartbeat aggregation — the live heartbeat data in Redis is authoritative, and PostgreSQL is updated periodically for historical records:

```java
// Runner sends heartbeat — write to Redis only (fast path)
public void updateHeartbeat(String runnerId, HeartbeatData data) {
    String key = "runner:heartbeat:" + runnerId;
    redisTemplate.opsForValue().set(key, serialize(data), Duration.ofSeconds(30));
}

// Scheduled job: flush heartbeat snapshots to PostgreSQL every 30s
@Scheduled(fixedDelay = 30000)
public void persistHeartbeats() {
    Set<String> keys = redisTemplate.keys("runner:heartbeat:*");
    for (String key : keys) {
        String data = redisTemplate.opsForValue().get(key);
        if (data != null) {
            runnerRepository.upsertHeartbeat(extractRunnerId(key), deserialize(data));
        }
    }
}
```

**Risk:** if Redis fails before the flush, data is lost. Only use for data where loss is acceptable (heartbeats can be reconstructed from the next heartbeat).

## Distributed Locks with Redis

Distributed locks were introduced in chapter 1.4 (Leader Election). Here is the full implementation detail.

### The SET NX PX Pattern

```
SET lock:key unique-value NX PX 30000
```

- `NX`: set only if the key does not exist (atomic compare-and-set)
- `PX 30000`: expire the key after 30,000ms (30 seconds) — prevents deadlock if the holder crashes

```java
public boolean acquireLock(String lockKey, String lockValue, long ttlMs) {
    Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, Duration.ofMillis(ttlMs));
    return Boolean.TRUE.equals(acquired);
}
```

The `lockValue` must be unique per lock holder (UUID or pod ID). This prevents a lock holder from releasing a lock it no longer owns:

```lua
-- Lua script for atomic check-and-delete (runs atomically on Redis server)
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

```java
public boolean releaseLock(String lockKey, String lockValue) {
    String script = """
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
        """;
    Long result = redisTemplate.execute(
        new DefaultRedisScript<>(script, Long.class),
        List.of(lockKey),
        lockValue
    );
    return Long.valueOf(1L).equals(result);
}
```

**Why a Lua script?** The check (`GET`) and delete (`DEL`) must be atomic — another process could acquire the lock between the `GET` and `DEL` if they were separate commands. Lua scripts on Redis are atomic.

### Fencing Tokens with Locks

As discussed in chapter 1.4, Redis TTL-based locks have a subtle problem: a process can hold a lock, pause (GC, slow network), the lock expires, another process acquires the lock, and both processes now believe they hold the lock.

Fencing tokens solve this: the lock returns an incrementing token. Every operation that requires lock protection sends the token to the resource. The resource rejects requests with a token lower than the highest seen.

```java
public LockResult acquireLockWithToken(String lockKey) {
    long token = redisTemplate.opsForValue().increment("lock:counter:" + lockKey);
    String lockValue = "holder:" + podId + ":token:" + token;

    boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, Duration.ofSeconds(30));

    return new LockResult(acquired, token);
}
```

The database operation includes the token:
```sql
-- Only update if fencing token is higher than stored
UPDATE runners SET active_jobs = active_jobs + 1, fencing_token = 43
WHERE id = 'runner-001' AND fencing_token < 43;
```

If the update affects 0 rows, a stale lock holder tried to write — rejected.

### Redlock — Multi-Node Distributed Locks

Redis single-node locks fail if the Redis node crashes between the `SET NX` and the lock expiry. The lock is lost, and no process can acquire it until TTL expires (or forever if the node doesn't recover).

Redlock acquires the lock on a majority of N independent Redis nodes:

```
5 Redis nodes (no replication between them)
Acquire lock on at least 3 (majority)
If fewer than 3 succeed: release all acquired locks, retry
If 3 or more succeed: lock is held
```

**Pravah's use of Redlock:** only for the Scheduler leader election — the highest-stakes lock in the system. A failed scheduler election means no pipelines are triggered. The cost of Redlock (3 Redis round trips instead of 1) is acceptable for this use case.

For runner heartbeat TTL locks and rate limiting, single-node Redis is sufficient — lock failures are self-healing (next heartbeat re-establishes the key).

Pravah uses the Redisson library for Redlock:
```java
RLock lock = redissonClient.getMultiLock(
    redissonClient1.getLock("scheduler:leader"),
    redissonClient2.getLock("scheduler:leader"),
    redissonClient3.getLock("scheduler:leader")
);
lock.lock(30, TimeUnit.SECONDS);
```

## Redis Pub/Sub — Real-Time Signals

Redis pub/sub delivers messages to all subscribers on a channel instantly. Unlike Kafka, messages are not persisted — if no subscriber is listening when a message is published, it is lost.

**When to use Redis pub/sub over Kafka:**

| | Redis Pub/Sub | Kafka |
|---|---|---|
| Durability | None — fire and forget | Durable, replicated |
| Delivery | At most once | At least once (with consumers) |
| Latency | Microseconds | 5–50ms |
| Use case | Real-time UI signals | Business events, audit |
| Subscribers | Any number, simultaneous | Consumer groups |
| Replay | No | Yes |

Pravah uses Redis pub/sub for WebSocket dashboard updates:

```
Job completes on runner
  │
  ▼
Execution Service receives job result via gRPC
  │
  ▼
1. Writes event to Kafka (durable — job.results topic)
2. Publishes to Redis channel (transient — for live UI)
  │
  ▼
Redis pub/sub: channel "job:events:tenant:megacorp"
  │
  ▼
All API Gateway pods subscribed to this channel
receive the message simultaneously
  │
  ▼
Each API Gateway pod pushes via WebSocket to
connected browsers for tenant megacorp
```

This solves the WebSocket scaling problem: in a multi-pod deployment, a user's WebSocket connection is pinned to one pod. Job completion events originate from whichever pod handled the gRPC callback. Without a broker, the completion event only reaches the pod that handled it — which might not be the pod holding the user's WebSocket. Redis pub/sub broadcasts to all pods:

```java
// Execution Service: broadcast job completion
@Service
public class JobCompletionPublisher {

    public void publishCompletion(JobResult result) {
        String channel = "job:events:tenant:" + result.getTenantId();
        String message = serialize(result);
        redisTemplate.convertAndSend(channel, message);
    }
}

// API Gateway: listen for job events and push to WebSocket
@Component
public class JobEventListener implements MessageListener {

    @Override
    public void onMessage(Message message, byte[] pattern) {
        JobResult result = deserialize(message.getBody());
        // Push to all WebSocket sessions for this tenant
        webSocketSessions.getForTenant(result.getTenantId())
            .forEach(session -> session.sendMessage(result));
    }
}
```

## Redis Persistence and Failure Modes

Redis is in-memory. What happens when it fails?

### Persistence Options

**RDB (Redis Database snapshots):** periodic point-in-time snapshots to disk. Fast to load on restart. Loses data since the last snapshot (seconds to minutes).

**AOF (Append-Only File):** every write command is appended to a log file. On restart, Redis replays the log. Can be configured to `fsync` every second or after every write.

```ini
# redis.conf — Pravah configuration
# RDB snapshots for fast recovery
save 900 1     # save if 1 key changed in 900s
save 300 10    # save if 10 keys changed in 300s
save 60 10000  # save if 10000 keys changed in 60s

# AOF for minimizing data loss
appendonly yes
appendfsync everysec    # sync every second (balance between safety and performance)
```

### Pravah's Data Loss Tolerance per Use Case

```
Runner heartbeats:    Loss OK — next heartbeat re-establishes the key
Rate limit counters:  Loss OK — brief burst allowed after restart
Leader election lock: Loss OK — new election happens automatically after TTL
Pipeline config cache: Loss OK — falls through to PostgreSQL on miss
Scheduler next-run set: Rebuilt from PostgreSQL on startup — Loss OK

Only case requiring care:
Tenant quota counters: Loss means quota enforcement gap
  → Write-through to PostgreSQL ensures durable state
  → Redis is a fast read cache; PostgreSQL is authoritative
```

The key insight: Pravah treats Redis as a performance layer, not the source of truth (except for the scheduler sorted set, which is rebuilt from PostgreSQL on startup). PostgreSQL remains the durable source of truth for all important state.

### Redis Sentinel vs Redis Cluster

**Redis Sentinel:** monitors Redis master; promotes a replica to master if the master fails. Applications talk to Sentinel to discover the current master. One master at a time.

**Redis Cluster:** data sharded across multiple master nodes. Each master has replicas. Automatic failover per shard. Supports datasets larger than single-node RAM.

Pravah uses **Redis Sentinel** for its simplicity — Pravah's Redis data footprint (heartbeats, locks, caches) fits comfortably in a single master's memory. Redis Cluster adds operational complexity (cluster routing, slot management, cross-slot operation restrictions) that is not warranted at current scale.

Configuration via Redisson:
```yaml
redisson:
  sentinelServersConfig:
    masterName: pravah-redis
    sentinelAddresses:
      - redis://redis-sentinel-0:26379
      - redis://redis-sentinel-1:26379
      - redis://redis-sentinel-2:26379
    readMode: SLAVE      # read from replicas when possible
    password: ${REDIS_PASSWORD}
```

## Key Namespacing in Pravah

With multiple services sharing one Redis instance, key collisions are prevented by a consistent naming convention:

```
{service}:{entity}:{id}:{field}

runner:heartbeat:runner-001             → string, TTL 30s
runner:state:runner-001                 → hash, no TTL
scheduler:leader                        → string (lock), TTL 30s
scheduler:pending                       → sorted set, no TTL
pipeline:config:pipe-abc               → string (JSON), TTL 5m
quota:remaining:megacorp               → string (integer), no TTL
ratelimit:api:megacorp:/pipelines:GET  → string (counter), TTL 2s
lock:counter:scheduler:leader          → string (fencing counter), no TTL
job:events:tenant:megacorp             → pub/sub channel (ephemeral)
session:user:user-abc                  → hash (JWT session cache), TTL 1h
```

This prevents Runner Service from accidentally reading Pipeline Service keys and enables pattern-based key operations when needed:
```
SCAN 0 MATCH runner:heartbeat:* COUNT 100
```

## System Design Interview Angles

**"How does Pravah use Redis alongside PostgreSQL — what is each responsible for?"**

> Redis and PostgreSQL are complements, not alternatives. PostgreSQL is the source of truth for all durable, relational data — pipeline configurations, job state, audit logs. It handles ACID transactions, complex queries, and data that must survive any failure.
>
> Redis handles ephemeral, high-frequency, low-latency access patterns. Runner heartbeats with TTL-based auto-expiry — setting a key with `EX 30` is one atomic command, versus a PostgreSQL row update plus a background expiry job. Leader election via `SET NX PX` — atomic compare-and-set in microseconds. Pipeline config caching — a 5-minute TTL cache reduces PostgreSQL reads by 99% for hot configs during a job execution surge. Rate limiting — `INCR` plus `EXPIRE` handles millions of counter operations per second.
>
> The principle: PostgreSQL for durability and correctness, Redis for speed and ephemerality. Redis failures fall through to PostgreSQL. PostgreSQL is never a cache fallback for Redis — it is always the authoritative store.

**"How does Pravah handle the WebSocket scaling problem with multiple pods?"**

> WebSocket connections are pinned to a specific API Gateway pod. A job completion event from the Execution Service arrives on whichever pod handled the gRPC callback — which might not be the pod holding the user's WebSocket connection.
>
> Redis pub/sub solves this: when a job completes, Execution Service publishes to a Redis channel keyed by tenant ID. All API Gateway pods are subscribed to these channels. Every pod receives the message simultaneously and pushes it to any WebSocket sessions for that tenant it holds. The message delivery latency is under a millisecond.
>
> Importantly, this is in addition to Kafka — the durable `job.results` event still goes to Kafka for audit, billing, and replay. The Redis pub/sub message is a transient signal purely for real-time UI updates. If a pod is restarting when the message is published, it misses it — the next Kafka poll will catch it up, with slightly higher latency.

**"How do distributed locks work in Redis, and what can go wrong?"**

> The core primitive is `SET key value NX PX ttl` — set the key only if it does not exist (`NX`), with an automatic expiry (`PX`). The value is a unique identifier for the lock holder (pod ID or UUID). Release uses a Lua script that checks the value before deleting — ensuring you only release your own lock.
>
> The failure mode: a lock holder pauses (GC stop-the-world, slow network, machine hibernation) longer than the TTL. The lock expires. Another process acquires the lock. The paused process wakes up, believes it still holds the lock, and proceeds. Now two processes hold the lock simultaneously.
>
> Fencing tokens prevent this: the lock returns a monotonically increasing token. The protected resource (PostgreSQL row) stores the highest token it has seen. Operations with a token lower than the stored value are rejected with a version conflict error. The paused process's stale operation fails — the newer lock holder's operations succeed.
>
> For Pravah's highest-stakes lock (Scheduler leader election), we use Redlock across three independent Redis nodes. This prevents the single-node failure case where Redis crashes and the lock is lost — a majority of nodes must agree the lock was acquired.

## Key Takeaways

1. **Redis is an in-memory data structure store** — not a simple key-value cache. Strings, hashes, sorted sets, lists, sets, and pub/sub channels each serve distinct use cases.

2. **Pravah's Redis use cases:**
   - Runner heartbeats: strings with TTL auto-expiry
   - Leader election: `SET NX PX` with Redlock for critical locks
   - Config caching: cache-aside with 5-minute TTL, invalidate on write
   - Rate limiting: atomic `INCR` + `EXPIRE`
   - Scheduler index: sorted set by next-run timestamp
   - WebSocket fanout: pub/sub channels per tenant

3. **Three caching patterns:**
   - Cache-aside (lazy loading): read-through on miss, invalidate on write — Pravah's default
   - Write-through: write to both PostgreSQL and Redis atomically — for quota state
   - Write-behind: write to Redis only, flush to PostgreSQL periodically — for heartbeats

4. **Distributed locks require three things:** `SET NX PX` for atomic acquisition, Lua script for atomic release, and fencing tokens to handle the expired-lock-with-paused-holder failure case.

5. **Redis pub/sub solves WebSocket multi-pod fanout.** Message published to a channel → all subscribed pods receive it simultaneously → each pod pushes to its local WebSocket sessions. Not a replacement for Kafka — complements it for ephemeral real-time signals.

6. **Redis is not the source of truth.** PostgreSQL holds all durable state. Redis is a performance layer. Redis failures fall through to PostgreSQL gracefully.

7. **Persistence configuration:** RDB snapshots + AOF `fsync everysec` for Pravah's Redis. Most cached data can tolerate loss — rebuilt from PostgreSQL on restart. Quota counters use write-through for durability.

8. **Redis Sentinel for HA.** Single master with replicas and automatic failover via Sentinel. Redis Cluster not needed at current scale — adds operational complexity not yet warranted.
