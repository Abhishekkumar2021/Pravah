# 3.10 Cache Invalidation Strategies

## The Two Hard Problems

Phil Karlton's famous observation: "There are only two hard things in Computer Science: cache invalidation and naming things." Cache invalidation is genuinely hard because a cache is a copy of data that lives elsewhere. The moment the original data changes, every copy is potentially stale — and you must either know about the change to update the copies, or accept that copies may be stale for some bounded time.

A cache that returns wrong data is worse than no cache at all. A cache that is invalidated too aggressively provides no performance benefit. The goal is to find the point where cache hit rates are high, data is fresh enough for the use case, and the invalidation mechanism is reliable.

---

## Cache-Aside (Lazy Loading)

The application controls all cache interactions. The cache is consulted before every database read, and populated on a miss.

```
Read path:
  1. Check cache: cache.get(key)
  2. If HIT: return cached value
  3. If MISS: query database, store result in cache, return result

Write path:
  1. Write to database
  2. DELETE the cache key (invalidate)
```

```java
public Pipeline getPipeline(String pipelineId) {
    String cacheKey = "pipeline:" + pipelineId;

    Pipeline cached = redis.get(cacheKey, Pipeline.class);
    if (cached != null) return cached;     // cache hit

    Pipeline pipeline = db.findById(pipelineId);  // database miss
    redis.set(cacheKey, pipeline, Duration.ofMinutes(10));
    return pipeline;
}

public void updatePipeline(Pipeline pipeline) {
    db.save(pipeline);
    redis.delete("pipeline:" + pipeline.getId());  // invalidate cache
}
```

**Why DELETE on write rather than UPDATE?**

Writing an updated value to the cache on a write seems efficient — avoid the next cache miss. But it creates a race condition:

```
t=1: Writer A reads pipeline from DB (balance=100)
t=2: Writer B writes balance=200 to DB, deletes cache key
t=3: Writer B finishes — DB has 200, cache is empty (correct)
t=4: Writer A writes balance=150 to DB, puts balance=150 in cache
     DB has 150, cache has 150 (consistent, but business logic may be wrong)

But if Writer A instead puts balance=100 (the value it read at t=1):
     DB has 150, cache has 100 — INCONSISTENT
```

DELETE is safe because it forces the next reader to go to the database and see the most current value. Writing a specific value to the cache risks stale-write bugs.

**Pros:** Simple, works with any database. Only caches what is actually read.  
**Cons:** First request after invalidation always misses (cold start); thundering herd when many requests hit a cold key simultaneously.

## Write-Through

The cache is updated synchronously on every write. The database and cache are updated together.

```
Write path:
  1. Write to database
  2. Write to cache (same value)

Read path:
  1. Check cache
  2. If HIT: return cached value (cache always has current data)
  3. If MISS: query database (only on first access or cache eviction)
```

```java
public void updatePipeline(Pipeline pipeline) {
    db.save(pipeline);                          // write to database
    redis.set("pipeline:" + pipeline.getId(),   // write to cache
        pipeline, Duration.ofHours(1));
}
```

**Pros:** Cache always contains current data; no stale reads immediately after writes; no thundering herd because the cache is always warm.  
**Cons:** Every write takes two operations (DB + cache); adds latency to the write path; caches data that may never be read (cache pollution with write-heavy workloads where read/write keys don't overlap).

---

## Write-Behind (Write-Back)

The application writes to the cache first; the cache asynchronously flushes to the database. The cache is the primary write target.

```
Write path:
  1. Write to cache (fast)
  2. Cache queues the write for asynchronous DB flush

Read path:
  1. Read from cache (always current — it IS the primary)
```

**Pros:** Extremely low write latency (write completes when cache accepts it).  
**Cons:** Data loss risk — if the cache crashes before the async flush, writes are lost. Rarely used in systems where durability matters. Appropriate for analytics counters, rate limiting state, and other data where loss is acceptable.

---

## TTL-Based Expiration

Every cached item has a time-to-live (TTL). After the TTL expires, the item is evicted and the next read goes to the database.

```java
redis.set("pipeline:" + id, pipeline, Duration.ofMinutes(5));
// After 5 minutes, the key automatically expires
// Next read goes to DB and re-caches
```

**This is not really cache invalidation** — it is cache expiration. The cache does not know the data changed; it simply discards it after a time interval. Data can be stale for up to one TTL period.

TTL-based expiration is:
- Simple (no write-side logic required)
- Safe (always eventually consistent with the DB)
- Appropriate when some staleness is acceptable

Choosing the right TTL:
- Too short: cache hit rates are low; performance benefit is small
- Too long: stale data window is large; reads return outdated values

**Rule of thumb:** TTL should be shorter than the expected time between writes. If a pipeline is updated once per day on average, a 1-hour TTL provides good hit rates while keeping staleness bounded.

## Event-Driven Invalidation

Rather than TTL or write-side invalidation in the application, changes in the database publish events that cache consumers subscribe to. This decouples the writer from cache management.

```
Database change (via Outbox or CDC):
  → Kafka event: { "type": "PipelineUpdated", "pipeline_id": "abc" }

Cache consumer (subscribes to pipeline.events):
  → Receives PipelineUpdated
  → redis.delete("pipeline:abc")
  → All cache instances receive the invalidation
```

**This solves the multi-instance problem:** if 5 instances of the Pipeline Service each have their own Redis connection, a write by instance 1 must invalidate the cache for instances 2, 3, 4, and 5. With event-driven invalidation, all instances subscribe to the same Kafka topic and receive the same invalidation event.

In Pravah, pipeline events published to `pipeline.events` (from the event store in ADR-017) are consumed by all Pipeline Service instances to invalidate their local Redis cache. This is more reliable than write-side invalidation in the application because:
- Events are durable (Kafka) — an invalidation is not lost if an instance is restarted
- All instances see the same events regardless of which instance handled the write

## The Thundering Herd Problem

When a popular cache key expires or is invalidated, many requests simultaneously find a cache miss and all race to the database. The result is a burst of database load at the exact moment the cache is cold.

**Solution 1 — Mutex (single-flight):**

```java
// Only one goroutine/thread fetches from DB; others wait for the result
String cacheKey = "pipeline:" + id;
Pipeline result = singleFlightMap.computeIfAbsent(cacheKey, key -> {
    Pipeline cached = redis.get(key, Pipeline.class);
    if (cached != null) return cached;
    Pipeline fromDb = db.findById(id);
    redis.set(key, fromDb, Duration.ofMinutes(10));
    return fromDb;
});
```

**Solution 2 — Probabilistic early expiration:**

Refresh the cache slightly before it expires, probabilistically, to avoid the cliff when TTL reaches zero:

```java
// If expiration is within 30 seconds and random probability triggers, refresh now
if (remainingTtl < 30 && Math.random() < 0.1) {
    // Refresh in background without making the caller wait
    executor.submit(() -> refreshCache(key));
}
```

**Solution 3 — Staggered TTLs:**

Add jitter to TTLs so that keys don't all expire at the same time:

```java
Duration ttl = Duration.ofMinutes(10).plus(
    Duration.ofSeconds(ThreadLocalRandom.current().nextInt(60))
);
redis.set(key, value, ttl);
```

## Which Strategy for Which Use Case

| Use Case | Strategy |
|----------|----------|
| Pipeline definitions (read-heavy, infrequent writes) | Cache-aside + event-driven invalidation on `pipeline.events` |
| Tenant configuration (read-heavy, very infrequent writes) | Write-through + long TTL (1 hour) |
| User session data | Cache-aside + short TTL (15 minutes) |
| Rate limiting counters | No DB at all — Redis is the source of truth (write-behind semantics) |
| Job queue state | No cache — job state must be authoritative in PostgreSQL |
| API response caching (idempotent reads) | Cache-aside + TTL (5 minutes) + ETag validation |

---

## Application in Pravah

Pipeline Service uses **cache-aside + event-driven invalidation**:

- Cache key: `pipeline:{pipeline_id}` with 10-minute TTL as a safety net
- Invalidation: consumer of `pipeline.events` Kafka topic deletes the cache key on every `PipelineUpdated` event
- This provides instant invalidation (event-driven) with TTL as a fallback

Tenant configuration uses **write-through**:

- Tenant config is updated very rarely (once per week on average)
- Writing to both DB and cache on update keeps the cache always warm
- 1-hour TTL as a safety net in case the cache is corrupted

Rate limiting uses **Redis as the primary store** (no DB). The rate limiting state does not need durability — if Redis restarts, counters reset and users get a brief reprieve. This is acceptable.
