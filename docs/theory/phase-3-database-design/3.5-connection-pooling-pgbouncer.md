# 3.5 Connection Pooling & PgBouncer

## The Problem: PostgreSQL Connections Are Expensive

Every connection to PostgreSQL is not a lightweight handle. It is a full OS process.

When a client connects to PostgreSQL, the `postmaster` process forks a new backend process dedicated to that connection. That backend process:
- Allocates its own memory (typically 5–10 MB per connection)
- Loads shared catalog caches
- Maintains its own transaction state
- Stays alive for the entire duration of the connection

For a single application server with 10 threads, this is fine. For Pravah — dozens of microservices, each running 10–50 Spring Boot threads per pod, deployed as multiple replicas — the math breaks quickly.

**Pravah's connection demand at moderate load:**

```
Service             Pods    Threads/Pod    Connections
──────────────────────────────────────────────────────
Pipeline Service      3         20              60
Scheduler Service     2         20              40
Execution Service     5         30             150
Runner Service        3         20              60
Billing Service       2         20              40
Metadata Service      2         20              40
Audit Service         2         10              20
──────────────────────────────────────────────────────
Total                                          410
```

410 connections just at moderate load. PostgreSQL's default `max_connections = 100`. Even with `max_connections = 500` — each connection consumes ~8 MB of RAM, so 500 connections = 4 GB of RAM spent purely on connection overhead, before any actual work happens.

At peak load, Pravah might scale to:
- Execution Service: 10 pods × 30 threads = 300 connections from one service
- Total platform: 800–1,000+ connections

This causes three distinct failures:

**Failure 1: Connection exhaustion.** New service instances cannot connect. Spring Boot fails to acquire a pool connection and throws `Unable to acquire JDBC Connection`. Jobs stop processing.

**Failure 2: Memory pressure.** PostgreSQL server with 500 idle connections consumes several gigabytes just in backend process overhead, reducing memory available for `shared_buffers`, working memory, and OS cache.

**Failure 3: Thundering herd.** After a deployment, all pods restart simultaneously and each tries to establish all their pool connections at once. PostgreSQL receives hundreds of connection requests in seconds, causing CPU spikes and delaying startup.

## PgBouncer — The Solution

PgBouncer is a lightweight connection pooler that sits between applications and PostgreSQL. Applications connect to PgBouncer. PgBouncer maintains a small pool of real PostgreSQL connections and multiplexes application requests across them.

```
┌────────────────────────────────────────────────────────────────┐
│                       Pravah Services                          │
│                                                                │
│  Pipeline Svc   Scheduler Svc   Execution Svc   Runner Svc    │
│  (60 threads)   (40 threads)    (150 threads)   (60 threads)  │
└────────────┬────────────┬──────────────┬────────────┬─────────┘
             │            │              │            │
             └────────────┴──────────────┴────────────┘
                                  │
                        410 application connections
                                  │
                    ┌─────────────▼─────────────┐
                    │         PgBouncer          │
                    │                            │
                    │  Receives 410 connections  │
                    │  Maintains pool of 50–100  │
                    │  real PostgreSQL connections│
                    │  Multiplexes efficiently   │
                    └─────────────┬─────────────┘
                                  │
                        50–100 real connections
                                  │
                    ┌─────────────▼─────────────┐
                    │         PostgreSQL         │
                    │                            │
                    │  max_connections = 200     │
                    │  (leaves headroom for      │
                    │   migrations, admin, DBA)  │
                    └────────────────────────────┘
```

The application still uses 410 threads, all waiting for a connection when needed. But only the threads actually executing a query hold a real PostgreSQL connection. Idle threads hold nothing.

## Three Pooling Modes

PgBouncer supports three modes with fundamentally different behaviors.

### Mode 1: Session Pooling

A PostgreSQL connection is assigned when the client connects and released when the client disconnects.

```
Client A connects → gets PG connection C1
Client A executes queries using C1
Client A disconnects → C1 returned to pool
Client B connects → gets C1 (or another)
```

Session pooling provides zero benefit for Pravah. An application thread holding an idle pool connection continues to hold a PgBouncer connection, which continues to hold a real PostgreSQL connection. No multiplexing happens.

### Mode 2: Transaction Pooling

A PostgreSQL connection is assigned when a transaction starts (`BEGIN` or the first statement) and released when the transaction ends (`COMMIT` or `ROLLBACK`).

```
Client A: BEGIN
  → PgBouncer assigns PostgreSQL connection C1 to Client A
Client A: UPDATE jobs SET status='RUNNING' WHERE id='xyz'
Client A: COMMIT
  → PgBouncer releases C1 back to pool

Client B: BEGIN
  → PgBouncer assigns C1 to Client B (or any available connection)
```

Between transactions, Client A holds no PostgreSQL connection. If Client A is idle 99% of the time (waiting for the next HTTP request), the underlying PostgreSQL connection is free for other clients during that idle time.

**This is the mode Pravah uses.** It provides the strongest multiplexing.

### Mode 3: Statement Pooling

A PostgreSQL connection is assigned per individual SQL statement and released after each statement.

Multi-statement transactions are impossible in this mode because each statement gets a different connection. Effectively unusable for application code that relies on transactions.

---

## Why Transaction Mode Is the Right Choice for Pravah

Consider the connection lifecycle in a typical Pravah request:

```
HTTP request arrives at Execution Service
  │
  ▼
Thread picked up from thread pool
  │
  ▼
Business logic runs (validation, gRPC call to Pipeline Service, etc.)
— no DB needed yet, no connection held —
  │
  ▼
BEGIN TRANSACTION
  → PgBouncer assigns PostgreSQL connection (connection held)
  │
  ▼
INSERT into jobs table
UPDATE outbox table
COMMIT
  → PgBouncer releases connection (connection free)
  │
  ▼
HTTP response sent
```

The thread is busy for ~50ms total. The actual database transaction takes ~5ms. In session pooling, the thread holds the connection for 50ms (idle 45ms). In transaction pooling, the connection is held for only 5ms and freed for other threads for the remaining 45ms.

At 150 concurrent Execution Service threads: session pooling needs up to 150 connections. Transaction pooling, with average 10% transaction active ratio, needs only ~15 connections to serve the same load.

## The Gotchas of Transaction Pooling

Transaction pooling is powerful but breaks several PostgreSQL features that assume a connection is sticky to a client across transactions.

### Gotcha 1: Prepared Statements

Prepared statements are connection-scoped in PostgreSQL. When you prepare a statement, it is stored in the backend process for that connection.

```sql
PREPARE get_job (uuid) AS SELECT * FROM jobs WHERE id = $1;
EXECUTE get_job('abc-123');
```

In transaction pooling: `PREPARE` executes on connection C1. On the next transaction, PgBouncer might assign connection C2. `EXECUTE get_job(...)` fails — C2 has no knowledge of this prepared statement.

**Pravah's solution:** disable server-side prepared statements in PgBouncer configuration (`max_prepared_statements = 0`). Spring Boot's HikariCP and Hibernate work correctly with this — they fall back to plain statement execution. The performance difference is negligible compared to the connection multiplexing gains.

If prepared statement caching is needed, use PgBouncer's client-side prepared statement support (`max_prepared_statements > 0`) which tracks and re-prepares statements on whichever server connection is assigned.

### Gotcha 2: Session-Level State (`SET` Variables)

`SET` commands in PostgreSQL modify session-level variables on the current connection:

```sql
SET search_path TO tenant_megacorp, public;
SET lock_timeout = 5000;
SET application_name = 'execution-service';
```

In transaction pooling: these are set on connection C1. Next transaction, PgBouncer assigns C2. The `SET` is gone. The query runs with default `search_path`, potentially reading from the wrong schema.

**Pravah's solutions:**

Option A — Set in `pgbouncer.ini` as startup parameters (applied to all connections):
```ini
[databases]
pravah_execution_db = host=postgresql port=5432 dbname=pravah_execution_db
    application_name=execution-service
```

Option B — Use `SET LOCAL` inside the transaction (scoped to the transaction, not the session):
```sql
BEGIN;
  SET LOCAL search_path TO public;
  SELECT * FROM jobs WHERE ...;
COMMIT;
-- SET LOCAL is automatically rolled back with the transaction
```

Option C — Avoid `SET` entirely in application code. Use connection URL parameters for `search_path`. Configure defaults at the database level:
```sql
ALTER DATABASE pravah_execution_db SET search_path TO public;
ALTER ROLE pravah_execution_user SET statement_timeout TO 30000;
```

Pravah uses Option C as the primary approach, with Option B as a fallback for per-request needs.

### Gotcha 3: Advisory Locks

PostgreSQL advisory locks are session-scoped. `pg_advisory_lock(key)` locks until `pg_advisory_unlock(key)` or the session ends.

In transaction pooling: Lock acquired on C1. Transaction commits, C1 returned to pool. Lock remains held on C1 but the application thread no longer has C1. Another thread gets C1 and unknowingly holds the lock. The original thread tries to unlock on C2 — the lock is not there.

**Pravah's solution:** never use advisory locks in transaction-pooling mode. Use transaction-scoped advisory locks instead (`pg_advisory_xact_lock`), which are automatically released at transaction end:

```sql
BEGIN;
  SELECT pg_advisory_xact_lock(hashtext('scheduler-lock'));
  -- critical section
COMMIT;
-- lock automatically released
```

Or better: use Redis distributed locks for coordination across services (covered in 3.8).

### Gotcha 4: `LISTEN` / `NOTIFY`

PostgreSQL's `LISTEN`/`NOTIFY` mechanism registers a listener on a specific connection. In transaction pooling, the connection is not persistent — the listener disappears.

**Pravah's solution:** don't use `LISTEN`/`NOTIFY` for inter-service communication. Use Kafka for all async events. Redis pub/sub for lightweight real-time signals. If PostgreSQL `NOTIFY` is needed (e.g., for Debezium trigger-based CDC), use a dedicated long-lived connection outside PgBouncer for that purpose.

## Pravah's PgBouncer Configuration

Pravah deploys one PgBouncer instance per database, running as a sidecar container in the same Kubernetes pod as the PostgreSQL primary (via Patroni).

```ini
[databases]
pravah_pipeline_db  = host=127.0.0.1 port=5432 dbname=pravah_pipeline_db
pravah_execution_db = host=127.0.0.1 port=5432 dbname=pravah_execution_db
pravah_runner_db    = host=127.0.0.1 port=5432 dbname=pravah_runner_db
pravah_billing_db   = host=127.0.0.1 port=5432 dbname=pravah_billing_db
pravah_audit_db     = host=127.0.0.1 port=5432 dbname=pravah_audit_db

[pgbouncer]
listen_addr         = 0.0.0.0
listen_port         = 5432

# Transaction pooling — the right mode for Pravah
pool_mode           = transaction

# Maximum server-side (PostgreSQL) connections per database
default_pool_size   = 25

# Reserve connections for admin and emergency use
reserve_pool_size   = 5
reserve_pool_timeout = 3

# Maximum client connections PgBouncer accepts
max_client_conn     = 1000

# How long clients wait for a connection from the pool
client_login_timeout = 60
query_wait_timeout   = 30

# Disable server-side prepared statements for transaction pooling
max_prepared_statements = 0

# Health checking — detect dead server connections
server_check_delay  = 30
server_check_query  = SELECT 1

# TLS for client connections (internal K8s network — mTLS via service mesh)
client_tls_sslmode  = allow

# Logging
log_connections     = 0    # too noisy at scale
log_disconnections  = 0
log_pooler_errors   = 1
stats_period        = 60   # emit stats every 60s

# Authentication
auth_type           = scram-sha-256
auth_file           = /etc/pgbouncer/userlist.txt
```

**Pool sizing rationale:**

`default_pool_size = 25` means PgBouncer maintains up to 25 real PostgreSQL connections per database. For `execution_db` handling 150 application threads: at any given moment roughly 10–15 threads are in an active transaction (10% of 150). 25 connections provides comfortable headroom.

The formula for initial sizing:

```
active_connections_needed = total_threads × avg_transaction_duration / avg_request_duration
                          = 150 × 5ms / 50ms
                          = 15

pool_size = active_connections_needed × 1.5 (buffer)
          = ~23 → round to 25
```

Adjust based on observed `pgbouncer_pool_stats.sv_used` (active server connections) in Prometheus.

## Connection String in Pravah Services

Every Pravah service connects to PgBouncer, not directly to PostgreSQL:

```yaml
# execution-service application.yaml
spring:
  datasource:
    url: jdbc:postgresql://pgbouncer:5432/pravah_execution_db
    username: pravah_execution_user
    password: ${EXECUTION_DB_PASSWORD}
    hikari:
      # HikariCP pool — application-level pool of PgBouncer connections
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000      # wait up to 30s for a pool connection
      idle-timeout: 600000           # release idle connections after 10 min
      max-lifetime: 1800000          # recycle connections after 30 min
      keepalive-time: 300000         # keepalive every 5 min
      # Disable prepared statement caching (transaction pooling requirement)
      connection-init-sql: "SET application_name='execution-service'"
      data-source-properties:
        prepareThreshold: 0          # disable server-side prepared statements
```

**Two levels of pooling in Pravah:**

```
Application Thread
      │
      ▼
HikariCP (application-level pool)
  max-pool-size: 20 connections to PgBouncer
      │
      ▼
PgBouncer (process-level multiplexer)
  25 real connections to PostgreSQL
      │
      ▼
PostgreSQL
```

HikariCP manages connections from the application to PgBouncer. PgBouncer multiplexes those onto real PostgreSQL connections. The application never needs to wait for a PostgreSQL connection as long as PgBouncer has capacity.

## Observing PgBouncer in Production

PgBouncer exposes an admin interface via a virtual `pgbouncer` database:

```sql
-- Connect to PgBouncer admin
psql -h pgbouncer -p 5432 -U pgbouncer pgbouncer

-- Pool statistics — the most important view
SHOW POOLS;
-- Output columns:
-- database:   which database
-- user:       which user
-- cl_active:  clients currently executing a query
-- cl_waiting: clients waiting for a server connection ← alert if > 0 for long
-- sv_active:  server connections currently in use
-- sv_idle:    server connections idle in pool
-- sv_used:    server connections used at least once
-- maxwait:    longest time a client has been waiting ← alert if > 1s

-- Per-database stats
SHOW STATS;
-- total_requests, total_received, total_sent, total_query_time, avg_req, avg_query

-- Current server connections
SHOW SERVERS;

-- Current client connections
SHOW CLIENTS;
```

**Prometheus metrics via pgbouncer_exporter:**

Critical alerts for Pravah:

```yaml
# Alert: clients waiting for connections — pool is undersized
- alert: PgBouncerPoolExhausted
  expr: pgbouncer_pools_client_waiting_connections > 5
  for: 30s
  annotations:
    summary: "PgBouncer pool exhausted — {{ $labels.database }}"

# Alert: pool utilization above 80% — scale soon
- alert: PgBouncerPoolHighUtilization
  expr: pgbouncer_pools_server_active_connections /
        pgbouncer_pools_server_idle_connections > 0.8
  for: 2m

# Alert: maximum wait time exceeded
- alert: PgBouncerHighWaitTime
  expr: pgbouncer_pools_client_maxwait_seconds > 1
  for: 30s
```

## PgBouncer in Pravah's Kubernetes Architecture

Each PostgreSQL primary runs a PgBouncer sidecar in the same pod. Services address PgBouncer via a Kubernetes Service (ClusterIP):

```yaml
# Each database has its own PgBouncer service
apiVersion: v1
kind: Service
metadata:
  name: pgbouncer-execution-db
  namespace: pravah-data
spec:
  selector:
    app: postgresql-execution-db
    role: primary
  ports:
    - port: 5432
      targetPort: 6432    # PgBouncer listens on 6432, PostgreSQL on 5432
```

Services connect to `pgbouncer-execution-db:5432` via Kubernetes DNS. If the primary fails and Patroni promotes a standby, the Service selector switches to the new primary pod, and PgBouncer reconnects automatically.

**Why sidecar instead of standalone PgBouncer deployment:**

A standalone PgBouncer pod introduces a single point of failure between services and PostgreSQL. A sidecar per primary eliminates this — if the primary fails, its pod (including PgBouncer) fails together, and the Service immediately routes to the new primary's PgBouncer sidecar.

## FAANG Interview Angles

**"Why does Pravah use PgBouncer in transaction mode rather than session mode?"**

> PostgreSQL connections are OS processes — each consumes 5–10 MB of RAM regardless of whether it is doing work. Pravah has roughly 400 application threads across all services at moderate load. In session mode, PgBouncer provides no multiplexing — 400 threads means 400 PostgreSQL processes, consuming 2–4 GB of RAM just for connection overhead, and we'd need `max_connections = 500`.
>
> In transaction mode, a PostgreSQL connection is held only while a transaction is executing — typically 5–10ms out of a 50ms request. With a 10% active ratio across 400 threads, we need only ~40 concurrent PostgreSQL connections. `pool_size = 25` per database, with multiple databases, keeps total PostgreSQL connections under 150.
>
> The constraint is that transaction mode breaks session-scoped features: server-side prepared statements, `SET` variables, advisory locks, and `LISTEN`/`NOTIFY`. Pravah handles these explicitly — prepared statements disabled, `SET` moved to database-level defaults or `SET LOCAL` inside transactions, Redis for distributed locks, Kafka for async notifications.

**"What breaks when you use PgBouncer in transaction mode and how do you fix it?"**

> Three main gotchas. First, prepared statements — they are stored on a specific PostgreSQL backend process. When PgBouncer routes the next transaction to a different backend, the prepared statement doesn't exist there. Fix: set `prepareThreshold = 0` in JDBC to disable server-side prepared statements. The performance difference is negligible.
>
> Second, `SET` variables — `SET search_path` or `SET lock_timeout` modifies the session on one connection, but the next transaction lands on a different connection with different state. Fix: configure defaults at the database or role level using `ALTER DATABASE` or `ALTER ROLE`. Use `SET LOCAL` inside transactions for per-transaction overrides.
>
> Third, advisory locks — they are session-scoped, so the lock is held on a connection the application no longer has access to. Fix: use transaction-scoped advisory locks (`pg_advisory_xact_lock`) which release on commit, or use Redis distributed locks for anything that crosses service boundaries.

**"How do you size the PgBouncer pool for Pravah's Execution Service?"**

> The formula: `pool_size = total_threads × (avg_transaction_time / avg_request_time) × safety_factor`.
>
> Execution Service: 150 threads across 5 pods, average transaction 5ms, average request 50ms. So `150 × (5/50) × 1.5 = ~22`, round to 25.
>
> I validate this against `pgbouncer_pools_server_active_connections` in Prometheus. If observed active connections consistently exceed 20 out of 25, I increase the pool. If `client_waiting` is non-zero for more than a few seconds, the pool is too small and jobs are being delayed waiting for a database connection.

## Key Takeaways

1. **PostgreSQL connections are OS processes.** Each costs 5–10 MB of RAM. 500 connections = 4 GB RAM in overhead alone. `max_connections` is not a soft limit — exceeding it means new connections are rejected.

2. **PgBouncer is mandatory at Pravah's scale.** Without it, 400+ application threads would require 400+ PostgreSQL processes, exhausting both connection limits and memory.

3. **Transaction pooling is the right mode.** Connections are held only during active transactions. 400 threads with a 10% active ratio need only ~40 real connections — not 400.

4. **Transaction mode breaks three things — handle each explicitly:**
   - Prepared statements: disable with `prepareThreshold = 0`
   - Session `SET` variables: use `ALTER DATABASE`/`ALTER ROLE` defaults, or `SET LOCAL`
   - Advisory locks: use `pg_advisory_xact_lock` (transaction-scoped), or Redis

5. **Two-tier pooling in Pravah:** HikariCP (application → PgBouncer) + PgBouncer (process → PostgreSQL). Each tier has its purpose.

6. **Pool sizing formula:** `threads × (transaction_ms / request_ms) × 1.5`. Validate against `sv_active` metric; alert on `cl_waiting > 0`.

7. **Sidecar deployment:** PgBouncer runs as a sidecar next to the PostgreSQL primary pod. Avoids a standalone single point of failure. Patroni failover automatically reroutes via Kubernetes Service.

8. **Never use `LISTEN`/`NOTIFY` through PgBouncer.** Use Kafka for async events, Redis pub/sub for lightweight signals.
