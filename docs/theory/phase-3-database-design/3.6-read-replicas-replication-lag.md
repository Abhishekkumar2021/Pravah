# 3.6 Read Replicas & Replication Lag

## The Problem: One Database, Two Workloads

PgBouncer solved connection exhaustion. The PostgreSQL primary now handles a manageable number of real connections. But there is a different problem: the primary is doing two fundamentally different types of work simultaneously.

**Write workload (Execution Service):**
- 10,000 job inserts per minute
- 30,000–50,000 status update mutations per minute
- Short transactions (5–10ms each)
- WAL generation at high rate
- Autovacuum running constantly

**Read workload (Dashboard, Reports, API):**
- Dashboard: "Show all jobs for tenant megacorp in last 24 hours" — index scan, result set of hundreds of rows
- SLA report: "What percentage of jobs completed in under 30 seconds per tenant this month?" — aggregate across millions of rows
- Billing: month-end report scanning full `billing_events` partition
- Lineage: graph traversal across audit events

These workloads have conflicting resource profiles. The write workload wants fast I/O, minimal lock contention, and predictable latency. The heavy read workload wants lots of `work_mem` for sorts and hash joins, sequential scans across large tables, and can afford to take seconds.

When they run on the same PostgreSQL instance:
- A month-end billing report scanning 50 million rows evicts hot pages from `shared_buffers`, degrading write throughput for minutes
- Autovacuum (needed for writes) competes with read queries for I/O
- A slow SLA report query holding a snapshot prevents MVCC dead tuple cleanup
- Peak write load degrades read latency, making dashboards slow precisely when users need them most — during a job execution surge

The solution is to separate reads from writes physically: **read replicas**.

## How PostgreSQL Streaming Replication Works

PostgreSQL's streaming replication is built on top of WAL — the same Write-Ahead Log used for crash recovery (covered in 3.2).

### The Replication Architecture

```
┌────────────────────────────────────┐
│           PRIMARY                  │
│                                    │
│  Write → WAL Buffer                │
│           │                        │
│           ▼                        │
│  WAL Disk (pg_wal/)                │
│           │                        │
│           ▼ WAL sender process     │
│    ─────────────────────►          │
└───────────────────────────────────-┘
                │
        Network: WAL stream
                │
┌───────────────▼────────────────────┐
│           STANDBY (Replica)        │
│                                    │
│    WAL receiver process            │
│           │                        │
│           ▼                        │
│  WAL applied to local data files   │
│  (standby is a read-only copy)     │
│                                    │
│  Hot Standby: read queries run     │
│  against the current state of      │
│  local data files ✅               │
└────────────────────────────────────┘
```

The primary runs a WAL sender process for each standby. The standby runs a WAL receiver process. WAL records stream continuously from primary to standby over a TCP connection. The standby's recovery process applies WAL records to its local data files in the same order they were written on the primary.

**Hot Standby mode:** the standby allows read-only queries while applying WAL. This is what makes read replicas useful — they serve reads while continuously replicating writes.

### Synchronous vs Asynchronous Replication

**Asynchronous replication (Pravah's default for replicas):**
- Primary writes WAL, sends to standby, and returns `COMMIT` to the application immediately — without waiting for the standby to confirm receipt
- Maximum performance, minimal write latency impact
- Risk: if the primary crashes after commit but before the standby receives the WAL, the standby is missing some committed transactions
- Replication lag: the standby is always slightly behind the primary (milliseconds to seconds depending on network and load)

**Synchronous replication (Pravah's Patroni HA cluster):**
- Primary waits for at least one standby to confirm WAL receipt before returning `COMMIT`
- No data loss on primary failure — at least one standby has everything
- Write latency increases by ~1 round trip over the network
- Pravah uses this for the HA standby (the Patroni failover candidate), not for read replicas

```
┌──────────────┐  sync  ┌──────────────┐
│   PRIMARY    │───────►│  HA STANDBY  │  ← Patroni failover candidate
│  (writes)    │        │  (sync replica│    synchronous_commit=on
└──────────────┘        └──────────────┘
        │
        │ async
        ▼
┌──────────────┐        ┌──────────────┐
│  READ REPLICA│        │  READ REPLICA│
│  (eu-west)   │        │  (ap-south)  │  ← async, slight lag acceptable
└──────────────┘        └──────────────┘
```

## Replication Lag — The Core Problem

Replication lag is the delay between when a transaction commits on the primary and when its changes become visible on the replica. It is always non-zero in asynchronous replication.

### Why Lag Happens

**Network transit:** WAL records travel over the network. Even at 1 Gbps between availability zones, there is physical latency (typically 1–5ms within a cloud region).

**WAL application backlog:** during a write surge, the primary generates WAL faster than the standby can apply it. The standby's recovery process applies WAL records sequentially. If the primary has a burst of 50,000 updates in 100ms, the standby may take 200–300ms to apply all of them. During this time, the replica is behind.

**Long-running queries on the replica:** a read query on the replica acquires a snapshot at start time. MVCC requires that the replica retain all row versions newer than the oldest running query's snapshot. If a billing report runs for 5 minutes on the replica, the replica cannot apply WAL records that would conflict with that snapshot. This is `hot_standby_feedback = on` behavior — discussed below.

### Measuring Replication Lag

```sql
-- On the primary: how far behind is each replica?
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,       -- time between primary write and standby write
    flush_lag,       -- time between primary flush and standby flush
    replay_lag,      -- time between primary flush and standby replay
    sync_state
FROM pg_stat_replication
ORDER BY replay_lag DESC;

-- On the replica: how far behind am I?
SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag;
```

`replay_lag` is the most important: it tells you how old the data is on the replica right now.

## Read Routing in Pravah

Not all reads can tolerate lag. Pravah classifies reads into two tiers and routes them accordingly.

### Reads That Must Go to the Primary

**After-write reads:** a user creates a pipeline via POST, then immediately loads the pipeline detail page (GET). If the GET hits a replica with 200ms lag, it returns a 404 — the row hasn't replicated yet. The user sees a broken UI.

```
POST /pipelines → writes to primary
GET  /pipelines/pipe-abc → must go to primary
                           (replica may not have it yet)
```

**Critical consistency reads:** before dispatching a job, Execution Service reads the pipeline configuration. This must come from the primary — a stale configuration from a replica could dispatch jobs with an old, incorrect version.

**Transactional reads:** any read that is part of a write transaction must go through the primary. This includes optimistic locking reads (`SELECT ... FOR UPDATE`), saga state reads before updates, and idempotency key checks.

### Reads That Can Go to Replicas

**Dashboard queries:** "Show me all jobs for tenant megacorp in the last hour." A 1–3 second lag is invisible to users — jobs that completed 1 second ago showing up 1 second late is perfectly acceptable for a monitoring dashboard.

**Reporting and analytics:** month-end billing reports, SLA computations, historical job trend analysis. These queries scan millions of rows. They belong on replicas — both because lag is acceptable for historical data, and because they would severely impact write throughput on the primary.

**Search and catalog reads:** lineage queries, pipeline search, dataset catalog browsing. Users do not notice seconds of lag in search results.

**Audit queries:** audit logs are append-only. Reading last week's audit records can tolerate replication lag entirely — those records are long since stable.

### Routing Implementation in Pravah

Spring Boot does not support automatic read/write splitting natively. Pravah implements it via an `AbstractRoutingDataSource`:

```java
public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {

    private static final ThreadLocal<Boolean> useReplica = new ThreadLocal<>();

    public static void routeToReplica() {
        useReplica.set(true);
    }

    public static void routeToPrimary() {
        useReplica.remove();
    }

    @Override
    protected Object determineCurrentLookupKey() {
        return Boolean.TRUE.equals(useReplica.get())
            ? DataSourceType.REPLICA
            : DataSourceType.PRIMARY;
    }
}
```

Paired with a `@ReadOnly` annotation that triggers routing before the transaction opens:

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Transactional(readOnly = true)
public @interface ReadOnly {}

@Aspect
@Component
public class ReadOnlyRoutingAspect {

    @Around("@annotation(ReadOnly)")
    public Object routeToReplica(ProceedingJoinPoint joinPoint) throws Throwable {
        ReadWriteRoutingDataSource.routeToReplica();
        try {
            return joinPoint.proceed();
        } finally {
            ReadWriteRoutingDataSource.routeToPrimary();
        }
    }
}
```

Usage in services:

```java
@Service
public class JobQueryService {

    // Route to replica — lag is acceptable for dashboard reads
    @ReadOnly
    public Page<JobSummary> getDashboardJobs(String tenantId, Pageable pageable) {
        return jobRepository.findByTenantIdAndStatusIn(
            tenantId,
            List.of("PENDING", "RUNNING", "FAILED"),
            pageable
        );
    }

    // Route to primary — must be fresh (called right after job creation)
    @Transactional
    public JobDetail getJobDetail(String jobId) {
        return jobRepository.findById(jobId)
            .orElseThrow(() -> new JobNotFoundException(jobId));
    }
}
```

Both data sources point to PgBouncer endpoints — primary PgBouncer and replica PgBouncer respectively:

```yaml
datasources:
  primary:
    url: jdbc:postgresql://pgbouncer-execution-primary:5432/pravah_execution_db
  replica:
    url: jdbc:postgresql://pgbouncer-execution-replica:5432/pravah_execution_db
```

## Handling Replication Lag Gracefully

### The Read-Your-Writes Problem

A user creates a pipeline, then immediately clicks to view it. The write went to the primary. The read hits the replica. The replica is 200ms behind. The user sees a 404 or stale data.

**Pravah's solution — sticky session after writes:**

After any write, return a `replication_token` (the primary's current LSN at the time of the write) in the response header:

```
POST /pipelines
Response headers:
  X-Replication-Token: 0/1A2B3C00
```

On the subsequent GET, the client sends this token back:

```
GET /pipelines/pipe-abc
Request headers:
  X-Replication-Token: 0/1A2B3C00
```

The API gateway checks whether the replica has caught up to this LSN:

```sql
-- On the replica: have we replayed past the client's token?
SELECT pg_last_wal_replay_lsn() >= '0/1A2B3C00'::pg_lsn;
```

If not: route to the primary. If yes: route to the replica.

Alternative (simpler): after a write operation, sticky-route all reads for that session to the primary for 1–2 seconds. Sufficient for most replication lag scenarios without tracking LSNs.

### Preventing Replica Lag from Long Queries

Long-running read queries on the replica cause `hot_standby_feedback`. When enabled, the replica tells the primary which transactions it needs to retain for ongoing queries. The primary cannot vacuum those rows — they might still be needed by the replica's query snapshot.

```ini
# postgresql.conf on replica
hot_standby_feedback = on   # prevents conflicts but causes primary bloat risk
```

**Pravah's approach:**

- `hot_standby_feedback = on` for the HA standby (used for failover — must stay healthy)
- `hot_standby_feedback = off` for read replicas (billing reports, analytics)
- `max_standby_streaming_delay = 30s` on analytics replicas — if the replica falls more than 30 seconds behind due to a conflict, PostgreSQL cancels the conflicting query on the replica with: `ERROR: canceling statement due to conflict with recovery`

This means analytics queries must be designed to be cancellable and retriable. Application code wraps these with retry logic:

```java
@Retry(maxAttempts = 3, backoff = @Backoff(delay = 2000))
@ReadOnly
public BillingReport generateMonthlyReport(String tenantId, YearMonth month) {
    // If cancelled by replication conflict, retry automatically
    return billingRepository.computeMonthlyReport(tenantId, month);
}
```

## Primary Failover and Replica Behavior

Pravah uses Patroni for automatic PostgreSQL failover. When the primary fails:

1. Patroni detects the failure (via health check timeout, typically 10–30s)
2. Patroni promotes the HA standby (synchronous replica) to primary
3. Patroni updates the Kubernetes Service endpoints — the primary ClusterIP now points to the new primary
4. Other standbys are reconfigured to replicate from the new primary
5. PgBouncer sidecar on the new primary begins accepting connections

**What happens to read replicas during this window:**

Read replicas continue serving reads from their last replicated state. They are now further behind (primary was down, no new WAL arriving). Queries continue to work against stale-but-consistent data.

Once the new primary is elected, replicas receive its WAL stream and catch up (typically seconds to minutes depending on lag at time of failure).

**What happens to Pravah services during failover:**

- Writes fail for 10–30 seconds (the failover window)
- PgBouncer queues connection attempts during this time (up to `client_login_timeout`)
- Spring Boot HikariCP retries failed connection attempts
- In-flight transactions that were on the old primary are rolled back (PostgreSQL guarantees this)
- After failover, services reconnect and retry

Saga compensating transactions handle jobs that were in-flight during the primary failure — Execution Service detects missing heartbeats and re-dispatches or cancels appropriately.

**Configuration per replica type:**

```ini
# Read replica (dashboard queries)
max_standby_streaming_delay = 5s      # cancel queries if > 5s lag conflict
hot_standby_feedback        = on      # prevent unnecessary query cancels
work_mem                    = 32MB    # dashboard queries: modest memory
max_connections             = 150     # smaller; PgBouncer in front

# Analytics replica (reports, billing)
max_standby_streaming_delay = 60s     # allow longer before cancelling
hot_standby_feedback        = off     # don't hold primary bloat hostage
work_mem                    = 512MB   # reports need memory for sorts/joins
max_parallel_workers        = 8       # parallelism for large aggregations
max_connections             = 50      # fewer, larger queries
```

## FAANG Interview Angles

**"Pravah's dashboards are slow when there's a write surge. How do you fix this?"**

> The root cause is read/write contention on the same PostgreSQL primary. During a write surge — 10,000 job inserts per minute plus 50,000 status updates — the primary is doing heavy I/O, running autovacuum, and generating WAL. Dashboard queries compete for the same buffer cache, I/O bandwidth, and CPU.
>
> The fix is read replicas with explicit read routing. Streaming replication asynchronously copies all changes to one or more standbys. Dashboard queries — which can tolerate 1–3 seconds of lag — are routed to the read replica via `AbstractRoutingDataSource`. This completely separates read I/O from write I/O.
>
> The replica has its own `shared_buffers` warmed with the hot pages for dashboard queries. Its autovacuum runs independently. Write surges on the primary don't affect replica read latency.

**"How do you handle the read-your-writes problem with replicas?"**

> After a write, the client gets a response header containing the primary's current WAL LSN at the time of the write — a `replication_token`. On the subsequent read, if the client sends this token, the routing layer checks `pg_last_wal_replay_lsn() >= token_lsn` on the replica. If the replica has caught up to that point, serve from replica. If not, route to primary.
>
> A simpler version: after any write, the session is sticky to the primary for a configurable window (1–2 seconds). This handles the common case of immediate after-write reads without tracking LSNs per request.

**"What happens to your read replicas during a primary failover?"**

> Read replicas continue serving reads from their last-replicated state during the failover window. They have consistent, albeit slightly stale, data. Queries work correctly — they're just reading data from before the failure point.
>
> Once Patroni promotes the HA standby to primary (typically 10–30 seconds), the read replicas detect the new primary via Patroni's configuration update and reconnect their WAL receivers to the new primary. They then catch up on any WAL that was generated after the last data they received.
>
> The HA standby is a synchronous replica — it has all committed transactions from the old primary. When promoted, it has zero data loss. Read replicas were async, so they might be a few seconds behind the old primary's last state, but they catch up from the new primary quickly.

## Key Takeaways

1. **Read/write separation is necessary at Pravah's scale.** Writes and heavy reads have conflicting resource profiles — running them on the same instance degrades both.

2. **Streaming replication works via WAL.** Primary generates WAL → WAL sender streams to standby → WAL receiver applies to standby data files → Hot Standby allows reads during recovery.

3. **Asynchronous replication introduces lag.** The replica is always slightly behind the primary. This is a fundamental trade-off for not impacting write latency.

4. **Not all reads can use replicas.** After-write reads, transactional reads, and critical consistency reads must go to the primary. Dashboard queries, reports, and historical reads can use replicas.

5. **Routing in Pravah:** `AbstractRoutingDataSource` + `@ReadOnly` annotation routes queries to the appropriate data source before the transaction opens.

6. **Read-your-writes is solved** by LSN-tracking replication tokens or session-level primary stickiness for 1–2 seconds after writes.

7. **Long queries on replicas cause conflicts.** `hot_standby_feedback = on` for dashboard replicas (prevents cancellations), `off` for analytics replicas (protects primary from bloat). `max_standby_streaming_delay` cancels queries that block replication beyond the threshold.

8. **Patroni topology:** one synchronous HA standby (failover candidate, zero data loss), one or more async read replicas (dashboard), one analytics replica (heavy reports). Each optimized differently.

## What's Next

Replicas handle read scale. But there is a ceiling. A single PostgreSQL primary — even with replicas taking all reads — has a maximum write throughput. Pravah's `job_runs` table at 100M rows/month per large tenant, across thousands of tenants, eventually exceeds what a single write path can handle.
