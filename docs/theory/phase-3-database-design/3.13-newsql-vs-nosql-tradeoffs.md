# 3.13 NewSQL vs NoSQL — Trade-offs and When to Choose

## The Context: Why This Question Arises

Every large-scale system eventually faces this question: as data grows and traffic scales, should we keep PostgreSQL, switch to a NoSQL database (MongoDB, Cassandra, DynamoDB), or adopt a NewSQL database (CockroachDB, TiDB, Spanner)?

The answer depends on which properties your workload actually requires, and which properties you are willing to sacrifice. Phil Karlton's CAP theorem (Chapter 1.1) showed that distributed systems can have at most two of Consistency, Availability, and Partition tolerance. But in practice, the real trade-offs are richer — and the decision space is between relational (ACID, joins, SQL), NoSQL (flexible schema, horizontal scale, eventual consistency), and NewSQL (horizontal scale with ACID).

---

## The NoSQL Landscape

NoSQL databases share one characteristic: they relax relational constraints (no ACID by default, no joins, no fixed schema) to achieve horizontal scalability. But they are not a single category — they solve different problems.

**Document stores (MongoDB, Firestore):**

Store JSON-like documents. Flexible schema — documents in the same collection can have different fields. Queries are document-centric (find a document by its fields); joins between collections require application-level logic or `$lookup` aggregation.

Good for: content management, user profiles, product catalogs — entities with variable structure and mostly accessed as a whole.

Bad for: relational data with many joins, financial transactions, anything requiring ACID across multiple documents.

**Wide-column stores (Apache Cassandra, DynamoDB):**

Store rows organized by a partition key and sort key. All data for a partition key lives on the same node — reads for a single partition are extremely fast. Writes are always local (no coordination with other nodes). Built for massive write throughput and horizontal scalability.

Good for: time-series data (metrics, events, logs), IoT sensor readings, activity feeds — high-volume writes with predictable access patterns.

Bad for: ad-hoc queries (you must know the access pattern at schema design time), ACID transactions across partitions, complex filtering.

**Key-value stores (Redis, DynamoDB in simple mode):**

The simplest data model: key → value. Lookups by key are O(1) and extremely fast. No rich query language beyond key lookup.

Good for: caching, sessions, rate limiting, feature flags, distributed locks.

Bad for: anything requiring querying by value, range scans, or relationships.

**Graph databases (Neo4j, Amazon Neptune):**

Optimized for traversing relationships between entities. Native graph storage with O(1) traversal per hop (no table join needed). Excellent for social graphs, recommendation engines, fraud detection (pattern matching in transaction graphs).

Bad for: tabular data, simple CRUD, analytical workloads.

## The NewSQL Family

NewSQL databases provide **horizontal write scalability with ACID guarantees**. They achieve this through different means:

**CockroachDB:** Distributed SQL. Every node can accept writes. Sharding is automatic and transparent. Uses Raft consensus per range (16MB chunks of key space) for consistency. SQL-compatible (PostgreSQL wire protocol). Global transactions via timestamp-based serializable isolation.

**TiDB:** MySQL-compatible distributed SQL. Separates storage (TiKV — distributed key-value) from compute (TiDB — SQL processing). Scales reads and writes independently.

**Google Spanner:** Globally distributed, externally consistent transactions. Uses TrueTime (atomic clocks + GPS) for global linearizability. Available only as a cloud service.

**PlanetScale:** Serverless MySQL with sharding based on Vitess. Horizontal scaling via virtual sharding.

## The Real Trade-offs

### ACID vs Scale

PostgreSQL provides ACID transactions on a single node. Scaling writes requires either:
1. Accepting read replicas only (writes scale horizontally only for reads)
2. Application-level sharding (complexity moves to application code)
3. NewSQL (CockroachDB) which provides multi-node writes with ACID

NoSQL databases sacrifice ACID for multi-node write scalability. Cassandra's "last write wins" conflict resolution can silently overwrite data. MongoDB before version 4.0 was not ACID-compliant across documents.

**Rule**: if you need multi-node writes with ACID guarantees, you need NewSQL, not NoSQL.

### Schema Flexibility vs Query Power

MongoDB's flexible schema is appealing when requirements are unclear. But query power is proportional to schema structure. Elasticsearch can search any field because it indexes everything — but it cannot join with another index. PostgreSQL's relational model enables joins, foreign keys, and complex aggregations because the schema enforces structure.

Flexible schema is a short-term advantage and a long-term liability. As data accumulates with variable structure, queries become defensive: `WHERE field IS NOT NULL` everywhere, null handling in every query, no enforcement of required fields.

**Rule**: use flexible schema (NoSQL) only when the variability is genuine and permanent, not when requirements are unclear.

### Write Throughput vs Query Flexibility

Cassandra achieves its write throughput by giving up ad-hoc queries. You cannot efficiently do `SELECT * FROM events WHERE event_type = 'FAILED'` in Cassandra unless you partition by `event_type`. All queries must be expressible as "give me all rows in partition X, sorted by Y." This is the fundamental limitation: the access pattern must be known at design time and encoded in the partition/clustering key.

PostgreSQL allows you to add an index later for any query pattern. NoSQL requires you to know your queries upfront.

**Rule**: if your query patterns are unknown or evolving, PostgreSQL's flexibility is valuable. If your query patterns are fixed and your volume is massive (billions of writes/day), Cassandra's write throughput justifies its constraints.

### Operational Complexity

A 3-node PostgreSQL cluster with Patroni (ADR-022) is well-understood. Engineers know how to operate it. A CockroachDB cluster has Raft consensus groups, leaseholder assignments, range rebalancing, and clock skew sensitivity — significantly more complex.

MongoDB's schema-less nature creates operational risks: without schema validation, bad data accumulates. Cassandra's compaction strategies (STCS, LCS, TWCS) must be chosen per table based on the read/write mix.

**Rule**: operational complexity is a real cost. Don't adopt a more complex database unless the performance or scale benefit is demonstrably necessary.

## Decision Framework

```
Does the workload require multi-node writes at JDBC scale?
  NO → Use PostgreSQL (single-node primary, read replicas for scale)
  YES → Does it require ACID across writes?
    YES → NewSQL (CockroachDB, TiDB)
    NO → NoSQL (Cassandra for write-heavy time-series; MongoDB for document-centric)

Is the primary access pattern:
  Full-text search / relevance ranking → Elasticsearch
  Graph traversal (social, fraud) → Neo4j / Amazon Neptune
  Sub-millisecond key-value lookup → Redis
  Analytics over large datasets (columnar) → DuckDB, BigQuery, Snowflake
  Everything else with moderate scale → PostgreSQL
```

## Why Pravah Uses PostgreSQL (and Specific Supplementary Stores)

Pravah's data is fundamentally relational:
- Pipelines have tenants, steps have pipelines, jobs have steps, executions have jobs — all foreign key relationships
- Multi-table transactions are common: creating a job + publishing to the outbox must be atomic
- Query patterns are diverse and evolving — new monitoring queries, new audit queries, new projection queries
- Write volume is bounded: a platform processing 10,000 pipeline runs/day generates manageable write volume for a single primary

The answer to "why not Cassandra" or "why not MongoDB" for Pravah's core data is simple: Pravah's workload does not require the trade-offs those systems impose. The write volume does not justify giving up joins and ACID. Patroni (ADR-022) provides HA. Table partitioning (3.4) manages data volume. Read replicas handle read scale.

**The supplementary stores Pravah adds are justified by specific requirements:**

| Store | Specific Requirement | Why Not PostgreSQL |
|-------|---------------------|-------------------|
| Redis | Sub-millisecond caching, distributed locks, pub/sub | PostgreSQL cannot hold advisory locks across processes reliably at scale; pub/sub needs a broker |
| Elasticsearch | Full-text search, lineage graph traversal | PostgreSQL's tsvector is insufficient for relevance ranking; recursive CTEs are slow for deep graph traversal |
| MinIO | Large binary artifact storage | PostgreSQL BYTEA is not designed for 50GB files |
| Kafka | Event streaming, fan-out to many consumers | PostgreSQL's LISTEN/NOTIFY is not a durable message bus |

Each supplementary store solves a specific problem that PostgreSQL is not designed for. Adding stores arbitrarily — "let's use MongoDB because it's flexible" — adds operational complexity without solving a real problem.
