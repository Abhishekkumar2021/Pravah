# 3.1 Database Per Service — Why & How

## The Shared Database Anti-Pattern

Many teams building microservices start with a shared database: one PostgreSQL instance containing tables for all services. The reasoning is appealing — simpler infrastructure, easy cross-table JOINs, less to manage.

```
┌─────────────────────────────────────────────────┐
│              SHARED DATABASE                    │
│  pipelines | jobs | runners | billing | audit   │
└─────────────────────────────────────────────────┘
         ▲           ▲           ▲           ▲
   Pipeline     Scheduler   Runner      Billing
   Service      Service     Service     Service
```

Here is what happens in production at scale.

---

## Why Shared Databases Fail

**Problem 1: Schema coupling — teams block each other**

Runner Service needs to add a column to the `runners` table:
```sql
ALTER TABLE runners ADD COLUMN docker_version VARCHAR(50);
```

But Pipeline Service also queries the `runners` table. It must be updated simultaneously. Both services must deploy together. Teams cannot deploy independently. Deployment coordination meetings become the norm. Microservices lose their core benefit.

**Problem 2: Performance interference — one bad query kills everyone**

Billing Service runs month-end reports:
```sql
SELECT tenant_id, SUM(compute_units)
FROM billing_events
GROUP BY tenant_id;
-- Scans 100 million rows, takes 45 minutes
```

During those 45 minutes: Pipeline Service timeouts, Scheduler slowdowns, Runner registration failures. One team's analytical query causes an outage for every other team.

**Problem 3: Single point of failure**

Shared PostgreSQL goes down:
- Pipeline Service: down
- Scheduler Service: down
- Runner Service: down
- Billing Service: down
- **All of Pravah: down**

One database failure equals total platform failure.

**Problem 4: Scaling impossibility**

Different services have different storage requirements:
- Pipeline Service: fast transactional writes (10K inserts/sec)
- Billing Service: complex analytical reads
- Runner Service: fast key-value heartbeat lookups
- Audit Service: append-only time-series

A single database cannot be optimized for all four simultaneously. Vertical scaling is expensive. Horizontal sharding with cross-service joins is a nightmare.

**Problem 5: Technology lock-in**

Runner heartbeats fit Redis perfectly (TTL, fast atomic operations). Lineage traversal fits Neo4j (graph queries). Log search fits Elasticsearch (inverted index). Audit trails fit append-only PostgreSQL. A shared database forces everything into one technology chosen by historical accident, not fitness.

---

## Database Per Service — The Solution

Every service owns its data exclusively. No other service reads from or writes to it directly. Cross-service data access happens only via API or Kafka.

```
┌──────────────────────────┬───────────────────────────────┐
│  Pipeline Service        │  PostgreSQL: pipeline_db      │
│                          │  Tables: pipelines, events,   │
│                          │          outbox, snapshots    │
├──────────────────────────┼───────────────────────────────┤
│  Scheduler Service       │  PostgreSQL: scheduler_db     │
│                          │  Tables: schedules, triggers, │
│                          │          backfill_runs, outbox│
├──────────────────────────┼───────────────────────────────┤
│  Execution Service       │  PostgreSQL: execution_db     │
│                          │  Tables: jobs, saga_state,    │
│                          │          outbox, processed_msg│
├──────────────────────────┼───────────────────────────────┤
│  Runner Service          │  PostgreSQL: runner_db        │
│                          │  Tables: runners, assignments │
│                          │  Redis:    heartbeats, state  │
├──────────────────────────┼───────────────────────────────┤
│  Agent Service           │  PostgreSQL: agent_db         │
│                          │  Tables: suggestions, actions │
│                          │  Redis:    agent context      │
├──────────────────────────┼───────────────────────────────┤
│  Metadata Service        │  PostgreSQL: metadata_db      │
│                          │  Elasticsearch: lineage,      │
│                          │               catalog, search │
├──────────────────────────┼───────────────────────────────┤
│  Billing Service         │  PostgreSQL: billing_db       │
│                          │  Tables: usage, quotas,       │
│                          │          invoices (partitioned)│
├──────────────────────────┼───────────────────────────────┤
│  Audit Service           │  PostgreSQL: audit_db         │
│                          │  (append-only, 365d retention)│
└──────────────────────────┴───────────────────────────────┘
```

**The rule:** Service A never queries Service B's database. No shared connection strings. No shared ORM entities. No cross-service foreign keys.

## How Cross-Service Data Works

Without a shared database, three patterns handle cross-service data needs.

**Pattern 1: Synchronous API call**

Use when: real-time data is needed from another service; the data is specific and small; temporary unavailability is acceptable.

```
Execution Service ──gRPC──► Pipeline Service
                            "GetPipelineConfig(pipe-abc)"
                  ◄──────── PipelineConfig{...}
```

With circuit breaker and local Redis cache (5-minute TTL, invalidated by consuming `pipeline.config.changes` events). On cache miss, fall back to gRPC call.

**Pattern 2: Event consumption (async)**

Use when: slight staleness is acceptable; multiple services need the same data; decoupling is important.

Execution Service publishes `job.results` events. Billing Service consumes them and writes to its own `billing_events` table. Billing Service never calls Execution Service directly — it maintains its own projection of job data.

**Pattern 3: Data duplication (read model)**

Use when: a service needs to query data it does not own and join performance is critical.

Runner Service needs tenant quota information for enforcement. Tenant Service publishes `tenant.events`. Runner Service consumes and caches tenant quota in Redis. The cache is eventually consistent — quota enforcement does not need millisecond precision.

**Anti-pattern — never do this:**
```sql
-- ❌ Execution Service directly reading Pipeline Service's database
SELECT * FROM pipeline_service.pipelines WHERE id = 'pipe-abc';
```

This violates service boundaries completely, breaks independent deployability, and creates hidden coupling.

## Why Each Service Chose Its Database

**Pipeline Service → PostgreSQL**
Strong ACID for pipeline configuration consistency. JSONB for flexible config storage. Append-only event store. Rich indexing and optimistic locking.

**Scheduler Service → PostgreSQL**
Transactional schedule updates. Complex time-based queries (find next N pipelines to trigger between time X and Y).

**Execution Service → PostgreSQL**
Saga state requires ACID — compensating transactions are critical. Outbox pattern requires same-DB transaction. Idempotency store via unique constraint on key. Job history queries with filtering and pagination.

**Runner Service → PostgreSQL + Redis**
PostgreSQL: runner registration, history, audit trail.
Redis: live heartbeats with TTL auto-expiry:
```
SET runner:heartbeat:runner-001 {load:0.73} EX 30
```
Auto-expires after 30 seconds if runner goes silent — no cleanup job needed. Also Redis for leader election (`SET NX PX`) and fast load score reads.

**Metadata Service → PostgreSQL + Elasticsearch**
PostgreSQL: catalog CRUD, glossary, ownership tracking.
Elasticsearch: full-text search across millions of datasets (LIKE queries on 10M rows = full table scan; ES inverted index = millisecond response). Also handles column-level lineage graph queries and log search.

**Billing Service → PostgreSQL (partitioned)**
Usage events are append-only time-series. Table partitioned by month (`RANGE` partitioning). Old months archived to MinIO after 90 days. Monthly invoice queries scan only one partition.

**Audit Service → PostgreSQL (append-only)**
Immutable audit trail. No `UPDATE`, no `DELETE`. Row-level security restricts tenants to their own data. 365-day retention with archival.

## Data Consistency Across Services

**Scenario: User deletes pipeline-abc**

Without careful design, Execution Service might still have jobs queued for the deleted pipeline.

**Solution — event-driven eventual consistency with defensive coding:**

```sql
-- Step 1: Pipeline Service marks deleted + publishes event atomically
BEGIN TRANSACTION;
  UPDATE pipelines SET deleted_at = NOW() WHERE id = 'pipe-abc';
  INSERT INTO outbox (type='PIPELINE_DELETED', aggregate_id='pipe-abc', ...);
COMMIT;
-- Outbox relay publishes to Kafka: pipeline.events (PIPELINE_DELETED)
```

Step 2: Execution Service consumes `PIPELINE_DELETED` → cancels pending jobs for `pipe-abc` → publishes `job.cancelled` for each.

Step 3: Runner Service consumes `PIPELINE_DELETED` → if runner currently executing a job for `pipe-abc`, sends `CancelJob` signal via gRPC.

Step 4: Scheduler Service consumes → removes all schedules for `pipe-abc`.

**Defensive coding handles the race condition:**

A job might be picked up from `job.assigned` between the delete event and the cancel event being processed. Before dispatching any job, Execution Service validates the pipeline still exists via a gRPC call to Pipeline Service. A 404 response → job marked cancelled immediately.

**Reference data management:**

Pipeline Service owns pipeline config. It publishes `pipeline.config.changes` on every update. Execution Service caches config in Redis with a 5-minute TTL, invalidated by consuming these events. On cache miss, fall back to gRPC call. If Pipeline Service is down: serve stale cache (AP system choice for this case).

## Physical Database Setup in Pravah

**Physical arrangement:**

Separate PostgreSQL databases on a shared cluster managed by Patroni (HA with automatic failover). This gives logical isolation with lower physical overhead than running 10 separate PostgreSQL instances.

```
PostgreSQL Cluster (Patroni HA):
  database: pravah_pipeline_db   → Pipeline Service only
  database: pravah_scheduler_db  → Scheduler Service only
  database: pravah_execution_db  → Execution Service only
  database: pravah_runner_db     → Runner Service only
  ...
```

**Enforced isolation via database users:**

```sql
-- Each service has its own user with access ONLY to its database
CREATE USER pravah_pipeline_user WITH PASSWORD '...';
GRANT ALL PRIVILEGES ON DATABASE pravah_pipeline_db TO pravah_pipeline_user;
-- pravah_pipeline_user cannot connect to pravah_execution_db
```

**Connection string pattern:**

```
postgresql://pravah_pipeline_user:${PIPELINE_DB_PASSWORD}
            @pgbouncer:5432/pravah_pipeline_db
```

Secrets stored in HashiCorp Vault: `secret/pravah/production/pipeline-service/db-password`.

PgBouncer sits in front of the cluster for connection pooling — each service gets its own PgBouncer pool. Flyway manages migrations per service: each service owns its migration scripts, runs them on startup, completely independent of other services.

## Benefits Realized in Pravah

**Independent deployability:** Pipeline Service schema change → migrate `pipeline_db` → deploy Pipeline Service → zero coordination with other teams.

**Failure isolation:** Billing Service DB goes down → Billing Service degrades, but Pipeline Service, Scheduler Service, and Execution Service remain fully operational. Jobs continue running. Billing catches up when DB recovers.

**Right tool for each use case:** Runner heartbeats in Redis (TTL auto-expiry), lineage search in Elasticsearch (full-text inverted index), pipeline audit in PostgreSQL (ACID append-only), agent context in Redis (fast expiring cache).

**Independent scaling:** Job processing spikes → scale Execution Service and `execution_db` independently. Month-end billing reports → add a read replica to `billing_db` for report queries. No cross-service contention.

**Team autonomy:** Runner team changes `runner_db` schema freely. Pipeline team has no opinion on runner schema. Billing team can rewrite `billing_db` from scratch. No coordination, no meetings, no blockers.

## FAANG Interview Angles

**"How does Pravah handle cross-service data consistency without a shared database?"**

> Three patterns depending on the use case. For real-time data needs, synchronous API calls via gRPC with circuit breakers and local Redis caching. Execution Service caches pipeline config with a 5-minute TTL, invalidated by consuming `pipeline.config.changes` events. Cache miss falls back to a gRPC call with circuit breaker protection.
>
> For async data propagation, event-driven updates via Kafka. Billing Service never calls Execution Service directly — it consumes `job.results` events and maintains its own projection in `billing_db`.
>
> For reference data, publisher-owns, consumers-cache pattern. Tenant quota data lives in Tenant Service but Runner Service caches it in Redis. The cache is rebuilt on `tenant.events` consumption. Stale quota for 30 seconds is acceptable for enforcement.

**"What happens when a pipeline is deleted but jobs are already queued for it?"**

> Pipeline Service marks the pipeline deleted and publishes `PIPELINE_DELETED` to `pipeline.events` via the outbox pattern — atomically in one transaction. Execution Service consumes this and cancels pending jobs. Runner Service consumes it and sends `CancelJob` signals to any runners currently executing that pipeline.
>
> There is a race condition: a job might be picked up between the delete and the cancel event being processed. We handle this defensively — before dispatching any job, Execution Service calls Pipeline Service to validate the pipeline still exists. A 404 means the job is cancelled immediately. The circuit breaker prevents this validation from blocking if Pipeline Service is slow.

## Key Takeaways

1. **Shared database anti-pattern** causes schema coupling, performance interference, single point of failure, scaling impossibility, and technology lock-in
2. **Database per service** gives independent deployability, failure isolation, right tool for each use case, independent scaling, and team autonomy
3. **Cross-service data: three patterns** — synchronous API (real-time, specific, with cache), async events (eventual consistency via Kafka), data duplication (read models)
4. **Physical setup:** shared PostgreSQL cluster with separate databases per service; enforced by separate DB users; PgBouncer for connection pooling; Flyway per service
5. **Consistency:** event-driven invalidation (Kafka + outbox), defensive validation before acting, circuit breakers + graceful degradation, explicit eventual consistency where acceptable
6. **Never access another service's database directly** — all cross-service data goes through API or Kafka
