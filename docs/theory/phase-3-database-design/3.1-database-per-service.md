3.1 Database Per Service — Why & How
🧩 Start With The Problem
THE SHARED DATABASE ANTI-PATTERN
────────────────────────────────────────────────────────────

Many teams building microservices make this mistake:

  ┌─────────────────────────────────────────────────┐
  │              SHARED DATABASE                    │
  │                                                 │
  │  pipelines | jobs | runners | billing | audit   │
  │  ──────────────────────────────────────────     │
  │  One schema. One PostgreSQL instance.           │
  └─────────────────────────────────────────────────┘
       ▲           ▲           ▲           ▲
  Pipeline     Scheduler   Runner      Billing
  Service      Service     Service     Service

  "It's simpler! One place for all data!"
  "We can JOIN across tables easily!"
  "Less infrastructure to manage!"

  All true. All wrong reasons.
  Here's what happens in production.
💥 Why Shared Database Fails at Scale
PROBLEM 1: SCHEMA COUPLING
────────────────────────────────────────────────────────────

Runner Service needs to add column to runners table:
  ALTER TABLE runners ADD COLUMN docker_version VARCHAR(50);

But Pipeline Service also queries runners table.
Pipeline Service must be updated SIMULTANEOUSLY.
Both services must deploy TOGETHER.

  "We can't deploy Runner Service v2 until
   Pipeline Service v2 is also ready."

Result:
  Services lose independent deployability.
  One team blocks another team.
  Deployment coordination meetings.
  "Big bang" releases instead of continuous delivery.
  This defeats the entire purpose of microservices. ❌

PROBLEM 2: PERFORMANCE INTERFERENCE
────────────────────────────────────────────────────────────

Billing Service runs month-end report:
  SELECT tenant_id, SUM(compute_units)
  FROM billing_events
  GROUP BY tenant_id
  -- This scans 100 million rows
  -- Takes 45 minutes

During those 45 minutes:
  Pipeline Service: "WHERE IS MY INDEX SCAN?!"
  Scheduler Service: "WHY IS THE DB SLOW?!"
  Runner Service: "TIMEOUTS EVERYWHERE!"

One bad query kills ALL services.
One team's bad SQL = everyone's outage. ❌

PROBLEM 3: SINGLE POINT OF FAILURE
────────────────────────────────────────────────────────────

Shared PostgreSQL goes down:
  → Pipeline Service down ❌
  → Scheduler Service down ❌
  → Runner Service down ❌
  → Billing Service down ❌
  → ALL OF PRAVAH DOWN ❌

One database failure = total platform failure.
No isolation. No graceful degradation. ❌

PROBLEM 4: SCALING IMPOSSIBILITY
────────────────────────────────────────────────────────────

Pipeline Service: needs fast writes (10K inserts/sec)
Billing Service:  needs complex analytical reads
Runner Service:   needs fast key-value lookups
Audit Service:    needs append-only time-series

One database cannot be optimized for all four.
Scale vertically (bigger machine) → expensive.
Scale horizontally (sharding) → nightmare with joins. ❌

PROBLEM 5: TECHNOLOGY LOCK-IN
────────────────────────────────────────────────────────────

Runner heartbeats: perfect for Redis (TTL, fast)
Lineage graph:     perfect for Neo4j (graph traversal)
Log search:        perfect for Elasticsearch
Audit trail:       perfect for append-only PostgreSQL

With shared DB: everything in PostgreSQL.
Redis, Neo4j, Elasticsearch → "too complex."
Technology chosen by historical accident, not fit. ❌
✅ Database Per Service — The Solution
PRAVAH DATABASE ISOLATION
────────────────────────────────────────────────────────────

Every service owns its data exclusively.
No other service reads from or writes to it directly.
Cross-service data access: only via API or Kafka.

┌──────────────────────────────────────────────────────────┐
│  Pipeline Service        │  PostgreSQL: pipeline_db      │
│                          │  Tables: pipelines, events,   │
│                          │          outbox, snapshots    │

RULE: Service A NEVER queries Service B's database.
      No shared connection strings.
      No shared ORM entities.
      No cross-service foreign keys.
🔄 How Cross-Service Data Works
WITHOUT SHARED DB — THREE PATTERNS
────────────────────────────────────────────────────────────

PATTERN 1: API CALL (synchronous)
  When: Need real-time data from another service.
        Small, specific data needed.
        Acceptable to be temporarily unavailable.

  Example: Execution Service needs pipeline config
           before dispatching a job.

  Execution Service ──gRPC──► Pipeline Service
                              "GetPipelineConfig(pipe-abc)"
                    ◄──────── PipelineConfig{...}

  Timeout: 5 seconds
  Circuit breaker: protects if Pipeline Service slow
  Cache: Execution Service caches config in Redis
         (invalidated when pipeline.config.changes event)

PATTERN 2: EVENT CONSUMPTION (async)
  When: Data can be slightly stale.
        Multiple services need same data.
        Decoupling is important.

  Example: Billing Service needs to know when
           jobs complete to charge compute units.

  Execution Service publishes: job.results event
  Billing Service consumes: job.results event
  Billing Service writes: billing_events to its own DB

  Billing Service NEVER calls Execution Service.
  It maintains its own projection of job data. ✅

PATTERN 3: DATA DUPLICATION (read model)
  When: Service needs to query data it doesn't own.
        Joining across services would require API calls.
        Read performance is critical.

  Example: Runner Service needs tenant info to
           enforce quotas. Tenant data lives in
           a separate Tenant Service.

  Tenant Service publishes: tenant.events to Kafka
  Runner Service consumes: caches tenant quota in Redis
  Runner Service: reads from local Redis cache

  Data is DUPLICATED with eventual consistency.
  Runner Service has slightly stale tenant data.
  Acceptable: quota enforcement doesn't need ms precision.

ANTI-PATTERN: DIRECT DB ACCESS
  ❌ Execution Service → Pipeline Service's DB
  ❌ SELECT * FROM pipeline_service.pipelines
     WHERE id = 'pipe-abc'

  This violates service boundaries completely.
  Breaks independent deployability.
  Creates hidden coupling.
  NEVER do this in Pravah.
🗄️ Pravah's Database Decisions Per Service
WHY EACH SERVICE CHOSE ITS DATABASE
────────────────────────────────────────────────────────────

PIPELINE SERVICE → PostgreSQL
  Data: Pipeline definitions, event store, outbox
  Why PostgreSQL:
    Strong ACID (pipeline config must be consistent)
    JSONB for flexible pipeline config storage
    Append-only event store (natural for Postgres)
    Rich indexing for pipeline queries
    Optimistic locking with version column

SCHEDULER SERVICE → PostgreSQL
  Data: Cron schedules, trigger history, backfill runs
  Why PostgreSQL:
    Transactional schedule updates (atomicity)
    Complex queries (find next N pipelines to trigger)
    Time-based queries (what runs between X and Y)

EXECUTION SERVICE → PostgreSQL
  Data: Jobs, saga state, outbox, processed messages
  Why PostgreSQL:
    Saga state requires ACID (compensations critical)
    Outbox pattern requires same-DB transaction
    Idempotency store (unique constraint on key)
    Job history queries (filter, sort, paginate)

RUNNER SERVICE → PostgreSQL + Redis
  Data: Runner registry (Postgres), live state (Redis)
  Why both:
    PostgreSQL: runner registration, history, audit
    Redis: live heartbeats (TTL auto-expiry!),
           runner load scores (fast read/write),
           leader election (SET NX PX)

  Runner heartbeats in Redis:
    SET runner:heartbeat:runner-001 {load:0.73} EX 30
    ← auto-expires if runner goes silent! ✅
    No cleanup job needed.
    No polling for dead runners.

METADATA SERVICE → PostgreSQL + Elasticsearch
  Data: Catalog (Postgres), search + lineage (ES)
  Why both:
    PostgreSQL: catalog CRUD, glossary, ownership
    Elasticsearch: full-text search across datasets,
                   column-level lineage graph queries,
                   log search for pipeline runs

  Why not PostgreSQL for search?
    LIKE queries on 10M datasets = full table scan
    ES inverted index = millisecond search ✅

AGENT SERVICE → PostgreSQL + Redis
  Data: Agent actions, suggestions (Postgres)
        Agent context, pipeline patterns (Redis)
  Why Redis for context:
    Agent needs fast read of recent pipeline history
    Context expires naturally (7-day TTL)
    Hash structure: agent:context:pipe-abc → {}

BILLING SERVICE → PostgreSQL (partitioned)
  Data: Usage events, invoices, quota ledger
  Why PostgreSQL with partitioning:
    Usage events = append-only time-series
    Table partitioned by month (RANGE partitioning)
    Old months: archived to MinIO after 90 days
    Monthly invoice queries: only scan one partition

AUDIT SERVICE → PostgreSQL (append-only)
  Data: Immutable audit trail
  Why PostgreSQL:
    Append-only table (no UPDATE, no DELETE)
    Row-level security: tenants only see their audit
    365-day retention with archival to MinIO
    Compliance queries: who did what, when
🔀 Data Consistency Across Services
THE CONSISTENCY CHALLENGE
────────────────────────────────────────────────────────────

Without a shared DB, cross-service consistency
requires careful thought.

SCENARIO: User deletes pipeline-abc
  Pipeline Service: marks pipeline deleted ✅
  But: job.assigned has pending jobs for pipe-abc!
       Execution Service doesn't know it's deleted.
       Runner starts executing deleted pipeline. ❌

SOLUTION: EVENTUAL CONSISTENCY + DEFENSIVE CODING
────────────────────────────────────────────────────────────

Step 1: Pipeline Service marks deleted + publishes event
  BEGIN TRANSACTION (pipeline_db)
    UPDATE pipelines SET deleted_at = NOW()
    INSERT INTO outbox (type='PIPELINE_DELETED', ...)
  COMMIT

  Outbox relay → Kafka: pipeline.events (DELETED)

Step 2: Execution Service consumes PIPELINE_DELETED
  Cancels any pending jobs for pipe-abc
  Publishes job.cancelled for each

Step 3: Runner Service consumes PIPELINE_DELETED
  If runner currently executing pipe-abc job:
    Sends CancelJob signal to runner via gRPC ✅

Step 4: Scheduler Service consumes PIPELINE_DELETED
  Removes all schedules for pipe-abc ✅

DEFENSIVE CODING:
  Every service validates pipeline exists before acting:
    Execution: call Pipeline Service.GetPipeline()
               circuit breaker if unavailable
               If 404: job marked cancelled

  This handles the race condition:
    Delete event in Kafka
    Old job in job.assigned
    Execution Service: validates → not found → cancel ✅

REFERENCE DATA MANAGEMENT:
────────────────────────────────────────────────────────────

Some data is read by many services (tenant info,
pipeline config, connector catalog).

Strategy: Publisher owns it, consumers cache it.

  Pipeline Service: OWNS pipeline config
    Publishes: pipeline.config.changes on every update
    
  Execution Service: CACHES pipeline config
    Redis: pipeline:config:pipe-abc → {config JSON}
    TTL: 5 minutes
    Invalidated by: consuming pipeline.config.changes

  On cache miss:
    Call Pipeline Service.GetPipelineConfig() ✅
    Update cache ✅
    
  Pipeline Service down:
    Cache hit → serve stale (AP choice) ✅
    Cache miss → circuit breaker → degrade gracefully ✅
🏗️ Physical Database Setup in Pravah
KUBERNETES DATABASE DEPLOYMENT
────────────────────────────────────────────────────────────

Each service gets dedicated PostgreSQL:

  Option A: Separate PostgreSQL instances (K8s pods)
    Pros: Full isolation, independent scaling
    Cons: Many pods to manage, resource overhead

  Option B: Shared PostgreSQL cluster, separate DATABASES
    Pros: Fewer pods, shared connection pooling
    Cons: Storage still shared, noisy neighbor risk

  PRAVAH CHOICE: Separate databases on shared cluster
    (hybrid: separate logical DB, shared physical cluster)

    PostgreSQL Cluster (HA with Patroni):
      database: pipeline_db  (Pipeline Service only)
      database: scheduler_db (Scheduler Service only)
      database: execution_db (Execution Service only)
      database: runner_db    (Runner Service only)
      ...

    PgBouncer: connection pooler (covered in 3.6)
    Patroni:   HA + failover (covered in 3.5)

  ENFORCED ISOLATION:
    Each service has its own PostgreSQL user:
      pipeline_svc_user: GRANT ALL ON pipeline_db ONLY
      scheduler_svc_user: GRANT ALL ON scheduler_db ONLY
      (cannot connect to other databases by design)

NAMING CONVENTIONS IN PRAVAH:
────────────────────────────────────────────────────────────

Database naming:
  pravah_{service}_db
  pravah_pipeline_db
  pravah_execution_db
  pravah_runner_db

Table naming:
  No service prefix needed (each DB is isolated)
  Use domain terms: pipelines, jobs, runners

User naming:
  pravah_{service}_user
  pravah_pipeline_user
  pravah_execution_user

Connection string pattern:
  postgresql://pravah_pipeline_user:${PIPELINE_DB_PASSWORD}
              @pgbouncer:5432/pravah_pipeline_db

Secret in Vault:
  secret/pravah/production/pipeline-service/db-password

WHAT DATABASE PER SERVICE GIVES PRAVAH
────────────────────────────────────────────────────────────

BENEFIT 1: INDEPENDENT DEPLOYABILITY
  Pipeline Service schema change:
    Migrate pipeline_db ✅
    Deploy Pipeline Service ✅
    Zero coordination with other teams ✅

  Billing Service DB goes down:

  Runner heartbeats: Redis (TTL auto-expiry)

🎯 FAANG Interview Angles
❓ "How does Pravah handle cross-service data
    consistency without a shared database?"

Good answer:
  "Three patterns depending on the use case.

   For real-time data needs, synchronous API calls
   via gRPC with circuit breakers and local caching.
   Execution Service caches pipeline config in Redis
   with a 5-minute TTL, invalidated by consuming
   pipeline.config.changes events from Kafka. Cache
   miss falls back to a gRPC call to Pipeline Service.

   For async data propagation, event-driven updates
   via Kafka. Billing Service never calls Execution
   Service directly — it consumes job.results events
   and maintains its own projection of job data in
   billing_db. Eventually consistent but sufficient
   for billing accuracy.

   For reference data, publisher-owns, consumers-cache
   pattern. Tenant quota data lives in a Tenant Service
   but Runner Service caches it in Redis. The cache is
   rebuilt on tenant.events consumption. Stale quota
   data for 30 seconds is acceptable for enforcement."

❓ "What happens in Pravah when a pipeline is
    deleted but jobs are already queued for it?"

Good answer:
  "This is the classic cross-service consistency
   challenge without shared database transactions.

   Pipeline Service marks the pipeline deleted and
   publishes PIPELINE_DELETED to pipeline.events via
   the outbox pattern — atomically in one transaction.

   Execution Service consumes this event and cancels
   any pending jobs for that pipeline in job.assigned.
   Runner Service consumes it and sends CancelJob
   signals via gRPC to any runners currently executing
   that pipeline.

   But there's a race condition: a job might be picked
   up from job.assigned between the delete and the
   cancel event being processed. We handle this
   defensively — before dispatching any job, Execution
   Service calls Pipeline Service to validate the
   pipeline still exists. A 404 response means the
   job is cancelled immediately. The circuit breaker
   prevents this validation from blocking if Pipeline
   Service is slow."

❓ "Isn't database per service operationally
    expensive? How does Pravah manage it?"

Good answer:
  "The operational cost is real but manageable with
   the right tooling. Pravah uses a shared PostgreSQL
   cluster managed by Patroni for HA, but with
   separate databases per service. This gives logical
   isolation with lower physical overhead than 10
   separate PostgreSQL instances.

   PgBouncer sits in front of the cluster for
   connection pooling — each service gets its own
   PgBouncer pool pointing to its database. A single
   PgBouncer instance handles thousands of application
   connections with only tens of actual PostgreSQL
   connections.

   Flyway manages migrations per service — each
   service owns its migration scripts, runs them on
   startup, completely independent of other services.

   The operational cost of shared databases is much
   higher in practice: cross-team coordination for
   schema changes, debugging performance issues caused
   by other teams' queries, and the cascading failures
   when the single database goes down. We've traded
   operational complexity for team autonomy and
   system resilience."
📌 Key Takeaways
1. Shared database anti-pattern causes:
   Schema coupling (teams block each other)
   Performance interference (one bad query kills all)
   Single point of failure (one DB down = all down)
   Scaling impossibility (can't optimize for all)
   Technology lock-in (one DB for all use cases)

2. Database per service gives:
   Independent deployability (no coordination)
   Failure isolation (one DB down ≠ all down)
   Right tool for each use case (Redis/ES/PG/etc)
   Independent scaling per service
   Team autonomy (no cross-team schema coordination)

3. Cross-service data access: three patterns
   Synchronous API: real-time, specific data, with cache
   Async events: eventual consistency via Kafka
   Data duplication: read models per consumer

4. Pravah physical setup:
   Shared PostgreSQL cluster (Patroni for HA)
   Separate databases per service (logical isolation)
   Enforced by separate DB users per service
   PgBouncer for connection pooling

5. Consistency challenge: handled with
   Event-driven invalidation (Kafka + outbox)
   Defensive validation before acting
   Circuit breakers + graceful degradation
   Explicit eventual consistency where acceptable

6. Never access another service's database directly
   This is the #1 microservices anti-pattern
   All cross-service data: API or Kafka only
