# 3.4 — Table Partitioning: Splitting `job_runs` by Date

## The Problem We're Solving

You built great indexes on `job_runs`. But imagine it's 2 years from now:

```
job_runs: 8 billion rows, 2.4 TB on disk
```

**What goes wrong at that scale:**
- Even a perfectly indexed query scans the index across all 8B rows to find the matching partition of the index
- VACUUM takes hours — the whole table is locked for updates during the longest VACUUM phase
- You can't `DROP` old data — `DELETE FROM job_runs WHERE created_at < '2023-01-01'` takes 30 minutes and generates massive WAL
- Cold data (runs from 2023) sits in the same pages as hot data (runs from today), destroying cache efficiency

**Partitioning solves all of this** by splitting one logical table into many physical child tables, transparently.

---

## How PostgreSQL Partitioning Works

When you query `SELECT * FROM job_runs WHERE created_at > now() - interval '7 days'`, PostgreSQL:

1. Looks at the partition key (`created_at`)
2. Eliminates all child tables whose range doesn't include your condition — **partition pruning**
3. Only touches the 1–2 relevant child tables instead of all 24

The application sees one table. The database does the routing.

```
              job_runs  (partitioned parent — no data stored here)
              /    |    \
 job_runs_2024_01  job_runs_2024_02  ...  job_runs_2026_05
 (Jan 2024 data)   (Feb 2024 data)        (May 2026 data)
```

---

## Three Partitioning Strategies

### 1. RANGE — split by value ranges

Best for: **time-series data** (dates, timestamps, sequential IDs).

```sql
PARTITION BY RANGE (created_at)
```

Partitions cover non-overlapping ranges:
- `2026-01-01 <= created_at < 2026-02-01`
- `2026-02-01 <= created_at < 2026-03-01`

✅ Pravah uses this for `job_runs` — queries almost always filter on time.

---

### 2. LIST — split by discrete values

Best for: **tenant sharding**, **region/datacenter splits**, **status-based splits**.

```sql
PARTITION BY LIST (tenant_id)
-- or
PARTITION BY LIST (region)
```

Partitions cover specific value sets:
- partition `us_east`: `('tenant_a', 'tenant_b', ...)`
- partition `eu_west`: `('tenant_x', 'tenant_y', ...)`

❌ Not ideal for `job_runs` — you have thousands of tenants and queries span tenants.

---

### 3. HASH — split by hash of a column

Best for: **uniform distribution**, **write sharding** when no natural range/list exists.

```sql
PARTITION BY HASH (job_id)
-- 4 partitions: hash(job_id) % 4 = 0, 1, 2, 3
```

✅ Good for tables with no time or list key — but you lose partition pruning for range queries.

---

## Pravah's Decision: Monthly Range on `created_at`

**Why monthly?**
- Daily = too many child tables (365+/year), overhead for planning
- Yearly = too large per partition, VACUUM still slow
- Monthly = sweet spot for Pravah's scale — ~50M rows/month, ~15 GB/partition
- Operational: add 1 new partition per month, drop oldest after retention window

**Why `created_at` not `tenant_id`?**
- 90% of queries filter on time (`WHERE created_at > now() - interval '7 days'`)
- Tenant queries span time anyway (`tenant_id = X AND created_at > Y`)
- Time-based allows efficient DROP of old partitions as a maintenance operation

## DDL: Creating the Partitioned Table

```sql
-- Parent table — declarative partitioning (pg 10+)
CREATE TABLE job_runs (
    id            BIGSERIAL,
    job_id        BIGINT        NOT NULL REFERENCES jobs(id),
    tenant_id     VARCHAR(64)   NOT NULL,
    status        VARCHAR(20)   NOT NULL,
    worker_id     VARCHAR(128),
    started_at    TIMESTAMPTZ,
    finished_at   TIMESTAMPTZ,
    created_at    TIMESTAMPTZ   NOT NULL DEFAULT now(),
    duration_ms   INT,
    error_msg     TEXT,
    metadata      JSONB
) PARTITION BY RANGE (created_at);

-- Primary key MUST include the partition key
-- (PostgreSQL requirement for partitioned tables)
ALTER TABLE job_runs ADD CONSTRAINT job_runs_pkey
    PRIMARY KEY (id, created_at);
```

**Why the PK must include `created_at`:** PostgreSQL enforces unique constraints per partition.
It can't guarantee global uniqueness across all partitions without including the partition key,
because each child table's constraint only covers its own data.

---

## Creating Monthly Partitions

```sql
-- May 2026
CREATE TABLE job_runs_2026_05 PARTITION OF job_runs
    FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

-- June 2026 (create ahead of time — never let the month flip without a partition)
CREATE TABLE job_runs_2026_06 PARTITION OF job_runs
    FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

-- July 2026 (pre-create next month too as buffer)
CREATE TABLE job_runs_2026_07 PARTITION OF job_runs
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');
```

**Rule of thumb:** Always have the current month's partition + 2 future months pre-created.
An insert into a range with no partition fails with an error. You don't want that at midnight on June 1st.

---

## Partition Pruning in Action

The payoff: PostgreSQL eliminates irrelevant partitions at query planning time.

```sql
-- This query only touches job_runs_2026_05:
EXPLAIN SELECT * FROM job_runs
WHERE created_at >= '2026-05-01'
  AND created_at <  '2026-06-01'
  AND tenant_id = 'acme';
```

Output will show:
```
Append  (cost=...)
  ->  Seq Scan on job_runs_2026_05  (...)
        Filter: (tenant_id = 'acme')
-- job_runs_2026_04, _03, _02, ... are NOT listed
```

```sql
-- This 7-day query touches only 1-2 partitions:
EXPLAIN SELECT * FROM job_runs
WHERE created_at > now() - interval '7 days'
  AND status = 'FAILED';
```

Compare with no partitioning: the planner would have to consider all 8B rows.

---

## Indexes on Partitioned Tables

Define indexes on the **parent** — PostgreSQL automatically creates matching indexes on all
existing and future child partitions:

```sql
-- These go on the parent; each child partition gets its own copy automatically
CREATE INDEX idx_job_runs_tenant_status_time
    ON job_runs (tenant_id, status, created_at DESC);

CREATE INDEX idx_job_runs_job_id
    ON job_runs (job_id, created_at);

CREATE INDEX idx_job_runs_worker_active
    ON job_runs (worker_id, created_at)
    WHERE status IN ('RUNNING', 'PENDING');

CREATE INDEX idx_job_runs_failed_recent
    ON job_runs (tenant_id, created_at DESC)
    WHERE status = 'FAILED';
```

**Key insight:** Each partition's index covers only that partition's rows. The index for
`job_runs_2026_05` has ~50M entries; without partitioning, the same index would have 8B entries.
That is the performance difference.

---

## Dropping Old Partitions — The Killer Feature

Retention policy: keep 12 months of `job_runs` data.

**Without partitioning:**
```sql
-- This is catastrophic at scale
DELETE FROM job_runs WHERE created_at < '2025-05-01';
-- Runtime: hours
-- WAL generated: enormous (every deleted row is logged)
-- Table bloat: massive (dead rows need VACUUM)
-- Locks: row-level, but still blocks autovacuum and impacts I/O
```

**With partitioning:**
```sql
-- Drop the whole May 2025 partition — instant
DROP TABLE job_runs_2025_05;
-- Runtime: milliseconds
-- WAL: just the catalog entry deletion
-- No VACUUM needed — the whole file is removed from the filesystem
-- Zero impact on current month's partition
```

This is the single most operationally important benefit of partitioning at Pravah's scale.

## The Operational Playbook

### Monthly rotation (automate with pg_cron or a cron job):

```sql
-- Step 1: On the 25th of each month, pre-create next month+1
-- (Running in May → create July)
CREATE TABLE IF NOT EXISTS job_runs_2026_07 PARTITION OF job_runs
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');

-- Step 2: On the 1st of each month, drop data outside retention window
-- (Keeping 12 months: in June 2026, drop May 2025)
DROP TABLE IF EXISTS job_runs_2025_05;

-- Step 3: Verify partition list looks clean
SELECT
    child.relname                             AS partition,
    pg_get_expr(child.relpartbound, child.oid) AS bounds
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
WHERE parent.relname = 'job_runs'
ORDER BY child.relname;
```

### Automated with `pg_partman` (recommended for production):

```sql
-- pg_partman is the standard extension for this
-- It handles pre-creation, retention drops, and gap detection
SELECT partman.create_parent(
    p_parent_table => 'public.job_runs',
    p_control      => 'created_at',
    p_type         => 'range',
    p_interval     => '1 month',
    p_premake      => 3   -- pre-create 3 future partitions
);

-- Set retention: drop partitions older than 12 months
UPDATE partman.part_config
SET retention             = '12 months',
    retention_keep_table  = false
WHERE parent_table = 'public.job_runs';
```

## What Breaks Partition Pruning

✅ **Pruning works — partition key in WHERE directly:**
```sql
WHERE created_at > now() - interval '7 days'
WHERE created_at BETWEEN '2026-05-01' AND '2026-05-31'
```

❌ **Pruning breaks — function wrapped around partition key:**
```sql
WHERE date_trunc('month', created_at) = '2026-05-01'
-- Fix: WHERE created_at >= '2026-05-01' AND created_at < '2026-06-01'

WHERE EXTRACT(year FROM created_at) = 2026
-- Fix: WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
```

Wrapping the partition key in a function makes it non-SARGable — the planner can't map
the expression to partition bounds, so it scans all partitions.

## Summary

| Concept | Detail |
|---|---|
| Why partition `job_runs` | 8B+ rows; fast time-range queries; instant DROP for retention |
| Strategy chosen | `RANGE` on `created_at`, monthly buckets |
| Pre-create rule | Always current + 2 future months ready |
| Index strategy | Define on parent; auto-propagates to each child |
| Partition pruning | Works when `created_at` appears in WHERE without a wrapping function |
| DROP vs DELETE | `DROP TABLE partition` = instant; `DELETE` on billions = hours |
| Tooling | `pg_partman` for automated creation/retention in production |

---

## 📌 Key Takeaways

1. **Partitioning splits one logical table into physical child tables** — transparent to queries, powerful for the planner
2. **Range on `created_at`** is the right choice for `job_runs` — matches query access patterns
3. **Partition pruning** is the core performance win — queries only scan 1–2 partitions instead of the whole 8B-row table
4. **`DROP TABLE partition` is instant** — this is the operational killer feature for time-series retention
5. **Primary key must include the partition key** — PostgreSQL requirement for partitioned tables
6. **Indexes defined on the parent auto-propagate** — no need to create per-partition indexes manually
7. **Never let the month flip without a partition pre-created** — inserts will error; automate with `pg_partman`
8. **Don't wrap the partition key in functions in WHERE** — breaks pruning, query hits all partitions
