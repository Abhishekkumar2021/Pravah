# 3.9 Optimistic vs Pessimistic Locking

## Why Locking Exists

Two transactions reading and writing the same row concurrently create a race condition. Without coordination, the final state of the row depends on the order of writes — which is non-deterministic. Locking is the mechanism databases use to serialize conflicting operations so the result is always consistent.

Every locking strategy is a trade-off between **concurrency** (how many transactions can run simultaneously) and **correctness** (whether conflicts are detected and handled).

---

## Pessimistic Locking

Pessimistic locking assumes conflicts will happen and prevents them proactively by acquiring an exclusive lock before reading.

**How it works:**

```sql
BEGIN;

-- Lock the row before reading
SELECT * FROM accounts WHERE id = 42 FOR UPDATE;

-- Now safely update — no other transaction can modify this row
UPDATE accounts SET balance = balance - 100 WHERE id = 42;

COMMIT;
```

`FOR UPDATE` acquires an exclusive row lock. Any other transaction that tries to `SELECT ... FOR UPDATE` or `UPDATE` row 42 will block until this transaction commits or rolls back.

**`FOR SHARE` vs `FOR UPDATE`:**

| Lock Mode | Allows Other Readers? | Allows Other Writers? | Use Case |
|-----------|----------------------|----------------------|----------|
| `FOR SHARE` | Yes | No | Read then validate; prevent writes but allow reads |
| `FOR UPDATE` | No | No | Read then write; prevent both |
| `FOR UPDATE SKIP LOCKED` | — | — | Job queue: grab a row, skip ones already locked |

**`SKIP LOCKED` for job queues:**

```sql
-- Multiple workers competing for jobs
SELECT * FROM jobs
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- Each worker gets a different job without blocking on each other
```

This is exactly how Pravah's Scheduler dispatches jobs without queue contention. Each Scheduler instance grabs one available job, skipping ones already locked by other Scheduler instances.

**When to use pessimistic locking:**

- High contention on the same rows (many concurrent writers to the same record)
- Conflict resolution is expensive (wasted work if conflicts are detected late)
- Critical financial operations where a retry is unacceptable

**Problems with pessimistic locking:**

- **Deadlocks**: Transaction A holds lock on row 1, waits for row 2. Transaction B holds row 2, waits for row 1. Neither can proceed. PostgreSQL detects deadlocks and aborts one transaction.
- **Lock starvation**: A long-running transaction holds a lock. All other transactions queue behind it. Overall throughput degrades.
- **Long-lived locks block replication**: Row locks are held for the duration of the transaction. Long transactions delay PostgreSQL replication slot advancement.

---

## Optimistic Locking

Optimistic locking assumes conflicts are rare and detects them at commit time rather than preventing them upfront.

**How it works:**

Every row has a version counter (or last-modified timestamp). When reading, you record the current version. When writing, you assert the version hasn't changed:

```sql
-- Read the current state
SELECT id, balance, version FROM accounts WHERE id = 42;
-- Returns: balance=1000, version=7

-- Application code processes the business logic (no lock held)

-- Update only if version hasn't changed
UPDATE accounts
SET balance = 900, version = 8
WHERE id = 42 AND version = 7;
-- If 0 rows affected: someone else updated first → retry
```

If the `WHERE version = 7` clause returns 0 affected rows, a concurrent transaction modified the row. The application must retry: re-read the row, re-apply the business logic, re-attempt the update.

**Spring Data JPA implementation:**

```java
@Entity
public class Pipeline {
    @Id
    private UUID id;

    @Version
    private Long version;    // JPA manages this automatically

    private String status;
}

// Repository
pipelineRepository.save(pipeline);
// → generates: UPDATE pipelines SET status=?, version=version+1
//              WHERE id=? AND version=?
// Throws OptimisticLockingFailureException if rows=0
```

**Retry pattern for optimistic locking failures:**

```java
@Retryable(
    value = OptimisticLockingFailureException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2)
)
public void updatePipelineStatus(UUID pipelineId, String newStatus) {
    Pipeline pipeline = pipelineRepository.findById(pipelineId).orElseThrow();
    pipeline.setStatus(newStatus);
    pipelineRepository.save(pipeline);
}
```

**When to use optimistic locking:**

- Low-to-medium contention (conflicts are rare, not the norm)
- Short-lived operations where retrying from the beginning is cheap
- Read-heavy workloads with occasional writes
- Distributed systems where holding a database lock for the duration of a remote call is too expensive

---

## Comparing the Two Approaches

| Dimension | Pessimistic | Optimistic |
|-----------|-------------|------------|
| Lock acquired | At read time | At write time (via version check) |
| Blocking | Other writers block while lock held | No blocking; conflicts detected at commit |
| Failure mode | Deadlocks, starvation under high contention | Retry storms under high contention |
| Best for | High contention, short transactions | Low contention, read-heavy workloads |
| Database support | `SELECT FOR UPDATE` | Application-managed version column |
| Risk | Long-held locks degrade throughput | High contention → repeated retries waste work |

---

## The Retry Storm Problem

Under high contention, optimistic locking creates a retry storm. Imagine 100 transactions competing to update the same row:

- All 100 read version=7
- One commits with version=8
- The other 99 fail, retry
- On retry, 99 read version=8; one commits with version=9
- The other 98 fail, retry
- ...

In the worst case, 100 transactions cause 100 + 99 + 98 + ... = ~5,000 total attempts to complete 100 updates. This is quadratic in the number of concurrent writers. Under extreme contention, pessimistic locking (which serializes writers without retry storms) is actually more efficient.

**Rule of thumb:** Use optimistic locking when the probability of conflict is below ~5%. Above that, pessimistic locking's predictable cost beats the stochastic cost of retry storms.

---

## Application in Pravah

**Pessimistic locking:** The Scheduler uses `SELECT ... FOR UPDATE SKIP LOCKED` to assign jobs to runners. This prevents two Scheduler instances from assigning the same job to two different runners.

**Optimistic locking:** Pipeline definition updates (editing a pipeline in the UI) use optimistic locking via event sourcing (ADR-017). The `sequence_num` in the event store serves as the version vector. Two users editing the same pipeline simultaneously: one succeeds, the other gets a conflict and must refresh and re-apply their change.

**Execution state transitions:** Job state transitions (WAITING → READY → RUNNING → SUCCEEDED) use atomic `UPDATE ... WHERE status = 'EXPECTED_STATE'` — a form of optimistic locking without a version counter. The transition only applies if the row is in the expected state, preventing double-transitions.
