# 3.11 Cold Storage Archival

## Why Cold Storage

Databases store data on disk in formats optimized for random access, transactions, and indexing. This is expensive — high-IOPS SSDs, careful memory management, index maintenance. This expense is justified for recent, actively-queried data where sub-millisecond response times matter.

But not all data is queried frequently. An execution log from 18 months ago is almost never queried. A pipeline run record from 2 years ago might be queried once per month for a compliance audit. Keeping this historical data in PostgreSQL means:

- Paying for expensive SSD storage for data that is rarely accessed
- Large table sizes slow down vacuum, index scans, and replication
- Partitioning strategies become complex (many partitions, many indexes)
- Backup size grows continuously

**Cold storage archival** moves historical data from the operational database to a cheaper, long-term store — typically object storage (MinIO/S3) in a compressed, columnar format (Parquet). Once archived, the data is:

- Queryable for audits and analytics (via DuckDB or Spark reading Parquet)
- Compressed 5–10× vs PostgreSQL's on-disk format
- Stored on cheaper object storage (at ~10% of the cost of block storage)
- Out of the way — no impact on vacuum, index scans, or replication

## The Archival Pipeline

### Step 1: Define the Archival Boundary

Data older than the **retention threshold** becomes a candidate for archival. The threshold balances operational needs (recent data is frequently queried) vs storage cost.

Common thresholds:
- Execution logs: archive after 90 days
- Pipeline run records: archive after 2 years
- Audit events: archive after 7 years (regulatory requirement in many jurisdictions)
- Lineage events: archive after 2 years (Elasticsearch ILM, ADR-019)

### Step 2: Export to Parquet on MinIO

```sql
-- For PostgreSQL → MinIO archival (using DuckDB as the bridge)
-- Alternatively: pg_dump, COPY TO, or Spark JDBC

-- DuckDB on the archival job:
ATTACH 'postgresql://user:pass@host/execution_db' AS pg (TYPE POSTGRES);
COPY (
    SELECT * FROM pg.job_attempts
    WHERE completed_at < NOW() - INTERVAL '90 days'
)
TO 's3://pravah-archives/tenants/{tenant}/job_attempts/year=2026/month=01/part-001.parquet'
(FORMAT PARQUET, COMPRESSION ZSTD, ROW_GROUP_SIZE 100000);
```

**Why Parquet?**
- **Columnar**: queries that read 3 columns out of 50 only read 3 columns from disk — not the full row
- **Compressed**: ZSTD compression achieves 5–8× compression ratio over raw text for typical database tables
- **Predicate pushdown**: Parquet's row group statistics (min/max per column per group) let query engines skip row groups that don't match the query filter without reading the data
- **Self-describing**: schema is embedded in the file header — no external schema catalog needed to read the file

**Parquet partition scheme (Hive-style):**

```
s3://pravah-archives/tenants/{tenant_id}/
├── job_attempts/
│   ├── year=2026/month=01/   ← date partitioning
│   │   ├── part-001.parquet  ← ~100MB per file
│   │   └── part-002.parquet
│   └── year=2026/month=02/
├── pipeline_events/
│   └── year=2026/month=01/
└── lineage_events/
    └── year=2026/month=01/
```

The `year=` / `month=` partition naming follows the Hive metastore convention, which is understood natively by Spark, Athena, and DuckDB:

```sql
-- DuckDB reading partitioned Parquet with partition pruning
SELECT * FROM read_parquet(
    's3://pravah-archives/tenants/megacorp/job_attempts/year=2026/**/*.parquet',
    hive_partitioning=true
)
WHERE year = 2026 AND month = 1 AND status = 'FAILED';
-- DuckDB skips all other year/month partitions automatically
```

### Step 3: Delete from Operational Database

Only after the archival is verified complete (file exists on MinIO, row count matches):

```sql
-- Verify archival completeness first
-- Then delete from operational table
DELETE FROM job_attempts
WHERE completed_at < '2026-02-01'
  AND tenant_id = 'megacorp';

-- Or drop the entire partition (if using table partitioning — much faster)
ALTER TABLE job_attempts DETACH PARTITION job_attempts_2026_01;
DROP TABLE job_attempts_2026_01;
```

Dropping a partition is near-instantaneous — it is a metadata operation, not a row-by-row DELETE. This is why table partitioning (ADR chapter 3.4) and cold storage archival are designed together.

### Step 4: Register in the Archive Catalog

After archival, register the archive location in the Metadata Service so queries can discover historical data:

```json
{
  "table": "job_attempts",
  "tenant_id": "megacorp",
  "period": "2026-01",
  "archive_location": "s3://pravah-archives/tenants/megacorp/job_attempts/year=2026/month=01/",
  "row_count": 8450000,
  "size_bytes": 2147483648,
  "archived_at": "2026-02-05T00:00:00Z",
  "schema_version": 3
}
```

## Querying Cold Archives

Cold data is not gone — it is queryable, just slower (seconds, not milliseconds):

```sql
-- Audit query: show all failed jobs for tenant X in January 2026
-- This runs against MinIO (cold), not PostgreSQL (hot)
SELECT job_id, pipeline_id, step_id, error_category, completed_at
FROM read_parquet(
    's3://pravah-archives/tenants/megacorp/job_attempts/year=2026/month=01/**/*.parquet'
)
WHERE status = 'FAILED'
ORDER BY completed_at DESC;
```

DuckDB can read this directly from MinIO in ~5–30 seconds for a 1 billion row table, with predicate pushdown and parallel read across Parquet files. For compliance audits and historical analytics, this is perfectly acceptable.

For more complex analytics across multiple archive periods, Spark or Athena can run against the same Parquet files in parallel.

## The Archival Safety Protocol

Archival must be **idempotent** and **verified**. Deleting data from the database before confirming the archive exists is catastrophic.

The protocol:

```
1. Export to Parquet (with a .tmp suffix: part-001.parquet.tmp)
2. Verify: read the .tmp file, compare row count vs source table
3. If counts match: atomically rename .tmp → part-001.parquet
4. Verify: the renamed file exists and is readable
5. Only then: DELETE from the operational database
6. Record: archival metadata in catalog
```

If step 2, 3, or 4 fail: abort, delete the .tmp file, alert. Do not proceed to step 5.

If the process crashes between steps 4 and 5: the archive exists but the database has not been cleaned. On next run, the archival job detects the archive already exists (the .parquet file, not the .tmp), skips the export, and proceeds to the delete. Idempotency is preserved.

## Storage Tiering

Object storage is not uniform. S3 and MinIO support storage classes (tiers) with different access latency and price:

| Tier | Access Time | Cost | Use |
|------|------------|------|-----|
| Standard (Hot) | Milliseconds | Highest | Archives queried weekly |
| Standard-IA (Warm) | Milliseconds | Medium | Archives queried monthly |
| Glacier / Archive | Minutes | Lowest | Compliance archives (7 years) |

Pravah's lifecycle policy (ADR-021) transitions archives through tiers automatically:

```
Archive created → Standard (hot)  for 30 days
→ Standard-IA (warm)              for 1 year
→ Glacier (cold)                  for 5 years
→ Deleted                         after 7 years (or configured retention)
```

This provides compliance-grade retention at a fraction of the cost of keeping data in Standard storage forever.

## Application in Pravah

**Tables that are archived:**

| Table | Service DB | Archive Threshold | Retention |
|-------|-----------|-------------------|-----------|
| `job_attempts` (logs) | execution_db | 90 days | 2 years |
| `pipeline_events` (event store) | pipeline_db | 2 years | 7 years |
| `lineage_events` | Elasticsearch | 90 days hot + ILM | 2 years |
| `audit_events` | audit_db | 1 year | 7 years |

Archival runs as a nightly Kubernetes CronJob at 2am UTC, processing one month of data at a time for each tenant. The archival job is idempotent — re-running it for a period that is already archived does nothing.
