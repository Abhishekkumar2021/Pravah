# 3.7 Sharding Strategies

## What Is Sharding and When Does It Become Necessary?

Sharding is horizontal partitioning of data across multiple independent database instances. Unlike table partitioning (covered in 3.4 — which splits data across child tables within the same database), sharding splits data across physically separate databases, each on its own hardware.

Before discussing how to shard, the more important question is: **when does sharding actually become necessary?** Most systems reach for sharding far too early, adding massive operational complexity before exhausting simpler options.

---

## The Scaling Ladder — Work Through These First

When a PostgreSQL primary starts showing signs of stress, the correct order of remediation is:

**Step 1: Query optimization** — before anything else. Verify indexes exist and the planner is using them. Run `EXPLAIN (ANALYZE, BUFFERS)` on slow queries. A missing index is responsible for 80% of "database can't keep up" complaints.

**Step 2: Hardware upgrade (vertical scaling)** — modern hardware is surprisingly capable. A 64-core, 512 GB RAM PostgreSQL server with NVMe SSDs handles extraordinary throughput. PostgreSQL scales well with more RAM (larger `shared_buffers`, better cache hit rates) and faster I/O. For many companies, this option is underexplored because cloud VMs default to small sizes.

**Step 3: Connection pooling** — covered in 3.5. Eliminates connection overhead and allows the primary to focus resources on actual query work.

**Step 4: Read replicas** — covered in 3.6. Offloads all read traffic to replicas, giving the primary its full capacity for writes.

**Step 5: Table partitioning** — covered in 3.4. Range-partitioned tables with efficient partition pruning dramatically reduce the data scanned per query and enable instant data retention via `DROP TABLE`.

**Step 6: Application-level caching** — Redis caches frequently read, rarely changing data. Dashboard queries that run every 30 seconds for the same tenant can return cached results for 10 seconds. Reduces primary read load by orders of magnitude for common access patterns.

**Only after exhausting Steps 1–6 is sharding worth the operational cost.**

For reference: Instagram ran PostgreSQL single-primary until hundreds of millions of users. GitHub ran on a single MySQL primary longer than anyone expected. Sharding is the nuclear option — it is the right option for the right scale, but that scale is much higher than most teams think.

---

## When Pravah Will Actually Need Sharding

**Current scale target:** Pravah's Phase 1 target is 10,000 tenants, up to 10,000 jobs per minute peak, 50 million job records per year total. This is entirely manageable on a well-tuned single-primary PostgreSQL with partitioning, connection pooling, and read replicas.

**Scale where sharding becomes necessary for Pravah:**

```
jobs table: ~10 billion rows
Write rate: 1 million inserts/minute sustained
Tenant count: 100,000+
Per-tenant data: terabytes
```

At that scale, even with monthly partitioning, the primary's write throughput becomes the bottleneck. WAL generation saturates I/O. Autovacuum cannot keep up across thousands of partitions. The primary's single-core sequential commit log becomes a bottleneck.

Pravah is not at that scale now. But the architecture must be designed so that sharding is possible when needed — not require a full rewrite.

---

## Sharding Key — The Most Important Decision

When you do shard, the sharding key determines everything: which shard a row lives on, which queries are efficient, which queries require scatter-gather, and how hard it is to rebalance.

**The ideal sharding key:**
- High cardinality (many distinct values — enables even distribution)
- Corresponds to the natural query boundary (most queries filter on this key)
- Immutable (never changes — otherwise rows must move between shards)
- Not monotonically increasing (avoids all writes hitting the same shard — "hot shard")

**For Pravah, the natural sharding key is `tenant_id`:**

Almost every query in Pravah is tenant-scoped:
```sql
WHERE tenant_id = 'megacorp' AND ...
WHERE tenant_id = 'techgiant' AND ...
```

No cross-tenant queries exist in the operational path — a tenant can only see their own data. This means a query for tenant `megacorp` only needs to hit the shard containing `megacorp`'s data. No scatter-gather. No cross-shard joins.

`tenant_id` is stable — a tenant doesn't change their ID. It has sufficient cardinality (100,000 tenants → even distribution across shards).

## Sharding Strategy Options for Pravah

### Option 1: Application-Level Sharding

The application knows which shard to use. A routing layer maps `tenant_id` to a shard connection.

```java
@Component
public class ShardRouter {

    private final Map<String, DataSource> shards;  // shard-0, shard-1, ...
    private final int shardCount;

    public DataSource getShardFor(String tenantId) {
        int shardIndex = Math.abs(tenantId.hashCode()) % shardCount;
        return shards.get("shard-" + shardIndex);
    }
}
```

The application calls `shardRouter.getShardFor(tenantId)` before every database operation.

**Pros:**
- Full control over routing logic
- No additional infrastructure
- Can route to different shard types (hot tenants get dedicated shards, etc.)

**Cons:**
- Cross-shard queries are application code (scatter-gather)
- Schema changes must be applied to every shard
- Adding a shard requires re-hashing and migrating data (rebalancing is hard)
- Cannot do cross-tenant joins (even for admin/billing reporting)

### Option 2: Citus — Distributed PostgreSQL

Citus is a PostgreSQL extension (open source, also available as Azure Cosmos DB for PostgreSQL) that transparently distributes tables across multiple PostgreSQL nodes.

```sql
-- Distribute the jobs table across shards by tenant_id
SELECT create_distributed_table('jobs', 'tenant_id');

-- From the application's perspective, it still queries the coordinator:
SELECT * FROM jobs WHERE tenant_id = 'megacorp' AND status = 'RUNNING';
-- Citus: "megacorp hash → shard 4" → routes to shard 4's PostgreSQL
-- Returns result as if it were a single table ✅
```

The application connects to a Citus coordinator node. The coordinator routes queries to the appropriate worker nodes transparently. Cross-tenant queries that span multiple shards are handled by the coordinator (scatter-gather at the database level, not application level).

**How Citus shards work:**

```
Coordinator (logical entry point)
       │
       │ query: WHERE tenant_id = 'megacorp'
       │
       ▼
Shard routing: hash('megacorp') % 32 = shard-14
       │
       ▼
Worker Node 2 (owns shard-14)
  jobs_14 table: only megacorp's rows
  pipeline_14 table: only megacorp's pipelines
  ...
       │
       ▼
Result returned to coordinator → returned to application
```

**Pros:**
- Transparent to application code (still looks like one PostgreSQL database)
- Citus handles rebalancing when adding worker nodes
- Standard SQL, standard PostgreSQL extensions, Flyway migrations work normally against coordinator
- Co-location: if `jobs` and `pipelines` are both sharded by `tenant_id`, a JOIN between them stays on the same worker node

**Cons:**
- Complex to operate (coordinator is a single point of failure; HA requires Patroni for coordinator too)
- Not all PostgreSQL features work across shards (no distributed foreign keys, limited cross-shard transactions)
- Licensing: Citus open source is good; Citus Analytics (columnar storage) requires a commercial license
- Adds significant operational expertise requirement

### Option 3: Functional Decomposition (Not Sharding, But Adjacent)

Before sharding a database, consider splitting it differently — by service or by data type rather than by tenant.

Pravah already does this: database per service. Each service has its own database. If `execution_db` becomes a write bottleneck, you can split it further:

```
execution_db  → job_definitions_db  (low write, high read)
              → job_runs_db         (very high write — the hot path)
              → saga_state_db       (moderate write, small dataset)
```

This is functional decomposition — splitting by access pattern rather than by tenant. It is operationally simpler than sharding and addresses many write bottlenecks.

### Option 4: Hybrid Sharding — Dedicated Shards for Large Tenants

Large enterprise tenants may generate disproportionate load — 20% of tenants might generate 80% of data.

```
┌──────────────────────────────────────────────────────┐
│             Shard Router                             │
├──────────────────┬───────────────────────────────────┤
│  Large tenants:  │  Small/medium tenants:            │
│  Dedicated shard │  Shared shard pool                │
│                  │                                   │
│  megacorp        │  shard-0: 1,000 tenants           │
│  ─► shard-MEGA   │  shard-1: 1,000 tenants           │
│                  │  shard-2: 1,000 tenants            │
│  techgiant       │  ...                              │
│  ─► shard-TECH   │                                   │
└──────────────────┴───────────────────────────────────┘
```

This is the approach used by many SaaS companies. Largest tenants get dedicated infrastructure (dedicated shard, dedicated connection pool, potentially dedicated hardware). Smaller tenants share shards. The shard mapping is stored in a routing table:

```sql
CREATE TABLE tenant_shard_map (
    tenant_id    VARCHAR(255) PRIMARY KEY,
    shard_id     VARCHAR(50)  NOT NULL,  -- 'shard-0', 'shard-MEGA', etc.
    shard_host   VARCHAR(255) NOT NULL,
    shard_db     VARCHAR(255) NOT NULL
);
```

This also enables pricing tiers: dedicated infrastructure = Enterprise plan; shared infrastructure = Growth plan.

## The Cross-Shard Query Problem

Sharding by `tenant_id` makes intra-tenant queries efficient. But some queries must span tenants:

**Admin and operations queries:**
```sql
-- Find all tenants with jobs stuck in RUNNING > 24 hours (ops alert)
SELECT tenant_id, count(*) FROM jobs
WHERE status = 'RUNNING' AND started_at < NOW() - INTERVAL '24 hours'
GROUP BY tenant_id;
```

This query must scan every shard. With 32 shards, the application (or Citus coordinator) must:
1. Send the query to all 32 worker nodes in parallel
2. Collect results from all 32
3. Merge and aggregate
4. Return final result

This is scatter-gather. It works but is slow for ad-hoc queries and must not be on the critical path.

**Pravah's solution for cross-shard operational data:**

Use a separate analytics system, not the sharded operational database:

```
Sharded PostgreSQL (operational)
       │
       │ Debezium CDC
       ▼
Kafka (job.events, pipeline.events, ...)
       │
       │ consumer
       ▼
ClickHouse or BigQuery (analytics store)
       │
All tenants' data in one place, optimized for aggregate queries
Billing reports, ops dashboards, SLA metrics all go here
```

The sharded operational database handles transactional writes per tenant. The analytics store (non-sharded, columnar, append-only) handles cross-tenant queries. This separation is clean and scales each system independently.

## Rebalancing — The Hardest Part of Sharding

When adding a new shard (because existing shards are full), data must move. Some tenants need to migrate from their current shard to the new one.

**Hash-based sharding (tenant_id hash % N):** adding a shard changes N, changing the hash modulus for every tenant. Half the data moves to the new shard. This is catastrophic — you cannot do it live without a complete migration.

Solution: **consistent hashing**. The hash ring approach assigns each shard to a range of the hash space. When adding a shard, only the range adjacent to the new shard moves:

```
Before (3 shards):
  Hash range 0–33%:  Shard 0
  Hash range 33–66%: Shard 1
  Hash range 66–100%: Shard 2

After (4 shards, insert Shard 3):
  Hash range 0–25%:   Shard 0 ← only 0–25% of Shard 0's data stays
  Hash range 25–50%:  Shard 3 ← new shard
  Hash range 50–75%:  Shard 1
  Hash range 75–100%: Shard 2
```

25% of data moves instead of 50%. With virtual nodes (multiple hash points per shard), the migration is further minimized and distributed across all existing shards.

Citus handles rebalancing automatically: `SELECT rebalance_table_shards('jobs')` moves shards between worker nodes while the system remains online.

## Pravah's Actual Sharding Plan

**Current state:** single-primary PostgreSQL with partitioning, connection pooling, and read replicas. This handles Pravah's target scale for Phase 1 and Phase 2.

**When write throughput on `job_runs` becomes the bottleneck** (sustained > 500,000 inserts/minute, terabytes of active data): migrate `job_runs` to Citus with `tenant_id` as the distribution column. Other tables remain on standard PostgreSQL.

**Why Citus over application-level sharding:**
- Existing query code does not change
- Flyway migrations continue to work against the coordinator
- Citus handles rebalancing
- Co-location with `tenant_id` means intra-tenant joins work efficiently

**The migration path:**

```
Phase 1: PostgreSQL + partitioning (now)
Phase 2: PostgreSQL + partitioning + read replicas (when read load grows)
Phase 3: Citus for job_runs only (when write throughput bottleneck hits)
Phase 4: Full Citus distribution (when operational table sizes become unmanageable)
```

Each step adds complexity only when the previous step is demonstrably insufficient.

## FAANG Interview Angles

**"How does Pravah scale its database when write throughput becomes the bottleneck?"**

> The answer depends on where we are on the scaling ladder. Before sharding, there are several steps worth exhausting first: query optimization to ensure no table scans or missing indexes, vertical scaling (a 64-core machine with NVMe SSDs handles extraordinary write throughput), connection pooling via PgBouncer to eliminate connection overhead, and table partitioning to keep individual table sections small and vacuum-friendly.
>
> Read replicas address read throughput, not write throughput — the primary still handles all writes. When the primary's write throughput is genuinely exhausted, Pravah's plan is Citus distributed PostgreSQL sharded by `tenant_id`. Almost every operational query is tenant-scoped, so sharding by `tenant_id` avoids scatter-gather for the hot path. The application connects to the Citus coordinator and queries as if it were a single database — the distribution is transparent.

**"Why is `tenant_id` the right sharding key for Pravah?"**

> Three reasons. First, it matches the natural query boundary — every operational query in Pravah filters on `tenant_id` first. Routing a query to one shard eliminates scatter-gather entirely for the common case. Second, it enables co-location — if `jobs`, `pipelines`, and `job_runs` are all distributed by `tenant_id`, a join between them stays on the same worker node. Third, `tenant_id` is immutable — tenants don't change their ID, so rows never need to migrate between shards due to key changes.
>
> The alternative — sharding by `job_id` — would spread a single tenant's data across all shards. A query for `megacorp`'s jobs would scatter across all shards, collect results, and merge. That's the opposite of what we want.

**"What's the hardest problem in sharding and how do you solve it?"**

> Rebalancing — adding or removing shards without downtime. With naive hash-based sharding (`tenant_id % N`), adding a shard changes N, and roughly half of all data needs to move. You cannot do this live without a complex migration.
>
> Consistent hashing solves this: the hash space is a ring, and each shard owns a range of the ring. Adding a shard inserts it into the ring, and only the adjacent range migrates — typically 1/N of total data where N is the new shard count. With virtual nodes, the migration is distributed across all existing shards rather than concentrated on one.
>
> Citus handles rebalancing automatically via `rebalance_table_shards()`, which migrates shards between worker nodes while keeping the system online. This is one of the primary reasons to choose Citus over application-level sharding — the rebalancing infrastructure is built in.

---

## Key Takeaways

1. **Exhaust the scaling ladder before sharding.** Query optimization → vertical scaling → connection pooling → read replicas → table partitioning → application caching. Most systems never need sharding.

2. **Sharding key determines everything.** For Pravah: `tenant_id`. Every operational query is tenant-scoped. No scatter-gather for the hot path. Immutable. Sufficient cardinality.

3. **Three sharding options for Pravah:**
   - Application-level sharding: full control, operational burden, rebalancing is hard
   - Citus: transparent to application, handles rebalancing, preferred choice
   - Functional decomposition: split by access pattern, not tenant — often sufficient and far simpler

4. **Cross-shard queries belong in analytics, not operations.** Cross-tenant queries (ops dashboards, billing aggregations) should use a separate analytics store (ClickHouse, BigQuery) fed by Debezium CDC, not scatter-gather across shards.

5. **Rebalancing is the hardest problem.** Consistent hashing minimizes data movement when adding shards. Citus handles it automatically.

6. **Dedicated shards for large tenants.** The top 20% of tenants generating 80% of write volume get dedicated shards. Smaller tenants share shards. Enables different SLA tiers and pricing.

7. **Pravah's current answer: not yet.** Phase 1 and 2 scale is handled by partitioning + pooling + replicas. Citus sharding by `tenant_id` is the plan when write throughput becomes the genuine bottleneck.
