# 7.4 Retrieval-Augmented Generation (RAG)

## The Problem RAG Solves

An LLM's knowledge is frozen at its training cutoff. It does not know:
- Your pipeline names, schemas, and failure history
- The schema of your source databases
- Your organization's data contracts and business rules
- The specific error that occurred at 9am this morning

You could provide all of this in the prompt — but:
1. Context windows have limits (even 200K tokens is finite)
2. Providing everything is expensive (token cost is proportional to context size)
3. Most information is not relevant to most questions — drowning the LLM in irrelevant context degrades response quality

**RAG** (Retrieval-Augmented Generation) solves this by fetching only the relevant subset of your knowledge base at query time and including it in the prompt. Instead of "here is everything," it is "here is what is relevant to this question."

The name describes the process: **retrieve** relevant documents → **augment** the prompt with them → **generate** a response with that augmented context.

---

## Embeddings

The key technology enabling RAG is **embeddings**: numerical representations of text that capture semantic meaning. Sentences with similar meaning have similar (close) embeddings in the embedding space.

```
"The orders pipeline failed with a schema error"
→ [0.023, -0.156, 0.892, ..., -0.031]  (1536-dimensional vector)

"Schema validation failed for the orders ETL job"
→ [0.019, -0.148, 0.901, ..., -0.028]  (very similar vector)

"The weather in London is rainy"
→ [-0.445, 0.234, -0.123, ..., 0.567]  (very different vector)
```

Embedding models (OpenAI `text-embedding-3-small`, Cohere `embed-v3`, or open-source `BGE-M3`) convert text into these vectors. The closer two vectors are (measured by cosine similarity or dot product), the more semantically similar the original texts are.

This enables **semantic search**: find documents that are semantically relevant to a query, even if they don't share exact keywords.

## Vector Databases and pgvector

A vector database stores embeddings and supports efficient similarity search: "find the N most similar vectors to this query vector."

**pgvector** is a PostgreSQL extension that adds vector storage and similarity search. Rather than running a separate vector database, Pravah uses pgvector inside the existing PostgreSQL cluster.

```sql
-- Enable the extension
CREATE EXTENSION vector;

-- Table for failure pattern embeddings
CREATE TABLE failure_patterns (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    pipeline_id  UUID,
    tenant_id    VARCHAR(255),
    description  TEXT,                     -- human-readable text
    embedding    vector(1536),             -- OpenAI text-embedding-3-small dimension
    metadata     JSONB,                    -- { "error_category": "SCHEMA", "resolution": "..." }
    occurred_at  TIMESTAMPTZ
);

-- HNSW index for approximate nearest-neighbor search
-- HNSW: Hierarchical Navigable Small World — efficient for high-dimensional vectors
CREATE INDEX ON failure_patterns USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
```

**Similarity search:**

```sql
-- Find the 5 most similar past failure patterns to the current error
SELECT id, description, metadata,
       1 - (embedding <=> $1::vector) AS similarity  -- cosine similarity
FROM failure_patterns
WHERE tenant_id = $2
ORDER BY embedding <=> $1::vector  -- <=> is the cosine distance operator
LIMIT 5;
```

The `<=>` operator computes cosine distance. The HNSW index makes this fast even with millions of vectors — rather than computing distance to every vector (linear scan), HNSW navigates a graph of approximate nearest neighbors.

## The RAG Pipeline

### Step 1: Indexing (offline)

Before queries can be answered, knowledge must be embedded and stored.

```java
@Service
public class FailurePatternIndexer {

    private final EmbeddingModel embeddingModel;  // Spring AI abstraction
    private final FailurePatternRepository repository;

    // Called when a pipeline failure is resolved (by human or agent)
    public void indexResolvedFailure(ResolvedFailure failure) {
        String text = String.format("""
            Pipeline: %s
            Error type: %s
            Root cause: %s
            Resolution: %s
            """, failure.getPipelineName(), failure.getErrorType(),
             failure.getRootCause(), failure.getResolution());

        // Get embedding from the embedding model
        float[] embedding = embeddingModel.embed(text);

        repository.save(FailurePattern.builder()
            .pipelineId(failure.getPipelineId())
            .tenantId(failure.getTenantId())
            .description(text)
            .embedding(embedding)
            .metadata(Map.of(
                "error_category", failure.getErrorType(),
                "resolution_type", failure.getResolutionType()
            ))
            .build());
    }
}
```

### Step 2: Retrieval (online, at query time)

```java
@Service
public class RAGContextBuilder {

    private final EmbeddingModel embeddingModel;
    private final FailurePatternRepository repository;

    public String retrieveRelevantContext(String query) {
        // Embed the query
        float[] queryEmbedding = embeddingModel.embed(query);

        // Find similar failure patterns
        List<FailurePattern> similar = repository.findSimilar(
            queryEmbedding, tenantId, 5  // top 5
        );

        // Format for inclusion in the prompt
        StringBuilder context = new StringBuilder("## Similar Past Failures\n\n");
        for (FailurePattern pattern : similar) {
            context.append(pattern.getDescription()).append("\n---\n");
        }
        return context.toString();
    }
}
```

### Step 3: Augmented generation

```java
String userQuery = "Why did the orders pipeline fail with error code 500?";
String retrievedContext = ragContextBuilder.retrieveRelevantContext(userQuery);

String augmentedPrompt = userQuery + "\n\n" + retrievedContext;

// The LLM now has both the question and relevant past examples
ChatResponse response = chatClient.prompt()
    .user(augmentedPrompt)
    .tools(tools)
    .call();
```

## Chunking Strategies

Long documents must be split into chunks before embedding. The chunking strategy determines what "one embedding" represents — if chunks are too large, the embedding averages too many concepts and similarity is diluted. If chunks are too small, context is lost.

**Fixed-size chunking:** split into N tokens regardless of content boundaries. Simple, predictable.

**Sentence-based chunking:** split on sentence boundaries. Better for prose — each chunk is a coherent idea.

**Recursive character splitting:** split on natural boundaries (paragraph → sentence → word) until the chunk is under the size limit.

**Document-aware chunking (for Pravah's pipeline definitions):**

```java
// A pipeline definition has natural sections: steps, triggers, connections
// Each section becomes its own chunk with metadata
chunks = [
    { "text": "Pipeline orders-etl, step extract: SELECT * FROM orders", "step": "extract" },
    { "text": "Pipeline orders-etl, step transform: SELECT customer_id, ...", "step": "transform" },
    { "text": "Pipeline orders-etl trigger: CRON 0 9 * * *", "section": "trigger" }
]
```

Metadata attached to each chunk enables **metadata filtering** alongside semantic search:

```sql
SELECT ... FROM chunks
WHERE tenant_id = $1
  AND metadata->>'step' = 'transform'          -- filter by step
ORDER BY embedding <=> $2::vector LIMIT 5;     -- then by similarity
```

## Hybrid Retrieval

Pure semantic search misses exact keyword matches. Pure keyword search (like PostgreSQL full-text search) misses semantic similarities. **Hybrid retrieval** combines both:

```java
// Semantic: find conceptually similar documents
List<Document> semantic = vectorSearch(queryEmbedding, limit=10);

// Keyword: find documents with matching terms
List<Document> keyword = fulltextSearch(query, limit=10);

// Reciprocal Rank Fusion: combine rankings from both searches
List<Document> hybrid = reciprocalRankFusion(semantic, keyword, k=60);
// RRF: score = sum(1 / (k + rank)) for each result across search methods
```

Hybrid retrieval significantly outperforms either method alone, especially for technical queries that mix semantic intent with specific terminology (e.g., "find pipelines using loyalty_tier column" — semantic: pipelines about loyalty, keyword: exact "loyalty_tier" match).

## RAG in Pravah's Agent

The Agent Service uses RAG for the **long-term memory tier** described in ADR-020:

- **What is indexed**: resolved failure patterns with root cause and resolution
- **When indexed**: after each agent-assisted or human resolution of a pipeline failure
- **What is retrieved**: at the start of each diagnosis session, retrieve the 5 most similar past failures based on the current error message + pipeline context
- **How it is used**: similar past failures are included in the system prompt as examples: "Here are similar failures I've seen before and how they were resolved..."

This gives the agent "institutional memory" — it improves over time as more failures are resolved and indexed. After 6 months of use, the agent has seen thousands of failure patterns and can diagnose novel failures by analogy to past ones.
