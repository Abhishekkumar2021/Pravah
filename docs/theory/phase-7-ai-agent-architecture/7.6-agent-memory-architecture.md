# 7.6 Agent Memory Architecture

## Why Agents Need Memory

An LLM call is stateless. Every call receives the full conversation history and returns a response — there is no persistent state inside the model. For a one-shot question-and-answer interaction, this is fine. For an agent that must:

- Remember what it diagnosed last week to see patterns
- Maintain context through a long debugging session
- Recognize that this failure is similar to one it solved three months ago
- Understand a pipeline's history without being told it every time

...statelessness is a problem. Memory is the solution: structured external state that the agent loads at the beginning of each interaction and updates at the end.

The three memory tiers in ADR-020 correspond to three different timescales and access patterns:

| Tier | Timescale | Content | Storage | Access Pattern |
|------|-----------|---------|---------|---------------|
| Short-term | Current session (minutes to hours) | Recent conversation turns | Redis | Loaded on session start |
| Episodic | Weeks to months | Pipeline-specific event history | Event store + PostgreSQL | Retrieved by pipeline_id |
| Long-term | Months to years | Cross-pipeline patterns, resolved failures | pgvector (PostgreSQL) | Semantic similarity search |

## Short-Term Memory: Conversation Context

Short-term memory maintains the conversation within a session. When a user says "why is it still failing?" — the agent must know what "it" refers to from earlier in the conversation.

```java
@Service
public class ConversationMemory {

    private final RedisTemplate<String, ConversationHistory> redis;

    private static final Duration SESSION_TTL = Duration.ofHours(24);
    private static final int MAX_TURNS = 20;

    public List<Message> load(String sessionId) {
        ConversationHistory history = redis.opsForValue().get("session:" + sessionId);
        if (history == null) return List.of();
        return history.getMessages();
    }

    public void save(String sessionId, String userMessage, String assistantResponse) {
        ConversationHistory history = redis.opsForValue()
            .getAndExpire("session:" + sessionId, SESSION_TTL);

        if (history == null) history = new ConversationHistory();

        history.addUserMessage(userMessage);
        history.addAssistantMessage(assistantResponse);

        // Keep only the last MAX_TURNS turns — older turns fall off
        if (history.getTurns() > MAX_TURNS) {
            history.trimToLast(MAX_TURNS);
        }

        redis.opsForValue().set("session:" + sessionId, history, SESSION_TTL);
    }
}
```

**Why Redis:** session memory is high-read, low-write, ephemeral. 24-hour TTL means sessions automatically clean up. Redis's sub-millisecond reads ensure adding memory retrieval to every agent call doesn't noticeably increase latency.

**Why 20 turns maximum:** a 20-turn conversation with typical response lengths is approximately 10,000–20,000 tokens. This comfortably fits in Claude's context window while providing enough history for coherent multi-turn debugging sessions. Older turns are summarized and dropped — the agent does not need the verbatim text of turn 1 when it's on turn 25.

**Summarization for turn overflow:**

When the conversation exceeds the turn limit, rather than simply dropping the oldest turn, summarize it:

```java
if (history.getTurns() > MAX_TURNS) {
    // Summarize the 5 oldest turns into a single context paragraph
    String oldestTurns = history.getOldestTurns(5);
    String summary = summarizationClient.summarize(oldestTurns);
    history.replaceOldestWithSummary(5, summary);
}
```

This preserves the key information from old turns (root cause identified, tools called, hypotheses tested) without keeping the full verbatim text.

## Episodic Memory: Pipeline History

Episodic memory gives the agent access to the full history of a specific pipeline — its events, run history, schema changes, and past failures — without putting it all in context simultaneously.

**Sources for episodic memory:**

1. **Pipeline event store (ADR-017)**: all `PipelineCreated`, `PipelineStepUpdated`, `PipelineVersionPublished` events — the complete change history
2. **Execution history**: recent runs with status, duration, error categories
3. **Schema drift events**: when source/destination schemas changed
4. **Agent action log**: what the agent diagnosed and fixed in the past

**Loading episodic context at diagnosis time:**

```java
@Service
public class EpisodicMemoryLoader {

    public EpisodicContext load(String pipelineId, String tenantId, int lookbackDays) {
        LocalDate from = LocalDate.now().minusDays(lookbackDays);

        // Recent pipeline events (lightweight — just event types and timestamps)
        List<PipelineEvent> recentEvents = eventStore.findByPipelineId(pipelineId, from);

        // Last 20 runs with status and error category
        List<RunSummary> recentRuns = executionRepository.findRecent(pipelineId, 20);

        // Past agent diagnoses and resolutions for this pipeline
        List<AgentResolution> pastResolutions = agentLogRepository
            .findByPipelineId(pipelineId, from);

        return EpisodicContext.builder()
            .pipelineEvents(recentEvents)
            .recentRuns(recentRuns)
            .pastResolutions(pastResolutions)
            .build();
    }
}
```

**Formatting episodic context for the prompt:**

```java
public String formatForPrompt(EpisodicContext context) {
    return """
        ## Pipeline History (last 30 days)

        ### Recent Events
        %s

        ### Run History (last 20 runs)
        %s

        ### Past Agent Diagnoses
        %s
        """.formatted(
            formatEvents(context.getPipelineEvents()),
            formatRuns(context.getRecentRuns()),
            formatResolutions(context.getPastResolutions())
        );
}

// Example formatted output:
// 2026-05-08 14:32 — PipelineStepUpdated (transform, changed SQL)
// 2026-05-08 16:00 — Run FAILED (error: SchemaValidationException)
// 2026-05-09 09:00 — Run FAILED (error: SchemaValidationException)
// 2026-05-10 09:00 — Run FAILED (error: SchemaValidationException)
// (Agent sees: 3 consecutive failures after a step update on May 8 → obvious hypothesis)
```

The episodic context is the most powerful memory tier for pipeline diagnosis: it gives the agent the temporal pattern of when failures started, correlated with when configuration changes occurred.

## Long-Term Memory: Pattern Memory via RAG

Long-term memory accumulates knowledge across all pipelines and all tenants over months and years. It is the "institutional knowledge" of the platform — patterns that generalize across pipelines.

**Storage: pgvector in a dedicated `agent_memory_db`:**

```sql
CREATE TABLE failure_patterns (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       VARCHAR(255) NOT NULL,
    error_category  VARCHAR(100) NOT NULL,
    context_text    TEXT NOT NULL,      -- description of the failure context
    resolution_text TEXT NOT NULL,      -- what was done to fix it
    embedding       vector(1536) NOT NULL,
    occurred_at     TIMESTAMPTZ NOT NULL,
    resolved_at     TIMESTAMPTZ,
    resolution_type VARCHAR(100),       -- AUTO_HEALED / HUMAN_FIXED / PROPOSED_ACCEPTED
    success         BOOLEAN NOT NULL    -- was the resolution effective?
);

CREATE INDEX ON failure_patterns USING hnsw (embedding vector_cosine_ops);
```

**What gets indexed:**

- Every failure that the agent diagnoses (regardless of whether it was auto-healed or human-resolved)
- The context: pipeline type, error category, step type, schema involved
- The resolution: what was changed, what was the outcome

**Retrieval at diagnosis time:**

```java
public String retrieveSimilarPatterns(String currentContext, String tenantId) {
    float[] queryEmbedding = embeddingModel.embed(currentContext);

    List<FailurePattern> similar = failurePatternRepository.findSimilar(
        queryEmbedding, tenantId, 5,
        0.75f  // minimum similarity threshold — don't retrieve dissimilar patterns
    );

    // Filter to only successful resolutions
    return similar.stream()
        .filter(FailurePattern::isSuccess)
        .map(this::formatPatternForPrompt)
        .collect(joining("\n---\n"));
}
```

**Cross-tenant patterns (careful with privacy):**

For some pattern types (e.g., known DuckDB bug causing transform failures on specific data shapes), the pattern is not tenant-specific. Pravah can index anonymized patterns across tenants — stripped of pipeline names, schema names, and business data:

```
Anonymized pattern:
"Transform step with window function over an unindexed column failed with OOM 
when source table exceeded 100M rows. Resolution: added index on the partition 
column; row count threshold configured in step parameters."
```

This anonymized cross-tenant knowledge (only the technical pattern, no business context) makes all tenants benefit from every failure resolution across the platform.

## Memory Assembly at Runtime

Before each agent invocation, all three tiers are loaded and assembled into the context:

```java
@Service
public class AgentContextAssembler {

    public AgentContext assemble(AgentRequest request) {
        // 1. Short-term: conversation history (fast, Redis)
        List<Message> conversationHistory = conversationMemory.load(request.getSessionId());

        // 2. Episodic: pipeline-specific history (medium, PostgreSQL)
        EpisodicContext episodic = episodicMemoryLoader.load(
            request.getPipelineId(), request.getTenantId(), lookbackDays=30
        );

        // 3. Long-term: similar past failures (semantic search, pgvector)
        String currentContext = buildCurrentContextDescription(request, episodic);
        String similarPatterns = longTermMemory.retrieveSimilarPatterns(
            currentContext, request.getTenantId()
        );

        // Assemble the prompt
        return AgentContext.builder()
            .conversationHistory(conversationHistory)
            .episodicContext(episodic.formatForPrompt())
            .similarPatterns(similarPatterns)
            .build();
    }
}
```

**Token budget management:**

The assembled context must fit within the model's context window, leaving room for:
- The system prompt (~2,000 tokens)
- The assembled context (budgeted: ~20,000 tokens)
- Tool definitions (~3,000 tokens)
- Tool call results (~10,000 tokens)
- The final response (~4,000 tokens)

Total: ~40,000 tokens — well within Claude's 200K window, with room for tool call sequences.

If the episodic context is very long (a pipeline with 100 runs), it is summarized to fit the budget:

```java
if (episodicContext.estimatedTokens() > TOKEN_BUDGET) {
    episodicContext = episodicContext.summarize(TOKEN_BUDGET);
}
```

Summarization is an LLM call itself (using a faster, cheaper model like Claude Haiku) that compresses the long history into the key events.
