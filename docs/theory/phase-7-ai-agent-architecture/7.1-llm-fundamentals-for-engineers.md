# 7.1 LLM Fundamentals for Engineers

## What an LLM Actually Is

A Large Language Model (LLM) is a neural network trained to predict the next token in a sequence. That is literally it. The network takes a sequence of tokens as input and produces a probability distribution over the vocabulary for the next token. The engineering challenge of building "intelligence" from this single prediction task is what makes LLMs fascinating and deceptively complex.

The model learned this task by training on a corpus of hundreds of billions of tokens from the internet, books, code repositories, and curated datasets. During training, the network's billions of parameters were adjusted by gradient descent to minimize the difference between predicted and actual next tokens. After enough training, the model has effectively compressed a vast amount of human knowledge into its weights.

**Importantly: the model is stateless.** There is no "memory" between API calls. Every API call receives the full conversation history as input and produces the next response. The apparent continuity of a conversation is an illusion maintained by the application that keeps assembling the conversation history.

---

## Transformers and Attention

The architecture underlying all major LLMs is the **Transformer**, introduced in the paper "Attention Is All You Need" (Vaswani et al., 2017).

The key innovation is **self-attention**: for every token in the sequence, the model learns which other tokens in the sequence are relevant to it. The word "it" in "The pipeline failed because it ran out of memory" is more relevant to "pipeline" than to "memory" — self-attention learns these relationships from training data.

**Why attention matters for engineers:** the attention mechanism is what gives LLMs their ability to handle context. Earlier architectures (RNNs, LSTMs) degraded badly for long sequences because they processed tokens sequentially. Transformers compute attention across all token pairs in parallel — a 10,000-token sequence is handled in the same number of passes as a 100-token sequence (though with more computation).

## Tokenization

LLMs do not operate on characters or words — they operate on **tokens**. A tokenizer splits text into subword units using algorithms like BPE (Byte-Pair Encoding).

```
Text: "PostgreSQL uses MVCC for concurrency"
Tokens: ["Post", "gre", "SQL", " uses", " MV", "CC", " for", " concurrency"]
Token IDs: [4247, 657, 17861, 2315, 20999, 4093, 323, 17715]
```

Key engineering facts about tokenization:

- **Whitespace matters**: " uses" (with leading space) is a different token than "uses". Token boundaries depend on context.
- **Common words are one token**: "the", "and", "is" are single tokens. Rare technical terms split into multiple tokens: "PostgreSQL" → 2 tokens, "MVCC" → 2 tokens.
- **Code tokenizes differently than prose**: code has more unique tokens per line because identifiers, operators, and keywords are all distinct.
- **Token count ≠ word count**: approximately 1 word ≈ 1.3 tokens for English prose. Code and technical text tokenize at higher ratios.

**Why this matters for engineers building agents:**

1. **Cost**: LLM APIs are priced per token (input + output). Knowing how much text costs how many tokens matters for budget planning.
2. **Context window limits**: a model with a 200K token context window can hold approximately 150,000 words — roughly 600 pages of text. Exceeding this limit truncates input.
3. **Structured output formatting**: some token sequences (JSON keys, specific words) are easier for the model to predict than others. Understanding tokenization helps explain why `"status": "FAILED"` is more reliably produced than `"st": "f"`.

## Context Window

The context window is the maximum number of tokens a model can process in a single call (input + output combined).

| Model | Context Window |
|-------|---------------|
| GPT-4o | 128K tokens |
| Claude claude-sonnet-4-5 | 200K tokens |
| Gemini 1.5 Pro | 1M tokens |

**What fits in 200K tokens:**

- Roughly 150,000 words
- A 10,000-line Java codebase
- The last 2 days of pipeline execution logs
- 500 pipeline event records (as JSON)
- A 600-page technical document

**The context window is not "memory":** information outside the context window is not accessible to the model. An agent that needs to reason about events from 3 months ago must either retrieve those events explicitly (RAG) or have them summarized and stored.

**Practical implication for Pravah's Agent Service:** a pipeline with 10,000 job attempts over its lifetime cannot have all attempts in context simultaneously. The episodic memory layer (ADR-020) selects the most relevant 20–50 attempts based on temporal proximity and semantic similarity and includes only those in the context.

## Sampling and Temperature

When the LLM predicts the next token, it produces a probability distribution over all tokens in its vocabulary. **Sampling** decides how to choose from this distribution.

**Temperature** controls the "creativity" vs "determinism" of the output:
- `temperature = 0`: always choose the highest-probability token. Deterministic, consistent, but repetitive.
- `temperature = 0.7`: sample from the distribution with some randomness. Natural-sounding, varied.
- `temperature = 1.0`: sample from the raw distribution. More creative, less predictable.
- `temperature > 1.0`: flatten the distribution toward uniform. Very random, often incoherent.

**For agents doing technical reasoning:** use `temperature = 0` or very low temperatures. You want consistent, deterministic tool calls. A temperature of 0.7 might cause the agent to sometimes call `get_execution_logs` and sometimes call `get_pipeline_definition` for the same query — inconsistent behavior makes agents hard to test.

**For agents generating natural language explanations:** use `temperature = 0.3–0.7`. Some variation in phrasing makes responses sound less robotic.

**Top-P (nucleus sampling):** limits sampling to the smallest set of tokens whose cumulative probability exceeds P. With `top_p = 0.9`, only tokens that together account for 90% of the probability mass are considered. This prevents sampling very-low-probability tokens while still providing variation.

## Tool Calling / Function Calling

Modern LLMs support **tool calling**: the model can output a structured JSON object specifying a function to call instead of natural language text. This is the mechanism that makes agents possible.

```
User: "Why did the orders pipeline fail this morning?"

LLM response (tool call, not text):
{
  "tool": "get_execution_logs",
  "arguments": {
    "execution_id": "exec-abc-123",
    "step_id": "transform",
    "last_n_lines": 50
  }
}

Application calls the function, returns result to LLM:
[
  "2026-05-10 09:15:22 ERROR Column 'loyalty_tier' not found in table 'orders'",
  "2026-05-10 09:15:22 ERROR Schema validation failed"
]

LLM response (natural language):
"The pipeline failed because the 'loyalty_tier' column is missing from the source
table. This is likely a schema change in the source database. I recommend..."
```

Tool calling requires:
1. The LLM to understand what tools are available (defined in the API call as JSON schemas)
2. The LLM to correctly format the tool call JSON
3. The application to execute the tool and return the result
4. The LLM to reason about the result and continue

The LLM is not running code — it is generating structured text that the application interprets as a function call. Security comes from validating and sandboxing the actual function execution in application code, not from trusting the LLM.

## Key Engineering Principles

**The LLM is a component, not the system.** The value of an LLM-powered feature comes from the surrounding system: the tools it can call, the data it has access to, the memory architecture, the validation of its outputs. A powerful LLM with no tools produces only text. A less powerful LLM with rich tools and good context produces real actions.

**Output is not ground truth.** LLMs hallucinate — they produce confident-sounding statements that are factually wrong. Every LLM output that will affect a system (a SQL query, a fix proposal, a routing decision) must be validated before execution.

**Prompts are code.** A system prompt is part of the software. It has bugs, regressions, and requires version control. A change to the system prompt must be treated as a code change with testing.

**Latency is high.** A single LLM API call takes 500ms–10s depending on output length and model. Multi-turn ReAct loops with 5 steps can take 20–60 seconds. Design for this — show users progress indicators, stream responses token-by-token, time out long-running agent tasks.
