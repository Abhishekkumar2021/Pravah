# 7.2 Agentic Patterns — ReAct, Plan-and-Execute, Tool Use

## What Makes an Agent

A simple LLM call takes user input and returns a response. An **agent** takes user input and takes actions — it queries APIs, reads files, executes code, and modifies state in the world. The difference is not the model; it is the surrounding system.

An agent has:
- **Tools**: typed functions the LLM can invoke
- **A loop**: the LLM can take multiple steps before returning a final answer
- **Memory**: context from previous steps and past interactions
- **Goals**: a task to complete, not just a single question to answer

The loop is what distinguishes an agent from a single LLM call. An agent can reason, act, observe the result, and reason again — iterating until the task is complete or it determines the task cannot be completed.

## ReAct (Reasoning + Acting)

**ReAct** (from the paper "ReAct: Synergizing Reasoning and Acting in Language Models", Yao et al., 2022) is the foundational agentic pattern. Each step of the agent's loop has three parts:

1. **Thought**: the LLM reasons about what it knows and what it needs to find out next
2. **Action**: the LLM calls a tool (or produces a final answer)
3. **Observation**: the application executes the tool and returns the result

This interleaving of reasoning and acting is the key insight. Without explicit reasoning steps, the LLM makes decisions based only on the original prompt. With ReAct, the LLM integrates each observation into its reasoning before the next action — it builds understanding incrementally.

**ReAct loop for "why did pipeline X fail?":**

```
Input: "The orders pipeline failed at 9am. Diagnose and fix it."

=== Step 1 ===
Thought: I need to find out what error occurred. I'll check the execution logs for the most recent run.
Action: get_execution_logs(pipeline_id="orders-etl", execution_id="latest", last_n_lines=50)
Observation: ["ERROR Column 'loyalty_tier' not found in table 'orders'",
               "ERROR SchemaValidationException at step: transform"]

=== Step 2 ===
Thought: The error is a missing column. I need to understand when this column existed and when it disappeared. I'll check the lineage for the orders table.
Action: get_column_lineage(dataset_id="postgres://prod/public.orders")
Observation: { "current_schema": ["customer_id", "revenue", "order_date"], 
               "last_seen_schema": ["customer_id", "loyalty_tier", "revenue", "order_date"],
               "drift_detected_at": "2026-05-08T14:32:00Z" }

=== Step 3 ===
Thought: The column 'loyalty_tier' was removed from the source table on May 8. The transform was written before that removal. I need to get the current transform SQL to understand the fix.
Action: get_pipeline_definition(pipeline_id="orders-etl", step_id="transform")
Observation: { "sql": "SELECT customer_id, loyalty_tier, revenue FROM orders" }

=== Step 4 ===
Thought: The SQL references 'loyalty_tier' which no longer exists. I can fix this by either removing the column from the SELECT (if downstream doesn't need it) or providing a default value. Since I can't know downstream impacts, I'll use COALESCE with a default and create a draft version.
Action: propose_fix(pipeline_id="orders-etl", step_id="transform",
  new_sql="SELECT customer_id, COALESCE(loyalty_tier, 'UNKNOWN') AS loyalty_tier, revenue FROM orders")
Observation: { "draft_version": "v5", "validation": "PASSED", "dry_run_rows": 42150 }

=== Final Answer ===
"Root cause: Column 'loyalty_tier' was removed from the source table 'orders' 
on May 8, 2026, causing a schema validation failure in the transform step.

Fix applied: Created draft version v5 with COALESCE to handle the missing column.
The dry run processed 42,150 rows successfully.

Recommendation: Verify with the data engineering team whether 'loyalty_tier' 
removal was intentional. If so, remove it from downstream transforms entirely 
rather than using a default value."
```

The final answer emerges from 4 tool calls and the reasoning between them — not from the initial prompt alone.

## Plan-and-Execute

ReAct generates the next action at each step based on the previous observation. This is reactive — great for unknown problem spaces but inefficient when the solution path is predictable.

**Plan-and-Execute** separates planning from execution:

1. **Planning phase**: the LLM generates a full multi-step plan before any tools are called
2. **Execution phase**: each plan step is executed in sequence (possibly by a specialized sub-agent)
3. **Re-planning (optional)**: if a step fails or produces an unexpected result, return to planning

```
Input: "Build a pipeline that extracts from our Salesforce CRM, 
       transforms the data, and loads into Snowflake."

Planning phase:
Plan:
  1. Discover the Salesforce schema (available objects, fields)
  2. Identify relevant objects: Account, Contact, Opportunity
  3. Design the extraction SQL per object
  4. Design the transformation (denormalize to analytics schema)
  5. Generate the Pravah pipeline YAML
  6. Validate the YAML against the pipeline schema
  7. Create a draft pipeline

Execution phase:
  Execute step 1: get_connector_schema(connector="salesforce", ...)
  Execute step 2: [LLM selects Account, Contact, Opportunity from schema]
  Execute step 3: [LLM generates extraction SQL for each object]
  ...
```

Plan-and-Execute is better for:
- Long, predictable tasks where intermediate results are unlikely to change the overall approach
- Tasks where the user wants to see and approve the plan before execution
- Parallel execution (steps 3a, 3b, 3c can execute in parallel once step 2 is done)

ReAct is better for:
- Debugging and diagnosis where the solution path is unknown upfront
- Tasks where each observation significantly changes the next action
- Interactive tasks where latency per step matters (ReAct gets results faster per step)

## Multi-Agent Systems

Complex tasks can be decomposed into specialized sub-agents. Each sub-agent is optimized for one part of the problem.

**Pravah multi-agent example:**

```
Orchestrator agent receives: "My pipeline has been failing for 3 days. Fix it."

Orchestrator spawns:
  ├── Diagnosis agent: analyzes logs and lineage to find root cause
  ├── Impact agent: determines what downstream systems are affected
  └── Fix agent: proposes and validates code changes

Orchestrator receives results:
  Root cause: schema drift in source DB (diagnosis agent)
  Impact: 3 downstream dashboards affected (impact agent)
  Fix: updated transform SQL, validated (fix agent)

Orchestrator composes final response and initiates fix
```

Multi-agent patterns add complexity: agent coordination, partial failure (one sub-agent fails while others succeed), context sharing between agents. Start with single-agent ReAct and graduate to multi-agent only when the task is genuinely too complex for a single agent loop.

## Tool Design Principles

Tools are the interface between the LLM and the real world. Their design directly determines the agent's capability.

**Make tools specific, not general:**

```java
// Bad: too general, ambiguous parameters
@Tool("query_database")
public String queryDatabase(String sql) { ... }

// Good: specific purpose, typed parameters
@Tool("get_execution_logs")
public ExecutionLogs getExecutionLogs(
    @ToolParam("execution_id") String executionId,
    @ToolParam("step_id") String stepId,
    @ToolParam("last_n_lines") int lastNLines  // bounded parameter
) { ... }
```

A general `queryDatabase(sql)` tool would let the LLM construct arbitrary SQL — opening injection vulnerabilities and making the LLM's job harder (it must construct SQL instead of just specifying what it wants).

**Write tool descriptions for the LLM, not for humans:**

The tool description is what the LLM reads to decide whether to call the tool. It must be precise about what the tool does, what its parameters mean, and when to use it.

```java
@Tool(description = """
    Retrieves the last N lines of execution logs for a specific step in a pipeline run.
    Use this when diagnosing a step failure to understand the error message and stack trace.
    Returns structured log entries with timestamps, severity levels, and messages.
    For step-level errors, prefer this over pipeline-level logs.
    """)
public ExecutionLogs getExecutionLogs(...) { ... }
```

**Always bound the output size:** a tool that returns unbounded data can overflow the context window. `get_execution_logs` takes `last_n_lines` (default 50, max 200). `get_recent_runs` takes `last_n` (default 10, max 50). The agent can request more if needed, but the default is bounded.

**Never trust tool input:** the LLM might hallucinate tool arguments. Validate every argument in the tool implementation:

```java
if (lastNLines < 1 || lastNLines > 200) {
    throw new ToolArgumentException("last_n_lines must be between 1 and 200");
}
if (!executionRepository.existsByIdAndTenantId(executionId, currentTenantId)) {
    throw new ToolArgumentException("Execution not found in current tenant");
}
```

## Agentic Anti-Patterns

**Over-tooling:** giving the agent 50 tools creates confusion. The LLM must choose from 50 options at each step — it will sometimes choose poorly. Keep the tool set focused on the task domain: diagnosis agents get diagnosis tools; pipeline builder agents get pipeline creation tools.

**Runaway loops:** an agent that cannot solve a problem may loop forever — calling tool after tool in search of a solution that doesn't exist. Always set a maximum step limit (e.g., 15 steps) and terminate with a "could not resolve" answer if exceeded.

**Silent failures:** if a tool call fails, the agent must know about it. Do not catch exceptions in tools and return empty results — return structured error information so the agent can reason about the failure: `{ "error": "PERMISSION_DENIED", "message": "Agent lacks access to this pipeline's logs" }`.

**Ignoring context:** agents should not repeat the same tool call with the same arguments. If the agent calls `get_execution_logs(exec-abc, transform)` twice in a loop, it has gotten stuck. Detection: if the last 3 tool calls are identical, terminate the loop.
