# 7.5 Prompt Engineering & Guardrails

## Prompts Are Code

A system prompt is not documentation. It is executable code that runs inside the LLM and directly controls the agent's behavior. Like code, it:
- Has bugs (instructions that produce wrong behavior in edge cases)
- Has regressions (a change that fixes one problem creates another)
- Requires version control (what prompt produced this output?)
- Requires testing (does it behave correctly across a range of inputs?)

The discipline of **prompt engineering** is writing precise, testable, maintainable instructions that produce consistent, correct behavior from an LLM.

---

## The System Prompt

The system prompt is the foundation of the agent's behavior. It runs at the beginning of every interaction and sets the agent's persona, capabilities, constraints, and formatting expectations.

**Structure of an effective system prompt:**

```
# Identity
You are Pravah's AI assistant for data pipeline operations...

# Core Capabilities
Your primary tasks are:
1. Diagnosing pipeline failures (use execution logs, lineage, schema)
2. Suggesting and validating fixes (create draft versions only)
3. Answering questions about data lineage and quality

# Behavioral Rules
- Always check execution logs before forming a diagnosis hypothesis
- Never make a diagnosis based solely on the error message without log evidence
- When proposing a fix, always validate it before presenting it to the user
- If you need more information, ask one specific question rather than multiple

# Scope and Constraints
- You operate within the {tenant_id} tenant's data only
- You cannot modify production pipeline definitions (use propose_fix to create drafts)
- You cannot trigger pipelines without user confirmation in chat mode
- Maximum 10 tool calls per investigation

# Output Format
Structure your final answer as:
## Root Cause
[one-paragraph explanation]

## Evidence
- [bullet points of supporting evidence]

## Recommended Action
[specific steps the user should take]
```

**Specificity over generality**: vague instructions ("be helpful") produce vague behavior. Specific instructions ("always check execution logs before forming a hypothesis") produce testable, consistent behavior.

**Rules should be actionable**: "be careful about security" is not actionable. "Never generate SQL with DROP, DELETE, or TRUNCATE unless the user explicitly provides the table name and confirms the operation" is actionable.

## Few-Shot Prompting

Providing examples of correct behavior in the prompt significantly improves output quality. This is **few-shot prompting**: showing the model a few examples of the input-output pattern you want.

```
## Example Investigations

### Example 1: Schema Error
User: "The transform step failed"
Correct approach:
1. Called get_execution_logs(step_id="transform") → found "Column 'email' not found"
2. Called get_column_lineage(dataset="orders") → found email was removed 2 days ago
3. Called get_pipeline_definition → confirmed SQL references 'email'
4. Called propose_fix with COALESCE → validation passed
Response: Explained schema drift, proposed fix with validation results

### Example 2: Timeout Error
User: "Pipeline hung for 4 hours"
Correct approach:
1. Called get_execution_logs → found "Query exceeded 3600 second timeout"
2. Called get_recent_runs → found this step normally takes 45 minutes
3. Called get_pipeline_definition → found no index on the join column
Response: Identified missing index as root cause, suggested adding index
```

Few-shot examples teach the model the expected reasoning pattern more reliably than abstract rules alone. The model learns by example: "when I see a schema error, I check these things in this order."

## Chain-of-Thought Prompting

For complex multi-step reasoning tasks, instructing the model to think step-by-step before answering produces more accurate results than asking for a direct answer.

```
System prompt addition:
"Before providing your diagnosis, think through the following:
1. What error type is this? (schema, timeout, resource, permission, data quality)
2. What evidence would confirm or deny each possible cause?
3. Which tool should I call first to gather the most informative evidence?
4. What is the probability of each root cause based on the evidence so far?
Then state your conclusion."
```

Chain-of-thought is especially important for diagnostic agents because the reasoning process (Thought in the ReAct loop) should be explicit. If the model's reasoning is visible in the output or logs, debugging incorrect diagnoses is much easier.

## Structured Output

When the agent must produce data that the application will process programmatically (not display to a human), use **structured output** — constrain the model to produce valid JSON that matches a schema.

```java
// Spring AI structured output
DiagnosisResult result = chatClient.prompt()
    .user(diagnosticPrompt)
    .tools(tools)
    .call()
    .entity(DiagnosisResult.class);  // Spring AI validates and deserializes JSON output

// DiagnosisResult schema is communicated to the LLM in the prompt
// Spring AI appends: "Respond with JSON matching this schema: { root_cause: string, ... }"
```

Without structured output, parsing LLM text for data fields is fragile. The model might format things differently on different runs. Structured output constrains the format with a JSON schema, making the agent's output machine-readable and reliable.

## Guardrails

Guardrails are constraints that prevent the agent from taking harmful actions, even if the LLM's reasoning leads it there.

**Input guardrails** — validate or filter user input before it reaches the LLM:

```java
public String sanitizeUserInput(String input) {
    // Prevent prompt injection attempts
    if (input.contains("Ignore all previous instructions")) {
        return "[Input contained disallowed pattern]";
    }

    // Truncate excessively long inputs
    if (input.length() > 10_000) {
        input = input.substring(0, 10_000) + "...[truncated]";
    }

    return input;
}
```

**Tool-level guardrails** — validate the agent's tool calls before executing:

```java
@Tool("propose_fix")
public FixProposal proposeFix(String pipelineId, String stepId, String newSql) {
    // Guardrail: SQL cannot contain data-modifying statements
    if (containsWriteOperations(newSql)) {
        return FixProposal.error("Transform SQL must be read-only SELECT statements only");
    }

    // Guardrail: pipeline must belong to current tenant
    if (!pipelineRepository.belongsToTenant(pipelineId, currentTenantId())) {
        return FixProposal.error("Pipeline not found in current tenant");
    }

    // Guardrail: validate SQL parses correctly before proposing
    SqlValidationResult validation = sqlValidator.validate(newSql);
    if (!validation.isValid()) {
        return FixProposal.error("SQL syntax error: " + validation.getError());
    }

    return createDraftVersion(pipelineId, stepId, newSql);
}
```

**Output guardrails** — validate the agent's final response before sending to the user:

```java
public String validateAndFilter(String agentResponse) {
    // Detect if the response contains any PII patterns
    if (piiDetector.containsPii(agentResponse)) {
        log.warn("Agent response contained PII — redacting");
        agentResponse = piiDetector.redact(agentResponse);
    }

    // Detect if the response contains internal system details that shouldn't be exposed
    if (containsInternalPath(agentResponse)) {
        agentResponse = removeInternalPaths(agentResponse);
    }

    return agentResponse;
}
```

**The defense-in-depth principle applies to guardrails**: a single system prompt instruction saying "never expose internal details" is not sufficient. The system prompt can be overridden via prompt injection. Tool-level validation and output filtering provide defense even if the LLM is tricked.

## Prompt Version Control

Every production deployment must know which prompt produced which output. This enables:
- **Debugging**: "this diagnosis was wrong — what prompt was active?"
- **Regression testing**: "did changing the prompt break any existing test cases?"
- **A/B testing**: "does version A or version B of the prompt produce better diagnoses?"

```java
@Entity
public class PromptVersion {
    private UUID id;
    private String name;              // "diagnosis-agent-v3"
    private String systemPrompt;
    private String modelId;           // "claude-sonnet-4-5-20251101"
    private boolean active;
    private Instant activatedAt;
    private String activatedBy;
}

// Every agent invocation records the prompt version used
@Entity
public class AgentInvocation {
    private UUID id;
    private UUID promptVersionId;     // which prompt was used
    private String tenantId;
    private int toolCallCount;
    private boolean resolved;
    private Duration duration;
    private Instant occurredAt;
}
```

This creates a queryable history: "show me all invocations using prompt v3 that took more than 30 tool calls" — which indicates the prompt is not guiding the agent efficiently.

## Prompt Testing

Prompts require an evaluation framework (Chapter 7.7), but simple regression tests can catch obvious breakage:

```java
@Test
class DiagnosisPromptTest {

    @Test
    void shouldCallExecutionLogsOnFirstStep() {
        // For any schema failure, the first tool call must be get_execution_logs
        MockLLMResponse response = runAgentWithMockLLM(
            "The transform step failed with error code 500",
            new SchemaErrorLogs()
        );
        assertThat(response.getFirstToolCall().getName())
            .isEqualTo("get_execution_logs");
    }

    @Test
    void shouldNotCallTriggerPipelineInChatMode() {
        // In chat mode, the agent must never trigger a pipeline directly
        MockLLMResponse response = runAgentWithMockLLM(
            "Retry the pipeline",
            new TriggerRequestLogs()
        );
        assertThat(response.getToolCalls())
            .noneMatch(call -> call.getName().equals("trigger_pipeline"));
    }
}
```

These tests use the mock `ChatModel` from Spring AI (Chapter 7.3) to verify that the agent's behavior matches expectations for known input patterns — without real LLM calls.
