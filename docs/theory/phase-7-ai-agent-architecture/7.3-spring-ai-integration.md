# 7.3 Spring AI Integration

## What Spring AI Is

Spring AI is the Spring Framework's abstraction layer for AI/LLM integration. Its core value is the same as Spring's value everywhere: a consistent programming model that hides vendor-specific details. You configure a model, write your tool functions, and interact through standardized `ChatClient` and `ChatModel` interfaces — regardless of whether the underlying model is Claude, GPT-4, Gemini, or a locally-hosted Llama.

This matters for Pravah because:
- Model APIs change frequently. Claude claude-sonnet-4-5's API today is not what it will be in 2027. Spring AI absorbs these changes.
- Testing: Spring AI allows swapping in a mock `ChatModel` for unit tests — no real LLM calls needed.
- Vendor switching: moving from Claude to GPT-4o is a configuration change, not a code rewrite.

---

## Core Abstractions

**`ChatModel`**: the lowest-level abstraction. Takes a `Prompt`, returns a `ChatResponse`. Blocking.

**`StreamingChatModel`**: same but returns a `Flux<ChatResponse>` for token-streaming.

**`ChatClient`**: higher-level, fluent API. Manages conversation history, tool definitions, and streaming. This is the primary API for building agents.

**`FunctionCallback`**: Spring AI's representation of a tool. Each `FunctionCallback` has a name, description, input schema (JSON Schema), and an execution function.

## Basic ChatClient Setup

```java
@Configuration
public class AgentConfig {

    @Bean
    public ChatClient chatClient(ChatClient.Builder builder) {
        return builder
            .defaultSystem("""
                You are Pravah's AI assistant for data pipeline operations.
                You help diagnose pipeline failures, suggest fixes, and answer
                questions about data lineage and quality.

                Rules:
                - Always retrieve execution logs before diagnosing a failure
                - Never modify production pipeline definitions directly (create drafts)
                - When uncertain, explain what information you need rather than guessing
                - Limit each investigation to at most 10 tool calls
                """)
            .build();
    }

    @Bean
    public ChatModel chatModel() {
        return AnthropicChatModel.builder()
            .apiKey(System.getenv("ANTHROPIC_API_KEY"))
            .model("claude-sonnet-4-5-20251101")  // specific version pinned
            .temperature(0.1)
            .maxTokens(4096)
            .build();
    }
}
```

## Defining Tools with Spring AI

Spring AI supports two approaches to tool definition:

**Approach 1 — `@Tool` annotation on a method (recommended):**

```java
@Component
public class ExecutionTools {

    private final ExecutionRepository executionRepository;
    private final MinioClient minioClient;

    @Tool(description = """
        Retrieves the most recent execution logs for a pipeline step.
        Use when diagnosing why a step failed.
        Returns timestamps, log level, and message for each log entry.
        """)
    public ExecutionLogs getExecutionLogs(
        @ToolParam(description = "The execution ID of the pipeline run") String executionId,
        @ToolParam(description = "The step ID within the pipeline") String stepId,
        @ToolParam(description = "Number of log lines to return (max 200)") int lastNLines
    ) {
        // Validate
        if (lastNLines > 200) lastNLines = 200;

        // Fetch logs from MinIO
        String logPath = "tenants/%s/executions/%s/steps/%s/logs/execution.log.gz"
            .formatted(currentTenant(), executionId, stepId);

        return minioClient.getObject(logPath, lastNLines);
    }

    @Tool(description = "Retrieves recent pipeline runs including status, duration, and error summary.")
    public List<RunSummary> getRecentRuns(
        @ToolParam("The pipeline ID") String pipelineId,
        @ToolParam("Number of recent runs to return (max 50)") int count
    ) {
        if (count > 50) count = 50;
        return executionRepository.findRecentByPipelineId(pipelineId, count);
    }
}
```

**Approach 2 — `FunctionCallback` bean (for dynamic tools):**

```java
@Bean
public FunctionCallback getMetadataCallback(MetadataClient metadataClient) {
    return FunctionCallback.builder()
        .name("get_dataset_schema")
        .description("Returns the current schema (columns and types) of a dataset")
        .inputType(DatasetSchemaRequest.class)
        .function(request -> metadataClient.getSchema(request.getDatasetId()))
        .build();
}
```

## The ReAct Loop with ChatClient

```java
@Service
public class DiagnosisAgent {

    private final ChatClient chatClient;
    private final ExecutionTools executionTools;
    private final MetadataTools metadataTools;
    private final PipelineTools pipelineTools;

    public AgentResult diagnose(String executionId, String tenantId) {
        // Load relevant context for this execution
        String context = loadExecutionContext(executionId, tenantId);

        ChatClient.CallResponseSpec response = chatClient.prompt()
            .user("Diagnose the failure for execution " + executionId + "\n\nContext:\n" + context)
            .tools(executionTools, metadataTools, pipelineTools)   // provide all tools
            .call();

        // Spring AI handles the ReAct loop internally:
        // - LLM produces tool call → Spring AI invokes the @Tool method → returns result to LLM
        // - Loop continues until LLM produces a text response (final answer)
        // - Max iterations: configured via spring.ai.chat.client.max-tool-calls=10

        String finalAnswer = response.content();
        return AgentResult.of(executionId, finalAnswer);
    }
}
```

Spring AI manages the multi-turn tool calling loop automatically. The `chatClient.call()` does not return until the LLM has produced a final non-tool response. The application does not need to implement the "call tool → return result → call LLM again" loop manually.

## Streaming Responses

For the chat UI, tokens must stream to the browser as they are generated. Spring AI supports streaming natively:

```java
@Service
public class ChatAgent {

    public Flux<String> chat(String userMessage, String sessionId, String tenantId) {
        // Load conversation history from Redis
        List<Message> history = conversationMemory.load(sessionId);

        return chatClient.prompt()
            .messages(history)
            .user(userMessage)
            .tools(conversationTools)
            .stream()
            .content()                     // Flux<String> — one token per emission
            .doOnNext(token -> {
                // Accumulate tokens for conversation history
                streamBuffer.append(token);
            })
            .doOnComplete(() -> {
                // Save full response to conversation history
                conversationMemory.save(sessionId, userMessage, streamBuffer.toString());
            });
    }
}
```

The WebSocket controller receives this `Flux<String>` and sends each token to the browser:

```java
@MessageMapping("/chat")
public Flux<String> handleChat(ChatRequest request, Principal principal) {
    return chatAgent.chat(request.getMessage(), request.getSessionId(),
        tenantContext.getTenantId(principal));
}
```

## Model Abstraction in Practice

Switching from Claude to GPT-4o requires one configuration change:

```yaml
# application.yml

# Claude
spring:
  ai:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}
      chat:
        options:
          model: claude-sonnet-4-5-20251101
          temperature: 0.1

# GPT-4o (same code, different config)
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: gpt-4o
          temperature: 0.1
```

The `ChatClient`, `@Tool` methods, and agent service code are unchanged. This is the key architectural benefit of Spring AI: model switching is a deployment concern, not a code concern.

## Error Handling and Timeouts

LLM API calls can fail (rate limits, network errors, model errors). Spring AI throws typed exceptions:

```java
try {
    return chatClient.prompt()
        .user(userMessage)
        .tools(tools)
        .call()
        .content();
} catch (RateLimitException e) {
    // Anthropic / OpenAI rate limit hit — retry with exponential backoff
    throw new AgentRetryableException("Rate limit exceeded", e);
} catch (ModelException e) {
    // Model returned an error (safety filter, context exceeded, etc.)
    log.error("Model error for tenant {}: {}", tenantId, e.getMessage());
    return "I encountered an error processing this request. Please try again.";
} catch (TimeoutException e) {
    // LLM call exceeded timeout (configured: 60 seconds)
    return "The analysis took too long. Please try a more specific question.";
}
```

**Timeout configuration:**

```yaml
spring:
  ai:
    anthropic:
      chat:
        options:
          timeout: 60s          # per LLM API call
    chat:
      client:
        max-tool-calls: 10      # max ReAct loop iterations
```

## Testing Agent Code

One of Spring AI's most important features for production systems: you can replace the real LLM with a deterministic mock for unit tests.

```java
@SpringBootTest
class DiagnosisAgentTest {

    @MockBean
    ChatModel chatModel;

    @Autowired
    DiagnosisAgent diagnosisAgent;

    @Test
    void shouldDiagnoseSchemaFailure() {
        // Arrange: mock LLM to call get_execution_logs, then return a diagnosis
        when(chatModel.call(any(Prompt.class)))
            .thenReturn(ChatResponse.toolCall("get_execution_logs", Map.of(
                "execution_id", "exec-abc",
                "step_id", "transform",
                "last_n_lines", 50)))
            .thenReturn(ChatResponse.text("Schema drift detected in column 'loyalty_tier'"));

        // Act
        AgentResult result = diagnosisAgent.diagnose("exec-abc", "megacorp");

        // Assert
        assertThat(result.getDiagnosis()).contains("Schema drift");
        assertThat(result.getToolsUsed()).containsExactly("get_execution_logs");
    }
}
```

This allows testing agent logic, tool invocation sequences, and error handling without paying for real LLM API calls — and without the non-determinism of real LLM responses.
