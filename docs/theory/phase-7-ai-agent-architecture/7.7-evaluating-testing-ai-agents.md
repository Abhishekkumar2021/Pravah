# 7.7 Evaluating & Testing AI Agents

## Why Agent Evaluation Is Hard

Unit testing a function is straightforward: given input X, assert output Y. Agent evaluation is harder because:

1. **Output is non-deterministic**: the same input can produce different outputs on different runs (especially with temperature > 0)
2. **Output is open-ended**: there is no single correct answer — there may be many valid diagnoses and many valid fixes
3. **Multi-step evaluation**: the final answer may be correct, but the reasoning path matters too (a correct answer via wrong reasoning is fragile)
4. **Latency and cost**: a comprehensive eval suite that calls a real LLM 1,000 times costs significant money and takes hours

These challenges require a dedicated evaluation framework, not just traditional unit testing.

---

## Evaluation Dimensions

**Correctness**: did the agent arrive at the right root cause or take the right action?

**Reasoning quality**: did the agent use the right tools in a logical order? Did it form hypotheses before jumping to conclusions?

**Tool use efficiency**: did the agent minimize unnecessary tool calls? An agent that calls 15 tools when 3 would suffice is expensive and slow.

**Safety**: did the agent avoid taking actions it was not authorized to take? Did it respect guardrails?

**Latency**: how long did the full ReAct loop take? Acceptable thresholds depend on the use case (auto-heal: <60s, chat: <30s per turn).

**Grounding**: did the agent's response cite evidence from tool results, or did it hallucinate facts?

## The Three Testing Layers

### Layer 1: Unit Tests (Mock LLM)

Test individual agent behaviors with a mock `ChatModel` (Chapter 7.3). Fast, deterministic, no API cost.

```java
@Test
void shouldCallLogsBeforeDiagnosis_onSchemaError() {
    // Arrange
    MockChatModel mockModel = MockChatModel.builder()
        .firstResponse(toolCall("get_execution_logs", Map.of(
            "execution_id", "exec-abc", "step_id", "transform", "last_n_lines", 50)))
        .secondResponse(toolCall("get_column_lineage", Map.of(
            "dataset_id", "postgres://prod/public.orders")))
        .thirdResponse(text("Schema drift detected. Column 'loyalty_tier' was removed."))
        .build();

    // Act
    AgentResult result = diagnosisAgent.diagnose("exec-abc", "megacorp");

    // Assert: first tool call must be get_execution_logs
    assertThat(mockModel.getFirstToolCall().getName()).isEqualTo("get_execution_logs");
    assertThat(result.getDiagnosis()).contains("Schema drift");
    assertThat(result.getToolCallCount()).isLessThanOrEqualTo(5);
}

@Test
void shouldNotTriggerPipelineWithoutConfirmation_inChatMode() {
    MockChatModel mockModel = MockChatModel.responseText("I'll retry the pipeline for you.");

    // Even if the LLM says it will trigger, the guardrail prevents it
    assertThatCode(() -> chatAgent.chat("retry the pipeline", "session-1", "megacorp"))
        .doesNotThrowAnyException();

    assertThat(mockModel.getToolCallsNamed("trigger_pipeline")).isEmpty();
}
```

These run in milliseconds and can be part of the standard CI pipeline.

### Layer 2: Evals — LLM-as-Judge

For subjective quality dimensions (correctness, grounding, explanation quality), use a separate LLM to evaluate the agent's output. This is **LLM-as-Judge**: a powerful LLM (Claude claude-opus-4-5 or GPT-4o) evaluates the diagnosis agent's output against a rubric.

```java
@Component
public class LLMJudge {

    private final ChatClient judgeClient;  // uses a strong model (Claude Opus)

    public EvalScore evaluate(EvalCase evalCase, String agentResponse) {
        String prompt = """
            You are evaluating a data pipeline diagnosis agent's response.

            ## Scenario
            %s

            ## Ground Truth
            Root cause: %s
            Recommended action: %s

            ## Agent Response
            %s

            ## Evaluation Criteria
            Rate the agent's response on these dimensions (1-5 scale):
            1. Correctness: Did it correctly identify the root cause?
            2. Evidence quality: Did it cite specific evidence from logs/lineage?
            3. Actionability: Is the recommended action specific and implementable?
            4. Conciseness: Did it avoid unnecessary verbosity?

            Respond in JSON: { "correctness": N, "evidence": N, "actionability": N, "conciseness": N, "explanation": "..." }
            """.formatted(evalCase.getScenario(), evalCase.getRootCause(),
                         evalCase.getRecommendedAction(), agentResponse);

        return judgeClient.prompt().user(prompt).call().entity(EvalScore.class);
    }
}
```

**Building eval cases (the golden dataset):**

```java
List<EvalCase> goldenCases = List.of(
    EvalCase.builder()
        .id("schema-001")
        .scenario("orders pipeline failed. Logs: 'Column loyalty_tier not found'. Schema drift at 2026-05-08.")
        .rootCause("Source table schema change removed 'loyalty_tier' column on 2026-05-08")
        .recommendedAction("Update transform SQL to remove or provide default for loyalty_tier")
        .expectedFirstTool("get_execution_logs")
        .maxToolCalls(6)
        .build(),

    EvalCase.builder()
        .id("timeout-001")
        .scenario("pipeline hung for 4 hours. No errors in logs. Step: 'load_to_snowflake'.")
        .rootCause("Snowflake warehouse was suspended and auto-resume took >3600s")
        .recommendedAction("Check Snowflake warehouse auto-resume configuration; increase step timeout")
        .expectedFirstTool("get_execution_logs")
        .maxToolCalls(8)
        .build()
);
```

### Layer 3: Integration Tests (Real LLM, Minimal Cases)

A small set of end-to-end tests against the real LLM API, run in CI on every PR merge (not on every commit — too slow and expensive).

```java
@IntegrationTest
@Tag("llm-integration")
class DiagnosisAgentIntegrationTest {

    @Test
    @Timeout(120)   // 2 minute timeout
    void schemaErrorDiagnosis_shouldIdentifySchemaChange() {
        // Setup: real test environment with seeded data
        String executionId = testDataSeeder.createFailedExecution(
            FailureType.SCHEMA_ERROR, "loyalty_tier column missing");

        // Act: real LLM call
        AgentResult result = diagnosisAgent.diagnose(executionId, TEST_TENANT);

        // Assert: flexible assertions (content, not exact string)
        assertThat(result.getDiagnosis().toLowerCase())
            .containsAnyOf("schema", "column", "loyalty_tier");
        assertThat(result.getToolCallCount()).isLessThanOrEqualTo(8);
        assertThat(result.getDuration()).isLessThan(Duration.ofSeconds(60));
    }
}
```

## Regression Testing Prompts

When changing the system prompt, verify that the change does not break existing eval cases:

```bash
# Run eval suite against both prompt versions
./eval-runner.sh \
  --prompt-a "prompts/diagnosis-v2.txt" \
  --prompt-b "prompts/diagnosis-v3.txt" \
  --eval-cases "evals/diagnosis/*.yaml" \
  --judge-model "claude-opus-4-5" \
  --output "eval-results/v2-vs-v3.json"

# Output:
# prompt-a (v2): avg score 4.1 / 5.0 across 50 cases
# prompt-b (v3): avg score 4.3 / 5.0 across 50 cases
# Regressions in v3: schema-007 (correctness 5→3)
# Improvements in v3: timeout-003 (correctness 3→5), grounding-001 (4→5)
```

The eval suite answers: "Did this prompt change make the agent better or worse, and in which cases?"

## Production Monitoring

Evaluation does not stop at deployment. In production, every agent invocation generates signals for ongoing quality monitoring:

```java
// After every agent invocation, collect signals
AgentInvocationMetrics metrics = AgentInvocationMetrics.builder()
    .executionId(executionId)
    .promptVersion(promptVersion.getId())
    .toolCallCount(result.getToolCallCount())
    .duration(result.getDuration())
    .resolved(result.isResolved())
    .resolutionType(result.getResolutionType())
    .build();

metricsRepository.save(metrics);

// Prometheus metrics
agentToolCallCount.observe(result.getToolCallCount());
agentDuration.observe(result.getDuration().toMillis());
agentResolutionRate.increment(result.isResolved() ? 1 : 0);
```

**Key production metrics:**

| Metric | Alert Threshold | Meaning |
|--------|----------------|---------|
| `agent_resolution_rate` | < 60% | Agent failing to resolve too many cases |
| `agent_avg_tool_calls` | > 12 | Agent is not reasoning efficiently |
| `agent_p95_duration_seconds` | > 60s | Auto-heal is too slow to be useful |
| `agent_max_tool_calls_hit` | > 5% of invocations | Agent hitting the loop limit too often |

**Human feedback loop:**

After each auto-heal, the affected pipeline's owner receives a notification:
- "I diagnosed and fixed your pipeline — [link to RCA]"
- "Was this helpful? [Yes] [No, it was wrong] [No, I already fixed it]"

Negative feedback triggers a review: was the diagnosis wrong? Was the fix incorrect? The case is added to the golden eval dataset to prevent regression.

---

## Summary: Building a Quality Agent

Quality in an AI agent is not achieved at deployment — it is maintained continuously:

1. **Unit test** behavioral constraints: tool ordering, safety guardrails, bounded parameters
2. **Eval golden dataset**: 50–200 cases covering the main failure types, used to score prompt changes
3. **LLM-as-Judge**: automate quality assessment for open-ended outputs without human review of every case
4. **Integration tests**: small set of real-LLM tests for end-to-end validation on each release
5. **Production monitoring**: resolution rate, tool call count, latency — alert on regressions
6. **Human feedback loop**: negative feedback feeds the eval dataset and triggers prompt refinement

The feedback loop is what separates a research prototype from a production AI system. The agent improves with every failure it encounters — as long as the tooling to capture, evaluate, and learn from those failures is in place.
