# 5.1 Threat Model & Security Principles

## Why Security Starts with a Threat Model

Every security control costs something — engineering time, operational complexity, performance overhead, developer friction. Without a threat model, security controls are chosen based on convention ("everyone uses JWT"), anxiety ("we should encrypt everything"), or compliance checkbox ("the audit requires MFA").

A threat model forces clarity: who are the realistic attackers, what assets are they after, how would they get there, and what is the actual impact if they succeed? This maps threats to specific controls with measurable tradeoffs — and explicitly decides which risks are acceptable without a control.

For Pravah, the threat model is not hypothetical. As a platform that executes arbitrary user-defined code on behalf of hundreds of enterprise tenants, handles their secrets and credentials, stores their sensitive data, and provides infrastructure for critical business pipelines — the attack surface is real and the stakes are high.

## Assets — What We Are Protecting

**Tier 1 — Critical (compromise = catastrophic)**

```
Tenant pipeline credentials and secrets
  What: API keys, database passwords, SSH keys tenants provide to access their data sources
  Why critical: compromise gives attacker access to tenant's entire data infrastructure,
                not just Pravah

Tenant pipeline code and configurations
  What: SQL queries, transformation logic, business rules
  Why critical: competitive intelligence, IP theft

Execution infrastructure access
  What: ability to execute arbitrary code in Pravah's runner infrastructure
  Why critical: lateral movement, crypto mining, attack other tenants

Cross-tenant data access
  What: one tenant reading another tenant's job results, pipeline configs, or secrets
  Why critical: destroys product trust, regulatory liability (GDPR, SOC 2)

Pravah's own infrastructure credentials
  What: cloud provider API keys, Kubernetes service account tokens, database root credentials
  Why critical: complete platform compromise, all tenants affected
```

**Tier 2 — High (compromise = severe but bounded)**

```
Job execution results and logs
  What: output data from tenant pipelines, log lines from job execution
  Why high: business-sensitive data, may contain PII

Tenant account information
  What: billing details, usage data, user information
  Why high: regulatory and reputational impact

Platform availability
  What: ability of legitimate tenants to run their pipelines
  Why high: SLA breach, revenue impact, customer trust
```

**Tier 3 — Moderate (compromise = significant but recoverable)**

```
Pipeline metadata
  What: pipeline names, schedules, DAG structure (not credentials)

Internal service configuration
  What: feature flags, tuning parameters

Monitoring and observability data
  What: metrics, traces, logs (about Pravah, not tenant data)
```

## Threat Actors — Who Would Attack Pravah

### External Attacker — No Prior Access

**Motivation:** financial gain (ransomware, crypto mining, data theft for sale), competitive intelligence, political/ideological.

**Capabilities:** Internet access, publicly available exploit tooling, automated scanning, social engineering.

**Likely attack vectors:**
- API abuse: brute force authentication, credential stuffing (reused passwords from other breaches)
- Injection attacks: SQL injection, command injection through pipeline config fields
- Dependency vulnerabilities: CVEs in Pravah's Java/npm dependencies
- Public-facing service exploitation: Kubernetes API server, management endpoints

**Realistic threat level: HIGH** — automated attacks are constant. Every public API receives credential stuffing attempts within hours of launch.

### Malicious Tenant — Authenticated but Unauthorized

**Motivation:** access other tenants' data (competitive intelligence, data theft), abuse Pravah's infrastructure (crypto mining with other tenants' resource quotas), cause harm to competitors.

**Capabilities:** legitimate API credentials, knowledge of Pravah's API, ability to probe behaviors.

**Likely attack vectors:**
- IDOR (Insecure Direct Object Reference): accessing `GET /jobs/{other-tenant-job-id}` — does the API validate tenant ownership?
- Resource abuse: submitting computationally expensive jobs that exceed fair quota, affecting other tenants
- Escape from execution sandbox: user-defined pipeline code that tries to access other tenants' data or Pravah's internal network
- Information leakage through error messages: does an error on a non-existent resource reveal whether it exists for another tenant?

**Realistic threat level: HIGH** — multi-tenant platforms face this constantly. One misconfigured authorization check exposes all tenant data.

### Compromised Runner — Insider (Self-Hosted)

**Motivation:** attacker who has compromised a self-hosted runner machine attempts to pivot into Pravah's cloud infrastructure.

**Capabilities:** runner's gRPC credentials, access to job data passed to the runner, ability to send arbitrary gRPC messages.

**Likely attack vectors:**
- Runner sends malicious gRPC messages claiming to be other runners
- Runner attempts to access Vault secrets beyond its entitlement
- Runner tries to communicate directly with internal services (not just the gRPC gateway)
- Runner impersonates completion of jobs it did not execute (data manipulation)

**Realistic threat level: MODERATE** — self-hosted runners are by definition in environments Pravah does not control. The attacker would need to compromise a customer's server first.

### Malicious Insider — Pravah Engineer

**Motivation:** financial (selling data), disgruntlement, coercion.

**Capabilities:** access to production systems, ability to modify deployments, knowledge of the architecture.

**Likely attack vectors:**
- Direct database access to read tenant data
- Exfiltrating secrets from Vault
- Modifying pipeline execution to include data exfiltration

**Realistic threat level: LOW for most organizations, but high impact if realized.** Controls: least-privilege access, audit logs, separation of duties, Vault policies requiring multiple approvals for sensitive operations.

### Supply Chain Attacker

**Motivation:** compromise many organizations through a shared dependency.

**Capabilities:** ability to push malicious code to a library Pravah depends on (NPM, Maven).

**Likely attack vectors:**
- Typosquatting: `pravah-utils` vs `pravah_utils` — attacker publishes malicious package
- Dependency hijacking: compromised maintainer account pushes malicious version
- Build pipeline compromise: poisoned Docker base images

**Realistic threat level: MODERATE** — growing attack vector. Controls: dependency pinning, SBOM generation, image signing, build pipeline isolation.

## The Seven Security Principles Pravah Follows

### 1. Defense in Depth

No single control is the last line of defense. Every layer assumes the previous layer can fail.

An attacker who bypasses JWT authentication (layer 1) still faces service-level authorization (layer 2) → database-level row security (layer 3) → audit logs that detect the anomaly (layer 4).

An attacker who compromises a runner (bypassing all application-layer controls) still cannot reach other services — the runner has no network access to internal services, only the gRPC gateway.

### 2. Least Privilege

Every component gets exactly the permissions it needs to do its job. Nothing more.

```
Execution Service PostgreSQL user:
  GRANT INSERT, UPDATE, SELECT ON jobs, sagas, outbox TO execution_svc;
  -- No access to pipeline_db, runner_db, or any other database
  -- No DROP TABLE, no TRUNCATE

Runner gRPC identity:
  Can: receive job assignments, report heartbeats, report job completion
  Cannot: read other tenants' job data, access Pipeline Service, query Vault for other secrets

Pravah engineer (production access):
  Can: read logs (no PII), view dashboards, query anonymized metrics
  Cannot: directly query the tenant data tables, access Vault production secrets
  Requires: additional approval workflow for elevated production access
```

### 3. Secure by Default

The secure option is the default. Insecure options require explicit opt-in.

- All inter-service communication uses mTLS by default. Plaintext is explicitly disabled.
- All database connections require TLS. Unencrypted connections are rejected at the PostgreSQL configuration level.
- New API endpoints require an explicit authorization rule. There is no "public by default."
- New Vault policies grant zero permissions. Permissions are added explicitly.
- New Kubernetes service accounts have no RBAC roles. Roles are bound explicitly.

### 4. Fail Secure

When a security check fails due to an error (network timeout, unavailable service), the default is to deny access — not grant it.

```java
// ❌ Wrong: on error, allow (fail open)
try {
    boolean authorized = authorizationService.check(tenantId, resourceId);
    return authorized;
} catch (Exception e) {
    log.warn("Auth check failed, defaulting to allowed", e);
    return true;   // ← fail open: attacker can trigger timeouts to bypass auth
}

// ✅ Correct: on error, deny (fail secure)
try {
    return authorizationService.check(tenantId, resourceId);
} catch (Exception e) {
    log.error("Auth check failed, denying access", e);
    throw new AuthorizationException("Authorization service unavailable");
}
```

### 5. Zero Trust Between Services

Every service-to-service call is authenticated and authorized, regardless of network position. Being inside the Kubernetes cluster does not grant implicit trust.

A compromised Execution Service pod must not be able to call Pipeline Service's admin APIs. Every gRPC and HTTP call between services presents a client certificate (mTLS). Every call is logged.

"Trust but verify" is replaced with "verify always."

### 6. Audit Everything Security-Relevant

Every security-relevant event is logged with sufficient context to reconstruct the actor, action, resource, and outcome. Audit logs are immutable — services cannot delete their own audit trail.

```json
{
  "event_type": "AUTHORIZATION_DENIED",
  "timestamp": "2024-01-15T10:00:23.987Z",
  "actor": {
    "type": "TENANT_USER",
    "tenant_id": "megacorp",
    "user_id": "user-abc",
    "api_key_id": "key-xyz"
  },
  "action": "READ",
  "resource": {
    "type": "JOB",
    "id": "job-999",
    "owner_tenant_id": "othercorp"   ← different tenant
  },
  "outcome": "DENIED",
  "reason": "tenant_mismatch",
  "request": {
    "ip": "203.0.113.42",
    "user_agent": "PravahSDK/1.0",
    "request_id": "req-abc123"
  }
}
```

### 7. Minimize Secret Lifetime

Secrets that never expire are ticking time bombs. Every secret has an expiry:

```
JWT access tokens:       15 minutes
JWT refresh tokens:      7 days (rotated on use)
mTLS certificates:       90 days (auto-rotated by cert-manager)
Vault dynamic secrets:   1 hour (database passwords generated per-request)
API keys:                1 year (user-controlled, forced rotation recommended)
Vault AppRole secrets:   24 hours (auto-renewed by agent)
Kubernetes secrets:      Synced from Vault (rotated with Vault)
```

Short-lived secrets limit the window of exposure when a secret is compromised. Combined with audit logs, a compromised 15-minute JWT can be detected and expired before significant damage occurs.

## STRIDE Threat Analysis for Pravah's Critical Paths

STRIDE is a threat classification framework: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege.

### Critical Path: Pipeline Trigger

```
User → API Gateway → Pipeline Service → Execution Service → Runner → Result

Spoofing:
  Threat:  Attacker spoofs another tenant's identity to trigger their pipeline
  Control: JWT with tenant_id claim validated on every request
           API keys hashed (SHA-256) in database, never stored plaintext

Tampering:
  Threat:  Attacker modifies job configuration in transit to change behavior
  Control: TLS for all external communication (no MITM possible)
           mTLS for all internal communication
           Pipeline configs signed with tenant-specific key

Repudiation:
  Threat:  Tenant claims they did not trigger a specific pipeline run
  Control: Immutable audit log records every trigger with API key ID, IP, timestamp, and full request context

Information Disclosure:
  Threat:  One tenant can read another tenant's pipeline results or configs
  Control: Every data access checks tenant_id against JWT tenant_id claim
           PostgreSQL RLS policies enforce tenant isolation at database level
           Error messages never reveal existence of resources belonging to other tenants

Denial of Service:
  Threat:  Attacker submits thousands of jobs to exhaust runner pool
  Control: Rate limiting per API key and per tenant (token bucket)
           Per-tenant job quota enforcement
           Execution cost metering

Elevation of Privilege:
  Threat:  Tenant user gains admin access; runner gains access to other tenants' data
  Control: RBAC with explicit role assignment (no default elevated roles)
           Runner identity scoped to specific tenant (Vault policy)
           No service mesh admin APIs exposed externally
```
