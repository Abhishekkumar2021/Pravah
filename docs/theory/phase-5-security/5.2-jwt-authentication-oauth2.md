# 5.2 JWT Authentication & OAuth 2.0

## The Authentication Problem

Authentication answers one question: who is making this request?

In a distributed system like Pravah, the answer must be verifiable by any service that receives the request — without that service making a synchronous call to a central identity database on every request. Synchronous auth lookups make every service dependent on the auth service's availability and create latency on every API call.

JWTs (JSON Web Tokens) solve this with cryptographic verification: the identity is encoded in a token that is signed by the auth server. Any service can verify the signature using the auth server's public key — without contacting the auth server. Verification is pure CPU, not a network call.

---

## JWT Structure

A JWT consists of three Base64URL-encoded parts separated by dots:

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6InByYXZhaC0yMDI0LTAxIn0
.
eyJzdWIiOiJ1c2VyLWFiYzEyMyIsInRlbmFudF9pZCI6Im1lZ2Fjb3JwIiwicm9sZXMiOlsiUElQRUxJTkVfRURJVE9SIl0sImlhdCI6MTcwNTMxODQwMCwiZXhwIjoxNzA1MzE5MzAwLCJqdGkiOiJ0b2tlbi11dWlkLTEyMyIsImlzcyI6Imh0dHBzOi8vYXV0aC5wcmF2YWguaW8ifQ
.
[RS256 signature bytes]
```

### Header

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "pravah-2024-01"   // key ID — which public key to use for verification
}
```

### Payload (Claims)

```json
{
  "sub":        "user-abc123",           // subject — unique user ID
  "tenant_id":  "megacorp",             // Pravah-specific: which tenant
  "tenant_tier":"ENTERPRISE",           // for feature gating and rate limits
  "roles":      ["PIPELINE_EDITOR"],    // Pravah RBAC roles
  "email":      "alice@megacorp.com",   // display only — never used for auth decisions
  "iat":        1705318400,             // issued at (Unix epoch)
  "exp":        1705319300,             // expires at — 15 minutes after iat
  "jti":        "token-uuid-123",       // JWT ID — unique, enables revocation
  "iss":        "https://auth.pravah.io" // issuer — must match expected value
}
```

### Signature

```
RS256(
  base64url(header) + "." + base64url(payload),
  private_key
)
```

The signature is created with the auth server's RSA private key. Any service can verify it with the corresponding public key (fetched from the JWKS endpoint). Tampering with any part of the token (even changing `"PIPELINE_EDITOR"` to `"ADMIN"`) invalidates the signature.

---

## RS256 vs HS256 — Why Pravah Uses RS256

Two common signing algorithms:

**HS256 (HMAC-SHA256):** uses a single symmetric secret key for both signing and verification. Any service that can verify tokens must possess the same secret. If the secret leaks from any service, tokens can be forged. All services become equal trust principals for token creation.

**RS256 (RSA-SHA256):** uses an asymmetric key pair. The auth server signs with the private key (kept secret, never leaves the auth service). All other services verify with the public key (freely distributed). A service can verify tokens but cannot create them — even if the public key leaks, no token can be forged without the private key.

Pravah uses RS256. The private key lives only in the Auth Service and in Vault. Execution Service, Pipeline Service, Runner Service — all have the public key and can verify tokens, but none can mint new tokens. This is the correct security model for a microservices architecture.

**JWKS endpoint:** the auth server publishes its public keys at `https://auth.pravah.io/.well-known/jwks.json`. Services fetch this at startup and cache it (refreshing when they encounter an unknown `kid`):

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "pravah-2024-01",
      "alg": "RS256",
      "n":   "...",     // RSA modulus
      "e":   "AQAB"    // RSA public exponent
    }
  ]
}
```

The `kid` (key ID) in the JWT header tells the verifying service which key to use. This enables key rotation without breaking in-flight tokens: publish the new key alongside the old key, start issuing tokens with the new `kid`, phase out the old key after all old tokens expire.

## Token Lifetime and the Refresh Pattern

Access tokens are short-lived: 15 minutes. This limits the damage window if a token is stolen — even if an attacker intercepts one, it expires quickly.

But users cannot log in every 15 minutes. Refresh tokens solve this:

```
Authentication Flow:
  User → POST /auth/login (credentials)
  Auth Service → validates credentials
  Auth Service → issues:
    access_token (JWT, 15 min)
    refresh_token (opaque random string, 7 days, stored in DB)
  Client → stores both tokens

Normal API Usage:
  Client → API request with access_token in Authorization header
  API Gateway → validates JWT signature + expiry
  API Gateway → routes request (no auth service call needed)

Token Refresh (access_token expires):
  Client → POST /auth/refresh { refresh_token: "..." }
  Auth Service → validates refresh_token in DB (not expired, not revoked)
  Auth Service → issues new access_token (15 min)
  Auth Service → issues NEW refresh_token (rotation: old one revoked)
  Client → stores new tokens
```

### Refresh Token Rotation

Every time a refresh token is used, it is immediately invalidated and a new one is issued. This detects token theft:

```
Normal case:
  Client A uses refresh_token_1 → gets access_token_2 + refresh_token_2
  refresh_token_1 is now invalid
  Client A uses refresh_token_2 → success

Stolen token case:
  Client A uses refresh_token_1 → gets refresh_token_2
  Attacker (who stole refresh_token_1) also tries to use refresh_token_1 → REJECTED
    (already used — rotation detected)
  
Attacker stole refresh_token_2 and uses it first:
  Attacker uses refresh_token_2 → gets refresh_token_3
  Client A tries refresh_token_2 → REJECTED (already used)
  → Auth service detects reuse of already-used token from this family
  → REVOKE ENTIRE TOKEN FAMILY (all tokens for this session)
  → User must log in again
```

Token families (tracking which refresh tokens belong to the same login session) enable detection and revocation of stolen tokens, even when the attacker acts before the legitimate client.

### Token Revocation for Long-Lived Tokens

The 15-minute access token cannot be revoked before expiry without a lookup on every request. This is an intentional tradeoff for stateless verification. For most cases (user logout, role change), waiting 15 minutes for the token to expire is acceptable.

For emergency cases (security breach, account compromise): invalidate the refresh token immediately — the user's next refresh attempt will fail, forcing re-authentication. At that point, they receive new tokens that reflect their current state.

For administrative actions (ban user, downgrade tenant tier): Pravah implements a short-term revocation list: a Redis set of `jti` (JWT ID) values that are revoked before their natural expiry. Services check this list on every request. The list has TTL equal to the access token lifetime — after 15 minutes, the token would have expired anyway, so there is no need to keep tracking it.

```java
// Redis revocation check — only for emergency revocations
@Component
public class JwtRevocationFilter {

    private final RedisTemplate<String, String> redis;

    public boolean isRevoked(String jti) {
        return redis.hasKey("revoked_tokens:" + jti);
    }

    public void revoke(String jti, Duration tokenRemainingLifetime) {
        redis.opsForValue().set(
            "revoked_tokens:" + jti,
            "revoked",
            tokenRemainingLifetime
        );
    }
}
```

## API Keys — For Programmatic Access

OAuth 2.0 with user login is appropriate for human users via a browser or CLI. But Pravah pipelines are often triggered programmatically — from CI/CD systems, other services, or scripts. These cannot go through an OAuth login flow.

API keys solve this: a long-lived opaque credential that identifies a tenant (and optionally a specific integration).

### API Key Design

```
Format: prv_{version}_{random_bytes_base64url}
Example: prv_1_2F8kL9mN4vQ7xZ3wY5tR6uP

- Prefix "prv_" for identification and accidental commit detection
- Version number for future format changes
- 32 random bytes (256 bits) of entropy — brute force infeasible
```

**Storage:** API keys are **never stored in plaintext**. The database stores only a SHA-256 hash:

```java
public ApiKey createApiKey(String tenantId, String name, String[] scopes) {
    String rawKey = "prv_1_" + generateSecureRandom32Bytes();
    String hashedKey = sha256(rawKey);

    ApiKey apiKey = new ApiKey();
    apiKey.setTenantId(tenantId);
    apiKey.setName(name);
    apiKey.setKeyHash(hashedKey);       // stored in DB
    apiKey.setKeyPrefix(rawKey.substring(0, 12));  // for identification in UI: "prv_1_2F8kL9"
    apiKey.setScopes(scopes);
    apiKey.setCreatedAt(now());
    apiKey.setExpiresAt(now().plusYears(1));
    apiKeyRepository.save(apiKey);

    // rawKey is returned ONCE to the user — Pravah cannot retrieve it again
    return new ApiKeyResponse(rawKey, apiKey.getId());
}
```

**Verification on request:**
```java
public Authentication verifyApiKey(String rawApiKey) {
    String hash = sha256(rawApiKey);
    ApiKey key = apiKeyRepository.findByKeyHash(hash)
        .orElseThrow(() -> new AuthenticationException("Invalid API key"));

    if (key.isExpired() || key.isRevoked()) {
        throw new AuthenticationException("API key expired or revoked");
    }

    // Exchange API key for an internal representation equivalent to a JWT
    return new ApiKeyAuthentication(key.getTenantId(), key.getScopes());
}
```

No database timing attack is possible because SHA-256 comparison is constant-time and the lookup is by hash index.

### API Keys vs OAuth 2.0 — When to Use Each

| Scenario | Use |
|---|---|
| Web dashboard (browser) | OAuth 2.0 + PKCE |
| CLI tool (interactive login) | OAuth 2.0 device flow |
| CI/CD triggering pipelines | API key |
| Service-to-service (internal) | mTLS (no token needed) |
| Webhook receivers | API key (scoped to specific operation) |
| Third-party integrations | API key with limited scopes |

## Spring Security Configuration

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // Stateless — no session cookies
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))

            // CSRF not needed for stateless JWT API
            .csrf(csrf -> csrf.disable())

            // JWT validation via Spring's built-in OAuth2 resource server
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt
                    .jwkSetUri("https://auth.pravah.io/.well-known/jwks.json")
                    .jwtAuthenticationConverter(pravahJwtConverter())
                )
            )

            // Request authorization rules
            .authorizeHttpRequests(auth -> auth
                // Health and metrics: public
                .requestMatchers("/actuator/health/**", "/actuator/prometheus").permitAll()
                // Auth endpoints: public
                .requestMatchers("/auth/login", "/auth/refresh").permitAll()
                // Everything else: requires valid JWT or API key
                .anyRequest().authenticated()
            )

            // Custom filter: accept API keys in addition to JWTs
            .addFilterBefore(apiKeyAuthFilter(), BearerTokenAuthenticationFilter.class);

        return http.build();
    }

    @Bean
    public JwtAuthenticationConverter pravahJwtConverter() {
        JwtGrantedAuthoritiesConverter grantedAuthoritiesConverter =
            new JwtGrantedAuthoritiesConverter();
        grantedAuthoritiesConverter.setAuthoritiesClaimName("roles");
        grantedAuthoritiesConverter.setAuthorityPrefix("ROLE_");

        JwtAuthenticationConverter jwtConverter = new JwtAuthenticationConverter();
        jwtConverter.setJwtGrantedAuthoritiesConverter(grantedAuthoritiesConverter);
        return jwtConverter;
    }
}
```

### Custom JWT Validator — Pravah-Specific Claims

Spring's default JWT validation checks signature, expiry, and issuer. Pravah adds custom validation:

```java
@Component
public class PravahJwtValidator implements OAuth2TokenValidator<Jwt> {

    @Override
    public OAuth2TokenValidatorResult validate(Jwt jwt) {
        List<OAuth2Error> errors = new ArrayList<>();

        // 1. Tenant ID must be present
        String tenantId = jwt.getClaimAsString("tenant_id");
        if (tenantId == null || tenantId.isBlank()) {
            errors.add(new OAuth2Error("missing_tenant_id",
                "JWT must contain tenant_id claim", null));
        }

        // 2. Token must not be revoked (emergency revocation check)
        String jti = jwt.getId();
        if (jti != null && revocationService.isRevoked(jti)) {
            errors.add(new OAuth2Error("token_revoked",
                "This token has been revoked", null));
        }

        // 3. Token must have at least one role
        List<String> roles = jwt.getClaimAsStringList("roles");
        if (roles == null || roles.isEmpty()) {
            errors.add(new OAuth2Error("no_roles",
                "JWT must contain at least one role", null));
        }

        return errors.isEmpty()
            ? OAuth2TokenValidatorResult.success()
            : OAuth2TokenValidatorResult.failure(errors);
    }
}
```

### Extracting Tenant Context in Services

After authentication, every service method can access the current tenant's identity:

```java
@Service
public class PipelineService {

    public Pipeline getPipeline(String pipelineId) {
        // Extract tenant from security context — set by JWT filter
        String tenantId = SecurityContextHolder.getContext()
            .getAuthentication()
            .getName(); // or custom method to extract tenant_id claim

        // Always scope queries to the authenticated tenant
        return pipelineRepository.findByIdAndTenantId(pipelineId, tenantId)
            .orElseThrow(() -> new ResourceNotFoundException(
                // Deliberately vague: don't reveal if it exists for another tenant
                "Pipeline not found: " + pipelineId
            ));
    }
}
```

The repository method `findByIdAndTenantId` includes `tenant_id` in the WHERE clause. Even if the authorization layer has a bug and a wrong tenant ID reaches this method, the database query returns nothing.

## System Design Interview Angles

**"Why does Pravah use RS256 instead of HS256 for JWT signing?"**

> With HS256, all services that verify tokens must share the same secret. In a microservices architecture, this means the secret is distributed across every service — Execution Service, Pipeline Service, Runner Service. If any of these is compromised, the attacker can forge tokens for any tenant with any claims.
>
> With RS256, only the Auth Service holds the private key. Other services verify with the public key, which they fetch from the JWKS endpoint. The public key, by definition, cannot be used to forge tokens. Compromising Execution Service gives the attacker the public key — which they already had, since it's publicly available. They still cannot create valid tokens.
>
> Additionally, RS256 enables clean key rotation: publish a new key alongside the old one in the JWKS endpoint, start issuing tokens with the new `kid`, and phase out the old key after old tokens expire. Services automatically pick up the new key when they encounter an unknown `kid`.

**"How does Pravah handle token revocation without making a network call on every request?"**

> The 15-minute access token lifetime is the primary mechanism. Most revocations (user logout, role change) can wait 15 minutes for natural expiry. This avoids any network call during verification.
>
> For emergency revocations (account compromise, security breach), Pravah maintains a Redis set of revoked JWT IDs (`jti` claims). Services check this set in addition to the signature verification. The Redis check is fast (sub-millisecond), and the entries have TTL equal to the token's remaining lifetime — after which the token would have expired anyway.
>
> For long-lived tokens like refresh tokens: these are stored in the database and looked up on every refresh attempt. Revocation invalidates the database record immediately. The next refresh attempt fails even if the attacker has a valid refresh token.

**"What happens if the Auth Service is unavailable? Can users still access Pravah?"**

> Yes. JWT verification is stateless — it only requires the public key, which is cached by every service at startup. As long as users have valid unexpired tokens (up to 15 minutes of remaining lifetime), they can continue making requests. No Auth Service contact is needed.
>
> New logins require the Auth Service. Token refresh requires the Auth Service. But in-flight users with valid tokens experience no disruption during a brief Auth Service outage.
>
> This is one of the key advantages of JWTs over opaque token reference schemes, where every request requires a lookup against the central auth server. An opaque token database outage makes every request fail immediately. A JWT scheme gives you up to the token lifetime before users notice.

## Key Takeaways

1. **JWT = signed, stateless identity token.** Header (algorithm + key ID) + payload (claims) + signature. Signature makes tampering detectable. Stateless verification removes auth service dependency on every request.

2. **RS256 over HS256.** Asymmetric signing: only auth service can create tokens, any service can verify. Correct trust model for microservices. Enables key rotation without coordinated secret changes.

3. **Short access token lifetime (15 minutes).** Limits stolen token damage window. Refresh tokens (7 days, opaque, stored in DB) enable session continuity. Refresh token rotation detects theft.

4. **API keys for programmatic access.** SHA-256 hashed in database (never stored plaintext). Returned to user exactly once. Prefix (`prv_`) for accidental commit detection in tools like GitHub secret scanning.

5. **Custom JWT validators add Pravah-specific rules:** `tenant_id` presence, revocation list check, role presence. Fail-secure: validation error denies access, never grants it.

6. **Tenant scoping is mandatory at every layer:** JWT contains `tenant_id` claim → service extracts it from SecurityContext → all repository queries include `AND tenant_id = ?` → database RLS also enforces it. Defense in depth: multiple independent enforcement points.

7. **JWKS endpoint enables key rotation without downtime.** `kid` in JWT header identifies which public key to verify with. Services refresh key cache when encountering unknown `kid`.

JWTs authenticate users making API calls from the outside. Internally, services call each other constantly — Execution Service calls Pipeline Service, Runner Service calls Runner Assignment, the scheduler calls Execution Service. These internal calls need authentication too, but the OAuth flow is not appropriate for service-to-service communication.
