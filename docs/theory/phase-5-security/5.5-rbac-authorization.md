# 5.5 RBAC & Authorization

## Authentication Is Not Authorization

Authentication establishes identity: "You are Alice, a user of tenant megacorp." Authorization answers the next question: "What is Alice allowed to do?"

The two are entirely separate concerns and must never be conflated. A correctly authenticated user can still be unauthorized for a specific action. An authentication bug that lets someone impersonate Alice is a different vulnerability than an authorization bug that lets Alice access another tenant's data.

In a multi-tenant platform like Pravah, authorization has two distinct dimensions:

1. **Role-based access control (RBAC):** what actions can this role perform in general?
   *Alice has role `PIPELINE_EDITOR` → she can create, edit, and trigger pipelines.*

2. **Resource ownership:** does this user/tenant own this specific resource?
   *Alice is authorized to edit pipeline `pipe-abc` only if it belongs to megacorp.*

Both checks are required. Role checks without ownership checks → IDOR vulnerability. Ownership checks without role checks → any tenant user can perform admin operations.

---

## Pravah's Role Hierarchy

```
TENANT_ADMIN
  Full access to all resources within the tenant
  Can manage users, API keys, runners, billing
  Cannot access other tenants' data (enforced by tenant scoping, not roles)

PIPELINE_EDITOR
  Can create, edit, trigger, and delete pipelines
  Can view all job history and logs
  Can manage pipeline secrets
  Cannot manage users or billing

PIPELINE_VIEWER
  Read-only access to pipelines and job history
  Can view (not download) job logs
  Cannot trigger pipelines or modify anything

RUNNER_ADMIN
  Can register, configure, and deregister runners
  Can view runner health and job assignment
  Cannot modify pipelines or billing

WEBHOOK_RECEIVER (non-human, API key scoped)
  Can trigger specific pipelines (defined by the API key)
  Cannot read or modify anything

AUDIT_VIEWER (compliance role)
  Read-only access to audit logs
  Cannot view actual data or trigger anything
```

These roles are additive and non-hierarchical — a user can have multiple roles. A CI/CD system might have both `PIPELINE_EDITOR` (to trigger deploys) and `RUNNER_ADMIN` (to provision runners).

## Spring Security Method-Level Authorization

Spring Security's `@PreAuthorize` and `@PostAuthorize` annotations enforce role checks at the method boundary — before or after the method executes.

### Basic Role Check

```java
@Service
public class PipelineService {

    // Only users with PIPELINE_EDITOR role can create pipelines
    @PreAuthorize("hasRole('PIPELINE_EDITOR') or hasRole('TENANT_ADMIN')")
    public Pipeline createPipeline(CreatePipelineRequest request) {
        String tenantId = SecurityContextHolder.getContext()
            .getAuthentication()
            .getPrincipal()
            .getTenantId();

        Pipeline pipeline = Pipeline.builder()
            .tenantId(tenantId)        // always set from auth context — never from request
            .name(request.getName())
            .schedule(request.getSchedule())
            .build();

        return pipelineRepository.save(pipeline);
    }

    // Anyone authenticated (any role) can view pipelines — but only their tenant's
    @PreAuthorize("isAuthenticated()")
    public List<Pipeline> listPipelines(PipelineFilter filter) {
        String tenantId = getCurrentTenantId();
        // tenantId from security context, not from filter parameter
        return pipelineRepository.findByTenantId(tenantId, filter);
    }

    // Deleting requires TENANT_ADMIN — higher privilege
    @PreAuthorize("hasRole('TENANT_ADMIN')")
    public void deletePipeline(String pipelineId) {
        String tenantId = getCurrentTenantId();
        // Ownership check within the method — even ADMIN cannot delete other tenants' pipelines
        Pipeline pipeline = pipelineRepository.findByIdAndTenantId(pipelineId, tenantId)
            .orElseThrow(() -> new ResourceNotFoundException("Pipeline not found: " + pipelineId));
        pipelineRepository.delete(pipeline);
    }
}
```

### The IDOR Vulnerability and Why Role Checks Alone Are Insufficient

IDOR (Insecure Direct Object Reference) is one of the most common vulnerabilities in multi-tenant APIs. The pattern:

```
Attacker (authenticated as megacorp user):
  GET /api/pipelines/pipe-rival-corp-secret-etl

Server (naive implementation — checks role, not ownership):
  Authentication check: ✅ valid JWT
  Role check: ✅ PIPELINE_VIEWER has read access
  Database query: SELECT * FROM pipelines WHERE id = 'pipe-rival-corp-secret-etl'
  Response: 200 OK — reveals rival corp's pipeline configuration

This is an IDOR. The role check passed, but the resource belongs to a different tenant.
```

**The correct pattern — always include tenant ID in queries:**

```java
// ❌ Vulnerable: checks role but not ownership
public Pipeline getPipeline(String pipelineId) {
    return pipelineRepository.findById(pipelineId)
        .orElseThrow(...);
}

// ✅ Correct: checks role (via @PreAuthorize) AND ownership (via tenant-scoped query)
@PreAuthorize("hasAnyRole('PIPELINE_VIEWER', 'PIPELINE_EDITOR', 'TENANT_ADMIN')")
public Pipeline getPipeline(String pipelineId) {
    String tenantId = getCurrentTenantId();
    return pipelineRepository.findByIdAndTenantId(pipelineId, tenantId)
        .orElseThrow(() -> new ResourceNotFoundException(
            // Deliberately vague: don't reveal if the resource exists for another tenant
            "Pipeline not found: " + pipelineId
        ));
}
```

The error message is deliberately vague. If it said "Pipeline exists but belongs to another tenant," it would reveal information about another tenant's resources. "Pipeline not found" is the correct response for both "does not exist" and "exists but belongs to another tenant."

### SpEL Expressions for Complex Authorization

Spring Security's `@PreAuthorize` supports Spring Expression Language (SpEL) for complex authorization rules:

```java
// Custom security expression: current user can edit this specific pipeline
// (either has TENANT_ADMIN, or is PIPELINE_EDITOR and owns the pipeline)
@PreAuthorize("""
    hasRole('TENANT_ADMIN') or
    (hasRole('PIPELINE_EDITOR') and @pipelineAuthService.canEdit(#pipelineId, authentication))
""")
public Pipeline updatePipeline(String pipelineId, UpdatePipelineRequest request) {
    // ...
}

// Custom authorization service
@Service("pipelineAuthService")
public class PipelineAuthorizationService {

    public boolean canEdit(String pipelineId, Authentication auth) {
        String tenantId = extractTenantId(auth);
        // Check that the pipeline exists AND belongs to the current tenant
        return pipelineRepository.existsByIdAndTenantId(pipelineId, tenantId);
    }
}
```

### @PostAuthorize for Response Filtering

`@PostAuthorize` runs after the method executes, useful when the authorization decision depends on the returned object's content:

```java
// Runner assignment details should only be visible to the runner's owning tenant
@PostAuthorize("returnObject.tenantId == authentication.principal.tenantId")
public RunnerAssignment getAssignment(String assignmentId) {
    return assignmentRepository.findById(assignmentId)
        .orElseThrow(...);
}
```

If the returned `RunnerAssignment.tenantId` does not match the authenticated user's `tenantId`, Spring Security throws an `AccessDeniedException` — without the service method knowing about authorization at all.

## Pravah's Authorization Decision Matrix

```
Resource          Action     TENANT_ADMIN   PIPELINE_EDITOR   PIPELINE_VIEWER   RUNNER_ADMIN
─────────────────────────────────────────────────────────────────────────────────────────────
Pipeline          CREATE     ✅             ✅                ❌                ❌
Pipeline          READ       ✅             ✅                ✅                ❌
Pipeline          UPDATE     ✅             ✅                ❌                ❌
Pipeline          DELETE     ✅             ❌                ❌                ❌
Pipeline          TRIGGER    ✅             ✅                ❌                ❌

Job               READ       ✅             ✅                ✅                ❌
Job               CANCEL     ✅             ✅                ❌                ❌

Job Logs          READ       ✅             ✅                ✅ (masked PII)   ❌
Job Logs          DOWNLOAD   ✅             ✅                ❌                ❌

Runner            REGISTER   ✅             ❌                ❌                ✅
Runner            READ       ✅             ❌                ❌                ✅
Runner            DEREGISTER ✅             ❌                ❌                ✅

User              MANAGE     ✅             ❌                ❌                ❌
API Keys          MANAGE     ✅             ❌                ❌                ❌

Audit Log         READ       ✅             ❌                ❌                ❌ (AUDIT_VIEWER)
```

All of the above are scoped to the authenticated user's tenant. Cross-tenant access is impossible regardless of role.

## Tenant Scoping — The Mandatory Second Check

Every authorization decision in Pravah has two parts:
1. Role check: `hasRole('PIPELINE_EDITOR')`
2. Tenant scope: `tenantId from JWT == tenantId of resource`

These are enforced at multiple independent layers (defense in depth):

**Layer 1 — Service method level:**
```java
@PreAuthorize("hasRole('PIPELINE_EDITOR')")
public void triggerPipeline(String pipelineId) {
    String tenantId = getCurrentTenantId();   // from JWT
    Pipeline pipeline = pipelineRepository.findByIdAndTenantId(pipelineId, tenantId)
        .orElseThrow(() -> new ResourceNotFoundException(...));
    // ...
}
```

**Layer 2 — Repository level:**
```java
public interface PipelineRepository extends JpaRepository<Pipeline, String> {
    // All repository methods include tenant_id in their queries
    Optional<Pipeline> findByIdAndTenantId(String id, String tenantId);
    List<Pipeline> findAllByTenantId(String tenantId, Pageable pageable);
    // There is no findById(String id) without tenantId — this is intentional
}
```

**Layer 3 — Database level (Row-Level Security):**

Covered in depth in 5.6, but the principle: even if layers 1 and 2 have a bug, PostgreSQL's RLS policy rejects any query from the execution-service user that attempts to read another tenant's data. The database enforces the invariant independently.

This is defense in depth: three independent enforcement points. A bug in one layer does not compromise tenant isolation.

## Admin API — Pravah Internal Operations

Pravah's internal admin API (not tenant-facing) is separate from the user-facing API. It is only accessible from within the Kubernetes cluster (no external Ingress), and services authenticate to it via mTLS (service identity, not user identity).

```java
@RestController
@RequestMapping("/internal/admin")
public class AdminController {

    // Only accessible via mTLS — enforced at the network level (Kubernetes NetworkPolicy)
    // Additional check: the calling service must have a specific SPIFFE identity
    @PreAuthorize("@serviceIdentityAuth.isAuthorizedService(authentication, 'scheduler-service')")
    @PostMapping("/tenants/{tenantId}/quota")
    public void updateTenantQuota(@PathVariable String tenantId,
                                  @RequestBody QuotaUpdate update) {
        // Admin operation — no tenant scoping needed (it's the target)
        tenantService.updateQuota(tenantId, update);
    }
}
```

No user JWT can access `/internal/admin` paths — the network policy blocks external traffic, and mTLS enforces service identity.

## Privilege Escalation Prevention

A `PIPELINE_EDITOR` must not be able to grant themselves `TENANT_ADMIN` privileges.

```java
@Service
public class UserManagementService {

    @PreAuthorize("hasRole('TENANT_ADMIN')")
    public void grantRole(String targetUserId, PravahRole roleToGrant) {
        String tenantId = getCurrentTenantId();

        // Additional check: cannot grant a role higher than your own
        // (prevents TENANT_ADMIN granting SUPER_ADMIN if that tier existed)
        PravahRole currentUserHighestRole = getCurrentUserHighestRole();
        if (roleToGrant.ordinal() > currentUserHighestRole.ordinal()) {
            throw new AuthorizationException(
                "Cannot grant a role higher than your own: " + roleToGrant
            );
        }

        // Verify target user belongs to same tenant
        User targetUser = userRepository.findByIdAndTenantId(targetUserId, tenantId)
            .orElseThrow(() -> new ResourceNotFoundException("User not found"));

        targetUser.addRole(roleToGrant);
        userRepository.save(targetUser);
        auditService.log("ROLE_GRANTED", targetUserId, roleToGrant);
    }
}
```

## System Design Interview Angles

**"What is IDOR and how does Pravah defend against it?"**

> IDOR — Insecure Direct Object Reference — occurs when an API uses a user-supplied ID to access a resource without verifying that the current user is authorized to access that specific resource. In a multi-tenant system, this means tenant A can access tenant B's data by guessing or enumerating resource IDs.
>
> The pattern: the API checks the role (is this user a PIPELINE_VIEWER?) but forgets to check ownership (does this pipeline belong to the current user's tenant?). Role check passes, data is returned, tenant isolation is broken.
>
> Pravah defends at three layers. At the service method level, all queries include `tenant_id` from the authenticated JWT: `findByIdAndTenantId(pipelineId, tenantId)` — not `findById(pipelineId)`. At the repository level, no method exists that fetches by ID without tenant ID — the missing method cannot be accidentally used. At the database level, PostgreSQL RLS policies reject queries that don't match the current session's tenant ID, even if a bug in layers 1 and 2 allows the wrong query to reach the database.
>
> Error messages are deliberately vague: "Pipeline not found" is returned whether the pipeline doesn't exist or belongs to another tenant. This prevents information leakage — an attacker cannot enumerate which resource IDs are valid for other tenants.

**"How does RBAC in Pravah relate to tenant isolation? Are they the same thing?"**

> They are separate and independent. RBAC controls what operations a role can perform in general — a PIPELINE_EDITOR can trigger pipelines, a PIPELINE_VIEWER cannot. Tenant isolation controls which resources a user can access — a user can only access resources belonging to their own tenant, regardless of role.
>
> Both checks are always required. Role check alone → an IDOR attack lets a PIPELINE_VIEWER from megacorp read othercorp's pipelines. Tenant scope alone → any tenant user could perform admin operations (modify billing, manage users) because there's no role check.
>
> The authorization logic is: the requested operation must be permitted by the user's roles AND the target resource must belong to the user's tenant. A `TENANT_ADMIN` from megacorp has full permissions for megacorp's resources and zero access (not even read) to any other tenant's resources.

## Key Takeaways

1. **Authentication ≠ authorization.** Authentication: who are you? Authorization: what are you allowed to do? Both are necessary, neither is sufficient alone.

2. **Two dimensions of authorization:** RBAC (what actions does this role permit?) + resource ownership (does this tenant own this resource?). Both must be checked on every operation.

3. **IDOR is the most common authorization failure.** Always scope database queries to the current tenant: `findByIdAndTenantId(id, tenantId)`. Never `findById(id)` alone.

4. **Defense in depth for tenant isolation:** service method (role + ownership check) + repository (tenant-scoped queries only) + database (RLS policies). Three independent enforcement points.

5. **Vague error messages prevent enumeration.** "Not found" for both "doesn't exist" and "belongs to another tenant." Never reveal whether a resource exists for a different tenant.

6. **`@PreAuthorize` at method level.** Role checks before the method executes. Custom SpEL expressions for complex authorization logic (ownership + role combined).

7. **Internal admin APIs via mTLS, not JWT.** Only accessible from within the cluster (NetworkPolicy). Services authenticate with their service identity, not user tokens.

8. **Privilege escalation prevention:** cannot grant a role higher than your own. Role management restricted to TENANT_ADMIN. All role changes audit-logged.
