# 5.4 Secret Management with HashiCorp Vault

## Why Kubernetes Secrets Are Not Enough

A common first approach: store secrets in Kubernetes Secrets objects.

```bash
kubectl create secret generic execution-db-credentials \
  --from-literal=username=execution_svc \
  --from-literal=password=SuperSecret123
```

This is better than hardcoding secrets in container images or application configuration. But Kubernetes Secrets have fundamental problems:

**They are base64-encoded, not encrypted.** `kubectl get secret execution-db-credentials -o yaml` displays the "secret" in base64, which decodes in one command. Anyone with `get secret` RBAC permission can read every secret in the namespace.

**They are static.** A compromised password remains valid forever unless rotated manually. Manual rotation is infrequent (typically quarterly at best), creating long windows of exposure.

**No access audit.** Kubernetes does not log which pod read which secret. If a secret is compromised, you cannot determine when it was accessed or by whom.

**No leakage detection.** Kubernetes has no concept of a secret being "leaked" — a secret in environment variables appears in process lists, crash dumps, log statements, and container inspection.

**Encryption at rest is Kubernetes configuration, not default.** `etcd` (where Kubernetes stores all objects) stores data unencrypted by default. Encryption-at-rest requires explicit configuration, and the encryption key must itself be stored somewhere.

HashiCorp Vault is a dedicated secret management system that addresses all of these problems.

---

## Vault's Core Value Propositions

**1. Dynamic secrets:** instead of giving a service a static database password that lives forever, Vault generates a temporary database credential (username + password) valid for 1 hour. When the lease expires, Vault revokes it from the database. Even if intercepted, the credential is useless after expiry.

**2. Centralized audit log:** every Vault operation (read, write, create, revoke) is logged with the requester's identity, timestamp, and result. You can answer "who accessed the execution-service database credentials, and when?"

**3. Fine-grained policies:** Vault policies control which secrets each identity can access. Execution Service can read only its own database credentials — not Pipeline Service's, not Vault's root token, not anything else.

**4. Encryption as a service:** Vault's Transit secrets engine provides AES-256-GCM encryption without exposing the encryption key to the calling service. Services encrypt/decrypt data through Vault's API — the key never leaves Vault.

**5. Secret leasing and revocation:** every secret issued by Vault has a lease. Leases can be revoked immediately (e.g., on security breach) or allowed to expire naturally.

## Authentication: How Services Prove Identity to Vault

Services authenticate to Vault using the **Kubernetes Auth Method**: they present their Kubernetes service account token (automatically mounted into every pod), and Vault validates it against the Kubernetes API.

```
1. Pod starts with a Kubernetes Service Account (e.g., execution-service-sa)
2. Kubernetes automatically mounts a service account token into the pod:
   /var/run/secrets/kubernetes.io/serviceaccount/token
3. Vault Agent (sidecar) reads this token
4. Vault Agent calls Vault's login endpoint:
   POST /v1/auth/kubernetes/login
   { "role": "execution-service", "jwt": "<service account token>" }
5. Vault calls the Kubernetes API to validate the token
6. If valid, Vault issues a Vault token with the policies for "execution-service" role
7. Vault Agent uses this Vault token for all subsequent secret operations
8. Vault Agent renews the Vault token automatically before expiry
```

Vault role configuration:

```hcl
# Vault configuration — Kubernetes auth role for Execution Service
resource "vault_kubernetes_auth_backend_role" "execution_service" {
  backend   = "kubernetes"
  role_name = "execution-service"

  # Only the execution-service service account in the pravah namespace
  bound_service_account_names      = ["execution-service-sa"]
  bound_service_account_namespaces = ["pravah"]

  # Token settings
  token_ttl        = 3600    # 1 hour
  token_max_ttl    = 86400   # 24 hours maximum
  token_policies   = ["execution-service-policy"]
}
```

Vault policy for Execution Service — least privilege:

```hcl
# execution-service-policy.hcl
# Allow reading the execution service's own static secrets
path "secret/data/pravah/execution-service/*" {
  capabilities = ["read"]
}

# Allow generating dynamic database credentials for execution_db
path "database/creds/execution-service-role" {
  capabilities = ["read"]
}

# Allow encryption/decryption with the execution-service transit key
# (for encrypting sensitive job metadata at rest)
path "transit/encrypt/execution-service-key" {
  capabilities = ["update"]
}
path "transit/decrypt/execution-service-key" {
  capabilities = ["update"]
}

# Explicitly deny everything else
path "*" {
  capabilities = ["deny"]
}
```

This policy is precise: Execution Service can read its own secrets, generate database credentials for its own database role, and use its encryption key. It cannot read Pipeline Service's secrets, cannot access Vault's root path, and cannot write to the KV store.

## Dynamic Database Credentials — The Core Pattern

This is the most important Vault pattern for Pravah. Instead of a static database password, Vault generates temporary credentials on demand.

### Vault Database Engine Configuration

```hcl
# Configure the database connection (Vault connects to PostgreSQL)
resource "vault_database_secret_backend_connection" "execution_db" {
  backend = "database"
  name    = "execution-db"

  postgresql {
    connection_url = "postgresql://{{username}}:{{password}}@postgres-primary.pravah:5432/pravah_execution_db"
    username       = "vault_admin"          # Vault's own DB user (can CREATE ROLE)
    password       = var.vault_db_password  # initial bootstrap only
    max_open_connections = 5
  }
}

# Role: what credentials to generate for execution-service
resource "vault_database_secret_backend_role" "execution_service" {
  backend = "database"
  name    = "execution-service-role"
  db_name = vault_database_secret_backend_connection.execution_db.name

  # SQL to create the temporary user when credentials are requested
  creation_statements = [
    "CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'",
    "GRANT INSERT, UPDATE, SELECT ON jobs, sagas, outbox, idempotency_keys TO \"{{name}}\"",
    "GRANT USAGE ON SCHEMA public TO \"{{name}}\""
  ]

  # SQL to revoke the user when the lease expires
  revocation_statements = [
    "REVOKE ALL ON ALL TABLES IN SCHEMA public FROM \"{{name}}\"",
    "DROP ROLE IF EXISTS \"{{name}}\""
  ]

  # Credential TTL
  default_ttl = "1h"    # expires after 1 hour
  max_ttl     = "24h"   # maximum renewal duration
}
```

When Execution Service requests credentials:

```
Vault generates:
  username: v-execution-svc-abc123-1705318400   (unique, includes timestamp)
  password: A3f9Kx2vPm7nL8qZ5rT0yU4wH6jD1e      (random, 32 chars)
  valid_until: 2024-01-15 11:00:00 UTC           (1 hour from now)

Vault executes on PostgreSQL:
  CREATE ROLE "v-execution-svc-abc123-1705318400"
    WITH LOGIN PASSWORD 'A3f9...' VALID UNTIL '2024-01-15 11:00:00';
  GRANT INSERT, UPDATE, SELECT ON jobs, sagas, outbox, idempotency_keys
    TO "v-execution-svc-abc123-1705318400";

Vault returns credentials to requesting service.

After 1 hour, Vault lease expires. Vault executes:
  DROP ROLE "v-execution-svc-abc123-1705318400";
  (PostgreSQL also enforces VALID UNTIL expiry independently)
```

**The security benefit:** even if these credentials are extracted from a running pod (memory dump, log leak, environment inspection), they expire in at most 1 hour. The attacker has a 1-hour window, not infinite access with a static password.

## KV v2 — Static Secrets with Versioning

Not all secrets can be dynamic. External API keys (GitHub, Slack, SendGrid), signing keys, and other externally-managed credentials are stored in Vault's KV (Key-Value) v2 engine.

KV v2 adds versioning: every update to a secret creates a new version. Previous versions are retained for a configurable period, enabling rollback.

```bash
# Writing a secret to KV v2
vault kv put secret/pravah/execution-service/github \
  api_token="ghp_abc123def456..." \
  webhook_secret="wh_secret_xyz..."

# Reading
vault kv get secret/pravah/execution-service/github
# Version 1

# Rotating the token
vault kv put secret/pravah/execution-service/github \
  api_token="ghp_new_token_789..." \
  webhook_secret="wh_secret_xyz..."   # unchanged
# Version 2 — version 1 retained for 10 versions (configurable)
```

**Version history is critical for incident response:** if a secret was compromised, you can check when it was last rotated (version history) and determine the exposure window.

## Vault Agent Sidecar — Transparent Secret Injection

Vault Agent is a sidecar container that runs alongside the application, handles all Vault interaction, and writes secrets to a shared volume (tmpfs — in-memory, never written to disk).

```yaml
# Pod spec — application + Vault Agent sidecar
spec:
  serviceAccountName: execution-service-sa

  initContainers:
    # Init container: fetch secrets before the main container starts
    - name: vault-agent-init
      image: hashicorp/vault:1.15
      args:
        - agent
        - -config=/vault/config/agent-config.hcl
        - -exit-after-auth
      volumeMounts:
        - name: vault-config
          mountPath: /vault/config
        - name: vault-secrets
          mountPath: /vault/secrets

  containers:
    - name: execution-service
      image: pravah/execution-service:1.4.2
      volumeMounts:
        - name: vault-secrets
          mountPath: /vault/secrets
          readOnly: true
      env:
        # Point Spring to the Vault-written properties file
        - name: SPRING_CONFIG_ADDITIONAL_LOCATION
          value: "file:/vault/secrets/"

    # Sidecar: keep secrets renewed during pod lifetime
    - name: vault-agent
      image: hashicorp/vault:1.15
      args: ["agent", "-config=/vault/config/agent-config.hcl"]
      volumeMounts:
        - name: vault-config
          mountPath: /vault/config
        - name: vault-secrets
          mountPath: /vault/secrets

  volumes:
    - name: vault-secrets
      emptyDir:
        medium: Memory    # tmpfs — in-memory, not persisted to disk
    - name: vault-config
      configMap:
        name: vault-agent-config
```

Vault Agent configuration:

```hcl
# vault-agent-config.hcl
vault {
  address = "https://vault.pravah.svc:8200"
  # TLS verification using Pravah's CA
  ca_path = "/etc/pravah/tls/ca.crt"
}

auto_auth {
  method "kubernetes" {
    config = {
      role = "execution-service"
    }
  }

  sink "file" {
    config = {
      path = "/vault/secrets/.vault-token"
    }
  }
}

template {
  source      = "/vault/config/db-credentials.ctmpl"
  destination = "/vault/secrets/application-secrets.properties"
  # Renew the secret when 70% of the lease has elapsed
  left_pad_decimal_digits = 0
}
```

Template file (`db-credentials.ctmpl`) — Consul Template syntax:

```
{{- with secret "database/creds/execution-service-role" -}}
spring.datasource.username={{ .Data.username }}
spring.datasource.password={{ .Data.password }}
{{- end }}

{{- with secret "secret/data/pravah/execution-service/github" -}}
github.api.token={{ .Data.data.api_token }}
github.webhook.secret={{ .Data.data.webhook_secret }}
{{- end }}
```

Vault Agent renders this template to `/vault/secrets/application-secrets.properties`. Spring Boot loads this as an additional properties file. The application never calls Vault directly — it just reads files. When Vault Agent renews the database credentials (at 70% of the 1-hour lease), it re-renders the template, and Spring Boot (with `@RefreshScope` or DataSource reconnect logic) picks up the new values.

## Transit Engine — Encryption as a Service

Pravah needs to encrypt sensitive data at rest — particularly tenant-provided secrets (database passwords, API keys tenants provide so Pravah can access their data sources). These are stored encrypted in PostgreSQL. The encryption keys never leave Vault.

```java
@Service
public class VaultEncryptionService {

    private final VaultTemplate vaultTemplate;

    public String encrypt(String tenantId, String plaintext) {
        String keyName = "tenant-" + tenantId;   // per-tenant encryption key

        VaultTransitContext context = VaultTransitContext.builder()
            .context(Base64.getEncoder().encodeToString(tenantId.getBytes()))
            .build();

        // Vault encrypts the data — the key never leaves Vault
        // Returns: vault:v1:AES256GCM...base64ciphertext...
        return vaultTemplate.transit()
            .encrypt(keyName, Plaintext.of(plaintext.getBytes()), context)
            .getCiphertext();
    }

    public String decrypt(String tenantId, String ciphertext) {
        String keyName = "tenant-" + tenantId;

        VaultTransitContext context = VaultTransitContext.builder()
            .context(Base64.getEncoder().encodeToString(tenantId.getBytes()))
            .build();

        return new String(
            vaultTemplate.transit()
                .decrypt(keyName, Ciphertext.of(ciphertext), context)
                .asBytes()
        );
    }
}
```

The tenant-specific encryption context (`Base64(tenantId)`) ensures that ciphertext encrypted for `megacorp` cannot be decrypted with `othercorp`'s key context — even if both use the same underlying Vault key. This is convergent encryption with context binding.

**Key rotation:** Vault's Transit engine supports key rotation without re-encrypting all data. The new key version is used for new encryptions. Old ciphertext (marked with version `v1`) is decrypted with the old key. When convenient, Vault can rewrap all ciphertext to the current key version.

## Vault High Availability

Vault uses integrated Raft storage for HA — no external Consul or ZooKeeper dependency.

```
Vault Raft Cluster (3 or 5 nodes):
  vault-0: Active (all reads + writes)
  vault-1: Standby (forward requests to active)
  vault-2: Standby (forward requests to active)

On vault-0 failure:
  Raft elects new leader (vault-1 or vault-2)
  Clients see a brief (~5–10 second) unavailability during election
  Vault Agent reconnects automatically to new leader
```

Pravah runs Vault on 3 nodes (quorum = 2). For production: 5 nodes (quorum = 3) for stronger fault tolerance.

**Vault seal/unseal:** Vault's data is encrypted with a master key. When Vault starts, it is "sealed" — it cannot decrypt its own data. The master key must be provided to "unseal" it. Pravah uses **auto-unseal** via cloud KMS (AWS KMS or GCP Cloud KMS): the master key is stored in the cloud KMS, and Vault automatically unseals on startup using the KMS. If the KMS key is deleted or access is revoked, Vault cannot unseal — this is a security feature (emergency seal).

## FAANG Interview Angles

**"Why does Pravah use dynamic database credentials instead of static passwords?"**

> Static database passwords are a liability that accumulates over time. Rotation is manual, infrequent, and error-prone. If the password is ever leaked — from logs, crash dumps, a compromised deployment pipeline — it remains valid indefinitely unless manually rotated.
>
> Vault's dynamic credentials change everything. When Execution Service starts, Vault generates a unique username and password for it, valid for 1 hour. Vault simultaneously creates this user in PostgreSQL with exactly the permissions it needs. When the lease expires, Vault drops the user from PostgreSQL. The window of exposure for any credential is at most 1 hour.
>
> There is no shared static password to compromise. Each pod instance gets its own unique credential. Even if an attacker extracts credentials from a running pod's memory, they expire within the hour. Audit logs show exactly which pod instance used which credential and when.

**"How does a Kubernetes pod authenticate to Vault without storing any credentials?"**

> Kubernetes automatically mounts a service account token into every pod — a JWT signed by the Kubernetes API server that identifies the pod's service account. Vault's Kubernetes auth method validates this token: it calls the Kubernetes TokenReview API to verify the token is genuine and bound to the claimed service account.
>
> If valid, Vault returns a Vault token with the policies attached to that service account's Vault role. The Vault Agent sidecar handles this automatically — the application never makes any Vault API calls itself. The application just reads files from a tmpfs volume that the Vault Agent keeps populated with current secret values.
>
> The security property: no Vault credentials (no username, no password, no token) are stored anywhere in the pod's environment, configuration, or image. The only credential is the Kubernetes service account token, which is ephemeral and only valid for that pod's lifetime.

**"How does Vault's Transit engine protect tenant secrets better than database-level encryption?"**

> Database-level encryption (Transparent Data Encryption) encrypts data files on disk. But the decryption happens transparently — any query that the database user can run sees the data in plaintext. If a service has SELECT permission on the secrets table, it reads plaintext secrets. Database-level encryption protects against disk theft, not application-level compromise.
>
> Vault's Transit engine keeps the encryption key inside Vault. A service that wants to decrypt a tenant's stored secret must make an explicit API call to Vault with its authenticated identity. Vault's policy for that service may allow decryption only for its own tenant's key. Even if an attacker gains direct database access and reads the ciphertext, they cannot decrypt it without a valid Vault identity with the right policy.
>
> Additionally, Vault logs every decrypt operation with the requester's identity and timestamp. If a service is compromised and starts bulk-decrypting tenant secrets, the anomaly appears in Vault's audit log immediately.

## Key Takeaways

1. **Kubernetes Secrets are base64, not encrypted.** Anyone with `get secret` RBAC permission can read them. No audit log. Static forever. Vault solves all three problems.

2. **Dynamic database credentials are the key pattern.** Vault generates a temporary username+password valid for 1 hour, creates the PostgreSQL user, and drops it when the lease expires. Window of exposure: 1 hour, not forever.

3. **Kubernetes auth method eliminates bootstrap credentials.** Pods authenticate to Vault using their Kubernetes service account token. No secrets stored in environment variables or configuration files.

4. **Least-privilege Vault policies:** each service can read only its own secrets, generate its own database credentials, and use its own encryption key. Explicitly deny everything else.

5. **Vault Agent sidecar pattern:** agent handles all Vault interaction, writes secrets to tmpfs (in-memory, never on disk), renews leases automatically. Application reads files — no Vault SDK in application code.

6. **Transit engine = encryption as a service.** Encryption key never leaves Vault. Services encrypt/decrypt via API. Per-tenant keys with context binding prevent cross-tenant decryption.

7. **KV v2 with versioning** for static secrets. Previous versions retained — critical for incident response (when was this secret last rotated?).

8. **Auto-unseal via cloud KMS.** Vault unseals automatically using a cloud-managed master key. Emergency seal by revoking KMS access — stronger than manual seal procedures.
