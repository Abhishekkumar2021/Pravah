# 5.6 Multi-Tenancy & Data Isolation

## The Multi-Tenancy Spectrum

Multi-tenancy means multiple customers share the same platform infrastructure. How they share it determines the isolation guarantee.

```
Silo Model (one-per-tenant)                   Pool Model (shared)
───────────────────────────────────────────────────────────────────
Database per tenant                           Shared database, rows tagged with tenant_id
Cluster per tenant                            Shared cluster, namespaces or labels
Complete isolation                            Logical isolation via application/DB rules
Highest cost                                  Lowest cost
No cross-tenant risk                          Cross-tenant risk if isolation is misconfigured
Used by: large enterprise, regulated tenants  Used by: SaaS products at scale
```

**Pure silo:** Salesforce sells "Government Cloud" with a completely separate instance per large customer. Highest isolation, highest operational cost — each customer is effectively a separate deployment.

**Pure pool:** a typical B2C SaaS — all customers share the same database tables. The `user_id` column is the only isolation. Any bug that forgets to filter by `user_id` exposes all users' data.

**Pravah's approach:** pool model by default, silo model as an enterprise upgrade.

For most tenants, Pravah uses a single PostgreSQL cluster with all tenants' data separated by `tenant_id`. For enterprise tenants with strict compliance requirements (HIPAA, FedRAMP, financial regulations), Pravah provisions a dedicated PostgreSQL instance in an isolated Kubernetes namespace. The application layer is the same; the infrastructure is separate.

This chapter focuses on the pool model — where isolation is logical rather than physical.

## PostgreSQL Row-Level Security (RLS)

RLS is PostgreSQL's mechanism for enforcing data access policies at the database level. Even if application code has an authorization bug and executes a query without a `WHERE tenant_id = ?` clause, PostgreSQL's RLS policy rejects or filters the result automatically.

RLS is the last line of defense in Pravah's multi-layer tenant isolation.

### Enabling RLS on a Table

```sql
-- Enable RLS on the jobs table
ALTER TABLE jobs ENABLE ROW LEVEL SECURITY;

-- Force RLS even for table owners (prevents owner-level bypass)
ALTER TABLE jobs FORCE ROW LEVEL SECURITY;
```

### Creating Policies

```sql
-- Policy: service users can only read/write their own tenant's rows
CREATE POLICY tenant_isolation_policy ON jobs
  USING (tenant_id = current_setting('pravah.current_tenant_id'));

-- The USING clause is checked on SELECT, UPDATE, DELETE
-- (which rows can this user see/modify?)

-- For INSERT, add a WITH CHECK clause
CREATE POLICY tenant_insert_policy ON jobs
  AS PERMISSIVE
  FOR INSERT
  WITH CHECK (tenant_id = current_setting('pravah.current_tenant_id'));
```

The `current_setting('pravah.current_tenant_id')` function reads a session-level setting. Before every database query, the application (via PgBouncer transaction mode) sets this value to the current request's tenant ID:

```java
@Aspect
@Component
public class TenantContextAspect {

    @Around("@annotation(TenantScoped)")
    public Object setTenantContext(ProceedingJoinPoint pjp) throws Throwable {
        String tenantId = getCurrentTenantId();

        try (Connection conn = dataSource.getConnection()) {
            // Set the tenant context for this database transaction
            conn.createStatement().execute(
                "SET LOCAL pravah.current_tenant_id = '" + escapeIdentifier(tenantId) + "'"
            );
            // SET LOCAL is scoped to the current transaction — cleared on commit/rollback
            return pjp.proceed();
        }
    }
}
```

**Alternative — via JDBC connection decorator:**

```java
@Bean
public DataSource tenantAwareDataSource(DataSource baseDataSource) {
    return new TenantAwareDataSource(baseDataSource) {
        @Override
        public Connection getConnection() throws SQLException {
            Connection conn = super.getConnection();
            String tenantId = TenantContext.getCurrentTenantId();
            if (tenantId != null) {
                try (Statement stmt = conn.createStatement()) {
                    stmt.execute("SET LOCAL pravah.current_tenant_id = '" +
                        escapeIdentifier(tenantId) + "'");
                }
            }
            return conn;
        }
    };
}
```

**Superuser bypass:** RLS policies do not apply to PostgreSQL superusers or table owners (unless `FORCE ROW LEVEL SECURITY` is set). This is why Pravah's application database users are never superusers, and `FORCE ROW LEVEL SECURITY` is explicitly enabled.

### RLS for All Tenant-Scoped Tables

```sql
-- Apply the same pattern to every tenant-scoped table

ALTER TABLE jobs ENABLE ROW LEVEL SECURITY;
ALTER TABLE jobs FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON jobs
  USING (tenant_id = current_setting('pravah.current_tenant_id', true));

ALTER TABLE pipelines ENABLE ROW LEVEL SECURITY;
ALTER TABLE pipelines FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON pipelines
  USING (tenant_id = current_setting('pravah.current_tenant_id', true));

ALTER TABLE runners ENABLE ROW LEVEL SECURITY;
ALTER TABLE runners FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON runners
  USING (tenant_id = current_setting('pravah.current_tenant_id', true));

ALTER TABLE job_runs ENABLE ROW LEVEL SECURITY;
ALTER TABLE job_runs FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON job_runs
  USING (tenant_id = current_setting('pravah.current_tenant_id', true));

-- Outbox: no RLS (application-level service, not tenant-scoped per row)
-- Audit logs: special policy — insert only, no SELECT for service users
ALTER TABLE audit_log ENABLE ROW LEVEL SECURITY;
ALTER TABLE audit_log FORCE ROW LEVEL SECURITY;
CREATE POLICY insert_only ON audit_log
  FOR INSERT WITH CHECK (true);  -- allow all inserts
-- No USING clause = no SELECT, UPDATE, DELETE by service users
-- Audit log is only read by the audit service (separate user with explicit SELECT policy)
```

### Testing RLS — Verify It Actually Works

```sql
-- Test: as the execution_svc user with tenant_id = 'megacorp'
SET pravah.current_tenant_id = 'megacorp';

-- Should return only megacorp's jobs
SELECT id, tenant_id FROM jobs LIMIT 5;
-- id: job-001, tenant_id: megacorp ✅
-- id: job-002, tenant_id: megacorp ✅

-- Test: try to access another tenant's job (should be filtered out by RLS)
SELECT id, tenant_id FROM jobs WHERE id = 'othercorp-job-999';
-- 0 rows — correct, RLS filtered it

-- Verify: what does the query planner show?
EXPLAIN SELECT * FROM jobs WHERE id = 'job-001';
-- Should show: Filter: (tenant_id = current_setting('pravah.current_tenant_id'::text))
-- RLS predicate is pushed into the query plan
```

## Tenant Isolation in Kafka

Kafka is a shared infrastructure. All tenants' job events flow through the same topics. Isolation is achieved through structural design, not Kafka ACLs (which operate at topic level, not message level).

### Topic Structure

Pravah does NOT use per-tenant Kafka topics. Creating thousands of topics (one per tenant) causes problems:
- Kafka controller overhead scales with number of partitions/topics
- Consumer rebalancing becomes slow with thousands of topics
- Partition assignment and monitoring becomes complex

Instead, Pravah uses shared topics with `tenant_id` as the message key and in the message payload:

```java
// All job events flow through shared topics
// tenant_id is in both the key (for routing) and the payload (for filtering)
ProducerRecord<String, byte[]> record = new ProducerRecord<>(
    "job.events",                           // shared topic
    job.getTenantId() + ":" + job.getId(), // key: routes to consistent partition per tenant
    serialize(JobEvent.builder()
        .tenantId(job.getTenantId())        // payload field — consumers always filter
        .jobId(job.getId())
        .build())
);
```

**Consumer-side tenant isolation:**

Every consumer that processes job events must filter by tenant ID. This is enforced by Pravah's Kafka consumer base class:

```java
@Component
public abstract class TenantScopedKafkaConsumer {

    @KafkaListener(topics = "#{@kafkaTopicConfig.jobEvents}")
    public final void onMessage(ConsumerRecord<String, byte[]> record) {
        JobEvent event = deserialize(record.value());
        String tenantId = event.getTenantId();

        if (tenantId == null || tenantId.isBlank()) {
            log.error("Received event without tenant_id — routing to DLQ");
            dlqService.sendToDlq(record, "missing_tenant_id");
            return;
        }

        // Set tenant context for all downstream processing
        TenantContext.set(tenantId);
        try {
            processEvent(event);
        } finally {
            TenantContext.clear();
        }
    }

    // Subclasses implement this — they are guaranteed to have tenant context set
    protected abstract void processEvent(JobEvent event);
}
```

The abstract base class ensures tenant context is always set before processing, and always cleared after. Subclasses cannot accidentally process an event without tenant context.

### Kafka ACLs for Operational Isolation

While message-level isolation is by `tenant_id`, Kafka ACLs add a coarser layer: only Pravah's internal services can publish to `job.events`. External services (tenant webhooks, integration partners) have ACLs allowing them to produce only to specific, limited topics:

```
Principal: pravah-execution-service
  ALLOW: PRODUCE on topic: job.events
  ALLOW: CONSUME on topic: job.events (consumer group: execution-service)
  ALLOW: PRODUCE on topic: job.assigned

Principal: external-webhook-receiver
  ALLOW: PRODUCE on topic: webhook.events
  DENY: All other operations
```

External principals cannot publish to `job.events` directly — preventing injection of fake job events.

## Encryption at Rest — Per-Tenant Keys

For the most sensitive data (tenant-provided secrets, job results containing PII), Pravah uses per-tenant encryption with Vault's Transit engine. Even if an attacker gains direct database access (bypassing all application and RLS controls), each tenant's data requires a separate Vault key to decrypt.

### What Gets Encrypted

```
Encrypted (per-tenant Vault key):
  pipeline_credentials (API keys, database passwords tenants provide)
  job_results containing PII (configurable per tenant)
  runner registration secrets

Not encrypted (shared, low-sensitivity):
  pipeline metadata (names, schedules, DAG structure)
  job status (PENDING, RUNNING, COMPLETE)
  runner health metrics
  audit log entries (are themselves sensitive — secured via RLS + access control)
```

### Per-Tenant Key Management

```hcl
# Vault Transit policy — each tenant gets their own named key
# Key name: transit/keys/tenant-{tenant_id}

# Service policy allows encryption/decryption only for the requesting tenant
path "transit/encrypt/tenant-{{identity.entity.aliases.auth_kubernetes_default.metadata.tenant_id}}" {
  capabilities = ["update"]
}
path "transit/decrypt/tenant-{{identity.entity.aliases.auth_kubernetes_default.metadata.tenant_id}}" {
  capabilities = ["update"]
}
```

In application code:

```java
@Service
public class TenantSecretService {

    public void storePipelineCredential(String tenantId, String secretName, String secretValue) {
        // Encrypt with this tenant's key
        String encrypted = vaultEncryption.encrypt("tenant-" + tenantId, secretValue);

        PipelineCredential credential = PipelineCredential.builder()
            .tenantId(tenantId)
            .secretName(secretName)
            .encryptedValue(encrypted)   // stored as: vault:v1:BASE64_CIPHERTEXT
            .build();

        credentialRepository.save(credential);
    }

    public String getPipelineCredential(String tenantId, String secretName) {
        PipelineCredential credential = credentialRepository
            .findByTenantIdAndSecretName(tenantId, secretName)
            .orElseThrow(...);

        // Decrypt using this tenant's key
        // Only possible with the correct Vault policy + tenant key
        return vaultEncryption.decrypt("tenant-" + tenantId, credential.getEncryptedValue());
    }
}
```

**The isolation guarantee:** megacorp's secrets are encrypted with `transit/keys/tenant-megacorp`. othercorp's secrets are encrypted with `transit/keys/tenant-othercorp`. Even with direct database access to both rows, decrypting megacorp's ciphertext with othercorp's key produces garbage — or Vault rejects the request because the wrong key was specified.

## Tenant Context Propagation

When a request arrives at the API Gateway, the tenant ID is extracted from the JWT and propagated through the entire call chain:

```
API Gateway: extract tenant_id from JWT → set in request header
  ↓ HTTP (header: X-Tenant-ID: megacorp)
Service A: read tenant_id from header → set in ThreadLocal
  ↓ Database: SET LOCAL pravah.current_tenant_id = 'megacorp' (RLS enforcement)
  ↓ gRPC (metadata: tenant-id: megacorp)
Service B: read tenant_id from gRPC metadata → set in ThreadLocal
  ↓ Kafka message (payload field: tenant_id: megacorp)
Consumer: read tenant_id from message → set in TenantContext
  ↓ Database: SET LOCAL pravah.current_tenant_id = 'megacorp'
```

The tenant context is never derived from the request body or path parameters. It always comes from the authenticated JWT claim. A malicious request with `{"tenant_id": "othercorp"}` in the body is ignored — the application uses the JWT's `tenant_id`.

```java
// ❌ Wrong: tenant from request body
public void triggerPipeline(@RequestBody TriggerRequest request) {
    String tenantId = request.getTenantId();  // user can put anything here
    // ...
}

// ✅ Correct: tenant from authenticated JWT
public void triggerPipeline(@RequestBody TriggerRequest request) {
    String tenantId = SecurityContextHolder.getContext()
        .getAuthentication()
        .getPrincipal()
        .getTenantId();  // from JWT — cannot be forged
    // ...
}
```

## Enterprise Silo Model

For tenants with strict compliance requirements, Pravah offers a dedicated instance:

```
Shared infrastructure (default):
  All tenants → shared PostgreSQL cluster → tenant_id RLS
  All tenants → shared Kafka cluster → tenant_id filtering
  All tenants → shared Kubernetes namespace → pod isolation via RBAC

Enterprise silo:
  Large tenant → dedicated PostgreSQL cluster in isolated namespace
  Large tenant → dedicated Kafka topics (or dedicated Kafka cluster)
  Large tenant → dedicated Kubernetes namespace with NetworkPolicy
  Large tenant → dedicated Vault namespace with isolated policies
```

The application code is identical — services are configuration-driven. The Enterprise tier configuration points them at a dedicated PostgreSQL endpoint and dedicated Kafka topics. The tenant ID filtering still runs (defense in depth), but the underlying infrastructure is physically separate.

## System Design Interview Angles

**"How does Pravah prevent one tenant's data from being accessed by another at the database level?"**

> Two independent mechanisms. First, all database queries from application code include `tenant_id` in the WHERE clause — there is no `findById()` without tenant scoping. Second, PostgreSQL Row-Level Security adds an independent enforcement layer. When Execution Service connects, it sets `pravah.current_tenant_id` to the current request's tenant ID at the start of each transaction (`SET LOCAL`). Every row read or written is filtered by this setting automatically by the RLS policy.
>
> Even if the application layer has a bug and executes a query without a `WHERE tenant_id = ?` clause, PostgreSQL's RLS policy applies the filter automatically. The query returns only the rows matching the current session's tenant ID. This is defense in depth: the application layer and database layer enforce isolation independently.
>
> `FORCE ROW LEVEL SECURITY` is enabled on all tenant-scoped tables. This ensures the policy applies even to the table owner's queries — preventing accidental bypass during maintenance operations by a developer with elevated DB access.

**"What is the tradeoff between silo and pool multi-tenancy models? Which does Pravah use and why?"**

> The silo model gives each tenant completely separate infrastructure — separate databases, separate clusters. Zero cross-tenant risk, but operationally expensive: provisioning a new tenant means provisioning a new database, new cluster, new certificates, new monitoring. O(n) operational cost with n tenants.
>
> The pool model shares infrastructure with logical isolation (tenant_id filters, RLS). Operationally efficient — onboarding a new tenant is a database row. The risk: any isolation bug could expose one tenant's data to another. The pool model requires rigorous defense in depth (application layer + RLS + encryption + audit logs).
>
> Pravah uses pool by default for cost efficiency at scale, and silo as an enterprise upgrade for compliance-heavy customers (HIPAA, FedRAMP, financial regulation). The application code is identical in both cases — infrastructure configuration differs. The default pool model is hardened with PostgreSQL RLS and per-tenant encryption keys, so the isolation guarantee is strong even without physical separation.

**"How does tenant context propagate through Kafka messages in Pravah?"**

> Kafka consumers cannot rely on connection-level session settings like database connections can. Each message is processed independently, potentially by different consumer threads.
>
> Pravah embeds `tenant_id` directly in every Kafka message payload (not just as a key). The consumer base class extracts the tenant ID from the message payload, calls `TenantContext.set(tenantId)` on the current thread, and clears it in a `finally` block after processing. All downstream operations (database queries, cache lookups, nested Kafka publishes) read the tenant context from `TenantContext.get()`.
>
> The database queries that run during message processing set `SET LOCAL pravah.current_tenant_id` at the transaction boundary, activating RLS enforcement. The tenant context flows consistently from the message payload through the entire processing chain to the database.

## Key Takeaways

1. **Silo vs pool:** silo = one infrastructure per tenant (maximum isolation, maximum cost). Pool = shared infrastructure with logical isolation (efficient, requires rigorous controls). Pravah uses pool by default, silo as enterprise upgrade.

2. **PostgreSQL RLS is the database-level enforcement boundary.** `current_setting('pravah.current_tenant_id')` set at transaction start. Policy applied by PostgreSQL on every read/write. `FORCE ROW LEVEL SECURITY` prevents owner bypass.

3. **RLS is the last line of defense.** It catches application bugs where tenant scoping is accidentally omitted. Three independent layers: service method (JWT tenantId + query scoping) + repository (tenant-scoped query methods) + PostgreSQL RLS.

4. **Kafka isolation:** shared topics with tenant_id in payload. Consumer base class always sets tenant context before processing. Kafka ACLs prevent external principals from publishing to internal topics.

5. **Per-tenant encryption keys in Vault Transit.** Even with direct database access, ciphertext from megacorp cannot be decrypted with othercorp's key. Adds isolation below the application and database layers.

6. **Tenant context comes from JWT, never from request body.** A request with `{"tenant_id": "othercorp"}` in the body is ignored — application always uses JWT claim.

7. **`SET LOCAL` for per-transaction RLS context.** The tenant ID setting is transaction-scoped — cleared on commit/rollback. Prevents context leakage between requests in a PgBouncer connection pool.

8. **Testing RLS is mandatory.** Write explicit tests that verify queries without `WHERE tenant_id =` return empty results when RLS is active, and queries with the wrong tenant context return empty results.
