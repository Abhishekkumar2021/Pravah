# 5.3 mTLS for Service-to-Service Communication

## The Problem with Internal Network Trust

Traditional architecture: services behind a firewall trust each other implicitly. If you are inside the perimeter, you are trusted. This worked when "inside the perimeter" meant a physically secured data center with known, controlled machines.

In Kubernetes, "inside the cluster" means very little from a security perspective:
- A compromised pod is inside the cluster
- A misconfigured admission controller may allow unauthorized container images inside the cluster
- A container escape vulnerability puts an attacker inside the cluster
- A cloud provider misconfiguration may expose the cluster network

The Zero Trust principle (from 5.1): **being inside the network grants no implicit trust.** Every service-to-service call must be authenticated. mTLS (mutual TLS) is how Pravah implements this.

---

## How mTLS Works

Standard TLS is one-sided authentication: the server presents a certificate, the client validates it. This ensures the client is talking to the real server — but the server has no cryptographic proof of who the client is.

Mutual TLS requires both sides to present and validate certificates:

```
Standard TLS (one-way):
  Client: "Who are you?"
  Server: "I am pipeline-service.pravah.svc, here is my certificate"
  Client: Verifies certificate against trusted CA → "OK, you are who you say"
  Client sends request (server has no idea who the client is)

mTLS (mutual):
  Client: "Who are you?"
  Server: "I am pipeline-service.pravah.svc, here is my certificate"
  Client: Verifies server certificate → "OK"
  Server: "Who are you?"
  Client: "I am execution-service.pravah.svc, here is my certificate"
  Server: Verifies client certificate → "OK, execution-service is authorized to call me"
  Both: Encrypt the connection with the negotiated session key
```

The certificate is the identity. Execution Service's certificate has a Subject Alternative Name (SAN) of `execution-service.pravah.svc`. Pipeline Service's authorization layer can check: "the caller presented a certificate with this SAN — is this service allowed to call this API?"

## Certificate Anatomy for Service Identity

Every Pravah service gets a certificate with the following attributes:

```
Subject: CN=execution-service
Subject Alternative Names (SANs):
  DNS: execution-service.pravah.svc.cluster.local
  DNS: execution-service.pravah.svc
  URI: spiffe://cluster.local/ns/pravah/sa/execution-service

Issuer: Pravah Internal CA (intermediate CA signed by root CA)
Valid For: 90 days (auto-rotated at 80% lifetime by cert-manager)
Key Usage: Digital Signature, Key Encipherment
Extended Key Usage: Server Authentication, Client Authentication
```

The SPIFFE URI (`spiffe://cluster.local/ns/pravah/sa/execution-service`) is the SPIFFE (Secure Production Identity Framework For Everyone) identity format — designed specifically for workload identity in Kubernetes. It encodes the cluster, namespace, and Kubernetes service account into a cryptographically verifiable identity.

## cert-manager — Automated Certificate Lifecycle

Manually managing certificates across dozens of services is operationally infeasible and error-prone. cert-manager is a Kubernetes controller that automates certificate issuance and renewal.

### CA Hierarchy

```
Root CA (offline, stored in Vault / HSM)
  │ signs
  ▼
Intermediate CA (online, managed by cert-manager)
  │ signs
  ▼
Service Certificates (per-pod, 90 days, auto-rotated)
```

The root CA never signs service certificates directly. Using an intermediate CA means the root CA can be kept fully offline — even if the intermediate CA is compromised, the root CA can revoke it and issue a new intermediate. The root CA's private key never touches an online system.

### cert-manager Configuration

```yaml
# ClusterIssuer — uses the intermediate CA stored as a Kubernetes Secret
# (synced from Vault by the Vault Agent)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: pravah-internal-ca
spec:
  ca:
    secretName: pravah-intermediate-ca-tls   # contains ca.crt and tls.key
```

```yaml
# Certificate for Execution Service
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: execution-service-tls
  namespace: pravah
spec:
  secretName: execution-service-tls-secret
  duration: 2160h      # 90 days
  renewBefore: 432h    # renew when 18 days remain (80% of lifetime)
  isCA: false
  usages:
    - server auth
    - client auth
  subject:
    organizations: ["Pravah"]
  commonName: execution-service
  dnsNames:
    - execution-service
    - execution-service.pravah
    - execution-service.pravah.svc
    - execution-service.pravah.svc.cluster.local
  uris:
    - spiffe://cluster.local/ns/pravah/sa/execution-service
  issuerRef:
    name: pravah-internal-ca
    kind: ClusterIssuer
```

cert-manager creates the Kubernetes Secret `execution-service-tls-secret` containing:
- `tls.crt` — the service certificate (and intermediate CA chain)
- `tls.key` — the service private key
- `ca.crt` — the CA bundle (for peer verification)

This secret is mounted into the service pod as a volume. The service reads the certificate and key at startup, and cert-manager handles renewal — including sending a SIGTERM to trigger a certificate reload when it rotates the secret.

### Pod Configuration

```yaml
# Deployment — mount TLS certificate as volume
spec:
  containers:
    - name: execution-service
      volumeMounts:
        - name: tls-certs
          mountPath: /etc/pravah/tls
          readOnly: true
  volumes:
    - name: tls-certs
      secret:
        secretName: execution-service-tls-secret
        items:
          - key: tls.crt
            path: tls.crt
          - key: tls.key
            path: tls.key
          - key: ca.crt
            path: ca.crt
```

## mTLS in Pravah's gRPC Connections

The most critical mTLS path in Pravah is the runner ↔ cloud gRPC connection. Runners are self-hosted in customer infrastructure. The mTLS certificate is how Pravah verifies the identity of a connecting runner and prevents impersonation.

### Runner Certificate Provisioning

When a tenant registers a new runner, Pravah provisions a unique certificate for it:

```
Tenant: "I want to register a new runner named 'build-runner-eu-01'"
Pravah: 
  1. Create a Certificate in Kubernetes for this runner
  2. Certificate SAN includes: runner ID and tenant ID
     URI: spiffe://cluster.local/runners/megacorp/runner-abc123
  3. Package certificate + key into a secure bundle
  4. Tenant downloads the bundle to install on their runner machine
  5. Runner uses this certificate for all gRPC connections
```

The runner's certificate encodes its identity. When it connects to the gRPC gateway, the gateway can extract:
- Which tenant this runner belongs to (`megacorp`)
- Which specific runner ID (`runner-abc123`)
- That the certificate was issued by Pravah's CA (not self-signed)

No API key or additional authentication is needed — the certificate IS the identity.

### gRPC Server with mTLS — Java Configuration

```java
@Configuration
public class GrpcServerConfig {

    @Value("${pravah.tls.cert-path:/etc/pravah/tls/tls.crt}")
    private String certPath;

    @Value("${pravah.tls.key-path:/etc/pravah/tls/tls.key}")
    private String keyPath;

    @Value("${pravah.tls.ca-path:/etc/pravah/tls/ca.crt}")
    private String caPath;

    @Bean
    public Server grpcServer(RunnerGrpcService runnerService) throws Exception {
        SslContext sslContext = SslContextBuilder
            .forServer(new File(certPath), new File(keyPath))
            // Require client certificates — this is the "mutual" in mTLS
            .clientAuth(ClientAuth.REQUIRE)
            // Trust only certificates signed by Pravah's CA
            .trustManager(new File(caPath))
            .sslProvider(SslProvider.OPENSSL)
            .protocols("TLSv1.3")
            .build();

        return NettyServerBuilder
            .forPort(9090)
            .sslContext(sslContext)
            .addService(runnerService)
            // Interceptor: extract runner identity from the client certificate
            .intercept(new RunnerIdentityInterceptor())
            .keepAliveTime(30, TimeUnit.SECONDS)
            .keepAliveTimeout(10, TimeUnit.SECONDS)
            .build();
    }
}
```

### RunnerIdentityInterceptor — Extracting Identity from Certificate

```java
@Component
public class RunnerIdentityInterceptor implements ServerInterceptor {

    public static final Context.Key<RunnerIdentity> RUNNER_IDENTITY =
        Context.key("runner-identity");

    @Override
    public <Req, Resp> ServerCall.Listener<Req> interceptCall(
            ServerCall<Req, Resp> call,
            Metadata headers,
            ServerCallHandler<Req, Resp> next) {

        SSLSession sslSession = call.getAttributes()
            .get(Grpc.TRANSPORT_ATTR_SSL_SESSION);

        if (sslSession == null) {
            call.close(Status.UNAUTHENTICATED.withDescription("mTLS required"), new Metadata());
            return new ServerCall.Listener<>() {};
        }

        try {
            // Extract the client certificate from the TLS session
            X509Certificate clientCert = (X509Certificate)
                sslSession.getPeerCertificates()[0];

            // Parse the SPIFFE URI from the SAN
            RunnerIdentity identity = extractRunnerIdentity(clientCert);

            // Attach to gRPC context — available to all service handlers
            Context ctx = Context.current().withValue(RUNNER_IDENTITY, identity);
            return Contexts.interceptCall(ctx, call, headers, next);

        } catch (SSLPeerUnverifiedException e) {
            call.close(Status.UNAUTHENTICATED.withDescription("Invalid client certificate"),
                new Metadata());
            return new ServerCall.Listener<>() {};
        }
    }

    private RunnerIdentity extractRunnerIdentity(X509Certificate cert) {
        // Parse SPIFFE URI: spiffe://cluster.local/runners/{tenant_id}/{runner_id}
        Collection<List<?>> sans = cert.getSubjectAlternativeNames();
        String spiffeUri = sans.stream()
            .filter(san -> san.get(0).equals(6))  // type 6 = URI
            .map(san -> (String) san.get(1))
            .filter(uri -> uri.startsWith("spiffe://"))
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException("No SPIFFE URI in certificate"));

        // spiffe://cluster.local/runners/megacorp/runner-abc123
        String[] parts = spiffeUri.split("/");
        return new RunnerIdentity(
            parts[parts.length - 2],  // tenant_id
            parts[parts.length - 1]   // runner_id
        );
    }
}
```

### gRPC Client with mTLS — Runner Side

```java
// On the self-hosted runner (Java agent)
public ManagedChannel createAuthenticatedChannel(String serverAddress) throws Exception {
    // Load the certificate provisioned by Pravah
    SslContext sslContext = SslContextBuilder.forClient()
        // Runner's own certificate (client certificate for mTLS)
        .keyManager(new File("/etc/pravah-runner/tls.crt"),
                    new File("/etc/pravah-runner/tls.key"))
        // Trust only Pravah's CA (do not trust arbitrary server certificates)
        .trustManager(new File("/etc/pravah-runner/ca.crt"))
        .sslProvider(SslProvider.OPENSSL)
        .protocols("TLSv1.3")
        .build();

    return NettyChannelBuilder
        .forAddress(serverAddress, 443)
        .sslContext(sslContext)
        .build();
}
```

## Service Mesh Alternative — Istio / Linkerd

For service-to-service communication within the cluster (not runner ↔ cloud), Pravah can delegate mTLS to a service mesh rather than implementing it in application code.

**How Istio mTLS works:**

Every pod gets an Envoy sidecar proxy injected automatically. All inter-pod traffic is intercepted by Envoy and encrypted with mTLS. The application code does not need to know about TLS at all — it makes a plain HTTP call to `http://pipeline-service:8080` and Envoy handles the mTLS transparently.

```yaml
# Istio PeerAuthentication — require mTLS in the pravah namespace
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: pravah
spec:
  mtls:
    mode: STRICT   # STRICT = only mTLS allowed, no plaintext
```

```yaml
# Istio AuthorizationPolicy — Execution Service can call Pipeline Service
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: pipeline-service-authz
  namespace: pravah
spec:
  selector:
    matchLabels:
      app: pipeline-service
  rules:
    - from:
        - source:
            # Only pods with execution-service service account can call pipeline-service
            principals:
              - cluster.local/ns/pravah/sa/execution-service
              - cluster.local/ns/pravah/sa/scheduler-service
      to:
        - operation:
            methods: ["POST", "GET"]
            paths: ["/pipelines/*", "/schedules/*"]
```

**Tradeoffs:**

| Approach | Pros | Cons |
|---|---|---|
| Application-level mTLS | Full control, works for gRPC runners, no sidecar overhead | More code, certificate management per service |
| Istio/Linkerd | Transparent to app code, uniform policy, observability | Sidecar overhead (CPU, memory, latency), operational complexity |
| Hybrid (Pravah's approach) | Application mTLS for runners (required), Istio for internal | Two systems to manage |

Pravah uses a hybrid approach: application-level mTLS for the runner ↔ cloud gRPC path (because runners are outside the cluster and a service mesh cannot reach them), and Istio for internal service-to-service communication.

## Certificate Rotation Without Downtime

cert-manager rotates certificates automatically before expiry (at 80% of the 90-day lifetime, which is at 72 days). The new certificate is written to the Kubernetes Secret. But the running pod still has the old certificate in memory.

Two approaches for zero-downtime rotation:

**Approach 1: Periodic reload**

The service watches the mounted certificate directory and reloads when it changes:

```java
@Component
public class CertificateReloader {

    private final AtomicReference<SslContext> sslContextRef = new AtomicReference<>();

    @Scheduled(fixedDelay = 3600000)  // check every hour
    public void reloadIfChanged() {
        File certFile = new File("/etc/pravah/tls/tls.crt");
        // Compare modification time with current cert's notAfter date
        // If the file is newer, reload
        if (certificateHasChanged(certFile)) {
            SslContext newContext = buildSslContext();
            sslContextRef.set(newContext);
            log.info("mTLS certificate reloaded — new expiry: {}", getExpiry(certFile));
        }
    }
}
```

**Approach 2: Rolling restart**

cert-manager can be configured to annotate the pod when a certificate rotates, triggering a Kubernetes rolling restart. The new pods pick up the new certificate. Zero downtime because rolling restart keeps old pods running until new ones are ready.

## Debugging mTLS Problems

mTLS failures are often opaque — the connection is terminated at the TLS layer before any application code runs. Common failure modes:

**"certificate verify failed" — client does not trust server's CA**
```bash
# Test the TLS handshake with openssl
openssl s_client -connect pipeline-service.pravah:443 \
  -CAfile /etc/pravah/tls/ca.crt \
  -cert /etc/pravah/tls/tls.crt \
  -key /etc/pravah/tls/tls.key

# Expected: "Verify return code: 0 (ok)"
# If you see "Verify return code: 21 (unable to verify the first certificate)":
#   → the server's certificate was not signed by the CA in ca.crt
```

**"SSLV3_ALERT_CERTIFICATE_UNKNOWN" — server does not trust client's CA**
```bash
# Check what certificate the client is presenting
openssl x509 -in /etc/pravah/tls/tls.crt -noout -text | grep -A5 "Subject:"
# Verify the issuer matches the server's trusted CA
openssl x509 -in /etc/pravah/tls/tls.crt -noout -text | grep -A5 "Issuer:"
```

**"certificate has expired"**
```bash
# Check certificate expiry
openssl x509 -in /etc/pravah/tls/tls.crt -noout -dates
# notBefore: Jan 15 10:00:00 2024 GMT
# notAfter:  Apr 14 10:00:00 2024 GMT   ← if this is in the past, rotation failed
```

**Certificate not in SAN**
```bash
# Check SANs
openssl x509 -in /etc/pravah/tls/tls.crt -noout -ext subjectAltName
# Should show: DNS:execution-service, URI:spiffe://...
# If the hostname being connected to doesn't match any SAN → TLS error
```

## System Design Interview Angles

**"How do runners authenticate to Pravah's cloud infrastructure?"**

> Runners authenticate with mTLS — mutual TLS. When a tenant registers a runner, Pravah provisions a unique X.509 certificate for it. The certificate's SPIFFE URI encodes the tenant ID and runner ID: `spiffe://cluster.local/runners/megacorp/runner-abc123`. The tenant installs this certificate bundle on their runner machine.
>
> When the runner connects to Pravah's gRPC gateway, it presents this certificate. The gateway's `RunnerIdentityInterceptor` extracts the SPIFFE URI from the certificate's Subject Alternative Names and derives the runner's identity. No API key lookup is needed — the certificate IS the identity, cryptographically verifiable against Pravah's CA.
>
> A compromised runner cannot impersonate a different runner because it does not have the other runner's private key. A self-signed certificate would be rejected because Pravah's gRPC server only trusts certificates signed by Pravah's CA (`ClientAuth.REQUIRE` + explicit `trustManager`).

**"What happens when a runner's certificate expires?"**

> cert-manager monitors certificates and automatically renews them at 80% of their 90-day lifetime (at day 72). The renewed certificate is written to the Kubernetes Secret. For cloud runners (inside the cluster), the pod picks up the new certificate either through a periodic reload or a rolling restart triggered by cert-manager's annotation.
>
> For self-hosted runners (outside the cluster), the renewed certificate must be delivered to the runner. Pravah handles this through the runner agent: the agent periodically calls a Pravah API endpoint to check whether its certificate is approaching expiry and downloads a refreshed bundle if so. The runner rotates the certificate without stopping — the gRPC connection is re-established with the new certificate on the next reconnect.
>
> An expired runner certificate causes an immediate mTLS handshake failure. The runner will appear offline in Pravah's dashboard. This is the intended behavior — an expired certificate means the runner has not been actively maintaining its identity, which could indicate it was decommissioned.

**"How is Istio mTLS different from application-level mTLS?"**

> With application-level mTLS, the service itself handles the TLS certificates, loads them, and terminates the TLS connection. The application code is aware of security — it configures the gRPC SslContext, validates peer certificates, and extracts identity from the certificate chain.
>
> With Istio, an Envoy sidecar proxy intercepts all network traffic before it reaches the application. The application makes plain HTTP calls; Envoy transparently upgrades them to mTLS using SPIFFE certificates managed by Istio's control plane. The application code doesn't need to know about TLS at all.
>
> Pravah uses both. For runner communication — self-hosted runners are outside the Kubernetes cluster, so Istio's sidecar cannot intercept their traffic. Application-level mTLS is required. For internal service-to-service: Istio provides mTLS transparently, and its `AuthorizationPolicy` CRDs provide fine-grained service-level authorization without application code changes.

## Key Takeaways

1. **mTLS = both sides present certificates.** Server proves identity to client (standard TLS) + client proves identity to server. The client certificate is cryptographically bound to the service identity.

2. **Certificate = identity.** No API key, no token, no lookup. The SPIFFE URI in the certificate's SAN encodes the service identity in a standard, verifiable format.

3. **CA hierarchy:** offline root CA signs intermediate CA. Intermediate CA (online) signs service certificates. Root CA never touches online systems — compromise of intermediate CA doesn't compromise the root.

4. **cert-manager automates everything:** certificate issuance, renewal at 80% lifetime, rotation into Kubernetes Secrets. Services mount the Secret as a volume.

5. **Runner mTLS is critical:** self-hosted runners are in untrusted networks. Certificate-based identity ensures only legitimate Pravah-provisioned runners can connect. Impersonation is cryptographically impossible.

6. **Hybrid approach for Pravah:** application-level mTLS for runner ↔ cloud gRPC (runners are outside the cluster). Istio service mesh mTLS for internal service-to-service (simpler, policy-driven).

7. **Rotation without downtime:** cert-manager rotates before expiry. Periodic reload or rolling restart ensures services always have valid certificates without interruption.

8. **Debug with openssl:** `s_client` shows the full TLS handshake including certificate chain and verification result. Essential for debugging mTLS failures.
