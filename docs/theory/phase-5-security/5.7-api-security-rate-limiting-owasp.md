# 5.7 API Security — Rate Limiting, Input Validation & OWASP

## The External Attack Surface

Every API endpoint Pravah exposes is a potential attack vector. Unlike internal service communication (secured by mTLS) or database access (secured by credentials + RLS), the external API is designed to be reachable from anywhere.

This means:
- Automated attack tools probe it continuously
- Credential stuffing bots attempt authentication around the clock
- Malicious tenants probe for logic bugs and injection vulnerabilities
- Denial of service attempts come from botnets

API security is not a feature added at the end — it is designed in from the beginning.

---

## Rate Limiting — Protecting Against Abuse

Rate limiting controls how many requests a client can make in a time window. Without it:
- A compromised API key floods the platform with millions of job submissions
- Credential stuffing tools make unlimited authentication attempts
- A misconfigured client (infinite retry loop) consumes all available capacity
- A competitive attack submits expensive jobs to exhaust shared runner capacity

### Token Bucket Algorithm

Pravah uses the token bucket algorithm. Each client has a bucket with a fixed capacity. Tokens accumulate at a fixed rate. Each request consumes one token. If the bucket is empty, the request is rate-limited.

```
Bucket capacity: 100 tokens
Refill rate:     10 tokens per second

Request pattern:
  t=0s:  burst of 100 requests → bucket empties
  t=1s:  10 tokens added → 10 requests allowed
  t=10s: 100 tokens added (bucket full) → next burst of 100 allowed

Vs fixed window (simpler but worse):
  "100 requests per minute" — allows 200 requests in 1 second (at boundary between minutes)
  Token bucket: allows 100 requests maximum in any short window
```

Token bucket is implemented in Redis — shared across all API Gateway pods, so limits are enforced globally, not per-pod.

### Redis-Based Rate Limiter

```java
@Service
public class RateLimiterService {

    private final RedisScript<List<Long>> rateLimitScript;
    private final StringRedisTemplate redis;

    // Lua script — atomic token bucket check + decrement
    private static final String RATE_LIMIT_LUA = """
        local key = KEYS[1]
        local capacity = tonumber(ARGV[1])
        local refill_rate = tonumber(ARGV[2])   -- tokens per second
        local now = tonumber(ARGV[3])           -- current time (milliseconds)
        local cost = tonumber(ARGV[4])          -- tokens this request costs

        -- Get current bucket state
        local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
        local tokens = tonumber(bucket[1]) or capacity
        local last_refill = tonumber(bucket[2]) or now

        -- Calculate tokens added since last request
        local elapsed = (now - last_refill) / 1000.0
        local added = elapsed * refill_rate
        tokens = math.min(capacity, tokens + added)

        -- Check if request can proceed
        if tokens >= cost then
            tokens = tokens - cost
            redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
            redis.call('EXPIRE', key, 3600)   -- expire if no activity for 1 hour
            return {1, math.floor(tokens)}    -- allowed, remaining tokens
        else
            redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
            redis.call('EXPIRE', key, 3600)
            return {0, 0}                     -- denied
        end
    """;

    public RateLimitResult checkRateLimit(String tenantId, String apiKeyId, RateLimitTier tier) {
        // Hierarchical rate limit keys: per-API-key and per-tenant
        String keyByApiKey = "ratelimit:key:" + apiKeyId;
        String keyByTenant = "ratelimit:tenant:" + tenantId;

        long now = System.currentTimeMillis();

        // Check per-API-key limit first (stricter)
        List<Long> keyResult = redis.execute(rateLimitScript,
            List.of(keyByApiKey),
            String.valueOf(tier.getKeyCapacity()),
            String.valueOf(tier.getKeyRefillRate()),
            String.valueOf(now),
            "1"
        );

        if (keyResult.get(0) == 0) {
            return RateLimitResult.denied("API key rate limit exceeded");
        }

        // Check per-tenant limit (broader)
        List<Long> tenantResult = redis.execute(rateLimitScript,
            List.of(keyByTenant),
            String.valueOf(tier.getTenantCapacity()),
            String.valueOf(tier.getTenantRefillRate()),
            String.valueOf(now),
            "1"
        );

        if (tenantResult.get(0) == 0) {
            return RateLimitResult.denied("Tenant rate limit exceeded");
        }

        return RateLimitResult.allowed(tenantResult.get(1));
    }
}
```

### HTTP Rate Limit Headers

Return headers so clients can implement backoff correctly:

```java
// After rate limit check
response.setHeader("X-RateLimit-Limit", String.valueOf(tier.getKeyCapacity()));
response.setHeader("X-RateLimit-Remaining", String.valueOf(remaining));
response.setHeader("X-RateLimit-Reset", String.valueOf(resetEpochSeconds));
response.setHeader("Retry-After", String.valueOf(secondsUntilReset));   // on 429

// If rate limited:
response.setStatus(429);   // Too Many Requests — NOT 403
return ResponseEntity.status(429)
    .body(ErrorResponse.of("RATE_LIMIT_EXCEEDED",
        "Rate limit exceeded. Retry after " + secondsUntilReset + " seconds."));
```

Status 429 (Too Many Requests) is the correct response — not 403 (Forbidden), which implies a permanent access denial.

## Input Validation — First Line of Defense

All external input is untrusted. Validation must happen at the earliest possible point — at the API Gateway or service controller boundary, before the input reaches any business logic.

### SQL Injection Defense — Parameterized Queries

SQL injection occurs when user input is concatenated into a SQL query string. The defense: always use parameterized queries (prepared statements), never string concatenation.

```java
// ❌ Vulnerable to SQL injection
String query = "SELECT * FROM jobs WHERE tenant_id = '" + tenantId +
               "' AND name LIKE '%" + searchTerm + "%'";
// Input: searchTerm = "'; DROP TABLE jobs; --"
// → Executes: ... LIKE '%'; DROP TABLE jobs; --%'

// ✅ Parameterized query — user input never interpreted as SQL
@Query("SELECT j FROM Job j WHERE j.tenantId = :tenantId AND j.name LIKE :pattern")
List<Job> findByName(@Param("tenantId") String tenantId,
                     @Param("pattern") String pattern);

// Usage
List<Job> results = jobRepository.findByName(tenantId, "%" + searchTerm + "%");
// searchTerm is treated as a literal string, never as SQL syntax
```

**With JPA/Hibernate:** all `@Query` annotations with `:param` placeholders use parameterized queries. Avoid `@NativeQuery` with string interpolation.

**Pravah's safety net:** even if a parameterized query is forgotten and a raw query reaches PostgreSQL, RLS policies ensure the query can only access the current tenant's rows. SQL injection that produces `SELECT * FROM jobs` without `WHERE tenant_id = ?` returns only the current tenant's data — not all tenants.

### Command Injection Defense

Pravah allows tenants to define pipeline steps that run commands. These commands must never be interpolated into a shell command string:

```java
// ❌ Shell injection — user input in a shell command
ProcessBuilder pb = new ProcessBuilder(
    "bash", "-c", "python3 " + userProvidedScriptPath  // injection here
);

// ✅ Argument array — no shell interpretation
ProcessBuilder pb = new ProcessBuilder(
    "python3",
    validatedScriptPath  // validated path — no ../, no special chars
);
pb.command().add("--input");
pb.command().add(validatedInputFile);
```

Pipeline step definitions are stored as structured data (JSON/Protobuf), not as shell command strings. The execution layer translates them to `ProcessBuilder` argument arrays — never to `bash -c`.

### SSRF — Server-Side Request Forgery

SSRF is a critical vulnerability for Pravah specifically. Tenants can configure webhook URLs — Pravah calls these URLs after pipeline completion. A malicious tenant provides a webhook URL that points to Pravah's internal infrastructure:

```
Webhook URL: http://169.254.169.254/latest/meta-data/  (AWS EC2 metadata — contains IAM credentials)
Webhook URL: http://vault.pravah.svc:8200/v1/sys/health  (internal Vault)
Webhook URL: http://postgres-primary.pravah:5432        (internal PostgreSQL)
Webhook URL: file:///etc/passwd                         (local file)
```

If Pravah makes an HTTP request to any of these, the response may contain sensitive internal data or allow the attacker to pivot into internal infrastructure.

**SSRF Defense:**

```java
@Component
public class WebhookUrlValidator implements ConstraintValidator<WebhookUrl, String> {

    // Blocklist of private IP ranges (RFC 1918, loopback, link-local)
    private static final List<InetAddressRange> BLOCKED_RANGES = List.of(
        InetAddressRange.of("10.0.0.0/8"),
        InetAddressRange.of("172.16.0.0/12"),
        InetAddressRange.of("192.168.0.0/16"),
        InetAddressRange.of("127.0.0.0/8"),        // loopback
        InetAddressRange.of("169.254.0.0/16"),     // link-local (AWS metadata)
        InetAddressRange.of("::1/128"),             // IPv6 loopback
        InetAddressRange.of("fc00::/7")             // IPv6 private
    );

    @Override
    public boolean isValid(String urlString, ConstraintValidatorContext context) {
        if (urlString == null) return true;  // @NotNull handles null separately

        URL url;
        try {
            url = new URL(urlString);
        } catch (MalformedURLException e) {
            context.buildConstraintViolationWithTemplate("Invalid URL format").addConstraintViolation();
            return false;
        }

        // Only allow HTTPS (not HTTP, file://, ftp://, etc.)
        if (!"https".equalsIgnoreCase(url.getProtocol())) {
            context.buildConstraintViolationWithTemplate("Webhook URL must use HTTPS").addConstraintViolation();
            return false;
        }

        // Resolve hostname to IP and check against blocklist
        try {
            InetAddress[] addresses = InetAddress.getAllByName(url.getHost());
            for (InetAddress addr : addresses) {
                if (isBlockedAddress(addr)) {
                    context.buildConstraintViolationWithTemplate(
                        "Webhook URL resolves to a private or reserved IP address"
                    ).addConstraintViolation();
                    return false;
                }
            }
        } catch (UnknownHostException e) {
            context.buildConstraintViolationWithTemplate("Webhook URL hostname cannot be resolved")
                .addConstraintViolation();
            return false;
        }

        return true;
    }
}
```

**DNS rebinding defense:** even after validation, a DNS rebinding attack can change the resolved IP after validation but before the request. Pravah's HTTP client re-validates the resolved IP at connection time:

```java
// Custom HTTP client that prevents SSRF even with DNS rebinding
@Bean
public HttpClient ssrfSafeHttpClient() {
    return HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .followRedirects(HttpClient.Redirect.NEVER)   // no redirect following (another SSRF vector)
        .version(HttpClient.Version.HTTP_2)
        .sslContext(sslContext)
        .build();
}
```

## OWASP Top 10 — Pravah's Defense Map

The OWASP Top 10 is the standard reference for web application security vulnerabilities. Each applies directly to Pravah.

### A01: Broken Access Control

The most prevalent vulnerability. Includes IDOR, missing authorization checks, privilege escalation.

**Pravah's controls:** role checks via `@PreAuthorize`, tenant scoping in every query, PostgreSQL RLS as the database-level backstop, `findByIdAndTenantId` instead of `findById`. Covered in 5.5 and 5.6.

### A02: Cryptographic Failures

Sensitive data transmitted or stored without adequate encryption.

**Pravah's controls:** TLS 1.3 for all external communication, mTLS for internal service communication, AES-256-GCM encryption for tenant secrets via Vault Transit, bcrypt for stored user passwords, SHA-256 for API key hashing (never stored plaintext).

```java
// User passwords — bcrypt with cost factor 12
PasswordEncoder encoder = new BCryptPasswordEncoder(12);
String hash = encoder.encode(rawPassword);
// Verification is constant-time (bcrypt)
boolean valid = encoder.matches(rawPassword, hash);
```

### A03: Injection

SQL injection, command injection, SSRF, LDAP injection.

**Pravah's controls:** JPA parameterized queries, `ProcessBuilder` argument arrays (not shell strings), SSRF validator on webhook URLs, input schema validation via Bean Validation. Covered above.

### A04: Insecure Design

Security not designed in — added as an afterthought.

**Pravah's approach:** threat modeling from the start (5.1), security design decisions documented in architecture, "secure by default" principle, explicit security review for every new API endpoint.

### A05: Security Misconfiguration

Default credentials, unnecessary features enabled, error messages revealing stack traces.

**Pravah's controls:**
- Actuator endpoints only on the management port (not exposed via Ingress)
- Error responses never include stack traces:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e, HttpServletRequest req) {
        // Log with full stack trace internally
        log.error("Unexpected error processing request", e);

        // Return sanitized error to client — no stack trace, no internal detail
        return ResponseEntity.status(500)
            .body(ErrorResponse.of("INTERNAL_ERROR",
                "An unexpected error occurred. Reference: " + generateErrorRef(e)));
    }
}
```

- All default passwords changed during Vault/PostgreSQL provisioning
- Kubernetes API server not publicly accessible (private endpoint)
- No debug endpoints in production

### A06: Vulnerable and Outdated Components

Dependencies with known CVEs.

**Pravah's controls:** Dependabot/Renovate for automatic dependency update PRs, SBOM (Software Bill of Materials) generated on every build, vulnerability scanning in CI (Trivy for containers, OWASP Dependency-Check for Java), container image minimal base (distroless).

```yaml
# CI pipeline: scan container image for vulnerabilities
- name: Scan container image
  run: |
    trivy image --exit-code 1 --severity CRITICAL,HIGH \
      pravah/execution-service:${VERSION}
# Fails build on CRITICAL or HIGH vulnerabilities
```

### A07: Identification and Authentication Failures

Weak passwords, credential stuffing, missing brute force protection.

**Pravah's controls:**
- Account lockout after 5 failed login attempts (exponential backoff)
- CAPTCHA on login after 3 failures
- Credential stuffing detection (check email against HaveIBeenPwned on registration)
- Minimum password entropy enforcement
- JWT short lifetime (15 minutes) + rotation on use for refresh tokens

```java
// Brute force protection — tracked in Redis
public AuthResult login(String email, String password) {
    String lockoutKey = "lockout:" + email;
    int failureCount = getFailureCount(lockoutKey);

    if (failureCount >= 5) {
        long lockoutRemaining = getLockoutRemaining(lockoutKey);
        throw new AuthenticationException(
            "Account locked. Try again in " + lockoutRemaining + " seconds."
        );
    }

    // Attempt authentication (constant-time regardless of outcome)
    boolean authenticated = userService.verify(email, password);

    if (!authenticated) {
        // Increment failure count with exponential backoff
        int newCount = failureCount + 1;
        long lockoutSeconds = (long) Math.pow(2, newCount);  // 2, 4, 8, 16, 32...
        redis.opsForValue().set(lockoutKey, String.valueOf(newCount),
            Duration.ofSeconds(lockoutSeconds));
        throw new AuthenticationException("Invalid credentials");
    }

    redis.delete(lockoutKey);  // reset on success
    return generateTokens(email);
}
```

### A08: Software and Data Integrity Failures

Unsigned code, deserialization of untrusted data.

**Pravah's controls:**
- Container images signed with Sigstore/Cosign
- `VERIFY_IMAGE` admission controller in Kubernetes — unsigned images rejected
- Kafka message deserialization uses typed Protobuf schemas (not Java serialization, not arbitrary JSON deserialization)
- Webhook payloads verified via HMAC signature before processing

### A09: Security Logging and Monitoring Failures

Not logging security events, not detecting attacks.

**Pravah's controls:** audit log for all security-relevant events (authentication, authorization decisions, permission changes, API key operations), alert on anomalies (>10 authentication failures/minute per IP, >5 authorization denials in 1 minute per user, unexpected admin API calls). Covered in Phase 4 (alerting strategy).

### A10: Server-Side Request Forgery (SSRF)

**Pravah's controls:** webhook URL validation blocking private IP ranges, DNS rebinding protection at connection time, no `file://` or `ftp://` protocols, redirect following disabled. Covered above.

## Content Security Policy and HTTP Security Headers

For Pravah's web dashboard (not the API):

```java
@Bean
public SecurityFilterChain webSecurityChain(HttpSecurity http) throws Exception {
    http.headers(headers -> headers
        // Prevent clickjacking
        .frameOptions(frame -> frame.deny())
        // Prevent MIME type sniffing
        .contentTypeOptions(Customizer.withDefaults())
        // Force HTTPS for 1 year
        .httpStrictTransportSecurity(hsts -> hsts
            .includeSubDomains(true)
            .maxAgeInSeconds(31536000)
        )
        // Content Security Policy — restrict resource loading
        .contentSecurityPolicy(csp -> csp.policyDirectives(
            "default-src 'self'; " +
            "script-src 'self' 'nonce-{RANDOM}'; " +
            "style-src 'self'; " +
            "img-src 'self' data:; " +
            "connect-src 'self' https://api.pravah.io; " +
            "frame-ancestors 'none'"
        ))
        // Referrer policy — don't leak paths to external sites
        .referrerPolicy(ref -> ref
            .policy(ReferrerPolicyHeaderWriter.ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN)
        )
    );
    return http.build();
}
```

## System Design Interview Angles

**"How does Pravah prevent SSRF attacks from tenant-configured webhook URLs?"**

> Pravah allows tenants to configure webhook URLs that are called after pipeline completion. This is a classic SSRF vector — a tenant could configure `http://169.254.169.254/latest/meta-data/` (AWS metadata service) or `http://vault.pravah.svc:8200` to try to access internal infrastructure.
>
> Defense is multi-layered. At configuration time, a custom Bean Validation annotation resolves the webhook URL's hostname and checks the resulting IP against a blocklist: all RFC 1918 private ranges, loopback, and link-local addresses (which includes the AWS metadata service at 169.254.169.254). Only HTTPS URLs are accepted. URLs with `file://`, `ftp://`, or other schemes are rejected.
>
> At request time, we add DNS rebinding protection: even after the URL passes validation, the HTTP client re-validates the resolved IP at connection time. DNS rebinding attacks change the IP after validation but before the connection. Re-validating at connection time defeats this. Additionally, HTTP redirects are disabled — a redirect to an internal URL after an initially valid URL would otherwise bypass validation.

**"What rate limiting approach does Pravah use, and why is token bucket better than a fixed window?"**

> Pravah uses the token bucket algorithm implemented atomically in Redis with a Lua script. Each API key has a bucket with configurable capacity and refill rate. Requests consume tokens; the bucket refills at a constant rate.
>
> Fixed window rate limiting — "100 requests per minute" — has a burst problem at window boundaries. At minute 0:59, a client submits 100 requests (within limit). At minute 1:00, the window resets and they submit another 100 immediately. The system sees 200 requests in 1 second — far more than intended.
>
> Token bucket prevents this. Even with a 100-token capacity, the bucket cannot accumulate more than 100 tokens. A burst of 100 empties the bucket; the next request must wait for a token to accumulate at the refill rate. The burst window is controlled.
>
> Pravah has hierarchical limits: per-API-key (stricter) and per-tenant (broader). A tenant with 10 API keys cannot multiply their rate limit 10x — the per-tenant limit applies to the aggregate traffic from all their API keys.

**"How do you defend against SQL injection in Pravah?"**

> Primarily through parameterized queries — all database access goes through JPA/Hibernate with `:param` placeholders. User input is never concatenated into SQL strings. The JDBC driver sends parameter values as data to PostgreSQL, not as part of the SQL syntax. Even if user input contains `'; DROP TABLE jobs; --`, it is treated as a literal string value.
>
> Beyond parameterization: the PostgreSQL user for each service has minimal permissions (SELECT, INSERT, UPDATE on specific tables — no DROP, no ALTER). Even a successful SQL injection attack cannot drop tables or modify schema.
>
> As a final layer, PostgreSQL RLS ensures that any query that accidentally omits the `WHERE tenant_id = ?` clause returns only the current tenant's rows — limiting the blast radius of a successful injection to that tenant's own data rather than the entire platform.

## Key Takeaways

1. **Rate limiting with token bucket via Redis.** Atomic Lua script ensures no race conditions across API Gateway pods. Hierarchical: per-API-key (burst control) + per-tenant (aggregate control). Returns 429 with `Retry-After` header.

2. **Input validation at the boundary.** Bean Validation annotations on request DTOs. `@Valid` on controller parameters. Validation before any business logic.

3. **SQL injection: parameterized queries always.** Never concatenate user input into SQL strings. JPA `:param` placeholders are parameterized by design. Complement with minimal database permissions.

4. **SSRF: validate webhook URLs at multiple points.** Resolve hostname, check against private IP blocklist, at configuration time AND at connection time (DNS rebinding defense). HTTPS only, no redirect following.

5. **OWASP Top 10 as a checklist:** A01 (IDOR → RLS + tenant scoping), A02 (weak crypto → TLS 1.3 + Vault), A03 (injection → parameterized queries + SSRF defense), A07 (auth failures → lockout + bcrypt), A08 (integrity → signed images + HMAC webhooks), A09 (logging → audit trail + anomaly alerts).

6. **Error responses never reveal internals.** Generic error message + opaque reference ID. Log the full stack trace internally. Client gets no information useful for an attacker.

7. **HTTP security headers for the dashboard.** CSP to prevent XSS, X-Frame-Options to prevent clickjacking, HSTS for HTTPS enforcement, referrer policy to prevent path leakage.

8. **Constant-time comparisons for secrets.** `MessageDigest.isEqual()` instead of `String.equals()` for API key and HMAC comparisons. Timing attacks extract secrets character-by-character from non-constant-time comparisons.
