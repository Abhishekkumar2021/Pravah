# 8.4 Backfill Safety & Idempotency in Practice

## Why Backfills Are Dangerous

A backfill re-runs a pipeline for historical date ranges — typically to correct bad data, apply a new business rule, or recover from a missed run. It seems simple: run the pipeline again for the dates where data is wrong.

In practice, backfills are among the most dangerous operations in data engineering. Done incorrectly, they:
- Double-count: the same order appears twice in the warehouse
- Overwrite good data: a partial backfill corrupts the days it touches
- Cause cascading failures: downstream pipelines and dashboards receive inconsistent data mid-backfill
- Overwhelm source systems: 30 parallel queries to a production database, each reading millions of rows

Safe backfills require explicit design at every layer: the destination must support idempotent overwrites, the pipeline must be parameterized by date, the source must not be overwhelmed, and downstream consumers must be coordinated.

---

## The Core Requirement: Idempotent Writes

An idempotent operation produces the same result regardless of how many times it is applied. For backfills, this means: running the pipeline for May 1st once and running it twice must produce the same result in the destination.

**The wrong approach — INSERT:**

```sql
-- Running this twice for the same date_range inserts duplicate rows
INSERT INTO dw_orders (order_id, order_date, revenue)
SELECT order_id, order_date, revenue
FROM orders
WHERE order_date BETWEEN '2026-05-01' AND '2026-05-01';
```

The second run sees the same source data and inserts the same rows again. The warehouse now has duplicates for May 1st.

**The right approach — MERGE (upsert):**

```sql
-- Running this twice produces the same final state
MERGE INTO dw_orders AS target
USING (
    SELECT order_id, order_date, revenue
    FROM orders
    WHERE order_date BETWEEN '2026-05-01' AND '2026-05-01'
) AS source
ON target.order_id = source.order_id
   AND target.order_date = source.order_date
WHEN MATCHED THEN
    UPDATE SET revenue = source.revenue
WHEN NOT MATCHED THEN
    INSERT (order_id, order_date, revenue)
    VALUES (source.order_id, source.order_date, source.revenue);
```

The second run finds all rows MATCHED (already exist) and updates them with the same values — a no-op.

**Partition overwrite (for partitioned tables / columnar destinations):**

For destinations that support it (BigQuery, Snowflake, Hive-partitioned Parquet on S3), partition overwrite is cleaner than MERGE:

```sql
-- BigQuery partition overwrite
INSERT INTO dw_orders
PARTITION(order_date = '2026-05-01')
OVERWRITE
SELECT order_id, order_date, revenue
FROM orders
WHERE order_date = '2026-05-01';

-- This atomically replaces the entire May 1 partition with fresh data
-- Running it twice: first run loads data, second run overwrites with identical data — safe
```

Partition overwrite is preferred when:
- The destination supports it natively (BigQuery, Snowflake external tables, Delta Lake)
- The backfill is date-partitioned (one partition per day)
- The full partition must be replaced (not just updated rows)

## Date Parameterization

For a pipeline to be backfillable, it must be parameterized by the processing date — not hardcoded to "today."

**Hardcoded — not backfillable:**

```sql
SELECT * FROM orders
WHERE order_date = CURRENT_DATE - INTERVAL '1 day'
```

Running this tomorrow produces tomorrow's data, not May 1st's data. Backfill is impossible.

**Parameterized — backfillable:**

```sql
SELECT * FROM orders
WHERE order_date = '{{ business_date }}'
```

The `business_date` parameter is injected at runtime. For a regular daily run, it is yesterday's date. For a backfill run, it is the specific historical date.

In Pravah, parameters are injected via the pipeline run configuration:

```json
{
  "pipeline_id": "orders-daily-etl",
  "parameters": {
    "business_date": "2026-05-01",
    "extract_start": "2026-05-01T00:00:00Z",
    "extract_end":   "2026-05-02T00:00:00Z"
  }
}
```

The runner receives these parameters and substitutes them in all SQL queries via template rendering. All queries in the pipeline use the same `business_date` — ensuring consistency across all steps.

## Source System Safety

A backfill reads historical data from the source system. If the backfill runs 30 parallel queries against a production PostgreSQL database, it competes with live application traffic.

**Strategies for protecting the source:**

**1. Read from read replicas:**

```json
{
  "connection": {
    "primary": "postgres://prod-primary:5432/db",    // live writes
    "replica": "postgres://prod-replica:5432/db"     // read here for ETL
  },
  "use_replica_for_reads": true
}
```

Even the replica can be overwhelmed by large parallel queries. Use `max_parallel_runs` in the backfill configuration to limit concurrent reads:

```json
{
  "backfill": {
    "start_date": "2026-05-01",
    "end_date": "2026-05-15",
    "max_parallel_runs": 3    // at most 3 dates running simultaneously
  }
}
```

**2. Rate-limit queries on the runner:**

For API sources (REST, Salesforce, Stripe) with rate limits, the runner enforces per-step rate limiting:

```json
{
  "step_id": "salesforce_extract",
  "rate_limit": {
    "max_requests_per_second": 5,
    "burst": 10
  }
}
```

**3. Use export artifacts rather than re-querying the source:**

If the source ran a daily export to S3 / MinIO, backfill should read from those exports rather than re-querying the live database. The export is already a point-in-time snapshot for that date — exactly what the backfill needs:

```sql
-- Read from historical export (immutable Parquet file)
SELECT * FROM read_parquet('s3://exports/orders/year=2026/month=05/day=01/*.parquet')
```

This does not touch the source system at all during backfill.

## Coordinating Downstream Consumers

When backfilling a pipeline, its downstream consumers may also need to be backfilled. A dashboard that reads from `dw_orders` will show corrupted numbers while the backfill is in progress (some dates are updated, others aren't yet).

**Options for downstream coordination:**

**1. Notify downstream owners:** inform downstream teams that a backfill is running for dates X to Y and results will be inconsistent until the backfill completes.

**2. Block downstream during backfill:** pause any downstream pipelines that depend on the backfilled table during the backfill window. Resume when the backfill completes. This requires the orchestration platform (Pravah) to understand pipeline dependencies.

**3. Backfill downstream too:** after the upstream backfill completes, automatically trigger backfills of downstream pipelines. Pravah can model this via the lineage graph: find all pipelines that depend on `dw_orders` and trigger backfills for the same date range.

In Pravah, option 3 is the default when `cascade_backfill: true` is set on the backfill configuration:

```json
{
  "backfill": {
    "start_date": "2026-05-01",
    "end_date":   "2026-05-15",
    "cascade_backfill": true    // trigger downstream backfills after completion
  }
}
```

The Metadata Service provides the lineage graph to identify downstream pipelines. Pravah triggers them in topological order — each downstream pipeline backfills after its upstream dependencies complete.

## Idempotency at Every Layer: A Checklist

A fully idempotent backfill ensures every component can be safely re-run:

| Layer | Idempotency Mechanism |
|-------|----------------------|
| Source extraction | Read from immutable snapshots (Parquet) or parameterized window queries |
| Step checkpoints (ADR-024) | `.completed` sentinel prevents re-execution of completed steps |
| Destination write | MERGE / UPSERT / partition overwrite |
| Lineage events | `run_id` in OpenLineage events is idempotent — duplicate events are rejected |
| Backfill trigger | Idempotency key per (pipeline_id, business_date, backfill_id) — duplicate triggers detected |
| Downstream notification | Backfill completion event is deduplicated by Notification Service via idempotency key |

If every layer is idempotent, a backfill that is accidentally triggered twice (or a step that retries after a partial failure) produces exactly the correct final state — no duplicates, no missing data, no corruption.
