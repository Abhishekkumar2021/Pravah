# 8.7 Data Quality Frameworks

## What Data Quality Means

Data quality is the degree to which data is fit for its intended purpose. "Fit for purpose" is critical — a column with 15% nulls is fine for a recommendation feature that degrades gracefully, and catastrophic for a revenue calculation where nulls silently propagate as zero.

Data quality is measured across multiple dimensions:

| Dimension | Question | Example |
|-----------|----------|---------|
| **Completeness** | Are required values present? | `customer_id` is never null |
| **Uniqueness** | Are values deduplicated? | `order_id` is unique per day |
| **Timeliness** | Is data fresh enough? | Table updated within the last 2 hours |
| **Accuracy** | Are values in the valid domain? | `status` ∈ {PLACED, SHIPPED, DELIVERED, CANCELLED} |
| **Consistency** | Is data internally consistent? | `total_price = unit_price × quantity` |
| **Referential integrity** | Do foreign keys resolve? | Every `customer_id` exists in the customers table |

A data quality framework provides tooling to define expectations, validate data against them, report results, and block or alert on violations.

## Profiling: Understanding Your Data Before Writing Rules

Before you can write quality expectations, you must understand the data. **Data profiling** computes statistics about each column:

```
Profile of table "orders" (42,150 rows):
  order_id:
    type: BIGINT  | nulls: 0 (0%)  | unique: 42,150 (100%)  | min: 1  | max: 9,999,234
  customer_id:
    type: BIGINT  | nulls: 312 (0.74%)  | unique: 8,432  | min: 1  | max: 654,321
  status:
    type: VARCHAR | nulls: 0 (0%)  | unique: 4  | top values: PLACED(45%), SHIPPED(30%), DELIVERED(20%), CANCELLED(5%)
  revenue:
    type: NUMERIC | nulls: 0 (0%)  | min: 0.01  | max: 99,999.99  | mean: 152.34  | p95: 450.00  | p99: 1,200.00
  created_at:
    type: TIMESTAMP | nulls: 0 (0%) | min: 2025-01-01 | max: 2026-05-10 | freshness: 45 minutes ago
```

DuckDB makes profiling straightforward:

```java
public DataProfile profile(Connection conn, String tableName) {
    Map<String, ColumnProfile> columns = new HashMap<>();

    ResultSet meta = conn.getMetaData().getColumns(null, null, tableName, null);
    while (meta.next()) {
        String col = meta.getString("COLUMN_NAME");
        String type = meta.getString("TYPE_NAME");

        // Compute statistics per column
        ResultSet stats = conn.createStatement().executeQuery(String.format("""
            SELECT
                COUNT(*)                                            AS total_rows,
                COUNT(%s)                                          AS non_null_count,
                COUNT(DISTINCT %s)                                 AS distinct_count,
                MIN(%s)::VARCHAR                                   AS min_value,
                MAX(%s)::VARCHAR                                   AS max_value
            FROM %s
            """, col, col, col, col, tableName));

        columns.put(col, buildColumnProfile(col, type, stats));
    }

    return new DataProfile(tableName, columns);
}
```

Profiling runs automatically at the end of every pipeline step in Pravah. The profile is stored in MinIO as `profile.json` alongside the step output, and key metrics (row count, null rates per column) are published to Prometheus.

## Expectations: Defining Quality Rules

An **expectation** is a testable assertion about the data. Expectations can be:
- Derived from the profile: "null rate should not exceed 2× the observed null rate"
- Defined by the data owner: "revenue must always be positive"
- Derived from contracts: "status must be one of the values in the approved enumeration"

**Expectation definition in Pravah (YAML format):**

```yaml
# expectations/orders.yaml
table: public.orders
expectations:
  - id: order_id_unique
    column: order_id
    type: UNIQUE
    severity: ERROR    # fail pipeline on violation

  - id: customer_id_not_null
    column: customer_id
    type: NOT_NULL
    severity: ERROR

  - id: revenue_positive
    column: revenue
    type: EXPRESSION
    expression: "revenue > 0"
    severity: ERROR

  - id: status_valid_values
    column: status
    type: ACCEPTED_VALUES
    values: [PLACED, SHIPPED, DELIVERED, CANCELLED]
    severity: ERROR

  - id: customer_id_null_rate
    column: customer_id
    type: NULL_RATE_BELOW
    threshold: 0.01    # max 1% nulls
    severity: WARNING  # warn but don't fail pipeline

  - id: row_count_reasonable
    type: ROW_COUNT_BETWEEN
    min: 1000
    max: 5000000
    severity: WARNING

  - id: referential_integrity_customer
    column: customer_id
    type: REFERENTIAL_INTEGRITY
    references: { table: customers, column: id }
    severity: ERROR
    sample_pct: 10    # check 10% of rows (for performance on large tables)
```

**Severity levels:**
- `ERROR`: violation fails the pipeline step. Data is not passed to the next step.
- `WARNING`: violation is logged and published to the data quality report, but the pipeline continues.
- `INFO`: informational only — anomaly detection, trend tracking.

## Running Expectations in Pravah

The quality validation step runs as a pipeline step of type `QUALITY_CHECK`:

```json
{
  "step_id": "validate_orders",
  "type": "QUALITY_CHECK",
  "depends_on": ["extract_orders"],
  "config": {
    "expectations_file": "expectations/orders.yaml",
    "sample_pct": 100,              // validate all rows (or set to % for large tables)
    "fail_on_error": true,          // ERROR violations fail the step
    "publish_report": true          // publish quality report to Metadata Service
  }
}
```

The runner executes all expectations against the step's output (Parquet on MinIO) using DuckDB:

```java
public QualityResult evaluate(List<Expectation> expectations, String parquetPath) {
    conn.execute("CREATE TABLE data AS SELECT * FROM read_parquet('" + parquetPath + "')");

    List<ExpectationResult> results = new ArrayList<>();
    for (Expectation exp : expectations) {
        String validationSql = exp.toValidationSql("data");
        ResultSet rs = conn.createStatement().executeQuery(validationSql);
        results.add(ExpectationResult.from(exp, rs));
    }

    return QualityResult.of(results);
}
```

**Generated SQL for common expectations:**

```sql
-- NOT_NULL check
SELECT COUNT(*) AS violation_count FROM data WHERE customer_id IS NULL;

-- ACCEPTED_VALUES check
SELECT COUNT(*) AS violation_count FROM data
WHERE status NOT IN ('PLACED', 'SHIPPED', 'DELIVERED', 'CANCELLED');

-- NULL_RATE_BELOW check
SELECT (COUNT(*) - COUNT(customer_id))::FLOAT / COUNT(*) AS null_rate FROM data;
-- violation: null_rate > 0.01

-- ROW_COUNT_BETWEEN check
SELECT COUNT(*) AS row_count FROM data;
-- violation: row_count < 1000 OR row_count > 5000000
```

## Quality Scores and Data Catalog Integration

Each validation run produces a **quality score** for the dataset: the percentage of expectations that passed, weighted by severity.

```
Total expectations: 8
Passed: 7
Failed (WARNING): 1 (customer_id_null_rate: 0.74% < 1% — PASSED, actual was below threshold → all 8 pass)

Actually:
Quality score = (passed_expectations / total_expectations) * 100 = 100%

With a violation:
If status_valid_values found 150 rows with status = "REFUNDED" (not in list):
  passed: 7, failed (ERROR): 1
  Quality score = 7/8 * 100 = 87.5%
```

Quality scores are published to the Metadata Service and displayed in the pipeline catalog:

```json
// Dataset quality in the catalog
{
  "dataset_id": "postgres://prod-db/public.orders",
  "quality_score": 87.5,
  "last_validated_at": "2026-05-10T09:01:30Z",
  "validation_run_id": "exec-abc",
  "violations": [
    {
      "expectation_id": "status_valid_values",
      "severity": "ERROR",
      "violation_count": 150,
      "sample_values": ["REFUNDED"]
    }
  ]
}
```

This powers a "data quality dashboard" in the UI — which datasets are healthy, which have active violations, and which failed their last quality check.

## Anomaly Detection

Beyond static expectations, quality also means detecting unexpected changes from a baseline — **anomaly detection**. Automated anomaly detection notices:

- Row count drops 40% compared to the last 7-day average → probable extraction failure
- Null rate for `customer_id` jumps from 0.1% to 15% → possible schema change in source
- Revenue mean drops by 30% → possible data truncation or wrong WHERE clause

Pravah implements statistical anomaly detection on key metrics:

```java
// For each column metric (null rate, mean, row count):
// Compute a rolling baseline (7-day average ± 2σ)
// Alert if current value is outside [baseline - 2σ, baseline + 2σ]
public void detectAnomalies(DataProfile currentProfile, List<DataProfile> historicalProfiles) {
    for (String column : currentProfile.getColumns()) {
        double[] historicalNullRates = historicalProfiles.stream()
            .mapToDouble(p -> p.getColumn(column).getNullRate())
            .toArray();

        double mean = Arrays.stream(historicalNullRates).average().orElse(0);
        double stdDev = computeStdDev(historicalNullRates, mean);

        double currentNullRate = currentProfile.getColumn(column).getNullRate();

        if (Math.abs(currentNullRate - mean) > 2 * stdDev) {
            publishAnomaly(column, "null_rate", currentNullRate, mean, stdDev);
        }
    }
}
```

Anomalies are published to the `data.quality.alerts` Kafka topic, consumed by the Notification Service (alert the pipeline owner) and the Agent Service (attempt to diagnose the anomaly).

## Application: The Quality Check Step in Pravah

Every pipeline in Pravah has an optional (but recommended) `QUALITY_CHECK` step after each extract or transform. The convention:

```
extract → quality_check_extract → transform → quality_check_transform → load → notify
```

Quality checks after extract detect problems in the source data before wasting compute on transformations.  
Quality checks after transform detect problems introduced by the transformation logic itself.

Quality results are stored in MinIO alongside the data, published to the Metadata Service for catalog display, and trigger alerts via the Notification Service. The Agent Service monitors `data.quality.alerts` and attempts to diagnose and auto-resolve common quality violations (e.g., adding a COALESCE for unexpected nulls, filtering invalid status values with a warning log).
