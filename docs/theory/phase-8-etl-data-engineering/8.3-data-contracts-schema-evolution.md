# 8.3 Data Contracts & Schema Evolution

## The Data Contract Problem

A data pipeline is an integration between a data producer (the source system) and a data consumer (the pipeline and its downstream users). When these two systems are operated by different teams, the implicit contract between them — "the orders table will have an `order_id`, `customer_id`, and `status` column" — is fragile.

The source team changes the schema for their operational reasons:
- Rename `status` to `order_status` for clarity
- Remove `legacy_code` because it's been unused for 2 years
- Change `amount` from `NUMERIC(10,2)` to `NUMERIC(15,2)` to support larger orders
- Add `NOT NULL` constraint to `customer_id`

None of these are breaking changes for the source application. All of them can silently break the consuming pipeline — a schema mismatch that only surfaces at 9am when the daily ETL fails.

**A data contract** makes the implicit explicit: it is a formal specification of the data that a producer commits to providing and a consumer expects to receive. It answers: what columns exist, what types they are, which are nullable, what values are valid, and what the backward/forward compatibility guarantees are.

## Schema Registry

A **Schema Registry** is a centralized service that stores and versions data schemas and enforces compatibility rules when schemas evolve.

Confluent Schema Registry (used with Kafka) is the most common implementation. It:
- Stores Avro, Protobuf, or JSON Schema definitions
- Assigns each schema a numeric ID
- Enforces a **compatibility level** when new schema versions are registered
- Provides the schema ID in Kafka message headers — consumers fetch the schema by ID to deserialize messages

**Schema registration:**

```
Producer registers schema for "orders-etl.orders.value":
{
  "type": "record",
  "name": "Order",
  "fields": [
    { "name": "order_id",    "type": "long" },
    { "name": "customer_id", "type": "long" },
    { "name": "status",      "type": "string" },
    { "name": "amount",      "type": { "type": "bytes", "logicalType": "decimal", "precision": 10, "scale": 2 }}
  ]
}

Schema Registry assigns: schema_id=42
Producer embeds schema_id=42 in each message's header
Consumer reads schema_id from header → fetches schema 42 → deserializes message
```

**Without Schema Registry:**

Producers and consumers must agree on the schema out-of-band (documentation, email, convention). A schema change breaks consumers silently — the consumer reads `status` as a string but the producer wrote `order_status`, causing a deserialization error or null value.

## Compatibility Levels

Schema Registry enforces **compatibility rules** that determine which schema changes are allowed.

**BACKWARD compatible:** new schema can read data written by the previous schema. Old producers, new consumer works.

```
Previous: { "name": "order_id", "type": "long" }
New:      { "name": "order_id", "type": "long" },
          { "name": "loyalty_tier", "type": ["null", "string"], "default": null }  ← ADDED with default
→ BACKWARD compatible: new consumer reads old messages (loyalty_tier is null — has a default)
```

```
Previous: { "name": "status", "type": "string" }
New:      remove "status" field
→ NOT backward compatible: new consumer cannot find status field in old messages
```

**FORWARD compatible:** old schema can read data written by the new schema. New producer, old consumer works.

**FULL compatible:** both backward and forward. The strictest — most changes are disallowed.

**Practical rules:**

| Change | Backward | Forward | Full |
|--------|----------|---------|------|
| Add optional field (with default) | ✅ | ❌ | ❌ |
| Add required field (no default) | ❌ | ❌ | ❌ |
| Remove field | ❌ | ✅ | ❌ |
| Rename field | ❌ | ❌ | ❌ |
| Widen type (INT → LONG) | ✅ | ❌ | ❌ |
| Narrow type (LONG → INT) | ❌ | ✅ | ❌ |

Renaming a field is always breaking under any compatibility mode — the field is removed (old name) and added (new name), which is not compatible either way. The correct approach for renaming: add an alias, migrate consumers, then remove the old name in a later version.

## Data Contracts in Practice

A data contract extends beyond schema to include:

**Structural contract** (what Schema Registry enforces):
- Column names and types
- Nullable vs required
- Default values

**Semantic contract** (what data quality checks enforce):
- Value ranges: `order_total BETWEEN 0 AND 1000000`
- Cardinality: `status IN ('PLACED', 'SHIPPED', 'DELIVERED', 'CANCELLED')`
- Uniqueness: `order_id` is unique per table
- Not-null rate: `customer_id` is never null
- Freshness: table is updated at least once per hour

**SLA contract** (what monitoring enforces):
- Data arrives within 30 minutes of the event occurring at the source
- Row count between 1,000 and 10,000,000 for the daily batch
- No more than 0.1% null rate on `customer_id`

Pravah's data contract concept is implemented across three services:
- **Schema Registry** (via Confluent Schema Registry or the Metadata Service's schema catalog): structural contracts
- **Data Quality Framework** (Chapter 8.7): semantic contracts, run as a validation step in the pipeline
- **Observability** (Phase 4): SLA contracts, enforced via Prometheus alerts

## Schema Drift Detection in Pravah

When a source schema changes without updating the pipeline contract, it is **schema drift**. Pravah detects drift in two ways:

**1. From Debezium DDL events (CDC sources):**

Debezium emits a schema change event when the source database schema changes. The Connect Service forwards this to the `schema.drift.detected` Kafka topic.

**2. From OpenLineage events (batch sources):**

When the runner reads from a JDBC source, it captures the current schema from the JDBC metadata and includes it in the OpenLineage event. The Metadata Service compares the reported schema against the last-known schema. If they differ, it publishes `schema.drift.detected`.

```java
@KafkaListener(topics = "schema.drift.detected")
public void handleSchemaDrift(SchemaDriftEvent event) {
    // Find all pipelines that read from this dataset
    List<Pipeline> affectedPipelines = metadataService
        .findPipelinesUsingDataset(event.getDatasetNamespace(), event.getDatasetName());

    // Notify owners
    for (Pipeline pipeline : affectedPipelines) {
        notificationService.send(Notification.builder()
            .recipient(pipeline.getOwnerEmail())
            .subject("Schema drift detected in " + event.getDatasetName())
            .body(buildDriftNotification(event, pipeline))
            .build());
    }

    // Publish to Agent Service for auto-heal attempt
    agentEventPublisher.publish(AgentEvent.schemaDrift(event, affectedPipelines));
}
```

## Evolving Schemas Safely

When a schema change is required, the safe approach follows a **multi-step migration**:

**Step 1: Add new version alongside old (expand):**
```sql
-- Add new column with a default; keep old column
ALTER TABLE orders ADD COLUMN order_status VARCHAR(50) DEFAULT 'UNKNOWN';
```

**Step 2: Migrate consumers to use new version:**
- Update pipeline transform SQL to read `order_status` instead of `status`
- Test in staging
- Deploy new pipeline version

**Step 3: Backfill old data:**
```sql
UPDATE orders SET order_status = status WHERE order_status = 'UNKNOWN';
```

**Step 4: Remove old version (contract):**
```sql
-- Only after all consumers are confirmed migrated
ALTER TABLE orders DROP COLUMN status;
```

This expand/contract pattern (also called "parallel change") ensures no consumer breaks during the migration. The cost is that the old and new columns coexist temporarily, but this is far better than a breaking change that fails all consumers at midnight.
