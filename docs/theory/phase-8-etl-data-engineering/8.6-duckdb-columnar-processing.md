# 8.6 DuckDB & Columnar Processing

## Why Columnar Matters for Analytics

Traditional OLTP databases (PostgreSQL, MySQL) store data **row by row** on disk. A full row is a contiguous unit:

```
Row storage:
  [order_id=1][customer_id=100][email="a@b.com"][revenue=150.00][status="PLACED"]
  [order_id=2][customer_id=101][email="c@d.com"][revenue=200.00][status="SHIPPED"]
  ...
```

For transactional workloads, this is efficient: `SELECT * FROM orders WHERE order_id = 1` reads one row and returns all its columns.

For analytical workloads, this is deeply inefficient. Consider:

```sql
SELECT SUM(revenue) FROM orders WHERE status = 'PLACED'
```

To compute this, the database must:
1. Read EVERY row (billions of rows in a large orders table)
2. From each row, extract only `revenue` and `status` (2 of 50 columns)
3. Filter where `status = 'PLACED'`
4. Sum the `revenue` values

In row storage, reading 2 columns requires reading all 50 columns for every row — **48 columns of wasted I/O per row**. For a 100GB table with 50 columns, computing this aggregate reads 100GB when only 4GB of relevant column data exists.

**Columnar storage** stores each column separately:

```
Column storage:
  revenue:  [150.00, 200.00, 75.00, ...]
  status:   ["PLACED", "SHIPPED", "PLACED", ...]
  order_id: [1, 2, 3, ...]
  ...
```

The same query reads only the `revenue` and `status` columns — 2 columns instead of 50. I/O is reduced by 96%. Combined with SIMD instructions that operate on 512 values simultaneously, analytical queries run 10–100× faster than in row-based systems.

## DuckDB's Execution Engine

DuckDB is a columnar, in-process analytical database. Its execution engine is **vectorized**: instead of processing one row at a time (like PostgreSQL's executor), it processes a **vector** of values (typically 1024–4096 rows) through each operator in a single pass.

```
Input batch: 2048 revenue values as a contiguous float64 array
SUM operator: SIMD instruction adds 8 values per clock cycle
→ 2048/8 = 256 SIMD operations to sum 2048 values
```

This is why DuckDB can sum 1 billion rows in seconds on a single CPU core.

**Pipeline execution model:**

DuckDB uses a **morsel-driven parallelism** model for multi-core execution. The query is divided into "morsels" (chunks of input data), each processed independently by a thread. No global synchronization between threads within a phase — each thread pulls the next morsel when it finishes the current one.

```
Query: SELECT AVG(revenue) FROM orders WHERE status = 'PLACED'

Thread 1: processes rows 0–4095 → partial sum + count
Thread 2: processes rows 4096–8191 → partial sum + count
Thread 3: processes rows 8192–12287 → partial sum + count
...
Combiner: sums all partial results → final AVG
```

On a 16-core machine, this achieves near-linear speedup for aggregation queries over large datasets.

## Parquet: The Columnar File Format

Parquet is the standard on-disk columnar file format, used by DuckDB, Spark, and virtually every modern data processing system.

**Parquet file structure:**

```
Parquet file
├── Row Group 1 (128MB, rows 0–500,000)
│   ├── Column chunk: order_id      [values, statistics: min=1, max=500000]
│   ├── Column chunk: revenue       [values, statistics: min=0.01, max=99999.99]
│   └── Column chunk: status        [dictionary encoded: PLACED=0, SHIPPED=1, ...]
├── Row Group 2 (128MB, rows 500,001–1,000,000)
│   └── ...
└── Footer: schema + row group metadata (min/max per column per row group)
```

**Predicate pushdown (the killer feature):**

The Parquet footer contains row group statistics (min/max values per column per row group). Before reading any data, a query engine reads the footer and skips row groups that cannot possibly contain matching rows:

```sql
SELECT * FROM orders WHERE revenue > 50000

Row Group 1: revenue stats: min=0.01, max=150.00 → max < 50000 → SKIP (no expensive I/O)
Row Group 2: revenue stats: min=45000, max=99999  → POSSIBLE MATCH → read
Row Group 3: revenue stats: min=0.01, max=25000   → max < 50000 → SKIP
```

This can skip 90%+ of data without reading it — the filter evaluation happens on the footer metadata, not on decompressed column data.

**Compression:**

Parquet supports multiple compression codecs per column:
- `SNAPPY`: fast, moderate compression (~3× for typical data)
- `ZSTD`: slower, better compression (~5× with zstd level 3, up to 10× with level 19)
- `GZIP`: widely compatible, moderate compression

DuckDB defaults to `ZSTD` — best compression-to-speed ratio for Pravah's artifact storage.

**Dictionary encoding:**

Columns with low cardinality (like `status` with values: PLACED, SHIPPED, DELIVERED, CANCELLED) are dictionary-encoded: each unique value is assigned an integer ID, and the column stores the IDs:

```
Dictionary: { PLACED=0, SHIPPED=1, DELIVERED=2, CANCELLED=3 }
Column data: [0, 1, 0, 2, 3, 0, 0, 1, ...]   ← 1 byte per row instead of 9-10 bytes
```

A VARCHAR column with 10-character strings is stored as 1-byte integers — a 10× reduction in column size.

## DuckDB with Apache Arrow

Apache Arrow is an in-memory columnar format — the in-memory equivalent of Parquet. DuckDB uses Arrow as its internal representation for query intermediate results.

**Zero-copy data exchange:** when DuckDB reads a Parquet file, it decompresses column data into Arrow format. When the result is written as a new Parquet file, the Arrow buffers are directly encoded to Parquet without copying. For DuckDB → Pandas → DuckDB pipelines, Arrow enables zero-copy transfers:

```python
# Python: DuckDB reads Parquet → Arrow → Pandas (zero-copy)
import duckdb
import pandas as pd

conn = duckdb.connect()
arrow_table = conn.execute("SELECT * FROM read_parquet('data.parquet')").arrow()
df = arrow_table.to_pandas()  # zero-copy conversion via Arrow

# DuckDB can also read from Pandas directly (zero-copy in reverse)
conn.execute("SELECT AVG(revenue) FROM df WHERE status = 'PLACED'")
```

In Pravah's Java runner, Arrow is used for the internal representation of query results when passing data between pipeline steps in memory — avoiding serialization overhead.

## Larger-Than-Memory Processing

DuckDB handles datasets that exceed available RAM through **spill-to-disk**:

```java
conn.execute("SET memory_limit = '4GB'");
conn.execute("SET temp_directory = '/tmp/duckdb-spill'");

// Query that requires 40GB intermediate state → spills 36GB to /tmp
conn.execute("""
    SELECT customer_id, SUM(revenue) AS total_revenue
    FROM read_parquet('s3://data/orders/*.parquet')
    GROUP BY customer_id
""");
```

When the in-memory aggregation hash table fills the 4GB limit, DuckDB serializes partial aggregates to the temp directory (in columnar format) and continues processing. When the input is exhausted, it merges the partial results from disk — an external merge sort/aggregation pattern.

**Performance profile:**
- Fully in-memory: 1× speed (baseline)
- Spilling to NVMe SSD: 3–5× slower
- Spilling to spinning disk: 20–50× slower

The runner's temp directory must be on fast local storage (NVMe SSD). For queries known to require large intermediate state, allocate sufficient memory to the runner pod to minimize spilling.

## DuckDB's S3 Integration

DuckDB's `httpfs` extension allows reading and writing Parquet files directly on S3-compatible storage (including MinIO):

```sql
-- Configure MinIO access
SET s3_endpoint = 'minio.pravah.svc.cluster.local:9000';
SET s3_url_style = 'path';
SET s3_access_key_id = '...';        -- from pre-signed token
SET s3_secret_access_key = '...';

-- Read previous step's output from MinIO
CREATE TABLE input AS
SELECT * FROM read_parquet('s3://pravah-artifacts/tenants/megacorp/executions/exec-abc/steps/extract/output/data.parquet');

-- Write transform output to MinIO
COPY (
    SELECT customer_id, SUM(revenue) AS total_revenue
    FROM input GROUP BY customer_id
) TO 's3://pravah-artifacts/tenants/megacorp/executions/exec-abc/steps/aggregate/output/data.parquet'
(FORMAT PARQUET, COMPRESSION ZSTD, ROW_GROUP_SIZE 100000);
```

DuckDB streams data to/from MinIO in parallel — it doesn't load the entire file into memory before processing. For a 10GB Parquet file, DuckDB reads row groups in parallel across multiple TCP connections, achieving near-network-bandwidth read speeds.

**Key configuration for production:**

```sql
-- Parallel reads: match network bandwidth
SET s3_uploader_max_parts_per_file = 10000;
SET s3_uploader_max_filesize = '5GB';      -- 5GB max single-file upload

-- Row group size: affects parallelism and memory
-- Smaller row groups (50K rows) → more parallelism, better predicate pushdown
-- Larger row groups (500K rows) → less overhead, better compression
-- Default 100K rows is a good balance
```
