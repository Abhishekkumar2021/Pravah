# 8.2 CDC Internals & Debezium

## What Change Data Capture Is

**Change Data Capture (CDC)** is a technique for capturing every row-level change (INSERT, UPDATE, DELETE) in a source database and streaming those changes in real time to downstream consumers.

Traditional ETL approaches extract data via periodic batch queries:
```sql
SELECT * FROM orders WHERE updated_at > :last_run_time
```

This approach has fundamental problems:
- Deletes are invisible (a deleted row has no `updated_at` to query)
- Soft deletes must be implemented specifically to work around this
- The `updated_at` column must exist and be reliably set by the application
- Batch lag: changes from 11:59pm are not visible until the next extraction at midnight

CDC solves all of these by reading from the database's **transaction log** — the same source the database uses for replication. Every committed transaction is a change event, regardless of whether the row has an `updated_at` column.

---

## How PostgreSQL WAL Works for CDC

PostgreSQL's Write-Ahead Log (WAL) is a sequential log of all changes made to the database. It is primarily used for crash recovery (replay WAL to restore committed state after a crash) and streaming replication (replicate WAL to standby nodes).

CDC tools read the same WAL but decode it differently: instead of replaying changes, they decode them into structured change events (INSERT/UPDATE/DELETE with before/after values).

**Logical replication:** PostgreSQL provides logical decoding — a plugin that decodes the binary WAL format into a higher-level logical representation. Two plugins are commonly used:

- `pgoutput` (built-in since PostgreSQL 10): produces logical replication messages in PostgreSQL's own protocol format
- `wal2json` (third-party): produces changes as JSON

Debezium uses `pgoutput` by default — it is production-ready and maintained by the PostgreSQL core team.

**Setting up logical replication for Debezium:**

```sql
-- WAL level must be 'logical' (default is 'replica')
ALTER SYSTEM SET wal_level = 'logical';
-- Requires PostgreSQL restart

-- Create a replication slot — this is Debezium's read cursor in the WAL
SELECT pg_create_logical_replication_slot('debezium_slot', 'pgoutput');

-- Create a publication — defines which tables to replicate
CREATE PUBLICATION debezium_pub FOR TABLE orders, customers, products;

-- Create a replication user with necessary permissions
CREATE USER debezium REPLICATION LOGIN PASSWORD 'password';
GRANT SELECT ON orders, customers, products TO debezium;
```

**The replication slot is critical:** it guarantees that WAL segments will not be deleted until Debezium has consumed them. If Debezium goes down for maintenance, the replication slot retains the unconsumed WAL. When Debezium restarts, it resumes from exactly where it left off.

**Risk: replication slot lag.** If Debezium is stopped for too long, the retained WAL grows. PostgreSQL disk space fills up because WAL cannot be archived. This is why Debezium must be monitored closely:

```
Alert: replication slot lag > 1GB AND slot inactive > 1 hour
→ Action: restart Debezium connector or drop the slot (with impact assessment)
```

## Debezium Architecture

```
Source PostgreSQL
  → WAL (logical replication stream via pgoutput)
  → Debezium PostgreSQL Connector (deployed as Kafka Connect worker)
  → Kafka topic: {server}.{schema}.{table}
     e.g.: prod-db.public.orders

Downstream consumers:
  → Metadata Service (schema drift detection)
  → Execution Service (pipeline triggers on table changes)
  → DWH loader (real-time replication to Snowflake/BigQuery)
```

**Change event format (Debezium JSON):**

```json
{
  "before": null,
  "after": {
    "order_id": 12345,
    "customer_id": 678,
    "status": "PLACED",
    "created_at": "2026-05-10T09:15:22.000Z"
  },
  "source": {
    "db": "production",
    "table": "orders",
    "lsn": "0/16B374C",
    "ts_ms": 1715335722000,
    "txId": 1234567
  },
  "op": "c",   // c=create, u=update, d=delete, r=read (snapshot)
  "ts_ms": 1715335722150
}
```

For an UPDATE, `before` contains the row state before the update and `after` contains the new state. For DELETE, `before` has the deleted row and `after` is null. For INSERT, `before` is null.

## Initial Snapshot

When Debezium first connects to a new table, it must perform an **initial snapshot** — reading all existing rows to establish a baseline. Without this, downstream consumers only see changes from the moment Debezium started and have no knowledge of existing data.

**Snapshot modes:**

- `initial` (default): read all rows, then stream changes. Suitable for most tables.
- `initial_only`: take snapshot but do not stream changes. For one-time historical loads.
- `never`: skip snapshot, stream only new changes. Suitable when downstream already has historical data.
- `when_needed`: take snapshot if the replication slot doesn't exist. Recovery-focused.

**Snapshot coordination:**

Debezium takes a consistent snapshot by:
1. Acquiring an `ACCESS SHARE` lock on the tables (minimal lock — does not block reads or writes)
2. Reading the current WAL position (LSN) — this is the snapshot boundary
3. Reading all rows with a `SELECT * FROM table`
4. Releasing the lock
5. Beginning to stream WAL changes from the snapshot LSN

Rows inserted after the snapshot's LSN boundary are not in the snapshot data — they appear as INSERT events in the WAL stream. Rows read in the snapshot that were modified after the snapshot boundary appear as UPDATE events. The downstream consumer sees a complete, consistent view.

## Offset Management

Debezium tracks its position in the WAL via **offsets** stored in Kafka. An offset is the LSN (Log Sequence Number) of the last change event Debezium successfully published to Kafka.

On restart, Debezium reads the last committed offset from Kafka Connect's offset topic and resumes streaming from that LSN. This provides at-least-once delivery: in a crash, some events may be re-delivered, but none are lost.

**Exactly-once in CDC (at-least-once + idempotent consumers):**

CDC itself provides at-least-once (duplicate events possible on restart). Downstream consumers must handle duplicates via idempotent processing:

```java
// Consumer: idempotent upsert based on primary key + transaction ID
@KafkaListener(topics = "prod-db.public.orders")
public void handleOrderChange(DebeziumEvent event) {
    if ("d".equals(event.getOp())) {
        orderRepository.deleteById(event.getAfter().get("order_id"));
    } else {
        // UPSERT — idempotent on order_id
        orderRepository.upsert(event.getAfter());
    }
}
```

A duplicate event with the same `order_id` and same data is a no-op under UPSERT semantics.

## Schema Changes (DDL Events)

When the source schema changes (column added, renamed, or removed), Debezium detects the DDL change in the WAL and:
1. Emits a schema change event to the `{server}` topic
2. Updates its internal schema registry
3. Subsequent events use the new schema

```json
// Schema change event
{
  "source": { "db": "production", "table": "orders" },
  "databaseName": "production",
  "schemaName": "public",
  "ddl": "ALTER TABLE orders ADD COLUMN loyalty_tier VARCHAR(50)",
  "tableChanges": [{
    "type": "ALTER",
    "table": "public.orders",
    "columns": {
      "loyalty_tier": { "type": "VARCHAR", "length": 50, "optional": true }
    }
  }]
}
```

In Pravah's Connect Service, schema change events are published to the `schema.drift.detected` Kafka topic. The Metadata Service receives them, updates the schema catalog, and triggers agent notifications about affected pipelines.

## Debezium in Pravah's Connect Service

Pravah's Connect Service is a managed wrapper around Kafka Connect + Debezium. Rather than exposing raw Kafka Connect's REST API, it provides a tenant-aware connector management API:

```
POST /v1/connectors
{
  "name": "orders-cdc",
  "source_type": "POSTGRESQL",
  "connection": {
    "host": "prod-db.megacorp.com",
    "database": "production",
    "tables": ["public.orders", "public.customers"]
  },
  "trigger_pipeline_on_change": "orders-etl"
}
```

The Connect Service:
1. Creates the Kafka Connect connector configuration (with tenant-scoped topic names)
2. Stores connector credentials in Vault (database username/password)
3. Monitors connector health (lag, error events) and exposes metrics
4. Routes schema change events to the Metadata Service
5. Optionally triggers a Pravah pipeline when changes arrive (streaming trigger mode)
