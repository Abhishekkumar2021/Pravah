# 8.1 DAG Engine Design — From Theory to Implementation

## From Graph Theory to Running Code

A Directed Acyclic Graph (DAG) is a graph with directed edges and no cycles. In data engineering, a DAG represents a pipeline where nodes are processing steps and edges represent data dependencies: "step B requires the output of step A."

The academic concept is simple. The engineering challenge is: given a DAG definition at pipeline creation time, how do you reliably determine which steps to run, in which order, with which parallelism, at execution time — across a distributed system where any step can fail at any point?

This chapter walks from the mathematical definition through the concrete implementation decisions required to build ADR-018.

---

## Topological Sort

**Topological sort** orders DAG nodes such that for every edge (A → B), A appears before B in the ordering. This gives a valid sequential execution order where every step runs only after all its dependencies.

```
DAG: extract → validate → transform ──┬──→ load_dw
                                       └──→ load_s3

Topological sort (one valid ordering):
  [extract, validate, transform, load_dw, load_s3]

Another valid ordering:
  [extract, validate, transform, load_s3, load_dw]
  (load_dw and load_s3 have no ordering constraint between them)
```

**Kahn's algorithm** for topological sort:

```java
public List<String> topologicalSort(Map<String, List<String>> graph) {
    // Count in-degrees (number of incoming edges per node)
    Map<String, Integer> inDegree = new HashMap<>();
    for (String node : graph.keySet()) inDegree.put(node, 0);
    for (List<String> successors : graph.values())
        for (String s : successors) inDegree.merge(s, 1, Integer::sum);

    // Start with all nodes that have no prerequisites
    Queue<String> queue = new ArrayDeque<>();
    inDegree.forEach((node, degree) -> { if (degree == 0) queue.add(node); });

    List<String> sorted = new ArrayList<>();
    while (!queue.isEmpty()) {
        String node = queue.poll();
        sorted.add(node);
        // "Remove" this node: decrement in-degree of its successors
        for (String successor : graph.getOrDefault(node, List.of())) {
            inDegree.merge(successor, -1, Integer::sum);
            if (inDegree.get(successor) == 0) queue.add(successor);
        }
    }

    // If sorted.size() < graph.size(): there is a cycle (not all nodes reached)
    if (sorted.size() < graph.keySet().size()) {
        throw new CyclicDependencyException("Pipeline definition contains a cycle");
    }

    return sorted;
}
```

Cycle detection is automatic: if the sort completes with fewer nodes than the graph has, there is a cycle (some nodes' in-degrees never reached zero because they depend on each other).

## From Sequential Sort to Parallel Execution

Topological sort gives a valid sequential order. But the real value of a DAG is **parallelism**: steps with no path between them can run simultaneously.

**Finding parallelism levels:**

```
Level 0 (can start immediately, no dependencies):   [extract]
Level 1 (can start after Level 0 completes):        [validate]
Level 2 (can start after Level 1 completes):        [transform]
Level 3 (can start after Level 2 completes):        [load_dw, load_s3]  ← PARALLEL
Level 4 (can start after Level 3 completes):        [notify]
```

**Algorithm:**

```java
public Map<Integer, List<String>> computeLevels(Map<String, List<String>> dependsOn) {
    Map<String, Integer> level = new HashMap<>();

    // BFS from roots (no dependencies)
    Queue<String> queue = new ArrayDeque<>();
    dependsOn.forEach((node, deps) -> {
        if (deps.isEmpty()) {
            level.put(node, 0);
            queue.add(node);
        }
    });

    while (!queue.isEmpty()) {
        String node = queue.poll();
        int nodeLevel = level.get(node);

        for (String successor : getSuccessors(node, dependsOn)) {
            // Level = max(current level, predecessor_level + 1)
            int newLevel = nodeLevel + 1;
            if (newLevel > level.getOrDefault(successor, -1)) {
                level.put(successor, newLevel);
                queue.add(successor);
            }
        }
    }

    // Group by level
    return level.entrySet().stream()
        .collect(groupingBy(Map.Entry::getValue,
            mapping(Map.Entry::getKey, toList())));
}
```

At Level 3, `load_dw` and `load_s3` are at the same level — they can dispatch simultaneously.

## Event-Driven vs Level-Based Execution

There are two approaches to parallelism in DAG execution:

**Level-based (batch approach)**: execute all steps at Level 0, wait for all to complete, then execute all steps at Level 1, wait, then Level 2...

Problems:
- The slowest step in a level blocks the entire level from advancing
- Fine if levels have similar durations, but in practice they often don't

**Event-driven (individual completion triggers)**: when a step completes, immediately evaluate which new steps have all their prerequisites met and dispatch them.

This is the approach in ADR-018. When `validate` completes, the DAG engine evaluates `transform`: are all of `transform`'s dependencies (just `validate`) SUCCEEDED? Yes → dispatch `transform` immediately, without waiting for anything else.

```java
// Called when any job completes
public void onJobCompleted(String jobId, JobStatus finalStatus) {
    Job job = jobRepository.findById(jobId);

    if (finalStatus == JobStatus.SUCCEEDED) {
        // Find all jobs that depended on this one
        for (Job dependent : findDependents(job.getStepId(), job.getExecutionId())) {
            // Check if ALL of the dependent's prerequisites are SUCCEEDED
            boolean allMet = dependent.getDependsOn().stream()
                .allMatch(depStepId -> isSucceeded(depStepId, job.getExecutionId()));

            if (allMet) {
                dispatch(dependent);    // dispatch immediately
            }
        }
    } else {
        // Step failed — cancel all downstream steps
        cancelDownstream(job.getStepId(), job.getExecutionId());
    }

    // Check if all steps are terminal — execution complete?
    if (isExecutionComplete(job.getExecutionId())) {
        finalizeExecution(job.getExecutionId());
    }
}
```

## Fan-Out and Fan-In

**Fan-out**: one step produces N outputs that feed N parallel steps.
**Fan-in**: N parallel steps must all complete before a downstream step can start.

Fan-in is naturally handled by the dependency check: `notify.dependsOn = [load_dw, load_s3]`. The `onJobCompleted` handler for `load_dw` checks: is `load_s3` also SUCCEEDED? If not, `notify` stays WAITING. When `load_s3` completes, it checks: is `load_dw` SUCCEEDED? Yes → dispatch `notify`.

**Dynamic fan-out (Map step):**

```
pipeline step: process_shards
  type: MAP
  input: ${{ steps.list_shards.output.shard_ids }}  → ["shard-1", "shard-2", "shard-3"]
  child_step: process_single_shard
  parallelism: 5   → max 5 children running at once

At runtime:
  List_shards completes → output: ["shard-1", "shard-2", "shard-3"]
  DAG engine creates 3 child jobs: process_single_shard[shard-1, shard-2, shard-3]
  Dispatches up to 5 simultaneously (respects parallelism limit)

Fan-in: aggregate_results.dependsOn = [MAP:process_shards]
  → wait for ALL child jobs to complete
```

The `MAP:process_shards` dependency means "all children of the MAP step", dynamically resolved at runtime.

## Detecting and Handling Cycles at Runtime

Cycle detection during pipeline save (ADR-018) prevents most cycles. But what about dynamic DAGs where the cycle emerges at runtime (e.g., a Map step whose output creates a dependency back to an ancestor)?

```java
public void validateExecutionDAG(List<Job> jobs) {
    // Build the dependency graph for this execution's runtime DAG
    Map<String, List<String>> graph = jobs.stream()
        .collect(toMap(Job::getStepId, Job::getDependsOn));

    // Run topological sort — throws if cycle detected
    try {
        topologicalSort(graph);
    } catch (CyclicDependencyException e) {
        markExecutionFailed(executionId, "Cyclic dependency detected in DAG at runtime: " + e.getMessage());
    }
}
```

This is called once when the execution is created, before any jobs are dispatched. Runtime-created dynamic DAG cycles fail fast rather than hanging indefinitely.

## Concurrency Limits and Rate Control

Two types of concurrency limits:

**Pipeline-level concurrency limit:** at most N steps running simultaneously per pipeline execution. Controls resource usage per pipeline.

```java
private void dispatchIfAllowed(Job job, Execution execution) {
    long runningCount = jobRepository.countRunningByExecution(execution.getId());
    if (runningCount >= execution.getConcurrencyLimit()) {
        // Do not dispatch — leave in READY state
        // Will be re-evaluated when the next job completes
        return;
    }
    dispatch(job);
}
```

**Step-level rate limit:** some steps read from rate-limited APIs (e.g., Salesforce has API call limits). The step configuration specifies a rate limit:

```json
{
  "step_id": "salesforce_extract",
  "rate_limit": { "max_concurrent": 1, "calls_per_minute": 100 }
}
```

The runner enforces this rate limit internally. The DAG engine only enforces the concurrency limit (max N running across all steps).

## Execution State Persistence

The complete DAG state — which steps are WAITING, READY, RUNNING, SUCCEEDED — lives in PostgreSQL. This makes it durable across Execution Service restarts (ADR-024).

On startup, the Execution Service can reconstruct the complete state of all in-progress executions from the `jobs` table and resume dispatching without replaying events:

```java
// On startup: find all READY jobs and dispatch them
// (they were READY when the service crashed — nothing changed)
List<Job> readyJobs = jobRepository.findByStatusAndTenantId(
    JobStatus.READY, tenantId);
readyJobs.forEach(this::dispatch);

// Find all RUNNING jobs on dead runners (missed heartbeats)
List<Job> orphanedJobs = jobRepository.findRunningOnDeadRunners();
orphanedJobs.forEach(this::markInterruptedAndRequeue);
```

The DAG engine is stateless. All state is in PostgreSQL. Restarts are safe.
