# 1.7 Idempotency & Exactly-Once Semantics

## The Problem

Consider this scenario:

```
Pipeline: Load daily sales data from Postgres → Data Warehouse

t=0    Scheduler assigns Job-X to Runner-001
t=1    Runner-001 starts executing
t=45   Runner-001 finishes loading 1,000,000 rows
t=46   Runner-001 sends "Job Complete" to Scheduler
t=46   Network blip — message is lost

t=76   Scheduler: "No completion after 30s → runner dead?"
t=77   Scheduler reassigns Job-X to Runner-002
t=78   Runner-002 loads the same 1,000,000 rows again

Result in Data Warehouse:
  2,000,000 rows instead of 1,000,000
  Every sale appears twice
  Revenue reports show 2× actual revenue
  Finance team makes wrong decisions
```

This happens because the system is not idempotent.

---

## What Idempotency Means

An operation is idempotent if executing it multiple times produces the same result as executing it once: `f(f(x)) = f(x)`.

| Idempotent | Not Idempotent |
|---|---|
| `SET temperature = 20°C` — do it 10 times, still 20°C | `INCREASE temperature by 1°C` — do it 10 times, get +10°C |
| `PUT /pipelines/123 {name: "sales"}` — do it 5 times, same result | `POST /jobs/trigger` — do it 5 times, 5 jobs created |
| `abs(abs(x)) = abs(x)` | `x + 1` applied twice ≠ once |

---

## The Core Tool: Idempotency Keys

Every operation gets a unique ID. Before executing:
- If the ID has been seen before → return the cached result, do not re-execute
- If the ID is new → execute, store the result with the ID

This transforms any operation into an idempotent one.

**Pravah's idempotency key structure:**

```
{pipeline_id}-{scheduled_time}-{attempt_number}

Example: pipeline-abc123-2024-01-15T10:00:00Z-attempt-1
```

- `pipeline_id` — which pipeline
- `scheduled_time` — which scheduled execution (same pipeline runs daily; each run is distinct)
- `attempt_number` — which retry attempt. Same attempt retried = same key = deduplicated. A new attempt after failure = incremented number = intentionally different execution.

## Idempotency Layer by Layer

Pravah implements idempotency independently at every layer. One weak link breaks the entire guarantee.

```
Layer 1: API Gateway
Layer 2: Scheduler → Kafka  (Outbox Pattern)
Layer 3: Kafka → Execution Service
Layer 4: Execution Service → Runner
Layer 5: Runner → Data Destination
Layer 6: Kafka producer (Exactly-Once API)
```

### Layer 1: API Gateway

Clients triggering pipelines manually may retry on timeout. The gateway deduplicates using a client-provided idempotency key stored in Redis with a 24-hour TTL:

```
Client sends: POST /api/v1/pipelines/abc123/trigger
              Idempotency-Key: client-generated-uuid-here

Gateway:
  Check Redis: "seen this key before?"
  YES → return cached response, do not re-execute ✅
  NO  → forward to service, execute, cache the result
```

The pipeline is triggered exactly once even if the client sends the request ten times.

### Layer 2: Scheduler → Kafka (The Outbox Pattern)

Writing to the database and publishing to Kafka are two separate operations. What if one succeeds and the other does not?

```
Naive approach (broken):
  1. Write job to PostgreSQL ✅
  2. Publish to Kafka 💥 CRASH
     → Job in DB but never executed (silent data loss)

OR:
  1. Publish to Kafka ✅
  2. Write job to PostgreSQL 💥 CRASH
     → Job executing but no tracking record (ghost job)
```

The **Outbox Pattern** solves this by writing both to the database atomically, then relaying to Kafka separately:

```
┌──────────────────────────────────────────────────────┐
│                    PostgreSQL                        │
│                                                      │
│  ┌──────────────────┐   ┌──────────────────────┐   │
│  │    jobs table    │   │    outbox table       │   │
│  │  id: job-xyz     │   │  topic: job.assigned  │   │
│  │  status: PENDING │   │  payload: {job-xyz…}  │   │
│  │  idempotency_key │   │  sent: false          │   │
│  └──────────────────┘   └──────────────────────┘   │
│                                                      │
│  Written in ONE transaction ✅                       │
│  Either both succeed or both fail. No partial state. │
└──────────────────────────────────────────────────────┘
                          │
              Outbox Relay (runs every 100ms)
                          ▼
              ┌───────────────────────────┐
              │          Kafka            │
              │  topic: job.assigned      │
              │  headers:                 │
              │    idempotency: key-123   │
              └───────────────────────────┘
```

If the relay crashes mid-publish, the outbox record remains `sent=false` and is retried. Kafka deduplicates via idempotent producer sequence numbers.

### Layer 3: Kafka Consumer Deduplication

Kafka delivers at-least-once by default. The Execution Service deduplicates using a `processed_messages` table:

```sql
-- Atomically: check, process, and record
BEGIN TRANSACTION;

  INSERT INTO processed_messages (idempotency_key)
  VALUES ('key-123');
  -- Unique constraint violation if duplicate → transaction rolls back

  INSERT INTO job_assignments (job_id, runner_id)
  VALUES ('job-xyz', 'runner-001');

COMMIT;
```

If another consumer attempts to process the same message, the unique constraint violation rolls back the entire transaction — the duplicate is safely rejected.

### Layer 4: Runner Deduplication

Execution Service dispatches jobs to Runners via gRPC. gRPC calls may timeout and be retried. Each job assignment includes:

```protobuf
message JobAssignment {
  string job_id          = 1;
  string idempotency_key = 2;
  int64  fencing_token   = 3;
  int32  attempt_number  = 4;
  string pipeline_config = 5;
}
```

Runner checks its local SQLite database on receipt:

```
Same job_id, same attempt_number:
  → Already running or completed → return current status, do not re-execute ✅

Same job_id, different attempt_number:
  → Intentional retry after failure → cancel previous, start fresh ✅

Different job_id:
  → New job → execute ✅
```

### Layer 5: Data Destination (The Hardest Layer)

Writing to databases and data warehouses is not inherently idempotent. Pravah uses four strategies depending on the destination:

**UPSERT — for databases with a natural primary key:**
```sql
INSERT INTO orders (id, amount, status)
VALUES ('order-123', 500, 'completed')
ON CONFLICT (id) DO UPDATE
  SET amount = EXCLUDED.amount,
      status = EXCLUDED.status;
-- Retry 10 times → same result ✅
```

**Staging table — for large data warehouse batch loads:**
```sql
-- Step 1: Load into a uniquely-named staging table
--         Retry overwrites the same staging table (safe)
INSERT INTO staging_sales_job_xyz_attempt_1 ...

-- Step 2: Atomic MERGE into production
MERGE INTO production_sales AS t
USING staging_sales_job_xyz_attempt_1 AS s
ON t.id = s.id
WHEN MATCHED THEN UPDATE ...
WHEN NOT MATCHED THEN INSERT ...

-- Step 3: Drop staging table
DROP TABLE staging_sales_job_xyz_attempt_1;
```

**Write guard — for streaming destinations:**
Every row is tagged with `{pipeline_id, run_id, row_sequence_number}`. A unique index on these fields causes the database to reject duplicate rows automatically.

**Deterministic object paths — for file destinations:**
```
s3://pravah/pipeline-abc/2024-01-15/output.parquet
```
Retry writes to the exact same path, overwriting the previous (incomplete) file.

## Kafka Exactly-Once API

Kafka provides built-in exactly-once semantics via two mechanisms:

**Idempotent Producer:**
```properties
enable.idempotence=true
acks=all
retries=2147483647
```

Each producer gets a stable Producer ID (PID). Each message gets an auto-incrementing sequence number. The broker tracks `PID → last sequence number` and discards any retried message with a duplicate sequence.

**Kafka Transactions — for consume-process-produce:**

Without transactions, consuming, processing, and producing are three separate steps. A crash between any two leaves the system inconsistent. With transactions:

```java
producer.initTransactions();

try {
    producer.beginTransaction();

    // Consume from topic-A (offset not committed yet)
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));

    // Process and produce to topic-B
    for (ConsumerRecord<String, String> record : records) {
        producer.send(new ProducerRecord<>("topic-B", process(record)));
    }

    // Commit the offset as part of the same transaction
    producer.sendOffsetsToTransaction(currentOffsets, consumer.groupMetadata());

    producer.commitTransaction(); // All or nothing ✅
} catch (Exception e) {
    producer.abortTransaction();
}
```

Consumers must be configured with `isolation.level=read_committed` to only read from committed transactions.

## End-to-End Exactly-Once in Pravah

```
TRIGGER: Cron fires for Pipeline-abc at 10:00

Step 1  Scheduler writes atomically to PostgreSQL:
        BEGIN: INSERT job (status=PENDING) + INSERT outbox (sent=false) COMMIT ✅

Step 2  Outbox relay publishes to Kafka with idempotency_key header.
        Kafka idempotent producer deduplicates any relay retries. ✅

Step 3  Execution Service consumes job.assigned.
        Kafka transaction: consume + insert into processed_messages
        + insert into job_assignments + produce runner.dispatch
        + commit offset → all atomic ✅

Step 4  Runner receives job.
        Checks local SQLite: not seen → record RUNNING, begin execution ✅

Step 5  Runner executes ETL.
        Extract → Transform (DuckDB) → Load via staging table to warehouse ✅

Step 6  Runner sends result via gRPC.
        If network fails → runner retries (same idempotency key).

Step 7  Scheduler receives result.
        Validates fencing token + checksum.
        Idempotency check → if already marked complete, ignore duplicate.
        Marks job COMPLETE, publishes pipeline.completed event ✅

Step 8  Downstream consumers process pipeline.completed via Kafka transaction.
        Notifications, lineage updates, audit records — all exactly-once ✅

RESULT: Job runs exactly once end-to-end,
        even if any individual step retries N times.
```

## Delivery Semantics Comparison

| | At-Most-Once | At-Least-Once | Exactly-Once |
|---|---|---|---|
| Data loss? | Possible | Never | Never |
| Duplicates? | Never | Possible | Never |
| Complexity | Low | Medium | High |
| Performance | Highest | High | Lower |
| Pravah uses for | Runner capability broadcasts | Pipeline events, alerts | Job records, audit logs, data loads |

## System Design Interview Angles

**"How does Pravah ensure a pipeline doesn't load data twice if the runner crashes mid-execution?"**

> Multiple layers working together. Every job has an idempotency key: `pipeline_id + scheduled_time + attempt_number`. The runner checks its local SQLite before starting — same key already in progress or complete means skip. For the data load itself, we use a staging table approach: load into a uniquely named staging table, then atomic MERGE into production. Retry overwrites the same staging table and re-merges — idempotent end to end. Fencing tokens reject results from zombie runners even if the old runner wakes up.

**"Explain the outbox pattern and why Pravah uses it."**

> The outbox pattern solves the dual-write problem: if we write to PostgreSQL and then publish to Kafka separately, a crash between the two leaves the system in an inconsistent state. The outbox pattern writes both the business record and the outbox message in one atomic PostgreSQL transaction. A separate relay process reads unsent outbox messages and publishes to Kafka. If the relay crashes mid-publish, it retries — Kafka deduplicates via idempotent producer sequence numbers. This gives us atomic DB + Kafka without distributed transactions.

**"Can Kafka provide exactly-once semantics? How does Pravah use it?"**

> Yes. Idempotent producers use producer ID and sequence numbers — brokers automatically deduplicate retried messages. For consume-process-produce patterns, Kafka transactions make all three steps atomic. We configure consumers with `isolation.level=read_committed` to only read from committed transactions. Combined, this gives exactly-once semantics across our entire event processing pipeline.

## 📌 Key Takeaways

1. Idempotency = same operation N times equals same as once — achieved with unique keys + deduplication store
2. Every layer must be independently idempotent: API → Kafka → Consumer → Runner → Destination
3. **Outbox pattern** solves the dual-write problem: one atomic DB transaction for both business record and Kafka message
4. **Kafka exactly-once:** idempotent producer deduplicates on the broker; transactions make consume-process-produce atomic
5. **Destination strategies:** UPSERT for databases, staging table for warehouses, deterministic paths for object stores
6. **Exactly-once is expensive** — use only where correctness is critical; use at-least-once with idempotent consumers elsewhere
