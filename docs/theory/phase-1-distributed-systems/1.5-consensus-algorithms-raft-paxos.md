# 1.5 Consensus Algorithms — Raft & Paxos
## 🧩 What Problem Are We Solving?
We've established that Pravah needs:

Exactly one leader at a time
All nodes to agree on the same state
The system to keep working despite failures
But how do multiple nodes actually reach agreement when the network is unreliable and nodes can crash?

This is the consensus problem.

THE CONSENSUS PROBLEM
──────────────────────────────────────────────────────────

Given N nodes, each starting with a value,
consensus requires all of them to:

  Agreement:    All non-faulty nodes decide 
                the SAME value

  Validity:     The decided value was proposed
                by at least one node
                (can't just make up a value)

  Termination:  All non-faulty nodes eventually
                decide a value
                (can't wait forever)

  Fault         Works correctly as long as
  Tolerance:    majority of nodes are alive
Why is this hard?

WHAT MAKES CONSENSUS HARD
──────────────────────────────────────────────────────────

Messages can be:
  → Delayed (network congestion)
  → Lost    (packet drop)
  → Reordered (different network paths)
  → Duplicated (retries)

Nodes can:
  → Crash and restart
  → Be slow (GC pause)
  → Be partitioned from others

You cannot tell the difference between:
  → A node that crashed
  → A node that is very slow
  → A node you lost network to

FLP Impossibility (1985):
  In a fully asynchronous system,
  consensus is IMPOSSIBLE if even
  one node can fail.

So we make practical compromises:
  → Assume partially synchronous network
  → Assume messages eventually arrive
  → Accept bounded time for decisions
📜 Paxos — The Original (But Complex)
Paxos was invented by Leslie Lamport in 1989. It's the theoretical foundation. Understanding it helps understand everything that came after.

The cast of characters:

PAXOS ROLES
────────────────────────────────

Proposer:   Proposes a value to be agreed upon
            (In Pravah: the node trying to become leader)

Acceptor:   Votes on proposals
            (In Pravah: all scheduler nodes)

Learner:    Learns the final agreed value
            (In Pravah: all services that need to know the leader)

Note: In practice, one node plays multiple roles.
Paxos in two phases:

PHASE 1: PREPARE — "Can I propose?"
─────────────────────────────────────────────────────────

Proposer picks a unique proposal number N
(must be higher than any it has used before)

Proposer → ALL Acceptors: "PREPARE(N)"

Each Acceptor responds:
  If N > any prepare it has seen before:
    → "PROMISE: I won't accept proposals < N"
    → "Here's the highest proposal I already accepted (if any)"
  Else:
    → Ignore or reject

VISUAL:
────────

         Proposer (Scheduler-2, N=5)
              │
   PREPARE(5) │
    ┌──────────┼──────────┐
    ▼          ▼          ▼
 Accept-1   Accept-2   Accept-3
 "Promise!  "Promise!  "Reject!
  N=5>3"    N=5>3"     N=5<7"
  ✅         ✅          ❌

Proposer gets 2/3 promises = MAJORITY ✅
Can proceed to Phase 2.
PHASE 2: ACCEPT — "Here's my value"
─────────────────────────────────────────────────────────

Proposer → MAJORITY of Acceptors: "ACCEPT(N, value)"

value = highest previously accepted value from promises
        (or proposer's own value if none received)

Each Acceptor:
  If hasn't promised to ignore N:
    → Accept the value
    → Notify Learners
  Else:
    → Reject

VISUAL:
────────

         Proposer (Scheduler-2, N=5)
              │
  ACCEPT(5,   │  "I am the new leader"
  "Sched-2")  │
    ┌──────────┼──────────┐
    ▼          ▼          ▼
 Accept-1   Accept-2   Accept-3
 "Accepted! "Accepted! (unreachable)
  ✅         ✅          

Majority accepted → CONSENSUS REACHED
Scheduler-2 is the new leader ✅
Why Paxos is hard in practice:

PAXOS PROBLEMS
───────────────────────────────────────────────

1. Dueling proposers:
   Proposer A sends PREPARE(5)
   Proposer B sends PREPARE(6) — invalidates A's promises
   Proposer A sends PREPARE(7) — invalidates B's promises
   → They can fight forever (liveness problem)

2. Multi-Paxos needed for log replication:
   Single Paxos agrees on ONE value.
   We need to agree on a SEQUENCE of values (log entries).
   Multi-Paxos is complex and underspecified.

3. Implementation is extremely hard:
   Lamport himself said:
   "There is only one consensus protocol, and that's Paxos.
    All others are just broken versions of Paxos."
   → Yet Paxos itself is considered too hard to implement correctly.
🚀 Raft — Paxos Made Understandable
Raft was designed in 2013 with one explicit goal: be easier to understand than Paxos while providing the same guarantees.

Used by: etcd (Kubernetes), CockroachDB, TiKV, Consul

Raft decomposes consensus into 3 problems:

RAFT = Leader Election + Log Replication + Safety
──────────────────────────────────────────────────

1. Leader Election:
   Elect one leader, re-elect if it fails

2. Log Replication:
   Leader receives all writes,
   replicates to followers,
   commits when majority acknowledge

3. Safety:
   Ensure committed entries never change
   Only nodes with complete log can become leader
🗳️ Raft Part 1: Leader Election
Node states:

RAFT NODE STATES
─────────────────────────────────────────────────

Every node is always in one of three states:

  ┌────────────┐     times out,     ┌────────────┐
  │            │    starts election  │            │
  │  Follower  │──────────────────► │ Candidate  │
  │            │                    │            │
  └────────────┘                    └────────────┘
        ▲                                 │
        │                                 │ wins
        │ discovers                       │ election
        │ leader or                       ▼
        │ new term                 ┌────────────┐
        │                         │            │
        └─────────────────────────│   Leader   │
                                  │            │
                                  └────────────┘
                                        │
                                        │ discovers
                                        │ higher term
                                        ▼
                                   (→ Follower)
Terms — Raft's logical clock:

RAFT TERMS
───────────────────────────────────────────────────────

Time is divided into TERMS — monotonically increasing integers

  ──────────────────────────────────────────────────────
  Term 1      │ Term 2  │ Term 3       │ Term 4
  Leader: S1  │ S1 fails│ Leader: S2   │ Leader: S3
  ──────────────────────────────────────────────────────

  Each term begins with an election.
  If election succeeds → leader serves for that term.
  If election fails (split vote) → new term immediately.

  Terms act as logical clocks:
    → Old leader has term 3, new network has term 4
    → Old leader immediately steps down (term 3 < 4)
    → Prevents zombie leader problem!
Election process step by step:

RAFT ELECTION — STEP BY STEP
──────────────────────────────────────────────────────────────

Initial state: S1 is leader, S2 and S3 are followers

       S1 (Leader)          S2 (Follower)       S3 (Follower)
            │                     │                    │
            │ Heartbeat ─────────►│                    │
            │ Heartbeat ──────────────────────────────►│
            │                     │                    │
   💥 S1 CRASHES                  │                    │
            │                     │                    │
            │          Election timeout fires          │
            │          (randomized: S2=150ms,          │
            │                       S3=200ms)          │
            │                     │                    │
            │          S2 fires first!                 │
            │                     │                    │
            │          S2 increments term: 1→2         │
            │          S2 votes for itself             │
            │          S2 state: Candidate             │
            │                     │                    │
            │          RequestVote(term=2, S2) ───────►│
            │                     │                    │
            │                     │         S3: "term 2 > my term 1"
            │                     │         "S2's log is up to date"
            │                     │         "I grant vote"
            │                     │                    │
            │          ◄── VoteGranted(term=2) ────────│
            │                     │                    │
            │          S2 has 2/3 votes = MAJORITY     │
            │          S2 becomes LEADER for term 2    │
            │                     │                    │
            │          S2 sends heartbeat ────────────►│
            │          (establishes authority)         │
Why randomized timeouts?

RANDOMIZED ELECTION TIMEOUTS
──────────────────────────────────────────────────────────

Each follower picks a random timeout: 150ms to 300ms

Without randomization:
  All followers timeout at same time
  All become candidates simultaneously
  All vote for themselves
  Nobody gets majority
  Repeat forever → liveness failure!

With randomization:
  S2 times out at 150ms → starts election
  S3 times out at 200ms → sees S2's vote request
  S3 hasn't timed out yet → grants vote to S2
  S2 wins before S3 even becomes candidate

  Random timeout = natural tiebreaker
  Works almost always on first try
📋 Raft Part 2: Log Replication
This is where Raft ensures all nodes have the same sequence of operations.

THE REPLICATED LOG
───────────────────────────────────────────────────────────

Every node maintains an identical log of commands:

  Index:  1        2        3        4        5
          ┌────────┬────────┬────────┬────────┬────────┐
  S1:     │ term1  │ term1  │ term2  │ term2  │ term3  │
  (Lead)  │ job=A  │ job=B  │ job=C  │ job=D  │ job=E  │
          └────────┴────────┴────────┴────────┴────────┘
          ┌────────┬────────┬────────┬────────┐
  S2:     │ term1  │ term1  │ term2  │ term2  │  ← one behind
          │ job=A  │ job=B  │ job=C  │ job=D  │
          └────────┴────────┴────────┴────────┘
          ┌────────┬────────┬────────┬────────┬────────┐
  S3:     │ term1  │ term1  │ term2  │ term2  │ term3  │
          │ job=A  │ job=B  │ job=C  │ job=D  │ job=E  │
          └────────┴────────┴────────┴────────┴────────┘

  Committed = majority have it (S1+S3 have index 5)
  Index 5 is committed even though S2 is behind
How a write gets committed:

RAFT LOG REPLICATION — ONE WRITE
──────────────────────────────────────────────────────────────

Client sends: "Assign Job-X to Runner-001"

Step 1: Client → Leader (S1)
  ─────────────────────────────────
  Client: "Assign Job-X to Runner-001"
  S1: Appends to local log (index 5, term 3)
  S1: NOT committed yet

Step 2: Leader → Followers (AppendEntries RPC)
  ─────────────────────────────────────────────
  S1 ──► S2: AppendEntries(index=5, entry="Job-X→Runner-001")
  S1 ──► S3: AppendEntries(index=5, entry="Job-X→Runner-001")

Step 3: Followers acknowledge
  ─────────────────────────────
  S2: Appends to log → "Success"
  S3: Appends to log → "Success"
  S2 ──► S1: "Acknowledged"
  S3 ──► S1: "Acknowledged"

Step 4: Leader commits
  ───────────────────────────────
  S1: Has majority (S1+S2+S3 = 3/3, needs 2/3)
  S1: Marks index 5 as COMMITTED
  S1: Applies to state machine: "Job-X = Runner-001"
  S1 ──► Client: "SUCCESS"

Step 5: Leader notifies followers of commit
  ──────────────────────────────────────────
  Next heartbeat/AppendEntries carries commitIndex=5
  S2, S3 apply index 5 to their state machines

VISUAL TIMELINE:
─────────────────

         S1 (Leader)     S2 (Follower)    S3 (Follower)
t=0      Receives write
t=1      Appends log[5]
t=2      ──AppendEntries────►  Appends log[5]
         ──AppendEntries───────────────────►  Appends log[5]
t=3      ◄─ Ack ──────────────
         ◄─ Ack ─────────────────────────────
t=4      COMMIT log[5]
         Reply to client ✅
t=5      Next heartbeat carries commitIndex=5
         S2 commits     S3 commits
🛡️ Raft Part 3: Safety
The critical safety property — committed entries are never lost:

LEADER COMPLETENESS PROPERTY
──────────────────────────────────────────────────────────

A node can only become leader if its log contains
ALL committed entries from previous terms.

How enforced during election:
  Candidate sends: RequestVote(term, lastLogIndex, lastLogTerm)

  Voter grants vote ONLY IF:
    candidate's log is "at least as up-to-date" as voter's log

  "More up-to-date" means:
    Higher last log term, OR
    Same last log term but longer log

EXAMPLE:
─────────

  S1 log: [t1:jobA, t1:jobB, t2:jobC]  ← most complete
  S2 log: [t1:jobA, t1:jobB]           ← missing jobC
  S3 log: [t1:jobA, t1:jobB, t2:jobC]  ← complete

  S2 tries to become leader:
    Sends RequestVote with lastLogIndex=2, lastLogTerm=1

  S1 checks: "My last is index=3, term=2. S2's is index=2, term=1"
    "S2 is behind me. I reject."  ❌

  S3 checks: "My last is index=3, term=2. S2's is index=2, term=1"
    "S2 is behind me. I reject."  ❌

  S2 cannot get majority. Cannot become leader.
  jobC can never be lost. ✅

🔢 Quorum — The Magic Number
QUORUM
────────────────────────────────────────────────

Quorum = majority = floor(N/2) + 1

  3 nodes → quorum = 2
  5 nodes → quorum = 3
  7 nodes → quorum = 4

Why majority?

  If we require majority to commit:
    Write quorum = 3/5 nodes
    Read quorum  = 3/5 nodes

  Any read quorum and write quorum MUST overlap
  by at least 1 node.

  That overlapping node has the latest write.
  Reads always see the latest committed value.

PRAVAH KAFKA CLUSTER:
  3 brokers → quorum = 2
  min.insync.replicas = 2
  acks = all

  Write only succeeds when 2/3 brokers confirm.
  Survives 1 broker failure without data loss.
🎯 FAANG Interview Angles
❓ "How does Kafka guarantee message durability
    in Pravah's setup?"

Good answer:
  "Kafka uses Raft-based KRaft mode for metadata.
   For data durability we set replication factor 3,
   min.insync.replicas=2, acks=all. A write is
   only acknowledged to the producer after 2 of 3
   replicas confirm — this is a quorum write.
   We can lose one broker and lose zero messages."

❓ "What happens during a Kafka leader partition
    failover in Pravah?"

Good answer:
  "Kafka uses KRaft for controller election via Raft.
   On leader partition failure, the controller
   elects a new partition leader from in-sync replicas.
   During this window (typically under a second),
   producers get retriable errors. Our pipeline
   execution service uses idempotent producers
   so retries don't duplicate events."

❓ "How many Scheduler instances does Pravah run
    and why that number?"

Good answer:
  "Three instances. Quorum-based thinking —
   we can tolerate one failure while maintaining
   availability. Two instances gives no fault
   tolerance benefit since losing one means losing
   majority. Five would be overkill for our
   current scale and adds unnecessary cost."
## 📌 Key Takeaways
1. Consensus = getting distributed nodes to agree
   on a single value despite failures

2. FLP impossibility: perfect consensus impossible
   in async systems — we make practical compromises

3. Paxos = theoretical foundation, hard to implement
   Raft = practical, understandable, widely used

4. Raft = Leader Election + Log Replication + Safety

5. Leader election uses randomized timeouts
   Terms act as logical clocks (zombie prevention)

6. Quorum = majority = floor(N/2) + 1
   Pravah runs 3 instances everywhere by default

7. Kafka KRaft, etcd, Vault all use Raft internally
   Pravah inherits these guarantees for free
