# 1.5 Consensus Algorithms — Raft & Paxos

## The Consensus Problem

We established that Pravah needs exactly one leader at a time and all nodes to agree on the same state. But how do multiple nodes actually reach agreement when the network is unreliable and nodes can crash?

**Consensus** requires every non-faulty node to agree on a single value, and that value must have been proposed by at least one actual node. Four properties formalize this:

| Property | Requirement |
|---|---|
| **Agreement** | All non-faulty nodes decide the same value |
| **Validity** | The decided value was actually proposed by some node |
| **Termination** | All non-faulty nodes eventually decide (no infinite wait) |
| **Fault tolerance** | Works correctly as long as a majority of nodes are alive |

**Why is consensus hard?** Messages can be delayed, lost, reordered, or duplicated. Nodes can crash, pause (GC), or be temporarily partitioned. Crucially, you cannot tell the difference between a crashed node and a very slow one. The **FLP Impossibility** (1985) proves that perfect consensus is impossible in a fully asynchronous system if even one node can fail — so practical systems assume partially synchronous networks with bounded delays.

---

## Paxos — The Original

Paxos was invented by Leslie Lamport in 1989. It is the theoretical foundation for all modern consensus algorithms.

**Roles:**
- **Proposer** — proposes a value (the node trying to become leader)
- **Acceptor** — votes on proposals (all scheduler nodes)
- **Learner** — reads the final agreed value (all services needing the leader identity)

In practice, one node plays all three roles.

### Phase 1 — Prepare

The proposer picks a unique proposal number `N` (higher than any it has used before) and broadcasts a `PREPARE(N)` to all acceptors.

Each acceptor responds with a **promise** if `N` is higher than any prepare it has seen:
- "I will not accept proposals numbered less than N"
- "Here is the highest-numbered proposal I already accepted, if any"

```
Proposer (Scheduler-2, N=5)
        │
PREPARE(5)
  ┌─────┼──────┐
  ▼     ▼      ▼
A-1   A-2    A-3
"Promise  "Promise  "Reject
 N=5>3"    N=5>3"   N=5<7"
   ✅        ✅        ❌

2/3 promises = majority → proceed to Phase 2
```

### Phase 2 — Accept

The proposer sends `ACCEPT(N, value)` to a majority. The `value` is taken from the highest-numbered accepted proposal received in Phase 1 (or the proposer's own value if none was reported).

```
Proposer (Scheduler-2, N=5)
        │
ACCEPT(5, "Sched-2 is leader")
  ┌─────┼──────┐
  ▼     ▼      ▼
A-1   A-2    A-3
"Accepted" "Accepted" (unreachable)
  ✅         ✅

Majority accepted → Scheduler-2 is the leader ✅
```

### Why Paxos Is Hard in Practice

- **Dueling proposers:** Two proposers can keep invalidating each other's prepare rounds indefinitely — a liveness problem
- **Multi-Paxos underspecified:** Single Paxos agrees on one value; a replicated log requires a sequence of values, and Lamport underspecified how to extend it
- **Implementation complexity:** Correctly handling all edge cases is notoriously difficult

## Raft — Paxos Made Understandable

Raft was designed in 2013 with one explicit goal: be easier to understand than Paxos while providing identical guarantees. It decomposes the problem into three sub-problems:

```
Raft = Leader Election + Log Replication + Safety
```

Used by: etcd (Kubernetes), CockroachDB, Consul, HashiCorp Vault, Kafka KRaft.

---

### Part 1: Leader Election

**Node states:**

```
              times out, starts election
                        │
  ┌──────────┐          ▼          ┌──────────┐
  │ Follower │──────────────────► │Candidate │
  │          │◄─────────────────── │          │
  └──────────┘  discovers leader   └──────────┘
       ▲         or higher term          │
       │                                 │ wins
       │                                 ▼
       │                          ┌──────────┐
       └──────────────────────────│  Leader  │
            discovers higher term └──────────┘
```

**Terms — Raft's logical clock:**

Time is divided into monotonically increasing terms. Each term begins with an election. If the election succeeds, the winner leads for that term. If it fails (split vote), a new term starts immediately. A node that sees a message from a higher term immediately reverts to follower — this prevents zombie leaders without fencing tokens.

```
  ──────────────────────────────────────────────────────
  Term 1        │ Term 2  │ Term 3        │ Term 4
  Leader: S1    │ S1 fails│ Leader: S2    │ Leader: S3
  ──────────────────────────────────────────────────────
```

**Election step by step:**

```
S1 is leader, S2 and S3 are followers.

S1 💥 CRASHES

Followers have randomized election timeouts (150–300ms):
  S2 timeout: 150ms → fires first
  S3 timeout: 200ms → not yet fired

S2:
  Increments term: 1 → 2
  Votes for itself
  Sends RequestVote(term=2, lastLogIndex, lastLogTerm) to S3

S3:
  "Term 2 > my term 1. S2's log is up to date. Granting vote."
  → VoteGranted(term=2)

S2 has 2/3 votes = majority → S2 becomes LEADER for term 2
S2 immediately sends heartbeat to S3 to establish authority
```

**Why randomized timeouts?** Without randomization, all followers fire at the same time, all vote for themselves, and nobody gets a majority. Randomization creates a natural tiebreaker — the first to fire almost always wins before others even become candidates.

---

### Part 2: Log Replication

Every node maintains an identical log of commands. The leader receives all writes, replicates to followers, and commits when a majority acknowledge.

```
Index:  1        2        3        4        5
        ┌────────┬────────┬────────┬────────┬────────┐
S1(L):  │ t1:A   │ t1:B   │ t2:C   │ t2:D   │ t3:E   │ ← committed
        └────────┴────────┴────────┴────────┴────────┘
        ┌────────┬────────┬────────┬────────┐
S2:     │ t1:A   │ t1:B   │ t2:C   │ t2:D   │          ← one behind
        └────────┴────────┴────────┴────────┘
        ┌────────┬────────┬────────┬────────┬────────┐
S3:     │ t1:A   │ t1:B   │ t2:C   │ t2:D   │ t3:E   │ ← committed
        └────────┴────────┴────────┴────────┴────────┘
```

Index 5 is committed because S1 + S3 = majority, even though S2 is behind.

**How a write commits:**

```
Step 1  Client → S1 (Leader)
        "Assign Job-X to Runner-001"
        S1 appends to local log at index 5. Not committed yet.

Step 2  S1 → S2, S3: AppendEntries(index=5, entry="Job-X→Runner-001")

Step 3  S2, S3 append to their logs → "Acknowledged"

Step 4  S1 has majority (3/3). Marks index 5 COMMITTED.
        Applies to state machine. Replies to client: SUCCESS ✅

Step 5  Next heartbeat carries commitIndex=5.
        S2 and S3 apply index 5 to their state machines.
```

---

### Part 3: Safety

**Leader Completeness Property:** A node can only become leader if its log contains all committed entries from previous terms.

During an election, a candidate sends its `lastLogIndex` and `lastLogTerm`. A voter grants its vote only if the candidate's log is "at least as up-to-date" — defined as: higher last log term, or equal term but longer log.

```
S1 log: [t1:A, t1:B, t2:C]  ← most complete
S2 log: [t1:A, t1:B]        ← missing entry C
S3 log: [t1:A, t1:B, t2:C]  ← complete

S2 tries to become leader. Sends: lastLogIndex=2, lastLogTerm=1

S1 checks: "My last is index=3, term=2. S2 is behind. REJECT." ❌
S3 checks: "My last is index=3, term=2. S2 is behind. REJECT." ❌

S2 cannot get majority. Cannot become leader.
Entry C is safe — it can never be lost. ✅
```

## Paxos vs Raft

| Property | Paxos | Raft |
|---|---|---|
| Understandability | Very hard | Designed for understandability |
| Leader | Any node can propose | Strong leader — all writes go through leader |
| Log replication | Underspecified in basic Paxos | Explicitly defined |
| Used in production | Google Chubby, Spanner | etcd, Consul, CockroachDB, Kafka KRaft |
| Safety guarantees | Identical | Identical |

Both tolerate up to ⌊(N−1)/2⌋ failures: 3 nodes → 1 failure, 5 nodes → 2 failures.

---

## Quorum — The Magic Number

```
Quorum = floor(N/2) + 1

  3 nodes → quorum = 2
  5 nodes → quorum = 3
  7 nodes → quorum = 4
```

Any write quorum and read quorum must overlap by at least one node — that overlapping node always holds the latest write. This guarantees reads never miss a committed value.

Pravah Kafka cluster: 3 brokers, `min.insync.replicas=2`, `acks=all`. A write only succeeds when 2 of 3 brokers confirm — survives one broker failure with zero data loss.

## FAANG Interview Angles

**"How does Kafka guarantee message durability in Pravah?"**

> Kafka uses KRaft (Raft-based) for controller metadata. For data durability, replication factor 3, `min.insync.replicas=2`, `acks=all`. A write is acknowledged only after 2 of 3 replicas confirm — quorum write. We can lose one broker with zero message loss.

**"What happens during a Kafka partition leader failover?"**

> The KRaft controller detects the leader failure and elects a new partition leader from the in-sync replicas. During the brief window (typically under a second), producers receive retriable errors. Our execution service uses idempotent producers, so retries produce no duplicate events.

**"How many Scheduler instances does Pravah run and why?"**

> Three. Quorum thinking — we tolerate one failure while maintaining availability. Two instances provide no fault tolerance benefit since losing one would mean losing majority. Five would be overkill for our scale and adds unnecessary coordination overhead.

---

## 📌 Key Takeaways

1. Consensus = getting distributed nodes to agree on a single value despite failures
2. FLP impossibility means perfect consensus cannot exist in async systems — we make practical trade-offs
3. Paxos = theoretical foundation, extremely hard to implement correctly
4. Raft = practical, understandable, widely deployed — Leader Election + Log Replication + Safety
5. Randomized election timeouts create natural tiebreakers; terms act as logical clocks
6. Quorum = majority = ⌊N/2⌋ + 1; Pravah defaults to 3 instances everywhere
7. Kafka KRaft, etcd, and Vault all use Raft internally — Pravah inherits these guarantees
