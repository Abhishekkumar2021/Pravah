# 1.1 CAP Theorem & How Pravah Makes Consistency Choices

## Why Building Pravah Is Hard

When Pravah runs on a single machine, life is simple:

```
┌───────────────────────────────┐
│        Single Machine         │
│                               │
│  User ──► App ──► Database    │
│                               │
│  Write "Pipeline X = RUNNING" │
│  Read  "Pipeline X = RUNNING" │
│                               │
│  ✅ Always correct            │
│  ✅ Always available          │
│  ✅ Always fast               │
└───────────────────────────────┘
```

One machine, one truth. But Pravah cannot run on a single machine in production:

| Single Machine Problem | Pravah's Reality |
|---|---|
| If it crashes, everything goes down | Must survive node failures |
| Can't handle 10,000 concurrent pipelines | Must scale horizontally |
| One datacenter = single point of failure | Must run across regions for enterprise clients |

The moment you split across multiple machines, the CAP Theorem applies.

---

## The CAP Theorem

CAP states that a distributed system can guarantee **at most two** of these three properties simultaneously:

```
              Consistency
                   △
                  /|\
                 / | \
                /CP|CA \
               /   |   \
              /    |    \
             △─────────△
       Availability   Partition
                      Tolerance
```

- **C — Consistency:** Every node returns the same, most recent data. If you write to Node A, reading from Node B immediately after returns that write.
- **A — Availability:** Every request gets a response — never a timeout, never an error.
- **P — Partition Tolerance:** The system keeps working even when the network between nodes breaks.

---

## Why P Is Not Optional

A **network partition** is when nodes can no longer communicate:

```
NORMAL STATE
─────────────────────────────────────────
[Scheduler] ──────── [Runner Registry]
     │                       │
     └────── [Job Store] ────┘

✅ All nodes connected · Writes replicate instantly

PARTITION — network cut
─────────────────────────────────────────
[Scheduler]    ✕✕✕✕    [Runner Registry]
     │          ↑              │
     │     Network cut         │
     └──[Job Store]            ✕
```

Partitions happen because of:
- Network cable failures
- Kubernetes pod restarts
- Cloud provider outages
- Even high latency (looks identical to a partition)

If you opt out of P, it means: **when the network breaks, the system shuts down entirely.** For Pravah that means all pipelines stop and all runners disconnect. That is unacceptable for enterprise clients.

**P is mandatory. The real question is: when a partition happens, do you sacrifice C or A?**

---

## CP vs AP — The Real Trade-off

Consider this Pravah scenario:

> Runner Registry has two nodes: A and B. Runner `pravah-runner-001` registered on Node A. A network partition happens. User queries Node B: "Is runner-001 alive?"

**If Pravah chooses CP (Consistency over Availability):**

```
Node B: "I can't reach Node A to verify."
        "I refuse to return a potentially wrong answer."
        "Returning: 503 Service Unavailable"

Result: ✅ Data is never wrong · ❌ System is unavailable during partition
```

**If Pravah chooses AP (Availability over Consistency):**

```
Node B: "I can't reach Node A."
        "I'll serve what I last knew."
        "Runner-001 status: UNKNOWN (may be stale)"

Result: ✅ System stays up · ❌ Answer may be temporarily stale
```

Neither is universally right. The correct choice depends on **what the data is used for**.

---

## Pravah's CAP Decisions — Component by Component

Good system design means making different CAP choices per component, not a single global choice:

| Component | Choice | Reasoning |
|---|:---:|---|
| Pipeline definitions (PostgreSQL primary) | **CP** | Executing the wrong pipeline version = data corruption |
| Job run status (Redis cache) | **AP** | Stale UI status for 30s is fine; erroring is not |
| Runner heartbeats (Redis) | **AP** | ~30s of staleness is operationally acceptable |
| Secret store (HashiCorp Vault) | **CP** | Stale credentials = broken or insecure pipelines |
| Kafka event log | **CP** | Event ordering and durability are non-negotiable |
| Data catalog (Elasticsearch) | **AP** | Stale metadata is annoying, not catastrophic |
| Scheduler leader election (Redis lock) | **CP** | Two schedulers both thinking they're leader = chaos |
| Audit logs (PostgreSQL) | **CP** | Compliance requires complete, accurate records |

The mental model: **pipeline config is like a hospital record (CP), job status on a dashboard is like a news website view count (AP).**

## How Senior Interviewers Test This

They never ask "explain the CAP theorem." They make it concrete:

**"What happens to Pravah's scheduler if the database becomes unreachable?"**

> Scheduler Service is CP — it stops dispatching new jobs rather than risk dispatching based on stale pipeline config. Already-running jobs continue via runner-side checkpointing. The on-call alert fires immediately.

**"Two scheduler instances both think they're the leader — what happens?"**

> This is the split-brain problem during a network partition. We prevent it with Redis distributed lock + fencing tokens. Only the instance that holds the lock dispatches jobs. Covered in detail in 1.4.

**"Your UI shows a pipeline as RUNNING but the runner crashed 2 minutes ago — why?"**

> Job status cache in Redis is AP. It serves last-known state during a partition. The reconciliation loop detects missed heartbeats within 30s and transitions the job to FAILED. This is an intentional trade-off: UI availability over perfect real-time accuracy.

---

## 📌 Key Takeaways

1. **Network partitions are inevitable in production** — P is not optional
2. **The real choice is CP vs AP**, made independently per component
3. **No distributed system is purely CP or purely AP** — Pravah uses both
4. **CP = correctness over availability** (stop serving rather than serve wrong data)
5. **AP = availability over correctness** (serve stale data rather than return errors)
