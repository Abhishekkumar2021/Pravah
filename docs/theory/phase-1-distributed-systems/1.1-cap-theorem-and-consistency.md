1.2 Consistency Models — Strong, Sequential, Causal, Eventual
🧩 Why Consistency Models Exist
In 1.1 we learned CAP says "choose consistency or availability."

But consistency is not binary. It's a spectrum:

Each level makes a different promise about what you'll read after a write. Let's understand each one deeply.

1️⃣ Linearizability (Strongest)
The promise:

Once a write completes, every subsequent read — from any node, by any client — sees that write. The system behaves as if there's only one copy of the data.

Visual:

TIMELINE
─────────────────────────────────────────────────────────

Client A writes:  Pipeline X = RUNNING
                  ──────┤ write completes
                        │
                        ▼
                  ┌─────────────┐
                  │ Write done  │
                  └─────────────┘
                        │
Client B reads:         ├──► Node 1: Pipeline X = RUNNING ✅
Client C reads:         ├──► Node 2: Pipeline X = RUNNING ✅
Client D reads:         └──► Node 3: Pipeline X = RUNNING ✅

Every node immediately reflects the write.
No node ever returns old value after write completes.
Real world analogy:

ATM Machine
───────────
You deposit ₹10,000 at ATM in Mumbai.
Walk to ATM next door in same building.
Check balance → shows ₹10,000 added.

The world has ONE truth about your balance.
This is linearizability.
The cost:

To achieve this, nodes must coordinate
BEFORE confirming a write:

Client ──► Node A: "Write Pipeline X = RUNNING"
Node A ──► Node B: "Confirm you got this"
Node A ──► Node C: "Confirm you got this"
Node B ──► Node A: "Confirmed"
Node C ──► Node A: "Confirmed"
Node A ──► Client: "Write successful"

Every write = multiple network round trips
= HIGH LATENCY
= LOW THROUGHPUT
Where Pravah uses it:

┌────────────────────────────────────────────────────┐
│  Pipeline version being executed                   │
│  → Must be exact same version on all schedulers   │
│                                                    │
│  Leader election result                            │
│  → All nodes must agree on exactly one leader     │
│                                                    │
│  Secret values from Vault                          │
│  → All services must read same credentials        │
└────────────────────────────────────────────────────┘
2️⃣ Sequential Consistency
The promise:

All operations appear to execute in some sequential order, and that order is the same for all nodes. But the order doesn't have to match real-world time.

This is subtle — let's see it visually:

REAL WORLD TIME ──────────────────────────────────►

Client A:  Write X=1 ──────────────────────────────
Client B:             Write X=2 ───────────────────

LINEARIZABLE view (must match real time):
─────────────────────────────────────────
All nodes see:  X=1 then X=2  ✅ (matches real time order)

SEQUENTIAL CONSISTENT view (order can differ from real time):
──────────────────────────────────────────────────────────────
All nodes see:  X=2 then X=1  ✅ (different from real time BUT
                                  all nodes see SAME order)

Node 1: X=2, X=1  ✅
Node 2: X=2, X=1  ✅  ← all agree on same sequence
Node 3: X=2, X=1  ✅

NOT allowed:
Node 1: X=1, X=2  ❌
Node 2: X=2, X=1  ❌  ← nodes disagree on order
Node 3: X=1, X=2  ❌
Real world analogy:

Movie Theatre
─────────────
Everyone in the theatre watches the same film.
The scenes play in the same order for everyone.

But the movie might have been filmed out of order.
(Flashbacks, non-linear storytelling)

Everyone experiences the SAME sequence —
even if it doesn't match when things were filmed.
Where Pravah uses it:

┌────────────────────────────────────────────────────┐
│  Kafka topic consumption within a partition        │
│  → All consumers in a group see events in         │
│    same order, but absolute timestamps may vary   │
│                                                    │
│  Pipeline task execution ordering                  │
│  → Task B always runs after Task A completes,    │
│    even if system clock skew exists               │
└────────────────────────────────────────────────────┘
3️⃣ Causal Consistency
The promise:

Operations that are causally related are seen in the same order by all nodes. Unrelated operations can be seen in any order.

What does "causally related" mean?

CAUSAL RELATIONSHIP
───────────────────

Event B is causally related to Event A if:
  → B happened AFTER A on the same node, OR
  → B happened because of A (A caused B)

Example in Pravah:
  A: User creates Pipeline X
  B: User runs Pipeline X

B is causally dependent on A.
You cannot run something that doesn't exist yet.
Every node must see A before B.

NO CAUSAL RELATIONSHIP
────────────────────────
  A: User updates Pipeline X description
  B: User creates Pipeline Y

These are independent. Different nodes can see
them in different orders. That's fine.
Visual:

CAUSAL CONSISTENCY IN PRAVAH
─────────────────────────────────────────────────────

User actions (causally linked):
  t1: Create Pipeline X    ──────────────────────────
  t2: Add Task to X        ──── (depends on t1) ─────
  t3: Run Pipeline X       ──── (depends on t2) ─────
  t4: View Run Logs        ──── (depends on t3) ─────

Node A sees: t1 → t2 → t3 → t4  ✅
Node B sees: t1 → t2 → t3 → t4  ✅
(causal order preserved everywhere)

Independent actions (no causal link):
  t5: User Z updates their profile
  t6: User Y creates Pipeline W

Node A sees: t5 → t6  ✅
Node B sees: t6 → t5  ✅
(either order is fine — they're unrelated)
Real world analogy:

WhatsApp Group Chat
───────────────────
Rohan: "Did you see Pravah's new feature?" (msg 1)
Priya: "Yes! It's amazing!" (msg 2 — reply to msg 1)

Everyone must see msg 1 before msg 2.
Priya's reply without Rohan's message makes no sense.
This is causal consistency.

But if someone else posts "Good morning everyone!"
at the same time — that's unrelated.
Different phones can show it before or after.
Where Pravah uses it:

┌────────────────────────────────────────────────────┐
│  Pipeline lifecycle events                         │
│  CREATED → CONFIGURED → SCHEDULED → RUNNING       │
│  → Each state causally depends on previous        │
│                                                    │
│  Agent actions                                     │
│  → Agent detects failure THEN suggests fix        │
│  → Fix suggestion must come after failure event   │
│                                                    │
│  Data lineage tracking                             │
│  → Extract event must be recorded before          │
│    Transform event in lineage graph               │
└────────────────────────────────────────────────────┘
4️⃣ Eventual Consistency (Weakest)
The promise:

If no new updates are made, all nodes will eventually converge to the same value. No guarantee on when. No guarantee on what you read in the meantime.

Visual:

EVENTUAL CONSISTENCY TIMELINE
──────────────────────────────────────────────────────────

t=0:  Client writes "Runner-001 tags = [gpu, eu-west]"
      Write goes to Node A

t=1:  Node A has new value    [gpu, eu-west]
      Node B still has old    [gpu]            ← stale
      Node C still has old    [gpu]            ← stale

t=2:  Node A replicates to Node B
      Node A has              [gpu, eu-west]
      Node B has              [gpu, eu-west]   ← caught up
      Node C still has old    [gpu]            ← still stale

t=3:  Node B replicates to Node C
      All nodes:              [gpu, eu-west]   ✅ converged

How long did t=0 to t=3 take?
  Could be milliseconds.
  Could be seconds.
  Could be minutes if network is congested.
  System makes NO promise.
Real world analogy:

DNS Propagation
───────────────
You update your domain's IP address.
→ Your laptop resolves new IP immediately
→ Your colleague's laptop still gets old IP
→ Someone in another country gets old IP

Eventually (hours later) everyone gets new IP.
This is eventual consistency.

In Pravah terms:
You update a runner's capability tags.
Different scheduler instances may see different
tags for a short window. Eventually all agree.

🔄 How They Relate to CAP
CAP → Consistency choice maps to models like this:

CP systems tend to offer:
  → Linearizability (strongest)
  → Sequential Consistency

AP systems tend to offer:
  → Causal Consistency
  → Eventual Consistency

Pravah uses CP databases (PostgreSQL) for
linearizable data, and AP stores (Redis,
Elasticsearch) for eventual/causal data.

🎯 FAANG Interview Angles
❓ "How does Pravah ensure a pipeline isn't
    run with a stale configuration?"

Good answer:
  "Pipeline definitions are read with linearizable
   consistency from PostgreSQL primary. We never
   read from replicas for execution-critical config.
   This ensures the scheduler always has the exact
   current version before dispatching a job."

❓ "A runner's tags were updated — could a job
    get assigned to a runner missing a required tag?"

Good answer:
  "Yes, briefly. Runner tags use eventual consistency
   in Redis. There's a short window where a scheduler
   instance might use stale tags. We mitigate this
   with runner-side capability validation — the runner
   rejects jobs it can't handle and the scheduler
   reassigns. The system self-corrects."

❓ "How do you handle causal ordering of
    pipeline lifecycle events in Kafka?"

Good answer:
  "All lifecycle events for a pipeline are
   published to the same Kafka partition using
   pipeline ID as the partition key. This gives
   us sequential ordering within a pipeline's
   event stream, which is sufficient for causal
   consistency — CREATED always processed before
   RUNNING by all consumers."
📌 Key Takeaways
1. Consistency is a spectrum — not binary

2. Linearizable  → single copy illusion, highest cost
   Sequential    → same order everywhere, relaxed timing
   Causal        → cause before effect, unrelated = free
   Eventual      → converges sometime, cheapest

3. Pravah uses ALL four — different data needs
   different consistency levels

4. Picking the right consistency level per
   component is a core system design skill

5. Stronger consistency = more coordination
   = more latency = lower throughput
