# 1.11 Circuit Breaker, Bulkhead & Backpressure
## 🧩 The Problem: Cascading Failures
Before diving into solutions, understand the failure mode they prevent.

CASCADING FAILURE — HOW PRAVAH DIES WITHOUT THESE PATTERNS
────────────────────────────────────────────────────────────

Normal state:
  Execution Service calls Runner Service
  Runner Service calls Secret Service
  All healthy. Latency: 50ms each.

Step 1: Secret Service slows down
  Database connection pool exhausted.
  Secret Service responses: 50ms → 5000ms

Step 2: Runner Service starts backing up
  Waiting for Secret Service responses.
  Runner Service threads: all blocked waiting.
  Runner Service queue: filling up.
  Runner Service responses: 50ms → 8000ms

Step 3: Execution Service starts backing up
  Waiting for Runner Service responses.
  Execution Service threads: all blocked.
  Execution Service: completely unresponsive.

Step 4: Scheduler cannot dispatch jobs
  Calls Execution Service → timeout.
  Scheduler retries → more load on Execution Service.
  Execution Service gets MORE traffic while already dead.

Step 5: ENTIRE PRAVAH IS DOWN
  One slow database connection pool
  → took down the entire platform
  → thousands of pipelines affected
  → all tenant SLAs breached

VISUAL CASCADE:
────────────────────────────────────────────────────────────

Secret Service (slow DB)
    ↓ slow responses
Runner Service (threads blocked)
    ↓ slow responses  
Execution Service (threads blocked)
    ↓ unresponsive
Scheduler Service (can't dispatch)
    ↓ piles up retries
Everything collapses

This is called a CASCADING FAILURE.
One localized problem → total system death.
Three patterns prevent this:

SOLUTION MAP
────────────────────────────────────────────────────────────

Circuit Breaker → Stops calling a failing service
                  "Fast fail" instead of waiting forever

Bulkhead       → Isolates failure to one compartment
                  One tenant's failure ≠ all tenants fail

Backpressure   → Slow consumer signals slow producer
                  "Stop sending so fast, I can't keep up"
🔌 Pattern 1: Circuit Breaker
REAL WORLD ANALOGY
────────────────────────────────────────────────────────────

Electrical circuit breaker:
  Too much current → breaker trips → circuit opens
  No electricity flows → protects appliances
  You reset it manually or automatically after cooldown

Software circuit breaker:
  Too many failures → breaker opens → stop calling service
  Calls fail fast → protects calling service
  Breaker tests service periodically → closes when healthy

  t=28:  Runner → Secret: "Get creds"
         Circuit breaker intercepts IMMEDIATELY
         Returns: CircuitOpenException("Secret Service unavailable")
         Time taken: 1ms (not 5000ms!)
         
  t=29:  Runner → Secret: "Get creds" → 1ms ❌ (fast fail)

  Not blocked for 5 seconds each call.
  Runner Service stays responsive. ✅

HALF-OPEN STATE (testing):
  t=58:  Cooldown expires
         Circuit moves to HALF-OPEN
         
  t=58:  Runner → Secret: "Get creds" (test call)
         Secret Service DB recovered
         Response: 48ms ✅
         
         ONE success → CLOSE the circuit!

CLOSED STATE (recovered):
  t=59:  Runner → Secret: "Get creds" → 45ms ✅
  t=60:  Runner → Secret: "Get creds" → 50ms ✅
         Normal operation resumed ✅
What Happens When Circuit Is Open?
FALLBACK STRATEGIES IN PRAVAH
────────────────────────────────────────────────────────────

When circuit is OPEN, Pravah doesn't just fail.
It has fallback strategies per service:

Runner Service → Secret Service OPEN:
  Fallback 1: Return CACHED credentials
              (if cached within last 5 minutes)
              Redis: GET runner:creds:pipe-abc
              → serve stale creds (AP choice) ✅
  
  Fallback 2: If no cache → fail job dispatch
              Queue job as PENDING_CREDENTIALS
              Retry when circuit closes ✅

Scheduler → Execution Service OPEN:
  Fallback: Queue dispatch commands in local buffer
            (bounded queue, max 1000 entries)
            Flush when circuit closes ✅

Execution → Notification Service OPEN:
  Fallback: Log notification intent
            Notification Service picks up
            from outbox when it recovers ✅
            (Outbox pattern handles this naturally!)

Agent Service → LLM API OPEN:
  Fallback: Disable AI features gracefully
            Log: "Agent unavailable, manual review needed"
            Alert on-call ✅
            Platform still runs pipelines without AI ✅

KEY PRINCIPLE: Graceful degradation
  Circuit open ≠ complete failure
  Pravah degrades gracefully to reduced functionality
  Core ETL always works even when AI/notifications down

🛡️ Pattern 2: Bulkhead
REAL WORLD ANALOGY
────────────────────────────────────────────────────────────

Ship bulkheads:
  Hull is divided into watertight compartments.
  If one compartment floods → sealed off.
  Other compartments stay dry.
  Ship survives.

Without bulkheads:
  One hole → entire hull floods → ship sinks.

Software bulkheads:
  Resources divided into isolated pools.
  One tenant/service exhausts its pool → sealed off.
  Other tenants/services keep their pools.
  System survives.
The Thread Pool Exhaustion Problem
WITHOUT BULKHEADS — TENANT POLLUTION
────────────────────────────────────────────────────────────

Pravah has 200 threads in Execution Service.
Shared by ALL tenants.

Tenant A runs 1000 pipelines simultaneously (runaway job):
  → Claims 180 threads (all waiting for slow runner)
  → Only 20 threads left

Tenant B tries to run 1 pipeline:
  → Needs 1 thread
  → All 200 are taken!
  → Tenant B's pipeline QUEUED
  → Waits indefinitely

Tenant C, D, E, F all waiting...

ONE tenant's bad behavior
→ ALL tenants' pipelines stalled
→ Mass SLA breaches
→ Enterprise customer complaints
→ Potential contract violations

PRAVAH IS MULTI-TENANT
This is a critical production concern.
Bulkhead Types
TWO TYPES OF BULKHEADS
────────────────────────────────────────────────────────────

TYPE 1: THREAD POOL BULKHEAD
  Each tenant/service gets its own thread pool.
  One pool exhausted → others unaffected.

TYPE 2: SEMAPHORE BULKHEAD
  Limit concurrent calls using semaphore.
  Lighter weight than thread pool.
  Used for non-blocking/async calls.

🌊 Pattern 3: Backpressure
REAL WORLD ANALOGY
────────────────────────────────────────────────────────────

Garden hose with water pressure:
  Water flows at source pressure.
  If you kink the hose → water can't flow fast enough.
  Pressure builds up behind the kink.
  Without pressure release: hose bursts.

With backpressure valve:
  Sensor detects buildup.
  Signals pump to slow down.
  Pump produces less water.
  System stays stable.

In software:
  Consumer processing slower than producer sends.
  Buffer fills up → overflow → data lost.
  OR: unbounded memory → OOM crash.

Backpressure: consumer signals producer to slow down.
Producer slows down. System stays stable.
The Producer-Consumer Speed Mismatch
THE PROBLEM IN PRAVAH
────────────────────────────────────────────────────────────

Scheduler (producer):
  Can trigger 10,000 jobs/minute at midnight
  (all daily pipelines scheduled at midnight)

Execution Service (consumer):
  Can process 1,000 jobs/minute
  (limited by runner capacity)

Without backpressure:
  t=0:00  Scheduler fires 10,000 job events
  t=0:00  Kafka topic: 10,000 messages
  t=0:00  Execution Service starts consuming
  t=1:00  Consumed: 1,000. Remaining: 9,000
  t=2:00  Consumed: 2,000. Remaining: 8,000
  ...
  t=10:00 All consumed — but jobs queued for 10 minutes!
  
  SLA: "Jobs start within 2 minutes of trigger"
  Reality: Jobs starting 10 minutes late ❌
  
  Worse: If Scheduler keeps producing at 10,000/min
  and consumer does 1,000/min:
  → Queue grows forever → OOM → system crash
Backpressure Strategies in Pravah
STRATEGY 1: BOUNDED QUEUES
────────────────────────────────────────────────────────────

Use bounded queues instead of unbounded.
When queue is full → producer must slow down or drop.

  Execution Service internal queue:
    max size: 5,000 jobs
    
  When queue hits 5,000:
    New jobs REJECTED with 429 Too Many Requests
    Scheduler: backs off, retries later
    Queue drains: jobs processed
    Scheduler: resumes sending

STRATEGY 2: KAFKA AS NATURAL BUFFER + CONSUMER LAG SIGNAL
────────────────────────────────────────────────────────────

Kafka naturally buffers between producer and consumer.
Consumer lag (messages behind) = backpressure signal.

  ┌────────────────────────────────────────────────────┐
  │  Kafka Consumer Lag Monitor (Pravah)               │
  │                                                    │
  │  Topic: job.assigned                               │
  │  Consumer Group: execution-service                 │
  │  Lag: 0      → Normal. Scheduler: full speed       │
  │  Lag: 1,000  → Warning. Scheduler: 50% speed       │
  │  Lag: 5,000  → Critical. Scheduler: 10% speed      │
  │  Lag: 10,000 → Emergency. Scheduler: PAUSE         │
  │                                                    │
  │  Scheduler reads lag metric from Kafka             │
  │  Adjusts its dispatch rate dynamically             │
  └────────────────────────────────────────────────────┘

STRATEGY 3: REACTIVE STREAMS (PROJECT REACTOR)
────────────────────────────────────────────────────────────

Spring WebFlux + Project Reactor implement
backpressure at the code level via Reactive Streams.

  // Scheduler emits jobs
  Flux<Job> jobStream = scheduler.getJobStream();
  
  // Execution Service requests only what it can handle
  jobStream
    .onBackpressureBuffer(5000,           // max buffer
      job -> log.warn("Job dropped: {}", job.getId()),
      BufferOverflowStrategy.DROP_OLDEST) // drop oldest if full
    .flatMap(job -> executeJob(job), 50)  // max 50 concurrent
    .subscribe();

  // Consumer tells producer:
  // "Send me 50 at a time. Wait for me to request more."
  // Producer cannot overwhelm consumer.

STRATEGY 4: RATE LIMITING PER TENANT (Token Bucket)
────────────────────────────────────────────────────────────

Each tenant gets a token bucket:
  Enterprise: 100 jobs/minute
  Professional: 20 jobs/minute
  Free: 5 jobs/minute

  Token Bucket Algorithm:
    Bucket capacity: 100 tokens (Enterprise)
    Refill rate: 100 tokens/minute
    Each job costs: 1 token
    
    Tenant triggers 200 jobs in 1 minute:
      First 100: tokens available → dispatch ✅
      Next 100:  bucket empty → 429 Rate Limited ❌
      Next minute: bucket refills → dispatch ✅

TOKEN BUCKET IN PRAVAH (Redis):
  // Check and consume token atomically
  String script = """
    local tokens = redis.call('GET', KEYS[1])
    if tokens == nil then tokens = ARGV[1] end
    if tonumber(tokens) > 0 then
      redis.call('DECR', KEYS[1])
      redis.call('EXPIRE', KEYS[1], 60)
      return 1
    else
      return 0
    end
  """;
  
  Long allowed = redisTemplate.execute(script,
    Collections.singletonList("rate:tenant:" + tenantId),
    String.valueOf(maxTokens)
  );
  
  if (allowed == 0) throw new RateLimitExceededException();
🔗 All Three Patterns Working Together
PRAVAH RESILIENCE STACK — COMPLETE PICTURE
────────────────────────────────────────────────────────────

Incoming request: "Execute job for tenant-megacorp"

Layer 1: RATE LIMITING (Backpressure)
  "Is tenant-megacorp within their quota?"
  YES → proceed
  NO  → 429 response. Stop here. Fast fail.

Layer 2: BULKHEAD
  "Is enterprise-tier thread pool available?"
  YES → claim thread, proceed
  NO  → BulkheadFullException. Return 503. Fast fail.

Layer 3: CIRCUIT BREAKER
  "Is Runner Service circuit CLOSED?"
  CLOSED   → make the call, proceed
  OPEN     → CircuitOpenException, use fallback
  HALF-OPEN → test call, monitor result

Layer 4: TIMEOUT
  "Did Runner Service respond in time?"
  YES → process response
  NO  → TimeoutException, return error, record failure
        (Circuit Breaker counts this as a failure)

Layer 5: RETRY (with backoff)
  "Should we retry this call?"
  Retryable error → wait + retry (max 3 times)
  Non-retryable   → fail immediately

ORDER MATTERS:
  Rate Limit → Bulkhead → Circuit Breaker → Timeout → Retry
  
  Outermost (Rate Limit):
    Cheapest check. Reject early before any resources used.
  
  Innermost (Retry):
    Only retry after passing all outer checks.

RESILIENCE4J COMPOSITION IN PRAVAH:
  
  // Decorates service call with all patterns
  
  CircuitBreaker cb = CircuitBreaker.of("runner-service", config);
  Bulkhead bh = Bulkhead.of("runner-service", bhConfig);
  RateLimiter rl = RateLimiter.of("tenant-rate", rlConfig);
  Retry retry = Retry.of("runner-service", retryConfig);
  
  Supplier<JobResult> decoratedCall = Decorators
    .ofSupplier(() -> runnerService.dispatch(job))
    .withRateLimiter(rl)      // outermost
    .withBulkhead(bh)
    .withCircuitBreaker(cb)
    .withRetry(retry)         // innermost
    .withFallback(
      List.of(CircuitBreakerOpenException.class,
              BulkheadFullException.class),
      ex -> handleFallback(job, ex)
    )
    .decorate();
  
  Try<JobResult> result = Try.ofSupplier(decoratedCall);

🎯 FAANG Interview Angles
❓ "How does Pravah prevent one slow service
    from taking down everything else?"

Good answer:
  "Three layered patterns. Circuit breakers
   detect failure rates — after 50% failures
   in 60 seconds, the breaker opens and calls
   fail fast in 1ms instead of waiting 5 seconds.
   This frees threads immediately.

   Bulkheads give each service destination and
   tenant tier its own isolated thread pool.
   Secret Service slowness exhausts its own pool
   of 30 connections — the 50-connection Runner
   Service pool is completely unaffected.

   Together: no cascading. Failure is contained
   to the failing service and its pool."

❓ "How does Pravah handle a midnight thundering
    herd when 10,000 pipelines all trigger at once?"

Good answer:
  "Multiple layers. First, cron triggers have
   random jitter of ±30 seconds added — spreads
   the burst across a minute. Second, tenant-level
   token bucket rate limiting prevents any single
   tenant from flooding the queue. Third, Kafka
   acts as a natural buffer — consumer lag is
   monitored and when it exceeds 5,000 messages,
   the Scheduler throttles its dispatch rate.
   Finally, Execution Service uses bounded
   reactive streams — it requests only as many
   jobs as it has capacity to handle, exerting
   backpressure upstream."

❓ "What's the difference between circuit breaker
    and bulkhead? Don't they solve the same problem?"

Good answer:
  "They're complementary, not redundant. Circuit
   breaker is temporal — it detects failure over
   time and stops calls to a failing service until
   it recovers. It answers: 'is this service healthy
   right now?'
   
   Bulkhead is spatial — it divides resources into
   isolated pools so one consumer can't starve others.
   It answers: 'can I prevent one bad actor from
   consuming all resources?'
   
   You need both. Circuit breaker open doesn't help
   if a slow-but-not-failing service is still
   consuming all shared threads. Bulkhead alone
   doesn't help if a service starts failing — threads
   still block for timeout duration per call."
## 📌 Key Takeaways
1. Cascading failures: one slow service can kill
   the entire platform without protection patterns

2. Circuit Breaker: CLOSED → OPEN → HALF-OPEN
   Fail fast instead of waiting during failures
   Fallbacks: cache, queue, graceful degradation

3. Bulkhead: isolate resources into compartments
   Thread pool per tenant tier + per destination
   One tenant's misbehavior can't starve others

4. Backpressure: consumer controls producer speed
   Bounded queues, Kafka lag signaling,
   Reactive Streams, token bucket rate limiting

5. Order of decoration:
   Rate Limit → Bulkhead → Circuit Breaker
   → Timeout → Retry

6. All three work together — one pattern alone
   is insufficient for production resilience

7. Monitor everything: circuit state, bulkhead
   availability, consumer lag, token buckets
   → Alert before users feel the pain
