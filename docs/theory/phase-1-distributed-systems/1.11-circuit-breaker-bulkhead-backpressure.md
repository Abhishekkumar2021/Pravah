THE FUNDAMENTAL TENSION
────────────────────────────────────────────────────────────

Pravah needs operations that span multiple services
to be atomic — all succeed or all fail.

Example: Launch a pipeline job
  ✅ Create job record          (Pipeline Service DB)
  ✅ Reserve runner capacity    (Runner Service DB)
  ✅ Deduct billing quota       (Billing Service DB)
  ✅ Publish Kafka event        (Kafka)

If Billing fails after the first two:
  → Job record dangling ❌
  → Runner capacity wasted ❌
  → System inconsistent ❌

The naive engineer says:
  "Use a distributed transaction! 2PC!"

The experienced engineer says:
  "Never. Here's why."
📖 What Is Two-Phase Commit?
TWO-PHASE COMMIT — THE IDEA
────────────────────────────────────────────────────────────

2PC coordinates multiple resource managers
to either ALL commit or ALL abort a transaction.

Three participants:
  Transaction Manager (TM): the coordinator
  Resource Managers (RM):   databases, message brokers
  Application:              the service calling them

TWO PHASES:
  Phase 1: PREPARE   → "Are you ready to commit?"
  Phase 2: COMMIT    → "Everyone commit now"
           or ABORT  → "Everyone rollback now"
Phase 1 — Prepare:

PHASE 1: PREPARE
────────────────────────────────────────────────────────────

Application → TM: "Begin distributed transaction"

TM → Pipeline DB:  "PREPARE"
TM → Runner DB:    "PREPARE"
TM → Billing DB:   "PREPARE"
TM → Kafka:        "PREPARE"

Each Resource Manager:
  1. Performs the operation locally
  2. Writes to a REDO LOG (for recovery)
  3. Acquires LOCKS on affected rows
  4. Responds to TM: READY or ABORT

VISUAL:

        Transaction Manager
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
Pipeline    Runner    Billing
   DB         DB        DB
    │         │         │
"PREPARE"  "PREPARE" "PREPARE"
    │         │         │
    ▼         ▼         ▼
  READY     READY     READY
    │         │         │
    └─────────┴─────────┘
              │
    TM: "All READY → proceed to Phase 2"

STATE AFTER PHASE 1:
  All databases: locks held, redo logs written
  Waiting for Phase 2 instruction
  CANNOT do anything else with locked rows
Phase 2 — Commit:

PHASE 2: COMMIT
────────────────────────────────────────────────────────────

TM received all READY responses:
  TM → Pipeline DB:  "COMMIT"
  TM → Runner DB:    "COMMIT"
  TM → Billing DB:   "COMMIT"
  TM → Kafka:        "COMMIT"

Each Resource Manager:
  1. Makes changes permanent
  2. Releases locks
  3. Acknowledges: COMMITTED

VISUAL:

        Transaction Manager
              │
    COMMIT    │    COMMIT
    ┌─────────┼─────────┐
    ▼         ▼         ▼
Pipeline    Runner    Billing
   DB         DB        DB
    │         │         │
COMMIT     COMMIT    COMMIT
    │         │         │
    ▼         ▼         ▼
 DONE ✅   DONE ✅   DONE ✅
    │         │         │
    └─────────┴─────────┘
              │
    TM: "All COMMITTED ✅"
    Application: "Transaction complete"

IF ANY RM SAID ABORT IN PHASE 1:
  TM → ALL RMs: "ABORT"
  All RMs rollback using redo log
  All locks released
  Transaction fails atomically
💥 Why 2PC Fails in Practice
This is the critical section. Every failure mode.

FAILURE 1: TRANSACTION MANAGER CRASHES AFTER PHASE 1
────────────────────────────────────────────────────────────

t=0:  TM sends PREPARE to all RMs
t=1:  All RMs respond READY
t=2:  All RMs: locks held, waiting for commit...
t=2:  💥 TM CRASHES

      All Resource Managers:
        HOLDING LOCKS
        WAITING FOR PHASE 2
        CANNOT PROCEED
        CANNOT ABORT (didn't get ABORT instruction)
        CANNOT COMMIT (didn't get COMMIT instruction)

      Duration of lockout: UNTIL TM RECOVERS
      
      If TM takes 5 minutes to recover:
        Pipeline DB: locked for 5 minutes
        Runner DB:   locked for 5 minutes
        Billing DB:  locked for 5 minutes

      During this time:
        No other transaction can touch locked rows
        Pravah cannot dispatch ANY jobs
        Total scheduling halt

      This is called the BLOCKING PROBLEM.
      2PC is a BLOCKING PROTOCOL.
      It cannot make progress when coordinator fails.

WHAT THIS MEANS FOR PRAVAH:
  Scheduler crashes during peak hour
  → ALL job dispatching blocked
  → Thousands of pipelines halted
  → Enterprise SLAs breached
  → Unacceptable ❌
FAILURE 2: NETWORK PARTITION DURING PHASE 2
────────────────────────────────────────────────────────────

t=0:  Phase 1 complete. All RMs ready.
t=1:  TM sends COMMIT to all RMs
t=2:  Pipeline DB receives COMMIT → commits ✅
t=2:  Runner DB receives COMMIT → commits ✅
t=2:  Network partition! TM cannot reach Billing DB
t=3:  Billing DB: still waiting, locks held

      TM retries COMMIT to Billing DB...
      Partition lasts 2 minutes...

      State:
        Pipeline DB: COMMITTED (job record created)
        Runner DB:   COMMITTED (runner reserved)
        Billing DB:  LOCKED, UNCOMMITTED, WAITING

      This is PARTIAL COMMIT — the worst state.
      Some databases committed, some didn't.
      System is inconsistent.

      Even when partition heals:
        TM resends COMMIT to Billing DB
        Billing DB commits
        Consistency restored...

      But during those 2 minutes:
        Runner reserved but billing not charged
        If TM had crashed during partition:
          Billing DB might never get COMMIT
          Inconsistency could be PERMANENT
FAILURE 3: RM CRASHES AFTER SENDING READY
────────────────────────────────────────────────────────────

t=0:  Phase 1 begins
t=1:  Pipeline DB: READY ✅
t=2:  Runner DB:   READY ✅
t=3:  Billing DB:  READY ✅ → 💥 CRASHES immediately after
t=4:  TM receives all READY → sends COMMIT
t=5:  Pipeline DB: COMMITS ✅
t=6:  Runner DB:   COMMITS ✅
t=7:  TM → Billing DB: COMMIT (Billing DB is down!)
t=7:  No response...
t=8:  TM retries... retries... retries...

      Billing DB restarts at t=60:
        Checks its log: "I sent READY before crash"
        Contacts TM: "What was the decision?"
        TM: "COMMIT"
        Billing DB commits ✅

      This requires:
        TM to durably log its decision
        RM to contact TM on restart (recovery protocol)
        Both must implement complex recovery logic

      Implementation complexity: VERY HIGH
      Gets worse with every additional RM.
FAILURE 4: HEURISTIC DECISIONS — THE SILENT KILLER
────────────────────────────────────────────────────────────

RM held locks for 10 minutes waiting for TM.
RM administrator decides: "This is too long, unblock it."
RM makes HEURISTIC DECISION: commits or aborts unilaterally.

TM eventually recovers, sends COMMIT.
But RM already aborted heuristically.

Result:
  TM thinks: COMMITTED
  RM actually: ABORTED

HEURISTIC INCONSISTENCY — permanent data corruption.
No automatic recovery possible.
Requires manual intervention to reconcile.

This actually happens in production 2PC systems.
FAILURE 5: PERFORMANCE COLLAPSE UNDER LOAD
────────────────────────────────────────────────────────────

2PC performance characteristics:

  Single DB transaction:
    Lock acquisition:  1ms
    Commit:           2ms
    Total:            3ms

  2PC across 4 resources:
    Phase 1 (4 network round trips):  4 × 10ms = 40ms
    Waiting for all READY:            40ms
    Phase 2 (4 network round trips):  4 × 10ms = 40ms
    Total:                            ~80ms minimum

    With network jitter:             100-500ms typical
    Under high load:                 seconds

  Pravah launches 1,000 jobs/minute:
    With 2PC: 1,000 × 500ms = 500 seconds of lock time
    Concurrency: minimal (rows locked during each 2PC)
    Throughput: collapses completely

    Single DB alternative:
    1,000 × 3ms = 3 seconds of lock time
    167× faster ✅

🔄 Where 2PC Is Acceptable
2PC IS NOT ALWAYS WRONG
────────────────────────────────────────────────────────────

2PC works when:
  1. You control all resource managers
  2. All RMs are in same datacenter (low latency)
  3. Operations are short-lived (ms, not seconds)
  4. High consistency requirement justifies cost

PRAVAH USES 2PC IN ONE PLACE:
  Within a single service, across DB + outbox table.

  Wait — isn't that 2PC?

  NO. That's a LOCAL transaction.
  Both tables are in the SAME PostgreSQL instance.
  PostgreSQL handles atomicity internally.
  No network round trips between participants.
  No external TM needed.
  This is fast and safe. ✅

  BEGIN TRANSACTION;  ← single DB, single TM (Postgres)
    INSERT INTO jobs (...);      ← same DB
    INSERT INTO outbox (...);    ← same DB
  COMMIT;             ← instant, local, no blocking

GENUINE 2PC USE CASES (not in Pravah):
  Banking core systems:
    Debit account A + Credit account B
    Both in same bank's DB cluster
    Strong consistency required
    Short operations (ms)
    Acceptable trade-off ✅

  XA transactions in single datacenter:
    Java EE apps with JTA
    All resources physically co-located
    Operational team can handle blocking
    Legacy systems requiring ACID ✅

INDUSTRY LESSONS ON 2PC
────────────────────────────────────────────────────────────

Google (Spanner):
  Uses TrueTime + Paxos instead of classical 2PC.
  TrueTime gives bounded uncertainty on clocks.
  External consistency without coordinator blocking.
  → Even Google doesn't use classical 2PC at scale.

Amazon (DynamoDB):
  No distributed transactions in original design.
  Added limited transactions in 2018 — only within
  single partition, careful scope.
  → Avoided 2PC entirely for 10+ years.

Netflix:
  "We don't use distributed transactions.
   We use eventual consistency + compensation."
  Chaos Engineering shows 2PC creates correlated
  failures — one coordinator crash = mass outage.

Uber:
  Saga pattern for trip lifecycle.
  Payment + driver assignment + rider notification
  all via sagas, not 2PC.
  Scale: millions of trips/day — 2PC would collapse.

Martin Fowler:
  "Distributed transactions are to be avoided.
   They're complex to implement, slow, and prone
   to failure modes that are difficult to reason about."

CAP Theorem implication:
  2PC requires all participants to be available.
  In a distributed system this violates availability.
  → 2PC chooses CP but with terrible P tolerance.

🎯 FAANG Interview Angles
❓ "Why doesn't Pravah use distributed transactions
    across its microservices?"

Good answer:
  "2PC has three fundamental problems for our
   use case. First, it's blocking — if the
   transaction manager crashes after Phase 1,
   all participants hold locks indefinitely.
   For Pravah's scheduler, this means all job
   dispatching halts until manual recovery.

   Second, performance — 4 services × 2 network
   round trips × 10ms each = 80ms minimum per
   operation vs 3ms for local transactions.
   At 1,000 dispatches/minute this matters.

   Third, partial commits during network partitions
   leave the system in inconsistent state requiring
   complex recovery.

   Instead we use Saga + Outbox + Idempotency.
   Each service commits locally and immediately —
   no cross-service locks. The Saga orchestrator
   provides compensation if steps fail. The Outbox
   pattern guarantees atomic DB + Kafka writes.
   Idempotency keys make retries safe. Together
   they give us eventual consistency with always-
   forward progress and horizontal scalability."

❓ "What is the blocking problem in 2PC
    and why is it dangerous?"

Good answer:
  "After Phase 1, all Resource Managers hold locks
   on their data and wait for the Transaction Manager's
   Phase 2 decision. If the TM crashes at this point,
   all RMs are stuck — they cannot commit (no commit
   instruction), cannot abort (might be the wrong
   decision), and cannot release locks (might corrupt
   the transaction). They must wait until the TM
   recovers.

   In Pravah terms: if the scheduler crashes mid-
   dispatch, all four service databases are locked —
   no other job can be created, no runner can be
   allocated, no billing quota can be deducted. The
   entire platform halts for however long TM recovery
   takes. This is why we use non-blocking alternatives
   like Sagas — they always make forward progress."

❓ "Is there ANY place in Pravah where 2PC is used?"

Good answer:
  "Yes — implicitly, within individual services.
   When the Pipeline Service writes a job record
   and an outbox message in a single PostgreSQL
   transaction, that's a local 2PC managed entirely
   by PostgreSQL internally. Both writes go to the
   same database instance — no network round trips
   between participants, no external coordinator,
   no blocking problem. PostgreSQL's WAL handles
   crash recovery. This is safe and fast because
   all participants are in the same process.
   
   We only avoid DISTRIBUTED 2PC — across network
   boundaries between different services."
📌 Key Takeaways
1. 2PC coordinates multi-resource atomic commits
   via Prepare → Commit/Abort protocol

2. Three fatal flaws for microservices:
   → Blocking: coordinator crash = all services locked
   → Partial commits: partition during Phase 2
   → Performance: N × 2 network round trips

3. Heuristic decisions = silent permanent corruption
   The worst failure mode in distributed systems

4. Pravah's alternative stack:
   Local transactions (fast, ACID per service)
   + Outbox (atomic DB + Kafka)
   + Saga (coordinated multi-service with compensation)
   + Idempotency (safe retries everywhere)
   + Event Sourcing (full history, crash recovery)
   + Circuit Breaker/Bulkhead (failure isolation)
   + Consensus (single leader, no split brain)

5. Local 2PC (within one DB) = fine and used everywhere
   Distributed 2PC (across network) = avoid always

6. Industry consensus: Google, Amazon, Netflix, Uber
   all moved away from distributed transactions
   toward saga-based eventual consistency

1.2  ✅ Consistency Models

     - Sequential: Kafka event ordering within partition
     - Causal: pipeline lifecycle events, lineage
     - Eventual: runner tags, catalog, statistics

1.3  ✅ Distributed Clocks, Ordering & Causality
     - Lamport timestamps: causal ordering, not concurrency
     - Vector clocks: detect causality + concurrency
     - Hybrid Logical Clocks (HLC): Pravah's choice
       (real time + causality for job events)
     - Happens-before relationship
     - Kafka partition key = pipeline_id for ordering

1.4  ✅ Leader Election
     - Redis SET NX PX for scheduler leader election
     - Fencing tokens prevent zombie leaders
     - Follower watches Redis every 1s
     - Leader renews every 3s, TTL = 10s
     - Max failover time: 10 seconds
     - All leader state in shared stores (stateless)

1.5  ✅ Consensus Algorithms (Raft & Paxos)
     - Paxos: theoretical foundation, hard to implement
     - Raft: leader election + log replication + safety
     - Randomized timeouts prevent split votes
     - Terms as logical clocks (zombie prevention)
     - Quorum = floor(N/2) + 1
     - Pravah runs 3 instances everywhere by default
     - Kafka KRaft, etcd, Vault all use Raft internally

1.6  ✅ Failure Modes
     - Crash failures: fail-stop vs fail-recover
     - Byzantine failures: checksums, mTLS, signed tokens
     - Network partitions: CP for control plane,
       AP for runner status display
     - Message loss/duplication: delivery guarantees
     - Timing failures: adaptive timeouts, jitter
     - Failure detector state: ALIVE → SUSPECT → DEAD
       (30s suspect, 60s dead thresholds)
     - Adaptive thresholds under high load

1.7  ✅ Idempotency & Exactly-Once Semantics
     - Idempotency key structure:
       pipeline_id + scheduled_time + attempt_number
     - 6 layers: API → Kafka → Consumer →
       Runner → Destination → Result Store
     - Outbox pattern introduced (detailed in 1.10)
     - Kafka: idempotent producer + transactions
     - Destination strategies:
       UPSERT (DB), staging table (DWH),
       deterministic paths (S3)
     - At-most-once / at-least-once / exactly-once
       mapped to Pravah use cases

1.8  ✅ Saga Pattern
     - 2PC problems: blocking, partial commits,
       performance collapse
     - Saga = local transactions + compensating actions
     - Choreography vs Orchestration
     - Pravah uses Orchestration for complex flows
       (Job Launch, Runner Registration, Tenant Setup)
     - Pravah uses Choreography for simple fan-out
       (notifications, lineage tracking)
     - Saga state persisted to PostgreSQL (crash-safe)
     - Compensations: idempotent, reverse order,
       always eventually succeed
     - Pivot transactions for non-undoable actions

1.9  ✅ Event Sourcing + CQRS
     - Event store: immutable, append-only
     - Aggregate = entity tracked by events
     - Snapshots every 100 events (performance)
     - CQRS: write side (event store) separated from
       read side (purpose-built read models)
     - Read models: PostgreSQL (dashboard),
       Elasticsearch (search), Redis (agent),
       TimescaleDB (SLA), Neo4j (lineage graph)
     - Eventual consistency gap: handled with
       optimistic UI updates
     - Time-travel debugging: replay events to any point
     - Agent uses event history for auto-healing context

1.10 ✅ Outbox Pattern
     - Dual-write problem: 4 failure scenarios explained
     - Outbox table in same DB as business tables
     - Atomic: business write + outbox in one transaction
     - Relay process: SELECT FOR UPDATE SKIP LOCKED
     - Parallel relays: no contention, scales linearly
     - Failure handling: all crash scenarios covered
     - Dead letter after 5 failed attempts
     - Dead letter UI: inspect, replay, or discard
     - Stuck PROCESSING watchdog (5 minute timeout)
     - Every Pravah service has its own outbox table

1.11 ✅ Circuit Breaker, Bulkhead & Backpressure
     - Cascading failure: how one slow service kills all
     - Circuit Breaker: CLOSED → OPEN → HALF-OPEN
       50% failure rate in 60s → OPEN
       30s cooldown → HALF-OPEN test
     - Fallbacks: cache, queue, graceful degradation
     - Bulkhead: thread pool per tenant tier
       Enterprise: 50 threads each
       Professional groups: 100 threads shared
       Free tier: 50 threads shared
     - Service call bulkheads: pool per destination
     - Backpressure: bounded queues, Kafka lag signal,
       Reactive Streams, token bucket rate limiting
     - Decoration order:
       Rate Limit → Bulkhead → Circuit Breaker
       → Timeout → Retry
     - Resilience4j for all patterns

1.12 ✅ Two-Phase Commit & Why We Avoid It
     - 2PC phases: Prepare → Commit/Abort
     - Fatal flaws: blocking, partial commits,
       heuristic decisions, performance collapse
     - Blocking problem: coordinator crash = all locked
     - Partial commit: network partition during Phase 2
     - Heuristic inconsistency: silent permanent corruption
     - Performance: 80-500ms vs 3ms local transaction
     - Local 2PC within single DB = fine (PostgreSQL)
     - Distributed 2PC across network = never
     - Pravah's alternative: Saga + Outbox +
       Idempotency + Event Sourcing + Circuit Breaker
       + Consensus (all working together)
