# 1.11 Circuit Breaker, Bulkhead & Backpressure

## The Problem: Cascading Failures

One slow component can take down an entire platform. Here is exactly how it happens without protection:

```
Normal state: all services healthy, latency ~50ms each

Step 1  Secret Service DB connection pool exhausted
        Secret Service response time: 50ms → 5000ms

Step 2  Runner Service calls Secret Service — threads block waiting
        Runner Service threads: all occupied waiting for Secret Service
        Runner Service queue: filling up
        Runner Service response time: 50ms → 8000ms

Step 3  Execution Service calls Runner Service — threads block waiting
        Execution Service: completely unresponsive

Step 4  Scheduler cannot dispatch jobs
        Scheduler retries → sends more load to Execution Service (already dead)

Step 5  ENTIRE PRAVAH IS DOWN
        One exhausted database connection pool
        → took down the entire platform
        → thousands of pipelines failing
        → all tenant SLAs breached
```

Three patterns prevent cascading failures:

| Pattern | What It Does |
|---|---|
| **Circuit Breaker** | Detects a failing service and stops calling it — fail fast instead of waiting |
| **Bulkhead** | Isolates resources into pools — one tenant's failure cannot exhaust another's resources |
| **Backpressure** | Lets a slow consumer signal a fast producer to slow down |

## Pattern 1: Circuit Breaker

The name comes from electrical circuit breakers: too much current → breaker trips → circuit opens → no electricity flows → appliances protected. When the fault is resolved, the breaker resets.

### Three States

```
                    ┌──────────────────────────────────────┐
                    │                                      │
              ┌─────▼─────┐                               │
              │  CLOSED   │  Normal. All calls go through. │
              └─────┬─────┘                               │
                    │                                      │
         failure rate > threshold                         │
         (e.g. 50% failures in 60s)                       │
                    │                                      │
              ┌─────▼─────┐                               │
              │   OPEN    │  Fail fast. Return error in    │
              └─────┬─────┘  1ms. No calls to the service. │
                    │                                      │
          after cooldown (e.g. 30s)                       │
                    │                                      │
              ┌─────▼─────┐                               │
              │ HALF-OPEN │  Allow 1 test call through.    │
              └─────┬─────┘                               │
                    │                                      │
           ┌────────┴────────┐                            │
           ▼                 ▼                            │
       succeeds           fails                           │
           │                 │                            │
        CLOSED             OPEN ──────────────────────────┘
```

### Step-by-Step in Pravah

```
CLOSED STATE — Runner Service calling Secret Service:

  t=0    "Get creds for pipe-abc" → 45ms ✅
  t=1    "Get creds for pipe-def" → 52ms ✅
  t=2    "Get creds for pipe-xyz" → 48ms ✅
  
  failure_rate = 0%. threshold = 50%. State: CLOSED.

Secret Service DB fails at t=3:

  t=3    "Get creds" → TIMEOUT (5000ms) ❌
  t=8    "Get creds" → TIMEOUT (5000ms) ❌
  t=13   "Get creds" → TIMEOUT (5000ms) ❌
  t=18   "Get creds" → TIMEOUT (5000ms) ❌
  t=23   "Get creds" → TIMEOUT (5000ms) ❌
  
  failure_rate = 62.5%. threshold = 50%. TRIP THE BREAKER.

OPEN STATE — fail fast:

  t=28   "Get creds" → CircuitOpenException in 1ms ❌ (not 5000ms!)
  t=29   "Get creds" → 1ms ❌
  t=30   "Get creds" → 1ms ❌
  
  Runner Service threads are FREE. Not blocked for 5 seconds each.
  Runner Service stays responsive. ✅

Cooldown timer: 30 seconds…

HALF-OPEN STATE — test call:

  t=58   "Get creds" → Secret Service recovered → 48ms ✅
         ONE success → CLOSE the circuit!

CLOSED STATE — normal operation resumed ✅
```

### Fallback Strategies

When the circuit is open, Pravah doesn't just fail — it degrades gracefully:

| Service | Fallback Strategy |
|---|---|
| Runner → Secret Service open | Return cached credentials from Redis (stale but functional); if no cache, queue job as PENDING_CREDENTIALS |
| Scheduler → Execution Service open | Queue dispatch commands in bounded local buffer (max 1,000); flush when circuit closes |
| Execution → Notification Service open | Outbox pattern handles this naturally — notifications are sent when service recovers |
| Agent → LLM API open | Disable AI features, log alert, notify on-call; platform continues running pipelines without AI |

Core ETL always runs even when AI, notifications, or secondary services are down.

### Configuration (Resilience4j)

```yaml
resilience4j:
  circuitbreaker:
    instances:
      secret-service:
        sliding-window-type: TIME_BASED
        sliding-window-size: 60              # evaluate last 60 seconds
        failure-rate-threshold: 50           # 50% errors → OPEN
        slow-call-rate-threshold: 80         # 80% slow calls → OPEN
        slow-call-duration-threshold: 2000ms # "slow" = more than 2s
        wait-duration-in-open-state: 30s     # cooldown before HALF-OPEN
        permitted-calls-in-half-open: 3      # test calls in HALF-OPEN
        minimum-number-of-calls: 10          # need 10 samples to evaluate

      llm-api:
        sliding-window-size: 120
        failure-rate-threshold: 30
        slow-call-duration-threshold: 10000ms  # LLM is inherently slow
        wait-duration-in-open-state: 60s
```

## Pattern 2: Bulkhead

Ships use bulkheads — watertight compartments — so that flooding one section does not sink the entire vessel. Software bulkheads divide resources into isolated pools so one consumer cannot exhaust another's resources.

### Without Bulkheads — Tenant Pollution

```
Execution Service: 200 threads, shared by ALL tenants.

t=09:55  Tenant-Megacorp: 150 pipelines all trigger simultaneously
         → 150 threads claimed by Tenant-Megacorp
         → Remaining: 50 threads for everyone else

t=09:56  Tenant-Megacorp jobs running slowly (expensive SQL)
         Threads still occupied

t=09:57  Tenant-Startup triggers 3 pipelines
         → Only 50 threads available, 3 claimed immediately ✅
         But what if Megacorp had claimed all 200?
         → Tenant-Startup's pipelines queue
         → SLA breached for Tenant-Startup because of Megacorp's load
```

### With Bulkheads — Isolation

```
Thread pools divided by tier:

  Enterprise tier:    100 threads
  Professional tier:  60 threads
  Free tier:          40 threads

Tenant-Megacorp (Enterprise) uses 100 threads:
  → Enterprise pool full
  → Professional pool: unaffected ✅
  → Free tier pool: unaffected ✅
  → Tenant-Startup (Professional): normal execution ✅
```

### Bulkheads by Destination Service

A slow downstream service should not block calls to other services:

```
Secret Service destination pool:     30 threads
Runner Service destination pool:     50 threads
Billing Service destination pool:    20 threads
Notification Service destination pool: 10 threads

Secret Service becomes slow:
  → Its 30 threads fill up
  → Runner Service pool: still 50 threads, fully available ✅
  → Other services unaffected ✅
```

### Bulkhead Configuration (Resilience4j)

```yaml
resilience4j:
  bulkhead:
    instances:
      enterprise-tier:
        max-concurrent-calls: 100
        max-wait-duration: 100ms   # wait up to 100ms for a slot
      professional-tier:
        max-concurrent-calls: 60
        max-wait-duration: 50ms
      free-tier:
        max-concurrent-calls: 20
        max-wait-duration: 0ms     # fail immediately if pool full
      secret-service:
        max-concurrent-calls: 30
        max-wait-duration: 200ms
```

## Pattern 3: Backpressure

Backpressure is the mechanism by which a **slow consumer signals a fast producer to slow down**. Without it, the producer overwhelms the consumer's queue, which grows until OOM kills the service.

### Strategy 1: Bounded Queues

Use bounded queues instead of unbounded. When the queue is full, the producer must back off:

```
Execution Service internal queue: max 5,000 jobs

Queue hits 5,000:
  → New jobs rejected with HTTP 429 Too Many Requests
  → Scheduler backs off and retries later
  → Queue drains as jobs are processed
  → Scheduler resumes at normal rate
```

### Strategy 2: Kafka Consumer Lag Signaling

Kafka naturally buffers between producers and consumers. Consumer lag is the backpressure signal:

```
Topic: job.assigned | Consumer Group: execution-service

Lag = 0        →  Normal. Scheduler runs at full speed.
Lag = 1,000    →  Warning. Scheduler reduces to 50% dispatch rate.
Lag = 5,000    →  Critical. Scheduler reduces to 10% dispatch rate.
Lag = 10,000   →  Emergency. Scheduler pauses entirely.

Scheduler reads consumer lag metric from Kafka every 10 seconds
and adjusts its dispatch rate dynamically.
```

### Strategy 3: Reactive Streams (Project Reactor)

Spring WebFlux + Project Reactor implement backpressure at the code level:

```java
// Consumer requests only what it can handle
Flux<Job> jobStream = scheduler.getJobStream();

jobStream
    .onBackpressureBuffer(
        5000,                              // max buffer size
        job -> log.warn("Job dropped: {}", job.getId()),
        BufferOverflowStrategy.DROP_OLDEST // drop oldest if full
    )
    .flatMap(job -> executeJob(job), 50)   // max 50 concurrent
    .subscribe();

// Consumer tells producer: "Give me 50 at a time.
// Wait for me to request more."
// Producer cannot overwhelm the consumer.
```

### Strategy 4: Token Bucket Rate Limiting

Each tenant gets a token bucket. Each job costs one token. Refill rate = tier quota:

```
Enterprise:    100 tokens/minute
Professional:  20 tokens/minute
Free:          5 tokens/minute

Tenant triggers 200 jobs in 1 minute (Enterprise):
  First 100:  tokens available → dispatch ✅
  Next 100:   bucket empty → 429 Rate Limited ❌
  Next minute: bucket refills to 100 → dispatch ✅
```

Token bucket check in Redis (atomic Lua script):

```java
String script = """
    local tokens = redis.call('GET', KEYS[1])
    if tokens == nil then tokens = ARGV[1] end
    if tonumber(tokens) > 0 then
        redis.call('DECR', KEYS[1])
        redis.call('EXPIRE', KEYS[1], 60)
        return 1
    else
        return 0
    end
    """;

Long allowed = redisTemplate.execute(script,
    List.of("rate:tenant:" + tenantId),
    String.valueOf(maxTokens)
);

if (allowed == 0) throw new RateLimitExceededException();
```

## All Three Patterns Together

Incoming request: "Execute job for tenant-megacorp"

```
Layer 1  RATE LIMITING (Backpressure)
         Is tenant-megacorp within their quota?
         YES → proceed  |  NO → 429, stop here (cheapest check)

Layer 2  BULKHEAD
         Is the enterprise-tier thread pool available?
         YES → claim a thread  |  NO → 503, BulkheadFullException

Layer 3  CIRCUIT BREAKER
         Is the Runner Service circuit CLOSED?
         CLOSED    → make the call
         OPEN      → use fallback, return from cache or queue
         HALF-OPEN → test call, monitor result

Layer 4  TIMEOUT
         Did Runner Service respond within 2s?
         YES → process response  |  NO → TimeoutException, record failure

Layer 5  RETRY
         Is this error retryable?
         YES → wait + retry (max 3 times, exponential backoff)
         NO  → fail immediately
```

Order matters: evaluate the cheapest checks first. Reject at Rate Limiting before consuming a thread. Retry only after passing all outer checks.

**Composing with Resilience4j:**

```java
CircuitBreaker cb = CircuitBreaker.of("runner-service", cbConfig);
Bulkhead bh       = Bulkhead.of("enterprise-tier", bhConfig);
RateLimiter rl    = RateLimiter.of("tenant-rate", rlConfig);
Retry retry       = Retry.of("runner-service", retryConfig);

Supplier<JobResult> decoratedCall = Decorators
    .ofSupplier(() -> runnerService.dispatch(job))
    .withRateLimiter(rl)      // outermost — cheapest
    .withBulkhead(bh)
    .withCircuitBreaker(cb)
    .withRetry(retry)         // innermost
    .withFallback(
        List.of(CircuitBreakerOpenException.class, BulkheadFullException.class),
        ex -> handleFallback(job, ex)
    )
    .decorate();
```

## FAANG Interview Angles

**"How does Pravah prevent one slow service from taking down everything else?"**

> Three layered patterns. Circuit breakers detect failure rates — after 50% failures in 60 seconds, the breaker opens and calls fail fast in 1ms instead of waiting 5 seconds, freeing threads immediately. Bulkheads give each service destination and tenant tier its own isolated thread pool — Secret Service slowness exhausts its own 30-thread pool while the 50-thread Runner Service pool is completely unaffected. Together, failure is contained and never cascades.

**"How does Pravah handle a midnight thundering herd when thousands of pipelines all trigger at once?"**

> Multiple layers. Cron triggers have ±30s random jitter, spreading the burst across a minute. Tenant-level token bucket rate limiting prevents any single tenant from flooding the queue. Kafka acts as a natural buffer — consumer lag is monitored, and when it exceeds 5,000 messages the Scheduler throttles its dispatch rate. Execution Service uses bounded reactive streams — it requests only as many jobs as it has capacity to process, exerting backpressure upstream.

**"What's the difference between circuit breaker and bulkhead?"**

> They're complementary. Circuit breaker is temporal — it detects failure over time and stops calls to a failing service. It answers: "is this service healthy right now?" Bulkhead is spatial — it divides resources into isolated pools. It answers: "can one bad actor consume all resources?" You need both. A circuit breaker doesn't help if a slow-but-not-failing service consumes all shared threads. A bulkhead alone doesn't help if a service starts failing — threads still block for timeout duration per call.

## 📌 Key Takeaways

1. One slow service can kill the entire platform without protection patterns
2. **Circuit Breaker:** CLOSED → OPEN → HALF-OPEN; fail fast (1ms) instead of waiting during failures; graceful degradation with fallbacks
3. **Bulkhead:** isolate resources by tenant tier and destination service; one tenant's misbehavior cannot starve others
4. **Backpressure:** bounded queues, Kafka lag signaling, Reactive Streams, token bucket rate limiting
5. Decoration order: Rate Limit → Bulkhead → Circuit Breaker → Timeout → Retry (cheapest checks first)
6. All three patterns are required — each addresses a different dimension of the cascading failure problem
7. Monitor everything with Prometheus: circuit state, bulkhead slots, consumer lag, token buckets
