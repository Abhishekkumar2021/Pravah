# 1.3 Distributed Clocks, Ordering & Causality

## Why Physical Clocks Fail

On a single machine, ordering events is trivial — the OS clock says which happened first. Across machines, this breaks completely.

**Clock skew in practice:**

```
Pravah Scheduler  (Machine 1): dispatches job at  10:00:00.001
Pravah Runner-001 (Machine 2): receives job at    09:59:59.998
```

The runner appears to have received the job *before* it was sent. The timestamps are wrong — not the events.

Every machine has a hardware clock (quartz crystal) oscillating at a slightly different rate. Machine A may gain 1ms per 10 seconds; Machine B may lose 2ms per 10 seconds. After one hour, they are over a second apart. NTP syncs them periodically but the sync itself introduces network delay.

**The consequence for Pravah:**

```
Two schedulers racing to assign the same job:

Scheduler-1 (Machine A, clock ahead):  writes at 10:00:00.500
Scheduler-2 (Machine B, clock behind): writes at 10:00:00.200

The database sorts by timestamp.
DB sees Machine B wrote first (at .200).
DB keeps Machine B's assignment.
But Scheduler-1 already told Runner-001 to start.

Result: job runs twice. Data duplicated.
```

We cannot rely on physical clocks for ordering in distributed systems. We need logical ordering.

## Solution 1: Lamport Timestamps (Logical Clocks)

**Core idea:** Replace wall-clock time with a logical counter that increments on every event and synchronises on communication.

**Three rules:**

1. On every local event: `counter += 1`
2. Before sending a message: `counter += 1`, attach it to the message
3. On receiving a message: `counter = max(local, received) + 1`

**Pravah example — Scheduler dispatches a job, Runner executes:**

```
          Scheduler             Runner-001
          counter=0             counter=0
              │                     │
  E1:  Pipeline created             │
       counter → 1                  │
              │                     │
  E2:  Job dispatched ─────────────►│  Job received
       counter → 2   [msg: L=2]     │  counter = max(0, 2) + 1 = 3
              │                     │
              │                     │  Job started
              │                     │  counter → 4
              │                     │
              │                     │  Job completed
              │◄────────────────────│  counter → 5, send [msg: L=5]
       counter = max(2,5)+1 = 6     │
  E6:  Status updated               │
       counter → 7                  │
```

**Ordered event list by Lamport timestamp:**

| L | Event | Node |
|---|-------|------|
| 1 | Pipeline created | Scheduler |
| 2 | Job dispatched | Scheduler |
| 3 | Job received | Runner-001 |
| 4 | Job started | Runner-001 |
| 5 | Job completed | Runner-001 |
| 6 | Result received | Scheduler |
| 7 | Status updated | Scheduler |

**The key property:** If A happened-before B, then `Lamport(A) < Lamport(B)`. Always true.

**The limitation:** The reverse is not guaranteed. Two concurrent events can have any ordering of their Lamport timestamps. You cannot detect concurrency with Lamport clocks.

## Solution 2: Vector Clocks

**Core idea:** Instead of one counter, every node maintains a counter for *every* node in the system. This lets us detect both causal order and concurrency.

**Structure** (Pravah with Scheduler, Runner-001, Agent):

```
Each service maintains: [Scheduler, Runner001, Agent]
Starting:               [0,         0,         0     ]
```

**Trace:**

```
          Scheduler [S,R,A]    Runner-001 [S,R,A]    Agent [S,R,A]
          [0, 0, 0]            [0, 0, 0]             [0, 0, 0]

E1: Pipeline created
    Scheduler → [1, 0, 0]

E2: Job dispatched ──────────►  Runner receives
    Scheduler → [2, 0, 0]       Runner → [2, 1, 0]

E3:                             Job starts
                                Runner → [2, 2, 0]

E4: Schema check ──────────────────────────────────► Agent receives
    Scheduler → [3, 0, 0]                            Agent → [3, 0, 1]

E5:                             Job result ◄─────────
    Scheduler → [4, 3, 0]       Runner → [2, 3, 0]
```

**Comparing two events:**

```
Runner E3: [2, 2, 0]
Agent  E4: [3, 0, 1]

Is E3 before E4?
  2 ≤ 3 ✅
  2 ≤ 0 ✗  ← not all components satisfy ≤

→ CONCURRENT — neither caused the other.
```

**Comparison rules:**

- **A happened-before B:** every component of A ≤ B, and at least one is strictly less
- **Concurrent:** neither A ≤ B nor B ≤ A

## Solution 3: Hybrid Logical Clocks (HLC)

Used by CockroachDB and YugabyteDB in production. Combines the best of both worlds.

```
HLC = max(physical_clock, logical_clock) + ε
Format: [physical_timestamp | logical_counter]
Example: [2026-05-10T10:00:00.003 | 2]
```

**Properties:**

| Property | Lamport | Vector Clock | HLC |
|---|:---:|:---:|:---:|
| Captures causal order | ✅ | ✅ | ✅ |
| Detects concurrency | ✗ | ✅ | Partial |
| Human-readable timestamps | ✗ | ✗ | ✅ |
| Handles clock skew | ✅ | ✅ | ✅ |
| Scales with node count | ✅ | ✗ (vector grows) | ✅ |

**Pravah uses HLC for job event timestamps** — SLA monitoring needs real wall-clock time; causal ordering is required for correct lineage graphs. HLC satisfies both.

## The Happens-Before Relationship

Defined by Lamport: event A *happens-before* B (written A → B) if:

1. **Same node:** A and B are on the same node and A occurred first in program order
2. **Message passing:** A is sending a message; B is receiving that same message
3. **Transitivity:** if A → B and B → C, then A → C

If neither A → B nor B → A, the events are **concurrent** (written A ∥ B).

**Pravah job lifecycle — happens-before chains:**

```
A: Scheduler creates job record
B: Scheduler sends job via gRPC        A → B (same process)
C: Runner receives job                 B → C (send/receive)
D: Runner starts execution             C → D (same process)
E: Agent checks pipeline health        E ∥ D (concurrent — no causal link)
F: Runner completes job                D → F (same process)
G: Scheduler marks job complete        F → G (send/receive)

Full chain: A → B → C → D → F → G  (by transitivity, A → G)
```

## Pravah's Ordering Strategy

| Use Case | Mechanism |
|---|---|
| Job event ordering within a pipeline | Kafka partition by `pipeline_id` → sequential within partition |
| Cross-service event tracing | Correlation ID + HLC timestamp → Jaeger reconstructs the causal chain |
| SLA deadline monitoring | HLC physical component — human-meaningful deadlines |
| Audit log ordering | HLC — compliance needs both real timestamps and causal order |
| Distributed write ordering | PostgreSQL sequence numbers (monotonically increasing) + optimistic locking |

## FAANG Interview Angles

**"How do you order events across Pravah's microservices reliably?"**

> Within a single pipeline's event stream, Kafka partition ordering gives sequential consistency. Across services, we use Hybrid Logical Clocks — causality tracking plus human-readable timestamps for SLA monitoring. Every event carries a correlation ID so Jaeger can reconstruct the full causal chain.

**"Two scheduler instances write to the database at the same millisecond — how do you order them?"**

> We do not rely on timestamps for this. PostgreSQL sequence numbers for job IDs are monotonically increasing and are the single source of truth for ordering. Optimistic locking with version counters detects concurrent writes — one is rejected, never silently overwritten.

**"How does Pravah know if two events are causally related or concurrent?"**

> We propagate vector clock metadata in gRPC headers and Kafka message headers. When the Agent Service receives an event, it compares vector clocks to determine whether it is causally downstream of a scheduler event or happened concurrently. This prevents the agent from acting on events that have not yet causally reached it.

---

## 📌 Key Takeaways

1. **Physical clocks drift** — never use wall-clock time alone for distributed event ordering
2. **Lamport timestamps** capture happens-before but cannot detect concurrency
3. **Vector clocks** detect both causal order and concurrency, but grow with node count
4. **HLC** combines causality with real wall-clock proximity — Pravah's choice for job events
5. **Kafka partition key = `pipeline_id`** gives free sequential ordering within a pipeline's event stream at zero extra cost
