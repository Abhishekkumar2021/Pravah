# 1.10 The Outbox Pattern

## The Dual-Write Problem

Every Pravah service needs to do two things together: write business state to its database, and publish an event to Kafka. These are two separate systems — no single transaction can span both. This creates multiple failure modes, all dangerous:

**Scenario A — Write DB first, then Kafka:**
```
t=1  INSERT INTO jobs (id='job-xyz') ✅
t=2  Publish to Kafka 💥 SERVICE CRASHES

Result: Job exists in DB but Kafka never receives the event.
        Execution Service never dispatches the job.
        Silent data loss — job sits in DB forever.
```

**Scenario B — Write Kafka first, then DB:**
```
t=1  Publish to Kafka ✅
t=2  INSERT INTO jobs (id='job-xyz') 💥 SERVICE CRASHES

Result: Kafka has the event but DB has no job record.
        Execution Service tries to look up the job → not found.
        Ghost job — executing something untracked.
```

**Scenario C — Kafka publish times out:**
```
t=1  INSERT INTO jobs (id='job-xyz') ✅
t=2  Publish to Kafka → network unreachable

Result: How long do we retry? What if the service crashes during retry?
        If we give up, the job is lost. If we retry blindly, we
        may publish after the service restarts, but have no way
        to know if an earlier attempt already succeeded.
```

There is no safe ordering when the two systems are independent.

---

## The Core Idea

The key insight: instead of writing to Kafka directly, **write to an outbox table inside the same database**. The outbox write happens in the same transaction as the business write. Either both succeed or neither does — atomically.

A separate **relay process** then reads pending outbox messages and publishes them to Kafka asynchronously.

```
Physical outbox analogy:
  Write a letter (business operation)
  Put it in your outbox tray (outbox table)
  Both done in the same moment.

  Mail carrier picks up letters later (relay process).
  If the carrier is sick, letters wait in the tray.
  When the carrier returns, all pending letters are delivered.
  Letters are never lost and never sent before they are written.
```

## Outbox Table Design

```sql
CREATE TABLE outbox (
  id               UUID         PRIMARY KEY,
  aggregate_id     VARCHAR(255) NOT NULL,   -- e.g. "pipe-abc"
  aggregate_type   VARCHAR(100) NOT NULL,   -- e.g. "Pipeline"
  event_type       VARCHAR(100) NOT NULL,   -- e.g. "JOB_CREATED"
  kafka_topic      VARCHAR(255) NOT NULL,   -- e.g. "job.assigned"
  kafka_key        VARCHAR(255),            -- partition key
  payload          JSONB        NOT NULL,   -- event data
  headers          JSONB,                   -- correlation IDs etc.
  idempotency_key  VARCHAR(255) NOT NULL UNIQUE,
  status           VARCHAR(50)  NOT NULL DEFAULT 'PENDING',
  created_at       TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  processed_at     TIMESTAMPTZ,
  failed_attempts  INT          NOT NULL DEFAULT 0,
  last_error       TEXT
);

-- Efficient index for relay polling
CREATE INDEX idx_outbox_pending
  ON outbox (status, created_at)
  WHERE status = 'PENDING';
```

**The atomic write:**

```sql
BEGIN TRANSACTION;

  -- Business operation
  INSERT INTO jobs (id, pipeline_id, status, idempotency_key, created_at)
  VALUES ('job-xyz', 'pipe-abc', 'PENDING', 'pipe-abc-2024-01-15T10:00:00-attempt-1', NOW());

  -- Outbox message (same transaction)
  INSERT INTO outbox (aggregate_id, aggregate_type, event_type, kafka_topic, kafka_key, payload, idempotency_key)
  VALUES (
    'pipe-abc', 'Pipeline', 'JOB_CREATED', 'job.assigned', 'pipe-abc',
    '{"job_id": "job-xyz", "pipeline_id": "pipe-abc", "scheduled_time": "2024-01-15T10:00:00"}',
    'pipe-abc-2024-01-15T10:00:00-attempt-1'
  );

COMMIT;

-- Either BOTH inserted or NEITHER. No partial state possible. ✅
```

## The Relay Process

The relay runs as background threads inside each service, polling every 100ms:

**Step 1 — Claim messages (with `FOR UPDATE SKIP LOCKED`):**

```sql
UPDATE outbox
SET status = 'PROCESSING'
WHERE id IN (
  SELECT id FROM outbox
  WHERE status = 'PENDING'
  ORDER BY created_at ASC
  LIMIT 100
  FOR UPDATE SKIP LOCKED    -- concurrent-safe, no contention
)
RETURNING *;
```

`FOR UPDATE SKIP LOCKED` is the key. Multiple relay threads run in parallel. Without `SKIP LOCKED`, all threads would block on the same rows. With it, each thread claims its own batch — zero contention.

**Step 2 — Publish to Kafka:**

```
FOR each claimed message:
  KafkaProducer.send(
    topic:   message.kafka_topic,
    key:     message.kafka_key,
    value:   message.payload,
    headers: {
      "idempotency-key": message.idempotency_key,
      "correlation-id":  message.headers.correlation_id,
      "event-type":      message.event_type
    }
  )
  Wait for Kafka ACK (acks=all)
```

**Step 3 — Mark as processed or failed:**

```sql
-- On success:
UPDATE outbox SET status = 'PROCESSED', processed_at = NOW()
WHERE id = message.id;

-- On failure:
UPDATE outbox
SET status = 'PENDING',
    failed_attempts = failed_attempts + 1,
    last_error = 'connection timeout'
WHERE id = message.id;
-- Will be retried on next poll cycle
```

**Visual relay timeline:**

```
t=0ms    Poll → 3 PENDING messages found
t=1ms    Claim all 3 (status → PROCESSING)
t=2ms    Publish msg-001 to Kafka → ACK ✅  →  Mark PROCESSED
t=4ms    Publish msg-002 to Kafka → ACK ✅  →  Mark PROCESSED
t=6ms    Publish msg-003 to Kafka → TIMEOUT ❌  →  Back to PENDING (attempt=1)
t=100ms  Poll again → msg-003 still PENDING
t=101ms  Retry msg-003 → ACK ✅  →  Mark PROCESSED ✅
```

## All Failure Scenarios Handled

**Scenario 1 — Service crashes after DB write, before relay runs:**
```
Outbox message is PENDING in the DB.
Relay starts after restart → finds PENDING message → publishes ✅
No data loss.
```

**Scenario 2 — Relay crashes after Kafka publish, before marking PROCESSED:**
```
Outbox message is stuck in PROCESSING status.
Relay restarts → treats PROCESSING as potentially unpublished → retries.
Kafka receives duplicate → idempotent producer (PID + sequence number) deduplicates ✅
No duplicate event stored.
```

**Scenario 3 — Kafka is down for 5 minutes:**
```
Relay keeps polling → publishes fail → messages stay PENDING.
failed_attempts increments but message is not dead yet.
Kafka recovers → relay publishes all accumulated messages ✅
No messages lost.
```

**Scenario 4 — Service gets duplicate business request (API retry):**
```
Unique constraint on idempotency_key blocks duplicate INSERT into outbox.
Transaction rolls back → only one outbox message per idempotency key ✅
```

## Dead Letter Queue

After 5 failed attempts, a message is permanently stuck — structural issue (bad payload, wrong topic config). Retrying forever clogs the relay:

```sql
-- Move to dead letter after N failures
UPDATE outbox SET status = 'DEAD' WHERE id = message.id;

INSERT INTO dead_letter_outbox (original_message, failure_reason, failed_at)
VALUES (message, 'Kafka topic does not exist', NOW());
```

On dead-letter: PagerDuty alert fires. Pravah's UI shows a Dead Letter Queue viewer where operators can inspect the failure reason, fix the payload if needed, and replay the message — or acknowledge it as intentionally skipped.

## Scaling with Multiple Relay Instances

Running multiple relay threads or instances is safe because of `FOR UPDATE SKIP LOCKED`:

```
Relay-1: SELECT ... FOR UPDATE SKIP LOCKED → claims messages 1, 2, 3 (locked)

Relay-2 (simultaneous): SELECT ... FOR UPDATE SKIP LOCKED
  → sees messages 1, 2, 3 are locked → skips them
  → claims messages 4, 5, 6

No contention. No duplicates. Both relays work fully in parallel.
```

Pravah's deployment: 2 relay threads per service instance, 3 instances = 6 relay threads total. Each claims up to 100 messages per 100ms cycle = 6,000 messages/second throughput.

## Outbox Across All Pravah Services

Each service owns its own outbox (DB per service principle):

| Service | Events Published |
|---|---|
| Pipeline Service | `pipeline.created`, `job.assigned` |
| Scheduler Service | `pipeline.triggered`, `backfill.requested` |
| Runner Service | `runner.registered`, `job.dispatched` |
| Execution Service | `job.started`, `job.completed`, `job.failed` |
| Agent Service | `heal.suggested`, `drift.detected` |
| Notification Service | `notification.sent`, `alert.fired` |

No service ever writes directly to another service's database. All cross-service communication flows through Kafka via each service's outbox.

## Connecting Outbox, Event Sourcing, and Saga

When these three patterns compose:

```sql
-- USER TRIGGERS PIPELINE

-- 1. Event Sourcing write side (atomic transaction)
BEGIN TRANSACTION;

  -- Append to event store
  INSERT INTO events (aggregate_id, seq, type, payload)
  VALUES ('pipe-abc', 10, 'PIPELINE_TRIGGERED', {...});

  -- Outbox message for Kafka relay
  INSERT INTO outbox (event_type, kafka_topic, payload)
  VALUES ('PIPELINE_TRIGGERED', 'pipeline.events', {...});

COMMIT; -- atomic ✅

-- 2. Relay publishes to Kafka

-- 3. Saga Orchestrator consumes from Kafka
--    Each saga step does its own atomic write + outbox insert
--    Relay publishes result of each step to Kafka

-- 4. CQRS read models updated by Kafka consumers
```

The result: no distributed transactions, no data loss on crashes, exactly-once semantics, full event history, compensatable failures, and fast reads — all from composing three patterns.

## System Design Interview Angles

**"How does Pravah guarantee that a pipeline trigger always results in a Kafka event, even if the service crashes?"**

> The Outbox pattern. When a pipeline is triggered, we write both the job record and an outbox message in a single PostgreSQL transaction — atomic. A background relay polls the outbox with `SELECT FOR UPDATE SKIP LOCKED` and publishes to Kafka. If the relay crashes after publishing but before marking PROCESSED, it retries on restart. Kafka's idempotent producer deduplicates using producer ID and sequence number. Messages in the outbox wait until Kafka is available — they are never lost.

**"What is `SELECT FOR UPDATE SKIP LOCKED` and why does Pravah use it?"**

> It's a PostgreSQL feature for concurrent queue processing. `FOR UPDATE` locks selected rows. `SKIP LOCKED` skips rows already locked by another transaction instead of blocking. Multiple relay threads run in parallel. Without `SKIP LOCKED`, all threads would serialize on the same rows. With it, each thread claims its own batch with zero contention. Six relay threads process 600 messages per 100ms cycle.

**"How does Pravah handle messages that keep failing to publish to Kafka?"**

> After 5 failed attempts, the message moves to dead letter status. A PagerDuty alert fires and a UI Dead Letter Queue viewer shows the message with failure details. Operators can inspect the issue, fix the payload, and replay — or acknowledge it as intentionally skipped. This prevents bad messages from blocking healthy ones.

## 📌 Key Takeaways

1. Dual-write problem: writing to DB and Kafka separately always risks inconsistency on crash
2. Outbox pattern: write both atomically to the same DB; relay publishes to Kafka asynchronously
3. `FOR UPDATE SKIP LOCKED` enables safe parallel relay processing with zero contention
4. Three crash scenarios all handled: crash before relay (messages wait), crash after publish (idempotent producer deduplicates), Kafka down (messages wait until available)
5. Dead letter handling: after N failures, quarantine + alert + manual replay UI
6. Each service owns its own outbox — DB per service principle maintained throughout
7. Outbox + Event Sourcing + CQRS + Saga = complete, crash-safe distributed state management
