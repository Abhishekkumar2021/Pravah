# 1.12 Two-Phase Commit & Why Pravah Avoids It

## The Fundamental Tension

This is the final chapter of Phase 1 and a synthesis topic. Everything we have covered — sagas, outbox, idempotency, circuit breakers — exists because of the failure modes discussed here.

Pravah needs operations that span multiple services to be atomic:

```
Launching a pipeline job requires:
  ✅ Create job record        (Pipeline Service DB)
  ✅ Reserve runner capacity  (Runner Service DB)
  ✅ Deduct billing quota     (Billing Service DB)
  ✅ Publish Kafka event      (Kafka broker)

If Billing fails after the first two:
  → Job record dangling (Pipeline DB)
  → Runner capacity reserved but unused (Runner DB)
  → System is inconsistent
```

The instinctive solution is a **distributed transaction using Two-Phase Commit (2PC)**. Pravah explicitly rejects this approach. Here is why.

---

## What Is Two-Phase Commit?

2PC coordinates multiple resource managers to either all commit or all abort a single transaction. Three roles participate:

- **Transaction Manager (TM)** — the coordinator
- **Resource Managers (RM)** — individual databases, message brokers
- **Application** — the service orchestrating the operation

### Phase 1 — Prepare

```
Application → TM: "Begin distributed transaction"

TM → Pipeline DB:  "PREPARE"
TM → Runner DB:    "PREPARE"
TM → Billing DB:   "PREPARE"
TM → Kafka:        "PREPARE"

Each Resource Manager:
  1. Executes the operation locally
  2. Writes to a REDO log (durable, for recovery)
  3. Acquires ROW LOCKS on affected rows
  4. Responds to TM: READY or ABORT

        Transaction Manager
              │
    ┌─────────┼──────────┐
    ▼         ▼          ▼
Pipeline    Runner    Billing
   DB         DB         DB
  READY     READY      READY
    └─────────┴──────────┘
              │
  TM: "All READY → proceed to Phase 2"
```

### Phase 2 — Commit or Abort

```
All participants READY:
  TM → Pipeline DB:  "COMMIT"
  TM → Runner DB:    "COMMIT"
  TM → Billing DB:   "COMMIT"
  TM → Kafka:        "COMMIT"
  Each releases locks. Transaction complete.

Any participant ABORT:
  TM → Pipeline DB:  "ROLLBACK"
  TM → Runner DB:    "ROLLBACK"
  TM → Billing DB:   "ROLLBACK"
  TM → Kafka:        "ROLLBACK"
  Each undoes work and releases locks.
```

On paper, 2PC appears to solve the problem cleanly. In practice, it fails catastrophically in distributed cloud environments.

---

## Why 2PC Fails — Every Failure Scenario

### Failure 1: Coordinator Crash Between Phases

```
Phase 1 completes. All participants respond READY.
TM sends COMMIT to Pipeline DB ✅
TM 💥 CRASHES

State of the world:
  Pipeline DB:  committed ✅
  Runner DB:    WAITING for TM (holding locks)
  Billing DB:   WAITING for TM (holding locks)
  Kafka:        WAITING for TM (holding locks)

Three resource managers are BLOCKED indefinitely.
They hold row locks and cannot do anything.
No timeout. No progress. The system hangs.

This is called the BLOCKING PROBLEM of 2PC.
There is no correct recovery without the TM.
```

### Failure 2: Participant Crash After Voting READY

```
All participants vote READY.
TM sends COMMIT to all.

Billing DB receives COMMIT and 💥 CRASHES before applying it.

Billing DB recovers:
  "I have a READY entry in my REDO log.
   Did the TM commit or abort?
   I cannot know — TM might also have crashed.
   I must contact TM to find out."

If TM is also down:
  → Billing DB holds locks, waits indefinitely.
  → Blocking again.
```

### Failure 3: Network Partition During Phase 2

```
TM sends COMMIT to all participants.
Network partition: TM can reach Pipeline DB and Runner DB
                   but NOT Billing DB.

Pipeline DB: COMMITS ✅
Runner DB:   COMMITS ✅
Billing DB:  Never receives COMMIT, stays in PREPARED state.
             Holds locks indefinitely.

When partition heals:
  Billing DB contacts TM.
  TM checks its log: "I sent COMMIT to all."
  Billing DB applies COMMIT.

But what if Billing DB's connection to TM ALSO times out?
  Billing DB has no safe choice: commit or abort?
    Commit → might be wrong if TM actually aborted
    Abort  → might be wrong if TM actually committed
```

### Failure 4: Lock Hold Duration

```
Phase 1: All participants acquire locks.
Phase 1 to Phase 2 requires:
  - Network round trips to all participants
  - TM to write decision to durable log
  - Network round trips for commit acknowledgments

All of this takes: 50ms to 500ms in a LAN.
In a microservices deployment with network overhead: 1–5 seconds.

During this entire window:
  ALL affected rows are locked across ALL databases.
  No other transaction can read or write them.

With 10 concurrent distributed transactions:
  → 10 × 5s = 50 seconds of lock contention
  → Write throughput: near zero
  → Pravah's scheduling requires thousands of
     concurrent operations. 2PC makes this impossible.
```

### Failure 5: Not Supported by Modern Services

```
What uses 2PC:
  Traditional enterprise databases (Oracle, IBM DB2)
  Old-school Java EE with JTA/XA transactions

What does NOT support 2PC:
  Redis           ← no XA support
  Kafka           ← no XA support
  Elasticsearch   ← no XA support
  External REST APIs ← no XA support
  S3 / MinIO      ← no XA support

Pravah's stack requires coordination across:
  PostgreSQL, Kafka, Redis, Elasticsearch, S3, REST APIs

2PC cannot work across even half of these systems.
It is a non-starter.
```

## The 2PC Properties That Fail in Practice

| Property | What 2PC Claims | Reality |
|---|---|---|
| **Atomicity** | All commit or all rollback | Blocked indefinitely on coordinator crash |
| **Consistency** | System moves from one consistent state to another | Split state possible during partition |
| **Isolation** | Locks prevent interference | Lock hold time is seconds — kills throughput |
| **Durability** | Committed data persists | Only if coordinator survives — otherwise uncertain |

2PC trades availability for strong consistency guarantees that it cannot actually deliver under the failure modes of real distributed systems.

---

## What Pravah Uses Instead

Everything in Chapters 1.7–1.11 is the answer to 2PC. Here is the full picture:

**Problem: Atomic write to multiple databases across services**
→ **Saga Pattern (Chapter 1.8):** Local transactions + compensating transactions. No distributed locks. Each service commits locally. Failures trigger compensation in reverse.

**Problem: Atomic write to DB and Kafka**
→ **Outbox Pattern (Chapter 1.10):** Write both to the same database in one local transaction. Relay publishes to Kafka asynchronously. Idempotent producer deduplicates retries.

**Problem: Duplicate execution on retry**
→ **Idempotency Keys (Chapter 1.7):** Unique key per operation. Dedup check before execution. Staging tables for data loads. Exactly-once where required.

**Problem: Cascading failures from dependent services**
→ **Circuit Breaker + Bulkhead (Chapter 1.11):** Fail fast instead of blocking. Isolate resource pools. Prevent one failure from propagating.

**Problem: Maintaining consistency guarantee for leader election**
→ **Raft Consensus (Chapter 1.5):** Quorum-based agreement for control plane decisions. CP where it matters most.

### Side-by-Side Comparison

| Requirement | 2PC Approach | Pravah's Approach |
|---|---|---|
| Cross-service atomicity | Distributed transaction coordinator | Saga with compensating transactions |
| DB + Kafka atomicity | XA transaction | Outbox pattern |
| Exactly-once semantics | XA with Kafka | Idempotent producer + Kafka transactions |
| High availability | Blocking — crashes cause hangs | Non-blocking — sagas compensate |
| Performance | Locks for 1–5 seconds per operation | Local transactions — sub-millisecond |
| Cloud native | Requires XA support (most services lack it) | HTTP/gRPC + Kafka — any service |
| Debuggability | Distributed lock state — hard to inspect | Saga state in PostgreSQL — queryable |

## Where Pravah Does Use Distributed Transactions

Pravah does not completely eliminate distributed coordination. It uses it precisely where the trade-off is justified:

**Raft consensus for control plane decisions** — scheduler leader election, Kafka controller election, etcd cluster state. These use Raft, which provides linearizable consensus for CP decisions where correctness is critical and availability can briefly pause.

**Kafka transactions for consume-process-produce** — when consuming from one Kafka topic and producing to another as part of the same logical operation. Kafka's native transaction API handles this atomically within the Kafka ecosystem (not cross-system).

**PostgreSQL local ACID transactions** — within a single service's database. Full ACID guarantees within one database boundary, as always.

The principle: use the strongest guarantees within a single system's boundary. Never try to extend them across system boundaries with 2PC.

## System Design Interview Angles

**"Why doesn't Pravah use Two-Phase Commit for cross-service transactions?"**

> 2PC has a fundamental blocking problem. If the coordinator crashes between Phase 1 and Phase 2, all participants hold database locks and wait indefinitely — there is no safe timeout. In a distributed system with network partitions and service restarts, coordinator crashes are not exceptional events, they are routine. Additionally, most of Pravah's stack — Kafka, Redis, Elasticsearch — does not support XA transactions at all. We use sagas with compensating transactions instead: each service commits locally, and on failure, compensating transactions undo completed steps in reverse order.

**"How does Pravah achieve atomicity across PostgreSQL and Kafka without 2PC?"**

> The Outbox Pattern. We write both the business record and the Kafka message intent to the same PostgreSQL database in one local ACID transaction. A relay process then publishes from the outbox table to Kafka. This separates the atomicity guarantee (PostgreSQL's local transaction) from the eventual delivery guarantee (Kafka). The relay retries until Kafka acknowledges, and Kafka's idempotent producer deduplicates retried messages. No distributed transaction required.

**"What is the CAP theorem implication of choosing sagas over 2PC?"**

> 2PC is a CP approach that sacrifices availability — it blocks when the coordinator is unavailable. Sagas are an AP approach that sacrifices strong consistency — operations are eventually consistent through compensation rather than immediately atomic. For Pravah's use case, temporary inconsistency (a job record exists briefly with no billing entry while compensation runs) is acceptable, whereas blocking all scheduling operations for minutes during a coordinator crash is not.
