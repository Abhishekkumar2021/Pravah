1.10 The Outbox Pattern
🧩 Start With The Exact Problem
We touched on this briefly in 1.7. Now we go deep — because this pattern is foundational to every service in Pravah.

THE DUAL-WRITE PROBLEM — IN FULL DETAIL
────────────────────────────────────────────────────────────

Every Pravah service needs to do TWO things atomically:

  1. Write business state to its database
  2. Publish an event to Kafka

These are two SEPARATE systems.
You cannot wrap them in one transaction.

💡 The Outbox Pattern — Core Idea
THE KEY INSIGHT
────────────────────────────────────────────────────────────

Both problems (write DB, publish Kafka) happen because
we treat them as two separate operations.

What if we make it ONE operation?

Instead of writing to Kafka directly:
  Write to an OUTBOX TABLE in the same database.
  Same transaction as the business write.
  Either both succeed or both fail. Atomically.

Then a separate RELAY PROCESS reads the outbox
and publishes to Kafka asynchronously.

Crash safety: If relay crashes, it restarts
and retries — Kafka deduplicates.

Network partition: Outbox messages stay in DB
until Kafka is reachable again.

ANALOGY — Physical Outbox:
  You write a letter (business operation)
  Put it in your outbox tray (outbox table)
  Both done at same time, same action

  Mail carrier picks up letters (relay)
  Delivers to post office (Kafka)
  If mail carrier is sick: letters wait in tray
  When back: delivers all pending letters

  Letters never lost. Never sent before written.
  The tray is the guarantee.
🏗️ Outbox Pattern Structure
OUTBOX TABLE DESIGN IN PRAVAH
────────────────────────────────────────────────────────────

CREATE TABLE outbox (
  id              UUID PRIMARY KEY,
  aggregate_id    VARCHAR(255) NOT NULL,  -- pipe-abc
  aggregate_type  VARCHAR(100) NOT NULL,  -- Pipeline
  event_type      VARCHAR(100) NOT NULL,  -- PIPELINE_TRIGGERED
  kafka_topic     VARCHAR(255) NOT NULL,  -- pipeline.events
  kafka_key       VARCHAR(255),           -- pipe-abc (partition key)
  payload         JSONB        NOT NULL,  -- event data
  headers         JSONB,                  -- metadata, correlation IDs
  idempotency_key VARCHAR(255) NOT NULL,  -- deduplication key
  status          VARCHAR(50)  NOT NULL DEFAULT 'PENDING',
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  processed_at    TIMESTAMPTZ,
  failed_attempts INT          NOT NULL DEFAULT 0,
  last_error      TEXT,
  
  -- Ensure one attempt per idempotency key
  UNIQUE(idempotency_key)
);

-- Index for relay to find pending messages efficiently
CREATE INDEX idx_outbox_status_created 
  ON outbox(status, created_at) 
  WHERE status = 'PENDING';
The atomic write:

ATOMIC BUSINESS WRITE + OUTBOX INSERT
────────────────────────────────────────────────────────────

Scheduler triggers Pipeline-abc:

BEGIN TRANSACTION;

  -- Business operation
  INSERT INTO jobs (
    id, pipeline_id, status, idempotency_key, created_at
  ) VALUES (
    'job-xyz', 'pipe-abc', 'PENDING', 
    'pipe-abc-2024-01-15T10:00:00-attempt-1',
    NOW()
  );

  -- Outbox message (same transaction)
  INSERT INTO outbox (
    id,              aggregate_id,   aggregate_type,
    event_type,      kafka_topic,    kafka_key,
    payload,         idempotency_key
  ) VALUES (
    gen_random_uuid(), 'pipe-abc',   'Pipeline',
    'JOB_CREATED',   'job.assigned', 'pipe-abc',
    '{
      "job_id": "job-xyz",
      "pipeline_id": "pipe-abc",
      "scheduled_time": "2024-01-15T10:00:00",
      "runner_tags": ["gpu", "eu-west"],
      "params": {"date": "2024-01-15"}
    }',
    'pipe-abc-2024-01-15T10:00:00-attempt-1'
  );

COMMIT;

-- Either BOTH inserted or NEITHER inserted.
-- No partial state possible. ✅
🔄 The Relay Process — In Full Detail
OUTBOX RELAY DESIGN
────────────────────────────────────────────────────────────

The relay is a background process inside each service.
Runs continuously. Polls outbox for pending messages.
Publishes to Kafka. Marks as processed.

RELAY LOOP:
────────────

EVERY 100ms:

  Step 1: CLAIM pending messages (with lock)
  ─────────────────────────────────────────
  
  -- Claim up to 100 messages atomically
  -- SKIP LOCKED prevents multiple relay instances
  -- from picking same messages
  
  UPDATE outbox
  SET status = 'PROCESSING'
  WHERE id IN (
    SELECT id FROM outbox
    WHERE status = 'PENDING'
    ORDER BY created_at ASC
    LIMIT 100
    FOR UPDATE SKIP LOCKED  ← key: no contention
  )
  RETURNING *;

  Step 2: PUBLISH to Kafka
  ────────────────────────
  
  FOR each claimed message:
    
    KafkaProducer.send(
      topic:   message.kafka_topic,
      key:     message.kafka_key,
      value:   message.payload,
      headers: {
        "idempotency-key": message.idempotency_key,
        "correlation-id":  message.headers.correlation_id,
        "event-type":      message.event_type,
        "aggregate-id":    message.aggregate_id,
        "schema-version":  "1.0"
      }
    )
    
    -- Wait for Kafka ACK (acks=all)

  Step 3: MARK as processed (or failed)
  ──────────────────────────────────────
  
  IF Kafka ACK received:
    UPDATE outbox
    SET status = 'PROCESSED',
        processed_at = NOW()
    WHERE id = message.id;
  
  IF Kafka publish failed:
    UPDATE outbox
    SET status = 'PENDING',          -- back to pending
        failed_attempts = failed_attempts + 1,
        last_error = 'connection timeout'
    WHERE id = message.id;
    -- Will be retried next poll cycle

VISUAL RELAY TIMELINE:
────────────────────────────────────────────────────────────

t=0ms:   Poll outbox → 3 PENDING messages found
t=1ms:   Claim all 3 (status → PROCESSING)
t=2ms:   Publish msg-001 to Kafka → ACK ✅
t=3ms:   Mark msg-001 as PROCESSED
t=4ms:   Publish msg-002 to Kafka → ACK ✅
t=5ms:   Mark msg-002 as PROCESSED
t=6ms:   Publish msg-003 to Kafka → TIMEOUT ❌
t=7ms:   Mark msg-003 back as PENDING (attempt=1)
t=100ms: Poll again → msg-003 still PENDING
t=101ms: Retry publish msg-003 → ACK ✅
t=102ms: Mark msg-003 as PROCESSED ✅
💥 Failure Scenarios — All Handled
SCENARIO 1: Service crashes after DB write, before relay runs
────────────────────────────────────────────────────────────

t=0:  Transaction committed (job + outbox inserted) ✅
t=1:  💥 Service crashes
t=5:  Service restarts
t=6:  Relay starts polling
t=7:  Finds PENDING outbox message
t=8:  Publishes to Kafka ✅
t=9:  Marks PROCESSED ✅

Result: No data loss ✅

SCENARIO 2: Relay crashes after Kafka publish, before marking processed
────────────────────────────────────────────────────────────

t=0:  Relay claims msg-001 (status → PROCESSING)
t=1:  Publish to Kafka → ACK ✅
t=2:  💥 Relay crashes before UPDATE outbox SET status=PROCESSED
t=5:  Relay restarts
t=6:  Finds msg-001 stuck in PROCESSING status
t=7:  Treats PROCESSING as potentially unprocessed
t=8:  Retries publish to Kafka

      Kafka receives DUPLICATE!
      
      But Kafka producer is IDEMPOTENT:
        producer_id + sequence_number same as before
        Kafka broker deduplicates → one message stored ✅

Result: Exactly-once delivery despite crash ✅

SCENARIO 3: Kafka partition down for 5 minutes
────────────────────────────────────────────────────────────

t=0:   Kafka partition leader fails
t=0-5: Messages accumulate in outbox (PENDING)
t=0-5: Relay retries every 100ms → fails each time
t=0-5: failed_attempts increments
t=5:   New Kafka partition leader elected
t=6:   Relay succeeds → publishes all pending ✅

Result: No messages lost. Delivered in order.
        5 minute delay — acceptable for Pravah ✅

SCENARIO 4: PROCESSING messages stuck (relay never recovered)
────────────────────────────────────────────────────────────

msg-001 stuck in PROCESSING for >5 minutes
Relay that claimed it is dead (never completed)

STUCK MESSAGE RECOVERY:
  Separate watchdog process runs every minute:
  
  UPDATE outbox
  SET status = 'PENDING',
      failed_attempts = failed_attempts + 1
  WHERE status = 'PROCESSING'
  AND updated_at < NOW() - INTERVAL '5 minutes';
  
  Message goes back to PENDING.
  Next relay poll picks it up. ✅
🚨 Dead Letter Handling
WHAT IF A MESSAGE KEEPS FAILING?
────────────────────────────────────────────────────────────

After 5 failed attempts → message is a DEAD LETTER.
Something is structurally wrong (bad payload, wrong topic).
Retrying forever just clogs the system.

DEAD LETTER FLOW:
  ┌─────────────────────────────────────────────────────┐
  │  failed_attempts >= 5                               │
  │         │                                           │
  │         ▼                                           │
  │  UPDATE outbox SET status = 'DEAD'                  │
  │                                                     │
  │  INSERT INTO dead_letter_outbox (                   │
  │    original_message,                                │
  │    failure_reason,                                  │
  │    failed_at                                        │
  │  )                                                  │
  │         │                                           │
  │         ▼                                           │
  │  Alert on-call:                                     │
  │    "Outbox message dead: job.assigned               │
  │     for pipe-abc. Manual intervention needed."      │
  │         │                                           │
  │         ▼                                           │
  │  UI: Dead Letter Queue viewer                       │
  │    Shows dead messages with error details           │
  │    Operator can:                                    │
  │      → Replay (fix and re-queue)                    │
  │      → Discard (acknowledge skip)                   │
  └─────────────────────────────────────────────────────┘
🔀 Multiple Relay Instances (Scaling)
RUNNING MULTIPLE RELAY INSTANCES SAFELY
────────────────────────────────────────────────────────────

Single relay = single point of failure.
Multiple relays = parallel processing but dangerous
if they claim same messages.

Solution: FOR UPDATE SKIP LOCKED

  Relay-1 runs:
    SELECT ... FOR UPDATE SKIP LOCKED
    → Claims messages 1, 2, 3 (locks them)
  
  Relay-2 runs simultaneously:
    SELECT ... FOR UPDATE SKIP LOCKED
    → Sees messages 1, 2, 3 are LOCKED
    → Skips them, claims messages 4, 5, 6
  
  No contention. No duplicates. ✅
  
  Both relays work in parallel:
    Relay-1: processes 1, 2, 3
    Relay-2: processes 4, 5, 6
    
    Throughput doubles! ✅

PRAVAH RELAY DEPLOYMENT:
  2 relay threads per service instance
  3 service instances = 6 relay threads total
  Each claims up to 100 messages
  = 600 messages processed per 100ms cycle
  = 6,000 messages/second throughput
  Plenty for Pravah's workload ✅

🔗 Outbox + Event Sourcing + Saga Together
HOW ALL THREE PATTERNS CONNECT IN PRAVAH
────────────────────────────────────────────────────────────

USER TRIGGERS PIPELINE:

1. EVENT SOURCING (Write side)
   ─────────────────────────────
   Command: TriggerPipelineCommand
   
   BEGIN TRANSACTION
     -- Event sourcing: append to event store
     INSERT INTO events (
       aggregate_id='pipe-abc',
       seq=10,
       type='PIPELINE_TRIGGERED',
       payload={...}
     )
     
     -- Outbox: relay to Kafka
     INSERT INTO outbox (
       event_type='PIPELINE_TRIGGERED',
       kafka_topic='pipeline.events',
       payload={...}
     )
   COMMIT
   (atomic ✅)

2. OUTBOX RELAY
   ─────────────────────────────
   Relay picks up outbox message
   Publishes to Kafka: pipeline.events
   Marks PROCESSED

3. SAGA ORCHESTRATOR (triggered by Kafka event)
   ─────────────────────────────────────────────
   Execution Service consumes pipeline.events
   
   Saga: JobLaunchSaga starts
   
   Step 1: Call Pipeline Service
   
   BEGIN TRANSACTION (Pipeline Service)
     -- Create job record
     INSERT INTO jobs (id='job-xyz', ...)
     
     -- Outbox: notify next saga step
     INSERT INTO outbox (
       event_type='JOB_CREATED',
       kafka_topic='job.assigned',
       payload={...}
     )
   COMMIT
   (atomic ✅)
   
   Step 2, 3, 4... each service:
     Does its work + writes to outbox atomically
     Relay publishes to Kafka
     Saga orchestrator advances state

4. READ SIDE UPDATES (CQRS)
   ─────────────────────────────
   Kafka consumers receive all events
   Update read models (PostgreSQL views, ES, Redis)
   UI shows current pipeline state

RESULT:
  No distributed transactions ✅
  No data loss on crashes ✅
  Exactly-once semantics ✅
  Full event history (event sourcing) ✅
  Compensatable failures (saga) ✅
  Fast reads (CQRS read models) ✅
🎯 FAANG Interview Angles
❓ "How does Pravah guarantee that a pipeline
    trigger always results in a Kafka event,
    even if the service crashes?"

Good answer:
  "We use the Outbox pattern. When a pipeline
   is triggered, we write both the job record
   and an outbox message in a single PostgreSQL
   transaction. Either both succeed or neither
   does — atomically.
   
   A background relay process polls the outbox
   table using SELECT FOR UPDATE SKIP LOCKED and
   publishes to Kafka. If the relay crashes after
   publishing but before marking processed, it
   retries on restart — Kafka's idempotent producer
   deduplicates using producer ID and sequence
   number. Messages in the outbox are never lost
   — they wait until Kafka is available."

❓ "What is SELECT FOR UPDATE SKIP LOCKED
    and why does Pravah use it?"

Good answer:
  "It's a PostgreSQL feature for concurrent queue
   processing. FOR UPDATE locks selected rows.
   SKIP LOCKED skips rows already locked by another
   transaction instead of blocking.
   
   Multiple relay threads run in parallel. Without
   SKIP LOCKED, all threads would block on the same
   rows — serializing what should be parallel work.
   With SKIP LOCKED, each thread claims its own
   batch of messages with zero contention.
   Pravah runs 6 relay threads, each claiming 100
   messages — processing 600 messages per 100ms
   cycle without any thread waiting for another."

❓ "How does Pravah handle messages that keep
    failing to publish to Kafka?"

Good answer:
  "After 5 failed attempts, a message is moved
   to dead letter status. A separate watchdog
   moves these to a dead_letter_outbox table and
   fires a PagerDuty alert. Pravah's UI has a
   Dead Letter Queue viewer where operators can
   inspect the failure reason, fix the payload
   if needed, and replay the message — or
   acknowledge it as intentionally skipped.
   This prevents bad messages from blocking
   healthy ones in the processing pipeline."
📌 Key Takeaways
1. Dual-write problem: writing to DB and Kafka
   separately always risks inconsistency on crash

2. Outbox pattern: write both to same DB atomically
   Relay process publishes to Kafka asynchronously

3. FOR UPDATE SKIP LOCKED enables safe parallel
   relay processing without contention

4. Three crash scenarios all handled:
   → Crash before relay: messages wait in outbox
   → Crash after publish: idempotent producer dedups
   → Kafka down: messages wait until available

5. Dead letter handling: after N failures,
   quarantine + alert + manual replay UI

6. Every Pravah service has its own outbox table
   (DB per service principle maintained)

7. Outbox + Event Sourcing + CQRS + Saga =
   complete, crash-safe, distributed state
   management foundation for Pravah
