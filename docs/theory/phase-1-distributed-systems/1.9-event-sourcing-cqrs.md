# 1.9 Event Sourcing & CQRS

## 🧩 Start With a Problem

Let's look at how most systems store data — and where it falls short for Pravah.

TRADITIONAL STATE STORAGE

Pipeline-abc in our database:

```text
  ┌─────────────────────────────────────────────────┐
  │              pipelines table                    │
  │                                                 │
  │  id       │ name      │ status  │ updated_at   │
  │  ─────────────────────────────────────────────  │
  │  pipe-abc │ Sales ETL │ FAILED  │ 10:45:23     │
  └─────────────────────────────────────────────────┘
```

This tells us: Pipeline is currently FAILED.

What it CANNOT tell us:
  ❓ Why did it fail?
  ❓ How many times has it run?
  ❓ Was it RUNNING before FAILED?
  ❓ Who changed the config 3 days ago?
  ❓ What was the pipeline doing at 09:30?
  ❓ Which exact transformation caused the failure?
  ❓ What data did it process last Tuesday?

We overwrote history. It's gone.
This is a critical problem for Pravah because:

PRAVAH NEEDS FULL HISTORY FOR:

Debugging:
  "Why did the pipeline fail at 3am?"
```text
  → Need full sequence of events leading to failure
```

Audit & Compliance:
  "Who changed the pipeline config before the GDPR breach?"
```text
  → Need immutable record of every change
```

Agent Auto-Healing:
  "What pattern of events precedes failure?"
```text
  → Agent needs event history to learn from
```

Data Lineage:
  "Which exact run produced this output file?"
```text
  → Need traceable history of every execution
```

Backfill Safety:
  "Re-run pipeline for last 30 days"
```text
  → Need to know exactly what happened each day
```

Time-Travel Debugging:
  "Show me Pravah's state at 09:30 yesterday"
```text
  → Must be able to reconstruct past state
```

Instead of storing CURRENT STATE:

🏗️ Event Sourcing Structure
ANATOMY OF AN EVENT IN PRAVAH

Every event has:

{
  event_id:        "evt-001"           // unique ID
  event_type:      "PIPELINE_TRIGGERED" // what happened
  aggregate_id:    "pipe-abc"          // what entity
  aggregate_type:  "Pipeline"          // entity type
  sequence_number: 7                   // order in stream
  timestamp:       "10:00:00.001"      // when (HLC)
  actor:           "scheduler-1"       // who caused it
  payload: {                           // event data
    triggered_by:  "cron",
    scheduled_for: "10:00:00",
    params:        { date: "2024-01-15" }
  },
  metadata: {
    correlation_id: "corr-xyz",        // trace across services
    causation_id:   "evt-006",         // which event caused this
    schema_version: "1.0"              // for evolution
  }
}

AGGREGATE = entity whose events we track
  Pipeline is an aggregate
  Runner is an aggregate
  Job is an aggregate
  Tenant is an aggregate
The event store:

PRAVAH EVENT STORE STRUCTURE
```text
────────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────┐
│                    event_store table                     │
├──────────────┬──────────────┬──────┬────────────────────┤
│ aggregate_id │ seq_number   │ type │ payload            │
├──────────────┼──────────────┼──────┼────────────────────┤
│ pipe-abc     │ 1            │CREAT │ {name: Sales ETL}  │
│ pipe-abc     │ 2            │CONFI │ {tasks: [...]}     │
│ pipe-abc     │ 3            │SCHED │ {cron: "0 10 * *"} │
│ pipe-abc     │ 4            │TRIGG │ {triggered_by:cron}│
│ pipe-abc     │ 5            │RUNNI │ {runner: r-001}    │
│ pipe-abc     │ 6            │TASKC │ {task: extract}    │
│ pipe-abc     │ 7            │TASKC │ {task: transform}  │
│ pipe-abc     │ 8            │TASKF │ {task: load,       │
│              │              │      │  error: conn_err}  │
│ pipe-abc     │ 9            │FAILD │ {reason: task_fail}│
│              │              │      │                    │
│ runner-001   │ 1            │REGIS │ {tags: [gpu]}      │
│ runner-001   │ 2            │ASSIG │ {job: job-xyz}     │
│ runner-001   │ 3            │HEART │ {load: 0.75}       │
└──────────────┴──────────────┴──────┴────────────────────┘
```

RULES:
  ✅ Events are IMMUTABLE — never update or delete
  ✅ Events are APPEND-ONLY — only new events added
  ✅ Sequence numbers are MONOTONICALLY INCREASING
  ✅ Optimistic locking: expect seq_number = N,
     reject if another event got there first
🔄 Rebuilding State From Events
STATE RECONSTRUCTION — PIPELINE AGGREGATE

Pipeline starts as empty object:
  PipelineState { id: null, status: null, tasks: [] }

Apply event 1: PIPELINE_CREATED
  PipelineState {
    id:     "pipe-abc",
    name:   "Sales ETL",
    status: CREATED,
    tasks:  []
  }

Apply event 2: PIPELINE_CONFIGURED
  PipelineState {
    id:     "pipe-abc",
    name:   "Sales ETL",
    status: CONFIGURED,
    tasks:  [extract, transform, load]
  }

Apply event 3: PIPELINE_SCHEDULED
  PipelineState {
    ...
    status:   SCHEDULED,
    cron:     "0 10 * * *",
    next_run: "2024-01-15T10:00:00"
  }

```yaml
Apply events 4-9: TRIGGERED → RUNNING → tasks → FAILED
  PipelineState {
    id:           "pipe-abc",
    status:       FAILED,
    last_run:     "2024-01-15T10:00:00",
    failed_at:    "2024-01-15T10:45:23",
    failed_task:  "load",
    error:        "connection_error"
  }
```

This is exactly the current state.
And we can stop at ANY point in history:

  "What was pipeline-abc's state at 10:30?"
```text
  → Replay events 1 through 7 (up to 10:30)
  → Get state at that exact moment ✅
⚡ The Performance Problem — Snapshots
THE REPLAY COST PROBLEM
────────────────────────────────────────────────────────────
```

Pipeline has been running for 1 year:
  365 days × 24 runs/day = 8,760 runs
  Each run generates ~20 events
  Total: 175,200 events for one pipeline

Every time we need pipeline state:
```text
  Replay 175,200 events → very slow! 😱
```

SOLUTION: SNAPSHOTS

Periodically save a snapshot of current state.
On next load: start from snapshot, not from beginning.

```text
  ┌──────────────────────────────────────────────────────┐
  │                  snapshots table                     │
  ├──────────────────┬────────────┬──────────────────────┤
  │  aggregate_id    │ seq_number │ state_json           │
  ├──────────────────┼────────────┼──────────────────────┤
  │  pipe-abc        │ 8750       │ { id: pipe-abc,      │
  │                  │            │   status: SCHEDULED, │
  │                  │            │   runs: 437,         │
  │                  │            │   ... }              │
  └──────────────────┴────────────┴──────────────────────┘
```

LOADING STATE WITH SNAPSHOT:
```text
  1. Load latest snapshot (seq 8750) → base state
  2. Load events from seq 8751 onwards → small set
  3. Apply those events to snapshot state
  4. Get current state in milliseconds ✅
```

SNAPSHOT STRATEGY IN PRAVAH:
  Take snapshot every 100 events per aggregate
  Or every 24 hours for active pipelines
  Snapshots stored in PostgreSQL JSONB column
  Old snapshots retained for time-travel queries
📊 CQRS — Command Query Responsibility Segregation
Event sourcing naturally leads to CQRS. They're separate concepts but work beautifully together.

THE READ PROBLEM WITH EVENT SOURCING

Event store is optimized for WRITES:
  Append events quickly
  Reconstruct aggregate state

But UI needs complex READS:
  "Show all FAILED pipelines for tenant-xyz,
   ordered by failure time, with last 3 run stats,
   runner info, and failure reason"

This query across event streams = EXPENSIVE.
  Replay all pipeline aggregates?
  Filter failed ones?
```sql
  Join with runner events?
  → Impossible in real-time ❌
CQRS separates reads and writes:
```

CQRS — THE CORE SPLIT

WITHOUT CQRS (traditional):
```text
  ┌──────────────────────────────────────────┐
  │  Single Model                            │
  │  Same database, same schema              │
  │  Handles reads AND writes                │
  │                                          │
  │  Problem: Write optimization ≠           │
  │           Read optimization              │
  └──────────────────────────────────────────┘

WITH CQRS:
  ┌──────────────────────────────────────────────────────┐
  │                                                      │
  │   WRITE SIDE (Commands)   │   READ SIDE (Queries)   │
  │                           │                         │
  │   Command: "TriggerPipe"  │   Query: "GetFailed     │
  │            "ConfigPipe"   │           Pipelines"    │
  │            "CancelJob"    │          "GetRunStats"  │
  │                           │                         │
  │   Command Handler         │   Query Handler         │
  │   validates + executes    │   reads from            │
  │                           │   read model            │
  │   Writes to:              │                         │
  │   Event Store             │   Reads from:           │
  │   (append-only)           │   Read DB               │
  │                           │   (optimized views)     │
  │                           │                         │
  │   Publishes events ───────────────────────────────► │
  │   to Kafka                │   Event Handlers        │
  │                           │   update read models    │
  └──────────────────────────────────────────────────────┘
```

⚡ Eventual Consistency in CQRS
THE CONSISTENCY GAP

Write path: Event appended to store ✅
Kafka event published ✅
Read model updated... eventually ✅

There is a GAP between write and read model update.
Could be milliseconds. Could be seconds under load.

SCENARIO:
  t=0:  User triggers pipeline (write path)
  t=0:  Event appended to event store
  t=1:  Event published to Kafka
  t=2:  User refreshes dashboard (read path)
  t=3:  Kafka consumer processes event
  t=3:  Read model updated

  At t=2: User sees pipeline still as SCHEDULED
          (read model not yet updated)
```text
  At t=4: User refreshes again → sees RUNNING ✅
```

This is EVENTUAL CONSISTENCY — acceptable for Pravah UI.

HANDLING THE GAP IN PRAVAH UI:
  Option 1: Optimistic UI update
    When user clicks "Trigger":
      Immediately show "TRIGGERING..." in UI
      Don't wait for read model
```sql
      Update confirmed when event arrives
```

  Option 2: Read-your-writes
    After command: store event_id in user session
    Read model query: "give me current state,
    but wait until you've processed event_id=X"
    Read model waits for event to be processed
    Then returns ✅

  Pravah uses Option 1 for better UX.

```text
🎯 FAANG Interview Angles
❓ "How does Pravah maintain a complete audit trail
    of all pipeline changes?"
```

Good answer:
  "Pravah uses event sourcing for all core aggregates.
   Every change — config update, trigger, failure,
   compensation — is an immutable event appended to
   the event store. Events are never updated or deleted.
   
   For audit queries, we replay events up to any
   point in time. For compliance, we expose a
   time-travel API: 'show me pipeline state at
   2024-01-15T10:30:00'. This gives us perfect
   auditability without any additional audit table
   design — it's intrinsic to the storage model."

❓ "Why does Pravah use CQRS alongside event sourcing?"

Good answer:
  "Event sourcing optimizes writes — fast appends,
   aggregate reconstruction. But UI queries are
   complex: 'all failed pipelines for tenant X,
```sql
   with run stats, ordered by failure time.'
   Replaying events for every such query is
   impractical.
```
   
   CQRS solves this by maintaining separate read
   models — PostgreSQL views for filtering, 
   Elasticsearch for search, Redis for agent context.
   Kafka consumers update these models as events
   arrive. Reads are fast, pre-materialized queries
   against purpose-built schemas. The trade-off is
   eventual consistency between write and read sides
   — acceptable for our UI use cases."

❓ "How does Pravah's auto-heal agent know
    what caused a pipeline failure?"

Good answer:
  "The agent queries the event store directly.
   On failure detection, it loads all events
   for that pipeline in the last hour. It sees
   the causal chain: schema changed at 10:20,
   transform started failing at 10:21, pipeline
   failed at 10:45. The agent uses this event
   sequence as context when calling the LLM —
   'here are the events that led to this failure,
   suggest a fix.' Event sourcing gives the agent
   perfect, unambiguous history to reason about."

## 📌 Key Takeaways

1. Traditional state storage loses history —
   event sourcing preserves everything forever

2. Event sourcing: store events, derive state
   Current state = replay all events from beginning

3. Snapshots prevent full replay cost:
   Load snapshot + recent events only

4. CQRS separates write model (event store)
```sql
   from read models (purpose-built views)
```

5. Multiple read models serve different needs:
   PostgreSQL for filtering, ES for search,
   Redis for agent, TimescaleDB for SLA metrics

6. Eventual consistency gap between write
   and read side — handle with optimistic UI

7. Time travel = replay events up to any timestamp
   Critical for debugging, compliance, agent healing

8. Event sourcing + CQRS is the foundation of
   Pravah's observability and agent intelligence
