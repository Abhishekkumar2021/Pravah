# 1.9 Event Sourcing & CQRS

## The Limitation of Traditional State Storage

Most systems store only the current state:

```
pipelines table:
  id       │ name      │ status │ updated_at
  pipe-abc │ Sales ETL │ FAILED │ 10:45:23
```

This answers "what is the current status." It cannot answer:
- Why did it fail?
- How many times has it run?
- Was it RUNNING before FAILED?
- Who changed the config 3 days ago?
- What data did it process last Tuesday?
- Which exact transformation caused the failure?

History is overwritten. It is gone.

Pravah needs full history for debugging, compliance audits, agent auto-healing, data lineage, backfill safety, and time-travel debugging.

---

## Event Sourcing — The Core Idea

Instead of storing the current state, store every event that ever happened:

```
pipe-abc event log:
  seq  type                      when
  ─────────────────────────────────────────
  1    PIPELINE_CREATED           09:00:00
  2    PIPELINE_CONFIGURED        09:01:15
  3    PIPELINE_SCHEDULED         09:55:00
  4    PIPELINE_TRIGGERED         10:00:00
  5    PIPELINE_RUNNING           10:00:05
  6    TASK_COMPLETED (extract)   10:15:00
  7    TASK_COMPLETED (transform) 10:30:00
  8    TASK_FAILED (load)         10:45:00
  9    PIPELINE_FAILED            10:45:23
```

**Current state = apply all events in sequence from the beginning.**

The bank account analogy makes this concrete:

| Traditional | Event Sourced |
|---|---|
| `balance = ₹15,000` (just a number) | ACCOUNT_OPENED: ₹0 → DEPOSIT: +₹20,000 → WITHDRAWAL: -₹5,000 → DEPOSIT: +₹8,000 → WITHDRAWAL: -₹8,000 |

Both give you `₹15,000`. But the event-sourced version also tells you: balance on any past date, all large withdrawals, who authorized each transaction.

## Anatomy of an Event

Every event in Pravah is an immutable record:

```json
{
  "event_id":        "evt-001",
  "event_type":      "PIPELINE_TRIGGERED",
  "aggregate_id":    "pipe-abc",
  "aggregate_type":  "Pipeline",
  "sequence_number": 4,
  "timestamp":       "10:00:00.001",
  "actor":           "scheduler-1",
  "payload": {
    "triggered_by":  "cron",
    "scheduled_for": "10:00:00",
    "params":        { "date": "2024-01-15" }
  },
  "metadata": {
    "correlation_id": "corr-xyz",
    "causation_id":   "evt-003",
    "schema_version": "1.0"
  }
}
```

- `aggregate_id` — the entity whose lifecycle this event belongs to (Pipeline, Runner, Job, Tenant)
- `sequence_number` — monotonically increasing per aggregate; used for optimistic locking
- `causation_id` — which prior event caused this one (enables causal chain reconstruction)

**Rules that make event sourcing work:**
- Events are **immutable** — never update or delete
- Events are **append-only** — only new events are added
- Sequence numbers are **monotonically increasing**

## Rebuilding State From Events

The **aggregate** starts as an empty object, then each event is applied in sequence:

```
Initial state: PipelineState { status: null, tasks: [] }

Apply event 1 (PIPELINE_CREATED):
  → { id: "pipe-abc", name: "Sales ETL", status: CREATED }

Apply event 2 (PIPELINE_CONFIGURED):
  → { ..., status: CONFIGURED, tasks: [extract, transform, load] }

Apply event 3 (PIPELINE_SCHEDULED):
  → { ..., status: SCHEDULED, cron: "0 10 * * *" }

Apply events 4–9 (trigger → run → tasks → fail):
  → { ..., status: FAILED, failed_task: "load", error: "connection_error" }
```

This is the current state. And you can stop at any event:

```
"What was pipeline-abc's state at 10:30 yesterday?"
→ Replay events 1–7 (all events with timestamp ≤ 10:30)
→ Get exact state at that moment ✅
```

## Snapshots — Solving the Replay Cost

A pipeline running for one year generates roughly `365 × 24 runs × 20 events = 175,200 events`. Replaying all of these on every state load is too slow.

**Snapshots** periodically capture the materialized state:

```
┌──────────────────┬────────────┬────────────────────────────────┐
│  aggregate_id    │ seq_number │ state_json                     │
├──────────────────┼────────────┼────────────────────────────────┤
│  pipe-abc        │ 8750       │ { status: SCHEDULED,           │
│                  │            │   runs: 437, cron: "0 10 * *", │
│                  │            │   last_success: "2024-01-14" } │
└──────────────────┴────────────┴────────────────────────────────┘
```

Loading state with a snapshot:
1. Load the latest snapshot (e.g., seq 8750) → base state
2. Load only events from seq 8751 onwards → small set
3. Apply those events to the snapshot state
4. Current state in milliseconds ✅

Pravah takes snapshots every 100 events per aggregate, or every 24 hours for active pipelines. Old snapshots are retained for time-travel queries.

## CQRS — Command Query Responsibility Segregation

Event sourcing optimizes for writes (fast appends, aggregate reconstruction). But UI queries are complex:

> "Show all FAILED pipelines for tenant-xyz, ordered by failure time, with last 3 run stats and failure reason."

Replaying events for every such query is impractical. **CQRS** solves this by separating the write model from the read model:

```
WRITE SIDE (Commands)            READ SIDE (Queries)
─────────────────────            ───────────────────
TriggerPipeline                  GetFailedPipelines
ConfigurePipeline                GetRunHistory
CancelJob                        GetLineageGraph

Writes to:                       Reads from:
  Event Store                      Pre-built read models
  (append-only)                    (purpose-built schemas)
```

Kafka connects the two sides: events appended to the event store are published to Kafka, and consumers update the various read models.

**Pravah's read models:**

| Read Model | Store | Optimized For |
|---|---|---|
| Pipeline summaries | PostgreSQL views | Dashboard list views, filtering, sorting |
| Full-text search | Elasticsearch | Search by name, tag, description |
| Run history | PostgreSQL (partitioned by month) | SLA analysis, time-series queries |
| Lineage graph | Elasticsearch / Neo4j | Impact analysis, graph traversal |
| Agent context | Redis | Fast lookups during auto-heal decisions |

The write path appends one event. The read path queries a pre-materialized view optimized for that exact access pattern.

---

## Eventual Consistency Between Write and Read

There is a small gap between when an event is appended (write path) and when the read model is updated (after Kafka consumption):

```
t=0  User triggers pipeline (write path)
t=0  Event appended to event store
t=1  Event published to Kafka
t=2  User refreshes dashboard (read path)
     → Read model not yet updated → shows SCHEDULED (stale) 
t=3  Kafka consumer processes event, updates read model
t=4  User refreshes → sees RUNNING ✅
```

This is **eventual consistency** — acceptable for Pravah's UI use cases. Pravah handles the gap with **optimistic UI updates**: when a user clicks "Trigger", the UI immediately shows "TRIGGERING…" without waiting for the read model to catch up.

## Time-Travel Debugging

```
Request: GET /pipelines/pipe-abc/state?at=2024-01-14T10:30:00

Implementation:
  1. Load latest snapshot BEFORE 10:30
     → Snapshot at seq 8748, timestamp 09:55:00

  2. Load events from seq 8749 WHERE timestamp ≤ 10:30
     → Events 8749, 8750, 8751, 8752

  3. Apply those events to the snapshot state

  4. Return exact pipeline state at 10:30:
     {
       status: "RUNNING",
       current_task: "transform",
       records_processed: 45_230,
       transform_started_at: "10:15:00"
     }
```

The auto-heal agent uses exactly this for root cause analysis:

```
Agent detects failure at 10:45.
Agent queries: "Give me all events for pipe-abc from 10:15 to 10:45."

Events show:
  10:20  SCHEMA_CHANGED {table: orders, added_column: tax_rate}
  10:21  TASK_FAILED    {task: transform, error: "column not found: tax_rate"}
  10:45  PIPELINE_FAILED

Agent concludes: "Schema change at 10:20 caused the transform to fail."
Agent suggests:  "Update transform SQL to handle the new tax_rate column."
```

## System Design Interview Angles

**"How does Pravah maintain a complete audit trail of all pipeline changes?"**

> Pravah uses event sourcing for all core aggregates. Every change — config update, trigger, failure, compensation — is an immutable event appended to the event store. Events are never updated or deleted. For audit queries, we replay events up to any point in time. For compliance, we expose a time-travel API: `GET /pipelines/pipe-abc/state?at=2024-01-15T10:30:00`. Auditability is intrinsic to the storage model — no separate audit table needed.

**"Why does Pravah use CQRS alongside event sourcing?"**

> Event sourcing optimizes writes — fast appends, aggregate reconstruction. But UI queries are complex: "all failed pipelines for tenant X, with run stats, ordered by failure time." Replaying events for every such query is impractical. CQRS solves this by maintaining purpose-built read models — PostgreSQL views for filtering, Elasticsearch for search, Redis for agent context. Kafka consumers update these models as events arrive. Reads are fast queries against pre-materialized schemas. The trade-off is eventual consistency between write and read sides — acceptable for our UI use cases.

**"How does Pravah's auto-heal agent know what caused a pipeline failure?"**

> The agent queries the event store for all events in the relevant time window. It sees the causal chain: schema changed at 10:20, transform started failing at 10:21, pipeline failed at 10:45. The agent uses this event sequence as context when calling the LLM — "here are the events that led to this failure; suggest a fix." Event sourcing gives the agent perfect, unambiguous history to reason about.

---

## 📌 Key Takeaways

1. Traditional state storage loses history; event sourcing preserves everything forever
2. **Event sourcing:** store events, derive state; current state = replay all events
3. **Snapshots** prevent full replay cost: load snapshot + recent events only
4. **CQRS** separates write model (event store) from read models (purpose-built views)
5. Multiple read models serve different needs: PostgreSQL, Elasticsearch, Redis, TimescaleDB
6. **Eventual consistency** gap between write and read sides — handle with optimistic UI updates
7. **Time travel** = replay events up to any timestamp — critical for debugging, compliance, agent healing
