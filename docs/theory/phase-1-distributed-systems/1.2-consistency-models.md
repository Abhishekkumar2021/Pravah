# 1.2 Consistency Models — Strong, Sequential, Causal, Eventual

## Why Consistency Is a Spectrum

In 1.1 we learned CAP says "choose consistency or availability." But consistency is not binary. It is a spectrum with four distinct levels, each making a different promise about what you read after a write:

```
STRONGEST                                               WEAKEST
    │                                                       │
    ▼                                                       ▼
┌──────────────┐  ┌─────────────┐  ┌─────────┐  ┌──────────────┐
│Linearizable  │  │ Sequential  │  │ Causal  │  │  Eventual    │
│              │  │Consistency  │  │Consist. │  │ Consistency  │
└──────────────┘  └─────────────┘  └─────────┘  └──────────────┘
  Highest cost      Strong but        Cause &      Best effort,
  One copy          relaxed timing    effect        no timing
  illusion                            preserved     guarantee
```

Each level you go weaker, you gain performance and availability. You choose the weakest level that still keeps your data correct.

---

## Linearizability (Strongest)

**The promise:** Once a write completes, every subsequent read from any node by any client sees that write. The system behaves as if there is exactly one copy of the data.

```
Client A writes:  Pipeline X = RUNNING
                  ──────┤ write completes
                        │
Client B reads:         ├──► Node 1: Pipeline X = RUNNING  ✅
Client C reads:         ├──► Node 2: Pipeline X = RUNNING  ✅
Client D reads:         └──► Node 3: Pipeline X = RUNNING  ✅
```

Every node immediately reflects the write. No node ever returns an old value after the write completes.

**Analogy:** You deposit ₹10,000 at an ATM. You walk to the next ATM in the same building and check your balance — it shows the deposit. The world has one truth about your account.

**The cost:** Every write requires cross-node coordination before confirming:

```
Client ──► Node A:  "Write Pipeline X = RUNNING"
Node A ──► Node B:  "Confirm you received this"
Node A ──► Node C:  "Confirm you received this"
Node B ──► Node A:  "Confirmed"
Node C ──► Node A:  "Confirmed"
Node A ──► Client:  "Write successful"
```

Every write involves multiple network round trips → high latency, low throughput.

**Where Pravah uses it:**
- Pipeline version being executed (wrong version = data corruption)
- Leader election result (all nodes must agree on exactly one leader)
- Secret values from HashiCorp Vault (all services must read the same credentials)

---

## Sequential Consistency

**The promise:** All operations appear to execute in some total sequential order, and every node sees the same order. But that order does not have to match real-world timestamps.

```
Real world time ─────────────────────────────────────►
Client A:  Write X=1
Client B:             Write X=2

Linearizable view (must match real time):
  All nodes see: X=1 then X=2  ✅

Sequential consistent view (order may differ from real time):
  All nodes see: X=2 then X=1  ✅  — valid, as long as all nodes agree
```

The key: all nodes must see the **same** order, whatever it is. They just don't have to match wall-clock time.

**Analogy:** Everyone in a movie theatre watches the same film with scenes in the same order — even though the scenes may have been filmed non-linearly.

**Where Pravah uses it:**
- Kafka consumption within a single partition: all consumers in a consumer group see events in the same order, even if absolute timestamps vary between brokers
- Task execution ordering within a DAG: Task B always runs after Task A completes, regardless of system clock skew

---

## Causal Consistency

**The promise:** Causally related operations are seen in the same order by all nodes. Unrelated (concurrent) operations can be seen in any order.

Two events are causally related if:
- B happened after A **on the same node**, or
- B happened because A caused it (B read what A wrote)

```
Causally linked actions in Pravah:
  t1: User creates Pipeline X
  t2: User adds a Task to Pipeline X      (depends on t1)
  t3: User schedules Pipeline X to run   (depends on t2)
  t4: User views the run logs            (depends on t3)

Every node sees: t1 → t2 → t3 → t4  ✅

Unrelated concurrent actions:
  t5: User Z updates their profile
  t6: User Y creates a totally different Pipeline W

Node A sees: t5 → t6  ✅
Node B sees: t6 → t5  ✅  — both valid, they are not causally linked
```

**Analogy:** In a WhatsApp group, everyone must see Rohan's message before Priya's reply to it (causal dependency). But a "good morning" from someone else can appear in any order on different phones.

**Where Pravah uses it:**
- Pipeline lifecycle state transitions: `CREATED → CONFIGURED → SCHEDULED → RUNNING`
- Agent actions: failure event must be recorded before the healing suggestion that responds to it
- Data lineage graph: Extract event must precede Transform event in the lineage chain

---

## Eventual Consistency (Weakest)

**The promise:** If no new updates are made, all nodes will eventually converge to the same value. No guarantee on timing, no guarantee on what you read in the interim.

```
t=0:  Write "Runner-001 tags = [gpu, eu-west]" → Node A
      Node A: [gpu, eu-west]  ← updated
      Node B: [gpu]           ← stale
      Node C: [gpu]           ← stale

t=1:  Node A replicates to Node B
      Node A: [gpu, eu-west]
      Node B: [gpu, eu-west]  ← caught up
      Node C: [gpu]           ← still stale

t=2:  Node B replicates to Node C
      All nodes: [gpu, eu-west]  ✅ converged
```

How long does t=0 to t=2 take? Milliseconds, seconds, or minutes — the system makes no promise.

**Analogy:** DNS propagation. You update your domain's IP. Your laptop resolves the new IP immediately; a colleague's laptop still gets the old one; someone in another country gets the old one for hours. Eventually everyone converges.

**Where Pravah uses it:**
- Runner capability tags in Redis: a scheduler might assign a job based on slightly stale tags; the runner validates and rejects if needed, and the scheduler reassigns
- Data catalog metadata in Elasticsearch: a new dataset may not appear in search for a few seconds
- Pipeline run statistics: counters can be off by 1–2 for a short window

---

## Pravah's Full Consistency Map

| Data | Consistency Level | Why |
|---|---|---|
| Pipeline definitions (PostgreSQL primary) | **Linearizable** | Wrong version = data corruption |
| Leader election result (Redis lock) | **Linearizable** | Split-brain = chaos |
| Secret values (HashiCorp Vault) | **Linearizable** | Security-critical |
| Kafka event order within a partition | **Sequential** | Order matters; real-time less so |
| Pipeline lifecycle state transitions | **Causal** | Can't run before creating |
| Data lineage events | **Causal** | Extract must precede Transform in graph |
| Runner capability tags (Redis) | **Eventual** | Slight staleness is acceptable |
| Data catalog (Elasticsearch) | **Eventual** | Search lag is fine |
| Pipeline statistics / counters | **Eventual** | Approximate is acceptable |

---

## How They Map to CAP

CP systems tend to offer Linearizability or Sequential Consistency. AP systems tend to offer Causal or Eventual Consistency.

Pravah deliberately uses CP stores (PostgreSQL) for data requiring linearizability, and AP stores (Redis, Elasticsearch) where eventual or causal consistency is sufficient. The cost of linearizability everywhere would make the system unnecessarily slow.

## System Design Interview Angles

**"How does Pravah ensure a pipeline isn't run with a stale configuration?"**

> Pipeline definitions are read with linearizable consistency from the PostgreSQL primary. We never read from replicas for execution-critical config. The scheduler always has the exact current version before dispatching a job.

**"A runner's tags were updated — could a job get assigned to a runner missing a required tag?"**

> Yes, briefly. Runner tags use eventual consistency in Redis. There is a short window where a scheduler instance might act on stale tags. We mitigate this with runner-side capability validation — the runner rejects jobs it cannot handle, and the scheduler reassigns. The system self-corrects.

**"How do you handle causal ordering of pipeline lifecycle events in Kafka?"**

> All lifecycle events for a pipeline are published to the same Kafka partition using pipeline ID as the partition key. This gives sequential ordering within a pipeline's event stream — which is sufficient for causal consistency. `CREATED` is always processed before `RUNNING` by every consumer.

---

## 📌 Key Takeaways

1. **Consistency is a spectrum** — not a single property
2. **Linearizable** → single-copy illusion, every read sees the latest write, highest cost
3. **Sequential** → same total order on all nodes, timing can differ from real world
4. **Causal** → cause always precedes effect; unrelated ops can reorder freely
5. **Eventual** → converges eventually, cheapest, no timing guarantee
6. **Pravah uses all four** — the right level is chosen per component, not globally
7. **Stronger consistency = more coordination = more latency** — pay only for what you need
