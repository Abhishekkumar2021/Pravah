# 1.4 Leader Election & Why Pravah's Scheduler Needs It
## 🧩 Why Do We Need a Leader?
First, let's understand what the Scheduler Service does in Pravah:

PRAVAH SCHEDULER RESPONSIBILITIES
───────────────────────────────────

  ✅ Watches cron expressions → triggers jobs at right time
  ✅ Resolves DAG dependencies → what runs after what
  ✅ Assigns jobs to runners → which runner gets which job
  ✅ Monitors job timeouts → kills stuck jobs
  ✅ Handles backfill runs → re-runs historical data
  ✅ Manages concurrency limits → max N jobs simultaneously
Now, for high availability we run multiple instances of the Scheduler:

WHY MULTIPLE SCHEDULER INSTANCES?
───────────────────────────────────

Single Scheduler:
  ┌─────────────┐
  │  Scheduler  │  ← crashes → ALL scheduling stops
  └─────────────┘     pipelines miss their triggers
                       enterprise SLA breached

Multiple Schedulers:
  ┌─────────────┐
  │  Scheduler  │  ← one crashes
  ├─────────────┤
  │  Scheduler  │  ← this takes over
  ├─────────────┤
  │  Scheduler  │  ← standby
  └─────────────┘
  High availability ✅
But multiple schedulers create a dangerous problem:

💥 The Split-Brain Problem
WHAT HAPPENS WITHOUT LEADER ELECTION
──────────────────────────────────────

Three Scheduler instances. All running. No leader concept.

Cron triggers "Pipeline-X" at 10:00:00

  Scheduler-1: "I see the trigger! I'll dispatch it!"
  Scheduler-2: "I see the trigger! I'll dispatch it!"
  Scheduler-3: "I see the trigger! I'll dispatch it!"

All three dispatch Pipeline-X simultaneously.

Runner-001 gets Job from Scheduler-1 → runs Pipeline-X
Runner-002 gets Job from Scheduler-2 → runs Pipeline-X
Runner-003 gets Job from Scheduler-3 → runs Pipeline-X

Pipeline-X runs 3 times.
Data loaded into destination 3 times.
Duplicates everywhere.
Customer data corrupted.
This is called split-brain — multiple nodes think they're in charge simultaneously.

The solution: only ONE scheduler should be active at a time.

LEADER ELECTION GOAL
─────────────────────

From N scheduler instances:
  → Elect exactly ONE as Leader
  → Leader does all the scheduling work
  → Others are Followers — on standby
  → If Leader dies → elect new Leader automatically
  → Guarantee: never two leaders at same time
🔑 Concept: What Makes a Good Leader Election?
PROPERTIES WE NEED
───────────────────

Safety:    At most ONE leader at any time
           (never two leaders simultaneously)

Liveness:  Eventually ONE leader is elected
           (system doesn't get stuck leaderless forever)

Fault      If leader crashes, new leader elected
Tolerance: automatically within bounded time
🏗️ Approach 1: Redis Distributed Lock (Pravah's Primary)
How it works:

REDIS SET NX PX — The Building Block
──────────────────────────────────────

SET key value NX PX milliseconds

NX = Only set if key does NOT exist
PX = Expire after milliseconds

This is atomic in Redis.
Only ONE client wins the SET.
Others get "nil" back.
Leader election with Redis:

PRAVAH SCHEDULER LEADER ELECTION
──────────────────────────────────────────────────────────

Three schedulers start up simultaneously:

  Scheduler-1: SET "pravah:scheduler:leader" 
                   "scheduler-1-uuid" NX PX 10000
               → SUCCESS ✅  (key didn't exist)
               → "I AM THE LEADER"

  Scheduler-2: SET "pravah:scheduler:leader"
                   "scheduler-2-uuid" NX PX 10000  
               → nil ❌  (key already exists)
               → "I am a Follower. Will retry."

  Scheduler-3: SET "pravah:scheduler:leader"
                   "scheduler-3-uuid" NX PX 10000
               → nil ❌  (key already exists)
               → "I am a Follower. Will retry."

HEARTBEAT — Leader must keep renewing:
────────────────────────────────────────

Every 3 seconds, Scheduler-1 does:
  EXPIRE "pravah:scheduler:leader" 10000ms
  → Resets TTL to 10 seconds

If Scheduler-1 crashes:
  → Stops renewing
  → TTL counts down: 10s... 7s... 4s... 0s
  → Key expires and disappears

Scheduler-2 retries every second:
  SET "pravah:scheduler:leader" 
      "scheduler-2-uuid" NX PX 10000
  → SUCCESS ✅  (key expired)
  → "I AM THE NEW LEADER"

Failover time = TTL duration (max 10 seconds)
Visual timeline:

TIME  Scheduler-1 (Leader)    Scheduler-2 (Follower)  Redis Key TTL
────  ────────────────────    ──────────────────────  ─────────────
t=0   Wins election           Loses, starts polling   10s
t=3   Renews lock             Polls, loses            10s (renewed)
t=6   Renews lock             Polls, loses            10s (renewed)
t=9   💥 CRASHES              Polls, loses            10s → counting
t=10  (dead)                  Polls, loses            7s
t=11  (dead)                  Polls, loses            6s
t=16  (dead)                  Polls, loses            1s
t=17  (dead)                  Polls, loses            expired!
t=18  (dead)                  WINS ELECTION ✅        10s (new)
                              Becomes new leader
⚠️ The Fencing Token Problem
Even with Redis locks, there's a subtle but critical bug:

THE ZOMBIE LEADER PROBLEM
──────────────────────────────────────────────────────────

t=0:  Scheduler-1 wins lock. Is Leader.

t=5:  Scheduler-1 gets hit by Stop-the-World GC pause
      (Java GC pauses the entire JVM — nothing runs)
      Scheduler-1 is frozen. Can't renew lock.

t=10: Lock expires. Scheduler-2 wins. Becomes Leader.

t=12: Scheduler-1 GC pause ends. Resumes execution.
      Scheduler-1 still THINKS it's the leader.
      (It was frozen — doesn't know 2 seconds passed)

NOW WE HAVE TWO LEADERS:
  Scheduler-1 (zombie): dispatching jobs
  Scheduler-2 (real):   dispatching jobs

Split brain! Same problem as before!
Solution: Fencing Tokens

FENCING TOKENS
───────────────────────────────────────────────────────

Every time a new leader is elected,
Redis gives it a MONOTONICALLY INCREASING token number.

  Scheduler-1 wins election → gets token: 42
  Scheduler-1 crashes → Scheduler-2 wins → gets token: 43
  Scheduler-1 comes back (zombie) → still has token: 42

Every request to a resource MUST include the token.
Resource REJECTS any request with token ≤ current seen token.

FENCING IN ACTION:
───────────────────

Scheduler-2 (real leader, token 43):
  → Sends to Runner: "Run Job-X" [token: 43]
  → Runner records: "highest token seen = 43"
  → Runner executes ✅

Scheduler-1 (zombie, token 42):
  → Sends to Runner: "Run Job-X" [token: 42]
  → Runner checks: "42 < 43, this is stale!"
  → Runner REJECTS ❌ "Outdated leader token"
  → Scheduler-1 cannot cause damage

VISUAL:
────────

        Token 42              Token 43
Sched-1 ────────────────────────────────────►
(zombie)        │ "Run Job-X [42]"           │
                ▼                            ▼
              Runner ──────────────────── Runner
              REJECT ❌                  ACCEPT ✅
              (42 < 43)               (43 = current)

        Token 43
Sched-2 ────────────────────────────────────►
(real)          │ "Run Job-X [43]"
                ▼
              Runner
              ACCEPT ✅
🏗️ Approach 2: ZooKeeper / etcd (Stronger Guarantee)
For cases where Redis isn't strong enough (Redis is AP, remember):

ZOOKEEPER LEADER ELECTION
──────────────────────────────────────────────────────────

ZooKeeper uses a consensus algorithm (ZAB — similar to Raft)
Gives us CP — linearizable leader election

How it works with ephemeral sequential nodes:

1. All schedulers try to create:
   /pravah/election/candidate-0000000001  (Scheduler-1)
   /pravah/election/candidate-0000000002  (Scheduler-2)
   /pravah/election/candidate-0000000003  (Scheduler-3)

   ZooKeeper auto-assigns sequential numbers.
   These are EPHEMERAL — deleted when session dies.

2. Each scheduler checks: "Am I the lowest number?"
   Scheduler-1: sees 001, 002, 003 → I'm lowest → LEADER ✅
   Scheduler-2: sees 001 before me → watch node 001
   Scheduler-3: sees 002 before me → watch node 002

   (Each watches the node just before it — not all watch leader)
   (This prevents "herd effect" — all rushing at once)

3. Scheduler-1 crashes:
   Session expires → node 001 deleted automatically
   Scheduler-2 gets watch notification:
   "Node before me deleted — am I lowest now?"
   Scheduler-2: sees 002, 003 → I'm lowest → LEADER ✅
   Scheduler-3: watches node 002 now

4. Only ONE transition at a time.
   Guaranteed by ZAB consensus.
   No split brain possible.
Visual of the watch chain:

ZooKeeper Watch Chain
──────────────────────

/pravah/election/
  ├── candidate-001  ← Scheduler-1 (LEADER)
  │        ▲
  │   watched by
  ├── candidate-002  ← Scheduler-2 (Follower, watching 001)
  │        ▲
  │   watched by
  └── candidate-003  ← Scheduler-3 (Follower, watching 002)

If 001 dies:
  002 gets notified → becomes leader
  003 now watches 002

If 002 dies (before becoming leader):
  003 gets notified → watches 001 now
  003 becomes leader only when 001 also dies

FAILOVER SEQUENCE:
───────────────────

1. Scheduler-1 crashes at t=0
2. Redis TTL counts down 10s
3. Scheduler-2 wins lock at t=10
4. Scheduler-2 gets fencing token 43
5. Scheduler-2 reads last dispatched job from Redis
6. Scheduler-2 resumes from exact checkpoint
7. Scheduler-2 begins heartbeating every 3s

Total failover time: ≤ 10 seconds
In-flight jobs: continue on runners unaffected
Missed triggers: replayed from Kafka offset
🔄 How Followers Know What The Leader Was Doing
Critical question — when Scheduler-2 takes over, how does it know where Scheduler-1 left off?

LEADER STATE SHARING STRATEGY
───────────────────────────────────────────────────────

Leaders write ALL state to shared stores, not local memory:

  ┌─────────────────────────────────────────────────┐
  │  What Leader Writes              Where           │
  ├──────────────────────────────────┬──────────────┤
  │  Last processed Kafka offset     │ Redis         │
  │  Active job assignments          │ PostgreSQL    │
  │  Current DAG resolution state    │ PostgreSQL    │
  │  Runner load scores              │ Redis         │
  │  Pending trigger queue           │ Kafka         │
  └──────────────────────────────────┴──────────────┘

New leader just reads these stores.
No state transfer needed between schedulers.
Stateless leader = safe handover.

This is why "stateless services" is so important.
We covered this in system design principles.
🎯 FAANG Interview Angles
❓ "How does Pravah prevent two schedulers from
    dispatching the same job simultaneously?"

Good answer:
  "Leader election using Redis distributed lock
   with NX PX — only one scheduler holds the lock
   at a time. Combined with fencing tokens passed
   with every job dispatch to runners — runners
   reject any dispatch from a stale leader token.
   Leader renews every 3s, TTL is 10s, so max
   10s failover window on leader crash."

❓ "What if Redis itself goes down during
    leader election?"

Good answer:
  "Redis going down means no scheduler can acquire
   the lock. This is a CP decision — we accept
   scheduling unavailability over risk of split brain.
   In-flight jobs on runners continue executing
   since runners operate independently once assigned.
   New jobs queue in Kafka until Redis recovers.
   For production, Redis Sentinel or Redis Cluster
   provides HA for Redis itself."

❓ "What is the split-brain scenario and how
    do you handle it in Pravah?"

Good answer:
  "Split brain is when two schedulers both believe
   they're the leader — typically caused by GC
   pause or network hiccup causing lock expiry.
   We handle it with fencing tokens — monotonically
   increasing numbers issued per election. Runners
   track the highest token seen and reject any
   dispatch from a lower token. So even if a zombie
   scheduler wakes up, it cannot cause harm."
## 📌 Key Takeaways
1. Multiple schedulers needed for HA —
   but only ONE should be active at a time

2. Redis SET NX PX = atomic leader election primitive

3. Fencing tokens prevent zombie leaders from
   causing damage after losing election

4. ZooKeeper/etcd gives stronger CP guarantee —
   Redis is sufficient with fencing tokens

5. Leaders must be stateless — write all state
   to shared stores so failover is seamless

6. Follower → Leader transition in Pravah: ≤ 10s
   In-flight jobs unaffected during transition
