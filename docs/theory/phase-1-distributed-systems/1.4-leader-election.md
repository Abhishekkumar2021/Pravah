# 1.4 Leader Election & Why Pravah's Scheduler Needs It

## Why Pravah Needs a Leader

The Scheduler Service is the brain of Pravah. It:

- Watches cron expressions and fires triggers at the right time
- Resolves DAG dependencies — what runs after what
- Assigns jobs to the right runners based on capability and load
- Monitors job timeouts and kills stuck jobs
- Manages concurrency limits and backfill runs

For high availability, we run multiple Scheduler instances. But this creates a critical problem.

---

## The Split-Brain Problem

Without a leader concept, all schedulers watch the same triggers:

```
Cron fires "Pipeline-X" at 10:00:00

Scheduler-1:  "I see the trigger — dispatching!"
Scheduler-2:  "I see the trigger — dispatching!"
Scheduler-3:  "I see the trigger — dispatching!"

Result:
  Runner-001 runs Pipeline-X (from Scheduler-1)
  Runner-002 runs Pipeline-X (from Scheduler-2)
  Runner-003 runs Pipeline-X (from Scheduler-3)

Data loaded 3× into the destination. Duplicates. Corruption.
```

This is **split-brain** — multiple nodes simultaneously believing they are in charge.

The solution: elect exactly **one** Scheduler as Leader. Others stand by.

| Property | Requirement |
|---|---|
| **Safety** | At most one leader at any given time |
| **Liveness** | A leader is always eventually elected |
| **Fault tolerance** | If the leader crashes, a new one is elected automatically |

---

## Approach 1: Redis Distributed Lock (Pravah's Primary)

Redis provides an atomic `SET key value NX PX milliseconds` command:
- `NX` — only set if the key does **not** exist
- `PX` — expire after N milliseconds

Only one caller wins. All others get `nil` back.

**Election flow:**

```
Three schedulers start simultaneously:

Scheduler-1:  SET "pravah:scheduler:leader" "sched-1-uuid" NX PX 10000
              → OK ✅   (key was free)  →  "I AM LEADER"

Scheduler-2:  SET "pravah:scheduler:leader" "sched-2-uuid" NX PX 10000
              → nil ❌  (key exists)   →  "I am follower. Retrying every 1s."

Scheduler-3:  SET "pravah:scheduler:leader" "sched-3-uuid" NX PX 10000
              → nil ❌  (key exists)   →  "I am follower. Retrying every 1s."
```

**Heartbeat — the leader must keep renewing:**

```
Every 3 seconds, Scheduler-1 runs:
  EXPIRE "pravah:scheduler:leader" 10000

If Scheduler-1 crashes:
  → Heartbeat stops
  → TTL counts down: 10s … 7s … 4s … 0 → key deleted

Scheduler-2 wins on next retry:
  SET "pravah:scheduler:leader" "sched-2-uuid" NX PX 10000  → OK ✅
  → "I AM THE NEW LEADER"
```

**Failover timeline:**

```
Time  Scheduler-1 (Leader)     Scheduler-2 (Follower)   TTL
────  ─────────────────────    ──────────────────────   ───
t=0   Wins election            Polling…                 10s
t=3   Renews (EXPIRE)          Polling, nil             10s
t=6   Renews                   Polling, nil             10s
t=9   💥 CRASHES               Polling, nil             10s → counting down
t=17  (dead)                   Polling, nil             expires!
t=18  (dead)                   WINS ELECTION ✅          10s (new)
```

Max failover time = lock TTL = 10 seconds.

## The Fencing Token Problem

There is a subtle bug even with Redis locks: the **zombie leader**.

```
t=0:   Scheduler-1 wins lock. Is leader. Token = 42.

t=5:   Java GC stop-the-world pause freezes Scheduler-1.
       It cannot heartbeat.

t=10:  Lock expires. Scheduler-2 wins. Token = 43.

t=12:  GC pause ends. Scheduler-1 resumes.
       Scheduler-1 still thinks it is leader (it was frozen — it doesn't
       know the lock expired).

NOW: Two leaders. Scheduler-1 (zombie, token 42) and Scheduler-2 (real, token 43).
```

**Fencing tokens fix this.** Every new election issues a monotonically increasing token. Every resource (runner, database) **rejects requests from an outdated token**:

```
Scheduler-2 (real leader, token=43) sends to Runner:
  "Run Job-X" [token: 43]
  Runner: "Highest token seen = 43. Accept." ✅

Scheduler-1 (zombie, token=42) sends to Runner:
  "Run Job-X" [token: 42]
  Runner: "Highest token seen = 43. Token 42 < 43. REJECT." ❌
```

The zombie cannot cause any harm regardless of what it does.

## Approach 2: ZooKeeper / etcd

When a stronger CP guarantee is needed (Redis is AP), ZooKeeper uses the ZAB consensus protocol.

**How it works — ephemeral sequential nodes:**

```
Each scheduler creates an ephemeral sequential node:
  /pravah/election/candidate-0000000001  ← Scheduler-1
  /pravah/election/candidate-0000000002  ← Scheduler-2
  /pravah/election/candidate-0000000003  ← Scheduler-3

Each scheduler checks: "Am I the lowest-numbered node?"
  Scheduler-1: sees 001, 002, 003 → I'm lowest → LEADER ✅
  Scheduler-2: watches node 001 (the one just before it)
  Scheduler-3: watches node 002 (the one just before it)

Scheduler-1 crashes → ephemeral node 001 disappears:
  Scheduler-2 gets watch event → "Am I lowest now?"
  Scheduler-2: sees 002, 003 → LEADER ✅
  Scheduler-3 now watches node 002
```

Each follower watches only the predecessor — preventing "thundering herd" where all followers rush at once.

**Redis vs ZooKeeper:**

| Property | Redis + Fencing | ZooKeeper / etcd |
|---|---|---|
| Consistency | AP (eventual) | CP (linearizable) |
| Failure detection | TTL expiry (~10s) | Session expiry (faster) |
| Split-brain risk | Low (fencing tokens) | None (by design) |
| Operational cost | Low (already have Redis) | Separate cluster required |
| Pravah uses for | Scheduler leader election | Future multi-region |

## Pravah's Full Design

```
┌──────────────────────────────────────────────────────────┐
│                    Kubernetes Cluster                    │
│                                                          │
│  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐   │
│  │ Scheduler-1 │   │ Scheduler-2 │   │ Scheduler-3 │   │
│  │  (LEADER)   │   │  (Follower) │   │  (Follower) │   │
│  │  heartbeat  │   │  retry/1s   │   │  retry/1s   │   │
│  └──────┬──────┘   └──────┬──────┘   └──────┬──────┘   │
│         └─────────────────┴──────────────────┘          │
│                            │                            │
│              ┌─────────────▼─────────────┐              │
│              │           Redis            │              │
│              │  Key:   scheduler:leader  │              │
│              │  Value: scheduler-1-id    │              │
│              │  Token: 42                │              │
│              │  TTL:   10 000 ms         │              │
│              └───────────────────────────┘              │
└──────────────────────────────────────────────────────────┘

Leader does:   poll Kafka triggers, resolve DAGs,
               assign jobs via gRPC, monitor timeouts
Followers do:  poll Redis every 1s, stay ready
```

**Why stateless leaders matter:** The leader writes all scheduling state (Kafka offset, active assignments, DAG state, runner scores) to Redis and PostgreSQL — never in local memory. When a new leader takes over, it simply reads those stores. No state transfer between Schedulers is needed.

**Failover sequence:**

1. Leader crashes at `t=0`
2. Redis TTL counts down to zero (~10s)
3. Next follower wins the lock, gets fencing token `N+1`
4. New leader reads last Kafka offset from Redis, resumes from checkpoint
5. In-flight jobs on runners continue unaffected (runners run autonomously)
6. Total failover window: **≤ 10 seconds**

## System Design Interview Angles

**"How does Pravah prevent two schedulers from dispatching the same job?"**

> Redis `SET NX PX` gives atomic leader election — only one scheduler holds the lock. Every job dispatch includes a fencing token. Runners reject any dispatch with a token lower than the highest they've seen, so even a zombie leader cannot cause duplicate runs.

**"What if Redis goes down during leader election?"**

> No scheduler can acquire the lock — scheduling pauses. This is a deliberate CP choice: we accept brief scheduling unavailability over the risk of split-brain. In-flight jobs on runners continue independently. New triggers queue in Kafka and are replayed when Redis recovers. Redis Sentinel handles Redis HA in production.

**"What is split-brain and how do you prevent it?"**

> Split-brain is when two scheduler instances simultaneously believe they are the leader — typically caused by a GC pause or network hiccup causing lock expiry before the process notices. Fencing tokens prevent this: each election issues a monotonically increasing token number, and all downstream resources reject requests from outdated tokens.

---

## 📌 Key Takeaways

1. **Multiple schedulers are needed for HA**, but exactly one must be active — leader election solves this
2. **Redis `SET NX PX`** is the atomic primitive for distributed lock-based election
3. **Fencing tokens** prevent zombie leaders from causing harm after losing the election
4. **Leaders must be stateless** — all state in Redis/PostgreSQL so failover is instant
5. **Failover time ≤ 10 seconds**, in-flight jobs unaffected
6. **etcd/ZooKeeper** provides stronger CP guarantees when Redis's AP model is insufficient
