1.7 Idempotency & Exactly-Once Semantics
🧩 Why This Is Critical for Pravah
Let's start with a scenario that should scare you:

THE DUPLICATE JOB NIGHTMARE
────────────────────────────────────────────────────────────

Pipeline: Load daily sales data from Postgres → Data Warehouse

t=0:   Scheduler assigns Job-X to Runner-001
t=1:   Runner-001 starts executing
t=45:  Runner-001 finishes loading 1,000,000 rows
t=46:  Runner-001 sends "Job Complete" to Scheduler
t=46:  Network blip — message lost!
t=76:  Scheduler: "No completion after 30s → Runner dead?"
t=77:  Scheduler reassigns Job-X to Runner-002
t=78:  Runner-002 loads same 1,000,000 rows AGAIN

Result in Data Warehouse:
  2,000,000 rows instead of 1,000,000
  Every sale appears twice
  Revenue reports show 2x actual revenue
  Finance team makes wrong decisions
  This is a data catastrophe.
This happens because the system is not idempotent.

📖 What Idempotency Means
IDEMPOTENCY DEFINITION
────────────────────────────────────────────────────────────

An operation is idempotent if executing it
multiple times produces the SAME result
as executing it once.

f(f(x)) = f(x)

MATHEMATICAL EXAMPLES:
  Idempotent:     abs(abs(x)) = abs(x)       ✅
  Idempotent:     sort(sort(x)) = sort(x)    ✅
  NOT idempotent: x + 1 applied twice ≠ once ❌

REAL WORLD EXAMPLES:
  Idempotent:
    "Set temperature to 20°C"
    → Do it 10 times → still 20°C ✅

  NOT idempotent:
    "Increase temperature by 1°C"
    → Do it 10 times → 30°C instead of 21°C ❌

IN SOFTWARE:
  Idempotent:     PUT /pipelines/123 {name: "sales"}
                  → Do it 5 times → pipeline named "sales" ✅

  NOT idempotent: POST /jobs/trigger
                  → Do it 5 times → 5 jobs created ❌
🔑 The Core Tool: Idempotency Keys
IDEMPOTENCY KEY CONCEPT
────────────────────────────────────────────────────────────

Every operation gets a UNIQUE ID.
Before executing, check:
  "Have I seen this ID before?"
  YES → return cached result, don't re-execute
  NO  → execute, store result with ID

This transforms ANY operation into idempotent.

PRAVAH IDEMPOTENCY KEY STRUCTURE:
──────────────────────────────────

{pipeline_id}-{scheduled_time}-{attempt_number}

Example:
  pipeline-abc123-2024-01-15T10:00:00Z-attempt-1

  pipeline-abc123: which pipeline
  2024-01-15T10:00:00Z: which scheduled run
  attempt-1: which attempt (increments on retry)

Why include scheduled_time?
  Same pipeline runs daily.
  Each run is different job — needs different key.

Why include attempt_number?
  Each retry is intentionally different attempt.
  But same attempt retried = same key → deduped.

🔧 Layer 1: API Gateway Idempotency
IDEMPOTENT API REQUESTS
────────────────────────────────────────────────────────────

Client triggers pipeline manually via REST API.
Client might retry if response times out.

REQUEST DESIGN:
  POST /api/v1/pipelines/abc123/trigger
  Headers:
    Idempotency-Key: client-generated-uuid-here
  Body:
    { "params": { "date": "2024-01-15" } }

GATEWAY BEHAVIOR:
  ┌─────────────────────────────────────────────────┐
  │                   API Gateway                   │
  │                                                 │
  │  Receive request with Idempotency-Key           │
  │            │                                    │
  │            ▼                                    │
  │  Check Redis: "seen this key before?"           │
  │            │                                    │
  │     ┌──────┴──────┐                             │
  │     ▼             ▼                             │
  │   YES: NO:                                      │
  │   Return  Forward to                            │
  │   cached  Pipeline Service                      │
  │   result  Execute + cache result                │
  │           with 24h TTL                          │
  └─────────────────────────────────────────────────┘

TIMELINE:
  t=0:  Client sends trigger (key: uuid-123)
  t=0:  Gateway: key not seen → forward, execute
  t=5:  Pipeline triggered. Result cached.
  t=5:  Network timeout — client never got response!
  t=6:  Client retries (same key: uuid-123)
  t=6:  Gateway: key seen! → return cached result
  t=6:  Client gets success ✅
  Pipeline triggered exactly ONCE ✅
🔧 Layer 2: Scheduler → Kafka (Outbox Pattern)
This is where most systems fail. Writing to DB and publishing to Kafka are two separate operations. What if you do one but not the other?

THE DUAL-WRITE PROBLEM
────────────────────────────────────────────────────────────

NAIVE APPROACH (BROKEN):
  1. Scheduler writes job to PostgreSQL ✅
  2. Scheduler publishes to Kafka
     → CRASH HERE 💥
  3. Kafka never gets the message
  4. Job in DB but never executed
  5. Silent data loss!

OR:
  1. Scheduler publishes to Kafka ✅
  2. Scheduler writes job to PostgreSQL
     → CRASH HERE 💥
  3. DB never gets the record
  4. Job executing but no tracking record
  5. Ghost job!

Both orderings can fail. We need atomicity
across DB and Kafka. That's the outbox pattern.

THE OUTBOX PATTERN:
────────────────────────────────────────────────────────────

Key insight: Write BOTH to the DB atomically.
             Then relay to Kafka separately.

┌──────────────────────────────────────────────────────┐
│                  PostgreSQL                          │
│                                                      │
│  ┌─────────────────┐    ┌──────────────────────┐   │
│  │   jobs table    │    │   outbox table        │   │
│  │                 │    │                       │   │
│  │ id: job-xyz     │    │ id: msg-001           │   │
│  │ pipeline: abc   │    │ topic: job.assigned   │   │
│  │ status: PENDING │    │ payload: {job-xyz...} │   │
│  │ idempotency_key │    │ sent: false           │   │
│  │  : key-123      │    │ created_at: 10:00     │   │
│  └─────────────────┘    └──────────────────────┘   │
│                                                      │
│  BOTH written in ONE transaction ✅                  │
│  Either both succeed or both fail. No partial state. │
└──────────────────────────────────────────────────────┘

                          │
                          │ Outbox Relay (separate process)
                          ▼

              ┌───────────────────────┐
              │        Kafka          │
              │                       │
              │  topic: job.assigned  │
              │  key: pipeline-abc    │
              │  value: {job-xyz...}  │
              │  headers:             │
              │    idempotency: key-123│
              └───────────────────────┘

OUTBOX RELAY PROCESS:
  Every 100ms:
    SELECT * FROM outbox WHERE sent = false
    FOR EACH message:
      Publish to Kafka
      IF success: UPDATE outbox SET sent = true
      IF fail: leave as false, retry next cycle

  If relay crashes mid-publish:
    → Message sent to Kafka but outbox not updated
    → Relay restarts, sees sent=false, publishes again
    → Kafka receives DUPLICATE
    → That's ok! Kafka consumers handle duplicates
      via idempotency keys in message headers
🔧 Layer 3: Kafka Consumer Idempotency
IDEMPOTENT KAFKA CONSUMERS
────────────────────────────────────────────────────────────

Kafka delivers at-least-once by default.
Consumer must handle duplicates.

EXECUTION SERVICE CONSUMING job.assigned:
  ┌────────────────────────────────────────────────┐
  │           Execution Service                    │
  │                                                │
  │  Consume message from Kafka                    │
  │            │                                   │
  │            ▼                                   │
  │  Extract idempotency_key from headers          │
  │            │                                   │
  │            ▼                                   │
  │  Check PostgreSQL:                             │
  │    SELECT id FROM processed_messages           │
  │    WHERE idempotency_key = 'key-123'           │
  │            │                                   │
  │     ┌──────┴──────┐                            │
  │     ▼             ▼                            │
  │   FOUND:      NOT FOUND:                       │
  │   Already     Process message                  │
  │   processed   Insert into processed_messages   │
  │   Skip ✅     Commit Kafka offset              │
  └────────────────────────────────────────────────┘

IMPORTANT: Process + Insert must be atomic!

  BEGIN TRANSACTION:
    INSERT INTO processed_messages (idempotency_key)
    -- Unique constraint prevents duplicates
    
    INSERT INTO job_assignments (job_id, runner_id)
    
  COMMIT

  If another consumer processes same message:
    INSERT into processed_messages fails
    (unique constraint violation)
    Transaction rolls back
    Duplicate safely rejected ✅
🔧 Layer 4: Execution Service → Runner
IDEMPOTENT JOB DISPATCH TO RUNNER
────────────────────────────────────────────────────────────

Scheduler sends job to Runner via gRPC.
gRPC call might timeout. Scheduler retries.
Runner might receive job twice.

GRPC JOB ASSIGNMENT MESSAGE:
  message JobAssignment {
    string job_id           = 1;  // unique job ID
    string idempotency_key  = 2;  // execution-specific key
    int64  fencing_token    = 3;  // leader epoch
    string pipeline_config  = 4;
    int32  attempt_number   = 5;
  }

RUNNER RECEIVES JOB:
  Check local state:
    "Have I seen job_id: job-xyz before?"
    
    YES, same attempt_number:
      → Already executing or completed
      → Return current status
      → Don't start again ✅

    YES, different attempt_number:
      → This is an intentional retry
      → Check if previous attempt completed
      → If yes: return previous result
      → If no: start fresh execution ✅

    NO:
      → New job, start execution ✅

RUNNER LOCAL STATE (SQLite on runner):
  ┌────────────────────────────────────────────────┐
  │  job_executions table                          │
  │                                                │
  │  job_id     │ attempt │ status    │ result_ref │
  │  ──────────────────────────────────────────── │
  │  job-xyz    │ 1       │ RUNNING   │ null       │
  │  job-abc    │ 1       │ COMPLETED │ s3://...   │
  │  job-def    │ 2       │ COMPLETED │ s3://...   │
  └────────────────────────────────────────────────┘
🔧 Layer 5: Runner → Data Destination (Hardest Part)
This is where exactly-once is hardest. Writing to databases and data warehouses is not inherently idempotent.

MAKING DATA LOADS IDEMPOTENT
────────────────────────────────────────────────────────────

STRATEGY 1: UPSERT (for databases)
  Instead of INSERT (duplicates on retry):
    INSERT INTO orders (id, amount, status)
    VALUES (order-123, 500, 'completed')
    ON CONFLICT (id) DO UPDATE
    SET amount = 500, status = 'completed'

  Retry 10 times → same result ✅
  Works when destination has unique key.

STRATEGY 2: DELETE + INSERT (for batch loads)
  Before loading: DELETE WHERE batch_id = 'job-xyz-attempt-1'
  Then INSERT all rows with batch_id tag

  Retry → deletes previous partial load, reloads ✅
  Atomic in most data warehouses (BigQuery, Snowflake).

STRATEGY 3: STAGING TABLE (for large loads)
  Step 1: Load ALL data into staging table
          staging_sales_job_xyz_attempt_1

  Step 2: MERGE staging → production
          (atomic swap in most warehouses)

  Step 3: DROP staging table

  Retry at Step 1 → overwrites staging (safe)
  Retry at Step 2 → merge is idempotent
  Retry at Step 3 → staging already gone (safe) ✅

STRATEGY 4: WRITE GUARD (for streaming destinations)
  Every row tagged with:
    {pipeline_id, run_id, row_sequence_number}

  Destination has unique index on these fields.
  Duplicate rows rejected by unique constraint ✅

PRAVAH USES ALL FOUR:
  Database destinations    → UPSERT
  Data warehouse batch     → STAGING TABLE
  Data warehouse streaming → WRITE GUARD
  File destinations (S3)   → Deterministic path
    s3://pravah/pipeline-abc/2024-01-15/output.parquet
    Retry overwrites same path ✅
🔧 Layer 6: Exactly-Once in Kafka (Producer Side)
KAFKA EXACTLY-ONCE SEMANTICS
────────────────────────────────────────────────────────────

Kafka provides built-in exactly-once via:
  1. Idempotent Producer
  2. Transactional API

IDEMPOTENT PRODUCER:
  Each producer gets a Producer ID (PID)
  Each message gets a Sequence Number

  Broker tracks: PID → last sequence number

  If producer retries message:
    Broker sees: "PID=X, Seq=5 — already have this!"
    Broker deduplicates. One copy stored. ✅

  Config:
    enable.idempotence=true
    acks=all
    retries=Integer.MAX_VALUE

KAFKA TRANSACTIONS (for consume-process-produce):
  Pravah pattern:
    Consume from topic-A
    Process
    Produce to topic-B
    Commit offset

  Without transactions:
    Process + produce + commit are 3 separate steps
    Crash between any two = duplicate or loss

  With transactions:
    BEGIN TRANSACTION
      Consume message (offset not committed yet)
      Produce to topic-B
      Commit offset
    COMMIT (atomic!)

  Either ALL happen or NONE happen.
  Exactly-once across consume-process-produce ✅

PRAVAH KAFKA CONFIG:
  // Producer config
  enable.idempotence=true
  transactional.id=pravah-execution-{instance-id}
  acks=all

  // Consumer config
  isolation.level=read_committed
  // Only read messages from committed transactions
🏗️ Pravah's Complete Exactly-Once Architecture
EXACTLY-ONCE JOB EXECUTION IN PRAVAH
────────────────────────────────────────────────────────────

TRIGGER:
  Scheduler: cron fires for Pipeline-abc at 10:00

STEP 1: Atomic outbox write
  BEGIN TRANSACTION (PostgreSQL)
    INSERT INTO jobs (id='job-xyz', key='abc-10:00-1', status=PENDING)
    INSERT INTO outbox (topic='job.assigned', payload=..., sent=false)
  COMMIT ✅

STEP 2: Outbox relay → Kafka
  Outbox relay reads unsent messages
  Publishes to Kafka with idempotency_key header
  Kafka producer is idempotent (PID + sequence)
  Marks outbox message as sent ✅

STEP 3: Execution Service consumes
  Kafka transaction:
    Consume job.assigned message
    Check processed_messages table (dedup check)
    Insert into processed_messages
    Insert into job_assignments
    Produce runner.dispatch message
    Commit Kafka offset
  All atomic ✅

STEP 4: Runner receives job
  Checks local SQLite for job_id
  Not seen → begins execution
  Records: job-xyz attempt-1 RUNNING ✅

STEP 5: Runner executes ETL
  Extract: reads from source
  Transform: DuckDB processing
  Load: staging table → production table (idempotent)
  Records result checksum ✅

STEP 6: Runner sends completion
  gRPC: JobResult(job_id, key, checksum, result_ref)
  If network fails → runner retries

STEP 7: Scheduler receives result
  Validates fencing token
  Validates checksum
  Checks: already marked complete? (dedup)
  Marks job COMPLETE ✅
  Publishes pipeline.completed event

STEP 8: Downstream consumers
  Kafka transaction:
    Consume pipeline.completed
    Trigger notifications
    Update lineage
    Commit offset
  All atomic ✅

RESULT: Job runs EXACTLY ONCE end-to-end
        Even if any single step retries N times

🎯 FAANG Interview Angles
❓ "How does Pravah ensure a pipeline doesn't
    load data twice if the runner crashes
    mid-execution and retries?"

Good answer:
  "Multiple layers. First, every job has a unique
   idempotency key: pipeline_id + scheduled_time
   + attempt_number. The runner checks its local
   SQLite before starting — same key already
   running or complete means skip.

   For the data load itself, we use a staging table
   approach: load into a uniquely named staging
   table, then atomic MERGE into production.
   Retry overwrites the same staging table then
   re-merges — idempotent end to end.

   Finally, the scheduler uses fencing tokens to
   reject results from zombie runners. Only the
   current attempt's result is accepted."

❓ "Explain the outbox pattern and why Pravah uses it"

Good answer:
  "The outbox pattern solves the dual-write problem.
   If we write to PostgreSQL and then publish to
   Kafka separately, a crash between the two leaves
   the system inconsistent. The outbox pattern writes
   both the business record and the outbox message
   in one atomic PostgreSQL transaction. A separate
   relay process reads unprocessed outbox messages
   and publishes to Kafka. If the relay crashes
   mid-publish, it retries — Kafka deduplicates
   via idempotent producers. This gives us atomic
   DB + Kafka writes without distributed transactions."

❓ "Can Kafka provide exactly-once semantics?
    How does Pravah use it?"

Good answer:
  "Yes, via two mechanisms. Idempotent producers
   use producer ID and sequence numbers — brokers
   deduplicate retried messages automatically.
   For consume-process-produce patterns, Kafka
   transactions make all three steps atomic —
   either all commit or none do. We configure
   consumers with isolation.level=read_committed
   to only read from committed transactions.
   This gives us exactly-once across our entire
   event processing pipeline."
📌 Key Takeaways
1. Idempotency = same operation N times = same as once
   Achieved with: unique keys + deduplication store

2. Every layer must be independently idempotent:
   API → Kafka → Consumer → Runner → Destination

3. Outbox pattern = atomic DB + Kafka write
   Solves the dual-write problem without 2PC

4. Kafka exactly-once:
   Idempotent producer → dedup on broker
   Transactions → atomic consume-process-produce

5. Data destination strategies:
   UPSERT for databases
   Staging table for warehouses
   Deterministic paths for object stores

6. Idempotency key structure matters:
   pipeline_id + scheduled_time + attempt_number

7. Exactly-once is expensive — use only where
   correctness is critical. Use at-least-once
   with idempotent consumers elsewhere.
