# 1.6 Failure Modes — Crash, Byzantine & Network Partitions

## Why Failure Taxonomy Matters

Most engineers instinctively treat all failures the same: "something broke, retry." In reality, distributed systems fail in fundamentally different ways, and applying the wrong recovery strategy makes things worse — duplicated data, silent corruption, cascading failures.

A Pravah runner can:
- Crash cleanly (easy to detect)
- Hang forever (hard to detect, looks like a partition)
- Run slowly (indistinguishable from a partitioned node)
- Return wrong results (very hard to detect)
- Crash mid-write, leaving partial state
- Lie about its status while healthy

Each failure type requires a different response.

## 1. Crash Failures

A node simply stops. No more messages sent or received. The most common failure, and the easiest to handle.

**Fail-stop:** Node crashes and never returns (hardware failure, OOM kill).

**Fail-recover:** Node crashes but restarts. Most common in Kubernetes environments. The subtlety here: when it comes back, does it remember what it was doing? Did it complete the job before crashing, or only partially? Should it resume or start over?

**How Pravah handles crash failures:**

```
Detection:
  Runner sends heartbeat every 10s via gRPC stream.
  Scheduler marks runner SUSPECT after 30s of silence.
  Scheduler marks runner DEAD after 60s of silence.

Timeline:
  t=0   Heartbeat ✅
  t=10  Heartbeat ✅
  t=20  Heartbeat ✅
  t=25  Runner 💥 CRASHES
  t=30  No heartbeat → SUSPECT
  t=60  No heartbeat → DEAD
  t=61  Scheduler reassigns job to Runner-002
```

Why wait 60 seconds? A network hiccup can cause a missed heartbeat without the runner being dead. Declaring a runner dead too quickly causes unnecessary job reassignment, and if the runner isn't actually dead, two runners attempt the same job simultaneously — data duplication.

**On recovery:** Runner-001 restarts with a new registration and a new fencing token (higher than the previous). If it tries to submit results for the old job, the scheduler rejects the stale token. No duplicate data.

## 2. Byzantine Failures

Named after the Byzantine Generals Problem — a scenario where generals surrounding a city must all agree to attack or all retreat, but some generals are traitors who send contradictory messages to different generals.

In distributed systems, a Byzantine node does not just crash. It actively sends **incorrect or contradictory information** to different nodes.

**Byzantine failure types in Pravah:**

| Type | Behavior | Impact |
|---|---|---|
| **Lying** | Runner reports "Job completed" but never ran it | Missing data at destination |
| **Contradicting** | Reports capacity=high to Scheduler, capacity=low to Agent | Wrong scheduling decisions |
| **Partial execution** | Executes Extract but not Load, reports full success | Partial data at destination |
| **Replay attack** | Captures old job token, replays to re-execute | Duplicate data load |
| **Data tampering** | Executes pipeline, modifies data silently | Corrupted analytics |

Byzantine failures can be accidental (buggy software, memory corruption) or malicious (compromised node).

**Byzantine Fault Tolerance (BFT) cost:** To tolerate `f` Byzantine nodes you need `3f+1` total nodes — three times more expensive than crash fault tolerance (which requires only `2f+1`). BFT algorithms (PBFT, HotStuff) also carry high message overhead.

Pravah does not implement full BFT. Instead, it uses targeted defenses:

| Defense | Mechanism | Prevents |
|---|---|---|
| **Cryptographic job tokens** | Signed JWT per job; signature verified on every result | Token replay and forgery |
| **Checksum verification** | SHA-256 of every data artifact; scheduler verifies independently | Data tampering |
| **Result cross-verification** | For critical pipelines: run on 2 runners, compare results | Lying runners |
| **mTLS everywhere** | Runner must present a valid certificate for all communication | Unauthorized runners |
| **Tamper-evident audit logs** | Every action logged with who, what, when, result, checksum | Post-hoc Byzantine detection |
| **Resource limits** | K8s resource limits enforced at the kernel level | Byzantine resource exhaustion |

## 3. Network Partitions

A network partition means some nodes can reach each other but not all nodes. The network splits into islands. Crucially: **both sides are perfectly healthy — they just cannot communicate**.

**Partition types in Pravah:**

```
Full partition:
  ┌────────────────────┐    ╳    ┌────────────────────┐
  │ Scheduler-1        │         │ Scheduler-2        │
  │ Runner-001, 002    │         │ Runner-003, 004    │
  └────────────────────┘         └────────────────────┘

Partial partition:
  Scheduler → Runner-001 ✅
  Scheduler → Runner-002 ✅
  Scheduler → Runner-003 ❌
  Scheduler → Runner-004 ❌

Asymmetric partition:
  Runner-001 → Scheduler ✅   (runner thinks it's connected)
  Scheduler  → Runner-001 ❌  (scheduler thinks runner is dead)

Flapping partition:
  t=0  Connected ✅ | t=5  Partitioned ❌ | t=8  Connected ✅ | t=12 Partitioned ❌
  (Worst case — triggers cascading election storms)
```

**How Pravah handles a partition between cloud and runner group:**

```
t=0    Runners executing jobs normally, heartbeats flowing
t=30   Network partition occurs

Cloud side:
  t=60   No heartbeat for 30s → runners marked SUSPECT
  t=90   No heartbeat for 60s → runners marked DEAD
  t=91   Scheduler attempts to reassign to other runners (if available)
  t=91   PagerDuty alert fired

Runner side (during partition):
  t=31   Heartbeat send fails → exponential backoff: 1s, 2s, 4s, 8s…
  t=60   Runner continues executing current job (runners work independently
         once a job is assigned)
  t=90   Job completes. Runner tries to send result.
         Connection still broken → result stored locally, retried with backoff

Partition heals at t=120:
  Runner re-establishes gRPC connection, sends stored result.
  Scheduler checks fencing token.

  Case A — job was NOT reassigned (all other runners were also partitioned):
    Result accepted ✅, job marked complete

  Case B — job WAS reassigned and completed by Runner-004:
    Job already marked complete in DB.
    Runner-001's result is a duplicate.
    Idempotency key check → duplicate rejected ❌
    No data duplication ✅
```

## 4. Message Loss and Duplication

Messages in distributed systems can be lost, delayed, reordered, or duplicated. These are not node failures — they are properties of the network.

**Three delivery guarantees:**

| Guarantee | Behavior | Pravah uses for |
|---|---|---|
| **At-most-once** | Sent once, not retried. May be lost, never duplicated | Runner capability broadcasts |
| **At-least-once** | Retried until acknowledged. Never lost, may be duplicated | Job assignments, pipeline events |
| **Exactly-once** | Never lost, never duplicated. Requires idempotency + dedup | Audit events, job completion records, data loads |

---

## 5. Timing Failures

**Performance degradation:** A runner processes at 10% of normal speed. Not crashed, not partitioned — just slow. Heartbeats arrive late. Risk: Scheduler declares it dead. Pravah's generous timeout buffer (60s vs 10s heartbeat interval) absorbs this.

**Clock skew:** Covered in Chapter 1.3. Pravah uses Hybrid Logical Clocks to avoid trusting wall-clock time for ordering.

**Thundering herd:** 1,000 pipelines all scheduled at midnight. All runners hit simultaneously. System overloads, timeouts cascade. Pravah mitigates with: cron trigger jitter (±30s random offset), priority queuing, backpressure signals from runners, and per-tenant rate limiting.

## Complete Failure Response Map

| Failure | Detection | Pravah's Response |
|---|---|---|
| Runner crash (fail-stop) | Heartbeat timeout | Mark DEAD after 60s, reassign job, reject stale fencing token |
| Runner crash (fail-recover) | Heartbeat + re-register | Resume from checkpoint, idempotency check, new fencing token |
| Scheduler crash | Redis lock TTL expires | Leader re-election, new leader reads state from shared store |
| Network partition (cloud↔runner) | Heartbeat timeout | CP: stop scheduling, alert on-call; runners store results locally |
| Network partition (within control plane) | Raft election failure | Minority stops serving writes, majority continues |
| Byzantine runner (wrong results) | Checksum mismatch | Reject result, quarantine runner, alert, re-run on different runner |
| Message loss | Timeout + retry | At-least-once retry, idempotency dedup at receiver |
| Message duplication | Idempotency key check | Second message ignored via dedup store |
| Slow runner | Job timeout exceeded | Kill after SLA breach, reassign to faster runner |
| Thundering herd | Queue depth spike | Backpressure, jitter, priority queue, rate limiting |

## Failure Detector Design

Pravah's Scheduler maintains an adaptive failure detector.

A good failure detector has two properties that conflict:
- **Completeness** — every crashed node is eventually suspected
- **Accuracy** — healthy nodes are not falsely suspected (faster detection = more false positives)

Pravah uses adaptive thresholds:

```
Normal operation:
  Heartbeat interval:  10s
  Suspect threshold:   30s  (3 missed heartbeats)
  Dead threshold:      60s  (6 missed heartbeats)

High load (queue depth > 80%):
  Suspect threshold:   60s  (runners may be legitimately slow)
  Dead threshold:     120s  (extra grace time)
```

Failure detector state machine:

```
  register ──► ALIVE ──► (30s no heartbeat) ──► SUSPECT
                  ▲                                  │
                  │ heartbeat received               │ (30s more)
                  │                                  ▼
                  └──────────────────────────────── DEAD ──► reassign, alert
                                                     │
                                                  restarts
                                                     │
                                                  ALIVE (new registration)
```

## System Design Interview Angles

**"A runner goes silent — how does Pravah decide if it crashed or is just slow?"**

> Adaptive failure detector. Under normal load, 30s marks SUSPECT and 60s marks DEAD. Under high load we extend both thresholds — a busy runner legitimately misses heartbeats. We never reassign until DEAD state to prevent dual execution. Fencing tokens ensure that even if we're wrong and the runner recovers, its stale result is rejected.

**"How does Pravah handle a runner that returns corrupted results without crashing?"**

> SHA-256 checksums on all data artifacts. The runner computes and uploads the checksum to MinIO alongside results. The Scheduler independently verifies. On mismatch: job marked FAILED, runner quarantined, on-call alerted, job re-queued to a different runner. For critical pipelines, we optionally run on two runners and compare results.

**"What happens if Pravah's control plane is partitioned into two halves?"**

> The control plane uses Raft via etcd for Kubernetes and Redis quorum for scheduler election. In a partition, the minority side cannot achieve quorum for writes — it stops accepting new scheduling. The majority side continues. This is a deliberate CP choice: brief unavailability over risk of split-brain. In-flight jobs on runners continue executing independently. When the partition heals, the minority re-syncs via Raft log replication.

## 📌 Key Takeaways

1. Failures are not binary — each type needs a different response; treating them all as "just retry" causes corruption
2. **Crash failures** → heartbeat detection, fencing tokens, reassignment
3. **Byzantine failures** → checksums, mTLS, signed tokens, result cross-verification
4. **Network partitions** → must choose CP or AP; Pravah chooses CP for the control plane
5. At-most-once, at-least-once, exactly-once — choose the right guarantee per use case
6. **Thundering herd** is a real failure mode — prevent with jitter, backpressure, and rate limiting
7. **Adaptive timeouts** balance fast failure detection against false positives under load
