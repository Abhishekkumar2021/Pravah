# 1.6 Failure Modes: Crash, Byzantine & Network Partitions

## 🧩 Why Failure Modes Matter

Most engineers think about failures like this:

NAIVE VIEW OF FAILURES

"Something either works or it doesn't.
 If it fails, we retry."

REALITY IN PRAVAH

A runner can:
```text
  → Crash cleanly            (easy to detect)
  → Hang forever             (hard to detect)
  → Run slowly               (looks like a partition)
  → Return wrong results     (very hard to detect)
  → Crash mid-write          (partial failure)
  → Lie about its state      (Byzantine)
  → Be reachable sometimes   (flapping)
  → Run the same job twice   (dangerous)
```

Each failure type needs a DIFFERENT response.
Treating them all as "just retry" causes
data corruption, duplicates, and cascades.

### 1️⃣ Crash Failures (Fail-Stop)

What it is:

Node simply stops. No more messages sent or received.
Clean death. The most common and easiest to handle.
Types of crash:

FAIL-STOP vs FAIL-RECOVER

FAIL-STOP:
```text
  Node crashes → never comes back
  Example: Hardware failure, OOM kill
```

  Timeline:
```text
  t=0  Runner-001: ALIVE ────────────────────────
  t=5  Runner-001: 💥 DEAD ─────────────────────►
       (gone forever)
```

FAIL-RECOVER:
```text
  Node crashes → restarts after some time
  Most common in Kubernetes (pod restarts)
```

  Timeline:
```text
  t=0   Runner-001: ALIVE ────────────────────────
  t=5   Runner-001: 💥 CRASH
  t=8   Runner-001: 🔄 RESTARTING
  t=10  Runner-001: ✅ ALIVE AGAIN ──────────────►
```

  Problem: When it comes back:
```text
    → Does it remember what it was doing?
    → Did it complete the job before crashing?
    → Did it partially complete the job?
    → Should it resume or start over?
How Pravah handles crash failures:
```

PRAVAH CRASH FAILURE HANDLING

Detection:
  Runner sends heartbeat every 10s via gRPC stream
  Scheduler marks runner SUSPECT if no heartbeat for 30s
  Scheduler marks runner DEAD if no heartbeat for 60s

  Timeline:
  t=0    Runner heartbeat ✅
  t=10   Runner heartbeat ✅
  t=20   Runner heartbeat ✅
  t=25   Runner 💥 CRASHES
```text
  t=30   No heartbeat → SUSPECT
  t=40   No heartbeat → (still SUSPECT)
  t=60   No heartbeat → DEAD
  t=61   Scheduler reassigns job to Runner-002
```

Why wait 60s and not 10s?
  Network hiccup could cause missed heartbeat.
  Declaring dead too fast = unnecessary reassignment.
  Job running on two runners = data duplication.
  30s suspect + 30s dead = safe balance.

Recovery:
  Runner-001 restarts at t=65
  Registers fresh with Scheduler (new runner ID)
  Gets new fencing token (higher than before)
  Old job already reassigned — Runner-001 ignores it

  If Runner-001 tries to submit old job result:
```text
    → Scheduler checks fencing token
    → Old token < current token
    → REJECTED ❌
    → Data not duplicated ✅
```

### 2️⃣ Byzantine Failures (The Hardest)

Named after the Byzantine Generals Problem.

THE BYZANTINE GENERALS PROBLEM

Imagine generals surrounding a city.
They must ALL attack or ALL retreat — split action fails.
They communicate only by messenger.

Problem: Some generals are TRAITORS.
```text
  → They send different messages to different generals
  → They lie about what other generals said
  → They try to cause disagreement
```

In distributed systems:
  A Byzantine node doesn't just crash.
  It actively sends INCORRECT or CONTRADICTORY
  information to different nodes.
Types of Byzantine behavior:

BYZANTINE FAILURE EXAMPLES IN PRAVAH

Type 1: LYING
  Runner reports "Job completed successfully"
  but actually never ran it.
  Data missing at destination.

Type 2: CONTRADICTING
  Runner tells Scheduler: "I have capacity"
  Runner tells Agent: "I'm overloaded"
  System makes wrong decisions.

Type 3: SELECTIVE DROPPING
  Runner executes Extract step.
  "Crashes" before Transform.
  But tells Scheduler it completed fully.
  Data partially loaded at destination.

Type 4: REPLAY ATTACKS
  Malicious runner captures old job token.
  Replays it to execute an old job again.
  Duplicate data loaded.

Type 5: DATA TAMPERING
  Runner executes pipeline but modifies data.
  Returns "success" with corrupted results.
  Downstream analytics get wrong numbers.

Note: Byzantine failures can be:
```text
  → Accidental (buggy software, corrupted memory)
  → Malicious (compromised node, hacker)
Why Byzantine is so hard:
```

BYZANTINE FAULT TOLERANCE (BFT) REQUIREMENT

To tolerate f Byzantine nodes you need 3f+1 total nodes.

  Tolerate 1 Byzantine: need 4 nodes
  Tolerate 2 Byzantine: need 7 nodes
  Tolerate 3 Byzantine: need 10 nodes

Compare to crash fault tolerance:
  Tolerate 1 crash: need only 3 nodes (Raft/Paxos)

BFT is 3x more expensive.

Also: BFT algorithms (PBFT, HotStuff) are
complex and have high message overhead.

For most enterprise systems (including Pravah):
```text
  → We don't face malicious nodes
  → We trust our own infrastructure
  → We use simpler crash fault tolerance
  → We add specific Byzantine mitigations
     only where needed
Pravah's Byzantine mitigations:
```

PRAVAH BYZANTINE DEFENSES

We don't implement full BFT (too expensive).
Instead targeted defenses:

Defense 1: CRYPTOGRAPHIC JOB TOKENS
  Every job has a signed JWT token.
  Runner cannot forge or replay tokens.
  Scheduler verifies signature on every result.
```text
  → Prevents replay attacks ✅
```

Defense 2: RESULT VERIFICATION
  For critical pipelines: run on 2 runners.
  Compare results — must match within threshold.
```text
  Mismatch → alert + human review.
  → Detects lying runners ✅
```

Defense 3: CHECKSUM VERIFICATION
  Every data artifact has SHA-256 checksum.
  Runner uploads result + checksum to MinIO.
  Scheduler verifies checksum independently.
```text
  → Detects data tampering ✅
```

Defense 4: mTLS EVERYWHERE
  All runner ↔ cloud communication is mTLS.
  Runner must present valid certificate.
  Compromised runner has no valid cert.
```text
  → Prevents unauthorized runners ✅
```

Defense 5: AUDIT LOGS
  Every action logged with:
    who, what, when, result, checksum
  Tamper-evident log (append-only).
```text
  → Detects Byzantine behavior post-hoc ✅
```

Defense 6: RESOURCE LIMITS
  Runner cannot consume more than quota.
  K8s resource limits enforced at kernel level.
```text
  → Prevents Byzantine resource exhaustion ✅
```

### 3️⃣ Network Partitions

What it is:

Network partition = some nodes can reach each other
but not all nodes. The network splits into islands.

This is NOT a node failure.
Both sides are perfectly healthy.
They just can't talk to each other.
Types of partitions:

PARTITION TYPES IN PRAVAH

TYPE 1: FULL PARTITION
```text
  ┌──────────────────┐    ╳    ┌──────────────────┐
  │ Scheduler-1      │         │ Scheduler-2      │
  │ Runner-001       │         │ Runner-003       │
  │ Runner-002       │         │ Runner-004       │
  └──────────────────┘         └──────────────────┘
  Two completely isolated islands.
```

TYPE 2: PARTIAL PARTITION
```text
  Scheduler-1 ──────────────► Runner-001 ✅
  Scheduler-1 ──────────────► Runner-002 ✅
  Scheduler-1 ──────╳──────► Runner-003 ❌
  Scheduler-1 ──────╳──────► Runner-004 ❌
```

  Scheduler can reach SOME runners.
  Must decide: assign only to reachable runners?
  Or wait for partition to heal?

TYPE 3: ASYMMETRIC PARTITION
```text
  Runner-001 ──────────────► Scheduler ✅
  Scheduler  ──────╳──────► Runner-001 ❌
```

  Runner can send to Scheduler.
  Scheduler cannot send to Runner.
  Runner appears dead to Scheduler.
  But Runner thinks it's connected!

  Pravah handles this via bidirectional
  gRPC stream — both sides must be healthy.

TYPE 4: FLAPPING PARTITION
  t=0   Connected ✅
  t=5   Partitioned ❌
  t=8   Connected ✅
  t=12  Partitioned ❌
  t=15  Connected ✅

  Network alternates. Worst case.
  Causes cascading election storms.
  Pravah's randomized timeouts help absorb this.
How Pravah responds to partitions:

PRAVAH PARTITION HANDLING

SCENARIO: Network partition between cloud and runner group

t=0:   Runner-001, 002, 003 executing jobs normally
t=30:  Partition occurs — cloud loses contact with runners

CLOUD SIDE (Control Plane):
  t=30:  Last heartbeat received from runners
```text
  t=60:  No heartbeat for 30s → runners marked SUSPECT
  t=90:  No heartbeat for 60s → runners marked DEAD
  t=91:  Scheduler attempts to reassign jobs to other runners
         (if available)
  t=91:  Agent: "Runner group unreachable — alerting on-call"
  t=91:  Notification: PagerDuty alert fired
```

RUNNER SIDE (during partition):
  t=30:  Partition occurs
```text
  t=31:  Runner tries to send heartbeat → connection error
  t=31:  Runner retries with exponential backoff
         1s → 2s → 4s → 8s → 16s → 32s (max)
  t=60:  Runner still executing current job
         (runner works independently once job assigned)
  t=90:  Job completes. Runner tries to send result.
         → Connection still broken
         → Runner stores result locally
         → Retries sending result with backoff
```

PARTITION HEALS at t=120:
  Runner-001: Re-establishes gRPC connection
  Runner-001: Sends stored job result
  Scheduler:  Checks fencing token on result
  Scheduler:  Was job reassigned to another runner?

  CASE A: Job was NOT reassigned (other runners also down):
```text
    → Scheduler accepts result ✅
    → Job marked complete
```

  CASE B: Job WAS reassigned and completed by Runner-004:
```text
    → Job already marked complete in DB
    → Runner-001's result is duplicate
    → Scheduler checks idempotency key
    → Duplicate REJECTED ❌
    → No data duplication ✅
```

### 4️⃣ Message Loss & Duplication

MESSAGES IN DISTRIBUTED SYSTEMS

Messages between services can be:

LOST:
  Sender sends. Receiver never gets it.
  No error. Just silence.
  Sender doesn't know if:
```text
    → Receiver got it and crashed
    → Receiver got it and is processing
    → Message was lost in network
```

DELAYED:
  Message arrives, but 30 seconds late.
  If sender retried, receiver gets BOTH.
  Now receiver has duplicates.

REORDERED:
  Message 1 sent before Message 2.
  Message 2 arrives before Message 1.
  If order matters (job steps), this breaks things.

DUPLICATED:
  Network layer retransmits message.
  Receiver gets same message twice.
```text
  If action is "charge customer" → charged twice!
Delivery guarantees:
```

THREE LEVELS OF DELIVERY GUARANTEE

AT-MOST-ONCE:
  Message sent once. Not retried.
  May be lost. Never duplicated.
  
  Use when: Losing is ok (metrics, non-critical logs)
  Pravah uses for: Runner capability broadcasts

AT-LEAST-ONCE:
  Message retried until acknowledged.
  Never lost. May be duplicated.
  
  Use when: Losing is NOT ok, duplicates handled
  Pravah uses for: Job assignments, pipeline events

  Requires: Idempotent receivers
  (handling the same message twice = same result)

EXACTLY-ONCE:
  Never lost. Never duplicated.
  
  Use when: Correctness critical
  Pravah uses for: Financial audit events,
                   job completion records

  Requires: Idempotency keys + deduplication store
  (We cover this deeply in 1.7)

### 5️⃣ Timing Failures

TIMING FAILURES IN PRAVAH

PERFORMANCE DEGRADATION:
  Runner processing at 10% normal speed.
  Not crashed. Not partitioned.
  Just very slow.

  Looks like: Heartbeats arrive late
  Risk: Scheduler thinks runner is dead
  Pravah response: Heartbeat timeout has
    generous buffer (60s vs 10s heartbeat)

CLOCK SKEW (from 1.3):
  Runner clock 2 minutes behind scheduler.
  SLA "complete by 10:00am" evaluated wrong.
  Pravah uses HLC to avoid this.

THUNDERING HERD:
  1000 pipelines all scheduled at midnight.
  All runners hit simultaneously.
```text
  System overloads → cascading timeouts.
```

  Pravah response:
```text
    → Jitter on cron triggers (±30s random offset)
    → Priority queue for job dispatch
    → Back-pressure from runners signals scheduler
    → Rate limiting per tenant
```

The Scheduler maintains a Failure Detector component.

Properties of a good failure detector:

  Completeness: Every crashed node is eventually suspected
  Accuracy:     Healthy nodes are not falsely suspected

These properties conflict:
```text
  → Faster detection = more false positives
  → Slower detection = slower recovery
```

Pravah uses ADAPTIVE timeouts:

  Normal operation:
    Heartbeat interval: 10s
    Suspect threshold:  30s  (3 missed heartbeats)
    Dead threshold:     60s  (6 missed heartbeats)

  High load detected (queue depth > 80%):
    Suspect threshold:  60s  (runners might be slow)
    Dead threshold:     120s (give more grace time)

  This reduces false positives during peak load.

```text
🎯 FAANG Interview Angles
❓ "A runner goes silent — how does Pravah
    decide if it crashed or is just slow?"
```

Good answer:
  "We use an adaptive failure detector.
   Under normal load: 30s marks SUSPECT,
   60s marks DEAD. Under high load we extend
   these thresholds to avoid false positives —
   a busy runner might miss heartbeats legitimately.
   We never reassign a job until DEAD state to
   prevent dual execution. Fencing tokens ensure
   that even if we're wrong and the runner recovers,
   its stale result gets rejected."

❓ "How does Pravah handle a runner that returns
    corrupted results without crashing?"

Good answer:
  "This is a Byzantine failure. We defend against
   it with SHA-256 checksums on all data artifacts.
   The runner computes and uploads the checksum
   alongside results to MinIO. The Scheduler
   independently verifies the checksum. Mismatch
   triggers: job marked FAILED, runner quarantined,
   on-call alerted, job re-queued to a different
   runner. For ultra-critical pipelines we optionally
   run on two runners and compare results."

❓ "What happens if Pravah's control plane gets
    partitioned into two halves?"

Good answer:
  "Control plane uses Raft via etcd for K8s
   and Redis with quorum for scheduler election.
   In a partition, the minority side cannot get
   quorum for writes — it stops accepting new
   scheduling requests. The majority side continues
   normally. This is a CP choice — we accept
   unavailability over risk of split-brain.
   In-flight jobs on runners continue executing
   independently. Once partition heals, minority
   re-syncs with majority via Raft log replication."

## 📌 Key Takeaways

1. Failures are not binary — there are many types,
   each needing a different response

```text
2. Crash failures → easiest: heartbeat detection,
   fencing tokens, reassignment

3. Byzantine failures → hardest: checksums, mTLS,
   result verification, signed tokens

4. Network partitions → must make CP vs AP choice
   Pravah: CP for control plane, AP for runner status
```

5. Message delivery: at-most-once, at-least-once,
   exactly-once — choose per use case

6. Thundering herd is a real failure mode —
   jitter, backpressure, rate limiting prevent it

7. Good failure detection = balance between
   fast detection and avoiding false positives

8. Adaptive timeouts handle the ambiguity between
   "crashed" and "just slow"
