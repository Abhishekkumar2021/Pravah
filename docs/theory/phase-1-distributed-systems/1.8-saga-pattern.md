# 1.8 Saga Pattern — Orchestration vs Choreography

## 🧩 Why We Need Sagas

First, let's understand what problem sagas solve.

THE DISTRIBUTED TRANSACTION PROBLEM

In a single database, transactions are simple:

```sql
  BEGIN TRANSACTION
    INSERT INTO jobs ...
    UPDATE pipelines SET status = 'running' ...
    INSERT INTO audit_log ...
  COMMIT  ← all succeed
```
  
  OR
  
```sql
  ROLLBACK ← all undone
```
  
  ACID guarantees: Atomic, Consistent, Isolated, Durable

BUT IN PRAVAH — operations span multiple services:

```text
  Step 1: Pipeline Service    → create job record
  Step 2: Secret Service      → fetch credentials
  Step 3: Runner Service      → allocate runner
  Step 4: Billing Service     → reserve compute quota
  Step 5: Execution Service   → dispatch job to runner
  Step 6: Notification Service→ notify stakeholders
```

  Each service has its OWN database.
  No single transaction can span all of them.

  What if Step 4 (Billing) fails?
    Step 1, 2, 3 already completed!
    We have a dangling job record,
    fetched credentials, allocated runner —
    but no billing record.
    System is in INCONSISTENT STATE. 😱
The naive solution — Two-Phase Commit (2PC) — and why we avoid it:

TWO-PHASE COMMIT (2PC) — THE TRAP

PHASE 1: PREPARE
  Coordinator asks all services:
  "Can you commit this transaction?"
  
  Pipeline Service:  "Ready ✅"
  Secret Service:    "Ready ✅"
  Runner Service:    "Ready ✅"
  Billing Service:   "Ready ✅"
  Execution Service: "Ready ✅"

PHASE 2: COMMIT
  Coordinator: "Everyone commit!"
  All services commit atomically.

PROBLEMS WITH 2PC IN PRAVAH:
  
  Problem 1: COORDINATOR CRASH
    Coordinator crashes after Phase 1.
    All services are LOCKED waiting.
    System hangs indefinitely.
    No timeouts. No progress.

  Problem 2: BLOCKING PROTOCOL
    All participants hold locks during 2PC.
    5 services locked = 5x contention.
    Performance collapses under load.

  Problem 3: NETWORK PARTITIONS
    If coordinator can't reach one participant
```text
    during commit → whole transaction blocked.
```

  Problem 4: NOT CLOUD NATIVE
    2PC assumes reliable network and fast nodes.
    Microservices on Kubernetes = neither.

CONCLUSION: 2PC is an anti-pattern for microservices.
            Pravah uses SAGAS instead.
📖 What Is a Saga?
SAGA DEFINITION

A Saga is a sequence of LOCAL transactions,
each in its own service, coordinated so that:

```text
  If ALL steps succeed → overall operation succeeds
  
  If ANY step fails → all PREVIOUS steps are
  COMPENSATED (undone) via compensating transactions
```

KEY INSIGHT:
  Instead of "lock everything, commit atomically"
  Sagas say: "do each step locally, undo if needed"

  No distributed locks.
  No coordinator holding resources.
  Each service is independently available.

SAGA = Forward Steps + Compensating Steps

```text
  Step 1:    Create job record        ←→  Delete job record
  Step 2:    Fetch credentials        ←→  Release credentials
  Step 3:    Allocate runner          ←→  Deallocate runner
  Step 4:    Reserve billing quota    ←→  Release billing quota
  Step 5:    Dispatch job             ←→  Cancel job dispatch
  Step 6:    Notify stakeholders      ←→  Send cancellation notice
⚠️ Sagas vs ACID Transactions
┌──────────────────────────────────────────────────────────────┐
│              ACID vs SAGA COMPARISON                         │
├─────────────────┬──────────────────────┬────────────────────┤
│ Property        │ ACID Transaction      │ Saga               │
├─────────────────┼──────────────────────┼────────────────────┤
│ Atomicity       │ All or nothing        │ Eventual: forward  │
│                 │ (synchronous)         │ or compensate      │
├─────────────────┼──────────────────────┼────────────────────┤
│ Consistency     │ Always consistent     │ Temporarily        │
│                 │                       │ inconsistent       │
│                 │                       │ (eventual)         │
├─────────────────┼──────────────────────┼────────────────────┤
│ Isolation       │ Full isolation        │ NO isolation —     │
│                 │                       │ intermediate       │
│                 │                       │ states visible!    │
├─────────────────┼──────────────────────┼────────────────────┤
│ Durability      │ Committed = permanent │ Each step durable  │
│                 │                       │ individually       │
├─────────────────┼──────────────────────┼────────────────────┤
│ Performance     │ Locks = slow          │ No locks = fast    │
├─────────────────┼──────────────────────┼────────────────────┤
│ Complexity      │ Simple                │ Complex            │
│                 │ (DB handles it)       │ (you handle it)    │
└─────────────────┴──────────────────────┴────────────────────┘
```

CRITICAL: Sagas have NO isolation.
  While saga is running, other services
  can see intermediate state.

  Example: Job record created (Step 1 done)
           But billing failed (Step 4 failed)
           Compensating — job being deleted

  During compensation, other services might
  see the job record briefly.
  
  Solution: Use status flags
  job.status = PROVISIONING (not yet READY)
  Other services ignore PROVISIONING jobs.
🎭 Two Types of Sagas
There are two fundamentally different ways to coordinate a saga:

SAGA COORDINATION APPROACHES

APPROACH 1: CHOREOGRAPHY
  No central coordinator.
  Each service listens to events,
  does its work, emits next event.
  Services react to each other.

APPROACH 2: ORCHESTRATION
  Central coordinator (Saga Orchestrator).
  Tells each service what to do.
  Waits for response.
  Decides next step.

Like a dance:
  Choreography = dancers follow the music,
                 react to each other.
                 No director.

  Orchestration = conductor leads the orchestra.
                  Every musician follows conductor.

CHOREOGRAPHY

PROS:
  ✅ No single point of failure
  ✅ Services fully decoupled
  ✅ Easy to add new steps
     (just subscribe to an event)
  ✅ High throughput (parallel reactions)
  ✅ Simple individual services

CONS:
  ❌ Hard to track overall saga state
     "Where is this job in its lifecycle?"

     → Must query all services

  ❌ Cyclic dependencies hard to prevent
```text

  ❌ Hard to debug
     Trace spans across many Kafka topics
  
  ❌ Testing is complex
     Must simulate all event combinations

     Understanding full flow requires

🎼 Approach 2: Orchestration (Pravah's Choice)

🔧 Compensating Transactions — Design Rules
DESIGNING COMPENSATING TRANSACTIONS
────────────────────────────────────────────────────────────
```

Rule 1: COMPENSATIONS MUST BE IDEMPOTENT
  Compensation might run multiple times (crashes).
  "Deallocate runner-001" run 3 times = safe.

Rule 2: COMPENSATIONS MUST EVENTUALLY SUCCEED
```text
  If compensation fails → retry with backoff.
  Cannot give up — partial saga = corrupted state.
  Use dead letter queue for stuck compensations.
  Alert on-call if compensation stuck > 5 minutes.
```

Rule 3: NOT ALL STEPS NEED COMPENSATION
```text
  Notification sent → cannot un-send.
  Instead: send "cancellation" notification.
  Called PIVOT TRANSACTION — can't truly undo,
  must do inverse action instead.
```

Rule 4: COMPENSATIONS RUN IN REVERSE ORDER
```yaml
  Forward:  Step 1 → 2 → 3 → 4 → 5
  Backward: Comp 4 → Comp 3 → Comp 2 → Comp 1
```

  Why? Step 3 might depend on Step 2's output.
  Compensating Step 2 before Step 3 = inconsistency.

Rule 5: SEMANTIC UNDO, NOT PHYSICAL UNDO
  Forward:  INSERT INTO jobs (id='job-xyz')
  Undo:     DELETE FROM jobs WHERE id='job-xyz'
  
  NOT a database ROLLBACK.
  It's a new forward transaction that undoes.
  This is why it's called "compensating transaction"
  not "rollback."

PRAVAH COMPENSATION TABLE:

Step              Forward                  Compensate
```text
────              ───────                  ──────────
1. Job record     INSERT job (PROVISION)   DELETE job
2. Credentials    Fetch + cache creds      Release creds
3. Runner         Reserve runner capacity  Free runner
4. Billing        Deduct quota             Refund quota
5. Dispatch       Send to runner           Cancel on runner
6. Notification   Send "started" email     Send "cancelled"
🏗️ Pravah's Saga Implementation
SAGA ORCHESTRATOR — IMPLEMENTATION DESIGN
────────────────────────────────────────────────────────────
```

class JobLaunchSaga {

  // FORWARD STEPS
  steps = [
    Step("CREATE_JOB",         pipelineService::createJob),
    Step("FETCH_CREDENTIALS",  secretService::fetchCredentials),
    Step("ALLOCATE_RUNNER",    runnerService::allocateRunner),
    Step("RESERVE_BILLING",    billingService::reserveQuota),
    Step("DISPATCH_JOB",       executionService::dispatchJob),
    Step("NOTIFY",             notificationService::notifyStarted),
  ]

  // COMPENSATING STEPS (reverse order)
  compensations = [
    Comp("CANCEL_NOTIFY",      notificationService::notifyCancelled),
    Comp("CANCEL_DISPATCH",    executionService::cancelJob),
    Comp("RELEASE_BILLING",    billingService::releaseQuota),
    Comp("DEALLOCATE_RUNNER",  runnerService::deallocateRunner),
    Comp("RELEASE_CREDENTIALS",secretService::releaseCredentials),
    Comp("DELETE_JOB",         pipelineService::deleteJob),
  ]

  execute(sagaContext):
    FOR each step IN steps:
      TRY:
        result = step.execute(sagaContext)
        sagaContext.addResult(result)
        persistState(step.name, sagaContext) // crash safe
      CATCH failure:
        compensate(sagaContext, completedSteps)
        THROW SagaFailedException

  compensate(sagaContext, completedSteps):
    FOR each comp IN reverse(completedSteps):
      RETRY_WITH_BACKOFF:
        comp.execute(sagaContext)
        persistCompensationState(comp.name)
}

  │ saga_id  │ current_step │ state      │ context_json  │
  ├──────────┼──────────────┼────────────┼───────────────┤
  │ saga-001 │ RESERVE_BILL │ EXECUTING  │ {job-xyz,     │

🎯 FAANG Interview Angles
❓ "How does Pravah handle a failure halfway
    through launching a pipeline job across
    multiple services?"

Good answer:
  "We use the Saga pattern with orchestration.
   The Job Launch Saga has 6 steps across Pipeline,
   Secret, Runner, Billing, Execution, and
   Notification services. The orchestrator persists
   its state to PostgreSQL after each step.
   
   If Step 4 (Billing) fails, the orchestrator
   triggers compensating transactions in reverse:
   deallocate runner, release credentials, delete
   job record. Each compensation is idempotent and
   retried until success.
   
   If the orchestrator itself crashes mid-saga,
   it resumes from the last persisted state on
   restart — no step is lost or double-executed."

❓ "Why did you choose orchestration over
    choreography for Pravah's sagas?"

Good answer:
  "For complex, critical flows like job launch
```sql
   with compensation logic, orchestration wins.
   It gives us a single, queryable source of
   saga state — crucial for debugging and monitoring.
   We can ask 'where is saga-001?' and get
   a direct answer instead of correlating events
   across six Kafka topics.
```
   
   We do use choreography for simpler fan-out
   patterns like data lineage tracking and
   notifications, where no compensation is needed
   and services truly are independent."

❓ "What's the difference between a saga's
    compensating transaction and a database rollback?"

Good answer:
  "A database rollback undoes changes at the
   storage level — it's a physical undo within
   one transaction boundary. A compensating
   transaction is a new forward transaction
   that semantically reverses a previous action.
   
   For example, if Step 3 reserved a runner,
   the compensation doesn't rollback Step 3's
   database write — it calls Runner Service with
   a new 'deallocate' request. This works across
```protobuf
   service boundaries, is durable, and is
   idempotent — unlike a database rollback
   which can't cross service boundaries."
```

## 📌 Key Takeaways

1. Distributed transactions across services
   cannot use 2PC — too fragile, too slow

2. Sagas replace 2PC with local transactions
   + compensating transactions

3. Two coordination styles:
```text
   Choreography → event-driven, decoupled
   Orchestration → central coordinator, clear state
```

4. Orchestration is better for:
   Complex flows, compensation logic,
   observability requirements

5. Choreography is better for:
   Simple fan-out, notifications,
   truly independent services

6. Compensating transactions are:
   Idempotent, run in reverse, always eventually succeed
   Semantic undo — not database rollback

7. Saga orchestrator state persisted to DB
   = crash safe, resumable, exactly-once
