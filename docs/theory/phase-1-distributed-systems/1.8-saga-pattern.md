# 1.8 Saga Pattern — Orchestration vs Choreography

## The Distributed Transaction Problem

In a single database, transactions are simple: `BEGIN`, do work, `COMMIT` or `ROLLBACK`. ACID gives you atomicity for free.

In Pravah, launching a pipeline job spans multiple services, each with its own database:

```
Step 1: Pipeline Service    → create job record
Step 2: Secret Service      → fetch credentials
Step 3: Runner Service      → allocate a runner
Step 4: Billing Service     → reserve compute quota
Step 5: Execution Service   → dispatch job to runner
Step 6: Notification Service→ notify stakeholders
```

If Step 4 (Billing) fails, Steps 1–3 already completed. We have a dangling job record, fetched credentials, and an allocated runner — but no billing record. The system is in an inconsistent state.

**Why not Two-Phase Commit (2PC)?** 2PC is a common instinct here, but it is an anti-pattern for microservices:

- If the coordinator crashes between phases, all participants hold locks and wait indefinitely
- All participants hold database locks during the protocol — catastrophic for throughput
- A network partition to any one participant blocks the entire transaction
- 2PC assumes reliable, fast network and nodes — the opposite of cloud-native services

---

## What Is a Saga?

A Saga is a sequence of **local transactions**, each within its own service, coordinated so that:
- If all steps succeed → the overall operation succeeds
- If any step fails → all previously completed steps are **compensated** (reversed) via compensating transactions

No distributed locks. No coordinator holding resources. Each service remains independently available.

Every forward step has a corresponding compensating step:

| Step | Forward Action | Compensating Action |
|---|---|---|
| 1 | Create job record | Delete job record |
| 2 | Fetch credentials | Release credentials |
| 3 | Allocate runner | Deallocate runner |
| 4 | Reserve billing quota | Release billing quota |
| 5 | Dispatch job | Cancel job dispatch |
| 6 | Notify stakeholders | Send cancellation notice |

**Sagas vs ACID:**

| Property | ACID Transaction | Saga |
|---|---|---|
| Atomicity | All or nothing (synchronous) | Eventual: forward or compensate |
| Consistency | Always consistent | Temporarily inconsistent (eventual) |
| Isolation | Full — other transactions see nothing until commit | **None** — intermediate states are visible |
| Durability | Committed = permanent | Each step is durable independently |
| Performance | Locks = slow | No locks = fast |

The loss of isolation is the key trade-off. While a saga runs, other services can see intermediate state. Pravah handles this with status flags: a job created in Step 1 has `status=PROVISIONING`, not `READY`. Other services ignore `PROVISIONING` records.

## Two Approaches to Saga Coordination

### Choreography — Event-Driven

Services communicate exclusively via Kafka events. No service calls another directly.

**Happy path:**

```
User triggers Pipeline-abc
        │
        ▼
Pipeline Service
  Creates job record (status: PROVISIONING)
  Publishes: job.provisioning.started
        │
        ▼ (Kafka)
Secret Service listens to job.provisioning.started
  Fetches pipeline credentials
  Publishes: job.credentials.ready
        │
        ▼ (Kafka)
Runner Service listens to job.credentials.ready
  Reserves runner capacity
  Publishes: job.runner.allocated
        │
        ▼ (Kafka)
Billing Service listens to job.runner.allocated
  Reserves compute quota
  Publishes: job.billing.reserved
        │
        ▼ (Kafka)
Execution Service dispatches job to runner
  Publishes: job.dispatched
        │
        ▼
Notification Service notifies stakeholders ✅
```

**Failure path — Billing fails:**

```
... runner allocated ...
        │
        ▼ (Kafka)
Billing Service: QUOTA EXCEEDED → publishes: job.billing.FAILED
        │
        ├──► Runner Service:   deallocate runner     (COMPENSATE)
        │                      publishes: job.runner.DEALLOCATED
        │
        ├──► Secret Service:   release credentials   (COMPENSATE)
        │
        └──► Pipeline Service: delete job record     (COMPENSATE)
                               notify user: "Quota exceeded"
```

**Choreography pros and cons:**

| Pros | Cons |
|---|---|
| No single point of failure | Hard to track overall saga state |
| Services fully decoupled | Cyclic dependencies hard to prevent |
| Easy to add new steps (subscribe to an event) | Scattered business logic across all service codebases |
| High throughput via parallel reactions | Complex to test — must simulate all event combinations |

---

### Orchestration — Pravah's Primary Choice

A central Saga Orchestrator manages the entire flow. It calls each service in sequence, waits for the response, and decides the next step.

**Happy path:**

```
User triggers Pipeline-abc
        │
        ▼
Job Launch Saga Orchestrator (in Execution Service)
        │
        ├─1─► Pipeline Service::createJob
        │     ← SUCCESS
        │
        ├─2─► Secret Service::fetchCredentials
        │     ← SUCCESS
        │
        ├─3─► Runner Service::allocateRunner
        │     ← SUCCESS (runner-001)
        │
        ├─4─► Billing Service::reserveQuota
        │     ← QUOTA EXCEEDED ❌
        │
        │  FAILURE — begin compensation in reverse
        │
        ├─3C─► Runner Service::deallocateRunner(runner-001) ✅
        ├─2C─► Secret Service::releaseCredentials           ✅
        └─1C─► Pipeline Service::deleteJob                  ✅

User notified: "Quota exceeded" ✅
```

The orchestrator persists its current step and context to PostgreSQL after every action. If it crashes mid-saga, it resumes from the last persisted state on restart — no step is lost or duplicated.

**Orchestration pros and cons:**

| Pros | Cons |
|---|---|
| Single queryable source of saga state | Orchestrator is a central component (mitigated by HA) |
| Easy to debug and monitor | Services know about the orchestrator (slight coupling) |
| Business logic centralized and readable | Can become a bottleneck (mitigated by per-saga-type pools) |
| Easy to add per-step timeouts | |
| Straightforward to unit-test | |

---

## When to Use Which Approach

| Saga Type | Approach | Reason |
|---|---|---|
| Job launch (6 steps, compensation) | Orchestration | Complex flow, must track state clearly |
| Runner registration (4 steps) | Orchestration | Sequential dependencies |
| Pipeline notifications (fan-out) | Choreography | Simple, no compensation needed |
| Data lineage tracking (many consumers) | Choreography | Async, truly independent subscribers |
| Tenant provisioning (billing, RBAC, storage) | Orchestration | Complex, business-critical path |

**Rule of thumb:** complex flow with compensation logic → Orchestration. Simple fan-out to independent services → Choreography.

## Designing Compensating Transactions

**Rule 1 — Compensations must be idempotent.** The orchestrator may crash and retry a compensation multiple times. "Deallocate runner-001" run three times must produce the same result as running it once.

**Rule 2 — Compensations must eventually succeed.** A partial saga is corrupted state. If a compensation fails, retry with exponential backoff. Use a Dead Letter Queue for permanently stuck compensations. Alert on-call if a compensation is stuck for more than 5 minutes.

**Rule 3 — Not all steps can be truly reversed.** A notification sent cannot be un-sent. Instead, send a "cancellation" notification — a **pivot transaction** that semantically reverses the effect rather than physically undoing it.

**Rule 4 — Compensations run in reverse order.** If Step 3 depended on the output of Step 2, compensating Step 2 before Step 3 breaks consistency. Always reverse the order.

**Rule 5 — Compensation is semantic, not physical.** The compensation for `INSERT INTO jobs` is `DELETE FROM jobs WHERE id='job-xyz'` — a new forward transaction, not a database `ROLLBACK`. This is why it is called a *compensating transaction*, not a rollback.

## Orchestrator Implementation

```java
class JobLaunchSaga {

  List<Step> steps = List.of(
    new Step("CREATE_JOB",        pipelineService::createJob),
    new Step("FETCH_CREDENTIALS", secretService::fetchCredentials),
    new Step("ALLOCATE_RUNNER",   runnerService::allocateRunner),
    new Step("RESERVE_BILLING",   billingService::reserveQuota),
    new Step("DISPATCH_JOB",      executionService::dispatchJob),
    new Step("NOTIFY",            notificationService::notifyStarted)
  );

  List<Compensation> compensations = List.of(
    new Compensation("CANCEL_NOTIFY",       notificationService::notifyCancelled),
    new Compensation("CANCEL_DISPATCH",     executionService::cancelJob),
    new Compensation("RELEASE_BILLING",     billingService::releaseQuota),
    new Compensation("DEALLOCATE_RUNNER",   runnerService::deallocateRunner),
    new Compensation("RELEASE_CREDENTIALS", secretService::releaseCredentials),
    new Compensation("DELETE_JOB",          pipelineService::deleteJob)
  );

  void execute(SagaContext ctx) {
    List<Step> completed = new ArrayList<>();
    for (Step step : steps) {
      try {
        step.execute(ctx);
        completed.add(step);
        persistState(step.name(), ctx); // crash-safe checkpoint
      } catch (Exception e) {
        compensate(ctx, completed);
        throw new SagaFailedException(e);
      }
    }
  }

  void compensate(SagaContext ctx, List<Step> completed) {
    for (Step step : reverse(completed)) {
      retryWithBackoff(() -> {
        step.compensation().execute(ctx);
        persistCompensationState(step.name());
      });
    }
  }
}
```

Saga state in PostgreSQL:

```
┌───────────┬──────────────────┬────────────┬────────────────────────────┐
│ saga_id   │ current_step     │ state      │ context_json               │
├───────────┼──────────────────┼────────────┼────────────────────────────┤
│ saga-001  │ RESERVE_BILLING  │ EXECUTING  │ {job: job-xyz,             │
│           │                  │            │  runner: runner-001,       │
│           │                  │            │  creds_ref: vault://...}   │
└───────────┴──────────────────┴────────────┴────────────────────────────┘
```

On crash and restart: load saga state, resume from `current_step`, execute with the same idempotency key → exactly-once execution of remaining steps.

## System Design Interview Angles

**"How does Pravah handle a failure halfway through launching a pipeline job?"**

> The Job Launch Saga has 6 steps across Pipeline, Secret, Runner, Billing, Execution, and Notification services. The orchestrator persists its state to PostgreSQL after each step. If Step 4 (Billing) fails, the orchestrator triggers compensating transactions in reverse: deallocate runner, release credentials, delete job record — each idempotent and retried until success. If the orchestrator itself crashes mid-saga, it resumes from the last persisted state on restart.

**"Why did you choose orchestration over choreography for Pravah's sagas?"**

> For complex, critical flows with compensation logic, orchestration wins. It gives us a single, queryable source of saga state — we can ask "where is saga-001?" and get a direct answer instead of correlating events across six Kafka topics. We do use choreography for simpler fan-out patterns like lineage tracking and notifications where no compensation is needed.

**"What's the difference between a compensating transaction and a database rollback?"**

> A database rollback undoes changes at the storage level within one transaction boundary. A compensating transaction is a new forward transaction that semantically reverses a previous action — for example, calling Runner Service with a "deallocate" request. This works across service boundaries, is durable, and is idempotent. A database rollback cannot cross service boundaries.

---

## 📌 Key Takeaways

1. Distributed transactions across services cannot use 2PC — it is fragile, slow, and blocks indefinitely on coordinator crash
2. Sagas replace 2PC with local transactions + compensating transactions — no distributed locks
3. **Choreography** — event-driven, decoupled, good for simple fan-out; **Orchestration** — central coordinator, clear state, good for complex flows
4. Compensating transactions are: idempotent, run in reverse order, always eventually succeed, and are semantic (not database rollback)
5. Saga orchestrator state persisted to DB = crash-safe, resumable, exactly-once
